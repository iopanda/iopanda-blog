          吞吐、延迟、可观测性与工程边界

          vLLM 的价值如果只停在“快”，其实还不够。真正进生产后，你会问的是：TTFT 怎么看、tokens/s 怎么看、P99 怎么看、调度是否健康、speculative decoding 有没有副作用、缓存命中是否在工作。metrics 文档和 benchmark/recipes 文档都说明，vLLM 已经把这些问题当成正式运行时问题，而不只是 benchmark 口号。[13][16]

          学习目标：学完本章，你将能够——

          1. 理解为什么 serving 的核心不是单个 benchmark，而是长期运行指标；
          2. 说出吞吐、延迟、请求调度、spec decode、MFU 指标分别在看什么；
          3. 判断什么时候应该做 scheduler tuning，而不是只换模型；
          4. 认识 vLLM 的生产边界：安全、部署、异构硬件、流量形态；
          5. 为服务写一张 observability card。

          1. serving 的正确目标不是“最快一次”，而是“稳态最优”

          生产环境里你更关心：

          • 并发起来后能否稳定；
          • TTFT 是否恶化；
          • P99 是否失控；
          • 调度是否在特定 workload 下退化。

          所以 vLLM 的 metrics 和 runtime tuning，实际上是在帮你从“单次快”转向“稳态快”。[16]

          2. /metrics 为什么重要

          metrics 文档明确说，vLLM 通过 /metrics 暴露生产指标。[16] 这说明它不是一个只能靠外部猜测健康度的黑箱，而是明确把 observability 作为产品面的一部分。

          3. 为什么 scheduler tuning 是正式工作流

          tools/recipes 文档里甚至把 scheduler 参数、QPS、TTFT/TPOT 目标和 benchmark-backed recommendation 写成正式流程。[13]

          这说明 serving 优化不是：

          • 盲调几个参数； 而是：
          • 根据 workload 形状、并发、token 长度和 SLA 去推 scheduler 预算。

          4. 工程边界：快不等于完整

          vLLM 很强，但也有清晰边界：

          • 安全通常要靠反向代理和外部边界收口；[14]
          • 多节点和分布式推理会显著提高运维复杂度；
          • disaggregated prefill/decode、LoRA、多模型共存会放大调度与观测难度；
          • 某些情况下，你也许更需要 Triton 这类平台层来统一多模型运营。

          5. 动手活动

          动手活动：输出

          vllm-observability-card.md

          为你的服务列 5 个指标：TTFT、TPOT、throughput、cache hit、P99。再写一句结论：你的 serving 风险更像算力不够、调度不稳，还是观测不足。

          6. 总结

          关键问题 一句话
          生产里真正该看什么 稳态 throughput 和 tail latency，而不是单次峰值
          /metrics 的价值 让 serving 健康度进入正式监控面
          scheduler tuning 的意义 让系统按 workload 形状而不是想象来配置
          最大边界 vLLM 是强引擎，但平台治理和安全仍需额外设计
