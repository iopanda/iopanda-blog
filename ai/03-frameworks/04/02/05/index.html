          性能优化、部署方式与工程边界

          SGLang README 几乎把所有性能词都摆上来了：RadixAttention、zero-overhead CPU scheduler、speculative decoding、continuous batching、paged attention、chunked prefill、多种 parallelism、多硬件支持。[7] 再加上 monitoring README、router / gateway 文档，可以看出它不仅想快，而且想把大规模 serving 的运行边界一起纳入体系。[9][10][11]

          学习目标：学完本章，你将能够——

          1. 理解为什么 SGLang 的性能主语不仅是 tokens/s；
          2. 说出 prefix cache、router policy、PD serving、monitoring 分别在服务哪类目标；
          3. 理解它的部署形态为什么明显比简单单机 server 更复杂；
          4. 判断什么时候该用它，什么时候 complexity 过高；
          5. 为系统写一张 serving-boundary card。

          1. 性能在这里是“系统性能”，不是单核 benchmark

          SGLang 关心的不只是 decode kernel 多快，还包括：

          • 前处理和后处理是否会拖慢整体链路；
          • 路由是否 cache-aware；
          • 推理和控制逻辑是否在同一条高性能路径中；
          • 多 worker、多模型、多阶段是否还能保持低开销。

          所以它在做的是 runtime-level performance，不只是 kernel-level performance。

          2. monitoring 为什么是正式能力

          examples/monitoring README 说明它有 Prometheus + Grafana 监控模板，并要求 server 显式开启 metrics。[9]

          这说明 SGLang 不是把 observability 当后补件，而是承认：

          • agentic serving 没有监控就不可运营；
          • 高吞吐、多阶段、结构化推理，没有指标很难排障。

          3. 部署复杂度从哪里来

          复杂度主要来自几个地方：

          • HTTP / gRPC 双栈；
          • router / gateway 分层；
          • PD 拓扑；
          • per-model policy；
          • tool / reasoning / storage / MCP 进入控制面；
          • 硬件和并行策略范围很广。[10][11]

          所以它适合复杂系统，但也不该被误用成“最简单上手的本地 server”。

          4. 工程边界

          SGLang 很强，但它的边界也很明确：

          • 如果你只是单模型简单 chat API，vLLM 可能更直接；
          • 如果你只是本地离线应用，llama.cpp 更自然；
          • 如果你主要追求通用多模型平台治理，Triton 可能更正交。

          5. 动手活动

          动手活动：输出

          sglang-serving-boundary.md

          列你的系统是否需要：router、gRPC、PD serving、metrics、tool parser、conversation storage。写一句结论：这些能力是必要复杂度，还是过度设计。

          6. 总结

          关键问题 一句话
          SGLang 的性能主语是什么 整个 runtime 和控制面的系统性能
          monitoring 为什么重要 没有可观测性，复杂 serving 不可运营
          最大边界 功能强，但复杂度也更高
          正确使用方式 在确实需要 structured/agentic serving 时再上强 runtime
