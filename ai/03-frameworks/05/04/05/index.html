          团队协作、基线管理与工程边界

          promptfoo 虽然不是典型 observability 平台，但它同样不是“一个人本地跑跑就完”的工具。README 和 CLI 文档都明显在强调 view、share、export、retry、logs、datasets、tags、outputs 这些能力。[10][11] 这说明它的 testing workflow 也是面向团队协作、基线比较和工程落地的。

          学习目标：学完本章，你将能够——

          1. 理解为什么 promptfoo 的团队价值不只在本地 eval；
          2. 说出 share、view、export、retry、logs、tags 为什么都是工程能力；
          3. 理解它的边界：它不是完整产品 observability 平台；
          4. 判断什么时候它足够，什么时候还需要 Langfuse/Phoenix/MLflow 配合；
          5. 为团队写一张 eval-collaboration card。

          1. 基线管理为什么重要

          如果没有稳定基线，团队很快会陷入：

          • 这次改动到底有没有更好；
          • 哪个结果是最新可信结果；
          • 哪些失败是临时错误，哪些是真回归。

          promptfoo 的 retry、share、export、list/show 等能力，本质上都在支撑“可比较的 eval 资产”。[11]

          2. 团队协作在这里意味着什么

          团队协作不只是多人看同一报表，而是：

          • 能共享 eval；
          • 能过滤失败案例；
          • 能重跑错误结果；
          • 能保留 output formats 用于审计或 PR 附件；
          • 能把 logs 拉出来查具体失败路径。

          3. 它的边界在哪里

          promptfoo 很强，但它不是完整线上观测平台：

          • 如果你要 trace-first diagnosis，Phoenix 更自然；
          • 如果你要产品化 feedback + prompt + traces 平台，Langfuse 更自然；
          • 如果你要统一传统 ML 与 GenAI 治理，MLflow 更广。

          所以 promptfoo 更适合作为 quality/security gate，而不是整个平台替代者。

          4. 动手活动

          输出

          promptfoo-collaboration-card.md

          列你的团队是否需要：shareable eval、retry failed cases、logs、导出报告、CI gate。写一句结论：你的主复杂度是测试门禁，还是线上 observability，还是两者断裂。

          5. 总结

          关键问题 一句话
          promptfoo 的团队价值是什么 让 eval 结果可共享、可重跑、可比较、可审计
          retry / export / logs 为什么重要 它们让 eval 从一次性运行变成工程资产
          最大边界 它不是完整 observability 平台
          正确位置 作为团队 regression / red-team / gate 工具，与平台类工具互补
