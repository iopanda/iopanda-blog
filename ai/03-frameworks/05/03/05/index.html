          线上监控、权限、成本与工程边界

          MLflow README 现在已经明确把 observability、evaluation、AI Gateway、prompt management、cost control 放进同一产品面。[31] 再加上 TypeScript SDK 和本地 docker-compose stack 的说明，可以看出它不仅在做实验记录，也在往 production governance 走。[32][35] 这意味着它的边界问题已经不只是“能不能追踪”，而是“能不能长期治理和运营”。

          学习目标：学完本章，你将能够——

          1. 理解为什么 MLflow 的重点之一是长期治理，而不是单次诊断；
          2. 说出 traces、feedback、eval、gateway、artifact store 在生产里如何互相关联；
          3. 理解成本、权限、追踪、部署为什么会在同一平台里交叉；
          4. 判断什么时候需要 MLflow 这类平台，什么时候它可能偏重；
          5. 为系统写一张 governance-ops card。

          1. 线上监控在 MLflow 里不只是 trace UI

          README 明确把 monitor、costs、model access 管理都放进平台叙事。[31] 这说明在 MLflow 视角里，生产问题不只是“这次 trace 哪里错了”，还包括：

          • 服务是否在稳态运行；
          • 成本是否可见；
          • 权限和访问是否可控；
          • traces 是否能回到后续治理动作。

          2. feedback 和 eval 为什么会连到运营问题

          TypeScript SDK 里已经把 trace feedback、assessment、severity level 这些对象直接做成可记录实体。[32] 这说明线上反馈不是旁路数据，而是平台内正式信号。

          3. artifact / metadata stack 为什么重要

          docker-compose README 清楚说明本地 stack 至少由：

          • Tracking Server
          • PostgreSQL metadata
          • S3-compatible artifact storage 组成。[35]

          这说明 MLflow 的平台主语天然不是“只看前端 UI”，而是后端 metadata 与 artifacts 的长期运营。

          4. 工程边界

          MLflow 很强，但也不是所有团队都该默认选它：

          • 如果你只想做 LLM-native trace/debug，Langfuse 或 Phoenix 可能更直接；
          • 如果你只要 CI regression，promptfoo 更轻；
          • 如果你只要 code-first eval，DeepEval 更直接。

          MLflow 更适合已经进入组织治理问题的团队。

          5. 动手活动

          输出

          mlflow-governance-ops-card.md

          列你的系统是否需要：tracking server、artifact store、trace feedback、prompt registry、gateway、access control。写一句结论：你的主复杂度是诊断、测试，还是平台治理和运营。

          6. 总结

          关键问题 一句话
          MLflow 的运营主语是什么 追踪、评估、工件、访问和成本的长期治理
          feedback 为什么重要 它把线上信号纳入平台正式对象
          artifact / metadata 为什么重要 平台治理必须有持久化、审计和复用能力
          最大边界 对轻量 LLM-only 团队可能偏重
