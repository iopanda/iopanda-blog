          观测、部署与工程边界

          Prefect 的价值不只是“装饰器好用”，它同时提供了一整套观测与部署面：自托管 server 或 Prefect Cloud 两种选择、SQLite/PostgreSQL 两种存储、push/hybrid 两类 work pool。[19][20][24] 这一篇把这些运营与部署细节讲清楚，并说明 Prefect 相对 Temporal/Airflow 的工程边界在哪里。

          学习目标：学完本章，你将能够——

          1. 理解自托管 Prefect server 与 Prefect Cloud 的关系与差异；
          2. 说出数据库选型（SQLite vs PostgreSQL）背后的权衡；
          3. 理解 push work pool 与 hybrid/pull work pool 为什么都存在；
          4. 理解它的工程边界：什么时候 Prefect 不是最佳答案；
          5. 为系统写一张 prefect-ops-boundary card。

          1. 自托管 server 与 Prefect Cloud 共享同一套核心能力

          Prefect 文档说得很直接：「Prefect Cloud and self-hosted Prefect server share a common set of capabilities」。[24] 启动一个自托管 server 会自动跑数据库迁移（用 Alembic 管理 schema），数据库负责记录 flow/task run 状态、运行历史、日志、deployments、并发限制、变量、artifacts、work pool 状态、events 和 automations。[24]

          数据库有两种选择：

          • SQLite：默认选项，「Recommended for lightweight, single-server deployments」，几乎零配置；[24]
          • PostgreSQL：「Best for production use, high availability, and multi-server deployments」，要求 PostgreSQL 14.9 以上并启用 pg_trgm 扩展。[24]

          本地默认可以在 http://localhost:4200 打开 UI 查看运行状态[13]，这与 Airflow 强调多视图运营 UI 的思路是一致的方向，只是 Prefect 的默认门槛更低。

          2. Prefect Cloud 多出来的是组织级能力，不是核心编排能力

          自托管和 Cloud 的核心编排功能是共享的，Cloud 额外提供的是组织治理能力：「Prefect Cloud provides the additional features required by organizations such as RBAC」，以及审计日志（Audit logs）和单点登录（SSO）。[24] 换句话说，选不选 Cloud，回答的是“需不需要企业级治理”，而不是“流程本身能不能跑”。

          一个容易被忽略的版本兼容细节：「Old clients are compatible with new servers, but new clients can be incompatible with old servers」，原因是 REST API 会持续新增字段，不匹配时通常表现为 422 状态码。[24] 这意味着自托管团队升级 client 前，要先确认 server 版本是否跟上。

          3. work pool 的 push/hybrid 分层，本质是在解耦“定义”和“执行”

          work pool 的比喻很形象：「Work pools are like pub/sub topics」——它把“flow 在哪里被定义”和“flow 实际跑在哪里”解耦开。[20] 具体分两类：

          • hybrid/pull：需要你自己运行 worker，worker 轮询 work pool 并把任务提交到你的基础设施；[19][20]
          • push/managed：不需要 worker，Prefect 直接把运行请求发到你配置好的 serverless 基础设施（如 Cloud Run push、ECS push）或 Prefect 托管的基础设施。[19][20]

          这层解耦的好处是：同一个 flow 代码，换一个 work pool 就能从本地调试切换到生产环境，接口对用户始终一致，即使底层执行机制（worker 轮询 vs 直接推送）完全不同。[20]

          4. 工程边界在哪里

          Prefect 很适合“脚本升级成生产工作流”，但它也有明显边界：

          • 如果流程本质上是长生命周期、跨审批、跨外部事件的 stateful business workflow，Temporal 的 durable execution 语义更正式、更彻底；
          • 如果主要问题是大量稳定 batch DAG 的定时调度和统一运营，Airflow 的成熟度和 ops UI 更完整；
          • 如果核心诉求是数据资产的血缘与治理，Dagster 的 asset-first 模型更自然。

          5. 正确位置

          Prefect 最自然的位置通常是：

          • Python 团队希望脚本原地升级为生产工作流；
          • 需要灵活切换本地/容器/K8s/serverless 执行环境；
          • 需要事件驱动的告警和自动化响应，但还不需要企业级 durable execution 或资产治理这类重语义。

          6. 动手活动

          输出

          prefect-ops-boundary-card.md

          列你的系统是否需要自托管还是 Cloud、SQLite 还是 PostgreSQL、push 还是 hybrid work pool。写一句结论：你的主问题是“把脚本变成能观测、能调度的生产工作流”，还是已经需要 durable state recovery 或资产治理这类更重的语义。

          7. 总结

          关键问题 一句话
          自托管与 Cloud 的关系 核心编排能力共享，Cloud 多的是 RBAC/审计/SSO 这类组织治理能力
          数据库怎么选 SQLite 轻量单机，PostgreSQL 面向生产与高可用
          work pool 分层的价值 解耦“flow 定义在哪”和“flow 跑在哪”，push/hybrid 各自适配不同基础设施
          最大边界 不以 durable execution 或 asset lineage 为第一主语
