          五个框架横向矩阵

          这一篇把上一篇的五个诊断维度，逐一对齐到 Temporal、Airflow、Prefect、Dagster、Kestra 五个框架，形成一张可以直接拿来对照的横向矩阵。所有判断都来自前五个子目录已经建立的事实，这里只做收敛，不引入新的定性判断。

          学习目标：学完本章，你将能够——

          1. 一眼看出五个框架在五个维度上的强弱分布；
          2. 理解“强/中/弱”背后各自对应哪个具体机制；
          3. 用“反向信号”快速排除不对症的框架；
          4. 判断两个框架看起来都“中等适合”时，该看哪个次要维度做区分；
          5. 把矩阵直接套进 workflow-framework-selection-card。

          1. 主矩阵：五维度 × 五框架

          维度 Temporal Airflow Prefect Dagster Kestra
          状态恢复 强——history/mutable state、retry/timer/signal 都是正式语义[11] 弱——靠幂等 task + backfill 补历史，不是状态机恢复[12] 中——retries/retry_condition_fn 正式化，但不是彻底的状态恢复引擎[13] 弱——不以流程状态恢复为设计中心[14] 中——Pause/HumanTask 让审批状态可持久化，但不是通用状态机语义[15]
          调度模型 弱——不是调度平台，靠 schedule/timer 辅助长流程[11] 强——DAG scheduling、backfill、schedule interval 是核心心智[12] 中——deployment + work pool 支持调度，但非重心[13] 中——schedule + sensor + partition 组合，服务于资产更新[14] 强——schedule 与事件触发被统一在同一套 trigger 接口下[15]
          lineage/治理 弱——不建模数据资产[11] 弱——任务图不等于数据资产血缘[12] 弱——同样不以资产血缘为中心[13] 强——AssetKey、column lineage、asset check、owners 都是一等对象[14] 弱——不以资产建模为核心[15]
          事件触发 中——signal/schedule 支持外部事件，但语义偏“等待”而非“广泛集成”[11] 弱——以定时批处理为主，事件驱动不是设计中心[12] 中——automations/events 支持告警和响应，但覆盖面不追求“统一接口”[13] 中——sensor 支持事件驱动的资产触发，服务于资产更新[14] 强——webhook/polling/realtime 三类事件 trigger + 插件生态[15]
          开发者体验 中——需要接受 durable execution 的心智成本[11] 中——成熟但偏重，运维负担大[12] 强——装饰器直接包裹已有 Python 函数，门槛最低[13] 中——需要先做资产建模，前期投入较高[14] 强——声明式 YAML + 无代码/AI Copilot，覆盖工程师和业务方[15]

          2. 怎么读这张矩阵

          • 看“强”的维度，而不是数格子数量：每个框架大概只在 1-2 个维度上是“强”，这才是它的真正定位，其余维度是“够用”而不是“最优”。
          • “中”不代表平庸，代表“可以用，但不是它的设计中心”：比如 Prefect 的调度能力是“中”，不是说它调度功能差，而是调度不是它要解决的第一性问题。
          • 两个框架都“中”时，回头看上一篇的方法论：先确认主矛盾到底是哪个维度，再看谁在那个维度上更接近“强”。

          3. 反向信号：快速排除不对症的框架

          如果你的系统… 优先排除
          主要是稳定的定时批处理，不需要状态恢复或资产血缘 Temporal、Dagster（先看 Airflow/Prefect/Kestra）
          核心诉求是数据资产的血缘和新鲜度治理 Kestra、Temporal（先看 Dagster）
          需要长时间等待人工审批、跨天补偿的业务流程 Airflow、Dagster（先看 Temporal）
          团队只想让已有 Python 脚本更可靠，不需要跨语言/多角色协作 Kestra、Dagster（先看 Prefect）
          需要工程师和非工程角色共同维护，且要统一调度与事件驱动 Temporal、Dagster（先看 Kestra）

          4. 一个容易被忽略的共性

          五个框架都支持“调度”和“重试”这两个基础能力——这恰恰说明这两项从来不是真正的选型分歧点。真正的分歧点永远落在“状态恢复的彻底程度”“任务图 vs 资产图”“血缘治理”“事件覆盖面”“开发者体验的取舍”这五个更深层的设计中心上。

          5. 动手活动

          动手活动：更新

          workflow-framework-selection-card.md

          把第 01 篇里给自己系统打的分，对照这张矩阵找出最接近的 1-2 个框架。用第 3 节的反向信号表再交叉验证一次：有没有哪个候选框架其实该被排除。

          6. 总结

          关键问题 一句话
          矩阵怎么用 找每个框架真正“强”的 1-2 个维度，而不是数格子
          “中”是什么意思 可以用，但不是设计中心
          反向信号的价值 排除法比正向比较更快、更可靠
          共性说明了什么 调度和重试不是分歧点，状态恢复/血缘/事件覆盖面/开发者体验才是
