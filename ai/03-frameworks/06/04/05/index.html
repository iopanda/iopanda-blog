          资产治理、可观测性与工程边界

          Dagster README 把自己的第三个关键特性描述成「unified control plane」——「Centralize your metadata in one tool with built-in observability, diagnostics, cataloging, and lineage」。[14] 这一篇讲清楚这句话具体落在哪些机制上：asset checks 怎么做数据质量门禁，metadata/tags 怎么撑起血缘与目录，以及 Dagster 相对其他编排框架的工程边界在哪。

          学习目标：学完本章，你将能够——

          1. 理解 asset check 如何把数据质量变成正式的、可阻断的门禁；
          2. 说出 owners、tags、metadata、column lineage 分别在治理里扮演什么角色；
          3. 理解资产目录（catalog）为什么是 Dagster 可观测性的核心载体；
          4. 理解它的工程边界：什么时候 asset-first 建模是过度投入；
          5. 为系统写一张 dagster-governance-boundary card。

          1. asset check：把数据质量变成正式的、可阻断的门禁

          asset check 是「tests that verify specific properties of your data assets, allowing you to execute data quality checks on your data」。[31] 典型场景包括「Ensure a particular column doesn’t contain null values」「Verify that a tabular asset adheres to a specified schema」「Check if an asset’s data needs refreshing」——也就是说，check 不只管“对不对”，也管“新不新鲜”。[31]

          最关键的工程能力是可阻断性：把 blocking=True 设置上之后，一个 check 失败会直接挡住下游资产的物化，「if the orders_id_has_no_nulls check fails, the downstream augmented_orders asset won’t be materialized」。[31] 这意味着数据质量问题不会静默地往下游传染，而是在源头被拦下。check 结果会展示在 UI 里，Dagster+ 用户还能针对 check 失败配置告警。[31]

          2. metadata/tags/owners：把治理信息挂在数据对象本身，而不是挂在某次运行上

          Dagster 提供了几层互补的标注机制：[32]

          • owners：标明资产负责人（邮箱或 team: 前缀的团队名），可以驱动 Dagster+ 自动告警；
          • tags：「the primary way to organize assets in Dagster」，键值对形式（如 {"domain": "marketing", "pii": "true"}），可在资产目录里搜索筛选；
          • metadata：分为定义期 metadata（代码不变就不变）和运行期 metadata（每次物化可能不同，Dagster 会存成时间序列，比如行数随时间变化）。

          3. 血缘不只是“谁依赖谁”，还能细到字段级别

          dagster/column_schema 记录字段结构，dagster/column_lineage 记录“某个输出字段依赖了哪些上游字段”，「Dagster+ provides rich visualization and navigation of column lineage in the Asset catalog」。[32] dagster/code_references 还能把资产链接回具体源码（本地文件或 GitHub/GitLab URL），做到「view those assets’ source code from the Dagster UI」。[32] 像 dbt 这类集成会自动填充这些 metadata，减少手工标注的工作量。[32]

          这说明 Dagster 的“可观测性”不是一个额外挂上去的监控面板，而是直接把血缘、结构、责任人这些信息焊在资产对象上——这也是它和 Airflow 的“任务运行监控”在心智上最大的不同：一个观测的是任务跑得怎么样，一个观测的是数据本身是什么样。

          4. 工程边界在哪里

          asset-first 建模不是没有代价：

          • 你需要先花时间把“什么是资产、依赖关系是什么”想清楚，这对快速原型/一次性脚本来说是额外成本；
          • 如果流程本质上是一串带副作用的动作（发消息、调外部审批），而不是“生产一份数据资产”，用 op/job 甚至更轻的框架反而更直接；
          • 如果主要问题是长生命周期业务流程的状态恢复，Temporal 的 durable execution 语义更对症；
          • 如果主要问题是大量稳定 batch DAG 的调度和运营，而资产血缘不是当务之急，Airflow 的成熟度可能性价比更高；
          • 如果团队只是想让已有脚本更可靠，还没到需要资产目录和字段血缘的阶段，Prefect 的门槛更低。

          5. 正确位置

          Dagster 最自然的位置通常是：

          • 数据/分析工程团队，需要跨工具（dbt、Spark、Python）统一的资产目录；
          • 需要把数据质量检查、字段血缘、责任人正式化，而不是靠文档或口头约定；
          • 组织已经大到需要“谁负责这份数据”“这份数据现在新鲜吗”这类问题有正式答案。

          6. 动手活动

          输出

          dagster-governance-boundary-card.md

          列你的资产里哪些需要 blocking 的数据质量门禁、哪些需要字段级血缘、哪些需要明确责任人。写一句结论：你的主问题是资产治理与可观测性，还是更轻的任务调度/脚本可靠性。

          7. 总结

          关键问题 一句话
          asset check 在做什么 把数据质量和新鲜度变成可阻断的正式门禁
          metadata/tags/owners 在做什么 把治理信息焊在数据对象本身，而不是某次运行
          血缘的独特之处 可以细到字段级别，并链接回源码
          最大边界 需要先投入资产建模成本，不适合纯副作用型或轻量脚本场景
