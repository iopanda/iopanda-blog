          可恢复性、幂等性、补偿与工程边界

          Temporal 的价值如果只被理解成“能自动重试”，那就太浅了。它真正困难、也真正值钱的地方，在于：系统必须把 workflow 设计成能恢复、activity 设计成可幂等、失败路径设计成可补偿。[6][7][9] 也就是说，Temporal 不是帮你逃避分布式复杂度，而是帮你把这类复杂度放进一个更正确的执行模型里。

          学习目标：学完本章，你将能够——

          1. 理解为什么 durable execution 不等于魔法容错；
          2. 说出幂等性、补偿、重试策略在 Temporal 里的真实角色；
          3. 判断什么时候 Temporal 是必要复杂度，什么时候是过度设计；
          4. 理解它的工程边界：服务化、状态化、运行成本；
          5. 为系统写一张 workflow-reliability card。

          1. 可恢复性为什么不是自动赠品

          Temporal 的平台可以帮你：

          • 记录历史；
          • 恢复状态；
          • 调度重试；
          • 继续执行。

          但它不能替你决定：

          • 某个副作用是否能安全重做；
          • 某个失败是否该补偿；
          • 某个外部系统调用是否幂等。

          这部分仍然是系统设计责任。

          2. retry 和 compensation 的关系

          retry 文档说明 Temporal 在服务与客户端层面都严肃对待重试语义。[7] 但重试不是无限正义：

          • 有些错误应重试；
          • 有些错误只会把副作用做两遍；
          • 有些错误应该进入补偿流程。

          所以 Temporal 强的不是“永远重试”，而是帮你把这些语义正式化。

          3. 幂等性为什么是关键纪律

          只要 workflow 会恢复、activity 会重放或再次触发，幂等性就不是可选项。 否则 durable execution 反而会把错误稳定重复放大。

          4. 工程边界

          Temporal 很强，但并不是所有流程都值得上：

          • 如果只是简单 nightly batch，Airflow 可能更直观；
          • 如果只是 Python app 内轻量 flow，Prefect 可能更轻；
          • 如果主要是数据资产治理，Dagster 更自然。

          Temporal 最适合那些真正被“状态恢复语义”主导的流程。

          5. 动手活动

          输出

          temporal-reliability-card.md

          列你的流程中哪些 activity 必须幂等、哪些失败要补偿、哪些错误可重试、哪些等待必须被持久化。写一句结论：你的系统是否真的需要 durable execution，而不是普通任务调度。

          6. 总结

          关键问题 一句话
          Temporal 真正值钱的地方是什么 把恢复、重试、补偿放进正式执行模型
          幂等性为什么关键 因为 durable execution 会稳定重放错误也稳定重放正确逻辑
          最大边界 不是所有流程都值得引入这么强的状态语义
          正确使用方式 在“恢复语义”真正成为主问题时上 Temporal
