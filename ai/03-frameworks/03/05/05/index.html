          分布式、导出、调参与工程边界

          Axolotl README 列出的能力非常“工程化”：FSDP1/FSDP2、DeepSpeed、多节点、Ray、Sequence Parallelism、Context Parallelism、Expert Parallelism、merge-lora、vllm-serve、quantization、profiling。[13][14][19] 这说明它不是停留在“会写 YAML”，而是要让 YAML 能够真正承载大规模训练系统的工程边界。

          学习目标：学完本章，你将能够——

          1. 理解为什么配置驱动框架最终一定会碰到分布式与导出边界；
          2. 说出 Axolotl 怎样把多 GPU、多节点、并行维度纳入 recipe；
          3. 解释 merge-lora、vllm-serve、profiling 为什么重要；
          4. 判断什么时候 config 可以继续承载复杂度，什么时候需要更重的平台；
          5. 为项目写一张 distributed-boundary card。

          1. YAML 只有能承载工程边界，才不是玩具

          很多配置框架在 demo 里很好看，但一到真实训练就碎掉：

          • 分布式要另写脚本；
          • 导出要另写脚本；
          • profile 要另写脚本；
          • 推理服务要另搞一套。

          Axolotl 的不同在于，它试图继续把这些都收进同一世界。[14]

          2. 分布式为什么是它的重要部分

          distributed-parallel 示例明确展示了：

          • FSDP + TP + CP 的组合；
          • HSDP + TP 的多节点组合；
          • 这些都能通过 YAML 表达。[19]

          这说明 Axolotl 的 recipe 不只描述“训什么”，还描述“如何在硬件拓扑上训”。

          3. 导出与服务为什么也必须进 recipe 世界

          AGENTS.md 中直接提供：

          • axolotl merge-lora config.yaml
          • axolotl vllm-serve config.yaml
          • axolotl inference config.yaml。[14]

          这很重要，因为训练系统最常断裂的地方就是：

          • 训练配置和推理配置脱节；
          • adapter merge 过程不可追溯；
          • RL/GRPO 的服务侧另起炉灶。

          4. profiling 为什么是训练工程的一部分

          SFT agent 文档里甚至把 profiler steps、trace、memory snapshot 直接写进 config 语义。[15] 这说明 Axolotl 认为性能诊断不是额外附加物，而是 recipe 生命周期的一部分。

          5. 动手活动

          输出

          axolotl-distributed-boundary.md

          为你的项目列出：单卡 / 多卡 / 多节点 / merge / inference / profiling 各自需要进入哪一层配置。写一句结论：为什么一个训练框架若不能承载这些边界，就很难长期服务团队。

          6. 总结

          关键问题 一句话
          分布式在 Axolotl 里像什么 recipe 的一部分，而不是外部脚本
          merge / serve 为什么重要 训练工件必须可交付、可追溯
          profiling 为什么重要 性能诊断也是训练流程的一部分
          最大边界 当组织复杂度高到需要更完整平台治理时，单框架仍有上限
