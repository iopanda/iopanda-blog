          模型卡与文档

          01.06 用七章评测证明课程助教「可以用」,上一章(01)又登记并管住了它背后的数据流——但模型本体还差最后一件交付物:一份随模型一起走的说明书。adapter 与 API 上线后,调用者看到的只是一个「会说话的接口」,训练历史、评测证据、已知风险都看不见;本章把这些年积累的评测结论与治理信息,压缩成一份结构化、可审计、随版本更新的模型卡(model card),并讲清它与 README、评测报告、运维文档的分工——让第三方只读文档,就能安全、正确地使用这个模型。

          学习目标:学完本章,你将能够——

          1. 说出模型卡的定义与目的,解释它为什么是「说明书」而不是「宣传页」;
          2. 解释为什么评测结论必须随模型一起交付,模型卡如何衔接 01.06 的评测报告;
          3. 说出模型卡的九个要素(参考 Model Cards for Model Reporting 论文与 Hugging Face 模板),并说明每个要素回答什么问题;
          4. 区分模型卡与 README、数据卡、评测报告、运维文档的分工与更新节奏;
          5. 把 01.03/08 的一页雏形补全为九要素齐备的 model-card.md,让第三方只读即可安全调用 API。

          1. 概念:模型卡 = 随模型发布的「说明书」

          • 模型卡(Model Card):随模型发布的一份结构化文档,记录模型的用途、禁止用途、训练数据、评测方法与结果、已知限制与风险、维护者与版本。它回答的不是「这个模型多厉害」,而是「这个模型是什么、能做什么、不能做什么、凭什么相信、出问题找谁」。
          • 术语出处:Google 团队的论文《Model Cards for Model Reporting》(Mitchell et al., 2019)提出,训练模型越来越多地用于高影响场景,发布方应随模型附上「性能特征」文档,明确预期用途、把模型用在它不适合语境的风险降到最低;论文还给出了建议段落清单——模型详情、预期用途、评测因素、指标、训练数据、量化分析、伦理考虑、告诫与建议。
          • 模型卡是交付物文档,不是宣传页:宣传页只展示最好的一面;模型卡必须主动说出「坏消息」——在哪里会错、什么输入不要喂给它、评测覆盖了哪些范围、哪些范围根本没测。01.03/08 收官章要求的那一页卡(用途边界、证据、回滚)是雏形,本章按权威模板把它补全成可长期随模型发布的标准件。
          • 它与数据卡互为姊妹:数据卡(datasheet)回答「数据怎么来的、许可与 PII 怎么处理」(01.02/02 与 01.03 的数据目录),模型卡回答「模型本身是什么」——上一章登记的数据治理结论,正好通过数据卡链接进模型卡。
          • 现代实践:Hugging Face Hub 把模型卡渲染成模型主页,用 YAML frontmatter 承载元数据(license、language、base_model 等)、用 Markdown 段落承载正文,并提供带注释的官方模板(Annotated Model Card Template);NIST AI RMF 也把透明与问责列为 AI 风险管理的核心特征——「发布即附文档」正从倡议变成工程纪律与合规预期。

          2. 为什么需要:评测结论必须随模型一起交付

          • 使用者看不到训练历史:学生、调用 API 的程序员、审查者面对的只有一个对话接口;他们无从知道模型被微调过什么、在哪些题上会错、数据是否合规。模型卡把「训练者已知的」转交给「使用者合理的预期」——没有它,预期要么过高(把课程助教当全能教师),要么过低(该问的不敢问)。
          • 评测报告是一次性快照,模型卡是长期档案:01.06/07 的 eval-report.md 回答「这一版评测后能不能上线」,但它躺在 eval 目录里、随每次评测作废;模型卡把关键指标、安全双比率与失败类别压缩成「跟着模型版本走」的摘要,并链接完整报告。分工一句话:报告负责拍板,模型卡负责长期引用。
          • 出问题时文档是第一现场:模型若在真实使用中出错(如学生把编造内容当真引发纠纷),第一个被检查的就是「文档当时怎么说的」——预期用途写没写清、已知限制有没有声明、维护者是谁。空口「我不知道它会这样」不可审计;模型卡把「已知/未知、能做/不能做」钉在纸面上,呼应 01 章数据治理留下的责任记录思路。
          • 模型会演进,版本必须可定位:同一个 API 后面可能挂过 base、SFT、LoRA、DPO 多个版本(01.03 全链路产物);线上报 bug 时若连「哪个模型答的」都无法确定,调查无从开始。因此版本号、变更记录与回滚方式是模型卡的必备字段,并与 01.04 的部署镜像 tag 一一对应。
          • 透明是可审计性的前提:无论对内发布还是对外分享,附文档的模型才谈得上「可审查、可质疑、可交接」;这也是 05 章发布评审逐项核对模型卡的伏笔——评审清单里没有模型卡的发布,等于没有说明书的上架。

          3. 位置:与 README、数据卡、评测报告、运维文档的分工

          本仓库从 01.02 到 01.06 积累了多份文档,容易混淆;它们服务不同读者、回答不同问题:

          文档 回答的问题 主要读者 更新节奏
          README 怎么安装、怎么调用、示例代码 开发者 代码变更时
          数据卡(01.02/02、01.03 data/) 训练数据来源、许可、PII 与去重处理 训练者、审计者 数据变更时
          评测报告(01.06/07 eval-report.md) 这一版评测后能不能上线、以什么条件 决策者 每次评测快照
          模型卡(本章 model-card.md) 模型是什么、能/不能做什么、证据与维护者 使用者、发布审查 模型版本变更时
          运维文档(01.04) 线上延迟、成本、错误率与事故处理 运维 持续
          • 一个分辨技巧:把每份文档标题换成「给谁、回答什么问题」——README 教调用、数据卡管数据、评测报告管放行、模型卡管使用、运维文档管运行;五者构成一条完整证据链,缺一环都不可审计。
          • 模型卡与 README 最容易混(在 Hugging Face 上甚至同处一页):README 面向「想运行代码的人」,可以不写边界;模型卡面向「想使用与审查模型的人」,必须写清边界与失败——README 可以只报喜,模型卡必须报忧。
          • 实际发布时五者互相链接:README 顶部放模型卡链接,模型卡里引用评测报告与数据卡的 commit,运维文档记录线上实际加载的模型版本号;05 章的发布评审会顺着这条链逐项核对「写的是否等于做的」。

          4. 模型卡九要素:每个部分回答什么问题

          综合论文建议段落与 Hugging Face 模板,一份可直接交付的模型卡至少包含九要素:

          # 要素 要回答的问题 课程助教上的示例
          1 模型概述 是什么模型、哪个版本、谁做的 name=course-ta;base=Qwen/Qwen2.5-0.5B-Instruct + LoRA adapter
          2 预期用途 设计给谁、解决什么任务、怎么调用 面向课程学习者,解答课程资料内的概念与作业疑问;经 01.04 API 调用,附同一 system prompt 约定
          3 禁止用途 什么场景不能用、为什么不建议 实时信息(天气/新闻)、医疗法律财务建议、代写作业与考试作弊、任何高利害决策
          4 训练数据 学了什么、来源与许可、含不含 PII 课程讲义衍生的指令数据 + 通用数据;来源、许可、PII 处理见数据卡(呼应 01.02/02 与 01 章)
          5 评测方法 用什么题、什么指标、什么条件测的 golden set 20 条四类别(01.03/08)+ eval spec 任务组(01.06/01)+ 安全 attack set(01.06/06);全模型同一 system prompt 与 do_sample=False
          6 评测结果 各项多少分、哪里会错 依据正确率、格式合规率、拒答正确率、裁判均分与一致率、安全双比率;失败例原样链接
          7 已知限制与风险 已知会出什么问题、缓解了没有 资料外可能编造、训练数据可能被生成时泄漏、语料偏见;缓解与遗留 blocker 状态如实标注
          8 维护者与反馈 谁负责、怎么联系、多久更新 维护者署名与联系方式、问题反馈渠道、随课程资料版本的更新节奏
          9 版本与回滚 哪一版、改了什么、如何回退 version + changelog;删除 adapter 回到 base、API 镜像回退上一 tag

          要点:

          • 九要素不是越长越好:一页纸能讲清就写一页;关键是每个要素都有内容、不空泛——「无」「不适用」必须写明理由(如「未评测多语言,因此禁止用途含非中文输入」),而不是留白。
          • 「预期用途」与「禁止用途」要成对写:只说「能答疑」不说「不能答什么」,使用者就会拿它问天气、问考试成绩,然后得到编造——论文的核心动机正是「把模型用在它不适合语境的风险降到最低」。
          • 每个数字都要能追溯到证据:评测结果注明来源(评测报告哪一节、哪次 run),禁止「口说 90%」;复用 01.06 的复现纪律——日期、模型与 adapter 版本、system prompt 版本、命令缺一不可。
          • 版本纪律:model card 的 version = adapter 目录名 = API 镜像 tag,三者不一致就是发布事故,05 章发布评审会拿这条规则核对。
          • 模型卡与系统提示词(system prompt)是「同一枚硬币的两面」:卡上写「资料外应拒答」,system prompt 里就必须真的这么要求——文档承诺的行为要与 01.06 评测时锁定的调用约定完全一致,评测才会算数。

          5. 从评测报告到模型卡:写作流程与元数据

          推荐写作顺序(直接把本章变成 checklist):

          1. 从 01.03/08 已有的 model-card.md 出发——模型 ID、训练目的、回滚方式已在,不推倒重来;
          2. 打开 01.06/07 的 eval-report.md 与 06 章的 safety-report.md,把指标汇总、安全双比率、失败类别与「有条件上线」的条件清单原样搬进要素 5~7;
          3. 对照 01 章 data-governance.md 的数据流登记,把训练数据来源、许可与 PII 处理链接进要素 4;
          4. 按「API 调用者视角」重写要素 2~3——真实使用者是调用接口的程序与最终学生,不是训练者自己;
          5. 补版本头、维护者与 changelog,提交 git,并把模型卡链接进 README 顶部与 API 文档。

          模型卡顶部的版本头可参考 Hugging Face 风格的 YAML 元数据:

          # model-card.md 顶部(HF 风格);version 与 adapter 目录、API 镜像 tag 必须一致
name: course-ta
version: 1.0.0
base_model: Qwen/Qwen2.5-0.5B-Instruct
adapter: runs/course-ta/adapter        # 01.03/08 验收通过的 LoRA
eval_report: reports/eval-report.md    # 01.06/07 结论快照(含安全结果)
data_card: data/data-card.md           # 01.02/02 数据许可 + 01 章数据登记
deploy: api:course-ta:1.0.0            # 01.04 API 镜像,版本号一一对应
license: 见 data-card.md(内部课程使用,不对外分发训练数据)
          yaml

          6. 动手活动:为课程助教 adapter + API 补全完整模型卡

          动手活动:补全 model-card.md

          目标:在 01.03 的 finetune/ 项目里,把 reports/model-card.md 从「一页雏形」补成九要素齐备、可随 API 发布的版本;若当时没写,则从零写出同样结构。

          步骤:

          1. 列证据清单:从 eval-report.md 抄指标表与三态结论,从 safety-report.md 抄安全双比率与缓解状态,从 data-governance.md 抄数据登记链接——模型卡不产生新证据,只汇总已有证据;
          2. 搭九要素骨架(第 4 节表),逐节填写:要素 2~3 按「API 调用者视角」重写,每条禁止用途给一句理由(「无实时数据,答天气必编造」);
          3. 写版本头 YAML,核对 version 与 adapter 目录、API 镜像 tag 一致;在要素 7 里如实写遗留 blocker(如评测报告「有条件上线」的条件清单)与关闭状态;
          4. 串起文档链:在 README 顶部与 API 文档加入模型卡链接,在模型卡里链接 eval report 与数据卡 commit;把维护者与反馈渠道写实;
          5. 通读测试:把模型卡给一个没参与训练与评测的同学读,请他说出「能做什么、不能做什么、证据是什么、出问题找谁」——他说不全,卡就没写完。

          完成标准:第三方只读 model-card.md 就能安全调用 API:知道哪些问题可以问、哪些不能问、凭什么信任、如何核对版本与回滚;全文找不到「感觉」「应该没问题」这类无证据表述。

          7. 边界与排错

          • 把模型卡写成宣传页:通篇「强大、精准、友好」,没有禁止用途、失败例与风险——这不是模型卡,是 README 的坏习惯;模型卡必须包含「坏消息」,写不出来说明你对模型还不够了解。
          • 整段复制评测报告:报告回答「这次能不能上线」,模型卡回答「长期如何使用」;卡只保留关键数字并链接报告,两者互相引用而非互相替代——报告随评测作废,卡随版本换版。
          • 只写训练态,不写交付态:卡上全是训练细节,却没有 system prompt、生成参数(do_sample=False、max_new_tokens)、API 镜像 tag——使用者按别的参数调用,行为就与评测不一致,卡的承诺全部落空。
          • 要素空泛或留白:「限制:无」不可接受;「未评测 X」本身就是一条诚实的声明,比假装全面更专业——写清评测边界正是模型卡的价值。
          • 版本与工件脱节:卡上 1.0.0、adapter 目录 0.9.9、镜像 tag 无号——线上事故时无法定位「谁答的」;发布前用 05 章的评审清单逐项核对版本一致性。
          • 写完不审、更新不留痕:模型卡也是代码,改要素要留 changelog、要过评审;把它当成「写完就再也不动」的静态文件,等价于让说明书慢慢腐烂成错误文档。

          8. 总结

          关键问题 一句话
          模型卡是什么 随模型发布的「说明书」:用途、限制、数据、评测、风险、维护者、版本
          为什么需要 使用者看不到训练历史;评测结论必须随模型长期交付;出问题时可追溯可问责
          与相邻文档分工 README 教调用、数据卡管数据、评测报告管放行、模型卡管使用、运维文档管运行
          九要素 概述、预期用途、禁止用途、训练数据、评测方法、评测结果、已知限制与风险、维护者与反馈、版本与回滚
          写作要领 从评测报告取数、按使用者视角写边界、版本号与工件一致、坏消息必须写
          动手产物 model-card.md:九要素齐备、证据可链接、第三方只读即可安全使用

          思考题:评测报告的结论是「有条件上线」时,模型卡的「评测结果」与「已知限制」两节应如何呈现,才能不误导使用者?模型卡写了「禁止用于考试代写」,调用 API 的第三方应用不遵守怎么办——文档能约束行为吗?发布后发现模型在卡上没写过的场景出了事,模型卡该承担什么责任?

          参考答案

          有条件上线时,结果节要如实写「达到阈值但存在未关闭 blocker」,限制节逐条列出条件、关闭状态与复核人——模型卡永远不能比评测报告更乐观,把「有条件」写没了就是隐瞒风险。卡上的禁止用途只是「声明」,约束不了不读卡的调用方,必须靠 API 层的输入过滤、最小权限与人工复核(03/04 章)把声明变成强制,这也正是下一章的主题。没写过的场景出事要分两层看:若是文档遗漏(实际场景属于预期用途却没写),补 changelog、修订卡并写明「此场景已评测/未评测」;若使用者拿它做卡上明令禁止的事,预期用途写得越清楚,责任边界越清晰——模型卡的价值就在于如实声明评测边界:既不夸大能力,也不揽下不属于它的责任;05 章的发布评审会用「写的是否等于做的」来核对这一切。
