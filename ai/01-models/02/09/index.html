          采样与定性评测

          2026-09-02 · iopanda

          • course
          • model-pretraining
          • text-generation

          上一章(08)把 Mini GPT 训到验证损失收敛,并保存了最佳 checkpoint;这一章回答紧接着的两个问题:模型怎样把 logits 变成一段文字,以及凭什么相信这段文字是好的。你将理解为什么生成必须逐 token 进行、解码参数到底在控制什么风险,并建立一套可重复的定性评测流程,而不是凭一次「看起来不错」的输出下结论。

          学习目标:学完本章,你将能够——

          1. 用自己的话解释「为什么生成是逐 token 的自回归循环」,以及它与训练前向过程的区别;
          2. 从 checkpoint 加载模型与 tokenizer,写出可运行的生成函数;
          3. 区分 greedy、temperature、top-k、top-p 四种解码策略,并说明它们各自在控制什么风险;
          4. 用固定提示词、固定 seed 和记录表完成一次可重复的定性评测;
          5. 识别重复、乱码、提示泄漏与训练文本记忆的迹象,并把问题定位到原因,而不是盲调参数。

          1. 生成为什么是逐 token 的

          1.1 概念:模型只会「预测下一个 token」

          • 概念:Decoder-only 语言模型在预训练阶段只学会了一件事——给定前文,输出词表上每个 token 成为「下一个」的概率分布。因此模型内部不存在「一次写好整段话」的功能:整段输出只能由一次次「预测下一个 token」拼接而成。这种把输出重新喂回输入端、一步接一步推进的过程,称为自回归生成(Autoregressive Generation)。
          • 为什么必须逐 token:这不是工程偷懒,而是架构与训练目标共同决定的。训练时模型被要求在每个位置做「下一个 token 预测」,并用因果掩码保证它永远看不见未来;到了生成阶段,模型只会用同一种方式工作——输入已有的前缀,输出下一个 token 的分布。你看到的「一句话」,其实是模型把这句话当作「下一个 token 的上下文」重复预测出来的。
          • 为什么不这样做会出问题:若尝试让模型一次输出整段(一步预测多个 token),模型从未被训练过这种输出格式,结果会偏离它学到的分布,变成无意义的乱码。生产环境中的 speculative decoding 等加速技巧,本质仍是「小模型逐 token 起草、大模型一次校验多个 token」,不改变本节结论。
          • 训练与生成的对比:
          环节 训练 生成
          输入 完整文本序列 已有 token 前缀(提示词 + 已生成部分)
          预测位置 所有位置同时计算 只取最后一个位置的 logits
          正确答案 有:右侧下一个 token 没有,只能按策略抽样
          权重 反向传播更新 冻结,只做前向(torch.no_grad())
          • 由此引出两个实操结论:① 输入超过训练时的 context_length 时,只保留最近 context_length 个 token——超出训练窗口的远古前缀,模型从未学会利用,留着只会拖慢计算;② 每生成一个 token 都要对整段上下文重新做一次前向,文本越长单步越慢(注意力开销随长度平方增长),这正是 01.04 推理单元中 KV cache 等优化的动机。

          1.2 第一个生成函数

          把 1.1 的循环写成代码,就是本章的第一个生成函数:输入已有 token → 取最后一个位置的 logits → 按策略选下一个 id → 追加到输入,循环 max_new_tokens 次。

          @torch.no_grad()
def generate(model, ids, max_new_tokens, temperature=1.0, top_k=None):
    model.eval()
    for _ in range(max_new_tokens):
        window = ids[:, -model.context_length:]
        logits = model(window)[:, -1, :]
        if temperature <= 0:
            raise ValueError("temperature 必须大于 0")
        logits = logits / temperature
        if top_k is not None:
            threshold = torch.topk(logits, min(top_k, logits.size(-1))).values[:, -1:]
            logits = logits.masked_fill(logits < threshold, float("-inf"))
        probabilities = torch.softmax(logits, dim=-1)
        next_id = torch.multinomial(probabilities, num_samples=1)
        ids = torch.cat([ids, next_id], dim=1)
    return ids
          python
          • 循环体四步:截窗 → 取末位 logits → 套解码策略 → 抽样并拼接;temperature 与 top_k 在这里已经出现,它们就是第 2 节的主角。
          • torch.multinomial 是按概率随机抽样,不是对 token id 做数学抽样。调用前确认模型、tokenizer、vocab_size 来自同一个实验;三者任意错配,结果都没有解释价值。
          • 因为抽样带随机性,同一提示词每次运行可能得到不同输出——这正是第 3 节要求「固定 seed、多 seed 复跑」的原因。

          2. 解码参数:在控制风险,不是在「加智能」

          2.1 概念:旋钮改的是「怎么选」,不是「会什么」

          • 概念:解码参数(温度、top-k、top-p)只作用于「从概率分布中挑选 token」这最后一步,不触碰权重、不增加知识、不改变模型的能力上限。它们是一组风险旋钮,用来在两类失败之间找平衡:确定性复读(greedy 导致的重复、呆板)与随机胡言(采样过度导致的发散、乱码)。
          • 为什么需要它们:模型学到的原始概率分布并不天然适合直接展示——直接取最大概率会陷入重复短句,直接按原始分布抽样又会被长尾噪声带偏。解码参数把「下一句该冒多大险」变成可调的工程参数。
          • 一个直觉:把概率分布想成一份候选菜单。greedy 是永远点销量第一的菜;temperature 决定你有多愿意尝试第二名之后的选择;top-k / top-p 是直接把「明显离谱的菜」从菜单上撕掉。菜单(模型学到的分布)没变,变的是点菜策略。
          • 如果不做会怎样:不做选择地「默认输出」,等于既不知道候选集、也不知道随机性来源,任何生成结果都无法解释、无法复现。

          2.2 四种策略对照:各在控制什么风险

          策略 做法 控制什么风险 代价与注意
          Greedy 总选概率最大的 token 消除随机性,输出可复现 最容易重复与死板
          Temperature logits 除以温度 T 后再归一化 T<1 压低低概率候选、抑制发散;T>1 抹平分布、减少机械重复 T 过高会放大噪声,开始胡言乱语
          Top-k 只保留概率最高的 k 个候选再抽样 剪掉长尾中离谱的候选 k 太小单调,k 太大约等于没剪
          Top-p(nucleus) 保留累计概率刚达到 p 的最小候选集 候选数随上下文自适应:分布集中时少剪、分散时多剪 仍需结合 temperature,不能包治百病
          • 实现 greedy 时使用 argmax,不要设置温度后仍声称它是 greedy。实现 top-p 时先按概率降序排序、计算 cumulative sum、屏蔽累计概率越过 p 的候选,再把概率映射回原 id 顺序;至少保留最高概率 token,避免全为负无穷。
          • 初学实验可先完成 greedy 与 top-k,并把 top-p 作为扩展练习;第 3 节的生成脚本先实现 temperature + top-k 组合。

          3. 定性评测:建立一份可重复的生成卡

          3.1 什么是定性评测,为什么 loss 不够

          • 概念:定性评测(Qualitative Evaluation)是让模型在固定提示词上生成文本、再由人按明确标签逐条审查的过程;与之相对的是 loss、困惑度这类定量指标。
          • 为什么 loss 下降还不够:验证 loss 是全体 token 上的平均信号——某些位置「非常糟」可以被大部分位置「普通好」摊平;它也不回答「生成出来像不像话、会不会重复、有没有背下训练文本」。这些问题只有把模型真正跑起来看输出才能暴露。一句话:loss 告诉你训练是否在收敛,生成样例告诉你模型是否可用。
          • 为什么评测必须可重复:如果每次临时挑提示词、换 seed,只展示最顺眼的一条输出,那么「这次训练比上次好」只是幸存者偏差。要比较两次训练,输入必须固定、参数必须记录、输出必须全留、审查必须有统一标签。
          • 在 eval/prompts.jsonl 固定 8–12 条提示词:短中文、英文、标点/数字、语料领域内的续写,以及至少两条从未出现在训练集的保留提示。不要临时挑选最好的输出。
          • 每次评测写入 reports/generation.md:
          checkpoint prompt id seed 参数 输出 人工标记
          best-valid zh-01 42 temp=0.8, top_k=40 原样保存 连贯/重复/乱码/疑似记忆
          • 同一参数和 seed 应产生相同结果(在相同硬件与可复现设置下尽量如此);同时至少用 3 个不同 seed 观察采样的稳定性。定性评测不是严格基准,但它能及早暴露训练 loss 看不出来的问题。

          3.2 创建可直接运行的生成脚本

          新建 src/generate.py。本脚本加载上一章训练出的最佳 checkpoint;请勿用未训练的 latest.pt 冒充最佳结果。

          from pathlib import Path
import torch
from tokenizers import Tokenizer
from src.model import MiniGPT

torch.manual_seed(42)
device = "cuda" if torch.cuda.is_available() else "cpu"
path = "runs/alice-bpe-v1/checkpoints/best-valid.pt"
checkpoint = torch.load(path, map_location=device, weights_only=True)
cfg = checkpoint["config"]["model"]
tokenizer = Tokenizer.from_file("artifacts/tokenizer.json")
model = MiniGPT(tokenizer.get_vocab_size(), **cfg).to(device)
model.load_state_dict(checkpoint["model_state"])

@torch.no_grad()
def generate(prompt, count=120, temperature=0.8, top_k=40):
    ids = torch.tensor([tokenizer.encode(prompt).ids], dtype=torch.long, device=device)
    model.eval()
    for _ in range(count):
        logits = model(ids[:, -model.context_length:])[:, -1] / temperature
        values, _ = torch.topk(logits, min(top_k, logits.size(-1)))
        logits[logits < values[:, -1:]] = float("-inf")
        ids = torch.cat([ids, torch.multinomial(torch.softmax(logits, -1), 1)], 1)
    return tokenizer.decode(ids[0].tolist())

for prompt in ["Alice was", "The Queen"]:
    print("PROMPT:", prompt)
    print(generate(prompt))
          python

          运行 python -m src.generate > reports/generation-raw.txt,再用编辑器打开该文件。首先应看到两个 PROMPT:,并保留所有输出。若 FileNotFoundError,回到上一章先训练出 best-valid.pt;若 size mismatch,说明 tokenizer、配置或 checkpoint 来自不同实验,不能混用。

          动手活动:生成并审计 10 条输出

          4. 发现问题时先定位,不要盲调参数

          解码参数只是抽样旋钮,不是质量修复。遇到坏输出,第一步是判断它属于哪一类问题,再决定改模型、改数据还是改采样:

          观察到的问题 可能原因 可验证动作
          很快重复一个短句 小数据、训练不足或过度贪婪 比较不同 checkpoint 与 temperature
          大量 <unk> / 乱码 tokenizer 或编码不一致 decode id、核对 tokenizer hash
          与训练文本逐字相同 小语料记忆或提示本身出现过 用搜索/哈希检查来源,报告而非掩盖
          完全不连贯 模型未学到、数据或标签错位 回查 loss、右移标签与 id 范围
          • 不要将「更高温度」当作质量修复:它只改变抽样分布,不能修复错误 tokenizer、错位标签或低质量训练数据。
          • 任何疑似个人信息或受限制内容都不能因为「模型生成了」而忽视;应回到数据来源和清洗记录处理(见 02、03 章)。

          5. 总结

          环节 产物 用途
          逐 token 生成 src/generate.py 把 checkpoint 变成文本
          解码策略 greedy / temperature / top-k / top-p 控制采样风险,而非「加智能」
          固定输入 eval/prompts.jsonl 评测输入不漂移
          记录表 reports/generation.md 保留全部输出与人工标记
          • 生成是以同一 tokenizer 反复调用已训练模型的过程。可靠的定性评测有四个要素:固定输入、记录参数、保留全部输出、按明确标签审查。这样下一次训练才能与本次真正比较。

          思考题:① 为什么只展示一个流畅输出不能证明模型较好?② 为什么 top-k 和 temperature 可以同时存在?③ 为什么评测既要固定 seed,又要求至少换 3 个 seed 复跑?

          参考答案

          ① 单个输出可能恰好幸运,且无法展示失败率或重复率;只有保留全部输出并按标签统计,才能比较两次训练。② temperature 调整候选之间的相对分布,top-k 限制候选集合,两者作用在不同阶段,因此可组合。③ 固定 seed 保证同一参数下的结果可复现、可核对;换 seed 则是检验结论是否依赖某一次具体的随机抽样,避免把一次运气当成能力。
