          训练分词器

          2026-09-02 · iopanda

          • course
          • model-pretraining
          • tokenization

          上一章确定了训练、验证、测试三份文本的边界;本章回答「文本如何变成数字」:训练一个 BPE 分词器,把它保存为工件,并验证编码与解码能够无损往返。动手前先建立两个心智模型:分词器为什么是模型的一部分,以及字符/词/子词三种方案如何取舍。

          学习目标:学完本章,你将能够——

          1. 解释为什么分词器是模型的一部分,以及更换分词器为何会使权重失效;
          2. 说明字符级、词级与子词三种切分方案的取舍,理解子词为何成为主流;
          3. 只在训练集上训练 BPE 分词器,并保存为 artifacts/tokenizer.json;
          4. 从文件加载分词器,完成编码、解码与往返一致性检查;
          5. 用 token 数与 <unk> 比例比较不同词表大小,并作出有依据的选择。

          1. 分词器是什么:为什么它是模型的一部分

          • 概念:分词器(Tokenizer)是什么。 它把文本切分成词元(token),再把每个词元映射为整数 id,并支持反向把 id 序列还原为文本(解码)。它的核心产物是词表(vocabulary)——一张「id ↔ 文本片段」的双向映射表,而词表大小直接决定模型 embedding 表与输出层的维度。
          • 为什么它是模型的一部分。 语言模型不直接处理字符串:输入必须先变成 id 序列,才能查 embedding 表得到向量。权重是在某个特定词表上训练出来的——embedding 的每一行都对应一个具体 token 的含义。所以词表不是可以随意更换的「预处理字典」,而是模型参数布局的一部分。
          • 如果不把分词器当作模型的一部分会怎样。 训练与推理必须使用完全相同的分词器文件。用另一个分词器加载同一份权重,id 的含义会整体错位:同一个 id 在训练词表里指「的」,在推理词表里可能指「模型」,模型却按训练时学到的含义去解释它,输出立刻不可用。
          • 工程结论:分词器文件要像权重一样被保存、被版本化、随 checkpoint 一起发布;第 8 章保存 checkpoint 时会再次遇到这一要求。

          词表由两类条目构成:普通 token(文本片段)与特殊 token。特殊 token 不是自然语言,而是训练与推理协议的信号,它们的 id 必须在训练前固定并写进配置,否则第 6~8 章的 batch 拼接与损失计算会对不上:

          特殊 token 角色
          <pad> 把 batch 内长短不一的序列补齐到等长
          <bos> 标记序列开始(用于条件生成)
          <eos> 标记序列结束,训练时是「文本末尾」的下一个目标
          <unk> 词表外输入的兜底

          2. 三种切分方案:字符、词与子词

          它们分别是什么,为什么子词成为主流? 字符级把文本拆到单字符甚至单字节;词级按空白与标点切成「词」;子词则让数据统计决定边界——高频词保留为整词 token,低频词与生僻词被拆成更小的常见片段。

          方案 优点 局限
          字符级 实现最简单,词表极小(几百),没有未知字符 每个 token 信息量小,序列很长,训练与推理慢
          词级 切分直观,序列短 词表巨大且永远收不全,未知词多;词形变化各自成词,参数浪费
          BPE/Unigram 子词 主流方案;兼顾词表规模与序列长度,未见过的词也能拼出来 训练与检查更复杂,词表大小需要实验调
          • 字符级的问题:序列过长会放大注意力与训练开销,模型也难以在合理上下文内捕捉长距离模式。
          • 词级的问题:自然语言词汇近乎无限,再大的词表也有未知词;每次遇到新词只能退化为 <unk>,信息直接丢失。
          • 子词的取舍:常见词一个 token(序列短),生僻词拆成片段(几乎无未知词),两边都拿到好处;代价是词表大小需要权衡——词表越大序列越短,但 embedding 与输出层参数越多;词表越小参数越省,序列却越长(第 5 节会量化比较)。
          • 真实世界的词表规模:GPT-2 用约 5 万词元(50,257),Llama 3 用 128K 词元,新一代模型普遍把词表做大以换取更短序列和更好的多语言表现——代价是 embedding 与输出层吃掉大量参数。教学实验从 2,000 起步,先跑通链路,再谈放大。

          3. 训练 BPE 分词器

          BPE(Byte Pair Encoding)的做法是:从字符/字节开始,反复合并语料中出现频率最高的相邻片段,直到词表达到目标大小。为什么只在训练集上训练? 若验证或测试文本参与词表构建,评估时模型就「见过」了测试文本的形状,属于第 4 章强调的信息泄漏——因此 BpeTrainer 只接收 data/processed/train.txt。

          使用 tokenizers 库,创建 src/train_tokenizer.py,复制以下完整文件。注意代码里 pre_tokenizer 与 decoder 成对设置为 ByteLevel:一个决定如何预切分文本与转写空格,另一个负责把 token 序列还原成原始文本,两者必须配套,否则 decode 无法复原输入:

          
# 导入必要的模块与路径配置
from tokenizers import Tokenizer, models, trainers, pre_tokenizers, decoders

INPUT = "data/processed/train.txt"
OUTPUT = "artifacts/tokenizer.json"

# 初始化 BPE 模型架构
# 创建一个 Tokenizer 对象，并指定使用 BPE（Byte-Pair Encoding）算法作为核心切词模型
tokenizer = Tokenizer(models.BPE(unk_token="<unk>"))

# 设置预分词器与解码器（ByteLevel 字节级）
# ByteLevel() 预分词：在切词前，把输入的文本转为基础字节流（0～255），并将特殊字符映射为可打印的符号（例如把空格转换为`Ġ`）。这样可以保证永远不会遇到未知自负（零 OOV），任何语言都能处理
# ByteLevel() 解码器：在编码还原时，负责把`Ġ`等符号重新还原为原文本中的空格和字符
tokenizer.pre_tokenizer = pre_tokenizers.ByteLevel()
tokenizer.decoder = decoders.ByteLevel()

# 配置训练参数（Trainer）
# vocab_size=2000：限制最终生成的词表最大容量为 2000 个 Token
# special_tokens=[...]：特殊 Token / 特殊标记，专门用来向模型传递结构信息或控制指令的特定符号，它们不属于普通的日常文本词汇
trainer = trainers.BpeTrainer(vocab_size=2000, special_tokens=["<pad>", "<bos>", "<eos>", "<unk>"])

# 读取文本数据，按 BPE 规则统计合并高频字符，生成词表
tokenizer.train([INPUT], trainer)

# 将训练好的词表和切词规则保存为 JSON 文件
tokenizer.save(OUTPUT)

# 打印最终实际生成的词表大小
print("vocab_size=", tokenizer.get_vocab_size())

          运行脚本,并检查实际文件与特殊 token 的 id:

          python src/train_tokenizer.py
python -c "from tokenizers import Tokenizer; t=Tokenizer.from_file('artifacts/tokenizer.json'); print(t.get_vocab_size()); print({x:t.token_to_id(x) for x in ['<pad>','<bos>','<eos>','<unk>']})"
          bash

          预期:词表大小接近(不一定等于)2,000,四个特殊 token 都有非负整数 id。若文件不存在,先确认你在项目根目录运行命令;不要在 IDE 的其他工作目录中运行脚本。

          训练完成后必须从文件重新加载并做一次往返,以证明后续训练与推理会使用同一个工件:

          from tokenizers import Tokenizer

# 加载词表模型 (`from_file`)**：重新从磁盘读取保存的 `tokenizer.json` 文件，验证模型持久化与加载功能是否正常。
loaded = Tokenizer.from_file("artifacts/tokenizer.json")

# 编码测试 (`encode`)：传入一段混合了中文、英文、符号和数字的测试文本（`sample`），将其切分为 Token 列表（`tokens`）并映射为数值 ID 列表（`ids`）。这能让你直观看到文本是如何被切碎和转成数字的。
sample = "数据库 database: v1.0"

# 解码验证 (`decode`)：将生成的数字 ID 列表还原回文本。用于检查“文本 \rightarrow ID \rightarrow 文本”的编解码过程是否可逆、是否存在信息丢失。
encoding = loaded.encode(sample)

print(encoding.tokens)
print(encoding.ids)
print(loaded.decode(encoding.ids))

# 安全性断言 (`assert`)：断言检查切分出的最大 Token ID 是否严格小于总词表大小（`vocab_size`），确保所有生成的 ID 都落在合法范围内，防止在后续训练神经网络时出现索引越界（Index Out of Bounds）的报错。
assert max(encoding.ids) < loaded.get_vocab_size()

          ByteLevel 是字节级预分词方式,通常能避免因少见 Unicode 字符而无法表示;它的空格显示形式可能与原文本视觉不同。验收时以 encode/decode 和实际训练 token 统计为准,而不是要求 token 字符串看起来等同于自然语言分词。

          动手活动:训练并检查分词器

          目标:提交 artifacts/tokenizer.json(词表 2,000 与 8,000 各一份)和 reports/tokenizer.md。

          步骤:

          1. 训练两个不同词表大小的分词器,均只用 train.txt;
          2. 对同一组中文、英文、标点和代码样本编码再解码;
          3. 统计验证集平均 token 数与 <unk> 比例。

          完成标准:解码后的文本与输入一致;报告说明选择哪个词表及其压缩率、未知 token 比例与理由。

          4. 常见错误

          • 在全量数据上训练分词器,使验证/测试文本信息泄漏;
          • 未固定特殊 token id,后续模型配置无法对应;
          • 只看词表大小,不看真实样本的切分质量;
          • 忘记将分词器与 checkpoint 一起保存。

          5. 用三个指标作出选择

          词表大小不是拍脑袋定的,用三个可计算的指标来比较两个实验:

          指标 如何计算 不能说明什么
          验证文本 token 总数 编码 valid.txt 后计数 token 少不必然质量高
          <unk> 比例 unk id 数 / 总 id 数 低 unk 不代表切分合理
          样本文本往返 decode(encode(text)) 人工核查 不能替代训练质量评估

          在本课程的 BPE 设置下,<unk> 比例异常高通常表示分词器配置或语料编码存在问题。选择词表大小时,把两个实验在同一验证集上的 token 数、典型中英文/数字/标点样本、训练资源约束一起记录;不要因为词表更大就默认更好——更大的词表会缩短序列,却也扩大 embedding 和输出层参数。

          6. 总结

          分词器是模型输入语义的一部分。只在训练集上训练它、固定特殊 token、保存完整文件并检查往返编码,才能保证之后的 .pt token id、权重和生成程序互相匹配。

          思考题:为什么 token id 17 脱离分词器文件没有含义?为何不能用新训练的分词器直接替换已训练模型的分词器?

          参考答案

          id 只是词表中某个 token 的索引,定义保存在分词器工件中。直接替换分词器会使相同 id 指向不同文本单位,而 embedding 权重仍按旧含义学习,导致输入和输出错位。
