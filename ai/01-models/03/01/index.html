          微调策略与基线

          2026-09-02 · iopanda

          • course
          • model-fine-tuning
          • baseline

          本章是 01.03 Fine-tuning and Alignment 的开篇。先想清楚三件事再动手指令微调:什么是微调、什么时候该微调(而不是用 RAG 或提示词)、为什么必须先建立基线。读完你会带着一份「可比较的对照组」进入后续 7 章,而不是盲目训练。

          学习目标:学完本章,你将能够——

          1. 说出微调、RAG、提示词三条路线的取舍,判断何时该微调;
          2. 区分基座模型与指令模型,解释「微调改变了什么」;
          3. 选择合适开源基座并在本地运行推理;
          4. 定义任务、成功条件并建立可复现的基线记录;
          5. 判断「何时不应微调」。

          1. 概念:微调是什么

          • 微调(Fine-tuning):在预训练模型的基础上继续训练,让模型参数稍微改变,使某类输入更倾向产生某种输出。它不是把新教材“塞进”模型,也不是检索资料,而是用大量「输入 → 期望输出」示例调整模型的输出倾向。
          • 举例:反复给「数据库课程问题 → 三点式、准确、简洁的答案」,模型会更稳定地模仿这种回答习惯——但它仍可能编造事实,也不会自动拥有实时信息。
          • 为什么叫「微」调?因为绝大多数知识在预训练(01.02)已经学完;微调只是把「通用通才」塑造成「某个领域的听话助手」。

          1.1 基座模型 vs 指令模型

          • 语言模型可以理解为一个巨大的「下一词猜测器」:读到「主键不能」后,根据训练中见过的大量文字给每个可能的下一个 token 打分,连续重复就形成一句回答。
          • 基础模型(Base Model):在通用文本上训练出的通才——能续写,但不一定“听话”。
          • 指令模型(Instruct Model):在通才基础上学习了「听从用户问题、以对话格式回答」的版本(如 Qwen2.5-Instruct)。
          • 微调做的正是在这两者之间的再塑形:让某个领域的输入稳定产出期望输出。

          2. 为什么需要微调:三条路线的取舍

          拿到一个任务,先别急着训练。有三条路线,各自解决不同问题:

          路线 做什么 适合场景 代价/局限
          提示词(Prompt) 在输入里写清要求与少量示例 任务数量少、规则可描述 长 prompt 占上下文、能力有限
          RAG(检索增强) 从外部库检索资料拼进上下文 知识频繁变化、需引用原文 检索质量决定上限,有延迟
          微调(Fine-tuning) 用示例改变模型参数 行为/格式/术语风格需稳定变化 需高质量数据,有成本
          • 微调适合:行为、格式、术语风格需要稳定变化,且有高质量示例的问题。例如“课程助教用三点式回答”。
          • 不适合:知识频繁变化(应 RAG)、必须逐条引用原文(应 RAG)、提示词已能满足且数量很少(不必训练)。
          • 一句话决策:微调改变“怎么答”,RAG 提供“答什么”,提示词规定“这一问怎么答”。工程上常组合使用。

          3. 项目范围:做什么,不做什么

          • 本系列项目:把 Qwen/Qwen2.5-0.5B-Instruct 适配成「课程助教」——根据给定课程资料回答问题,答不出来时明确说不知道。
          • 它是练习模型,不可用于高风险决策。
          • 动手前先在 Hugging Face 模型页查看:许可证、语言支持、显存要求、使用限制。模型能下载不表示可任意商用或再发布(呼应 01.02 第 2 章的数据许可纪律)。

          4. 为什么必须先建立基线

          • 若没有「改前成绩」,你无法判断微调是否真的有用。模型微调后回答变长、语气更自信,不代表更正确——它可能只是记住了训练问题。
          • 基线要求:固定问题、固定 system prompt、固定生成参数(如 do_sample=False),这样唯一变量才是模型本身。
          flowchart LR
 A[冻结的评测问题] --> B[原模型基线]
 C[审核过的训练示例] --> D[微调 adapter]
 D --> E[同一评测问题]
 B --> F[逐条比较]
 E --> F
 F --> G[保留、改数据或放弃]

          5. 动手:建立项目与运行基线

          在上一阶段的 minigpt-course 根目录执行(仍需激活 .venv):

          mkdir -p finetune/{data,configs,src,runs,reports,eval}
pip install "transformers>=4.45" datasets accelerate peft trl
          bash

          Windows PowerShell 用 mkdir finetune/data, finetune/configs, finetune/src, finetune/runs, finetune/reports, finetune/eval。创建 finetune/src/baseline.py:

          from transformers import pipeline
model_id = "Qwen/Qwen2.5-0.5B-Instruct"
pipe = pipeline("text-generation", model=model_id, device_map="auto")
messages = [{"role":"system","content":"你是课程助教。没有依据时说不知道。"}, {"role":"user","content":"什么是主键？"}]
print(pipe(messages, max_new_tokens=160, do_sample=False)[0]["generated_text"][-1]["content"])
          python

          运行 python -m finetune.src.baseline。首次会下载模型;若内存不足,改用更小模型或云端 GPU,不要通过删除错误信息假装成功。将完整问题、模型 ID、生成参数、原始回答写进 finetune/reports/baseline.md。

          5.1 排错速查

          现象 处理 原因
          401/403 阅读模型页访问要求并登录 HF 需先获得访问授权
          CUDA out of memory 用较短输入或更小模型 显存不足;后续章节用 LoRA/QLoRA
          输出 cpu 可继续,训练更慢 正常设备选择

          6. 动手活动:固定基线

          动手活动:固定基线

          目标:完成 baseline.md,建立后续所有微调实验的对照组。

          步骤:

          1. 写 10 条真实课程问题,至少含 2 条资料未覆盖的问题;
          2. 用完全相同 system prompt 和 do_sample=False 运行;
          3. 逐条标记:正确 / 错误 / 无依据 / 格式不符。

          完成标准:报告保留全部输入输出,并写出微调要改善的一个可测目标,例如「10 条中至少 8 条按三点结构回答」。

          7. 总结

          关键判断 一句话
          微调是什么 用示例小幅改变参数,让某类输入稳定产出期望输出
          什么时候该微调 行为/格式/风格需稳定变化且有高质量示例
          什么时候不微调 知识频繁(用 RAG)、提示词已够(不训)
          基线为什么重要 没有改前成绩,无法证明训练有效

          思考题:为什么「微调后回答更自信」不能作为成功证据?基线记录为什么必须包含生成参数?

          参考答案

          更自信可能只是模仿了训练数据的语气,不代表事实正确;没有固定生成参数,输出差异可能来自采样随机性而非模型变化。基线用 do_sample=False 就是为了排除随机性,让唯一变量是模型本身。
