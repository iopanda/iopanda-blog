          01.04.06

          压测与容量规划

          2026-09-02 · iopanda

          • course
          • model-deployment
          • load-testing

          上一章验证了 API「能答对」,本章回答「能扛住多少」:用受控请求测量服务,而不是凭单次体验估计并发能力。你会先弄清并发、吞吐、分位数延迟与失败率各回答什么问题、为什么平均值会骗人,再按「单变量、逐步加压、档间恢复」的方法论跑三档小压测,最后从实测证据推出一个保守的容量上限,并认清哪些边界不可逾越。

          学习目标:学完本章,你将能够——

          1. 说出并发、吞吐、P50/P95 延迟与失败率的定义,以及每个指标回答什么问题;
          2. 解释为什么平均延迟会骗人,为什么体验目标要用分位数表达;
          3. 说明「单变量、逐步加压、档间恢复」的压测方法论及其理由;
          4. 在本机 API 上运行小规模压测,并完整记录负载条件;
          5. 从实测证据推导保守的容量上限并给出依据;
          6. 遵守压测边界:只测自己的服务,不碰未获授权的目标。

          1. 概念:四个指标,各回答一个问题

          压测报告里最常见的四个数字,分别回答四个不同的问题,先对齐定义:

          指标 定义 回答的问题
          并发(concurrency) 同一时刻已发出但尚未收到响应的请求数 「同时有多少请求在途」
          吞吐(throughput) 每秒完成的请求数(requests/s) 「单位时间能消化多少请求」
          P50 / P95 延迟 把一次压测的所有延迟排序,P50 是中位数,P95 是「95% 的请求都不超过」的延迟 「用户实际要等多久」
          失败率(failure rate) 非 2xx 响应数 ÷ 总请求数 「多少请求根本没得到好结果」
          • 并发是你施加的压力,不是结果:把并发从 1 提到 10,只是同时放进 10 个在途请求;系统随后表现出什么延迟、什么吞吐,才是被测对象。并发数字必须写进报告,否则结果无法复现。
          • 吞吐回答产能,延迟回答体验:吞吐高只说明「单位时间完成得多」,不说明「单个用户等得久不久」。一个批处理式系统可以吞吐很高而每个请求都很慢——两个指标必须分开看。
          • P50/P95 描述体验分布:P50 是典型用户感受(一半请求比它快);P95 描述尾部——最慢的 5% 用户等了多久。P95 达标意味着 95% 的用户体验在目标内;想承诺「几乎所有人都不超过 X ms」,就要盯 P99。
          • 失败率是底线指标:任何压测结论都必须同时报告失败率。若某档并发下 20% 请求返回 503 或超时,那这一档的 P95 再好看也没有意义——它只是「活下来的请求」的延迟。
          • 失败也要分类记录:超时、连接拒绝与 5xx 含义不同——503 是服务明确拒绝,超时可能是排队太久或网络问题。只记一个「失败数」会丢掉定位线索。

          1.1 在 LLM 服务里,这些指标长什么样

          • 生成式推理是两阶段的(见 01 推理基础):prefill 处理整段提示、产出第一个 token,决定 TTFT(用户看到第一个字要等多久);decode 逐 token 生成,决定整段回答的总时长。一次 HTTP 请求的总延迟 ≈ TTFT + 逐 token 时间 × 输出长度。
          • 因此压测 /ask 时,提示越长、max_tokens 越大,每个请求占用 GPU 与 KV cache 的时间就越久,能测出的 requests/s 就越低。报告吞吐时必须同时写清输入提示长度与输出上限,否则同一个服务的两个数字无法比较。
          • 若工具支持,可把「每秒生成 token 数(tokens/s)」一并记录:它在输出长度不同的两档压测之间,比 requests/s 更能反映模型本身的产能。

          2. 为什么平均值会骗人

          • 平均延迟(mean)把所有请求的延迟加总再平分,少数极端慢的请求就能把均值拉高——而它们往往正是排队、重试或资源竞争的产物,不代表典型体验。
          • 一个直觉例子:10 个请求里 9 个耗时 100 ms,1 个耗时 10 s。平均值 ≈ 1.09 s,看起来「平均一秒多」;但 P50 是 100 ms(典型用户很快),而 P95 是 10 s(最慢的 10% 用户等了整整 10 秒)。三个数字讲的是三个故事,平均值那个最容易误导决策。
          • 更糟的是,负载下的延迟常呈长尾分布:请求进队列要等、GPU 上前一个长输出未结束、KV cache 换出……这些偶发事件制造长尾。均值把长尾摊进每个请求,让「本可以很快」的服务看起来「普遍很慢」;反之,个别慢请求也可能被大量快请求稀释得无影无踪。
          • 因此体验目标(以及告警、SLO)应当用分位数表达,例如「P95 ≤ 2 s、失败率 < 1%」;平均值最多作为参考,不作为承诺。
          • 均值对告警同样不友好:尾部劣化(某几秒内涌入大量慢请求)对均值影响小、变化平缓,等均值明显抬升时问题往往已持续很久;P95/P99 能在尾部一劣化就触发告警。

          3. 为什么需要压测:单次体验不等于负载能力

          • 一个 curl 成功只证明「功能通」,不证明「扛得住」。上一章的 /ask 单人试用时一切正常;当并发上升,请求开始争用同一批资源——GPU 算力、KV cache(见 01 推理基础)、CPU 与网络带宽。
          • 排队效应是核心原因:服务忙碌时把新请求排进队列。队列理论的一个朴素结论是——利用率越接近 100%,排队时间增长得越快,延迟在系统「看起来还没满」时就先起飞。所以不能靠「感觉不太忙」推断容量。
          • 更精确地说:当到达率逼近服务率,队列会失控。请求到达速度一旦接近服务的处理速度,队列越积越长,延迟失去上限,直到请求超时或被服务拒绝(503)——这就是「感觉还没满、其实已饱和」的机制。
          • 不压测的代价:容量上限只能靠猜,上线后第一个真实峰值就可能打穿服务,用户看到超时与 503,你只能事后从日志反推。受控压测把「猜」提前到上线之前,成本只是一次本机测量。
          • 压测就是把「负载 → 延迟 / 吞吐 / 失败率」的曲线测量出来:它不改进性能,只提供决策数字。容量上限、要不要限流、要不要扩容,都应当由这条曲线决定,而不是由「模型参数多不多」决定。

          4. 压测方法论:单变量、逐步加压、档间恢复

          • 单变量:一次只改一个变量。想测并发,就固定模型、硬件、提示长度、最大输出与版本,只改 -c;同时改两个变量,结果出问题时无法归因。
          • 逐步加压:从 c=1 开始,依次 c=2、c=4……观察延迟与失败率从哪一档开始劣化。逐步加压才能找到「拐点」——拐点之前的并发,就是容量上限的候选。
          • 档间恢复:每档之间让机器恢复——等队列排空、显存回落、进程稳定后再跑下一档。若连续加压,上一档堆积的排队会污染下一档的读数,整条曲线失真。
          • 并发翻倍 ≠ 吞吐翻倍:资源饱和前,吞吐随并发上升而上升;饱和后吞吐基本走平,延迟却继续恶化。看到「吞吐不再涨、延迟开始涨」的档位,就是饱和点——这是容量决策最有用的一张图。
          • 完整记录负载条件:压测结果只在「模型、硬件、提示长度、最大输出、版本和并发均相同」的条件下有效。每档必须记录:总数、成功数、平均、P95、requests/s、模型输出限制与峰值显存。缺了条件的数字无法对比、无法复现,等于没测。
          • 小规模起步:先跑 2040 个请求、并发 14,验证工具与读数可靠,再决定是否加大;不要在没弄清工具输出前就发起大流量。同一档可重复一两次取稳定读数,避免单次运行的抖动被当成趋势。

          5. 动手:运行安全的小压测

          前置:按 04、05 章启动 vLLM 与 FastAPI 服务(监听 127.0.0.1:8080)。压测只对自己的本机服务执行。hey 可通过包管理器或官方发布页安装;若 pip install hey 不可靠,使用 ApacheBench 或组织批准的工具。以下以 hey 为例:

          开压前先 curl http://127.0.0.1:8080/health 确认服务就绪;压测进行中可在另一终端用 nvidia-smi 观察显存,把峰值记进报告(无 GPU 的环境如实写「不适用」,与 03 章的做法一致)。

          hey -n 20 -c 1 -m POST -H 'Content-Type: application/json' -d '{"question":"什么是主键？"}' http://127.0.0.1:8080/ask
hey -n 40 -c 2 -m POST -H 'Content-Type: application/json' -d '{"question":"什么是主键？"}' http://127.0.0.1:8080/ask
          bash

          先做 c=1,再做 c=2、c=4,每档之间让机器恢复。每档记录总数、成功数、平均、P95、requests/s、模型输出限制与峰值显存;若出现非 2xx,把状态码一并记下。

          hey 的输出分四块读:Summary 给出总数与耗时;Status code distribution 出现非 200 即失败请求;Latency distribution 给出 50%/95%/99% 等分位延迟;Requests/sec 即吞吐。把四块数字抄进报告,不要只抄第一行。

          若 c=2 就出现 503 或超时:先回到 c=1 确认基线读数正常,再检查 vLLM 是否就绪、max_tokens 是否过大;不要直接跳到更大并发去「试运气」——低档失败通常意味着环境问题,而不是容量问题。

          动手活动:容量建议

          目标:完成 reports/load-test.md,给出一条基于证据的容量建议。

          步骤:三档并发各运行一次;原样粘贴工具摘要;画表记录 P50/P95、吞吐、失败率。

          完成标准:给出一个保守最大并发及依据,例如「c=2 时 P95 满足目标、c=4 出现 503,因此当前限制为 2」。

          6. 容量规划:从证据定上限

          • 容量上限 = 「体验目标仍成立」的最高实测档位。先定义目标(如 P95 ≤ 2 s、失败率 = 0),再逐档对照;目标成立的最大并发,就是当前配置下的保守上限。
          • 读数的顺序很重要:失败率先看,延迟后看。c=4 出现 503,说明已越过实际容量——503(见 05 章的状态码语义)是服务在明确说「我不行了」,这一档的延迟数字已无意义。503 或超时出现的那一档,通常就是上限的邻居。
          • 用整条曲线下结论,而不是孤立的单档数字:例如三档实测为——c=1:P50 80 ms / P95 120 ms / 11 req/s;c=2:P50 150 ms / P95 300 ms / 19 req/s;c=4:P50 700 ms / P95 2.4 s,且出现 503。若体验目标是 P95 ≤ 1 s,则 c=4 不合格;c=2 离目标还有余量,但距离 c=4 的崩溃只有一倍并发,建议值取 2 并写明依据。
          • 上限要保守:真实流量不会像压测一样均匀——用户请求有长有短、有突发。应取「达标档位」而非「崩溃前一档」作为建议值,并写明该数字依赖的负载条件。
          • 变坏时先查三层,再谈硬件:①排队(并发是否已超服务能力);②输出长度与 max_tokens(长输出占用 GPU 与 KV cache 更久);③KV cache 与显存(是否已触发换出)。这三层查完,才轮到「加机器、换模型」这类扩容讨论。
          • 上限要变成配置才算落地:得出保守上限后,把它转成限流与告警阈值(见 07 章),例如「并发超过 2 时排队或返回 429」;否则报告里的数字不会自动保护服务。
          • 容量不是模型参数量的别名,而是特定负载下的实测结论:同一个模型,短问答与长文生成的容量可能差一个数量级;报告必须写清是在什么输入形状下测得的。

          7. 压测的边界:只测自己的服务

          • 本章的压测目标只有一个:你在 127.0.0.1:8080 上的自己的服务。不要对未获授权的公共 API 或生产服务压测——那是在消耗别人的算力与稳定性,可能违反服务条款甚至法律;对生产环境压测也必须有授权窗口与回滚预案。这与 05 章的边界是同一纪律:演示服务无认证、无限流,本就不该暴露公网,压测同样只在自家院子里进行。
          • 边界还包括「结论的范围」:压测只证明被测服务在给定条件下的表现,不证明别的机器、别的负载形状、别家的模型也如此。不要把一个数字外推到它没被测量过的场景。
          • 突发与稳定是两种负载:hey 的固定并发是稳定负载,真实流量常有突发(瞬间到达的请求峰);上文「上限要保守、取达标档位」的建议,正是为突发预留缓冲。
          • 没有依据不下结论:若某档因环境限制未能测得,如实写「未测得」,不要用低档数据外推高档表现;边界的另一面是诚实。
          • 最后记住压测的定位:它是测量,不是修复。发现 P95 劣化,价值在于给你一张「在哪一档、因什么而坏」的地图;如何封装、监控与改进,是下一章与后续优化的事。

          8. 总结

          关键问题 一句话

          思考题:为什么「平均延迟 300 ms」不能作为体验承诺?为什么 c=4 出现 503 时,这一档的 P95 不再值得报告?同一个模型,为什么短问答与长文生成的容量可能差一个数量级?

          参考答案

          平均值会被少数长尾请求拉偏,可能掩盖「典型用户很快、最慢 5% 极慢」的真实分布,承诺必须用 P95/P99 等分位数表达。503 表示服务已明确拒绝或过载,「活下来的请求」的延迟不能代表系统在该负载下的真实体验,所以要先看失败率、再看延迟。长输出占用 GPU 计算与 KV cache 的时间随序列长度增长,单位时间能服务的请求数随之下降;容量是「特定输入形状下的实测结论」,不是固定数字。
