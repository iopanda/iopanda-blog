          01.04.01

          推理基础

          2026-09-02 · iopanda

          • course
          • model-inference
          • performance

          本章是 01.04 Inference and Deployment 的开篇,承接 01.03 微调收官项目里选定的模型。动手前先想清楚三件事:推理和训练有什么本质不同、一次生成内部为什么分两段、为什么必须先给「能跑的模型」测出性能基线。读完你会带着一份可比较的 baseline 进入后续 6 章(生成参数、量化、vLLM、API、压测、部署),而不是凭感觉判断快慢。

          学习目标:学完本章,你将能够——

          1. 说出推理与训练的本质差异,解释「训练 loss 下降」不等于「用户觉得快」;
          2. 拆解生成的 prefill 与 decode 两阶段,说明为什么必须分两段、各自决定什么体验;
          3. 读懂 TTFT、TPOT、tokens/s、总延迟、显存等指标,知道每个指标该看哪个;
          4. 解释 KV cache 的原理、收益与代价,并估算它对显存的影响;
          5. 用固定提示词与生成参数测量并记录可比较的性能基线。

          1. 推理 vs 训练:两件相反的事

          • 上一单元(01.03)结束于微调,那是训练:拿着大量样本反复前向+反向传播,花数小时把权重调好。评价看 loss、准确率,时间单位是分钟到天。
          • 本章起是推理(服务):模型参数已经固定,每次请求只做一次前向,在几十毫秒到几秒内产出一段回答。评价标准变成「多久开始回答、每秒吐几个字、几个人同时用会不会变慢」——这些正是本章要建立的基线。
          • 两者常被混淆:微调完跑通一次 demo 就以为「能服务了」。但 demo 里没人计时、没并发、输入短。能生成 ≠ 够快:性能是服务的第一属性,与正确性并列,没有基线就无从谈起。
          维度 训练 推理
          参数 不断更新 冻结不变
          计算方向 前向 + 反向传播 只有前向
          时长尺度 分钟~天 毫秒~秒
          随机性 dropout 等正则 仅可选采样
          评价指标 loss、评测分数 延迟、吞吐、显存
          关心的问题 「学没学会」 「多快、能扛多少人」

          2. 为什么必须先建性能基线

          • 若没有「改前成绩」,后面任何改动都无法归因:模型换成量化版(03 章)、换成 vLLM(04 章)、加上并发(06 章)之后「感觉快了/慢了」,你无法判断是哪个因素、快了多少。没有数字的优化汇报等于没优化。
          • 基线不是随便跑一次:要固定问题、固定 system prompt、固定生成参数(如 do_sample=False)、固定设备与输入长度,保证唯一变量是被测对象。这与 01.03 第 1 章的基线纪律同源——那边固定模型比数据,这里固定数据比性能。
          • 记录要完整可复现:模型 ID(含精确版本)、设备、输入 token 数、生成 token 数、总秒数、tokens/s、峰值显存、机器与日期。一周后的你或另一位同学拿到记录,要能复现同一测量。
          • 本章把结果写进 reports/inference-baseline.md,它就是后续每章优化实验的对照组:任何改动后的数字,都必须回到同一份提示词、同一个测量脚本上比较。

          3. 生成为什么分两段:prefill 与 decode

          解码器模型每步只能预测「下一个 token」,但一次请求往往有几百到几千个输入 token。把输入一次性并行读完、再逐个往外吐,天然形成两个阶段:

          3.1 prefill(预填充):读题

          • 模型把整个提示词(全部输入 token)一次性并行前向,算出每个 token 的隐状态与注意力 Key/Value,并顺势产出第一个新 token。
          • 因为是并行处理,prefill 是计算密集型(compute-bound),瓶颈在算力;耗时大致随输入长度线性增长,与输出长度无关。
          • 它决定 TTFT(首 token 延迟):用户发出问题后「多久开始有回应」。长文档、长 prompt 变慢,主要慢在这一段。

          3.2 decode(解码):逐字作答

          • 拿到第一个新 token 后,模型把它接到序列末尾再前向一次得到第二个……如此循环,一次只推一个 token,直到遇到结束符或达到 max_new_tokens。
          • 每步虽只算一个新 token,却要把所有权重和全部历史过一遍,读取量远大于计算量,所以 decode 是访存带宽密集型(memory-bound);速度几乎与输入多长无关,只取决于显存带宽与缓存规模。
          • 它决定 tokens/s(生成速度):输出 128 个 token 的任务,总时间几乎全部花在这一段。
          对比 prefill decode
          一次处理 整个输入并行 每次 1 个新 token
          瓶颈 算力(compute-bound) 显存带宽(memory-bound)
          决定的指标 TTFT tokens/s(TPOT)
          随输入长度 近似线性变慢 几乎不变(有 KV cache 时)
          用户感受 「有没有立刻回应」 「回答流不流畅」

          4. 指标表:服务性能看什么

          用户不关心 loss,他们只感受到五个数字——本章把它们全部测出来:

          指标 含义 由哪段决定 用户感受
          TTFT 请求发出到第一个输出 token 的耗时 prefill 「是否立刻有回应」
          TPOT 每个输出 token 的平均耗时(= 1 ÷ tokens/s) decode 「每个字等多久」
          tokens/s 每秒生成的 token 数 decode 「回答是否流畅」
          总延迟 请求开始到生成结束 prefill + decode 之和 「一次任务等多久」
          显存峰值 服务占用显存上限 权重 + KV cache + 激活 「能承受多长输入、多少并发」
          • 五个指标不是孤立的:总延迟 ≈ TTFT + 输出 token 数 × TPOT(≈ TTFT + 输出数 ÷ tokens/s)。有了 baseline 的 TTFT 与 tokens/s,你就能预测任意长度任务的耗时,也能在改动后反推「慢的部分出在 prefill 还是 decode」——这正是基线最大的实用价值。
          • 注意区分单请求视角与系统视角:TTFT、tokens/s 描述单个用户体感;系统能扛多少并发、总吞吐多少,要等 06 章压测。先量准单请求,才有资格谈并发。
          • 经验提醒:短输出任务(如打标签)用户几乎只感知 TTFT;长输出任务(如写文章)感知的是 tokens/s;若两端都慢,才需要分别排查 prefill 与 decode 两段。

          5. KV cache:用显存换掉重复计算

          • 是什么:decode 每推一个新 token,注意力都要与「前面所有 token」比较。若每步都重算历史的 Key/Value,第 n 步的代价随 n 增长,整段输出成本退化为 O(长度²),越写越慢。KV cache 就是 prefill 时把各层算出的 Key/Value 存进显存,之后每步只追加新 token 的 K/V、直接复用历史。
          • 为什么需要:没有它,decode 每一步都要重算整段历史,128 个输出 token 的任务可能慢一个数量级;有了它,每步成本与已生成长度基本解耦,decode 才能维持近似恒定的速度。
          • 换什么代价:显存。每多缓存 1 个 token 约需 2(K 与 V)× 层数 × KV 头数 × 头维度 × 每元素字节。以本项目 Qwen2.5-0.5B(24 层、2 个 KV 头、head_dim 64、BF16 2 字节)为例:每 token ≈ 2×24×2×64×2 ≈ 12 KB;8K 输出的单请求缓存 ≈ 100 MB,顶满 32K 上下文则逼近 400 MB——长输入与并发各自把缓存成倍放大,这正是服务端 OOM 最常见的来源(见第 7 节排错)。
          • 缓解方向早已埋在线索里:分组查询注意力(GQA)用少数 KV 头共享缓存,正是 Qwen2.5 把 KV 头压到 2~8 个的原因(呼应 01.01 架构章节);03 章量化、04 章 vLLM 的 PagedAttention 还会继续在缓存上做文章。
          • 想亲眼看到缓存的收益,把下面测量脚本里的 use_cache=True 改成 False 再测一次:tokens/s 会随输出变长一路下滑,输出越长对比越悬殊——「缓存换显存、显存换速度」的取舍就变成了你手上的数字。

          6. 动手:先做一个可重复的本地测量

          在上一阶段的 minigpt-course 根目录执行(仍需激活 .venv),创建 finetune/src/measure_generate.py,在已有 generate.py 加载模型后使用:

          import time, torch
prompt = "请用三点解释什么是主键。"
ids = torch.tensor([tokenizer.apply_chat_template(
    [{"role":"user","content":prompt}], tokenize=True, add_generation_prompt=True)], device=device)
torch.manual_seed(42); start = time.perf_counter()
with torch.no_grad():
    output = model.generate(ids, max_new_tokens=128, do_sample=False, use_cache=True)
elapsed = time.perf_counter() - start
new_tokens = output.shape[1] - ids.shape[1]
print({"input_tokens": ids.shape[1], "new_tokens": new_tokens,
       "seconds": round(elapsed, 3), "tokens_per_second": round(new_tokens/elapsed, 2)})
          python

          运行三次 python -m finetune.src.measure_generate,丢弃第一次下载/预热造成的异常值,记录其余三次的中位数到 reports/inference-baseline.md。如果有 NVIDIA GPU,同时在另一个终端运行 nvidia-smi -l 1 记录峰值显存;没有 GPU 就记录 CPU 与内存,不编造显存数据。

          对照第 4 节的公式解读两次测量:32 个新 token 的耗时里 prefill(读题)占比很高,主要反映 TTFT;128 个新 token 的耗时里 decode 占绝对多数,算出的 tokens/s 才是「流畅度」的真实数字。两次都做,才能把两段分开看。

          动手活动：性能基线

          目标：inference-baseline.md。步骤：对 32、128 个新 token 各测 3 次；记录模型 ID、设备、输入 token、总时间、tokens/s 和显存。完成标准：能说明短输出与长输出分别主要受 TTFT 或 decode 影响，并保留原始数字。

          7. 总结与排错

          关键判断 一句话
          推理 vs 训练 训练改参数,推理用固定参数换延迟与吞吐
          为什么分两段 prefill 并行读题决定 TTFT,decode 逐字作答决定 tokens/s
          KV cache 本质 缓存历史 K/V,用显存换掉 O(长度²) 的重复计算
          基线为什么重要 没有改前成绩,后续任何优化都无法归因
          • 首次很慢通常是权重加载或 GPU 预热,不能计入常态;OOM 常由长上下文或并发的 KV cache 引起,不能只看模型文件大小。后续所有优化都必须回到本章相同提示词和测量方法比较。

          思考题:为什么训练时几乎没人提 KV cache,推理时它却成了显存大头?「输出 128 个 token 很快」能不能证明服务已经足够快?

          参考答案

          训练时每个 batch 都要反向传播、历史表示本来就会重算,缓存没有意义;推理是自回归逐 token 生成、历史只读不复算,缓存收益才凸显。单请求快只代表延迟好,不代表高并发下不 OOM、不排队——那需要显存记录与压测证据,见 06 章。
