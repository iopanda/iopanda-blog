          01.04.04

          本地推理与 vLLM

          2026-09-02 · iopanda

          • course
          • model-inference
          • vllm

          前几章回答了「用哪个模型、怎么让它装得下跑得动」,本章回答「怎么让别人用起来」:把一个常驻内存的模型进程包装成网络服务——任何会发 HTTP 请求的程序(网页、命令行、另一个服务)都能调用,而不必读懂 Python、不必和你在同一台机器上。你会先弄清为什么脚本直调不够、朴素服务又慢在哪,再看 vLLM 用连续批处理与 PagedAttention 分别解决什么,最后亲手把它启动成 OpenAI 兼容的 /v1/chat/completions 端点,用 curl 完成冒烟验收,并用 host/port 守住「只在本机暴露」的安全边界。

          学习目标:学完本章,你将能够——

          1. 对比脚本直调与 HTTP 服务,说出服务化解决什么问题、引入什么代价;
          2. 解释朴素推理服务吞吐低的两大根源:串行/静态批处理与 KV cache 显存浪费;
          3. 说出 vLLM 的三项关键设计——连续批处理、PagedAttention、KV cache 管理——各解决哪个瓶颈;
          4. 读懂 OpenAI 兼容协议的请求与响应结构,说明「兼容」为什么值钱;
          5. 区分 127.0.0.1 与 0.0.0.0 的安全边界,判断练习与部署时该监听哪里;
          6. 启动 vLLM,用 curl 调用 /v1/chat/completions,完成服务连通性验收。

          1. 概念:为什么需要服务化:脚本 vs HTTP 服务

          • 上一阶段(01.03)的基线脚本把模型当进程内对象用:加载权重、generate、打印、退出。这条路对「自己跑一次评测」够用,但对「别人要用模型」处处是墙:调用方必须会 Python、装同一套依赖、能访问同一台机器与同一份权重文件,而且一次只能一个人跑——另一个人想用,得等你退出释放显存。
          • 每次脚本运行还要冷启动:重新下载/读盘权重、重新建 CUDA 上下文,几十秒里 GPU 只做搬运不做推理;而服务把模型加载一次、常驻内存,之后每个请求只花推理本身的时间。
          • 服务化(serving)的本质,是把「函数调用」升级成「网络接口」:模型进程监听一个端口,按 HTTP 请求应答。调用方只需要会发请求、会解析 JSON——语言无关、位置无关。这个「包装成服务」的动作,就是推理与部署的分水岭:
          维度 脚本直调 HTTP 服务
          谁可以调用 写脚本的人/同一进程 任何会发 HTTP 的客户端(curl、网页、别的服务)
          模型加载 每次运行重新加载 一次加载常驻,请求即答
          并发 无(独占进程) 可排队、可批处理、可多客户端
          调用方门槛 要懂 Python 与模型代码 只懂 URL + JSON
          生命周期与风险 用完即走,无监听面 进程常驻,多了端口=多了攻击面与运维义务
          • 代价要诚实:服务常驻占显存;多了一个监听端口就多了一个被攻击的入口;要处理启动/停止/崩溃/占用;并发请求来了还要有调度策略——这些正是本章与 05~07 章的主题。还要认清:服务 ≠ 产品。服务只解决「可被网络调用」,输入校验、鉴权、限流、健康检查都是后续章节的活,本章先不过界。

          2. 概念:朴素服务为什么慢:串行、静态批处理与 KV cache

          • 自回归解码每步只产出一个 token(01 章讲过 prefill/decode 两阶段):prefill 一次性并行处理整段 prompt,吞吐很高;decode 每步只算一个 token,GPU 大量时间花在搬运权重与 KV cache上而非计算。一个用户独占 GPU 时,大部分算力在空转。
          • 直觉解法是批处理:把多个请求拼成一个 batch,一次前向同时推进。但朴素实现是静态批处理——一批请求必须等最慢的那个全部生成完才整体结束,先完成的请求只能占着坑空等;而且为了省事常按「最大可能长度」预留资源。结果:批越大,尾部空等与资源浪费越严重。
          • 为什么请求之间的资源无法简单共享?因为每个请求都要缓存自己历史的 KV cache(01 章定义过:为避免每步重算历史 token 的注意力键值,把 K/V 张量存进显存)。它随序列长度线性增长:论文以 13B 级模型为例,FP16 下每 token 的 K/V 约 0.78 MB,一条 2048 token 的对话就要约 1.6 GB。多路并发 + 长上下文时,KV cache 总量会迅速逼近甚至超过权重本身的占用,成为显存里最大的「活账」。
          • 更糟的是管理方式:朴素 serving 常按请求一次性预分配整块连续显存(按 max_len 预留),而请求实际长度可能只有预留的几分之一——论文测量显示,这类方案下 60%~80% 的 KV cache 显存被过度预留与碎片浪费,平均只有约两成空间真正存放 token 状态。显存被浪费 → 能并发的请求变少 → 吞吐上不去。
          • 一句话:LLM 服务的吞吐瓶颈主要不在算力,而在「KV cache 怎么存、请求怎么调度」。这两个问题,正是 vLLM 的出发点。

          3. 概念:vLLM 的三个答案

          vLLM 是加州大学伯克利分校开源的 LLM 推理与服务引擎(PagedAttention 论文,ACM SOSP 2023),vllm serve 一行命令即可把 Hugging Face 模型变成 HTTP 服务。它并不改变模型本身——同样的权重,靠工程把 GPU 用得更满:

          vLLM 设计 解决的瓶颈 机制 效果
          连续批处理 静态批处理的尾部空等 以「每一步」为调度单位:每步结束,完成的请求立刻离场、新请求立刻入列(prefill 也可与 decode 混跑) 批大小不再被最慢请求钉死,吞吐显著上升
          PagedAttention KV cache 的预分配浪费与碎片 把 KV cache 切成固定大小块(默认 16 token/块),按需分配,块表映射逻辑→物理位置,如同操作系统虚拟内存分页 显存浪费从 60%~80% 压到 4% 以下,同样显存能容纳更多并发
          KV cache 管理 显存总账与长上下文 用 max-model-len、gpu-memory-utilization 等参数控制权重、KV cache 与激活值的分配;支持前缀缓存等进阶优化 显存预算可预期、可调参
          • 连续批处理(continuous batching / in-flight batching):思路源自 Orca 等 serving 系统,关键是把调度粒度从「请求」细化到「迭代」。传统做法像火车站整列整列发车,先到齐再走;连续批处理像地铁——每站都有上下的。请求到达速度不均、生成长短不一时,GPU 每一刻都在处理「当下确实能推进的集合」,空闲趋近于零。注意它牺牲不了单请求延迟:它不加快任何一条请求,而是让同一块 GPU 同时服务更多人。
          • PagedAttention:注意力计算时按块表去读散落的 KV 块,逻辑上仍是连续序列。省下的显存直接变成更大的有效批大小,论文报告:与当时最先进的 serving 系统(FasterTransformer、Orca)相比,相同延迟下吞吐提升 2~4 倍;相对「一次一条、无调度」的朴素 Transformers 服务,发布基准中最高约 24 倍。附带红利:并行采样(n 个输出)或 beam search 时,多条序列共享同一段 prompt 的 KV 块(写时复制),内存进一步复用。
          • 这两项设计都发生在引擎内部:你看到的仍是「发请求、收 JSON」。这也提醒我们:调服务参数(批大小、显存利用率)属于容量规划的活(06 章),本章先把「能跑、能调、边界安全」做扎实。

          4. 概念:OpenAI 兼容协议:为什么「兼容」值钱

          • vLLM 默认提供 OpenAI 兼容接口:/v1/chat/completions、/v1/models。OpenAI 的 Chat Completions 事实上成了大模型服务的通用语:成千上万的框架与工具(LangChain、Open WebUI、各类 SDK)已经会说这门语言。你的本地服务讲同一门语言,意味着这些工具零改动就能指向它,也意味着代码可以在「本地 vLLM ↔ 云端 OpenAI」之间原样切换——模型可换,协议不变。这就是「兼容」的工程价值:买的是生态与可移植性。
          • 一次 chat 请求就是一份 HTTP 文档,拆开看四部分:
          组成 本例取值 含义
          方法 POST 提交数据、请求生成
          URL http://127.0.0.1:8000/v1/chat/completions 服务地址 + 接口路径
          请求头 Content-Type: application/json 声明 body 是 JSON
          body model、messages、temperature、max_tokens messages 是 role+content 数组;temperature:0 表示贪心确定(02 章);max_tokens 设输出上限
          • 响应同样有约定俗成的结构:顶层含 id、object、created、model、choices、usage;正文在 choices[0].message.content;usage 给出 prompt_tokens / completion_tokens / total_tokens——每次调用把这三个数记下来,它们是 06 章容量规划的第一手证据。想要逐 token 输出可加 stream:true,走 SSE 分块推送,本章不展开。
          • 对开发者还有一个福利:http://127.0.0.1:8000/docs 提供 Swagger 交互页,/v1/models 返回当前已加载的模型列表——后者兼作「进程活着吗」的健康探针。

          5. 概念:host 与 port:你的服务听谁的

          • 服务要回答两个问题:监听哪个网络接口(host)、哪个端口(port)。port 是门牌号(默认 8000,被占用就换一个,curl 里的端口必须与启动参数一致);host 决定这扇门开在哪面墙上:
          host 值 谁能访问 用途
          127.0.0.1(回环) 仅本机 练习与开发默认值,本章用它
          0.0.0.0(所有接口) 局域网、容器网络;若机器有公网映射则等于全网 生产网关后的服务,须先有认证/TLS 等保护
          具体局域网 IP(如 192.168.x.x) 该网段 受信内网专用
          • vLLM 默认不带认证:谁连得上谁就能免费跑你的 GPU、读你发出的每一段 prompt。把无认证的 0.0.0.0 暴露到公网,等于把算力账单与隐私一起开门迎客。安全边界一句话:练习永远 127.0.0.1;要对外,先有 05~07 章讲的鉴权、限流与网关。Ctrl+C 停止服务后,端口即释放,可从系统侧确认没有残留监听。
          • 环境前提要认清:vLLM 服务化主要面向 Linux + 受支持的 NVIDIA GPU(官方也提供 CPU、AMD/Intel 等其他后端,以当前官方文档为准)。macOS/Windows 没有原生支持:可在 WSL2、Linux 容器或云 GPU 实例上照做本章命令;实在没有 GPU 环境,也请把 4、5 两节的概念读透——05 章会用跨平台的 FastAPI 复现同一套「服务 + 请求」流程。

          6. 动手:启动 vLLM 并调用

          在支持环境安装 pip install vllm,然后执行:

          vllm serve Qwen/Qwen2.5-0.5B-Instruct --host 127.0.0.1 --port 8000
          bash

          保持该终端运行,在第二个终端执行:

          curl http://127.0.0.1:8000/v1/chat/completions -H 'Content-Type: application/json' -d '{"model":"Qwen/Qwen2.5-0.5B-Instruct","messages":[{"role":"user","content":"什么是主键？"}],"temperature":0,"max_tokens":80}'
          bash

          预期 JSON 包含 choices[0].message.content。浏览 http://127.0.0.1:8000/docs 或调用 /v1/models 确认进程活着。停止服务用运行它的终端按 Ctrl+C,不是关闭整个终端窗口。第一个终端是「服务端」、第二个是「客户端」——请习惯这个双角色视角,后续所有服务类章节都这样工作。

          动手活动:服务连通性验收

          目标:reports/vllm-smoke-test.md。步骤:记录启动命令、模型 ID、端口;保存 /v1/models 和一次 chat 响应;确认 host 为 127.0.0.1。完成标准:新终端能收到 JSON;停止服务后请求失败;报告不含令牌或私密 prompt。

          8. 常见错误与结论

          现象 处理 原因
          Connection refused 先看服务终端日志;确认启动已完成后端口一致 服务未启动、还在加载权重或端口写错
          端口冲突报错 换 --port(curl 同步改)或停掉占用进程 8000 已被其他程序占用
          平台不支持无法启动 WSL2 / Linux 容器 / 云 GPU;或换官方支持的 CPU 后端 vLLM 服务化主要面向 Linux + 受支持 GPU
          显存不足(OOM) 换更小模型或调低上下文上限,不要靠把 host 改成公网地址「解决」 权重与 KV cache 超出显存;监听范围与显存无关
          adapter 加载/本地模型路径问题 以 vLLM 当前官方文档为准 加载方式随版本演进,别信过时教程

          一句话结论:服务化解决「谁都能用」,vLLM 解决「很多人同时用也不至于太慢」,host/port 解决「只有该用的人能用」——三件事分开想,动手时才不会互相甩锅。

          9. 总结

          关键问题 一句话
          为什么服务化 脚本只能被作者调用;服务让任何 HTTP 客户端都能用,代价是常驻与端口风险
          朴素服务慢在哪 decode 算力空转;静态批处理尾部空等;KV cache 预分配浪费 60%~80% 显存
          连续批处理 以迭代为调度单位,完成的走、新来的进,批大小不再被最慢请求钉死
          PagedAttention KV cache 分块按需分配,碎片近零,省下的显存换成并发与吞吐
          OpenAI 兼容为什么值钱 生态与工具零改动可切换,本地与云端代码同构
          host 边界 127.0.0.1 仅本机;无认证的 0.0.0.0 绝不用于对外

          思考题:为什么「脚本能跑通」不等于「服务能用」?连续批处理提高吞吐为什么不以牺牲单请求延迟为代价?把 --host 改成 0.0.0.0 且不加任何保护,会发生什么?冒烟测试为什么用 temperature:0?

          参考答案

          脚本只证明模型与代码正确;服务还要过网络栈、并发与生命周期这三关,任何一关出错客户端都收不到 JSON。连续批处理不改变任何单条请求的 prefill/decode 步数,只是把 GPU 空闲时间填满,所以延迟不变、吞吐上升。0.0.0.0 让服务监听所有网卡,vLLM 默认无认证,局域网乃至公网的人都能免费调用并读取 prompt——训练数据、成本与隐私一起失守。temperature:0 让输出确定(02 章),这样冒烟测试的成败只反映服务连通性,而不是采样运气。
