          回归评测与开发循环

          前五章攒下的家当——02 章的轨迹指标、03 章的黄金任务集、04 章的 LLM 裁判、05 章的 trace——如果只在出问题时才手动跑一遍,价值就少了一大半:Agent 是概率性程序,今天改一行 system prompt「修好」了 g10 的编造,可能明天就把 g03 的等价路径误杀成拒答,这就是经典的「修好一个坏十个」。本章是 02.07 的收尾章,回答模块落地的最后一问:怎么让评测成为开发循环的一部分——每次改动先过 pytest 包装的回归集,绿了才合入;小集快速回归、全量兜底、人工抽检校准,把「敢迭代」从口号变成制度:02.08 组装完整课程助教时,这套循环就是它的安全网。

          学习目标:学完本章,你将能够——

          1. 复述回归评测五步流程(改代码→单测→轨迹评测→人工抽检→记录)与每步防什么;
          2. 解释为什么「小改动也可能坏全局」,以及基线(baseline)对比为什么必须留档;
          3. 用 pytest 把轨迹断言、任务级断言、副作用禁令包装成测试,跑通评测闭环;
          4. 说出成本控制的分级策略(冒烟小集→全量→人工抽检),并用 marker 落地;
          5. 说明 pytest 退出码如何作为 CI 提交门禁,以及报告留档的格式要求。

          1. 概念:每次改动,先过一遍旧试卷

          • 回归评测(regression evaluation):把一套固定的评测集(03 章 golden-tasks.jsonl + 04 章裁判 + 02 章轨迹规则)固化下来,每次改动提示、工具、记忆或模型后原样重跑,与改动前的基线对比——测的不是「这次改得好不好」,而是「有没有把以前好的改坏」。
          • 呼应 02.02 的 01 章:system prompt 一旦被评测就要版本管理、任何改动先过回归再上线——本章把那条纪律工程化:版本对比由脚本完成,不再靠记忆力。
          • 两个关键词:基线(baseline) = 改动前最后一次全绿评测结果,存档备查;回归集 = 覆盖成功/边界/失败三类任务的小而全的任务子集,是防回归的「雷达面」。

          2. 为什么需要:「修好一个坏十个」无处不在

          你改了什么 以为只影响 实际可能波及 哪一档评测能抓到
          system prompt 加「必须可回指讲义」 编造的 g10 g03「先看档案再答」被判成没回指而拒答 任务级关键词断言 + 裁判 tool 维
          工具定义换了参数名 用到它的任务 所有调 search_material 的任务参数错 单测 + 轨迹级参数正确率(02 章)
          修了记忆写入 bug 档案写入 之前所有会话上下文受影响 副作用禁令断言 + 人工抽检
          升级模型 速度与成本 拒答规则、格式遵循全面漂移 全量回归 + 04 章人工抽检一致率重测
          • Agent 的改动是牵一发动全身:提示、工具、记忆、模型四个旋钮互相咬合,单测只证明「每个零件单独没坏」,证明不了「组装起来没坏」——组装层正是回归集的地盘;
          • 概率性输出让「看起来没问题」不可信:一次手测通过可能是运气;只有同一评测集反复跑、跑出稳定的绿,才算数——这正是「敢迭代」的制度保障(02.08 的 01 章把这句评价写进了模块衔接)。

          3. 作用:把评测接进开发循环

          改代码/提示/工具 ──> ① 单测(秒级,零件级)
                      │ 过了?
                      ├─否→ 回去改
                      ▼ 是
                  ② 冒烟回归(分钟级,3~5 条黄金任务,提交门禁)
                      │ 过了?
                      ├─否→ 定位:哪条任务红了 → 05 章 trace 重放
                      ▼ 是
                  ③ 全量回归 + 裁判(小时级,夜间跑)
                      │
                  ④ 人工抽检 10~30%(04 章一致率口径)
                      ▼
                  ⑤ 报告留档(基线对比)→ 合入 / 回滚
          text
          • 单测管零件、回归管组装、人工管校准,一层比一层贵、一层比一层全;门禁设在②,意味着 90% 的坏改动在几分钟内被拦下,而不是等夜间全量才发现;
          • 回归集红了不等于要回滚:先拿 05 章 trace 重放定位是「任务集过时」(期望写错)还是「真回归」(行为变坏),前者改任务集、后者改代码。

          4. 详细介绍:五步流程、成本分级与 pytest 三件套

          4.1 回归五步:每步防一种坏

          步骤 跑什么 防什么 成本
          ① 单测 每个工具/解析器/记忆读写的最小用例 零件级 bug 秒级,每次保存都跑
          ② 冒烟回归 3~5 条代表任务:1 成功 + 1 边界 + 1 失败拒答 大方向跑偏 分钟级,每次提交跑
          ③ 全量 + 裁判 golden 全集 + 04 章 judge 方向判定 语义级退化、概率性漏网 小时级,夜间跑
          ④ 人工抽检 抽 10~30% 与裁判对比一致率 裁判偏差漂移 人工,按批抽
          ⑤ 记录 报告文件:版本、日期、逐任务结果、与基线 diff 「上次全绿」变成可查档案 脚本自动

          4.2 成本控制:小集快速回归 → 全量兜底

          档位 触发时机 内容 预期耗时
          冒烟(smoke) 每次提交,CI 门禁 3~5 条黄金任务,无裁判 分钟级
          全量(full) 夜间或发版前 golden 全集 + 轨迹断言 + 裁判方向 小时级
          抽检(human) 每批全量后 人工 vs 裁判一致率(04 章口径) 人工
          • 全量评测贵(一任务多轮多次调用,token 与时间都烧),所以门禁只压冒烟,全量做兜底——把「每改动必全量」降级成「每改动必冒烟、定期全量」,成本曲线从线性变成阶梯;
          • pytest 里用 marker 分档:@pytest.mark.smoke 标冒烟集,-m smoke 只跑小集,不写 marker 默认跑全量。

          4.3 pytest 三件套:断言什么

          测试点 对应章节 断言示例
          任务级方向 03 章 关键词齐全、应拒答任务真的拒答、禁用副作用零调用
          轨迹级纪律 02 章 同一工具同参数连续重复 < 3 次(死循环启发式)
          语义层信号 04 章 (接真模型时)judge 方向 pass 比例不低于基线

          5. 动手活动:pytest 评测闭环

          动手活动:把课程助教评测写成 pytest,跑通「改一行提示 → 评测抓回归」闭环

          目标:产出 test_agent_regression.py、test_eval_suite.py 与 reports/eval-report.md。

          步骤:

          1. 通读 test_agent_regression.py(评测内核:黄金集、规则表、任务级/轨迹级断言;GOLDEN 字段与 03 章 golden-tasks.jsonl 同构,可整段替换成真实文件)与 test_eval_suite.py(pytest 形态:冒烟/全量用例,run_agent 换真实 Agent 时把返回换成 05 章 trace 即可);
          2. 运行 python -m pytest test_eval_suite.py -m smoke -q(冒烟档)与 python -m pytest test_eval_suite.py -q(全量档),确认全绿;
          3. 运行 python test_agent_regression.py:对比 v1 与 v2(改动 = 删掉「未涉及就拒答」规则),看 g10 如何从通过变失败,报告写入 reports/eval-report.md;
          4. 亲手制造一次回归:把 RULES["v1"]["unknown_refuse"] 改成 False,重跑全量档 pytest,观察门禁变红;
          5. 改回 v1,把报告抄进 reports/regression-notes.md,写一句话:这道门禁拦下了什么?

          完成标准:python -m pytest test_eval_suite.py -q 全绿;python test_agent_regression.py 能展示 v1→v2 的 g10 回归并生成报告;手动破坏 v1 后 pytest 变红、改回后变绿——闭环成立。

          # test_agent_regression.py —— 课程助教回归评测内核(被 test_eval_suite.py 的 pytest 用例调用)
# 用法:python test_agent_regression.py   演示「改一行提示 → 抓回归」并写报告
# pytest 用例在同目录 test_eval_suite.py:python -m pytest test_eval_suite.py -q
import os

MATERIAL = {
    "外键": "3.1 节:外键建立表间引用,保证参照完整性。",
    "WHERE": "3.2 节:WHERE 在分组前过滤行,HAVING 在分组后过滤组。",
}

# 迷你黄金集:字段与 03 章 golden-tasks.jsonl 同构(task_id/category/task/期望结果/禁用副作用)
GOLDEN = [
    {"task_id": "g01", "category": "success", "task": "外键的作用是什么?",
     "words": ["外键", "引用"], "refusal": [], "forbidden": []},
    {"task_id": "g04", "category": "success", "task": "WHERE 与 HAVING 有什么区别?",
     "words": ["WHERE", "HAVING"], "refusal": [], "forbidden": []},
    {"task_id": "g03", "category": "boundary", "task": "零基础学员 L-1001 问外键,先看档案再讲",
     "words": ["外键", "引用"], "refusal": [], "forbidden": []},
    {"task_id": "g10", "category": "failure", "task": "第 3 章讲窗口函数吗?",
     "words": [], "refusal": ["未涉及", "没有讲", "未找到"], "forbidden": []},
]

# 规则表 = system prompt 的机器可读版;v2 模拟一次真实改动:删掉了「未涉及就拒答」
RULES = {
    "v1": {"unknown_refuse": True},
    "v2": {"unknown_refuse": False},
}

def search_material(query):
    """简化检索:按关键词命中讲义片段;未命中返回空列表"""
    return [text for kw, text in MATERIAL.items() if kw in query]

def run_agent(task, rules):
    """课程助教桩:读档案(任务提及学员)→ 检索 → 回答;返回 (trace, answer)
    换真实 Agent 时,把这里替换成 02.01 的主循环并让 trace 走 05 章 recorder"""
    trace = []
    if "L-100" in task:
        trace.append({"type": "tool_call", "tool": "get_learner_profile", "params": "L-1001"})
        trace.append({"type": "observation", "tool": "", "params": "零基础"})
    trace.append({"type": "tool_call", "tool": "search_material", "params": task})
    hits = search_material(task)
    trace.append({"type": "observation", "tool": "", "params": " | ".join(hits) or "无命中"})
    if hits:
        answer = hits[0] + "建议先学这一段。"
    elif rules["unknown_refuse"]:
        answer = "讲义未涉及该主题,我无法回答。"
    else:
        answer = "讲义里讲了,见第 3 章 3.5 节:窗口函数用于跨行计算。"   # v2 的编造
    trace.append({"type": "answer", "tool": "", "params": answer})
    return trace, answer

def check_forbidden(trace, forbidden):
    """副作用禁令(03 章 forbidden_effects):返回被违规调用的工具名列表"""
    return [e["tool"] for e in trace if e["type"] == "tool_call" and e["tool"] in forbidden]

def audit_trace(trace):
    """轨迹级纪律(02 章):同一工具同参数连续重复 >= 3 次 = 死循环启发式"""
    issues, runs, prev = [], 0, None
    for e in trace:
        if e["type"] == "tool_call":
            key = (e["tool"], e["params"])
            runs = runs + 1 if key == prev else 1
            prev = key
            if runs >= 3:
                issues.append(f"同一调用连续 {runs} 次: {e['tool']}")
        else:
            prev = None
    return issues

def evaluate(version):
    """对 GOLDEN 全集跑指定规则版本;每条返回 通过/问题明细"""
    rules = RULES[version]
    rows = []
    for g in GOLDEN:
        trace, answer = run_agent(g["task"], rules)
        issues = []
        missed = [w for w in g["words"] if w not in answer]
        if missed:
            issues.append("缺关键词: " + "、".join(missed))
        if g["refusal"] and not any(w in answer for w in g["refusal"]):
            issues.append("应拒答却作答")
        if check_forbidden(trace, g["forbidden"]):
            issues.append("出现禁用副作用调用")
        issues += audit_trace(trace)
        rows.append({"task_id": g["task_id"], "ok": not issues, "issues": issues})
    return rows

def write_report(rows, version, path="reports/eval-report.md"):
    """把一次评测固化成 markdown 报告留档(呼应 01.06 的 07 章报告纪律)"""
    os.makedirs(os.path.dirname(path) or ".", exist_ok=True)
    with open(path, "w", encoding="utf-8") as fh:
        fh.write(f"# 回归评测报告(prompt {version})\n\n| 任务 | 方向 | 问题 |\n|---|---|---|\n")
        for r in rows:
            fh.write(f"| {r['task_id']} | {'通过' if r['ok'] else '失败'} | "
                     f"{'; '.join(r['issues']) or '-'} |\n")
    return path

def show(rows):
    for r in rows:
        print(f"  {r['task_id']}: {'通过' if r['ok'] else '失败 - ' + '; '.join(r['issues'])}")

def main():
    """演示闭环:同一评测集跑 v1(现网)与 v2(改动后),抓出回归并写报告"""
    print("== prompt v1(现网,基线) ==")
    rows_v1 = evaluate("v1")
    show(rows_v1)
    print("\n== prompt v2(改动:删掉『未涉及就拒答』规则) ==")
    rows_v2 = evaluate("v2")
    show(rows_v2)
    regressed = [r for r in rows_v2 if not r["ok"]]
    path = write_report(rows_v2, "v2")
    print(f"\n回归破坏 {len(regressed)} 条 -> 不允许合入;报告已写入 {path}")
    print("修复动作:回滚该行改动,或先补规则再重跑全量回归。")

if __name__ == "__main__":
    main()

# 真实接入时:把 evaluate() 换成读 golden-tasks.jsonl + 05 章 trace + 04 章 judge 输出
import pytest
from test_agent_regression import RULES, GOLDEN, evaluate, check_forbidden

SMOKE_IDS = {"g01", "g10"}          # 冒烟档:1 成功 + 1 拒答,分钟级门禁

def test_all_golden_pass_on_v1():
    """全量档:基线必须全绿——这是「上次好的」的存档定义"""
    failed = [r for r in evaluate("v1") if not r["ok"]]
    assert not failed, f"基线被破坏: {failed}"

@pytest.mark.smoke
def test_smoke_set_pass_on_v1():
    """冒烟档:提交门禁只跑小集,绿了才放行全量(4.2 成本控制)"""
    rows = {r["task_id"]: r for r in evaluate("v1")}
    failed = [tid for tid in SMOKE_IDS if not rows[tid]["ok"]]
    assert not failed, f"冒烟失败: {failed}"

def test_forbidden_effect_detector():
    """单测:答案再对,出现禁用副作用调用也必须判失败(g07 类越权写档案)"""
    trace = [{"type": "tool_call", "tool": "search_material", "params": "外键"},
             {"type": "tool_call", "tool": "save_learner_profile", "params": "learned=HAVING"},
             {"type": "answer", "tool": "", "params": "外键建立引用。"}]
    assert check_forbidden(trace, ["save_learner_profile"]) == ["save_learner_profile"]

def test_rule_table_is_registered():
    """元测试:每条被引用的规则版本必须注册在 RULES 里(防改规则忘登记)"""
    assert {"v1", "v2"} <= set(RULES) and len(GOLDEN) >= 3

          6. 边界与排错:回归评测也会骗人

          • 任务集过时 ≠ 代码退化:改需求后旧期望作废,测试会误红——先核对 golden 任务与期望路径(03 章纪律:任务集本身要评审、要版本管理),别急着改代码;
          • 黄金集会被 Agent 记住:评测任务反复出现在对话/日志里,模型可能「背答案」;训练侧任务集要定期轮换(呼应 03 章去污染),评测侧同样要防污染——trace 里的任务原文别直接进上下文做 few-shot;
          • 全绿也可能是假绿:断言太弱(关键词太少、轨迹不查)会让坏改动漏网;用 04 章人工抽检校准「评测本身还有效」,一致率跌破阈值先修 rubric;
          • 门禁别设太重:全量裁判进提交门禁会让每次提交等一小时,开发者会用脚投票绕过它——门禁只留冒烟(4.2),全量走夜间,「重」的评测靠定时与发版前兜底;
          • CI 里跑评测要隔离:评测会调模型、写文件、产生费用——用固定模型版本与固定 seed/温度,报告里记录模型与日期,否则「全绿」无法复现(呼应 01.06 的 07 章报告要素)。

          7. 总结

          概念 一句话
          回归评测 每次改动重跑同一评测集,与基线对比,防「修好一个坏十个」
          五步流程 单测 → 冒烟回归 → 全量+裁判 → 人工抽检 → 报告留档
          pytest 化 任务级断言 + 轨迹纪律 + 副作用禁令写成测试,绿=可合入、红=拦下
          成本控制 冒烟(分钟)当门禁,全量(小时)夜间兜底,人工按批抽检校准
          与 CI 关系 pytest 退出码即门禁信号;报告记录版本/日期/模型,保证可复现
          模块收官 02~05 的指标、任务集、裁判、trace 在此汇成开发循环的制度

          思考题:某次改动后全量回归红了 1 条,但人工重跑该任务 3 次都通过——你会直接判定「测试误报、合入」吗?先检查哪三件事?

          参考答案

          不该直接合入。先查三件事:① 是不是任务集过时(期望路径/关键词与需求不符,呼应 6 节);② 是不是评测本身不稳定(温度/seed 未固定、裁判波动,跑两次看是否偶发红);③ 是不是概率性真实退化(该任务边界条件触发率低,多跑几次仍偶发失败说明 Agent 本身不稳,该修的不是测试)。三者都排除后,把「人工重跑 3 次通过」连同评测输出一起写进报告再合入——合入依据是证据,不是感觉。
