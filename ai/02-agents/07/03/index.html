          轨迹级指标

          01 章说 Agent 评测要盯「轨迹 + 结果 + 副作用」三件套,可「盯」总得有尺子:说一条轨迹「走岔了」,岔在哪一步?绕几步算绕?同一个调用重复几次算死循环?本章给过程质量装上四个数字——工具选择正确率、参数正确率、无效步占比、死循环率,并把课程助教的 10 条轨迹逐条标注、统计成报告。这是 02.07 的第二课:任务级指标回答「到了没有」(03 章),轨迹级指标回答「路走得对不对」——本章先把后者量化。

          学习目标:学完本章,你将能够——

          1. 说出轨迹级指标的定位:评「每一步走得好不好」,与任务级指标互补;
          2. 定义工具选择正确率、参数正确率、无效步占比、死循环率及其计算口径;
          3. 按「先看工具、再看参数、最后查重复」三步给轨迹步打标签;
          4. 用脚本标注 10 条轨迹并统计出四指标与问题步清单;
          5. 说明轨迹级指标的盲区(抓不到内容幻觉),知道该交给任务级与裁判(03、04 章)。

          1. 概念:轨迹级指标评「每一步走得好不好」

          • 轨迹级指标(trajectory-level metrics):以整条轨迹为对象、以每一步为最小打分单元的一组指标,回答「这条路走得对不对、顺不顺、有没有白走」。
          • 课程助教的工具集沿用前几章:查讲义 search_material(keyword, chapter)、翻档案 get_learner_profile(learner_id)、写档案 save_learner_profile(learner_id, field, value)、计算 calculate(expression)——指标主要评其中的工具调用步。
          • 轨迹由四类步组成,先学会认步,才能评步:
          步类型 记号 是什么 例子
          思考 T 模型的内部推理 「先查讲义再回答」
          工具调用 C 调用某个工具及参数 search_material(query="外键")
          观察 O 工具返回的结果 「命中外键定义与示例」
          最终回答 A 交给学员的答案 「外键建立表间引用……」
          • 本模块四个核心指标:工具选择正确率、参数正确率、无效步占比、死循环率——前两个评「单步质量」,后两个评「过程卫生」。一句话:任务级问「到了没有」,轨迹级问「路走得对不对、白走了几步」。

          2. 为什么需要:任务成功了,但绕了远路

          • 「成功但绕远路」是 Agent 最常见的隐性坏味道——结果对,过程烂。只报任务成功率,这些全部被吞掉:
          现象 代价 轨迹级信号
          任务成功但绕路(搜 4 次才答对) token 与延迟成倍上涨,体验差 冗余调用多、步数超期望
          成功但瞎试(先错工具再纠正) 中途可能触发权限动作或副作用 wrong_tool、bad_args
          卡死重试(同一步重复 N 次) 烧钱、永不结束、需人工介入 死循环、无效步占比趋近 1
          成功路径里夹着越权写入 档案被污染,审计事故(呼应 01 章) 出现不该出现的写类工具
          • 证据:WebArena 论文分析弱模型时发现,最常见的失败正是重复无效动作、撞步数上限——这俩就是本章要量化的「无效步」与「死循环」;τ-bench(2024)则把任务成功拆成逐步判定:错工具(used_wrong_tool)、参数错(used_wrong_tool_argument)、多余动作(took_unintended_action)各有「罪名」,轨迹要全部工具调用都正确才算通过。
          • 呼应 02.06 的失败模式:级联错误的第一步往往是「某一步走错」;轨迹级指标的价值就是在级联放大之前,把坏步钉出来。

          3. 作用:轨迹级指标在评测体系里的位置

          trace(05 章) → 步类型标注(T/C/O/A)
   ↓ 对照「期望工具序列」(人工示例或黄金任务集提供)
规则判定:工具对不对 → 参数对不对 → 是否重复
   ↓
四指标 → 报告 → 喂给 03 章任务级判定与 04 章裁判做归因素材
          text
          • 给任务级指标当放大镜:03 章报「t06 失败」只给结论;本章能补一句「失败原因是连续 3 次重复检索,白烧了 token」。
          • 给回归评测当敏感探针:06 章的回归里,任务成功率常「大数不动」——改一行提示可能只影响一两条任务;无效步占比这类过程指标变化更灵敏,更容易暴露「提示把模型带偏了」。
          • 前提是拿得到轨迹:指标算在轨迹上,没有 05 章的 tracing 记录寸步难行;期望工具序列则来自人工或任务设计(03 章黄金任务集的「期望行动路径」正是这里的输入)。

          4. 详细介绍:指标定义与标注规则

          4.1 指标定义表

          指标 怎么算 异常信号 常见误判
          工具选择正确率 选中期望工具的步数 ÷ 工具步总数 下降 → 工具清单/描述写得差(呼应 02.04 的 02 章) 把「参数错」也算成选错工具
          参数正确率 工具与参数全对的步数 ÷ 工具步总数 下降 → 参数 schema 复杂、校验缺失 只数「最终调用」漏掉中间错步
          无效步占比 (错工具 + 参数错 + 冗余重复) ÷ 工具步总数 持续上升 → 提示退化、任务太难硬试 把 thought/observation 算进分母稀释
          死循环率 出现死循环的任务数 ÷ 任务总数 大于 0 → 查编排与失败处理(呼应 02.03 的 05 章) 把「多次尝试不同方案」误判为死循环
          • 口径声明:四个指标的分子分母统一用「工具调用步数」,thought/observation/answer 不参与,避免被思考文字稀释;换口径必须写进报告,否则跨团队没法比较。三个同分母指标的关系:参数正确率 + 无效步占比 = 1——从正反两面看同一件事,报告里写一个就够,但定义必须一致。

          4.2 标注三步规则

          1. 先看工具:该不该调这个工具?工具名对不对(拼错、张冠李戴)?不对 → wrong_tool;
          2. 再看参数:工具对了,参数是否符合任务需要?不对 → bad_args;
          3. 最后查重复:同样的(工具,参数)之前出现过?出现过 → redundant_repeat;
          4. 三步全过 → correct;思考、观察、回答步记为 ok,不参与统计。

          4.3 死循环的判定

          • 启发式:同一(工具,参数)连续出现 ≥ 3 次,或整条轨迹超过步数上限仍不产出最终回答,判死循环——前者是「原地打转」,后者是「无限外环」。阈值不是真理:工具偶发失败时重试是合法的,阈值要按工具稳定性调,并在报告里注明。

          5. 动手活动:标注 10 条轨迹并统计无效步占比

          动手活动:课程助教轨迹标注与四指标统计

          目标:产出 reports/trajectory-metrics.md——10 条轨迹全部完成步级标注,给出四指标与无效步清单。

          步骤:

          1. 读脚本头部注释,弄清 T/C/O/A 行格式与标注规则;对照 t01(干净)与 t06(死循环)理解规则如何落地;
          2. 运行 python annotate_trajectories.py,并抽查 t04、t09:手算各自的无效步数,与输出比对;
          3. 写报告:逐条列无效步清单与根因、汇总四指标、回答「t10 轨迹级全绿说明了什么」。

          完成标准:能说出 t06 被判死循环的依据(第几步起、连续几次、哪组参数);能指出 t09 的无效步属于哪一类;报告说明轨迹级抓不到的内容幻觉该交给哪一层。

          # annotate_trajectories.py —— 轨迹步级标注 + 四指标统计(离线可跑)
# 行格式:T:思考 / C:工具名|参数 / O:观察摘要 / A:最终回答
# expect:期望工具调用序列「工具名|参数关键词」;关键词为空表示不限参数
# 规则:按序命中且参数匹配 -> correct;工具对参数错 -> bad_args;工具不对 -> wrong_tool;
#      与前面某次调用相同 -> redundant_repeat;同一(工具,参数)连续 >= 3 次判死循环
# 口径:分母统一为工具调用步数

TRAJ = [
    # (id, 任务, 期望工具序列, 步列表)
    ("t01", "外键的作用?", ["search_material|外键"],
     ["T:先查讲义定位外键", "C:search_material|外键的作用", "A:外键建立表间引用……"]),
    ("t02", "练习 2.1 五位学员平均分", ["search_material|成绩表", "calculate|/5"],
     ["T:先找成绩表", "C:search_material|成绩表", "C:calculate|(85+92+78+90+88)/5", "A:平均分 86.6 分。"]),
    ("t03", "外键的作用?", ["search_material|外键"],
     ["T:先看档案再答", "C:get_learner_profile|L-1001", "C:search_material|外键", "A:外键建立表间引用……"]),
    ("t04", "WHERE 与 HAVING 区别?", ["search_material|WHERE 与 HAVING"],
     ["C:search_material|HAVING", "C:search_material|WHERE 与 HAVING", "A:WHERE 过滤行、HAVING 过滤组。"]),
    ("t05", "外键的作用?", ["search_material|外键"],
     ["C:search_material|外键的作用", "C:search_material|外键的作用", "A:外键建立表间引用……"]),
    ("t06", "第 3 章怎么讲索引?", ["search_material|第3章 索引"],
     ["T:学员问索引", "C:search_material|第3章 索引", "C:search_material|第3章 索引",
      "C:search_material|第3章 索引", "C:search_material|第3章 索引", "A:照抄第一条结果。"]),
    ("t07", "外键的作用?", ["search_material|外键"],
     ["C:save_learner_profile|L-1001|learned=HAVING", "C:search_material|外键", "A:外键建立表间引用……"]),
    ("t08", "练习 2.1 答案与平均分", ["search_material|练习题", "calculate|/5"],
     ["C:search_material|练习题 2.1", "C:search_material|练习题 2.1", "C:calculate|(85+92+78+90+88)/5",
      "A:答案如上,平均分 86.6 分。"]),
    ("t09", "外键的作用?", ["search_material|外键"],
     ["C:search_maeterial|外键", "C:search_material|外键", "A:外键建立表间引用……"]),
    ("t10", "第 3 章讲窗口函数吗?", ["search_material|窗口函数"],
     ["T:先查讲义", "C:search_material|窗口函数", "A:第 3 章 3.5 节讲了窗口函数。(编造)"]),
]

LOOP_RUN = 3  # 连续重复多少次判死循环

def split_step(raw):
    """拆一行轨迹为 (kind, tool, args);非 C 行 args 为空"""
    kind, _, payload = raw.partition(":")
    if kind == "C":
        tool, _, args = payload.partition("|")
        return kind, tool.strip(), args.strip()
    return kind, "", payload.strip()

def args_match(actual, keyword):
    return keyword == "" or keyword in actual

def annotate(steps, expect):
    """给一条轨迹打标签,返回 (labels, issues);label 为 (序号, 类型, 内容, 标签)"""
    labels, issues = [], []
    pending = list(expect)
    seen, run_key, run_len, run_start = set(), None, 0, 0
    for i, raw in enumerate(steps, 1):
        kind, tool, args = split_step(raw)
        if kind != "C":
            labels.append((i, kind, "-", "ok"))
            continue
        key = (tool, args)
        if key == run_key:
            run_len += 1
        else:
            run_key, run_len, run_start = key, 1, i
        if run_len == LOOP_RUN:
            issues.append(f"死循环:第 {run_start}~{i} 步连续 {run_len} 次重复 {tool}({args})")
        if key in seen:
            tag = "redundant_repeat"
        elif pending:
            exp_tool, _, exp_kw = pending[0].partition("|")
            if tool == exp_tool.strip():
                if args_match(args, exp_kw.strip()):
                    tag, pending = "correct", pending[1:]
                else:
                    tag = "bad_args"
            else:
                tag = "wrong_tool"
        else:
            tag = "wrong_tool"
        seen.add(key)
        labels.append((i, kind, f"{tool}({args})", tag))
    return labels, issues

def main():
    agg = {"correct": 0, "bad_args": 0, "wrong_tool": 0, "redundant_repeat": 0}
    looped = 0
    print("== 逐条标注 ==")
    for traj_id, task, expect, steps in TRAJ:
        labels, issues = annotate(steps, expect)
        stats = {"correct": 0, "bad_args": 0, "wrong_tool": 0, "redundant_repeat": 0}
        for _, kind, _, tag in labels:
            if kind == "C":
                stats[tag] += 1
        for tag in agg:
            agg[tag] += stats[tag]
        n = sum(stats.values())
        invalid = stats["wrong_tool"] + stats["bad_args"] + stats["redundant_repeat"]
        print(f"{traj_id} [{task}] 工具步 {n}:正确 {stats['correct']} / 错工具 "
              f"{stats['wrong_tool']} / 参数错 {stats['bad_args']} / 冗余 {stats['redundant_repeat']}")
        if n:
            print(f"  无效步占比 = {invalid / n:.1%}")
        for issue in issues:
            looped += 1
            print(f"  !! {issue}")
    total = sum(agg.values())
    tool_acc = (agg["correct"] + agg["bad_args"]) / total
    invalid_ratio = (agg["wrong_tool"] + agg["bad_args"] + agg["redundant_repeat"]) / total
    print("== 汇总 ==")
    print(f"轨迹数 {len(TRAJ)};工具步总数 {total};死循环率 = {looped / len(TRAJ):.1%} ({looped}/{len(TRAJ)})")
    print(f"工具选择正确率 = {tool_acc:.1%} ({agg['correct'] + agg['bad_args']}/{total});"
          f"参数正确率 = {agg['correct'] / total:.1%} ({agg['correct']}/{total})")
    print(f"无效步占比 = {invalid_ratio:.1%} ({total - agg['correct']}/{total})")

if __name__ == "__main__":
    main()

          6. 边界与排错:轨迹级指标的三个雷区

          • 期望序列是「必要不充分」的检查:期望只列「必须做的调用」,绕路会被抓,可若模型走了另一条完全合法的路径,死规则会冤枉它——解法:期望写宽松关键词,把「路径等价」的判断交给 04 章裁判。
          • 标注成本高,自评是循环论证:10 条轨迹人工标得动,1000 条不行;让模型给自己的步打标签等于「考生自己改卷」。规模化靠抽样人工 + 04 章 judge + 05 章自动 trace。
          • 指标会打架,别只看一个数:步数最少不代表最好(少而错);无效步占比降了,可能是模型干脆不调工具直接编——轨迹级必须和任务级指标(03 章)一起看。
          • 抓不到内容真实性:t10 就是例子——轨迹全绿,答案却是编的。轨迹级只管「路走得对不对」,「到的地方对不对、说的真不真」是 03 章任务级与 04 章裁判的职责。

          7. 总结

          概念 一句话
          轨迹级指标 评每一步走得好不好:正确率 + 过程卫生
          三个口径指标 工具选择正确率 = 选对工具 ÷ 工具步;参数正确率 = 全对 ÷ 工具步;无效步占比 = (错工具 + 参数错 + 冗余) ÷ 工具步
          死循环率 死循环任务 ÷ 任务总数(连续重复 ≥ 3 次为启发式)
          标注三步 工具对不对 → 参数对不对 → 是否重复
          盲区 内容幻觉看不见,交给任务级与裁判

          思考题:一条轨迹任务成功、四个指标全绿,但第 3 步把「学员已会 HAVING」写进了档案,而学员其实刚问完这个问题——指标为什么抓不到?如果想让它在回归评测里被自动抓到,该在哪一层补什么检查?

          参考答案

          指标只管「调用是否匹配期望序列」,不管「该写不该写」——若期望本身允许这次写入,轨迹级就哑了。该在系统层补副作用清单检查(写类工具按字段白名单放行,呼应 01 章与 02.04 的 06 章权限),并把「档案被改脏」作为 03 章任务级的失败条件;这也是 06 章回归评测要接进 CI 的原因。
