          五个角色：模型、上下文、规划、工具、记忆

          设想一个团队按“模块化”的思路搭建 Agent：先选一个规划库，再选一个记忆库，随后接入工具协议层，最后用模型把它们串起来。半年过去，集成出来的东西效果不及此前那个两百行的脚本。

          问题在于他们把角色当成了模块。模型、上下文、规划、工具、记忆，这五样是循环里必须有人承担的职责，无法当成五个独立组件去采购。同一个部件常常同时承担两项职责：对话历史既是上下文也是短期记忆，工具返回既是观察也是上下文的一部分。按角色去理解，你会问“这一轮谁在负责规划”；按模块去理解，你会问“我该装哪个规划组件”——后者会使工程决策系统性地偏离正确方向。

          所以这一节不讲“五要素”，讲五个失效模式，以及每个模式由谁兜住。

          模型：判断力的上限

          模型回答的是“现在该做什么”。它的推理能力决定了系统能做到多难的任务，这一点没有替代品——你把循环写得再漂亮，也没法让一个不会做多步推理的模型做出多步推理。

          但有一个常见误判值得提前拆掉：换模型能抬高上限，不能修复结构。如果循环没有把观察写回上下文，换更强的模型只会让它更快地重复同一个错误动作。如同为漏水的容器更换更精良的阀门，泄漏依旧。

          真正该看的信号是失败的形状；“效果不好”太笼统，指不出方向。如果失败集中在需要更深推理的地方（多约束规划、隐式前提识别），换模型有意义；如果失败集中在重复动作、丢状态、停不下来，那是结构问题，换模型只是在给结构问题付更贵的账。

          上下文：Agent 唯一的工作台

          模型没有内部状态。它在第 n 轮看到的世界，完全由你塞进上下文的那几千到几十万个 token 决定。

          这句话的推论比它听起来更狠：Agent 的“知道”，严格等于上下文里的字节。 它不记得上一轮做过什么，它只是这次又读到了。你以为的“记忆”，在模型眼里是一条历史消息。

          这带来两个直接的设计约束。第一，任何需要跨轮保留的东西，必须显式写进上下文，否则等于没发生。第二，上下文是有预算的：窗口再大也是有限的，而每一轮的工具返回都在消耗上下文预算，到某个点你必须决定丢什么、留什么、把什么压缩成摘要。这个决策的质量，往往比模型的选型更能决定系统在第 20 步还能不能正常工作。

          下一章整章都在讲这件事，这里只留一句话：把上下文当工作记忆来组织。 日志追求完整，工作记忆追求当前决策需要的刚好够用。把日志直接当上下文用，是新手最常见的失误：性能与质量同时受损。

          规划：下一步，而不是全程

          人类项目经理会先画甘特图再执行。多数 LLM Agent 不这样：它每一轮只决定下一个动作，看结果，再决定下一步。

          一次性生成完整计划的方案看似更具“智能”，也确实在某些场景里有效——计划可以提交人工审阅，可以并行调度。但它有两个结构性缺陷：对环境变化缺乏适应能力，且第一步判断有误则后续全部偏离。ReAct 之所以成为主流，是因为它把计划和执行交织在一起，使错误在第二步即暴露，而不会拖到第十二步。

          所以“规划”这个角色在 Agent 里通常以行为约定的形式存在：先想清楚再动手，想的时候把目标拆成可验证的子目标，动手后拿结果对照子目标。它写在哪里？写在 system prompt 里、写在 few-shot 例子里、写在工具描述里——形式上到处都是，职责上只有一个：在做之前先判断做什么值得做。

          这也是为什么“加一个 planner agent”经常没用：把规划交给另一个模型调用，中间就多了一次信息损失，而这次损失发生在最关键的地方。

          工具：与世界的全部接触面

          模型不能读文件、不能发请求、不能改数据库——除非你给它一个函数。工具不只是能力扩展，它是唯一的行动通道。

          工具设计里有两个反向的错误，都很常见。

          做太粗：只给一个 run_sql(query)，让模型自己拼 SQL。看似灵活，实际上把“这个系统能做什么”变成了不可枚举的东西，安全边界、审计、权限全部失效。

          做太细：二十个工具各管一个字段，get_user_name、get_user_email、get_user_plan。模型的推理预算大量消耗在选择工具上，错误率上升，而且这些工具本可以合成一个 get_user(id, fields=[])。

          更稳妥的做法是按“动作的语义”切分：一个工具对应一件业务上说得清的事，比如“查学员进度”而不是“查 progress 表的第 3 行”。粒度对齐业务语义，模型才好选，审计才看得懂。

          还有一个被严重低估的设计点：错误信息是工具接口的一部分。 工具失败时返回什么，直接决定模型能不能自我纠正。返回空字符串、返回 None、抛异常被框架吞掉——这三种做法都会让模型在“世界没变化”的状态下继续行动。好的做法是返回结构化的失败：{"error": "TIMEOUT", "detail": "search API exceeded 30s", "retryable": true}。模型读得懂，下一次决策就有依据。

          记忆：跨轮和跨会话是两件事

          跨轮的连续性，通常被上下文兼职掉了——把历史消息一直带着。这在任务短的时候没问题，在任务长的时候就是上下文预算的头号杀手。

          跨会话的连续性没法兼职，必须落到外部存储：数据库、向量库、文件。检索回来，再塞进上下文。

          这里最容易出现的错觉是“我加了向量库所以有记忆了”。存进去不等于用得上。检索质量差的记忆比没有记忆更糟——它会用看似相关、实则误导的内容污染判断，而模型没有能力判断“这条记忆是否适用于当前情境”。

          一个实用的判断标准：如果一段记忆被检索出来，模型无法验证它是否还成立（比如“学员上周卡在级联删除”），那它就应该带上时间戳和来源，让模型自己决定信几分。

          课程助教的一轮：五个角色同时在场

          拿课程助教跑一遍，能看清职责划分：

          学员说“帮我复习外键，按我的进度出五道题”。上下文里有课程大纲、当前对话、以及检索回来的学员画像。模型判断：先要拿到进度，再决定难度。它选择一个工具：get_progress(student_id)。工具返回“级联删除 2/5 正确，外键约束语法 4/5”。这个返回成为新的观察，写回上下文。规划根据它调整：外键语法已经会了，重点放在级联删除。模型选第二个工具 search_course_notes("cascade delete")，拿到三段讲义。最后生成五道题，其中三道针对级联删除。

          记忆在这一轮里出现在两个地方：学员画像是跨会话的（从外部检索），三段讲义是跨轮的（临时进了上下文，任务结束就可以丢）。

          同一轮里，五个角色都出现了，但没有一个是独立模块。这就是把它们当角色看的意义。

          五个角色里，最容易被做错的是上下文，最容易被粗放处理的是工具，最容易被误解的是规划，最容易被高估的是记忆，最容易被归咎的是模型。

          下一节换个角度：这五样都齐了，系统就一定该做成 Agent 吗？不一定。自主度是有价格的，而且价格常常比你预期的贵。
