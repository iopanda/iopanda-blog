          模型的边界就是 Agent 的边界

          设想一个课程组把“未提交作业提醒”做成了自动流程：Agent 读取未提交名单，生成提醒邮件，调用邮件接口发送。上线三天后，教务老师问为什么没有学员收到提醒。

          查下来的结果是：邮件服务的凭证在前一天过期，接口返回 401，Agent 在轨迹里记录了“发送成功”，并且在给老师的汇报中写明“已向 23 名学员发送提醒”。它没有撒谎的动机，只是把“我打算发送”和“已经发送”混在了一起。

          这件事在聊天机器人时代不会发生——对话系统最多说错一句话。装上工具之后，语言错误升级成了行动事故，而事故的代价不由模型承担。

          幻觉、窗口、以及不肯说“做不到”

          这里说的能力边界，指原理层面的行为特征，与响应慢、服务不稳无关。对 Agent 影响最大的有三条，它们的共同点是：模型自己感知不到它们的存在。

          幻觉。 语言模型的输出是“最可能的下一段文本”，而不是“对世界状态的测量报告”。在训练语料里，“我读到了 X”与“我推测是 X”的文本形态完全一致，模型没有区分二者的内部机制。这不是可以通过提示词消除的缺陷——有形式化工作论证了它在当前架构下不可完全消除（arXiv:2401.11817）。工程能做的只有降低频率与限制杀伤半径。

          上下文窗口。 模型的“记忆”完全等于这次输入里的 token。窗口之外不存在任何东西。Agent 是上下文的重度消费者：系统指令、任务描述、每轮的推理、工具描述、工具返回，每一轮都在增加几百到几千 token。一个处理五十份作业的任务，很容易在中途撞上上限，然后按截断策略丢掉最旧的内容——通常正是开头的约束条件和早期的工具结果。

          没有校准的“不知道”。 模型按概率逐 token 生成，任何输入都会得到输出。架构里没有一个部件能举手说“这个超出我的能力”。更麻烦的是，它对自己答对与答错的把握程度几乎相同，因此“说得很确定”不能作为可靠性信号。

          幻觉在 Agent 里的两种形态

          聊天场景里，幻觉表现为一段不准确的话，用户重问即可。Agent 场景里，它有两种更具破坏性的形态。

          编造工具结果。 模型没有调用工具，或者调用失败，却在推理中叙述出工具的“返回值”。例如没有读成绩表，直接给出“张三 88 分”。这类错误之所以危险，是因为假数据会进入下游计算，并被后续步骤当作事实引用。

          编造执行成功。 工具确实调用了，也确实失败了，但模型无视错误码，在回复中声称任务完成。开头那个案例就属于这一类。它比第一种更隐蔽：轨迹里确实有一次工具调用，只是结果被忽略了。

          还有第三种，出现在长会话的压缩环节：把早期未经验证的摘要当成已确认的事实继续使用。上下文压缩时，如果摘要写的是“已获取名单”，后续步骤就会把它当成已验证数据。这类失败很难在单条轨迹里看见，因为错误发生在压缩那一刻，而后果在很久之后。

          提示词改变分布，不改变机制

          “不要编造”“不确定就说不确定”——这类指令能降低频率，不能构成控制。

          原因有两层。第一层是概率性的：指令改变的是输出分布，输出机制没有变；幻觉从常见降到少见，但不会归零。第二层是结构性的：模型无法在生成过程中查询“我刚才那句话有没有依据”。它没有可靠的内省通道。

          因此可靠性的来源必须移出模型。具体的做法有三条，按效果排序：

          工具结果由执行环境注入，不经过模型的转述。 这是最重要的一条。Observation 应该是 harness 写入上下文的原始返回，而不是模型复述的版本。一旦允许模型“转述”工具结果，你就失去了验证的基准。

          关键状态读回验证。 涉及外部状态的结论（发送成功、写入完成、扣款成功），不能只信模型的声明，必须由代码读回或核对返回值。成本很低——一次幂等查询——但能拦住绝大多数“报喜”类错误。

          把失败做成可见事件。 工具失败必须产生一个结构化的、模型能读到的观察：错误码、是否可重试、原始信息。失败变成沉默是这类事故最常见的根因。

          补偿能修信息，不能修推理

          有一个宽松的说法：Agent 的有效能力 = 模型上限 + 工程补偿。这个加法需要一点修正，否则会误导投入方向。

          补偿能修复的是信息类缺陷：工具结果被注入、状态被验证、约束被重申、历史被摘要。它不能提升推理类能力：如果模型无法在五个约束下做出取舍，护栏不会帮它做出来。

          所以更准确的关系是乘法与截断的组合：工程补偿决定你能保住模型能力的多大比例，而模型上限决定这个比例的天花板。一个推理能力不足的模型，配上完善的验证，结果是“错得可控”；一个推理能力强的模型，配上糟糕的观察，结果是“自信地错”。

          这也解释了为什么很多团队在结构问题没解决时反复换模型：他们观察到的是“效果不够好”，但失败分布其实指向观察环节，换模型只是让错误来得更贵。

          先问：是模型编的，还是世界如此

          Agent 行为异常时，第一个要问的是：这是模型编的，还是世界真的如此？

          凡是涉及外部状态的结论，都回去查工具的真实日志，而不是查模型的叙述。这条习惯把大部分排查时间从“猜测模型意图”转移到“核对执行记录”，效率差别很大。

          第二个问题接着问：如果世界确实如此，模型看到的观察是否完整？有没有被截断、被丢弃、被摘要扭曲？多数“模型判断失误”追到第三层，都是一个信息在传递过程中丢失了。

          模型的三条边界决定了 Agent 的上限，而观察与验证的质量决定了你能贴近这个上限多远。

          下一节动手：写一个不依赖任何框架的最小 Agent，把循环、工具协议、终止条件全部手写一遍。你会亲眼看到这些边界在轨迹里的样子。
