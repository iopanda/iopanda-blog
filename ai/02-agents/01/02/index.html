          Agent 是什么：三条判据

          把 system prompt 里加一句 “You are an autonomous agent. Think step by step and use tools when needed.” 就当成了 Agent，是相当常见的误解。演示通常很成功：模型确实会调用工具。问题出在演示之后——它会连续调用同一个接口十几次，账单翻上去，而任务并没有完成。

          问题不在那句话，在于他们只加了提示，没加循环、没加停止条件、没加失败处理。Agent 是一种系统结构，模型只是其中一个部件。 这一节把结构里最硬的部分说清楚：怎么判断一个系统到底是不是 Agent，以及这条判据在工程实践中的含义。

          agent 这个词已经用了三十年

          “智能体”在中文里几乎没有历史包袱，但在英文里，agent 在 AI 领域已经用了三十年。1995 年 Wooldridge 和 Jennings 给过一套形式化定义，核心是“在环境中自主行动以达成目标”；Russell 与 Norvig 把 rational agent 作为整本书的组织单位，讨论的是感知—决策—行动的闭环。那一代 Agent 的代表是 SOAR、BDI 这类符号系统，还有强化学习里的 agent——AlphaGo 就是一个 agent：它感知棋盘，选择动作，根据胜负更新策略。

          大模型时代的 Agent 跟它们共享同一个骨架，但换掉了最关键的一块：决策那一层不再是人写的规则或训练出来的策略，而是一个语言模型。

          这带来两个后果，一个好一个坏。好处是通用性——不必为每个任务重新设计状态机，写几句自然语言就能定义目标。坏处是可控性——模型的选择空间是整个语言空间，它可能做出你从没想过的动作，也可能在你以为它该停的时候继续做。

          “LLM Agent”指用模型替换了决策器的那个系统。这个替换听起来是升级，实际上是把一个可验证的确定性部件换成了一个不可验证的概率部件。后面所有的工程手段——工具协议、停止条件、护栏、评测——本质上都是在给这个替换补课。

          循环、回流、终止

          我倾向于这个工作定义：

          一个 Agent 在循环中运行：观察环境，决定下一个动作，执行，再观察；直到目标达成或主动终止。动作会改变环境，观察来自环境。

          从这句话里能拆出三条判据。一个系统满足全部三条，才算 Agent；缺任何一条，它都只是别的东西。

          第一条：有循环。 一次调用、一次输出，不是 Agent。哪怕这一次调用里调了工具——那只是“带工具的单轮生成”。区分点很具体：上一次动作的结果，有没有成为下一次决策的输入。

          第二条：动作改变环境，观察回流。 工具必须真的做事，结果必须真的回到上下文。如果返回值被丢弃，或者每一轮拿到的上下文完全相同，你有一个循环的形状，却没有循环的功能——模型会重复同一动作，因为对它来说世界没有变化。前面那个连调十七次接口的例子，根因就在这里：他们没把工具返回值写回上下文，模型在第 3 次、第 17 次看到的世界完全一样。

          第三条：有终止。 这是最容易被忽略、也最容易出事的一条。终止可以有三种来源：模型自判断（任务完成、无法继续）、硬预算（步数、token、时间、金额）、外部信号（用户叫停、监控告警）。生产系统里，模型自判断的终止永远要和硬预算并存——前者负责正确结束，后者负责兜底。

          拿这三条去卡常见的东西，结论相当明确：

          天气问答机器人调一次 API 就返回，没有第二轮决策，不是 Agent。定时读 Git 记录生成周报的脚本，步骤由人预先定义，并非 Agent——但它是很好的 workflow。一个会根据搜索结果决定下一步搜什么、读几页之后决定是否继续的调研系统，三条同时满足，才属于 Agent。

          有一类边界情况值得单独说：固定流程里嵌了一次模型判断。比如工单系统先分类再路由，分类那一步用了模型。它有循环吗？没有，人定的。动作改变环境吗？改变了（路由），但观察不回流到决策。因此它仍属于用了模型的 workflow。这种系统在生产里占绝大多数，而且往往是对的——第 2.4 节会解释为什么。

          谁为第七步的错误负责

          评审会上经常出现这样的对话：有人问“我们这算不算 Agent”，回答是“看你怎么定义”。这种回答听起来很宽容，代价是责任无处落地——如果它是 Agent，就得有人对它的自主行为负责；如果它是 workflow，责任在流程设计者身上。定义模糊的时候，两边的义务都在往对方身上推。

          三条判据的价值就在这里：它们把“谁负责”变成可以指认的对象。

          有循环，意味着有多轮状态，意味着可能存在“第 7 步开始跑偏”这种失败，评测必须做到轨迹级，不能只测单点输出。观察回流，意味着工具返回的质量直接决定后续所有决策，工具的设计者要为下游的失败分担责任——很多线上事故追到根上，是某个工具在失败时返回了一个空字符串而不是一个明确的错误。有终止，意味着有人在设计“什么时候停”，这个人必须存在，而且必须有预算兜底。

          我在项目中采用一个更粗略的判断：如果我说不出这个系统“最坏情况下会做什么”，那它就不算被设计过，无论它是不是 Agent。

          它会编造动作的结果

          接入工具之后，模型的失败模式会变。没有工具时，它编造事实；有工具时，它编造动作的结果——它会告诉你“已为你创建了会议”，而实际上工具调用超时了，或者它根本没有调用。

          更麻烦的是，这个错误在轨迹里看起来是成功的：模型说了做了，上下文里有它自己的叙述，但没有工具返回。如果你只检查最终回复，你会以为任务完成了。

          这也是为什么第 2.1 节要强调“观察回流”：工具结果的缺失，必须是上下文里一个显式的、模型看得见的事件，而不是沉默。一个 null、一句 “ERROR: timeout after 30s”，比什么都没有强得多——它会迫使模型在下一次决策时面对现实。

          压缩成一句：设计 Agent 时，单位应当取循环。

          这句话的工程含义会在后面几节展开——循环一旦成为单位，你关心的东西就从“模型答得好不好”变成“每一步的观察质量如何、状态怎么传递、什么时候该停”。这三件事里最难的是第一件，因为它取决于你给模型的工具返回了什么，而工具返回往往是最没人愿意认真设计的地方。

          在拆开循环之前，先回答一个更基础的问题：这套东西的概念比大模型早了三十年，为什么直到 2023 年才有能用的产品？
