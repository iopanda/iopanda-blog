          生态与选型：框架解决的是哪一层问题

          设想一个立项会，有人问“用什么框架”，回答是“LangGraph，行业标准”。三个月后系统上线，功能是把周报模板填上本周的数据再发出——两个步骤，路径完全固定。

          他们为此引入了状态图、检查点、条件边，以及一套并不需要的持久化机制。真正的问题从来不在框架：这个任务根本不需要 Agent，一个函数调用加一次模板渲染就够了。选型错误发生在立项会上，代价在三个月后支付。

          这一节要处理的正是这类判断：Agent 生态里每一层解决什么问题，以及拿到一个具体任务时，该落在哪一档。

          用途和自主度是两回事

          讨论 Agent 类型时，最常见的混淆是把“用途”和“自主度”当成一回事。“代码 Agent”是用途标签，“自主 Agent”是自主度标签，二者可以任意组合：既有补全式的代码 Copilot（低自主度），也有能自己跑测试、改代码、提 PR 的编码 Agent（高自主度）。

          用途轴决定工具箱与权限边界。 代码类需要文件读写、终端、Git；数据分析类需要代码执行沙箱与 SQL；浏览器类需要页面操作与表单填写；客服类需要知识库检索与工单接口。用途不同，能接触的数据和能采取的动作完全不同。

          自主度轴决定谁在做决定。 每一步由代码预先固定，还是由模型临场判断。这一轴决定了系统的成本结构、可测试性和风险面，也是第 2.4 节讨论过的“价格”。

          两条轴都要回答，缺一条就会出问题：只回答用途，会做出权限过大的系统；只回答自主度，会做出接不上真实业务的空壳。

          四档：谁在决定下一步

          按“谁决定下一步”，可以分成四档。每一档的价值与代价都很明确。

          单步工具调用。 一问一答之间调用一次工具，没有循环。可预测、无状态，错误只影响当前回答。它是 Agent 的最小形态，也是绝大多数生产系统真正需要的形态。

          工作流（workflow）。 步骤、分支、顺序由代码预先定义，模型只在指定环节出力——写摘要、做分类、生成候选。可调试、成本可控、结果稳定。凡是能确定性写死的步骤，都不应该交给模型自由发挥。

          自主 Agent。 步骤无法预先枚举时（“查资料，但查什么要边查边定”），模型自己规划、行动、观察，循环到终止。第 2.5 节那个循环就是它的最小形态。灵活性换来的是漂移、成本不收敛和难以复现。

          多 Agent。 多个 Agent 各持角色与工具，通过消息协作。适用于单 Agent 难以兼顾的多域任务。代价是通信开销、错误跨角色传播，以及责任边界模糊——出问题时很难判定是哪个角色的判断失误。

          工程上的原则很朴素：能用低档解决的，不要上高档。 档位只是按需加装的组件，撑不起成熟度的招牌。Anthropic 在 2024 年底那篇文章里也给出同样的建议：从最简单的方案开始，只在它能带来明确收益时才增加复杂度。

          四层生态，解决的不是同一个问题

          把市面上的项目按“解决哪一层问题”归类，混乱会少很多。

          模型接口层：function calling。 2023 年 6 月由 OpenAI 引入，模型可以直接输出结构化的调用意图。它是所有上层方案的地基——没有它，工具调用只能靠提示词约定加正则解析。

          工具连接层：MCP。 Model Context Protocol 定义宿主与工具服务器之间的统一协议，解决“每个 Agent 都要为每个工具写一遍适配”的重复劳动。它的推进速度值得记录：2024 年 11 月由 Anthropic 开源，2025 年 3 月被 OpenAI 采纳、4 月 Google 跟进，2025 年 12 月捐给 Linux 基金会下的 Agentic AI Foundation 由多方治理。协议层面的分裂基本结束。

          单 Agent 编排层：LangGraph 一类。 用图结构描述循环，提供状态持久化、断点续跑、流式输出与人工确认（interrupt）。它解决的是“把第 2.5 节那个循环做成可运维的生产系统”，而不是“让 Agent 变聪明”。

          多 Agent 协作层：AutoGen 一类。 提供角色定义、消息路由、群聊式协作。微软已把 AutoGen 与 Semantic Kernel 合并为 Microsoft Agent Framework，新项目应关注后者。

          这四层叠加使用，彼此不替代。把它们当成“哪个更好”来比较，是选型阶段最常见的浪费。

          两个问题定档

          我当时用两个问题给任务定档，比看任何框架对比表都快。

          第一问：路线是否事先固定？ 能列出全部步骤的任务，用工作流；列不出但能列出大半的，用工作流加一个兜底分支；完全列不出的，才考虑自主 Agent。

          第二问：一步做错的代价有多大？ 代价低（答错一句话，重问即可），按第一问的结论执行；代价高（写库、发通知、删除数据、对外承诺），降一档，并在不可逆动作前加人工确认。

          把两问合起来，得到一张判定表：

          任务特征 推荐档位 理由
          单次查询，工具明确 单步工具调用 无状态，错误只影响一次问答
          多步但路线固定 工作流 可预测、可调试、成本低
          步骤开放，错误代价低 自主 Agent 可换路重试，试错成本可接受
          步骤开放，错误代价高 自主 Agent + 确认点 保留灵活性，在不可逆动作前设闸
          任务庞大，需多域专长 多 Agent 分工并行；先确认单 Agent 是否够用

          这张表的用处在于暴露分歧：如果团队在“路线是否固定”上有争议，通常说明任务还没被理解清楚，此时上任何档位都会返工。

          用了框架，不等于就是 Agent

          认为用了框架就是 Agent。 框架是脚手架。不理解循环、观察、终止条件，框架只会让你更快地把一个错误的循环部署上线。

          认为自主度越高越先进。 成本、延迟、不可预测性都随档位上升。把它当成能力等级是方向性错误。

          认为多 Agent 是银弹。 两个 Agent 能做的事，五个 Agent 往往做得更差：通信开销、上下文重复、错误跨角色传播，会吃掉分工带来的收益。多 Agent 值得用的场景很窄——子任务确实需要不同的工具集与权限，且彼此可以并行。

          这一章从“Agent 是什么”讲到“该用哪一档”，中间拆了循环、角色与边界。把这些压缩成一句：Agent 的价值来自它能自己决定下一步，代价同样来自这一点。 选型的本质，就是判断这份自主性能换来什么。

          下一章转向循环内部最关键的一件事：上下文。循环的每一步都要读写上下文，而上下文的质量决定了第 20 步还能不能正常工作。
