          自主度是有价格的

          设想两个团队做同一件事：把杂乱的客户反馈整理成结构化的问题清单。

          A 团队的方案是 workflow：先分类，再按类别走不同的提取模板，最后合并去重。三步，每步都是一次模型调用，流程固化在代码中。B 团队的方案是 Agent：给模型一组工具（读文件、搜索相似反馈、写条目、合并），让它自己决定怎么处理，跑到它认为完成。

          六个月后 A 的方案每天处理 4000 条，B 的处理 900 条。B 的效果在复杂样本上确实更好——那些跨多条反馈的合并判断，Agent 做得比固定模板细。但 B 的失败也更难查：同样的输入，两次运行结果不同，有一半的工单需要人工复核，因为没人能确定它是漏了还是判断了不该合并。

          B 团队并未做错什么，他们只是选择了成本更高的自主度，而没有先问清楚这份自主度能带来什么回报。

          谁在决定下一步

          “是不是 Agent”经常是个错问题。更有用的问题是：它在自主度的哪个位置，为什么在那里。

          最左端是 Copilot：人主导，模型建议，人接受或拒绝。代码补全、行内翻译、IDE 里的重构建议都在这里。往右一格是 workflow：流程由人预先固定，模型只负责其中若干节点的判断，比如“这条工单属于哪个队列”。再往右是 Agent：给定目标，模型自己决定步骤和顺序。最右是多 Agent：多个模型分工、互相审查或竞争。

          判断位置可以用一句话：如果我中途离开，它能自己把事办完并停下来吗？ 能，且停得合理，偏 Agent；不能，那就是 Copilot 或 workflow。

          这句话里其实藏了两个独立问题：谁决定下一步，和谁承担后果。位置越往右，第二个问题的答案越模糊——这也是为什么自主度高的系统在组织里推进得更慢，它不只是技术选型，还是一次责任分配的变更。

          可预测性、评测成本、护栏

          自主度每往右一档，你都要多付三样东西，而且这三样没法靠“更努力”省掉。

          第一笔：可预测性。 同样的输入可能走不同的路径，测试从“断言输出”变成“断言不变量”——比如“不管怎么走，都不能发出超过一封邮件”“不管合并多少次，条目总数不能增加”。写不变量比写断言难得多，而且它只能防住你能想到的坏事。

          第二笔：评测成本。 单步任务可以离线跑一千条样本算准确率；多步任务的失败分布是长尾的，你得设计轨迹级评测，还得专门构造“任务没完成但也没报错”这种最难发现的失败。B 团队一半的人工复核，本质就是在用人力补评测缺口。

          第三笔：护栏必须硬件化。 人盯着的时候可以靠常识兜底；人不在的时候，权限、预算、审批点必须写进系统，而不是写进提示词。提示词是建议，代码才是约束——这句话值得在每个 Agent 项目中反复强调。

          列得出路径，就别用 Agent

          Anthropic 在 2024 年底的《Building effective agents》里把 workflow 和 agent 明确分开，并给了一条很实用的建议：从最简单的方案开始，只在它能买到东西的时候才加复杂度。

          这句话经常被引用错，读成“别用 Agent”。它实际是在说，自主度是花钱买来的，你得知道买到了什么。

          workflow Agent
          路径 人预先定义 模型逐步决定
          失败定位 定位到具体失效步骤 需审阅整条轨迹
          测试 断点断言 不变量 + 抽样复核
          适合 路径可枚举、步骤稳定 路径取决于中间结果
          成本 低且可预测 随任务长度超线性增长

          一个可操作的判断流程是这样的：先把任务的所有可能路径列出来。能列完，用 workflow；列不完但能列出大部分，用 workflow 加一个“兜底分支交给模型”；完全列不出来，才考虑 Agent。

          实践中还有第三种选择，往往比纯 Agent 更好：用 Agent 做规划，用 workflow 做执行。 模型只负责决定“该做哪几件事、什么顺序”，具体的动作由确定的代码执行。这样你既拿到了灵活性，又保住了可测试性——B 团队若采用这种结构，分类和合并的具体动作就能被单元测试覆盖，只有“怎么分组”这一步是不可预测的。

          分阶段配置自主度

          自主度不必是全局的开关，它可以按阶段配。这可能是最被低估的一个技巧。

          以课程助教为例：读取学员进度是确定性的（工具调用，无自主度）；决定讲多深、出什么题，可以让模型自主；但把题发给学员、给作业打分，必须有确认或复核环节。也就是说，同一个系统里，规划段是 Agent，执行段的某些动作是 Copilot，另一些是 workflow。

          把这条思路做成工程，就是给每个动作标一个风险等级，然后按等级决定要不要人确认：

          • 只读操作（查进度、读讲义）→ 自动执行
          • 可逆写操作（存草稿、改标签）→ 自动执行，留审计日志
          • 不可逆写操作（发消息、改成绩、删除数据）→ 必须确认
          • 涉及金钱或对外承诺 → 必须确认 + 预算上限

          这套分级的意义不只是安全，它还让评测变得可行：你不需要对所有轨迹都做人审，只需要对高风险动作的触发点做人审。

          步数、成本、影响半径

          既然自主度有价格，就该有预算。实践中通常只需要三个数：

          步数上限。 超过 N 步还没完成，停下来问人或放弃。这个数不应凭直觉设定，而应从任务分布中推算——如果 95% 的成功任务在 8 步内完成，那 15 步就是很宽松的上限。

          成本上限。 单任务的 token 或金额上限。多步任务的成本是超线性的，一个失控的循环能在数分钟内耗尽单日预算。

          影响半径。 这个任务最坏能改到什么程度。发一封邮件是一个半径，批量更新一万条记录是另一个半径。半径大的动作，确认门槛要高。

          三个数写进代码，不写进提示词。提示词里写“请不要超过 10 步”的团队，最后往往拿到一个跑了 60 步的结果。

          自主度是一个可调参数，而非身份标签。调至哪一档，取决于你能承受多少不可预测性、能付多少评测成本、能给多少动作加护栏。

          下一节拆开循环本身——那是所有自主度的承载体。你会看到它有多脆：任何一步的观察质量下降，后面几步都会连锁走偏。
