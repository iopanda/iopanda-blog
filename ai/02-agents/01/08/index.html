          亲手造一个最小 Agent

          第一次跑通自己写的 Agent 时，最有可能发生的事情是它停不下来。

          它读文件、算数、再读一遍同一个文件、再算一遍同一个算式，轨迹打印到第四十行，费用涨到一个不该出现的数字。你会在这一刻意识到：循环本身不产生智能，它只是把模型的每一次判断串起来。串得对不对，取决于你写了什么。

          这一节用六十行代码把循环、工具协议、终止条件全部手写一遍，不引入任何框架。目的是把前面几节的概念落到能运行的东西上，产品化不在这一节的范围里——写过一遍之后，任何框架对你都不再是黑盒。

          协议、工具表、循环

          一个最小可运行的 Agent 由三部分组成。

          系统提示定义协议。 它规定模型每轮输出的格式：先写 Thought，再给 Action，完成时输出 Final Answer。这个格式不是装饰，它是模型与代码之间的接口——代码要靠它解析动作。

          工具表是能力清单。 一个“工具名 → 函数”的字典。模型只能通过这张表接触世界，表里没有的东西它做不到。

          循环是执行体。 调用模型、解析动作、执行工具、把结果写回上下文、再调用模型。第 2.5 节那个骨架在这里变成可运行的代码。

          这三个部件之外的一切——记忆库、重试策略、权限系统、并发调度——都是工程化加装。先有毛坯，再谈装修。

          完整实现

          下面这段代码，依赖只有 openai 一个包，任何兼容 Chat Completions 的端点都能跑。

          """react_min.py —— 最小 ReAct Agent，零框架。"""
import re
from openai import OpenAI

client = OpenAI()              # 自建端点：OpenAI(base_url=...)
MODEL = "gpt-4o-mini"

SYSTEM = """你是课程助教 Agent，按 ReAct 格式工作，每轮只输出：
Thought: 你的判断
Action: 工具名["参数"]
任务完成时输出：Final Answer: 最终回答
可用工具：read_file["路径"]、calc["算式"]
Observation 由系统注入，你不得编造。"""

def read_file(path: str) -> str:
    with open(path, encoding="utf-8") as f:
        text = f.read()
    # 显式截断：让模型知道它看到的不是全部
    return text[:1500] + ("\n[已截断，原文更长]" if len(text) > 1500 else "")

def calc(expr: str) -> str:
    if not re.fullmatch(r"[\d+\-*/().\s]+", expr):
        return "[错误] 算式含非法字符"
    try:
        return str(eval(expr, {"__builtins__": {}}, {}))
    except Exception as e:
        return f"[错误] {e}"

TOOLS = {"read_file": read_file, "calc": calc}

def run(task: str, max_steps: int = 8) -> str:
    messages = [{"role": "system", "content": SYSTEM},
                {"role": "user", "content": task}]
    seen = set()                                   # 重复动作检测

    for step in range(1, max_steps + 1):           # 终止②：步数上限
        reply = client.chat.completions.create(
            model=MODEL, messages=messages, temperature=0)
        text = reply.choices[0].message.content or ""
        print(f"\n=== step {step} ===\n{text}")

        if "Final Answer:" in text:                # 终止①：任务完成
            return text.split("Final Answer:", 1)[1].strip()

        m = re.search(r'Action:\s*(\w+)\["([^"]+)"\]', text)
        if not m:                                  # 终止③：协议破裂
            return "失败：无法解析 Action"

        name, arg = m.group(1), m.group(2)
        if (name, arg) in seen:                    # 终止④：重复动作
            return "失败：检测到重复动作，判定为停滞"
        seen.add((name, arg))

        try:
            obs = TOOLS[name](arg)                 # Observation 由代码注入
        except Exception as e:
            obs = f"[工具失败] {type(e).__name__}: {e}"

        print(f"--- Observation: {obs[:200]}")
        messages += [{"role": "assistant", "content": text},
                     {"role": "user", "content": f"Observation: {obs}"}]

    return "失败：达到步数上限"

if __name__ == "__main__":
    print(run("读取 homework/grades.txt，算全班平均分，指出最高分是谁。"))

          一次运行的轨迹

          === step 1 ===
Thought: 需要先读取成绩文件，才能计算平均分。
Action: read_file["homework/grades.txt"]
--- Observation: 张三 85 分，李四 90 分，王五 92 分（共 3 人）。

=== step 2 ===
Thought: 已拿到成绩。先算平均分。
Action: calc["(85+90+92)/3"]
--- Observation: 89.0

=== step 3 ===
Thought: 平均分 89.0；三人中 92 分最高。
Final Answer: 全班平均分 89.0 分，最高分是王五（92 分）。
          text

          这段轨迹里有两处值得停下来看。

          第一处是第一步：模型没有直接报出平均分，而是先调用工具。这是协议在起作用——系统提示要求它在拿到观察之前不得给出结论。协议承担了纪律的职责，这是第 2.5 节说的“把推理钉在外部事实上”的具体形式。

          第二处是第三步：它选择停下。这个决定是模型做的，代码只负责识别并放行。也就是说，正常终止由模型判断，兜底终止由代码判断——两者必须同时存在。

          它停不下来的时候

          上下文无限增长。 每轮把完整轨迹追加进 messages，二十步之后请求体积翻几倍，直到撞上窗口上限开始失忆。修法是设长度阈值，超限时只保留 system 消息与最近若干轮。更彻底的做法（下一章）是把早期轨迹压缩成结构化笔记，而不是原始文本。

          观察不截断。 一个读取工具把五兆的讲义全文塞进 Observation，一轮就吃掉大半个窗口。修法是工具侧统一限长，并且在返回内容里显式标注已截断——否则模型会以为看到的就是全部。

          没有停滞检测。 只有步数上限是不够的：模型可能在八步里重复同一个失败动作，烧完预算却毫无进展。上面的代码里 seen 集合就是为此存在：同一个动作被重复请求，意味着观察没有带来新信息，此时继续循环没有意义。

          这三个错误的共同点是，它们都不会报错。系统会正常返回一个结果，只是结果不对。这也是为什么轨迹打印必须从第一版开始，而不能等到出问题再加。

          框架藏起来的那部分，正是你要调的

          框架会替你隐藏机制：在可视化编排里连几个节点，循环就自动转起来了。问题在于，行为异常时你要调试的恰恰是被隐藏的那部分——重复调用、突然失忆、停不下来，这些现象在框架的抽象层里没有对应的概念。

          手写过一遍之后，再看任何框架，你看到的是同一组东西：状态存在哪里、观察怎么注入、终止由谁负责、错误如何传播。框架的价值在于把这几件事工程化——持久化、断点续跑、并发、人工确认——而不是让你不用理解它们。

          下一篇会沿着这条线索讲选型：什么时候该用框架，什么时候一个函数就够了。

          六十行代码足以跑通一个 Agent。剩下的九成工作量在别处：让观察可靠、让状态可控、让失败可见。

          把工具拿掉，再跑一次

          把 SYSTEM 改成“永远不要使用工具，直接回答”，再跑同一个任务。观察两件事：轨迹会变成什么形状，以及结果与真实数据是否一致。这道练习不需要写代码，它检验的是第 2.1 节那三条判据——去掉行动之后，这个程序还剩下什么。
