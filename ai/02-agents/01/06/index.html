          循环：Agent 的心跳

          设想这样一条轨迹。任务是把一份 PDF 里的表格提取成 JSON。Agent 走了十一步，输出一份结构完整的 JSON，声明任务完成。人工核对时发现，其中七行数据是错的。

          回放轨迹后原因很清楚：第二步的文件读取工具因为编码问题返回了空字符串，而循环把这当成一个正常观察写回了上下文。模型看到的是“文件内容为空”，它没有报错，也没有追问，而是依据任务描述和先验知识把表格“补”了出来——补得相当合理，格式完全正确。后面的九步都建立在这份捏造的数据上。

          这条轨迹说明了循环的两个事实。第一，循环让系统具备了多步能力；第二，循环同时把每一个中间结果的错误，放大成后续所有决策的前提。理解后者比理解前者更重要，因为前者是宣传语，后者是工程现实。

          为什么必须循环

          如果不是为了处理不确定性，一次生成就够了。循环存在的理由可以归结为四条，按重要性排列。

          信息在行动之后才出现。 回答“外键和级联删除有什么区别”之前，系统并不知道课程资料里是怎么写的。一次生成只能依赖模型参数中已有的知识；循环允许它先查、再看、后答。

          后一步依赖前一步的输出。 检索到什么决定怎么组织回答；学员的实际进度决定练习题难度。这种依赖链无法预先展开成固定脚本——这正是第 2.4 节讲的、workflow 列不出路径的情形。

          环境会失败。 工具超时、返回为空、权限不足、接口变更。循环提供了唯一的补救位置：看到失败，换一条路。一次生成没有第二次机会。

          错误可以局部化。 一次生成二十步的任务，中间错一步，整段输出作废；循环里每一步只看当前观察，错了重做这一步，前面九步的成果仍然有效。这条性质是循环最实际的收益，也是最容易被忽视的——它意味着你把一个长任务的可靠性，从“整体正确”降级为“单步正确 + 可重试”。

          最脆的是观察

          循环的四个环节是感知、规划、行动、观察。教科书式的讲解会平均分配篇幅，但从故障分布看，它们的权重极不平均。

          规划环节的失效最显眼：模型判断错了方向，或是在没有查证的情况下宣称“已查到”。这类错误容易发现，因为轨迹里的推理是明文的。

          行动环节的失效最常见于工程实现：工具名拼错、参数类型不符、解析器无法从模型输出中提取出结构化动作。这类问题有明确的报错，修复也直接。

          观察环节的失效最隐蔽，也最危险。工具调用“成功”了——HTTP 200，进程退出码 0——但返回的内容是空的、被截断的、或者是一段错误信息被当成了数据。模型没有能力区分“这里确实没有内容”和“这里本该有内容但读取失败”，它会用先验知识填补空白，然后继续往下走。

          本文开头那条轨迹，失效就在观察环节。它没有报错，没有异常，只在第七行数据的语义上与原文不符——而这一步之后，系统一直在正确地处理错误的数据。

          ReAct：把推理钉在外部事实上

          ReAct（Yao et al., 2022, arXiv:2210.03629）的核心主张可以用一句话概括：让推理与行动交替进行，使想法持续暴露在外部反馈之下。

          它的形式是三段交错：Thought 写下当前判断与下一步意图，Action 执行一个具体动作，Observation 接收真实结果。与思维链（chain-of-thought）的关键差别在第三段：思维链是一次性想完再给答案，推理过程不与外部世界接触，因此错误无法被发现；ReAct 每一步都要拿到外部结果才能继续，错误被迫提前暴露。

          这个设计有一个副作用值得注意：ReAct 把“模型在想什么”变成了可观测的产物。思维链的输出是给人看的解释，未必是真实推理过程；而 ReAct 的 Thought 后面必须跟一个 Action，Action 的后果由环境裁决。判断是否一致，有外部依据。

          观察是瓶颈

          如果只能在这一节留下一条工程建议，是这一条：把工具返回当作产品接口来设计，而不是当作调试输出。

          具体来说，有三个做法能显著降低观察环节的故障率。

          区分“空”与“失败”。 工具返回空列表和工具失败必须有不同的表示。前者是 {"items": [], "ok": true}，后者是 {"error": "ENCODING", "detail": "utf-8 decode failed at byte 1024", "retryable": true}。让模型读到结构化差异，它才可能做出不同决策。返回 null 或者让异常冒泡到框架里被吞掉，等于把决策权交给了模型的想象。

          主动截断，并显式标注。 工具返回超过预算时必须截断，但截断本身要写在返回内容里——{"truncated": true, "shown": 2000, "total": 18000}。否则模型会以为看到的就是全部。

          错误信息要有建议。 retryable: false 比一句“操作失败”有用得多，它直接告诉模型换路，而不是重试。

          这三条都不复杂，但它们决定了循环在第 5 步是面对现实，还是面对幻觉。

          误差累积：为什么第 12 步会突然崩

          单步成功率 95% 听起来很好。如果任务需要十二步全部正确，整体成功率是 0.95¹² ≈ 54%。二十步则是 36%。

          这个算术解释了为什么多步 Agent 的表现常常“突然变差”：模型并没有在第 12 步变笨；前面每一步都在收取利息。它也解释了为什么降低步数比提升单步质量更划算——把平均步数从 20 降到 8，成功率能从 36% 提到 66%，这通常比换一个更强的模型容易。

          工程上的应对有三种：减少步数（合并工具、提供更高层的原语）、提高单步可靠性（更好的观察、更明确的指令）、以及在关键节点插入可验证的检查点（比如“提取出的 JSON 必须能通过 schema 校验，否则重做”）。第三种最容易被忽略，效果也最直接——它把误差累积截断在一处。

          终止：责任在代码，不在模型

          循环必须有终止条件，这一点没有争议；有争议的是谁来负责终止。

          模型可以宣告完成，但它没有可靠的自我停止能力。它会在该停的时候继续找“还差的一步”，也会在没完成时宣布完成。因此终止条件必须由代码持有，且至少有三层。

          任务完成：模型输出终止信号，或产出一个通过校验的最终答案。这一层负责正确结束。

          预算上限：步数、token、金额、墙钟时间。任意一项超限即中断，并向用户报告已完成的进度。这一层负责兜底。

          重复检测：连续若干轮的动作序列相同，或上下文没有实质变化。这一层负责识别“世界没有变化但还在继续行动”的状态——它通常是观察环节故障的外部表征。

          还有第四种终止，常在设计中缺席：承认失败。查不到资料时，向用户说明并建议替代方案，比继续重试更专业。这需要在提示中明确允许模型放弃，也需要在代码里给放弃留一条正常的退出路径，而不是让它以异常收场。

          轨迹：循环的副产品，也是主要资产

          循环的每一轮都会产生一组 Thought、Action、Observation。把它们按顺序记录下来，就是轨迹（trace）。

          轨迹的价值在四个地方：调试时它是唯一能定位“想错、做错还是看错”的材料；对用户它是可解释性；对评测它是第 2.7 节的验收对象；对改进它是把成功路径蒸馏回提示词的原料。

          因此从第一版实现开始就应该打印轨迹，而不是等到出问题再加。下面是一个最小循环的骨架，省略了模型调用与工具实现：

          context = task                      # 任务描述
trace, seen_actions = [], set()

for step in range(MAX_STEPS):       # 终止②：预算上限
    thought, action = model(context)          # 规划
    trace.append(("thought", thought))

    if action.kind == "final":                # 终止①：任务完成
        return action.payload, trace

    if action.signature in seen_actions:      # 终止③：重复动作
        return fail("no progress", trace)
    seen_actions.add(action.signature)

    try:
        obs = call_tool(action)               # 行动
    except ToolError as e:
        obs = {"error": e.code, "retryable": e.retryable}   # 失败也是观察

    trace.append(("observation", obs))
    context += render(thought, action, obs)   # 观察回流：缺这一步，循环无效

return fail("budget exhausted", trace)        # 终止②：预算耗尽
          python

          这段代码里有三处值得注意。失败被转换成结构化的观察，而不是抛给调用方；动作签名进入去重集合，用于识别停滞；唯一改变上下文的语句是 context +=，如果这一行缺失，循环在形式上完整、在功能上无效——这正是第 2.1 节第二条判据的代码形态。

          循环给了系统多步能力，同时把每一步的错误变成后续的前提。因此循环的质量不取决于它转得多快，而取决于每一步的观察有多可靠。

          而观察的可靠性，最终受限于模型能理解什么、能记住什么。下一节讨论这条边界。
