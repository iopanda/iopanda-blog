          引言：当模型开始动手

          设想一家公司给做了半年的客服系统接上大模型。上线头一个月，回答质量的评价明显好转，比人工客服还高。第二个月，产品经理换了个统计口径，去看“用户请求真正被解决”的比例——数字立刻塌了下来。

          差的不是语言能力。用户说“把上周那张发票重开一下，抬头改成公司名”，模型的回答标准、礼貌、格式完美，然后建议用户“联系财务部门处理”。它答对了问题，但没办成事。要办成这件事，系统得先查订单，再调开票接口，再确认新发票号回给用户——三个动作，中间任何一步失败都要换路重试。模型在对话里做得很好，在流程里一步都走不了。

          这不是模型不够聪明。换成更强的模型，那个数字会好一点，然后停住。瓶颈不在语言，在行动。

          这一章讲的就是把“会回答”变成“会办事”的那一层。它不神秘，但工程复杂度被严重低估了：你要给模型工具，要让它在多轮里记住做过什么，要在它跑偏时拉回来，还要在它准备做危险动作时拦住。这些合起来，就是今天被叫作 Agent 的东西。

          课程助教：全书的主线

          我们有一条贯穿全书的线：课程助教（Course TA）。

          第一部分把它训练成了一个会回答的模型——给定问题能生成结构清晰、有依据的解释，评测报告显示它在课程问答集上达标。随后便会发现它不够用。学员问“帮我复习外键，按我现在的进度出五道题”，它给出的是一段关于外键的通用讲解。它不知道这个学员上周卡在级联删除，不能把题存成文件，也查不到做题记录。

          从这一章开始，我们给它加东西：循环与工具（本章）、上下文工程、规划、记忆，最后是评测与安全。每一节把这个系统往前推一步，并尽量诚实地说清楚这一步带来了多少复杂度。

          如果你想要一本“三天学会 Agent 框架”的书，这一章会让你失望——它更想解释这些框架为何形成当前形态，以及各自在哪些环节做了简化。

          这一章要确定什么

          第一节先把定义确定下来。今天“Agent”被用得太松：prompt 里写一句 “you are an agent” 的聊天框叫 Agent，一个固定三步的流水线也叫 Agent。这条判据要能在评审里用起来：出了问题，指着它说清谁负责。谁决定下一步，失败了谁负责重试，什么时候停。

          第二节解释时机。Agent 这个概念比大模型早三十年，1995 年就有成熟的形式化定义，为什么直到 2023 年才有像样的产品？答案要复杂一些：三个条件在同一时间窗口里到位。模型能可靠地调用工具、上下文窗口大到装得下多轮观察、推理成本低到可以为一个任务消耗数十次调用。

          第三节拆开运行循环。这是 Agent 真正的心脏——规划、行动、观察、再规划。你会看到这个循环有多脆：任何一步的观察质量下降，后面几步都会连锁走偏。理解这一点，才能理解为什么“加一个工具”从来不是加一行配置的事。

          第四节讲边界。模型的能力上限就是 Agent 的上限，但反过来不成立：很强的模型放进糟糕的循环里，表现会比弱模型放进好循环里更差。这一节给几个具体边界——长上下文里的信息丢失、工具参数幻觉、多步任务的误差累积。

          第五、六节动手。先写一个不依赖任何框架的 ReAct Agent，把循环、工具协议、停止条件全部手写一遍。一百五十行左右，跑通之后，框架中那些看似神奇的行为将不再难以理解。

          最后一节拉远看生态：哪些是真 Agent，哪些是包装过的 workflow，选型时该问什么。

          怎么读

          这一章假设你读过第一部分，知道 token、上下文窗口、采样这些概念，也写过多线程或异步任务——Agent 的循环与调度问题跟它们有大量重叠，许多失效模式是重复出现的。

          每节结尾不再有“思考题”，但会留一个具体问题或一组数字，你可以拿自己的系统去对。代码不追求能直接搬进生产，追求让你看清机制；生产实现的问题会在讨论边界时点出来。

          准备好了就往下走。第一个问题是：你手上那个东西，到底算不算 Agent。
