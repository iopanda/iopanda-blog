          为什么需要多 Agent

          02.05 让课程助教「记得住」:会话记忆、长期档案、向量检索、遗忘与隐私防线全部就位,单 Agent 的五大件——模型、循环、上下文、工具、记忆——至此集齐。可集齐之后你会撞上一堵新墙:有些任务,一个 Agent 就是做不好。让它同时当检索员、批改员、出题员和裁判,它要么上下文装不下,要么角色互相打架,要么十几步的长流程走着走着就偏了。本章是 02.06 Multi-Agent Systems 的第一课,回答:多 Agent 是什么、单 Agent 的天花板在哪、业界标杆 MetaGPT 怎么把「软件公司」搬进系统,以及多 Agent 会带来哪些新问题——最后这盆冷水,比前面的鸡汤更重要。

          学习目标:学完本章,你将能够——

          1. 说出多 Agent 的定义,以及它与「多个模型进程」的本质区别;
          2. 用「上下文有限、角色冲突、长流程失控」解释单 Agent 的三个天花板;
          3. 复述 MetaGPT 软件团队的五个角色与 SOP 思想,并映射到课程助教场景;
          4. 列出多 Agent 引入的四大新问题:通信成本、级联错误、责任归属、成本爆炸;
          5. 用三条初判标准判断一个任务是否值得上多 Agent。

          1. 概念:多 Agent 是什么

          • 多 Agent 系统:多个角色化的 Agent 单元分工协作完成任务,而不是一个「全能 Agent」单打独斗。这里「角色化」是关键词——每个单元只承担一个清晰角色,像公司里的岗位一样。
          • 回看 02.01 的定义:一个 Agent = 模型 + 循环 + 上下文 + 工具 + 记忆。多 Agent 就是把这套单元复制多份,每份换一张不同的角色卡(system prompt)、配不同的工具与记忆,再加一层「协作协议」(谁指挥谁、传什么、怎么结束)。
          • 澄清一个常见误解:多 Agent ≠ 多个模型进程。绝大多数实现是同一个模型配上 N 份不同的 system prompt 与工具集(也可以混用不同模型,成本与质量另算)。真正新增的,是单元之间那层「组织关系」。
          • 相关术语:角色(role)、编排(orchestration)、中间产物(artifact,一个角色的输出是下一个角色的输入)、SOP(标准作业程序,把团队流程固化下来)。
          • 课程助教场景:批改作业这件事,一个单元要同时是「查档案的人、按评分细则打分的人、写评语鼓励学员的人」;多 Agent 则拆成三个角色各干各的——这正是 02.05 末篇之后,单 Agent 能力齐备仍不够用的原因。

          1.1 单 Agent 全能型 vs 多 Agent 角色化

          维度 单 Agent 全能型 多 Agent 角色化
          角色卡 一张,越长越互相打架 每单元一张,短而聚焦
          上下文 全部知识塞一个窗口 按角色切分,各装各的
          流程 一个循环走到底 中间产物接力,每步可查
          出错定位 整条轨迹里猜 按角色/步骤切分定位
          成本 一次任务一次调用链 N 次调用 + 通信,明显更贵

          2. 为什么需要:单 Agent 的三个天花板

          2.1 上下文有限

          • 一个助教要同时装「课程讲义全文、学员长期档案(02.05)、评分细则、出题模板、历史会话」——单一上下文窗口装不下,装了也会互相稀释(呼应 02.02 的 02 章上下文窗口管理)。
          • 分工后:知识按角色切分而不是全塞一人——检索员只装资料索引,批改员只装评分细则,出题员只装题型模板。每个单元上下文变小、更聚焦,单个调用质量反而更高。

          2.2 角色冲突

          • 在一张 system prompt 里写「你是严格批改员,答案有错必须扣分」,又写「你是亲切助教,要多多鼓励学员」——两套行为准则在同一上下文里互斥(呼应 02.02 的 01 章角色层:顺序即优先级,约束互相打架时模型只能猜)。
          • 后果很典型:批改不严(该扣的不扣),鼓励也假(套话连篇)。同一上下文装不下两套互相矛盾的人格;分开成两个 Agent,每份 prompt 才能一致到底。

          2.3 长流程失控

          • 「查资料 → 想方案 → 批改 → 出报告」十几步的单循环,中间任何一步悄悄跑偏,后续步骤会在错误的基线上继续放大(呼应 02.03 长链规划难以中途校验)。
          • 分工后:检索片段、计算结果、评语草稿都成为独立的中间产物,可以单独检查、单独重跑。出问题时能定位「是哪一步的产物错了」,而不是重放整条轨迹。

          3. 作用:多 Agent 在 Agent 架构中的位置

          ┌──────────────────────────────────────────────┐
│ 应用层:课程助教产品(学员提问/作业批改入口)      │
├──────────────────────────────────────────────┤
│ 编排层(本章起新增):协作协议                     │
│   ├─ 谁指挥谁:编排者 / 流水线 / 辩论(03 章)     │
│   ├─ 传什么:消息与结构化结果(04 章)             │
│   └─ 何时结束:汇总、裁决、超时                  │
├──────────────────────────────────────────────┤
│ 单元层:多个角色化 Agent(每个 = 02.01 五要素) │
│   检索员 │ 批改员 │ 出题员 │ 裁判                │
└──────────────────────────────────────────────┘

          • 多 Agent 不是「架构升级」,而是复杂度升级:每多一个单元,就多一份 prompt 要维护、多条消息要传、多个失败点要排查。所以默认答案永远是单 Agent(06 章给完整决策清单),本模块只回答一个问题:什么时候值得。
          • 三条初判标准(详细版留到 06 章):① 任务是否同时需要两类以上互斥的技能或知识域?② 能否拆成边界清晰、可独立校验的子任务?③ 每个子任务是否都能由「一个小上下文 + 少量工具」的单元完成?三条全中,才考虑多 Agent。

          4. 详细介绍:MetaGPT——把软件公司搬进多 Agent

          4.1 五个角色与 SOP

          • MetaGPT(2023,论文见引用)把一次软件开发组织成一家「软件公司」:拿到一句话需求后,产品经理产出需求文档(PRD),架构师产出系统设计,项目经理拆解任务,工程师写代码,QA 工程师写测试并验证可运行性。
          • 核心思想 Code = SOP(Team):把人类团队的标准作业程序固化成角色流水线,每个角色的输出是结构化文档(PRD、设计、测试报告),而不是随口聊天——文档即中间产物,下游角色拿着文档干活,出错可以追溯到具体某份文档。
          • 论文消融实验很有说服力:角色从只有工程师 1 个,补齐到产品/架构/项目/QA 4 个后,生成代码从「完全不可运行」提升到「基本一次到位」,人工修订次数从 812 次降到 14 次。分工本身就在提升质量——每份 prompt 变短了,每个中间产物变可审计了。

          4.2 映射回课程助教

          MetaGPT 角色 产出 课程助教对应物
          产品经理 PRD(需求拆解、用户故事) 问题拆解卡:问题类型、需要哪些资料、输出要求
          架构师 系统设计(数据表、接口) 答题蓝图:引用哪些章节、调用什么工具、篇幅结构
          工程师 代码实现 答案正文(检索员取回的片段在此组装)
          QA 工程师 测试用例、可运行性检查 答案自检:是否回指资料、格式是否合规、结论是否一致

          4.3 结构骨架演示

          # team_skeleton.py:多 Agent「软件团队」骨架——角色卡与中间产物接力
# 真实场景里每个 act() 是一次带专属 system prompt 的模型调用(01.04 的服务);
# 这里用假模型占位,让你先看清「分工 + 产物接力」的结构,再替换成真实 API。

def fake_pm(requirement: str) -> str:
    # 产品经理:把一句话需求变成需求文档
    return "PRD:功能「每日一题」= 选题 + 自动批改 + 按学员进度出题;见 requirement-pool.md"

def fake_arch(prd: str) -> str:
    # 架构师:把 PRD 变成系统设计
    return "设计:新增 data/scores.db 与 quiz.py,复用 02.05 的档案表;见 design.md"

def fake_engineer(design: str) -> str:
    # 工程师:把设计变成代码
    return "代码:quiz.py 实现出题与计分,py_compile 通过;见 quiz.py"

def fake_qa(code: str) -> str:
    # QA:验证可运行性
    return "测试:3 条用例全过(正常出题/无题可出/重复练习);见 test_report.md"

FAKE_MODEL = {"产品经理": fake_pm, "架构师": fake_arch,
              "工程师": fake_engineer, "QA": fake_qa}

class RoleAgent:
    """一个角色化 Agent = 角色名 + 独占 system prompt(02.02 四层法)"""

    def __init__(self, name: str):
        self.name = name
        self.system_prompt = "你是%s,只产出本角色的中间产物,不越界替别人干活。" % name

    def act(self, upstream_artifact: str) -> str:
        """把上游产物加工成本角色的中间产物,传给下一个角色"""
        return FAKE_MODEL[self.name](upstream_artifact)

if __name__ == "__main__":
    pipeline = [RoleAgent(n) for n in ["产品经理", "架构师", "工程师", "QA"]]
    artifact = "一句话需求:给课程助教加「每日一题」功能"
    for agent in pipeline:
        artifact = agent.act(artifact)
        print("[%s] 产出 -> %s" % (agent.name, artifact))

          5. 动手活动:给课程助教画角色分工图

          动手活动:从「全能助教」到「角色团队」

          目标:产出 roles-vs-mega.md:左边是「全能单 Agent」会怎么崩,右边是你的角色分工方案。

          步骤:

          1. 列出课程助教日常的 4 类任务:检索答疑、作业批改、进度跟踪(02.05 档案)、出题;
          2. 对每个任务写一条「全能版 system prompt 里的要求」,并指出它与其他任务要求的冲突点(例如「批改要严格」vs「答疑要鼓励」);
          3. 把 4 类任务分给 3~4 个角色化 Agent,给每个角色写一句职责声明 + 它独占的工具与记忆(检索员配讲义索引,批改员配评分细则与成绩档案);
          4. 跑一遍上面 4.3 的 team_skeleton.py,把软件团队的四个角色换成你的角色,观察产物接力;
          5. 用三条初判标准,写出「哪一类任务我仍然坚持单 Agent 做」。

          完成标准:能指出至少两处「角色冲突」原文;每个角色的职责一句话说清、工具清单不重叠;对保留单 Agent 的任务能给出理由(通常是短问答,不值得上多 Agent)。

          6. 新引入的问题:多 Agent 不是免费的

          新问题 表现 何时在本模块展开
          通信成本 消息在单元间往返,数量随角色数近似平方增长;角色间还可能闲聊 04 章:消息 schema、超时
          级联错误 上游一个小错(检索跑偏)被下游放大成整篇错误答案 02 章:schema 校验;06 章:失败模式
          责任归属 答错了,分不清是拆题错、检索错还是批改错 02.07:tracing 轨迹级定位
          成本爆炸 N 个单元各带一份上下文,同一份资料被反复读入;Anthropic 实测其多 Agent 研究系统的 token 消耗约为单 Agent 的 15 倍 06 章:预算上限与「能单就不多」
          • 注意最后一行不是夸张:多 Agent 的收益是「质量与可控性」,代价是「token 与延迟」。一个任务值不值得多花 10 倍 token,是每次上多 Agent 前必须先回答的问题。

          7. 边界:什么时候别上多 Agent

          • 任务只有单一知识域、一轮能答完(如「主键和外键的区别」)→ 单 Agent 就够了,多 Agent 只是把钱烧在拆题上。
          • 任务不可拆(「给这段代码起个名字」)→ 拆不出子任务,编排层是空转。
          • 子任务之间强耦合、必须共享同一份最新状态 → 拆开反而要付出同步成本(04 章共享状态问题)。
          • 尚无稳定评测(02.07 会讲)→ 多 Agent 把失败面扩大 N 倍,没有评测前先别放大复杂度。本模块 06 章会给完整的决策清单,现在记住默认答案即可:能单 Agent 解决,就不要上多 Agent。

          8. 总结

          概念 一句话
          多 Agent 多个角色化 Agent 单元 + 协作协议,而非一个全能 Agent
          为什么需要 单 Agent 上下文有限、角色冲突、长流程失控
          标杆示例 MetaGPT:软件公司五角色 + SOP,结构化中间产物接力
          质量来源 prompt 变短聚焦 + 中间产物可审计,消融实验角色越多修订越少
          代价 通信成本、级联错误、责任归属难、成本爆炸
          默认答案 能单 Agent 解决就不要上多 Agent(06 章决策清单)

          思考题:为什么「让一个 Agent 既严格批改又热情鼓励」大概率两头不讨好,而拆成批改员与答疑员两个 Agent 后,两边的表现反而都会变好?如果 MetaGPT 让四个角色自由聊天而不产出文档,它还会那么有效吗?

          参考答案

          两套互斥的行为准则挤在同一上下文里,模型只能折中,批改不严、鼓励失真;拆开后每份 system prompt 短而一致,模型按字面执行的概率更高(呼应 02.02 的 01 章:具体一致优于抽象全能)。MetaGPT 的关键不在「多角色聊天」,而在结构化文档:文档是边界清晰的中间产物,下游角色拿到的是可审计、可回退的输入;自由聊天会让错误与观点在消息里滚雪球,既难追溯也难复用——这正是 02~04 章要解决的「传什么、怎么传」问题。
