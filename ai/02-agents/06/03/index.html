          协作模式编排者与工作者

          01 章讲了「为什么需要多 Agent」:角色冲突、上下文有限、长流程失控——结论是拆。可「拆」有很多种拆法:谁负责拆?拆完谁先干?干完怎么合?让几个 Agent 自由聊天是一种答案,但实践中聊着聊着就跑题、没人对结果负责。本章介绍最流行、也最适合课程助教起步的一种协作模式:编排者-工作者(orchestrator-workers)——一个编排者( orchestrator)拆任务、派活、校验、汇总,一群各司其职的 worker 只负责把自己那一亩三分地干好。Anthropic 的工程实践把它列为最常用的 workflow 模式之一;读完本章,你会亲手把课程助教拆成「检索员 + 计算员 + 回答员」三个 worker,并理解这套模式为什么清晰、可控、可观测。

          学习目标:学完本章,你将能够——

          1. 说清编排者-工作者模式的角色划分与一次完整协作的四个阶段;
          2. 解释它为什么比「自由讨论式多 Agent」更流行(清晰/可控/可观测);
          3. 应用三条设计要点:worker 单一职责、结果 schema 明确、编排者决定下一步;
          4. 实现并运行一个「检索员 + 计算员 + 回答员」三 worker 的课程助教 Demo;
          5. 说出编排者模式的主要失败点(拆错任务、schema 不合法、编排者成为瓶颈)。

          1. 概念:编排者-工作者模式

          • 编排者-工作者(orchestrator-workers):一个中央 Agent(编排者)接收任务后,动态地把任务拆成子任务、分配给专门的 worker Agent,最后收集并汇总各 worker 的结果。与 01 章 MetaGPT 的固定流水线不同,这里的「拆成几块、派给谁」是针对当前输入现场决定的,不是预先写死的管道。
          • 两个角色,责任边界非常清晰:
            • 编排者(orchestrator):负责思考——理解任务、决定拆法、判断 worker 结果是否够好、要不要追加一轮、何时收尾。它不亲自干苦力活。
            • 工作者(worker):负责执行——每个 worker 只擅长一件事(检索、计算、翻译……),拿到明确的子任务,干完返回结构化结果,不互相商量。
          • 把 01 章的软件团队套进来:MetaGPT 的「产品经理 + 架构师 + 项目经理」大体承担编排职责(拆解与设计),「工程师 + QA」是 worker;而本章的编排者是运行时动态决策的那一个角色。
          • 课程助教示例:学员问「我第三章练习平均分在班里什么水平?」——编排者把它拆成三步:检索员查成绩档案 → 计算员算平均分与差距 → 回答员把数字组织成学员能懂的话。

          2. 为什么流行:清晰、可控、可观测

          维度 自由讨论式多 Agent(聊天广场) 编排者-工作者
          谁决定下一步 没有,靠 Agent 自发接话 编排者一人决策,路径唯一
          消息量 随角色数近似平方增长,闲聊多 树状:编排者↔worker,无横向闲聊
          可控性 无法预判谁会接话、聊几轮 可加超时、重试、人工闸门
          可观测性 轨迹是一锅粥 每步「派给谁/返回什么」都可打印审计
          成本 不可控,可能聊到地老天荒 子任务数封顶,近似可预算
          • 清晰:职责树状展开,「谁负责什么」写进代码与角色卡,新人读代码就能复述整个流程。
          • 可控:编排者是唯一的决策点——想限制 worker 数量、想让某步必须人工确认、想对某个 worker 的结果重试,都只改一处。
          • 可观测:一次协作 = 一串「派活→返回」记录(本章 Demo 会打印给你看)。这正是 02.07 可观测性的雏形:每步的输入输出都在,出问题能定位到具体 worker。

          3. 作用:编排者在协作模式谱系中的位置

          模式 结构 强项 弱项 本章/后续
          编排者-工作者 中央拆解,树状派活 灵活、可控、可观测 编排者贵;拆错全队白跑 本章
          流水线 A→B→C 固定接力 快、便宜、稳定 僵,改流程要改代码 03 章
          辩论 多 Agent 各执一词再裁决 质量高,暴露盲点 慢、贵,可能互相附和 03 章
          • 选型直觉:子任务无法预先枚举(每次任务形状不同)时选编排者;子任务形状固定时流水线更便宜;答案质量攸关且存在对错之争时考虑辩论。
          • 编排者-工作者非常适合课程助教这种「宽而不深」的任务面:答疑、批改、统计、出题,每次来什么问题不一样,但都能拆成「查 → 算 → 组织」之类的固定技能组合。

          4. 详细介绍:三条设计要点

          4.1 worker 单一职责

          • 一个 worker 只做一件事:检索员只查不算,计算员只算不查,回答员只组织语言。判断标准:给 worker 写 system prompt 时,能不能用一句话说完它的职责且不含「以及」?
          • 好处:prompt 短而聚焦(02.02 的经验在这里复用);工具集最小(检索员只需要查档案的工具,不给它发计算器);出错时嫌疑犯只有一个人。

          4.2 结果 schema 明确

          • worker 之间不靠「人话段落」交接,而靠结构化结果(如 {"ok": true, "scores": [85, 90, 78]}):编排者用代码校验字段,缺了立刻报错,而不是让下游模型去猜。
          • 这是 04 章通信协议的地基:先定「传什么形状的数据」,再谈「怎么传」。Demo 里的 require() 就是最小版 schema 校验——失败在源头暴露,不让错误级联到下游。

          4.3 编排者决定下一步

          • 编排者不只是「把任务列表跑一遍」:它要决定——拆几个子任务、派给谁、worker 失败了是重试还是换人、结果不够好要不要追加一轮、何时收尾汇总。Demo 里这些决策写在代码中(便于离线跑),真实系统里是编排者的一次次 LLM 调用。
          • 编排者的 prompt 是全系统杠杆最高的组件:拆解方向错了,所有 worker 都在错误的路线上白干;小改动可能引起全队行为的大变化。所以编排者的角色卡值得单独反复打磨与评测(02.07 会讲怎么测)。

          5. 动手活动:课程助教「检索员+计算员+回答员」Demo

          动手活动:三 worker 编排 Demo(查 + 算 + 答)

          目标:运行 orchestrator_workers.py,让三个 worker 协作回答「我第三章三次练习多少分、平均分什么水平」,并观察编排轨迹。

          步骤:

          1. 新建 orchestrator_workers.py,粘贴下面代码(worker 内部用规则实现,离线可跑;真实场景把每个 run() 换成一次带专属 system prompt 的模型调用);
          2. 运行 python3 orchestrator_workers.py,对照输出逐行说出「现在是谁在干活」;
          3. 把 plan() 里的小红分支改掉,让问题「小红平均分多少」也查小明——观察编排者拆错任务时全队如何白跑;
          4. 删掉 Answerer.run() 返回里的 "answer" 字段再跑,观察 require() 如何拦住缺字段的结果;
          5. 在 reports/orchestrator-notes.md 里记录:为什么计算员不该自己查档案、回答员不该自己算数。

          完成标准:一次运行能看到完整的「提问 → 三次派活 → 三次返回 → 汇总交付」轨迹;未知学员的错误在源头被捕获并打印;能说出若换成真实 LLM worker,代码里只需替换哪一处。

          # orchestrator_workers.py:课程助教「编排者-工作者」Demo
# 检索员 + 计算员 + 回答员 三 worker 协作完成「查 + 算 + 答」(离线可跑)
# 真实场景:每个 worker 的 run() 内部换成一次带专属 system prompt 的模型调用
# (01.04 的服务),编排者的 plan() 换成一次 LLM 拆解调用。

CLASS_AVG = 86.0                     # 第三章班级平均分(教学统计)
DISPLAY = {"xiaoming": "小明", "xiaohong": "小红"}   # 学员档案的显示名

class Retriever:
    """检索员:单一职责——只查不算。成绩来自 02.05 的长期档案(dict 模拟)"""

    name = "retriever"

    def __init__(self):
        self.grades = {              # {学员: 第三章三次练习成绩}
            "xiaoming": [85, 90, 78],
            "xiaohong": [92, 88, 95],
        }

    def run(self, payload):
        learner = payload["learner_id"]
        scores = self.grades.get(learner)
        if scores is None:
            return {"ok": False, "error": "档案查无此学员: %s" % learner}
        return {"ok": True, "scores": scores, "learner_id": learner}

class Calculator:
    """计算员:单一职责——只算不查"""

    name = "calculator"

    def run(self, payload):
        scores = payload["scores"]
        avg = sum(scores) / len(scores)
        gap = avg - CLASS_AVG
        return {"ok": True, "avg": round(avg, 1), "gap": round(gap, 1)}

class Answerer:
    """回答员:单一职责——只组织语言。真实场景此处调用 LLM 生成个性化评语"""

    name = "answerer"

    def run(self, payload):
        name = DISPLAY[payload["learner_id"]]
        avg, gap = payload["avg"], payload["gap"]
        trend = "高于" if gap >= 0 else "低于"
        return {"ok": True,
                "answer": ("%s,你第三章三次练习的平均分是 %s 分,"
                           "%s班级平均分(%s 分)。" % (name, avg, trend, CLASS_AVG))}

def require(result, keys):
    """结果 schema 校验:ok=False 或缺字段立即抛错,失败在源头暴露、不级联"""
    if not result.get("ok"):
        raise RuntimeError("worker 失败: %s" % result.get("error", "未知原因"))
    missing = [k for k in keys if k not in result]
    if missing:
        raise RuntimeError("worker 返回缺字段: %s" % missing)
    return result

class Orchestrator:
    """编排者:拆任务 -> 按序派活 -> 校验 schema -> 汇总交付"""

    REQUIRED = {"retriever": ("scores",),
                "calculator": ("avg", "gap"),
                "answerer": ("answer",)}

    def __init__(self):
        self.workers = {"retriever": Retriever(),
                        "calculator": Calculator(),
                        "answerer": Answerer()}

    def plan(self, question):
        # 真实场景:这里是编排者的一次 LLM 调用,它现场决定拆几块、派给谁;
        # Demo 用规则固定三步,便于离线运行、逐行观察轨迹。
        learner = "xiaoming" if "我" in question else "xiaohong"
        return [("retriever", {"learner_id": learner}),
                ("calculator", {}),
                ("answerer", {})]

    def run(self, question):
        print("== 学员提问 ==\n%s\n" % question)
        carried = {}
        for name, payload in self.plan(question):
            payload.update(carried)          # 上游结果作为本步输入,链式传递
            print("-- 编排者派活给 [%s] --" % name)
            out = require(self.workers[name].run(payload), self.REQUIRED[name])
            carried.update(out)              # 收集本步结果,供下游使用
            print("   返回: %s\n" % out)
        print("== 编排者汇总,交付学员 ==")
        return carried["answer"]

if __name__ == "__main__":
    team = Orchestrator()
    answer = team.run("老师,我第三章的三次练习各多少分?平均分在班里是什么水平?")
    print(answer)

    print("\n--- 排错演示:未知学员,失败在源头暴露,不级联 ---")
    try:
        require(Retriever().run({"learner_id": "nobody"}), ("scores",))
    except RuntimeError as err:
        print("捕获到源头失败: %s" % err)

          6. 边界与排错

          症状 原因 处理
          全队结果对,答案错 编排者拆错任务(把小红的问题拆给查小明) 编排者角色卡多写「确认主语与意图」;加一步人工抽查(06 章护栏)
          worker 返回缺字段 worker 没按 schema 输出 看 require() 报的字段名,回改对应 worker 的 prompt 或代码
          计算员把档案查错 worker 越界干了别人的活 单一职责审查:计算员不该有检索工具(工具最小化)
          一个问题要 3 秒变 30 秒 编排者 + 3 worker = 至少 4 次模型调用 短问答直接单 Agent 答(01 章初判标准);长任务才拆
          编排者成了唯一瓶颈 所有决策都过它,慢且贵 子任务形状固定就降级成流水线(03 章);编排者用强模型、worker 用便宜模型
          worker 卡住不返回 没有超时机制 给每次派活加超时与重试上限(04 章通信设计展开)
          • 边界提醒:编排者-工作者不是银弹——它擅长「技能组合型」任务(查+算+答),不擅长需要反复对撞观点的任务(那是 03 章辩论的活),也不擅长形状完全固定的批量任务(流水线更便宜)。

          7. 总结

          概念 一句话
          编排者-工作者 中央 Agent 现场拆任务、派 worker、校验并汇总
          角色划分 编排者只思考不干活;worker 只干活不商量
          为什么流行 清晰(树状职责)、可控(单一决策点)、可观测(每步可打印)
          设计要点 worker 单一职责、结果 schema 明确、编排者决定下一步
          失败点 拆错任务全队白跑、schema 不合法、编排者成瓶颈

          思考题:为什么 worker 之间「不互相通信」反而被当成优点?如果学员问的是「我这次 78 分,下次要考多少才能把平均分拉到 85?」,需要新增一个什么 worker,编排者的拆解会变成几步?

          参考答案

          worker 横向通信意味着消息量与耦合随角色数平方增长,错误会在闲聊中滚雪球,轨迹也无法审计;让所有信息都经编排者中转,协作图保持树状——每个 worker 只需要「拿到输入、产出 schema 结果」,这正是可控与可观测的来源。新问题需要「规划员」worker(或让编排者直接算):拆解变成 检索(查历史成绩)→ 规划/计算(解出目标分数)→ 回答(组织成建议话术)三步,甚至可以让计算员先算出差值,再交给回答员补一句「下次至少考 X 分」——新 worker 的职责声明必须能一句话说完,否则就该继续拆。
