          协作模式流水线与辩论

          02 章的编排者是「现场决策」:拆几块、派给谁,都看任务临时定,灵活但贵。可很多任务形状天生固定——先查、再算、后答,或先写、再评、后改——与其让编排者每轮重新决策,不如把阶段焊成一条流水线;还有些问题存在「对错之争」(该不该重修、哪个方案更好),单 Agent 只看得见自己那一种立场,于是有了让多个 Agent 各执一词再裁决的辩论模式。本章是 02.06 的第三课,把 02 章谱系表里剩下的两种形状讲透:流水线的接力、辩论的对撞,以及三模式怎么取舍、辩论有哪两大风险。

          学习目标:学完本章,你将能够——

          1. 画出流水线(A→B→C 接力)与辩论(多 Agent 对撞 + 裁决)两种协作形状;
          2. 解释流水线为何适合形状固定的任务,并说出阶段闸门与轮数上限两个设计点;
          3. 用「生成→批评→改写」说明独立的 reviewer 为什么比自我批评更能找茬;
          4. 用取舍表对比编排者/流水线/辩论三模式,按任务特征选型;
          5. 说出辩论的两大风险(互相附和、裁决者上限)与对应对策。

          1. 概念:两种协作形状

          • 流水线(pipeline):任务被切成固定顺序的阶段 A→B→C,前一阶段的输出原样成为后一阶段的输入,像工厂流水线一样接力。阶段数、顺序、每阶段职责在写代码时定死,运行时不重新决策。
          • 辩论(debate):围绕同一问题,多个持有不同立场的 Agent 各自亮出论据、互相看得到对方发言,经过若干轮后由**裁决者(judge)**或投票机制收敛出最终答案。
          • 与 02 章编排者的根本区别在拓扑何时定型:编排者运行时「看任务拆形状」;流水线与辩论开工前形状就焊死了——差别只是流水线单向接力、辩论回合制对撞。
          • 课程助教的两个场景:讲解稿流水线「生成 → 批评 → 改写」(gen → critique → rewrite);学员问「平均分低于班级,要不要重修第三章?」——重修派与鼓励派各摆数据,裁决者拍板。
          流水线(接力)                    辩论(对撞)
┌──────┐  ┌──────┐  ┌──────┐     ┌──────────┐  立场A:重修派
│ 生成  │→ │ 批评  │→ │ 改写  │     │ 立场A    │→ 亮论据
└──────┘  └──────┘  └──────┘     └──────────┘   ↕ 互看互驳
 输出即输入,阶段固定               ┌──────────┐  立场B:鼓励派
 错误沿链传播                      │ 立场B    │→ 亮论据
                                  └──────────┘     ↓
                                      裁决者(或投票)收敛

          2. 为什么需要:接力省决策,对撞出盲点

          单 Agent 一步到位的毛病 流水线的解法 辩论的解法
          长任务一次生成质量差,开头结尾的错一起犯 每阶段只专注一步,阶段间可校验定位 多角度互挑毛病后收敛到更稳答案
          只看得见一种立场、一种解法 阶段职责各异,天然多视角 立场显式对撞,暴露各自盲点
          形状固定的任务还要重新规划,浪费 阶段焊死,零运行时决策开销 —
          自我批评(self-reflection)力度弱 独立批评员 prompt 更「狠」 对手即 reviewer,立场驱动找茬
          • 流水线的价值是省决策、可分段优化:形状固定的任务(查→算→答、写→审→发)每次让编排者现场拆解是浪费——LLM 调用又慢又贵(呼应 02 章成本)。阶段焊死后,每阶段还能单独设计 prompt、单独评测(02.02 与 02.07 的方法),哪段质量差就只调哪段,不必整条链推倒。
          • 辩论的价值是暴露单 Agent 盲点:让立场独立(角色卡不同、依据不同,最好模型也换)的 Agent 互相找茬,相当于给答案配了对抗式 reviewer。MIT 的多 Agent 辩论实验(Du 等,2023)把算术准确率从单 Agent 的 67.0% 提到 81.8%,传记事实类任务同样提升;代价是多次模型调用与更长延迟。
          • 一句话:流水线管「长而固定」,辩论管「有对错之争」;两者都不擅长「形状随输入变」——那是 02 章编排者的地盘。

          3. 作用:三种协作模式的取舍对比

          模式 结构 决策时机 强项 弱项 成本量级
          编排者 树状:中央拆解派活 运行时逐任务 灵活、可控、可观测(02) 编排者贵;拆错全队白跑 中~高
          流水线 链状:A→B→C 接力 代码期焊死 快、稳、便宜、可分段优化 僵:改流程要改代码 低(每任务 N 次调用)
          辩论 对撞 + 裁决 回合制 质量上限高、暴露盲点 慢、贵;可能互相附和 高(Agent 数 × 轮数)
          • 选型直觉(补全 02 章的表):子任务形状固定不变选流水线;形状随输入变选编排者;答案质量攸关、存在观点分歧且事实可核才考虑辩论。
          • 模式是积木不是宗教:流水线的批评阶段内部可以是两个批评员辩论;辩论的裁决者也可以走编排者式多步核查。真实系统常是三层嵌套。

          4. 详细介绍

          4.1 流水线:阶段、闸门与轮数上限

          • 阶段划分与 02 章 worker 单一职责同源:每阶段能用一句话说清职责,输入输出形状明确。课程助教讲解稿流水线里,批评员角色卡只许挑毛病、不许改稿,改写员只许按问题清单改——角色不越界,轨迹可审计。
          • 阶段间闸门(gate):阶段输出先过校验(缺字段、格式错立即报错,呼应 02 章 require() 与 04 章 schema),不让坏数据流进下一阶段。流水线最怕错误级联:第 1 阶段的错到第 3 阶段才爆,排错要回溯全程。
          • 轮数上限:批评→改写可循环多轮直到批评员说「无问题」,但必须设上限(如 ≤3 轮);没有上限的自我修正循环是无界烧钱,是 06 章要讲的典型失败模式。

          4.2 辩论:立场、回合与收敛

          • 立场要真不同:角色卡不同、给的依据不同,最好连模型也换——同模型同 prompt 的「辩论」只是自说自话的镜像。
          • 回合制而非自由聊天:固定轮数上限;每轮发言被要求引用或反驳对方论据,强制「看到对方再说话」。
          • 收敛三选一:裁决者拍板(质量最高、最贵)、多数投票(便宜,但多数可能一起错)、达成共识(最省,却最易以互相附和收场)。事实可核的任务,裁决者应带检索工具核证。

          4.3 两大风险:互相附和与裁决者上限

          风险 表现 机理 对策
          互相附和 第一轮各执一词,第二轮起「你说得对,我同意」 指令微调让模型倾向同意,论文观察到 agents「相当愿意附和」 各自独立作答后再互看;prompt 要求引用对方具体错误并鼓励坚持;匿名辩论
          裁决者上限 辩手全错时,裁判只能选出「错得最顺眼」的 裁判与辩手同源(同模型、同训练数据) 裁判换更强模型;给裁判检索工具核证;人工抽裁(01.06 裁判法)
          成本膨胀 质量没升,账单翻 3~6 倍 成本 = Agent 数 × 轮数 × token 固定轮数 ≤3;先跑小样本对比「辩 vs 不辩」再决定是否上线(02.07)
          • 论文的清醒提示:辩论的收益一部分来自 prompt 设计(鼓励坚持、要求互相驳斥),而非单纯「人多」;把几个 agree 倾向拉满的模型放一起,只会收获一场礼貌的茶话会。设计时默认「第一轮会吵起来、第二轮会和稀泥」,对策前置。

          5. 动手活动:跑通流水线与辩论

          动手活动:pipeline_debate.py——「生成→批评→改写」与「重修之争」

          目标:运行 pipeline_debate.py,观察流水线三次接力与辩论「两派发言 → 裁决」的完整输出;再动手把两种风险「造」出来。

          步骤:

          1. 保存为 pipeline_debate.py 并运行(纯 Python 3,离线可跑;每个 Agent 内部目前是规则函数,真实场景替换成一次带专属 system prompt 的模型调用,协作骨架不变);
          2. 对照输出回答:批评员和改写员为什么必须拆成两个 Agent?让生成员自己改自己的稿,推理上会缺什么?

          4. 给 Debater 增加一句附和发言(如「你说得对,我同意你的观点」)并跑 3 轮,观察辩论如何退化成互相吹捧;

# 每个 Agent 内部用规则函数模拟一次「带专属 system prompt 的模型调用」,

# ---------- 场景一:流水线 生成 → 批评 → 改写 ----------

def generate(question):
    """生成员:产出讲解初稿。真实场景 = 带「生成员」system prompt 的 LLM 调用"""
    return "索引能让查询变快,因为索引就是给数据建了一张目录。"

def criticize(draft):
    """批评员:只找茬不改稿,返回问题清单"""
    issues = []
    if "目录" in draft and "少读" not in draft:
        issues.append("「目录」类比没讲透:为什么建了目录就能少读数据块?")
    if "任何" in draft or "永远" in draft:
        issues.append("绝对化表述:插入与更新要维护索引,写密集时反而更慢")
    return issues if issues else ["无明显问题,可定稿"]

def rewrite(draft, issues):
    """改写员:只按问题清单改稿,不引入新观点"""
    if any("少读" in issue for issue in issues):
        draft += " 有了目录,查询不必逐块翻找,只读少量索引块;"
    if any("绝对化" in issue for issue in issues):
        draft += " 但插入与更新需要维护索引,写密集场景反而变慢。"
    return draft

def run_pipeline(question):
    print("== 流水线:生成 → 批评 → 改写 ==\n")
    draft = generate(question)
    print("[生成员] %s" % draft)
    issues = criticize(draft)
    print("[批评员] 问题清单: %s" % issues)
    final = rewrite(draft, issues)
    print("[改写员] %s\n" % final)
    return final

# ---------- 场景二:辩论 重修派 vs 鼓励派,裁决者拍板 ----------

class Debater:
    """辩论一方:角色卡 = 立场 + 论据。真实场景:speak() 换成一次带该立场
    system prompt 的 LLM 调用,并把对手上一轮发言拼进上下文再反驳。"""

    def __init__(self, name, arguments):
        self.name = name
        self.arguments = arguments

    def speak(self, round_no):
        print("[%s 第 %d 轮] %s" % (self.name, round_no, " | ".join(self.arguments)))
        return self.arguments

def run_debate(debaters, rounds=1):
    """回合制辩论:每轮每个辩手发言一次(真实场景是读对手上轮发言后反驳)"""
    print("== 辩论:各执一词,互看互驳 ==")
    transcript = []
    for r in range(1, rounds + 1):
        for d in debaters:
            transcript.extend(d.speak(r))
    return transcript

def judge(transcript):
    """裁决者:真实场景 = 带裁判 system prompt 的 LLM(事实题给它检索工具核证);
    这里用规则模拟:两方数据都对时,取「补练 + 复查」的中道。"""
    text = " ".join(transcript)
    if "下降" in text and "1.7 分" in text:
        return "不重修,但补第三章薄弱点练习,两周后复查达 85 分以上"
    return "维持班级平均线以上者不重修,否则重修"

if __name__ == "__main__":
    run_pipeline("为什么数据库索引能让查询变快?")

    strict = Debater("重修派", ["第三次练习 78 分,呈下降趋势(85→90→78)",
                                "第三章是后续章节地基,基础不牢会滚雪球"])
    gentle = Debater("鼓励派", ["三次平均 84.3,距班级平均 86 仅差 1.7 分",
                                "一次波动就重修会挫伤积极性,针对性补练即可"])
    transcript = run_debate([strict, gentle], rounds=1)
    print("\n[裁决者] %s\n" % judge(transcript))

          6. 边界与排错

          症状 原因 处理
          流水线末段输出仍是错的 错误在第 1 阶段产生、沿链级联 阶段间加闸门校验(02 章 require / 04 章 schema);逐段打印中间产物定位
          辩论两轮后全员一个调 互相附和:模型倾向同意对手 独立初稿再互看;prompt 要求引用对方具体错误;匿名或换模型
          裁决结果还是错的 裁决者上限:辩手全错时裁判无法翻盘 给裁判检索工具;换更强裁判模型;人工抽裁
          费用翻倍质量没升 轮数太多,或给不该辩论的任务开了辩论 轮数 ≤3;先跑 10 条样本对比「辩 vs 不辩」再决定(02.07)
          流水线想加/改一个阶段 任务形状变了,焊死的链要改代码 常变形状直接上编排者;流水线只留给真正固定的形状
          • 边界提醒:辩论放大的是「多视角的理性」,不是质量保险——任务没有可核证的事实与清晰立场时(如「怎么夸学员更舒服」),辩论只产出更长的废话。流水线也不是「必须串行」:阶段间无依赖时可并行(两个独立批评员同时找茬),那已接近编排者的领域。

          7. 总结

          概念 一句话
          流水线 形状固定任务的单向接力:阶段焊死、输出即输入
          辩论 有对错之争时多立场对撞 + 裁决收敛
          为什么有效 流水线省决策、可分段优化;辩论用对手当 reviewer 暴露盲点
          怎么取舍 固定形状→流水线;变形状→编排者;质量攸关且有分歧→辩论
          两大风险 互相附和、裁决者上限;对策:独立初稿、固定轮数、裁判带工具

          思考题:辩论论文观察到模型「相当愿意附和」,这对你的辩论设计有什么直接启示?学员问「学完 02 五个模块,先做哪个项目练手?」——这种开放建议题适合开辩论吗?为什么?

          参考答案

          启示是:辩论的收益不来自「人多」,而来自对抗性 prompt 设计。模型默认倾向同意,所以要让辩手先独立作答再互看、鼓励坚持己见并要求引用对方具体错误,必要时匿名或换模型,否则第二轮就是互相吹捧的共识,成本照付、质量不涨。开放建议题没有可核证的对错,辩论只会输出更长的「各有道理」,费用翻倍而信息不增;更适合单 Agent 依据学员水平直接建议,或流水线「检索学员档案 → 定制项目建议」——辩论应留给「对错可辩、事实可查」的任务(如该不该重修、两种 SQL 写法哪个更快)。
