          模型伸出手的地方

          一位老师对助教 Agent 说：“把第 3 题删掉，学生反馈题干有歧义。”

          Agent 调用了 delete_question(question_id=3)，题库里编号为 3 的那道题被删除。老师想删的是当前这份小测的第 3 题，题库里那一道是另一学期的基础题，被十七份进行中的作业引用。

          Agent 的理解没有大问题。它出错的地方在接口：工具只有一个 question_id 参数，而“第 3 题”这个说法在这套系统里对应至少两个不同的编号体系。参数叫法的歧义，最后由一次不可撤销的删除收尾。

          前一章的规划做得再好，也挡不住这一下。规划决定它想做什么，工具决定它能做什么、会造成什么后果。 这一节开始处理后果。

          工具的三个部分

          讨论工具时，经常把三件不同的事混成一件。

          声明。 名字、描述、参数结构。这份声明进入上下文，被模型阅读。它的质量直接决定模型会不会选对工具、会不会填对参数。

          执行。 真正干活的那段代码：查数据库、调接口、跑脚本。它不在模型里，在服务端。

          边界。 这段代码被调用时用什么身份、改什么数据、能不能撤销。它决定最坏情况的上限。

          这三部分可以分别设计，也必须分别验收。一个工具描述写得漂亮、执行代码没做参数校验，是没有边界；边界做足了、描述写得含糊，是模型天天选错工具。

          这一节要解决的四个问题

          它怎么选。 模型如何从工具清单里挑一个、填参数、把结果读回去。这是 mechanism，也是这一章唯一与模型能力直接相关的部分。

          它怎么被约束。 参数怎么校验、错误怎么回传、描述怎么写。这一层的目标是让调用“要么成功，要么明确失败”，不允许中间状态。

          它能碰到什么。 工具谱系里，只读工具与写入工具的风险差几个量级，代码执行型工具又是另一类。需要一条按后果分级的线。

          谁来兜底。 权限、确认、审计。这一层的原则只有一条：写在代码里，不写在提示词里。

          各节的位置

          4.1 模型只提议，不执行 拆开 function calling 的四步闭环，说明模型与执行之间的那道缝在哪里。

          4.2 工具描述是写给模型看的 讲工具定义。同一段逻辑换一种描述，选中率与参数正确率能差三十个百分点。

          4.3 只读与写入之间那道线 讲工具谱系与信任边界。读操作的失败可以重试，写操作的失败需要撤销，这两件事不该用同一套处理方式。

          4.4 沙箱划得住什么 讲代码执行。模型写代码、代码在机器上跑，是所有工具形态里风险最高的一种。

          4.5 工具变成了可插拔的 讲 MCP。它解决了接入成本，也把信任问题挪到了另一个位置——接进来的 server 是谁写的，决定了你放进来的是什么。

          4.6 权限写在代码里 讲权限层。白名单、参数收窄、人工确认、审计日志。

          这一章之后

          工具调通之后，Agent 能读、能写、能算。但它每次都从零开始——上一轮查到的东西，下一轮就忘了。
