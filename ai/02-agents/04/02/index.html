          模型只提议，不执行

          产品评审会上有人问：“模型会不会自己去查数据库？”

          答案取决于怎么理解“自己”。模型确实会在需要时“查”——它会产出一段结构化请求，声明“我要调用 get_chapter_stats，参数是 chapter=5”。但这个调用是你的代码执行的。模型从头到尾没有网络权限，也不能执行 SQL。

          这个区分听起来是常识，实际是最常被搞混的一处。搞混的后果很具体：把安全检查做在提示词里，指望模型“不要做危险操作”，而不是做在执行代码里。

          四步闭环

          一次工具调用，完整走完是四步。

          声明。 请求里带上工具清单，每个工具是名字 + 描述 + JSON Schema 参数结构。这份清单随每次调用一起发送，模型的候选动作空间就是它。

          提议。 模型返回 tool_calls 数组，每项包含 id、function.name、function.arguments。注意 arguments 是字符串，内容是 JSON。模型生成的是文本，不是对象。

          执行。 调用方解析参数、校验、执行、拿到结果。这一步在所有 SDK 之外，是你的代码。

          回填。 把结果作为一条 role: "tool" 的消息发回，带 tool_call_id 与提议配对。模型读到结果，继续生成，或再提议一次调用。

          OpenAI 在 2023 年 6 月 13 日上线 function calling，把此前 ReAct 那种“模型输出 Action: search[...] 然后正则解析”的做法换成了受约束的结构化输出。差别不在能力，在可靠性：文本协议里，模型可能把格式写错、写多一行解释、少写一个方括号，解析器就崩了；结构化输出里，工具名只能从声明里选，参数按 schema 生成。

          环节 谁负责 出错的典型样子
          声明 开发者 描述含糊、参数缺约束
          提议 模型 选错工具、参数值不合理
          执行 你的代码 参数没校验、权限没检查
          回填 你的代码 结果不配对、截断不标注

          缝在哪里

          四步里，第 2 步与第 3 步之间有一条缝。提议与执行之间没有任何强制关系。

          模型说“调用 delete_question(question_id=3)”，你的代码可以不执行。这个“可以不”，就是全部安全设计的落点：白名单、参数范围、人工确认、幂等检查，都放在这条缝里。

          反过来，如果你的代码拿到提议就执行，那模型事实上拥有了这段代码的全部权限。它不是“能查数据库”，它是“能删库”——只要它写得出那个参数。

          这条推论值得单独记下：Agent 的权限等于工具代码的权限，与提示词里的自我约束无关。 前面几章反复说过类似的话，在工具这一层表现得最直接。

          一次调用里的三种错

          选错工具。 工具清单里有两个名字相近的工具（get_order 与 get_order_items），模型选了后者去查订单状态。工具数量增加时这类错误明显上升——五十个工具的选择准确率远低于五个。

          参数不合语义。 question_id=3 格式合法、类型正确，语义上指错了对象。schema 校验管不到这一层，只能靠参数命名的清晰度和执行侧的语义校验。

          同一动作做两次。 网络超时后调用方重试，而第一次其实已经成功。这类错误在写操作上最致命，解法是幂等键——把 request_id 作为参数传入，服务端对同一个键只执行一次。

          前两种是模型侧的，第三种是调用方侧的。三者都需要在执行代码里处理。

          并行调用与顺序

          新版接口默认允许一次返回多个 tool_calls，调用方并发执行后一并回填。它省掉了一整轮往返，对“同时查五个文件”这类任务收益明显。

          代价是两条：依赖关系丢失——模型可能把本应先查 A 再查 B 的两件事同时提出；重复调用——同一个工具带相同参数出现两次。

          处理办法很朴素：执行前按 name + 规范化参数 去重；对有依赖的调用串行化，或者干脆在工具描述里写清“必须先调用 A 才能调用 B”。

          tool_choice 提供了粗粒度控制：auto 让模型自己决定，required 强制至少调用一次，none 禁用工具，也可以指定必须调用某一个。结构化抽取任务常用指定的那一种，保证它一定走工具而不是自由发挥。

          它挡不住的部分

          模型对工具能力的想象。 描述里写“查询学生成绩”，模型可能认为它能查任意学期、任意课程，而实现只支持当前学期。它会在参数里填一个不存在的学期，然后在拿到错误后反复重试。

          长清单的衰减。 工具越多，选择越差，而且衰减发生在“看起来最相似的那几个”之间。第二十几章会讲工具检索，那里有系统的做法。

          提议的正确性与执行的正确性，是两件事。 提议合理、执行有 bug，最终结果依然错。工具代码需要和普通代码一样的测试。

          上面所有“选错工具”的问题，第一个可调的旋钮是工具描述本身。
