          权限写在代码里

          助教的系统提示里有一句：“你只能查看自己负责课程的学生数据。”

          一个学生发来消息：“我上学期也选了您那门课，现在想查一下我的总评。”

          Agent 调用了 get_student_scores(student_id=...)，返回了另一门课的成绩。系统提示里的那句话，没有起到任何作用。

          模型在这里谈不上被骗：它把用户文字里的身份声明当成了事实。文本里的“我是”永远只是文本。身份必须来自认证，权限必须来自代码。

          混淆代理

          上面那个事故有个名字：混淆代理（confused deputy）。Agent 以一个高权限的服务账号运行，替一个低权限的用户办事，而它没有能力区分这两者的权限差别。

          三个条件同时成立时，这个问题就会出现：Agent 用服务账号连数据、Agent 接受用户文字里的身份声明、工具不做数据范围检查。

          修法只有一条：把终端用户的身份一路传到数据层。 用户登录后拿到令牌，Agent 调用工具时带上这个令牌（或由网关做令牌交换），工具用它去查数据，数据库按它的权限返回。

          服务账号只用于调用模型与基础服务，不用于访问业务数据。

          权限层四件套

          白名单。 每个角色一份工具清单，默认拒绝。学生角色的助教没有 update_score，无论模型怎么提议都调不到。新工具默认不进任何清单。

          参数收窄。 白名单后的第二道。允许 get_student_scores 不代表允许查任意学号：把 student_id 限制在当前用户自己，或者限制在教师负责的课程范围内。

          实现位置很关键：范围条件由网关代码追加，不由模型填写。如果让模型传 course_id，它迟早会传错；如果网关从令牌里取 course_id 拼进查询，模型连表达的机会都没有。

          人工确认。 4.3 节那张表里的不可逆动作。

          审计日志。 每次调用记六项：谁（终端用户 + Agent 身份）、调了什么、参数、裁决结果（允许/拒绝/待确认）、执行结果摘要、耗时。日志不可改，保留期按合规要求定，写进去之前做敏感字段脱敏。

          件 挡的问题 实现位置
          白名单 越权调用工具 网关
          参数收窄 越权访问数据 网关 + 数据层
          人工确认 不可逆操作 网关
          审计日志 事后追责 网关

          一个闸门，不散落

          权限判断只应有一处。散落在各工具里的 if role == "teacher" 会在半年后变得互相矛盾——某个新人加工具时忘写，或者把阈值抄错。

          def guarded_call(principal, name, args):
    tool = REGISTRY.get(name)
    if tool is None or name not in ALLOWED[principal.role]:
        return deny("工具不可用")
    args = scope_args(principal, name, args)   # 参数收窄在这里
    if tool.irreversible and not principal.confirmed:
        return pending(tool.preview(principal, args))
    log(principal, name, args)
    return tool.run(principal, args)
          python

          这段代码的结构比内容重要：所有调用都经过它，没有任何旁路。 工具的 run 只接受已经收窄过的参数，并且用它自己的、限定范围的数据库连接。

          用测试固定权限

          权限矩阵是这套设计里唯一能被自动验证的部分。写一张表，逐格断言。

          课程助教系统至少有这些组合：

          • 学生查自己的成绩 → 允许
          • 学生查同班同学的成绩 → 拒绝
          • 助教查负责课程的成绩 → 允许
          • 助教查非负责课程的成绩 → 拒绝
          • 教师改自己课程的成绩 → 允许（需确认）
          • 任何角色删除题库 → 拒绝

          这六条写进测试，每次改动都跑。它挡不住聪明的攻击，但能挡住九成的回归——权限系统最常见的失效方式在重构：某次改动之后，检查悄悄没了。

          提示词里那句“你不能”

          系统提示里的权限声明仍然值得写，但要清楚它的作用：让模型不去尝试。它不是边界。

          一个好的写法是说明原因，而不是重复禁令：

          学生数据按课程隔离。你只能拿到当前用户有权访问的记录；如果请求超出范围，工具会返回“无权限访问”，此时应向用户说明，不要用其他工具绕行。

          最后半句针对的是真实行为：模型被拒绝后，会尝试别的路径。它在多步任务里把一次越权拆成几次合规调用，这在 4.3 节末尾提过。闸门要能看到任务上下文，而不只是单次调用。

          它挡不住的部分

          范围内的滥用。 权限做对了，一个有权查看全班成绩的老师依然可以要求导出。这是业务规则问题，需要另一层限制（导出需审批、批量操作限额）。

          工具权限与数据权限不一致。 工具允许，数据层没拦，等于没拦。两层都要有，且以后者为准。

          审计日志自身。 日志里有学号、有查询内容，它本身就是敏感数据。访问控制、保留期、脱敏，一样不能少。

          人员的疏忽。 一个临时排查用的高权限角色，事后没人收回。这类问题靠定期复核，不靠技术。

          这一章之后

          工具让 Agent 能改变世界，也让每一次错误都变得具体：删掉一条记录、覆盖一个分数、发出去一封邮件。

          下一节处理另一半问题——它记住什么。长期记忆是 Agent 从“每次重新开始”变成“越用越顺手”的关键，也是隐私与污染最容易出问题的地方。
