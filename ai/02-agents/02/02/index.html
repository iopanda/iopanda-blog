          系统提示定义的是决策框架

          设想一份写了十四条规定、编号整齐的系统提示。测试时发现，模型稳定遵守其中十一条，剩下三条反复失效：一条要求“回答前先检索资料”，一条要求“遇到不确定的表达要标注置信度”，一条要求“输出必须是三点式”。

          追下去会发现失效的原因各不相同。第一条与工具调用的既有惯性冲突——模型更愿意直接回答，因为那更省 token；第二条要求的能力模型本身不具备，它无法内省自己的置信度；第三条则与另一条规则打架，那里写着“回答要自然、像人说话”。

          这三条失效指向同一个结论：系统提示不是一份规则清单，它是一个决策框架。 写进去的东西要能影响模型在每一步如何权衡，而不是像贴墙上的制度一样摆在那里。

          它真正做的四件事

          多数人把系统提示理解为“设定语气”，语气是它最不重要的功能。它实际承担四项工作。

          划定知识边界。 哪些问题在范围内，范围外如何应答。这一条决定了模型是“有用的助手”还是“什么都能聊的通用回答器”。缺了它，模型会对外部问题给出流畅但不负责任的答案。

          定义输出契约。 回答的形状：结构、长度、字段、语言、代码块格式。在 Agent 里这一条尤其硬，因为下游往往是代码——解析器读不懂散文。

          规定工具策略。 什么时候必须调工具、什么时候不许调、拿到结果后如何引用。缺了它，模型会在“我记得大概是这样”和“我去查一下”之间随机选择。

          规定失败协议。 查不到、工具报错、超出能力时怎么办。这是最常被漏掉的一项，也是 Agent 与聊天机器人分野最明显的地方：聊天机器人可以糊过去，Agent 必须把失败变成一个可被处理的事件。

          四项里缺任何一项，你都会看到一种典型的坏行为：缺边界→乱答；缺契约→格式漂移；缺工具策略→该查不查；缺失败协议→编造成功。

          规则改变概率，改不了机制

          系统提示改变的是概率分布；执行机制不受影响。这句话的工程含义很具体：凡是必须保证的事，都不能只写在提示里。

          必须保证“每个工具调用都有超时”？写在代码里。必须保证“不能给未缴费的学员发成绩”？写成权限检查。必须保证“输出能被解析”？加一层 schema 校验和失败重试。

          系统提示负责的是让正常情形下的行为稳定、让模型在模糊处倾向于正确的方向。它不负责兜底。

          我在评审里常用一个问题来区分这两类：如果模型完全无视这条规则，系统会不会出事？ 会出事，那这条规则就不该只存在于提示里。

          三个让它失效的原因

          矛盾。 “回答要专业严谨”与“语气要亲切自然”、“必须三点式”与“像人说话一样流畅”——这类冲突不会报错，模型会在两难处随机选一边，表现为“有时守、有时不守”。评审系统提示时，第一件事是找互相打架的条目。

          稀释。 提示越长，中段的约束越容易被忽略。这不是玄学：注意力在长文本上不均匀，开头与结尾权重更高。把二十条规则平铺开来，效果通常不如分成四组、每组两句，再加两个示例说明。

          不可执行的抽象。 “准确”“专业”“有同理心”“不要幻觉”——这些词的可解释空间太大，模型只能猜。可执行的是行为描述：“先给结论，再列理由，每条理由单独一行”；“资料未覆盖时回答『课程资料中没有相关内容』，并给出两个可查的方向”。

          一次重写

          把十四条规则重写成四组，是这类改造的典型动作。原稿的关键问题在层级混乱：角色、约束、格式、风格混在一起，互相牵制。

          重写后的结构大致是：

          【身份与范围】
你是 X 课程的助教。回答范围限于课程资料覆盖的数据库主题。
范围外的问题：说明未覆盖，给出两个可查方向，不猜测。

【输出契约】
先给一句话结论，再列 2–4 条理由，每条一行。
代码用 markdown 代码块并标注语言。
不确定的地方标注"未在资料中找到依据"，不要补全。

【工具策略】
涉及具体分数、进度、作业状态时，必须先调用查询工具，不得凭记忆回答。
工具返回为空时，视为失败，不得据此推断。

【失败协议】
工具报错：如实说明失败与错误类型，给出重试或替代方案。
超出能力：明确说明，不提供猜测性答案。

          对比原稿，删掉的是所有形容词式的风格要求与重复表述，补上的是原先缺失的失败协议，以及“工具返回为空视为失败”这条硬约束——它正是第 1.6 节那个事故的直接对策。

          系统提示是要版本管理的产物

          一旦它被用来评测，它就和代码同级：需要版本、需要回归集、需要变更记录。

          具体到操作：每次改动另存新版本，不在原文件上直接改；记录改了什么、为什么改；维护一组固定的测试问题（十到二十条足够），任何改动先跑一遍再上线；模型升级后重跑同一组问题——为小模型调好的提示，换到大模型上经常需要重新收一遍。

          没有回归集的提示修改是盲改。你会遇到“改了 A，B 坏了，但两周后才发现”这种情形，而且无法解释。

          它不是安全边界

          最后一点必须说清楚：系统提示挡不住恶意输入。

          不可信的用户消息与你的系统提示在同一个上下文窗口里，模型没有“哪句话具有系统权威”的硬隔离。用户写“忽略上面的规则”，模型有时会照做——尤其是当那句话读起来像一条更新的指令时。

          因此权限、审计、过滤这些必须落在代码层，系统提示只负责让正常用户得到稳定行为。这条边界在讲提示注入的那一节还会展开，那里会解释为什么它没有“参数化查询”式的干净解法。

          从提示转向预算

          系统提示是上下文里唯一常驻、完全由你控制的部分，写好它相当于把地板铺平。但地板之上还有大量内容在争夺同一个窗口：历史、工具返回、检索结果。
