          让输出能被程序接手

          一个出题接口的合规率是 97%。听起来可以上线了。

          按每天两万次调用算，那 3% 是六百条坏数据：解析失败、字段缺失、answer 从整数变成字符串。入库脚本在第 47 条上抛异常，批处理中断，第二天的成绩单少了一半学员。整条链路停在了一句 json.JSONDecodeError 上。

          这类事故的根源在于把“模型大多时候输出对的”当成了质量标准。给程序消费的输出，衡量单位是一次成功率，不是平均水平。 本章后面那些约束手段，都是为了让这个数字尽量接近 100%，以及在没达到时能体面地失败。

          两层结构，缺一层都不算数

          结构化输出有两层要求，任何一层失败都不算完成。

          语法层：这段文本是不是合法 JSON。json.loads 能过。

          形状层：字段是否齐全、类型是否正确、枚举值是否在允许集合内、数组长度是否满足约束。

          只满足第一层，下游依然会崩：{"answer": "1"} 是合法 JSON，但判分代码按整数比较；{"difficulty": "very-hard"} 是合法 JSON，但这一档在你的系统里不存在。

          四种约束强度

          从最软到最硬，手段有四种，能力边界差别很大。

          在提示里要求 JSON。 零成本，任何模型都吃。保证力最弱：模型可能裹上一层解释、加 markdown 围栏、用单引号、或者在你要求数组时给一个对象。

          JSON mode。 response_format={"type": "json_object"}，平台保证语法合法，不保证形状。适合“我只需要一段能解析的 JSON”的场景。

          Structured Outputs。 传入 json_schema 并开启 strict，平台把 schema 编译进解码过程，逐 token 屏蔽不合法的输出。这是目前最硬的保证，代价是 schema 有写法限制：每个对象必须 additionalProperties: false，所有键都要进 required，可选字段要用联合类型表达。

          function calling 的参数约束。 声明工具时，parameters 就是一份 JSON Schema。模型决定调用工具时，工具名只能从声明里选，参数按 schema 生成。它约束的是“行动参数”，与前面几种约束“回答内容”不同——要模型做事用这个，要模型交数据用 Structured Outputs。

          手段 约束发生在 语法 形状 适用
          提示要求 提示词 无 无 原型、非关键路径
          JSON mode 平台解码 有 无 只需可解析
          Structured Outputs 平台解码 有 有 交付数据
          function calling 平台解码 + 工具声明 有 有（参数级） 执行动作

          平台保证之后，还剩三类失败

          即使开了 strict，返回值依然可能不可用。三类失败平台管不到。

          拒答。 安全策略触发时，content 为空，message.refusal 里有说明。解析器如果直接 json.loads(content)，会拿到 None 并崩掉。

          截断。 输出达到长度上限时，finish_reason 是 length，JSON 只生成了一半。语法上它是残缺的，形状上更谈不上。

          语义错。 这是最隐蔽的一类：所有字段都合法，difficulty 是 easy，但这道题明显是难题。schema 校验通过，业务上是错的。这类问题只能靠抽样人工检查或规则抽检发现。

          校验闭环

          把上面三类失败接住，需要一个固定的处理顺序，五步。

          第一，检查 refusal 与 finish_reason，异常状态直接走失败分支，不进入解析。

          第二，清理污染。模型有时会把 JSON 包在围栏里或加一句客套话，用首尾花括号截取是最省事的做法——它天然排除了前后散文。

          第三，json.loads，失败则记录错误原文。

          第四，按 schema 校验形状。字段集合、类型、枚举、长度约束。这里有个常见坑：Python 里 bool 是 int 的子类，True 能通过整数类型检查，需要显式排除。

          第五，失败时把错误信息拼回提示、限次重试；重试耗尽就显式降级——把原始输出交给人工，或者换一种问法，绝不把坏数据喂给下游。

          重试次数控制在两到三次。每次重试都是一次真实调用，成本线性增长，而且大部分格式错误重试一次就能修好，修不好的通常提示本身有问题。

          信任模型：模型输出属于不可信输入

          这一节最重要的一句：模型输出和用户输入、网页抓取同级，都是不可信内容。 信任来自代码校验，不来自模型承诺。

          这条判断有两个推论。一是校验不能省，哪怕平台承诺 100% 形状合规——承诺覆盖的是形状，不覆盖拒答、截断与语义错。二是错误信息要能被下游消费，不能只是抛异常：结构化输出失败是一个可处理的事件，应该带错误类型与原始文本一起上报，让人能在一分钟内判断是提示问题、模型问题还是数据问题。

          它挡不住的

          schema 挡得住取值越界，挡不住取值合法而语义错误。这需要业务层的抽检规则。

          不同供应商对 json_schema 的支持度差异很大，自部署模型往往只支持 json_object。把平台保证当成优化项、把本地校验当底线，是唯一能跨供应商保持一致的做法。

          还有一条：结构化输出解决“形状”，解决不了“内容对不对”。模型可能严格按 schema 输出一个完全错误的答案，而且格式漂亮得让人放松警惕。

          从输出回到输入

          到现在为止，我们讨论的都是“模型吐出来什么”。但模型吐出什么，取决于它读到了什么——而 Agent 每一步读到的上下文，都是代码重新拼出来的。
