          引言：同一个模型，两种结果

          设想两个团队接同一个需求：让模型替学员解答数据库课程的疑问，并且只能依据课程资料。

          第一个团队把用户问题直接塞给模型，前面加一句“你是课程助教”。第二个团队做了五件事：写清楚这个助教的知识边界、把课程资料的检索结果按可信度排好、给三个示例说明“资料没覆盖时该怎么答”、把输出约束成固定结构、规定工具失败时如何回报。

          同一个模型、同一批问题，第二套的可用率通常是第一套的两到三倍。差别不在模型，在那几千个 token 里放了什么。

          这就是上下文工程的全部含义：在模型固定的前提下，你能拿到的剩余性能，几乎全部买在上下文里。

          上下文里到底有什么

          一次模型调用看到的全部内容，就是你构造的上下文。对 Agent 来说，它通常由五部分组成。

          系统提示：常驻、由产品方控制，定义角色、边界与输出契约。工具说明：模型可用的动作及其参数。历史轨迹：前面每一轮的思考、动作与观察。外部材料：检索到的文档、数据库查询结果、用户上传的文件。当前输入：用户这一轮说的话。

          这五部分争夺同一个预算——模型的上下文窗口。窗口是有限的，所以构造上下文本质上是分配问题，而不是“收集”问题：多放一段资料，就可能挤掉一段历史；多塞两个示例，就可能让系统提示的约束被稀释。

          为什么这件事比调模型更值钱

          换模型是一条成本曲线陡峭、收益不确定的路：价格可能翻倍，延迟变长，而失败模式往往照旧——因为很多失败的根子在材料：模型看到的上下文不对。

          第 1.6 节那个循环已经把这一点演示过一次：工具返回为空，模型没有报错，而是用先验知识把数据补了出来。根子在上下文里少了一条“这里本该有数据但读取失败”。

          上下文工程的收益则更直接：它不需要换模型、不改延迟、可以逐项验证。代价是它要求你把每一次调用当成一次信息设计，而不是一次提问。

          这一章要解决的六件事

          系统提示那一节讨论它的真实职责。多数人以为系统提示是在“设定语气”，实际上它做的是四件更硬的事：划定知识边界、定义输出契约、规定工具策略、规定失败协议。写不清楚这四件事，语气再对也没用。

          上下文预算那一节讲窗口经济学。窗口不是仓库，塞满不等于记住；这一节给出分配、淘汰与压缩的具体做法，以及为什么“保留最近 N 轮”这种朴素策略会在第 20 步失效。

          示例那一节解释一个反直觉的事实：示例对模型行为的影响通常大于规则。它同时解释示例为什么危险——一组不具代表性的示例，会把模型稳定地引向错误的方向。

          结构化输出那一节处理“下游是代码”的场景：提示里要求 JSON、平台层的 schema、工具参数约束，三种手段的强度差别很大，能保证什么、不能保证什么，要分清楚。

          上下文构建那一节把前面几件东西拼起来：一次 Agent 步的上下文应该如何分段、按什么顺序、哪些内容必须标记为不可信。

          最后一节讲提示注入。当上下文里出现第三方内容（网页、检索结果、用户上传的文档），你就有了一个攻击面；这一节解释为什么它没有“参数化查询”式的解法，以及三层缓解各自能挡住什么。

          主线还是课程助教

          整章继续用第一部分那个课程助教。它现在的状态是：循环能转，工具能调，但行为不稳定——同样的学员提问，有时答得很好，有时越界、有时格式全错。

          后面每一节都会拿它做一次改造，并且尽量给出可检验的结果：这样写之后，固定十问上的格式符合率变化多少。数字是示意，方法是真的——你应该在自己的十问上重跑一遍。

          怎么读

          这一章假设你手上有能调用的模型接口，以及第 1.6 节那个循环。所有例子都可以在几十行代码里复现，不需要框架。

          如果你只想记一句话：模型决定上限，上下文决定你能不能碰到上限。

          下一节先拆系统提示——那个被误解最深、写起来最随意、对行为影响却最直接的部分。
