          上下文是一份有限的预算

          一个 128K 窗口的 Agent，实测往往在第 6 轮就开始丢信息。窗口没变小，是里面的东西长大了。

          系统提示 2K token；每轮问答 1–3K；每次工具返回，如果不去截断，检索一整页讲义是 5–20K，一次调用带回三段就是 30K。按每轮 20K 的保守估计，128K 在第四轮就见底。看起来充裕的窗口，实际只能装四轮真实工作。

          所以“窗口够大”是个错觉。窗口是一份预算：它决定你每一次调用能装多少东西，而装什么、按什么顺序装、装不下时丢什么，才是决定第 20 步还能不能正常工作的变量。

          四轮就见底

          Token 不是字数。英文大致 4 字符 1 token；中文按字符算更接近 1 字 1–2 token，取决于分词器。所以“128K”和“12.8 万汉字”不是一个数量级——中文长文本的预算比直觉紧张得多。

          输入与输出共用同一个窗口。这一点经常被忽略：预算按输入算满，输出就没有位置，调用会直接报 context_length_exceeded；有些框架会静默截断，于是你看到的是“模型突然变笨”，而不是一个明确的错误。

          Agent 的增量比聊天机器人凶得多。聊天每轮只新增一问一答；Agent 每轮还要叠加工具结果、检索片段、以及它自己的推理轨迹。第 1.6 节那个循环里，Observation 是每一轮都要写回上下文的东西——如果工具返回不受约束，上下文增长主要来自工具，对话本身占得少。

          预算怎么分

          把窗口当预算，意味着在调用前先分配额度，而不是等超限了再补救。一个可用的分法（按 128K 窗口、输入控制在 100K 以内设计）：

          块 配额 超配时怎么办
          系统提示 ≤ 5K 精简措辞，不突破
          当前输入 ≤ 10K 让用户拆分，或先摘要
          工具结果 ≤ 40K 只留命中段落，源头截断
          历史 ≤ 35K 压缩早期轮次
          输出余量 ≥ 28K 前移压缩阈值

          这张表的价值不在于数字准确，而在于它把“每轮装什么”从临时判断变成可审计的约定。有表之后，“为什么这轮又超限”就有一个可以对照的答案。

          三种淘汰策略，三种代价

          窗口满了必须有东西退出。常见三种做法，代价不同。

          滑窗：只留最近 N 轮。 实现最简单，几行代码，把增长从线性变成封顶。代价是硬遗忘——被滑掉的早期信息模型彻底看不到。学员第 2 轮说过“我是零基础”，第 9 轮起这句话就不存在了，模型会默认他懂索引优化。

          滚动纪要：把旧轮次压成结论。 比丢掉好，因为它保留了语义。代价是失真：纪要由模型生成，压缩过程中会丢掉限定条件和依据。一句“外键示例已讲过”可能省略了“这个例子只适用于单列外键”，而后者恰恰是后面要用到的区分。

          钉住：把关键信息重新注入。 不指望它自己活下来，而是每轮或每隔几轮主动重写一次。代价是持续的 token 开销，好处是可控——你知道它在，而且知道它在哪里。

          工程上三者组合使用：纪要负责长程语义，滑窗负责封顶，钉住负责那些不能丢的硬约束（例如学员水平、课程范围、安全规则）。

          位置比顺序更影响效果

          同一段内容放在上下文的哪个位置，被遵循的概率不同。开头与结尾的权重高于中段，这是位置效应，和系统提示里中段规则被稀释是同一种现象。

          三条可操作的推论：

          把最重要的约束放在开头，或者放在系统提示里——它是唯一常驻的块。

          每一轮把“本轮要做什么”写进最后一条消息。模型对最近内容的注意力最强，而 Agent 的循环里，最后一条通常是 Observation，很容易把任务目标挤到中段去。

          不要把关键事实埋在历史中间。如果它必须一直在场，就进纪要或进系统提示；留在历史里，它一定是最先被截断的那批。

          什么时候压缩，压缩之后怎么知道有没有压坏

          压缩需要一个触发条件。用 token 利用率最直接：usage.prompt_tokens 除以窗口上限，70% 启动纪要、90% 强制压缩。两个阈值比一个阈值好，因为压缩本身有成本（一次额外的模型调用，或者一段规则抽取），而且会改变行为。

          压缩之后要回答三个问题，才算安全：

          影响规则吗？ 被丢掉的轮次里有没有约束条款？如果系统提示中段有规则，而压缩把它前面那段删了，模型可能重新解释自己的行为边界。

          影响事实吗？ 关键前提是否丢失？“零基础”“只考第三章”“不接受代码答案”这类事实一旦丢了，后面所有回答都会偏。

          影响证据吗？ 回答引用的检索片段还在不在？不在的话，模型会照着自己的印象继续引用，读者看到的是凭空出现的来源。

          三个问题都否，压缩才算无损。有一个是“是”，就得换策略——把它钉住，而不是指望它活下来。

          压缩救不了巨物

          一个常见的误判：以为压缩能处理任何超限。

          如果单条工具结果就有 30K，滑窗删不掉它（它是当前轮），纪要把整段结论化会失真，最后只能用一次模型调用去摘要——而摘要本身要花掉上下文。

          正确的做法发生在源头：工具返回时就截断，并且显式标注截断（“以下为前 2000 字，原文共 18000 字”）。这在第 1.6 节讲过，属于同一类问题——让模型知道它看到的不完整，比让它以为看到了全部要好得多。

          它解决不了的事

          窗口管理解决“装不下”，不解决“装进去的东西互相矛盾”或“装进去的东西是攻击者写的”。

          前者的典型症状是规则冲突：系统提示要求三点式，纪要说“回答要自然流畅”，模型在两难处随机选边。后者是提示注入，属于最后那一节的范围。

          还有一件边界：超长任务的出路在窗口之外——检索、外部存储、结构化笔记。窗口永远只放“这一轮要用的”，这个原则一旦动摇，你会在压缩策略上无限投入，而收益递减。

          从预算转向内容质量

          预算决定装多少，内容质量决定装了有没有用。

          下一节处理上下文里最容易被忽视、影响也最大的一类内容：示例。它比规则更能决定模型行为，也比规则更容易把模型带偏。
