          横向对比与可抄要避清单

          01~04 章把 Codex 拆成了仓库、循环、沙箱、配置四层零件;收官章把它们装回坐标系——02.09 的统一八维框架里同时摆着六个实现。孤立看每一行 Rust 都只是工程,放进坐标系才看得出:哪些是「值得抄的普遍解法」,哪些是「Codex 自己踩过、你要避开的坑」。本章只交付两样东西:带源码出处的抄/避清单,和一张能复用到你自己项目的填空表。 学习目标:学完本章,你将能够——

          1. 说出 02.09 的八维框架,并逐维给出 Codex 的设计签名与源码位置(文件:行号);
          2. 用对比表讲清 Codex 与 Claude Code/Hermes/OpenCode/Pi/Copilot 的差异(仅限各 README 核证信息,不给他人源码下结论);
          3. 从源码复述六条「可抄」:策略-平台分离、AGENTS.md 分层、审批插入点、deny-read 不变量、carveout 防逃逸、废弃值硬报错;
          4. 说出四条「要避」:macOS 网络放行坑、Landlock 降级、拒绝检测误判、工具表过大,各指一处出处;
          5. 给自己项目填一张「我要抄/我要避」表,每条标注出处与代码落点。

          1. 概念:八维框架与设计签名

          • 概念出处:02.09/00 Learning Path 为六个分析对象定了同一组解剖问题——①源码结构与入口、②循环、③上下文、④工具、⑤记忆、⑥协议与扩展、⑦评测与质量、⑧安全。八维是同一个 Agent 身上的八个问号;「设计签名」是一个实现反复出现的偏好答案,比如 Codex 在 ①④⑥⑧ 上下重注(工程化与安全),在 ⑤ 上则刻意克制。
          • 为什么 05 章要站在框架上写:源码分析回答「怎么做的」,横向对比回答「为什么这么选」——把 Codex 的答案与另外五种答案并排,每种选择的长处与代价才同时显形。

          2. 为什么:设计选择只有放进坐标系才有意义

          • 单看源码,每个实现都能自圆其说(Rust 快、TS 生态好、闭源可控),没有对错只有取舍;单看 README,宣传语无法证伪。坐标系的价值是让取舍可比较:同一个概念(权限闸门),六个实现都做了吗?做在哪一层(模型层/分发层/OS 层)?实现不了时怎么办(拒绝运行、降级还是裸奔)?
          • 同一问题的分层答案正是对比的乐趣:Codex 把审批做成分发链上的插拔闸(registry.rs:567-591),Claude Code 把授权做成 permissionMode + hooks 事件闸(见 01 README);两者功能等价,落点不同,可抄的姿势就不同。
          • 本章遵守一条研究伦理:Codex 侧论断全部给「文件:行号」,其他实现只引用各自 README 已核证内容并标注「见 XX README」——无法核证的不写,避免拿 README 粒度冒充源码结论。

          3. Codex 的设计签名一览

          签名 一句话 源码证据
          Rust 核心、单二进制低延迟 Cargo 工作区 110+ crates,一个二进制走完 exec/TUI/沙箱 cli/src/main.rs:1043;exec/src/lib.rs:246
          Responses API 深度绑定 + 双通道 wire_api 仅剩 responses(chat 报错),凭据按 ChatGPT 登录/API key 分流 model-provider-info/src/lib.rs:57/87、:292-310
          三态沙箱「策略-平台分离」 意图层枚举,平台层各自翻译成 Seatbelt/bwrap+seccomp/受限令牌 protocol.rs:1066-1118;seatbelt.rs:844
          AGENTS.md 分层拼接 root→cwd 逐层收集,--- project-doc --- 分隔 agents_md.rs:39-46、:352-378
          审批演进:approval_policy → AskForApproval 枚举显式四值,废弃值硬报错不留静默兼容 protocol.rs:966-1024;core/src/config/mod.rs:3635-3640

          4. 详细介绍:八维定位、横向对比与抄/避清单

          4.1 八维逐维定位 Codex 的设计签名

          维度 Codex 的设计签名 源码出处
          ①源码结构 Rust 核心多 crate + TS CLI,单二进制 cli/src/main.rs:1043
          ②循环 会话级 submission_loop 串行分发 → turn 内 SSE 步进,Completed end_turn=false 续跑 session/handlers.rs:529;session/turn.rs:162、:2666-2668
          ③上下文 整段 ResponseItem 历史(for_prompt)+ AGENTS.md 分层 + 压缩滚动 context_manager/history.rs:315-329;agents_md.rs:39-46;compact.rs:116
          ④工具 四来源注册 → 并行/串行读写锁 → PreToolUse 闸 → 沙箱化执行 spec_plan.rs:1028-1031;registry.rs:567-591;tools/parallel.rs:116-159
          ⑤记忆 克制:会话历史 + AGENTS.md 即项目记忆,无独立长期记忆子系统 context_manager/history.rs:315-329;agents_md.rs:344-378
          ⑥协议 Responses API 深度绑定 + MCP stdio/http + skills/hooks/plugins 扩展面 model-provider-info lib.rs:96-151;config_toml.rs:266-270、:457-464
          ⑦评测 otel 时序埋点 + jsonl 事件轨迹(exec 模式),行为由测试佐证 tools/registry.rs:646-661;event_processor_with_jsonl_output.rs:476-488

          4.2 与另五个实现的横向对比(信息均出自各对象 README,核证粒度止于 README)

          对象 一句话定位(见其 README) 与 Codex 的关键差异
          Claude Code 闭源 CLI 核心 + MIT SDK 外壳,SDK 以消息帧暴露循环(见 01 README) 核心不可读,开放面是 permissionMode/三级 settings/hooks 事件闸与 SKILL.md 开放标准;发行策略与 Codex 的全开源相反
          Hermes Agent MIT Python 全栈,主打「自我进化」:技能/记忆/画像为运行时可变资产(见 03 README) 记忆与技能是头等公民(FTS5 会话检索、Honcho 画像、cron),Codex 用 AGENTS.md 的克制路线与之成两极
          OpenCode MIT TS monorepo,client/server 解耦,开箱 LSP,AGENTS.md 自举(见 04 README) 全 TS 单语言栈;LSP 喂符号/诊断替代 Codex 的 grep 式理解;build/plan 双 agent 模式即「换权限上下文」的循环
          Pi Coding Agent 极简 TS,默认四工具,功能刻意外置为扩展(见 05 README) 无内置 MCP/子代理/plan mode/权限弹窗;Codex 把安全做进核心,Pi 把安全外包给容器与供应链硬化
          GitHub Copilot 平台化 Agent 家族,服务端 harness 闭源,Issue→draft PR 异步工作流(见 06 README) 循环跑在云平台,PR 即检查点与人工闸门;Codex 是本地单进程自治,护栏长在 OS 沙箱与审批里
          • 读表提醒:差异是「分层与落点」之别,不是优劣榜;例如审批,Claude Code 走事件闸、Codex 走分发链插入点、Copilot 走 PR/CI 平台闸——同一目标三种工程姿势。

          4.3 可抄清单(每条可直指源码)

          ① 策略-平台分离的沙箱架构。意图层与平台翻译层彻底分开:上层枚举只声明意图,平台后端各自翻译(seatbelt.rs:844 create_seatbelt_command_args;linux_run_main.rs:159)。抄法:新平台只需补一个翻译器,策略语义不漂移。

          // protocol/src/protocol.rs:1066-1118(节选)
pub enum SandboxPolicy {
    #[serde(rename = "danger-full-access")]
    DangerFullAccess,
    #[serde(rename = "read-only")]
    ReadOnly { network_access: bool },
    #[serde(rename = "workspace-write")]
    WorkspaceWrite { writable_roots: Vec<AbsolutePathBuf>, network_access: bool },
}
          rust

          ② AGENTS.md 分层拼接。文件名、分隔符全部收敛为常量,root→cwd 逐层收集、每层只取第一个命中文件、总量受预算截断(agents_md.rs:66-90)。抄法:常量集中 + 预算截断,防止拼接失控。

          // core/src/agents_md.rs:40-46
pub const DEFAULT_AGENTS_MD_FILENAME: &str = "AGENTS.md";
pub const LOCAL_AGENTS_MD_FILENAME: &str = "AGENTS.override.md";
const AGENTS_MD_SEPARATOR: &str = "\n\n--- project-doc ---\n\n";
          rust

          ③ 审批/策略插入点放在工具分发链上。PreToolUse hooks 在 dispatch 途中拦截,Blocked 以 RespondToModel 回灌模型继续对话(registry.rs:567-591),PostToolUse 复查结果(registry.rs:684-731)。抄法:把审批做成分发链上的可插拔闸,而不是散在各 handler 里自查——新增工具自动获得闸门。

          ④ deny-read 禁止裸奔不变量。策略含拒读路径时,禁止无沙箱升级执行;确需放宽也回退到默认沙箱再试,而非裸跑(unsandboxed_execution_allowed = !has_denied_read_restrictions(),sandboxing.rs:275-295)。抄法:拒绝集是硬边界,任何升级路径不得越过它。

          ⑤ 保护目录 carveout 与防逃逸。.git/.codex 等受保护元数据(permissions.rs:27-29)在策略里以 (require-not (literal/subpath ...)) 排除,连首次 mkdir .codex 也被挡(seatbelt.rs:555-563);对保护目录的祖先 rename/unlink 单独 deny,防「挪走目录逃出 carveout」(seatbelt.rs:871-889、:1008-1017)。抄法:保护一个路径时,同时保护它的祖先不被重命名。

          ⑥ 废弃值硬报错,不留静默兼容。审批从旧 approval_policy 演进到 AskForApproval(protocol.rs:966-1024,默认 OnRequest):旧值 untrusted 显式下发即报错(core/src/config/mod.rs:3635-3640),yolo 与其它旗标的冲突交给 clap 拒绝(tui/src/cli.rs:139-144)。抄法:迁移期宁可直接报错,也不让旧配置悄悄产生新语义。

          4.4 要避清单(每条有出处,抄之前先检查自己有没有同款坑)

          ① macOS 网络放行坑(issue #10390)。macOS 沙箱网络策略在代理/特定端口场景出过问题(模块 README 03 章已列为已知 issue;github.com/openai/codex/issues/10390)。教训:网络放行不能只信策略文本,要按 loopback 端口与受管代理逐场景实测;Codex 侧的做法是网络仅按最小注入、UNIX socket 默认受限(seatbelt.rs:77-110)。

          ② Landlock 容器降级。Linux 的线程内 landlock 路径(landlock.rs:137-163)已被 bwrap 双层结构取代、降级为兜底;容器内缺 user namespace 等能力时沙箱强度随之下降(linux_run_main.rs:159)。教训:别把「某个平台的某个机制」当主机制抄,抄 bwrap 外层建视图 + seccomp 内层管网络的组合,并给降级路径留显式告警。

          ③ 拒绝检测启发式误判。判定靠关键词查 stderr/stdout,业务输出里恰好出现 permission denied 的正常命令会被误判为沙箱拒绝,进而触发无谓的 escalation 打扰用户(denial.rs:50-58):

          // sandboxing/src/denial.rs:50-58
const SANDBOX_DENIED_KEYWORDS: [&str; 7] = [
    "operation not permitted",
    "permission denied",
    "read-only file system",
    "seccomp",
    "sandbox",
    "landlock",
    "failed to write file",
];
          rust

          教训:关键词判定只当提示;executor 侧上报的 sandbox_denied 标志才是可信证据(denial.rs:45-72)。

          ④ 工具表过大。每轮请求的工具定义来自 model_visible_specs()(turn.rs:1389-1406),MCP 工具全直出时工具 JSON 会撑爆上下文。教训:抄暴露控制,不抄全量直出——Deferred 工具被压缩成少量入口(如 list_tool)再发模型(spec_plan.rs:352),这是 4.3 清单里容易被漏抄的第六项的另一面。

          5. 动手活动:填自己项目的「抄/避」表

          动手活动:给课程助教骨架(02.08/05)或你手头项目填一张两列清单

          目标:把本章抄/避结论落成自己仓库里可执行的改动清单,每条都有出处与落点。

          步骤:

          1. 画出你项目里「用户输入 → 工具执行」的链路,标出命令执行与文件写入的位置(对应 Codex 的 registry.rs:567-591 与 seatbelt.rs:844);
          2. 从 4.3 六条里选 3 条抄,写下落点:例如「工具分发处加 pre-hook 拦截点」「把项目指令按目录分层拼接,分隔符收敛为常量」;
          3. 拿 4.4 四条逐条体检:你的 macOS 网络放行测过代理吗?容器里沙箱降级有告警吗?拒绝判定是关键词还是可信标志?发给模型的工具定义有多大?
          4. 填完下表并自查「每条都有出处」。
          我要抄(出处) 落点 我要避(出处) 我的同款坑?
          例:审批插入点(registry.rs:567-591) 分发函数前加 hook 检查 例:拒绝关键词误判(denial.rs:50-58) 输出含 permission denied 会被拦

          完成标准:表内 ≥4 行抄 + 3 行避;每条出处能指到文件或 issue;至少一条避项在你项目里真实存在并给出修法。

          6. 边界与坑

          症状/疑问 原因 处理
          行号对不上 行号是 2026-09 main 快照 引用前先 grep 对应符号确认
          对比表信息粒度不一 Codex 侧到源码,他人只到 README 差异结论只用于定位,不做源码级优劣断言
          说「三态」却数出四个变体 SandboxPolicy 实为四变体,含 ExternalSandbox(protocol.rs:1066-1118) 「三态」指三种本地沙箱语义,External 是外部沙箱标记
          想证明「Rust 更快」 本章未跑跨实现基准 设计意图 ≠ 实测结论,无数据不下判断
          • 边界提醒:本章的抄/避结论绑定 Codex 的具体取舍;抄的是「结构」(分层、插入点、不变量),不是「代码」——把 sandbox-exec 策略整段搬去别处,会连 issue #10390 一起搬走。

          7. 总结

          概念 一句话
          八维框架 六个实现共用的解剖模板,横向对比 = 把每个实现的「重注与缺席」照出来
          Codex 画像 Rust 单二进制 + Responses API 深度绑定 + 三态沙箱 + AGENTS.md 分层 + AskForApproval 演进
          最值得抄 策略-平台分离、分发链审批插入点、deny-read 不变量、carveout 防逃逸
          最该避 macOS 网络放行(issue #10390)、Landlock 降级、关键词误判、工具表过大
          抄的正确姿势 抄结构不抄代码;每条改动保留出处,才能应对版本演进

          思考题:Codex 把审批做成分发链上的可插拔闸(registry.rs:567-591)而不是让每个 handler 自查,好在哪里?「策略含拒读路径时禁止无沙箱执行」(sandboxing.rs:275-279)这条不变量,对应 02.04/06 的哪个原则?用 4.2 的对比表回答:哪一维是 Codex 的最强签名,哪一维它刻意缺席,缺席是否等于缺陷?

          参考答案

          插拔闸让「新增工具自动获得闸门」:审批逻辑只写一处,handler 越权或漏写都不再是风险面;自查式设计每加一个工具都要记得补闸,迟早漏。deny-read 禁裸奔对应「最小权限 + 拒绝优先」:被拒读的路径是硬边界,任何升级(哪怕是用户批准的)都不能悄悄放行它,否则审批就变成绕过 carveout 的梯子。Codex 的最强签名在 ⑧ 安全与 ① 工程化(全开源可核证的 OS 级沙箱);刻意缺席在 ⑤ 记忆——它没有 Hermes 式的长期记忆子系统(见 03 README),而是用 AGENTS.md + 会话历史回答记忆问题。缺席不等于缺陷:本地 CLI 的场景里,项目文档与历史足够,向量库是多余复杂度;但若把 Codex 的循环搬进「跨会话学习」的产品,⑤ 就要补课——这正是 03 Hermes 子单元要讲的另一种答案。
