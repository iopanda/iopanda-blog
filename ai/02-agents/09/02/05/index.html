          配置与审批模式

          03 章回答了「命令跑起来能碰到什么」,本章回答更前面的一道题:「这段代码凭什么按这套配置跑、哪条命令在什么时候需要问人」。Codex 的答案是两条互补的机制:一条从打包默认到 CLI 旗标的 11 个来源的优先级链,裁决「谁说了算」;一个 AskForApproval 枚举,裁决「要不要问」。贯穿始终的安全心法只有一句:配置来源可以很多层,但权力永远不能从低信任层往高信任层爬——仓库里的 .codex/config.toml 默认只能往下调,不能往上抬。

          学习目标:学完本章,你将能够——

          1. 画出配置从打包默认到会话旗标的加载链,说出 11 个来源位置、合并顺序与「数字大者胜」规则;
          2. 解释项目层 DENYLIST 机制:仓库里的 config.toml 哪些键会被剔除、为什么这是防提示注入的第二道闸;
          3. 说出 AskForApproval 的四个挡位及其语义,并解释为什么默认是 OnRequest、旧值 "untrusted" 为什么被硬拒绝;
          4. 讲清 --approve-for-me 改写哪三个配置键、--dangerously-bypass-approvals-and-sandbox(yolo)为何等于「DangerFullAccess + Never」双重强制,以及 clap 如何拒绝危险组合;
          5. 描述模型路由的三类凭据分流(ChatGPT 登录 / API key / 自建端点)与 mcp_servers、skills、hooks、plugins 四个扩展面的配置形态。

          1. 概念:配置分层与审批策略

          • 概念出处:02.04/06 权限边界讲过「最小权限 + 人工介入」,配置分层是它的管理面——同一台机器上,打包方、系统管理员、企业、用户、项目、命令行都在说话,必须有一个确定性的裁决顺序;审批策略是它的交互面——模型想执行有副作用的命令时,谁有权放行、放行到什么程度。
          • 骨架一句话:配置先按来源叠成「一层压一层」的栈(ConfigLayerStack),再统一落到一份生效配置;审批是生效配置里的一个枚举字段,决定「shell 升级、rules、skill 等各类请求」如何被路由给用户或自动审查者。两个机制在 core/src/config/mod.rs 的解析阶段汇合(默认值裁决在 mod.rs:3641-3662)。

          2. 为什么:配置来自多方,仓库内容不可信

          • 冲突必然发生:管理员想锁死模型、用户想换模型、项目想调工具、CLI 想临时覆盖——没有优先级数字,行为就取决于加载顺序这种实现细节,不可预测也不可审计。所以每个来源都挂一个显式的 precedence,谁大谁晚合并、谁覆盖谁,一眼可读。
          • 仓库是最低信任方:你会 git clone 陌生项目,而 02 章讲过模型会读仓库里的 AGENTS.md 和 README——如果 .codex/config.toml 能自由改 model_provider、openai_base_url,一个恶意仓库就能把模型对话静默导到攻击者服务器,或让本地命令被自选工具执行。这是提示注入从「文本层」升级到「配置层」的路径,必须从机制上掐断。

          3. 作用位置:一次启动的「定档」顺序

          codex 启动(cli/src/main.rs)
  → load_config_layers_state(loader/mod.rs:132)按 11 个来源位置逐层发现与解析
  → 每层一个 ConfigLayerEntry,带来源标记(ConfigLayerSource)
  → 项目层先过 sanitize_project_config(DENYLIST 剔除)→ 非 trusted 目录直接 disabled
  → 低→高逐层 merge,数字大者胜 → 一份有效 Config
  → 解析 AskForApproval / approvals_reviewer / sandbox_mode 的最终值
  → CLI 冲突由 clap 在参数解析期直接拒绝(根本走不到配置层)
          text
          • 分层加载入口是 load_config_layers_state(config/src/loader/mod.rs:132);官方注释(loader/mod.rs:109-125)按用户视角列出了完整顺序,并注明 cwd/祖先目录/仓库根三层项目配置「目录未信任时加载但禁用」。

          4. 详细介绍

          4.1 十一层来源与 precedence 数字

          • 代码里 9 个枚举变体(config_layer_source.rs:6-28),precedence() 给每个变体发一个 i16(config_layer_source.rs:33-51);「11 层」是按官方注释把 profile、项目 cwd/tree/repo 拆开计数的结果。数字越大越晚合并、越能覆盖低层:
          # 来源位置 枚举变体 precedence
          1 随包默认(内嵌 defaults.toml,loader/mod.rs:174 include_str!) PackagedDefaults -10
          2 macOS 托管设备描述(MDM) Mdm 0
          3 系统级 /etc/codex/config.toml(loader/mod.rs:66) System 10
          4 企业云配置 bundle EnterpriseManaged 15
          5 用户 ~/.codex/config.toml($CODEX_HOME) User(无 profile) 20
          6 用户 + 旧式 profile([profiles.<name>] 选中) User(profile=Some) 21
          7 项目 cwd 的 .codex/config.toml Project 25
          8 项目祖先目录逐层向上 Project 25
          9 仓库根(git rev-parse --show-toplevel) Project 25
          10 会话旗标 --config/-c 与运行时 UI 选择 SessionFlags 30
          11 旧式托管 managed_config.toml(文件 / MDM) LegacyManaged…FromFile / FromMdm 40 / 50 
          // config_layer_source.rs:33-51,注释为中文
pub fn precedence(&self) -> i16 {
    match self {
        ConfigLayerSource::PackagedDefaults { .. } => -10,   // 最低:随包默认,任何人可覆盖
        ConfigLayerSource::Mdm { .. } => 0,
        ConfigLayerSource::System { .. } => 10,              // /etc/codex/config.toml
        ConfigLayerSource::EnterpriseManaged { .. } => 15,
        ConfigLayerSource::User { profile, .. } =>
            if profile.is_some() { 21 } else { 20 },         // 带 profile 的 user 层 +1
        ConfigLayerSource::Project { .. } => 25,             // 仓库三处发现共用一档
        ConfigLayerSource::SessionFlags => 30,               // --config 等本次会话旗标
        ConfigLayerSource::LegacyManagedConfigTomlFromFile { .. } => 40,
        ConfigLayerSource::LegacyManagedConfigTomlFromMdm => 50,
    }
}
          rust
          • 项目层沿 cwd → 祖先目录 → 仓库根逐层发现(discover_project_layers,loader/mod.rs:1696-1822);判定目录 trust_level 后,非 trusted 目录的 .codex/config.toml 以 disabled_reason 挂载——不报错、不生效(loader/mod.rs:1050-1125)。

          4.2 项目层 DENYLIST:仓库内容不能抬高权限

          • 项目配置来自仓库内容,所以「不能决定用户的凭据发往哪里、本地跑哪些命令」——这是 loader/mod.rs:71-74 注释的原话。实现是一个常量表加一个剔除循环:
          // config/src/loader/mod.rs:75-88 —— 项目层强制剔除的键
const PROJECT_LOCAL_CONFIG_DENYLIST: &[&str] = &[
    "openai_base_url",
    "chatgpt_base_url",
    "apps_mcp_product_sku",
    "responses_api_metadata",
    "model_provider",
    "model_providers",
    "notify",
    "profile",
    "profiles",
    "experimental_realtime_webrtc_call_base_url",
    "experimental_realtime_ws_base_url",
    "otel",
];
          rust
          • sanitize_project_config(loader/mod.rs:1158 起)在合并前把这些键从项目层表里 table.remove 掉并记录告警(剔除循环在 1169-1174):键仍可从 user/system/managed/runtime 层生效(loader/mod.rs:73-74),只是仓库无权设置。观察名单:凭据去向(openai/chatgpt_base_url)、模型提供方(model_provider(s))、通知(notify)、profile 切换、遥测(otel)、实时通话端点——全是「仓库可借此钓鱼」的键。

          4.3 AskForApproval:审批的四个挡位

          • 定义在 protocol/src/protocol.rs:984-1024,#[default] 挂在 OnRequest 上(protocol.rs:993)——模型自行决定何时征求批准,是出厂默认:
          // protocol/src/protocol.rs:984-1004(节选,注释为中文)
pub enum AskForApproval {
    UnlessTrusted,    // "untrusted":内部策略,未信任项目里每条命令都要批准(用户不可写)
    #[serde(alias = "on-failure")]
    #[default]
    OnRequest,        // 模型自行决定何时征求批准(默认)
    Granular(GranularApprovalConfig), // 分细粒度开关
    Never,            // 永不询问,失败直接回给模型
}
          rust
          • GranularApprovalConfig(protocol.rs:1010-1024)把「哪类请求值得问」拆成开关:sandbox_approval(shell 升级批准)、rules(execpolicy prompt 规则)、skill_approval 与 request_permissions 默认 false=自动拒绝、mcp_elicitations。true=放行该类别到用户面前,false=自动拒绝且不展示。
          • "untrusted" 已停用:用户显式写 approval_policy = "untrusted" 会直接报错 is no longer supported; remove this setting(core/src/config/mod.rs:3635-3640)——旧「未信任项目需逐命令批准」语义只由内部信任态派生,不再暴露成用户可写字段。审批路由还分审查者:approvals_reviewer(protocol/config_types.rs:175-190)取 user(默认)或 auto_review,决定升级请求交给谁审。

          4.4 CLI 边界:三个旗标与 clap 的冲突拒绝

          • 共享 CLI 定义在 utils/cli/src/shared_options.rs:--sandbox/-s(L40-41)、--approve-for-me(L44-50,别名 not-so-yolo)、--dangerously-bypass-approvals-and-sandbox(L54-59,别名 yolo)。--approve-for-me 不是「一个开关」,而是改写三个配置键:
          // utils/cli/src/shared_options.rs:76-89(节选)——--approve-for-me 的实质
pub fn take_auto_review_config_overrides(&mut self, overrides: &mut CliConfigOverrides) {
    if self.auto_review {
        overrides.raw_overrides
            .push(r#"approvals_reviewer="auto_review""#.to_string());  // 审查者改自动
        overrides.raw_overrides
            .push(r#"approval_policy="on-request""#.to_string());      // 模型自决是否问
        overrides.raw_overrides
            .push(r#"sandbox_mode="workspace-write""#.to_string());    // 沙箱放宽到可写
        self.auto_review = false;
    }
}
          rust
          • yolo 则是「一个旗标关两道闸」:各处统一强制改写为 SandboxMode::DangerFullAccess + AskForApproval::Never(exec/src/lib.rs:296-300、tui/src/startup_orchestration.rs:15-25、cli/src/main.rs:2229-2238);它还会跳过「必须在 git 仓库内」的检查(exec/src/lib.rs:801-809,注释明示供外部沙箱环境使用)。CLI 注释自陈:EXTREMELY DANGEROUS(shared_options.rs:53)。
          • 危险组合在参数解析期就被 clap 拒绝,轮不到配置层裁决——交互面把 yolo 与 --ask-for-approval(approval_policy)、auto_review 与 approval_policy 设为互斥:
          // tui/src/cli.rs:139-144 —— clap 层冲突:yolo/-a 不能同用
fn mark_tui_args(cmd: clap::Command) -> clap::Command {
    cmd.mut_arg("dangerously_bypass_approvals_and_sandbox", |arg| {
        arg.conflicts_with("approval_policy") })
    .mut_arg("auto_review", |arg| arg.conflicts_with("approval_policy"))
}
          rust
          • 同理 --approve-for-me 声明与 sandbox_mode、yolo 互斥(shared_options.rs:48);--ask-for-approval/-a 只暴露 on-request|never 两值(approval_mode_cli_arg.rs:7-25),granular/untrusted 不进 CLI——CLI 是「快捷开关」,精细控制留给 config.toml。

          4.5 模型路由:三类凭据、一个 provider 表

          • model_provider 指向 model_providers 表里的键(内置 openai、amazon-bedrock、ollama、lmstudio,built_in_model_providers 在 model-provider-info/src/lib.rs:511-543),每个 provider 描述端点与认证(model-provider-info/src/lib.rs:96-151):base_url、env_key(API key 所在环境变量名)、auth(命令式取 token)、aws(SigV4),以及关键的 requires_openai_auth: bool(lib.rs:144)——true 表示走 ChatGPT 登录态(auth.json)。
          • 端到端默认 URL 在 to_api_provider 里一分定音(model-provider-info/src/lib.rs:292-306):认证模式属 ChatGPT 系 → CHATGPT_CODEX_BASE_URL(https://chatgpt.com/backend-api/codex,lib.rs:40);否则 → https://api.openai.com/v1;provider.base_url 优先。于是三类凭据自然分流:ChatGPT 登录(requires_openai_auth=true)、OpenAI API key(env_key)、自建端点 + env_key(–oss 或自写 base_url)。OSS 默认 http://localhost:\<port>/v1,可被 CODEX_OSS_PORT / CODEX_OSS_BASE_URL 覆盖(lib.rs:592-608);内置 id 不可被整体覆盖,用户扩展走 [model_providers.<name>](merge_configured_model_providers,lib.rs:550-590)。

          4.6 扩展面:mcp_servers / skills / hooks / plugins

          • mcp_servers(config_toml.rs:266-270):`mcp_servers.<name>` 键值表(TOML 数组表格语法),原始形态 RawMcpServerConfig(mcp_types.rs:323-382)——stdio 用 command/args/env/cwd,streamable_http 用 url/bearer_token/http_headers,stdio 与 url 互斥校验(mcp_types.rs:434-470);公共键含 enabled/required/default_tools_approval_mode/enabled_tools|disabled_tools/oauth。
          • skills(config_toml.rs:457):[skills] 下 bundled.enabled / include_instructions / max_context_tokens / config={path=… 或 name=…,enabled=true|false} (skills_config.rs:20-47);只有 User 与 SessionFlags 层参与合并(skills_config.rs:150-158),项目层改不了。
          • hooks(config_toml.rs:460):12 个事件表——PreToolUse / PermissionRequest / PostToolUse / PreCompact / PostCompact / SessionStart / SessionEnd / UserPromptSubmit / SubagentStart / SubagentStop / Stop / Interrupt;每事件一列 {matcher="…",hooks=[…]},handler 按 type 区分 command / mcp_tool / prompt / agent;[hooks.state.<key>] 持久化 enabled 与 trusted_hash(每次改动要重新信任),--dangerously-bypass-hook-trust 跳过信任。
          • plugins(config_toml.rs:463-464):[plugins.<name>] 只管开关与工具策略(enabled、mcp_servers..enabled_tools 等,types.rs:886-923),刻意不含 transport——启动方式归 plugin manifest;[marketplaces.<name>] 在同区(config_toml.rs:467-468);新式集中特性开关是 [features.<name>](config_toml.rs:470-474)。

          5. 动手活动:写最小 config.toml,并验证项目层 DENYLIST

          动手活动:最小安全配置 + 项目层剔除实验

          目标:亲手写一份「只读 + OnRequest」的配置并分别放到 user 层与项目层,观察同一份文件在两处命运不同,反推 DENYLIST 的边界。

          步骤:

          1. 在 ~/.codex/config.toml(或 $CODEX_HOME/config.toml)写入最小配置:
          # ~/.codex/config.toml —— 最小安全起步配置
approval_policy = "on-request"   # 模型自行决定何时征求批准(与默认一致,显式写出)
sandbox_mode = "read-only"       # 模型 shell 命令一律只读执行
          toml
          1. 启动 codex 跑一条会写文件的命令,确认它被沙箱挡下并进入审批(或直接拒绝);
          2. 把同一文件复制到仓库根 ./.codex/config.toml 再启动:观察两键是否仍生效(它们不在 DENYLIST 中,项目层可用);
          3. 向项目层文件追加 model_provider = "openai" 与 openai_base_url = "http://127.0.0.1:9999/v1" 后重启,观察剔除告警;再想:如果把这两键写回 user 层文件,仓库还能不能管到?

          完成标准:能写出——① 最小配置的两键为什么放项目层也不被剔(对照 4.2 名单逐键核对);② 若在项目层声明 model_provider / model_providers / openai_base_url / chatgpt_base_url / notify / profile / profiles / otel / experimental_realtime_*_base_url,会被剔除并告警,且不影响 user 层同键;③ 一句话说出该设计防的攻击路径(恶意仓库劫持凭据去向)。

          6. 边界与坑

          现象 原因 处理
          改了 ~/.codex/config.toml 却不生效 低层被覆盖:项目层(25)/会话旗标(30)压过 user(20) 用 --config 临时覆盖排查,或查该键是否在更高层被写
          写 approval_policy = "untrusted" 直接报错 旧策略值已废弃(core/src/config/mod.rs:3635-3640 硬拒绝) 删掉该键;未信任项目语义由系统按信任态派生
          仓库想固定模型或改凭据端点 键在 DENYLIST(loader/mod.rs:75-88),项目层剔除 这些键只从 user/system/managed 层设置
          -a 与 --dangerously-bypass-approvals-and-sandbox 同用 clap 互斥声明(tui/src/cli.rs:139-144) 二选一;不存在「后写覆盖先写」的侥幸
          想给项目开危险沙箱 项目层可写 sandbox_mode,但沙箱/审批双闸仍在(03 章 escalation 链) 用 --approve-for-me(workspace-write)或显式审批,别上 yolo
          profile 名含非法字符 ProfileV2 名字仅 ascii 字母数字与 +_-(protocol/config_types.rs:143-159) 改名后重试

          7. 总结

          概念 一句话
          配置分层 11 个来源位置 → 9 个枚举变体 → precedence 数字 -10~50,数字大者覆盖小者
          项目层 DENYLIST 仓库内容不能决定凭据去向与本地命令:剔除 + 告警,键仍可从 user/system 层生效
          AskForApproval UnlessTrusted(内部)/ OnRequest(默认)/ Granular / Never;untrusted 用户可写值已废弃
          CLI 快捷开关 –approve-for-me 改写三键(auto_review+on-request+workspace-write);yolo=DangerFullAccess+Never 双强制
          冲突拒绝 clap 在解析期拒绝 yolo/-a、approve-for-me 与 sandbox_mode 的组合,轮不到配置层
          模型路由 requires_openai_auth 分流 ChatGPT 登录 / API key / 自建端点;OSS 默认 localhost:<port>/v1
          扩展面 mcp_servers(stdio/http)、skills(仅 User/SessionFlags 层)、hooks(12 事件+信任持久化)、plugins(只管开关与工具策略)

          思考题:为什么 approval_policy 与 sandbox_mode 不在项目层 DENYLIST 里,而 model_provider 在?「项目层不能改 model_provider」与「项目层可以申请更宽沙箱」矛盾吗?

          参考答案

          DENYLIST 防的是「凭据去向与本地命令被仓库劫持」:改 model_provider/model_providers/base_url 等于把对话与命令静默导给攻击者服务器,是无声的泄密;而 sandbox_mode/approval_policy 再宽,也只是「请求更高权限」——命令仍要过 03 章的执行链:沙箱翻译、拒绝检测、escalation 升级仍需审批(未信任项目还默认逐命令批准)。也就是说,前者的危害发生在「看不见的配置层」,后者的危害发生在「看得见的执行闸门」,闸门系统保证每次越权都被看见、被批准;所以名单只剔「能静默改变信任边界」的键。若项目真被信任(trusted),它申请 workspace-write 也仍受审批约束——这正是「配置可分层、权力不可上行」的完整含义。
