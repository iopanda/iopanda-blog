          扩展系统

          02 章看到会话与压缩都收在 agent-session.ts 一个类里;Pi 能把内核压得这么小,秘密在于一切「没内置」的功能都有钩子可挂——官方文档第一行就是「pi can create extensions. Ask it to build one for your use case.」。本章拆开扩展系统的四层载体:TS 扩展、skills、prompt templates、pi packages,从 Extension API 的注册表、36 个生命周期事件与三级上下文权限,读到 examples 里 85 个「示例即契约」,最后沿内置 /reload 的 shutdown→invalidate→重建链路看 Pi 如何修改自己后热载重生。

          学习目标:学完本章,你将能够——

          1. 画出四层扩展载体的分工(TS 扩展/skills/prompt templates/pi packages),说出每层各自的文件形态与挂载点;
          2. 复述 Extension API 的注册模型:ExtensionFactory、注册表结构(types.ts:1765)、36 个 on() 事件六大类、registerTool/Command/Shortcut/Flag;
          3. 解释 ctx 三级权限的递进(ExtensionContext → ExtensionCommandContext → 动作面),并说明「为什么工具回调拿不到 ctx.reload()」;
          4. 走读 permission-gate/plan-mode/subagent/sandbox 等 examples,说出每个示例挂在哪些钩点上;
          5. 沿 /reload 热载链路(agent-session.ts:2810)复述「旧 runner shutdown→invalidate→重建」,并解释斜杠命令的三合一来源。

          1. 概念:四层载体 + 一个注册表

          • 内核保持小、能力外置(对照 02.04 的工具外置路线),外置能力分四层,每层是一种文件约定:
          层 载体 挂载点 主要源码
          TS 扩展 .pi/extensions/*.ts(或 ~/.pi/agent/extensions/、pi -e 显式路径) 注册表:工具/命令/快捷键/事件 extensions/types.ts、loader.ts、runner.ts
          Skills 目录式 SKILL.md + frontmatter /skill:name 展开或模型侧 XML 调用 core/skills.ts
          Prompt templates *.md + frontmatter + $1 占位符 /template args 文本展开 core/prompt-templates.ts
          Pi Packages npm/git 包,package.json 的 "pi" 字段声明资源 安装后按 manifest 分发到前三层 core/pi-manifest.ts、package-manager.ts
          • 三层用户可见层正好被一个类型收拢——斜杠命令的三种来源 slash-commands.ts:4:export type SlashCommandSource = "extension" | "prompt" | "skill";(pi packages 只是前三层的分发容器,不新增命令来源)。docs/index.md:3 自述「stay small at the core while being extended through TypeScript extensions, skills, prompt templates, themes, and pi packages」,四层即官方对「小核心」的补全答案。

          2. 为什么这样设计:让扩展成为头等公民

          • 01 章的内核最小化把权限弹窗、plan mode、子代理全部请出主循环,代价是这些功能必须有人能补——补的方式不是插件框架堆 API,而是事件面 + 注册表的窄接口:docs/extensions.md:1「pi can create extensions. Ask it to build one for your use case.」,README.md:15 自称 “our self extensible coding agent”——连「写扩展」这件事都能让 Agent 自己做。
          • 四层分工的深意是分层披露、按需加载:TS 扩展可执行任意代码(带信任门控),skills/templates 只是文本资产(无代码风险、可被模型自行触发),pi packages 负责把带依赖的复杂扩展分发到位。风险与便利随层递减/递增,内核只认「资源加载 → 注册 → 事件分发」一条链路。
          • 与 02.04 的对照:工具协议(如 MCP)把外部能力接成工具;Pi 更进一步,把「接工具的能力本身」做成事件——permission-gate 这类安全策略在 Pi 里不是内核功能,而是挂在 tool_call 事件上的示例(04 章再展开安全模型)。

          3. 作用:扩展在一条输入里被看见四次

          • 用户在 TUI 输入一行,同一个文本依次经过四种解释(agent-session.ts:1167-1206):① _tryExecuteExtensionCommand(:1168)先试扩展命令——命中即执行,可自行与 LLM 交互;② _extensionRunner.emitInput(:1186)把整行交给 input 事件,扩展可 handled/transform;③ _expandSkillCommand(:1205)把 /skill:name args 展开成 <skill> 内容块;④ expandPromptTemplate(:1206)把 /template args 按模板替换。扩展命令以外的展开失败会回退原文本而非报错——注释原话 :1383「Expands skill commands and prompt templates. Errors on extension commands.」:命令是「动作」,技能与模板只是「文本」。

          4. 详细介绍

          4.1 Extension API:工厂函数与注册表

          • 扩展 = 一个导出工厂的 TS 文件,签名极简 types.ts:1587-1588:
          /** Extension factory function type. Supports both sync and async initialization. */
export type ExtensionFactory = (pi: ExtensionAPI) => void | Promise<void>;
          typescript
          • 工厂拿到的 pi 上,注册结果落进每扩展一份的注册表 types.ts:1765-1778——一次加载的产物,除 path 元信息外全是 Map:
          export interface Extension {
	path: string;
	resolvedPath: string;
	hidden?: boolean;
	sourceInfo: SourceInfo;
	handlers: Map<string, HandlerFn[]>;          // 生命周期事件(36 种)
	tools: Map<string, RegisteredTool>;          // LLM 可调工具
	messageRenderers: Map<string, MessageRenderer>;
	markdownTransformer?: MarkdownTransformer;
	entryRenderers?: Map<string, EntryRenderer>;
	commands: Map<string, RegisteredCommand>;    // /命令
	flags: Map<string, ExtensionFlag>;           // CLI flag
	shortcuts: Map<KeyId, ExtensionShortcut>;    // 键盘快捷键
}
          typescript
          • 注册入口集中在 ExtensionAPI(types.ts:1252 起):registerTool :1308、registerCommand :1317、registerShortcut :1320、registerFlag :1329(取值 getFlag :1345);另有消息渲染三类(registerMessageRenderer :1352 / registerMarkdownTransformer :1355 / registerEntryRenderer :1358)与动作 sendMessage :1365、sendUserMessage :1375。而 plan-mode 动态换工具集用的 setActiveTools/refreshTools 在动作面 ExtensionActions :1705-1706,经 runner 初始化后复制进共享 runtime(types.ts:1760 注释「Created by loader with throwing action stubs, completed by runner.initialize()」)。
          • 事件订阅 on(event, handler) 共 36 个重载(types.ts:1257-1301),按事件对象分六类:
          类 事件 数
          resource project_trust、resources_discover 2
          session session_start、session_info_changed、session_before_switch/fork/compact/tree、session_compact、session_compact_failed、session_shutdown、session_tree 10
          agent context、before_provider_request、before_provider_headers、after_provider_response、before_agent_start、agent_start/end/settled、ui_prompt_start/end、turn_start/end、message_start/update/end 15
          model model_select、thinking_level_select 2
          tool tool_call(:1298,可 block/改写)、tool_execution_start/update/end、tool_result、user_bash 6
          input input(:1301,可 handled/transform) 1
          • 可返回结果的事件(带第二泛型参数,如 ExtensionHandler<ToolCallEvent, ToolCallEventResult>)是拦截点:返回 {block:true} 即否决,返回 undefined 即放行——这是 4.4 节 permission-gate 的机制基础。

          4.2 ctx 三级权限:工具拿不到会话控制权

          • 事件回调与命令处理器拿到的 ctx 不同(types.ts:309-355)。基础 ExtensionContext :309-349 只读:sessionManager(modelRegistry、cwd、isProjectTrusted()、signal/abort()、shutdown()、compact()、getSystemPrompt())+ UI 帮助 ui(select/confirm/input/editor/notify)——工具与普通事件回调只能到这级。命令处理器才拿到 ExtensionCommandContext :355+,追加 waitForIdle()、newSession()、fork()、switchSession()、reload(),接口注释 :351-354 原话:Includes session control methods only safe in user-initiated commands.
          • 动作面同样是三级清单:ExtensionActions(pi.* 全局动作):1696 → ExtensionContextActions(ctx.* 事件回调):1717 → ExtensionCommandContextActions(ctx.* 命令):1736,而 reload: () => Promise<void> 只出现在最后一级 :1755。设计意图一句话:能重启会话的动作,只允许用户发起的命令执行,模型与工具永远够不到——4.5 节的 reload-runtime.ts 就是这个边界的活教材。

          4.3 加载与发现:只扫一层,失败不拖垮

          • 发现规则刻在注释里 loader.ts:711-720:「No recursion beyond one level. Complex packages must use package.json manifest.」——① extensions/*.ts|*.js 直接加载;② 子目录带 index.ts|index.js 加载;③ 子目录带 package.json 的 "pi" 字段则按 manifest 加载(带依赖的复杂扩展走这条)。位置优先级 loader.ts:779-785:项目本地 cwd/.pi/extensions/ → 全局 agentDir/extensions/ → 显式 -e 配置路径。
          • 加载器用 jiti 直接 import TS(loader.ts:490-507,moduleCache:false、按运行形态切换 virtualModules/tsconfigPaths/alias),不打包不构建;模块缓存按 {cwd,generation} 作废(isCurrentCacheToken :482-488),保证改代码后热载拿到新工厂。事务式注册:工厂执行期间的注册先记 pending,成功才 commit()、抛错则 discard() 注销(loader.ts:463-479),单扩展失败只上报错误数组,不拖垮其余扩展(runner.ts 把处理器异常聚合成 ExtensionError[] 逐个上报)。

          4.4 examples:85 个「示例即契约」

          • examples/extensions/ 下 85 个 .ts(9 个自带目录,如 plan-mode/subagent/sandbox/doom-overlay/with-deps),同时是文档与 API 契约的活测试;examples/sdk/ 另有 13 个编号示例展示 createAgentSession() 编程式用法。挑四个看钩点:
          • permission-gate.ts(34 行,安全闸门)——权限管控「用事件 API 自造」的最小示范,挂在 tool_call 事件上:
          // examples/extensions/permission-gate.ts:10-34(节选)
pi.on("tool_call", async (event, ctx) => {
	if (event.toolName !== "bash") return undefined;
	const command = event.input.command as string;
	const isDangerous = dangerousPatterns.some((p) => p.test(command)); // rm -rf|sudo|chmod/chown 777
	if (isDangerous) {
		if (!ctx.hasUI) {
			return { block: true, reason: "Dangerous command blocked (no UI for confirmation)" };
		}
		const choice = await ctx.ui.select(`⚠️ Dangerous command:\n\n  ${command}\n\nAllow?`, ["Yes", "No"]);
		if (choice !== "Yes") { return { block: true, reason: "Blocked by user" }; }
	}
	return undefined;
});
          typescript
          • plan-mode/index.ts(390 行,只读探索模式)——三个钩点齐活:registerFlag("plan") :53 支持 pi --plan 启动即只读;/plan、/todos 命令(:141、:146)与 Ctrl+Alt+P 快捷键(:158)切换;切换时 pi.setActiveTools(...) :108 把工具集从 ["read","bash","edit","write"] 换成 ["read","bash","grep","find","ls","questionnaire"](:22-24),bash 再经 utils.ts 的 isSafeCommand 白名单只放行只读命令。plan mode 没有内置状态机,完全由扩展自己维护 planModeEnabled 布尔与工具列表。
          • subagent/index.ts(1038 行,隔离子代理)——用 spawn 起独立 pi 进程(args 含 --mode json -p --no-session :300)实现上下文隔离;single/parallel(≤8、并发≤4)/chain 三模式由 mode 参数选择(:164),JSON mode 捕获结构化输出;agents/ 目录用 .md 定义角色(scout/planner/reviewer/worker),对主循环只暴露一个 registerTool :472 的 subagent 工具。
          • sandbox/(带 package-lock 的目录扩展)——覆盖内置 bash 工具,把执行包进 @anthropic-ai/sandbox-runtime(OS 级沙箱);package.json:11-15 展示 pi manifest:"pi": { "extensions": ["./index.ts"] },依赖精确锁版 "@anthropic-ai/sandbox-runtime": "0.0.26"——第三层分发规则的实物。安全策略的四种答案(拦截/只读/隔离进程/沙箱)全在 examples 里,内核一个都没内置。

          4.5 Skills 与 prompt templates:文本资产,渐进披露

          • Skill = 目录式 SKILL.md + 附带文件。frontmatter 字段 skills.ts:67-72:name / description / "disable-model-invocation",名称限长 64、描述 1024(:11-14);扫描遵守 .gitignore/.ignore/.fdignore(:16)。两种触发:用户 /skill:name args(agent-session.ts:1353-1377 展开成 <skill name location> 块);模型侧直接输出 <skill name="..." location="..."> XML 块(parseSkillBlock :132-141),disable-model-invocation 可禁止模型自动调用。
          • 渐进披露的要点:skill 全文不常驻 system prompt,只在被点名时才把文件内容包进消息——对照 02.02 的上下文预算,技能这种「低频大文本」按需注入,不炸 prompt cache、不占每轮窗口。
          • Prompt template = markdown + frontmatter(name/description/argumentHint),内容用 $1、$2… 位置占位符(prompt-templates.ts:58-61),按名称参数化替换后整段进对话,适合「固定句式的工作流开场白」;加载自全局 agentDir/prompts/ 与项目 .pi/prompts/(:189-203,非递归扫 .md)。

          4.6 /reload 自举热载:修改自己然后重生

          • 内置命令表 slash-commands.ts:19-43 纯声明式 23 条,/reload :41 描述「Reload keybindings, extensions, skills, prompts, themes, and context files」。实现是「整旧建新」五步(agent-session.ts:2810-2835):
          async reload(options?): Promise<void> {
	const oldRunner = this._extensionRunner;
	const previousFlagValues = oldRunner.getFlagValues();
	await emitSessionShutdownEvent(oldRunner, { type: "session_shutdown", reason: "reload" }); // ① 通知旧扩展
	oldRunner.invalidate();                // ② 旧 ctx/pi 全部作废(runner.ts:593 起,再调用即抛错)
	await this.settingsManager.reload();
	resetApiProviders();
	await this._resourceLoader.reload();   // ③ 重扫扩展/skills/prompts/themes
	this._buildRuntime({ activeToolNames: this.getActiveToolNames(),
		flagValues: previousFlagValues, includeAllExtensionTools: true }); // ④ 重建(保留 flag 值)
	await this._extensionRunner.emit({ type: "session_start", reason: "reload" }); // ⑤ 向新扩展广播 session_start
	await this.extendResourcesFromExtensions("reload");
}
          typescript
          • 旧 runner 的 invalidate() 让任何持有旧 ctx 的代码在下次调用时抛「Do not use a captured pi or command ctx after ctx.newSession()…」(runner.ts:593-605)——热载不靠「尽量兼容旧引用」,而是显式作废,逼所有持有者走新 ctx。模块缓存按 generation 作废(loader.ts:482-488)保证改过的 .ts 重新 import。
          • AI 自改自身的闭环:reload-runtime.ts:14-36 演示边界——LLM 可调工具只有 ExtensionContext、不能直接 ctx.reload()(:22 注释 Tools get ExtensionContext, so they cannot call ctx.reload() directly),于是工具内 pi.sendUserMessage("/reload-runtime", { deliverAs: "followUp" })(:30)把命令排队,命令处理器里才执行 await ctx.reload()(:17)。模型「想重启运行时」只能请求,决定权在命令通道——与 4.2 节的三级权限互为表里。

          6. 边界与坑

          现象/坑 原因 处理
          行号与讲义不一致 2026-09 检出快照,仓库每日在变 grep/search 重定位,方法比行号可靠
          扩展能 rm -rf 整个家目录 扩展默认全系统权限(docs/extensions.md:111),无内置权限系统 只从可信来源安装;要边界用容器/沙箱扩展(04 章)
          在工具回调里调 ctx.reload() 报错 工具只有 ExtensionContext,无会话控制权(types.ts:351-354) 学 reload-runtime.ts:30 排队 followUp 命令
          /reload 后旧闭包还在跑且报 stale 错 invalidate() 显式作废旧 ctx(runner.ts:593) 热载后一切操作走新 ctx,别捕获旧 pi 对象
          以为 skill 全文常驻 prompt 渐进披露:按需展开,不炸窗口 看 agent-session.ts:1366 展开时才拼块
          扩展子目录没被加载 只扫一层,复杂包须 package.json 的 “pi” 字段(loader.ts:719) 带依赖的扩展按 sandbox/ 的 manifest 形态组织

          7. 总结

          概念 Pi 的落点 出处
          四层分工 TS 扩展(代码)/skills(目录 SKILL.md)/templates(.md+$1)/packages(“pi” manifest) slash-commands.ts:4、docs/index.md:3
          注册模型 ExtensionFactory=(pi)=>…,注册表全是 Map types.ts:1587、:1765
          事件面 36 个 on() 六类,可返回结果的事件即拦截点 types.ts:1257-1301
          ctx 权限 ExtensionContext → ExtensionCommandContext → 动作面,reload 只在最后一级 types.ts:309/355/1696/1755
          加载发现 只扫一层;jiti 直载;commit/discard 事务;失败隔离 loader.ts:711、:490、:463
          示例即契约 85 个 examples 覆盖工具/事件/UI/提供方,安全策略全在示例层 examples/extensions/
          自举热载 /reload = shutdown→invalidate→重扫→重建→session_start agent-session.ts:2810、slash-commands.ts:41
          斜杠三合一 extension 命令执行 / skill 与 template 文本展开 agent-session.ts:1168/1205/1206

          思考题:① 为什么 tool_call 事件的返回值协议要用「返回 undefined 即放行」而不是「默认放行+显式拒绝」——对同时挂多个拦截扩展意味着什么?② permission-gate 只在 ctx.hasUI 为真时弹窗,无 UI 直接 block——print/RPC 模式跑危险命令时,这个默认安全吗?③ 若把 reload 权限放开给工具回调,会出现什么滥用场景,reload-runtime.ts 的排队设计如何堵住它?

          参考答案

          ① 事件分发对每个 handler 收集返回值、聚合语义:任一返回 {block:true} 即拦截、全部 undefined 才放行——「undefined 即放行」让不关心的扩展零成本旁观,新拦截器只要返回 block 就生效;若反过来「默认拒绝」,任何旁观扩展的返回值类型都要精确定义,多拦截器叠加时语义会变成「全票通过才放行」,误伤率更高。② 安全但僵硬:非交互模式没有「人」在场,block 是唯一自洽选择(permission-gate.ts:20-23);代价是自动化流水线里 rm -rf 永远被拦,需要流水线自己改用受信环境或白名单工具——这正是「安全策略留给示例」的边界所在。③ 工具回调若能 reload,模型只需构造一次工具调用即可让整个运行时换血:正在执行的其他工具会因 invalidate 抛错、会话状态可能错乱,更糟的是这等于把「重启」交给可能被提示注入的模型输出;排队成 followUp 命令后,执行权回到用户发起的命令通道,模型只能「请求」不能「执行」。
