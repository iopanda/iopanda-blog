          技能系统

          01 章讲清了主循环「每轮怎么转」,本章回答「Agent 凭什么会干活」:Hermes 把可复用的操作知识做成文件系统里的声明式技能包——一个目录、一份 SKILL.md(frontmatter + markdown),其余交给加载链路。仓库自带 58 个内置技能,但系统提示词里从不塞技能正文,只给索引与一条铁律:「命中就用 skill_view(name) 加载」。匹配不靠向量检索,靠模型自读索引;技能会老化,curator 状态机把它们从 active 一路管到 archived,甚至用 LLM 把散技能合并成 umbrella——自我进化闭环的最小单元就在这里(呼应 02.02 的「可复用上下文包」)。 学习目标:学完本章,你将能够——

          1. 说清「技能 = 文件系统声明式技能包」的含义,并解释它比 system prompt 工程进在哪一步;
          2. 读懂真实 SKILL.md 的 frontmatter(name/description/platforms/metadata.hermes/prerequisites),指出每个字段在加载链路哪个环节被消费;
          3. 画出「扫描 → 解析 → 平台过滤 → 快照缓存 → 注入 volatile 段」加载链路,给每步标出文件:行号;
          4. 解释为何 Hermes 用「模型自读索引 + 按名加载」而非向量检索,并说明各环节的 fail-open 策略;
          5. 描述 curator 的 active/stale/archived 状态机与 consolidate LLM 合并(umbrella)的触发条件与更新优先级。

          1. 概念:技能 = 文件系统声明式技能包

          • 一个技能就是一个目录 skills/<category>/<name>/SKILL.md:YAML frontmatter 声明「元数据」,markdown 正文声明「怎么做」。正文常用 When to Use / When NOT to Use / Quick Reference / Pitfalls 等小节,让模型自己判断何时该用、何时坚决不用(如 apple-notes 正文明确「Quick agent-only notes → use the memory tool」,防止越界误用)。
          • 技能可附带支持文件子目录 references/ templates/ assets/ scripts/(参考资料/样板/脚本),它们不算独立技能——扫描器把它们当作所属技能的零件(agent/skill_utils.py:52,SKILL_SUPPORT_DIRS)。
          • 技能目录有多个来源,按优先级合并:项目技能 .hermes/skills(须显式信任)、profile 本地技能、org 镜像 _org/<org_id>、外部只读目录;内置 skills/ 是仓库自带的「出厂技能库」,用户级技能落在 ~/.hermes/skills/。

          2. 为什么这样设计:比 system prompt 工程更进一步

          • 02.02 的 system prompt 工程把知识焊死在提示词里,改一次技能就得重发整段 stable 上下文;技能把知识放回文件系统,提示词里只留索引与加载指令。新增、修订一个技能只改变注入的 volatile 段前缀,不动 stable/context 段——prompt cache 全部保住(system_prompt.py:20-21 把 skills index 归入 volatile 层)。
          • frontmatter 是声明式门控:platforms: [macos] 让同一份技能库在 darwin/linux/win32 各取所需;session_platforms 决定技能只对特定渠道(如 teams/cron)可见;prerequisites.commands 让技能在缺工具时自动隐身——门控逻辑集中在解析层,技能作者只写声明不写代码。
          • 技能是运行时可变资产:agent 用过之后可由后台评审与 curator 修改、合并、归档,知识随使用沉淀。知识资产的变更跟代码一样可审计、可回滚(curator 跑前有快照),这是「自我进化」的存储基础。

          3. 作用位置:技能「文件 → 上下文 → 执行」总览

          SKILL.md(frontmatter+正文)          每轮构建 system prompt 时
        │ ①扫描 iter_skill_index_files(skill_utils.py:1285)
        ▼
   解析+平台过滤 _parse_skill_file(prompt_builder.py:1759)
        │ ②双层缓存:内存 cache_key(:1925)+ 磁盘快照(:1663/:1681)
        ▼
   技能索引块(名称+一句描述+指令)
        │ ③注入 volatile 段最前(system_prompt.py:925-926)
        ▼
   模型收到提示词:「命中必须 skill_view(name) 加载」
        │ ④按名加载 tools/skills_tool.py:1086(全文+支持文件回流)
        ▼
   模型按正文执行;skill_manage / curator 事后修订、合并、归档

          4. 详细介绍

          4.1 frontmatter 真实样例:skills/apple/apple-notes/SKILL.md:1-14

          ---
name: apple-notes
description: "Manage Apple Notes via memo CLI: create, search, edit."
version: 1.0.1
author: Hermes Agent
license: MIT
platforms: [macos]
metadata:
  hermes:
    tags: [Notes, Apple, macOS, note-taking]
    related_skills: [obsidian]
prerequisites:
  commands: [memo]
---
          yaml
          • 解析入口 parse_frontmatter(agent/skill_utils.py:176):YAML CSafeLoader 全量解析,失败回退简单 key:value 切分,并剥离 UTF-8 BOM——Windows 编辑器存盘时可能注入 BOM,不剥掉整个 frontmatter 会被静默丢弃(name/platforms 门控全失效)。
          • platforms: [macos]:匹配时经 PLATFORM_MAP 映射(sys.platform 的 darwin/linux/win32,skill_utils.py:22-26),Termux 有特例——Android 上的 Linux userland 也接受 linux 标签(skill_utils.py:245-249);缺省 = 全平台。
          • prerequisites.commands: [memo]:环境相关门控 skill_matches_environment(skill_utils.py:353)检查命令/环境变量,不满足则技能不进索引。
          • metadata.hermes.session_platforms: [teams, cron](见 skills/productivity/teams-meeting-pipeline/SKILL.md:17)是渠道级门控——只在特定平台会话里展示,避免把只在会议渠道有用的技能塞给终端用户。
          • 解析后的快照条目由 _build_snapshot_entry(agent/prompt_builder.py:1700)产出 {skill_name, category, description, platforms, conditions},org 技能还会剥掉 _org/<id>/ 前缀再展示名称。

          4.2 加载链路:扫描 → 解析过滤 → 双层缓存 → 注入 volatile

          1. 扫描:iter_skill_index_files(agent/skill_utils.py:1285)遍历各来源目录的 SKILL.md,支持子目录 references/ 等按排除清单跳过;
          2. 解析 + 平台/环境过滤:_parse_skill_file(agent/prompt_builder.py:1759)读文件、parse_frontmatter、跑平台与环境匹配,失败时 fail-open(返回可显示、空 frontmatter),坏技能不拖垮整轮 prompt 构建;
          3. 条件过滤:_skill_should_show(prompt_builder.py:1785)处理 session_platforms、fallback_for(有主工具则藏掉弱替代技能)、requires(缺工具则藏),同样 fail-open;
          4. 双层缓存:入口 _build_skills_system_prompt_inner(prompt_builder.py:1912)先算 cache_key(skills_dir + 工具集 + 平台 + 禁用名单等,prompt_builder.py:1925),命中内存缓存直接返回;L2 是磁盘快照 .skills_prompt_snapshot.json——_load_skills_snapshot(:1663)按 mtime/size manifest 校验文件是否变过,变了才由 _write_skills_snapshot(:1681)重写。58 个技能每次全量重扫太重,快照让「没变化 = 零 IO」;
          5. 注入:system_prompt.py:619 先门控「skills_list/skill_view/skill_manage 任一在 valid_tool_names 才渲染」,:641 调 build_skills_system_prompt,结果 append 进 volatile 段最前(system_prompt.py:925-926),内存快照块在后——技能一变只破 volatile 前缀缓存,stable 段(角色与主指令)与 context 段毫发无损。

          索引块的指令文案(prompt_builder.py:2198-2204)值得逐字读:

          ## Skills
Before replying, scan the skills below. If a skill matches or is even partially relevant
to your task, you MUST load it with skill_view(name) and follow its instructions.
Err on the side of loading — it is always better to have context you don't need
than to miss critical steps, pitfalls, or established workflows.
          text

          「Err on the side of loading」是刻意的召回偏向:宁可多加载浪费 token,不可漏掉关键步骤。编码专注模式(compact_categories)只把索引降级为 names-only,绝不整段隐藏。

          4.3 匹配机制:无向量检索,模型自读索引 + 按名加载

          • Hermes 没有技能向量库:匹配 = 模型每轮扫一遍索引文本,自认为命中就发一次工具调用 skill_view(name)(tools/skills_tool.py:1086),工具返回该 SKILL.md 全文与支持文件,正文进入下一轮上下文。索引里只有「名称 + 一句话 description + 平台/条件」,正文不进提示词,天然省 token。
          • 为什么够用:技能数量级是几十到几百,远小于 RAG 要面对的文档库;技能名与 description 是作者精心写的「触发词」,模型按名检索的准确率足够;省掉的向量库换来零依赖、零同步问题。
          • 代价由指令补偿:索引文案要求「部分相关也加载」,宁滥勿缺;skill_view 的同任务去重(_record_skill_view tools/skills_tool.py:2062 / _check_skill_view_dedup :2085)保证同一 task 内不重复注入同一技能(磁盘未变时返回去重桩)。
          • 其余入口:/skill 命令体系(用户手动指定)、写工具 skill_manage(tools/skill_manager_tool.py,创建技能前校验 frontmatter/content/路径,后台评审强制 read-before-write)。

          4.4 curator 状态机:active → stale → archived 与 LLM 合并

          • 入口 run_curator_review(agent/curator.py:1521),流程分两段:先跑确定性状态流转 apply_automatic_transitions(curator.py:305),按每技能 usage 记录的最后真实活动时间推进状态机;consolidate 默认 OFF(get_consolidate,curator.py:204),开启时才 fork 一个子 AIAgent 做 LLM 评审。
          • 状态三值定义在 tools/skill_usage.py:53-55:STATE_ACTIVE = "active" / STATE_STALE = "stale" / STATE_ARCHIVED = "archived";usage 记录(created_by/state/last_used 等)存 skills/.usage.json,写时加锁。curator 只管理 created_by 为 agent 的技能——内置 bundled/hub/external/pinned/user-owned 全部禁止写入(background_review.py:563-577 的保护清单),防止评审把自己的偏好写进别人的技能。
          • LLM 评审的更新优先级写在 _SKILL_REVIEW_PROMPT(agent/background_review.py:476)的 Preference order 段(:501-541):①patch 本会话已加载且 curator-managed 的技能 → ②patch 现有 umbrella → ③在 references/templates/scripts 下加支持文件 → ④新建 class 级 umbrella。新建名禁止是 PR 号/错误串/一次性任务名(「fix-X-today」这种名字注定被拒),逼着 agent 沉淀类级知识而不是会话垃圾。
          • 用法 hermes curator run [--consolidate],跑前自动快照(curator_backup)以便回滚;评审 agent 自身把 nudge 间隔置 0 防递归。

          5. 动手活动:拆解一个真实 SKILL.md + 走注入链路

          动手活动:拆解 skills/apple/apple-notes/SKILL.md

          目标:能独立回答「一个技能从文件到模型上下文,代码各在哪几步」,并把 frontmatter 每个字段对到门控代码。

          步骤:

          1. 打开 /tmp/hermes-agent/skills/apple/apple-notes/SKILL.md 全文,逐字段核对 frontmatter(1-14 行)与正文小节(When to Use / When NOT to Use / Quick Reference),指出「When NOT to Use 里建议改用 memory 工具」这一句对应 4.3 的什么设计意图;
          2. 改一版「自杀式实验」:把 platforms: [macos] 改成 [win32],再读 prompt_builder.py:1759-1783 的过滤逻辑,推演在 macOS 上运行 hermes 时该技能还会不会出现在索引里(提示:看 fail-open 返回什么);
          3. 用 grep -n 在 prompt_builder.py 里找到 cache_key 的组成字段(:1925 起),说出「新增一个技能」会 invalidate 哪一层缓存、为什么磁盘快照 manifest 能挡住一半开销;
          4. 画出「文件 → 索引 → volatile 注入 → skill_view 回流」四步图,每步标文件:行号。

          完成标准:能不看代码复述加载链路五步(扫描/解析过滤/快照缓存/注入/按名加载);能解释 platforms 过滤失败后技能去哪了;能说出 curator 状态机三个状态各由什么代码推进、consolidate 默认开还是关。

          6. 边界与坑

          症状 原因 处理
          技能正文永远不进提示词 设计如此:索引只含 description 命中判断靠模型,别指望「全量技能进上下文」
          明明装了 memo 却看不到 apple-notes platforms: [macos] 或 prerequisites 门控未过 查 _parse_skill_file / skill_matches_environment(skill_utils.py:353)
          改了 SKILL.md 索引没变 命中磁盘快照 manifest 快照按 mtime/size 校验(prompt_builder.py:1663),确认文件真被保存
          评审 agent 想改内置技能被拒 保护清单 bundled/hub/external/pinned/user-owned 走 hermes curator adopt <name> 收养后才可改
          索引越来越长烧 token 技能库膨胀且 curator 未跑 定期 hermes curator run,stale/archived 自动压索引
          • 边界提醒:技能匹配依赖「模型读到 description 后正确发起 skill_view」,不是确定性检索——模型漏读就是漏了(有 Err on the side of loading 兜底,但没有硬保证);frontmatter 解析全程 fail-open 保证健壮,副作用是坏 frontmatter 的技能会「隐身」而非报错,排查时要先怀疑门控而非加载器。

          7. 总结

          概念 一句话
          技能本质 文件系统声明式技能包:frontmatter 元数据 + markdown 正文,可复用上下文包(02.02)
          加载链路 扫描 skill_utils.py:1285 → 解析+平台过滤 prompt_builder.py:1759 → 双层快照缓存 :1912 → 注入 volatile 段 system_prompt.py:925
          匹配机制 无向量检索:模型自读索引(description 命中)→ skill_view(name) 按名加载全文(skills_tool.py:1086)
          生命周期 curator:确定性状态流转 active/stale/archived(skill_usage.py:53-55)+ 可选 consolidate LLM 合并 umbrella(background_review.py:501-541)
          设计取向 声明式门控、fail-open、宁滥勿缺、只破 volatile 前缀缓存

          思考题:既然技能正文不进系统提示词,「模型必须记得去调 skill_view」这个约定可靠吗?如果让你给 Hermes 加一个确定性兜底(比如任务分类器预选技能),你会把它放在 4.2 链路图的哪一步、为什么?

          参考答案

          该约定并非硬保证:模型可能漏读索引或错误判断相关性——所以索引文案用「MUST load」「Err on the side of loading」把召回偏向调到最大,并以同 task 去重防重复注入,这是「概率匹配 + 强指令补偿」的工程取舍。若要加确定性兜底,最合理的位置是 4.2 第 3 步之后:在把索引交给模型前,用规则/小模型把候选技能缩减为「高相关子集」,或对高危任务类(如文件删除)强制预载对应技能;但注意兜底必须在 volatile 段构建期完成,否则会破坏前缀缓存,而且不能引入向量库,否则就背离了「零依赖按名加载」的原始设计。
