          自我进化设计

          前四章拆的是「器官」:循环、技能、记忆、网关;本章把它们装回一个活体——闭合学习环。Hermes 是本子目录 README 定位的「六对象中唯一主打自我进化」的实现,但它从不靠模型「自觉反思」:每一处进化都有确定性触发点——计数器、阈值、状态机、预算,LLM 只出现在「写什么」的最后一步决策。收官章的目标,是让你能指着代码说清:技能从哪一刻开始学、记忆在哪个回合沉淀、画像如何变深、行为凭什么改善,以及这套闭环哪些能抄、哪些必须避。

          学习目标:学完本章,你将能够——

          1. 画出「用中学技能 → 沉淀记忆 → 画像变深 → 行为改善」闭合学习环,并为每个环节标出文件:行号;
          2. 解释 memory 与 skill 两种 nudge 为何计数不同步(memory 按用户轮、skill 按工具迭代),以及评审为何必须放在响应送达之后;
          3. 说清 curator 的双轨制——确定性状态机(默认)与 LLM umbrella 合并(consolidate 显式开启),以及后台评审 fork 如何防递归、防越权、防烧钱;
          4. 依据各对象 README(不臆测源码)横向对比 6 个实现的「进化」形态,指出 Hermes 闭环的独特点;
          5. 形成收官判断:自我进化的工程本质是「用确定性机制约束 LLM 反思」,并交出一份可抄 / 要避清单。

          1. 概念:闭合学习环 = 四个环节 + 一个钟摆

          环节 载体 关键触发点(文件:行号)

          四环节没有一个是模型主动完成的:①的计数在每轮工具迭代后自增,②的判定在回合边界检查阈值,③④的生效依赖「下次构建 prompt 时读盘」。模型只回答「这段对话里什么值得沉淀、沉淀成什么」——背景 03 章已证:这是把「何时/何地/多大」交给确定性代码、「写什么」交给 LLM 的分工。

          2. 为什么这样设计

          • 「自我进化」是模块定位签名,不是附带功能:本子目录 README 明确 Hermes 是六对象中唯一主打自我进化的实现,并把技能、记忆、画像当作运行时可变资产——能力上限不只看模型,还看循环积累。仓库自己就是活例子:skills/autonomous-ai-agents/ 分类里沉淀着 hermes-agent/codex/claude-code/opencode 等子技能(编排自主 Agent 的经验),optional-skills/dogfood/ 存对抗性自测——「用自己、改进自己」既是产品也是开发方式。
          • LLM 反思不可靠,进化节奏必须确定:模型不会记得「上上个回合该写记忆了」,计数与阈值因此落在宿主代码里;让模型自选时机 = 把 token 预算交给随机性。Hermes 的回答是双轨制(见 4.3):该不该动、动哪些、花多少钱,由状态机与计数器裁决;LLM 只做「写什么内容」这最后一跳。
          • 进化不能打扰主任务:评审 fork 一次约 3 万 token、要再跑一个完整 agent 回合,若与用户任务抢模型注意力,「学会」就成了「变慢」。所以所有后台进化都钉在响应送达之后(turn_finalizer.py:810-830 注释原话:runs AFTER the response is delivered),而 cron 这类无人在环的会话干脆整体跳过(4.5)。

          4. 详细介绍

          4.1 环节①:用中学技能——按工具迭代计数的 skill nudge

          「学」发生在用之后:模型在任务中加载技能(skill_view)、或用户纠正了它的做法,这些回合结束时最有沉淀价值。skill nudge 的钟摆是工具迭代——每完成一轮「LLM 调用 + 工具执行」自增一次(agent/conversation_loop.py:2369-2373):

          # Track tool-calling iterations for skill nudge.
# Counter resets whenever skill_manage is actually used.
if (agent._skill_nudge_interval > 0
        and "skill_manage" in agent.valid_tool_names):
    agent._iters_since_skill += 1
          python

          真正的判定在回合收尾(turn_finalizer.py:794-800):_iters_since_skill >= _skill_nudge_interval(默认 10,agent/agent_init.py:2032)即置 _should_review_skills = True 并清零。注意两个门控细节:工具集里没有 skill_manage 就不计数(评审 fork 无 skill_manage 时不会自旋);一旦模型真的用过 skill_manage 写技能,计数器在 agent/tool_executor.py:711-712 归零——「刚写过就不催」。

          4.2 环节②③:沉淀记忆与画像变深——按用户轮的 memory nudge

          memory nudge 走用户轮(回合开始处,turn_context.py:869-877):_turns_since_memory += 1,达到 _memory_nudge_interval(默认 10)置 should_review_memory;会话恢复时按历史用户轮数补齐计数(:821-825),任一 memory 写操作成功即清零(agent/tool_executor.py:710)。两种钟摆刻意不同步:memory 绑用户轮、skill 绑工具迭代——一个闲聊型回合只走 memory 钟,一个重工具回合主要走 skill 钟,避免两个评审在同一回合集中爆发。

          「画像变深」没有独立代码路径,它与记忆共用评审链:内存评审提示词把用户侧信息列第一优先级(agent/background_review.py:465-473,原文 “Has the user revealed things about themselves — their persona, desires, preferences, or personal details worth remembering?”),模型经 memory 工具选 target 落 MEMORY.md 或 USER.md——03 章双文件在闭环里合流。

          4.3 派发与执行:送达后的后台评审 fork

          满足「有最终回复、未中断、未跳过、任一评审标记」四条件即派发(agent/turn_finalizer.py:810-830):

          if (
    final_response
    and not interrupted
    and not getattr(agent, "skip_background_review", False)
    and (_should_review_memory or _should_review_skills)
):
    try:
        # _spawn_background_review clones the snapshot structurally so
        # the fork's in-place sanitizers can't reach the live transcript.
        agent._spawn_background_review(
            messages_snapshot=list(messages),
            review_memory=_should_review_memory,
            review_skills=_should_review_skills,
        )
    except Exception:
        pass  # Background review is best-effort
          python

          线程构造在 agent/background_review.py:1754 spawn_background_review_thread(按触发标记选 _MEMORY_REVIEW_PROMPT :465 / _SKILL_REVIEW_PROMPT :476 / _COMBINED_REVIEW_PROMPT :615,/refine 聚焦可追加用户指令 :1769-1773)。fork 被刻意削成最小面:工具集只开 skills、按需前置 memory(background_review.py:1539-1541),无终端、读文件只读白名单——它整份工作就是发 memory / skill_manage 两种调用。防递归在 curator.py:1976-1978,注释即设计:

          # Disable recursive nudges — the curator must never spawn its own review.
review_agent._memory_nudge_interval = 0
review_agent._skill_nudge_interval = 0
          python

          再加一道身份标记:review_agent._memory_write_origin = "background_review"(curator.py:1986)——skill_manage 的后台评审写保护(read-before-write)靠它识别「这是评审 fork 在写,不是主会话在写」。

          4.4 技能生命周期:curator 双轨制

          技能侧的长期进化由 hermes curator run 驱动,agent/curator.py:1521 run_curator_review 文档串起四步:①确定性状态迁移(纯代码,无 LLM)→ ②consolidate 开启且有 agent 创建技能时,才 fork 子 AIAgent 跑 LLM 评审 → ③写 .curator_state → ④回调 on_summary。第一轨 apply_automatic_transitions(curator.py:305)按 .usage.json(tools/skill_usage.py:84-85)里的最近真实活动时间,把技能在 active/stale/archived 三态间搬运(tools/skill_usage.py:53-55),只管理 agent 创建(created_by: agent)的技能,内置/用户自有技能另有保护;第二轨 LLM umbrella 由 consolidate 门控(curator.py:204 get_consolidate,配置默认 OFF,hermes curator run --consolidate 才开):fork 一个 max_iterations=9999 的评审 agent(curator.py:1970)跑合并评审。合并动作有两层约束:回合尾技能评审提示词给出「patch 已加载且 curator-managed 的技能 → patch 现有 umbrella → 加 references/ 支持文件 → 新建 class 级 umbrella」的优先序(background_review.py:501-513);curator 的合并轮再按「并入现有 umbrella → 新建 class 级 umbrella → 降级为 references/templates/scripts 支持文件」三种方式执行(curator.py:488-541),硬规则包括:不动 bundled/hub/external 技能、archive 是最大破坏动作、跳过 pinned 与 cron=yes 技能、禁止把 PR 号/错误串/一次性任务名写成新技能名(curator.py:446-471、:535-538)。默认 OFF 是刻意的:确定性 prune 零模型成本,LLM 合并是可选增强。

          4.5 成本闸门与无人值守:cron 的 skip_background_review

          后台评审再省也是「又一个完整 agent 回合」,注释直说约 3 万 token/事件(turn_finalizer.py:812-814)。cron 定时会话没有人在环,评审结论无人即时受益,于是 job 构造 AIAgent 时硬编码 skip_background_review=True(cron/scheduler.py:6738,注释原文:Cron has no human-in-the-loop need for skill/memory review forks(~30K tok/event))——同时 skip_memory=False(:6737),即前台记忆读写照常、后台进化分叉关掉,区分「用户要的持久化」与「agent 自发的反思」两种成本。

          4.6 行为改善的收口:网关 post-turn hooks

          进化不只在单回合:网关每回合返回后跑 _run_post_turn_hooks(gateway/run.py:24598,调用点 :20431),内部收口 /goal 续跑(:24622)与 /loop 周期完成(:24658)——长时目标把多回合串成持续改进,同一核心在 Telegram/Discord/CLI 任何触达面上都走这条钩子。至此闭环四环节全部落位:回合内学、回合尾沉淀、跨会话生效、多端长时目标持续驱动。

          4.7 横向对比:六对象的「进化」形态(仅 README 核证)

          对象 README 核证的形态 与 Hermes 闭环对照
          01 Claude Code 闭源核心 + MIT SDK;SKILL.md 为跨厂商开放标准;hooks 可编程介入授权 技能标准同源,但无后台自我评审:进化靠外部文件显式供给
          02 OpenAI Codex Rust 极简 CLI;AGENTS.md 沿路径分层拼接=「项目记忆」 记忆主体是项目文件而非 agent 自身,无画像/自动沉淀
          04 OpenCode TS 全开源;AGENTS.md 自举(dogfooding)是「AGENTS.md 即项目记忆」活样本 自举精神同 Hermes,但记忆随项目走、不随 profile 走
          05 Pi Coding Agent 最小内核四工具;skills 渐进披露不炸 prompt cache;dynamic context 可挂 RAG/长期记忆 进化留给扩展生态;Hermes 是「内置闭环」与「外置扩展」两种路线对照
          06 GitHub Copilot automations 定时/事件触发 = 无人值守编排;PR 为检查点与人工闸门 无人值守编排对应 Hermes cron,但进化检查点在外部的 PR 而非内部记忆库

          Hermes 的独特处一句话:其余对象把「记忆/进化」放在项目文件(AGENTS.md)或外部工作流(PR),Hermes 把它做成 profile 级运行时资产 + 确定性触发——换项目技能记忆仍在,无人在环自动收敛成本。

          6. 边界与坑:要避清单

          症状 原因 处理(要避)
          MEMORY.md 越写越满,每回合 prompt 越来越长 无界追加 = 记忆膨胀 抄 Hermes 的字符预算(2200)与快照冻结;超限提示 replace 合并,别让记忆无限生长
          技能库变成几百条「一次会话一条」的窄技能 无约束的自动沉淀 = 技能失控 抄 skill 评审优先序(background_review.py:501-513):先 patch 已加载技能/现有伞,新伞必须 class 级;curator 硬规则禁动 bundled/hub/pinned/cron 技能(curator.py:446-471)
          后台 fork 拿到终端与全部工具 自主写记忆/执行 = 权限失控 抄最小工具集(background_review.py:1539-1541)+ 无终端 + 只读文件白名单;后台身份要可标记(curator.py:1986)
          评审 spawn 评审,费用雪崩 递归反思 抄 nudge 置 0(curator.py:1977-1978)与 cron 跳过(:6738);后台路径 best-effort 全吞异常
          记忆文件被注入毒内容 记忆是 prompt 输入面 抄 strict 威胁扫描 → [BLOCKED:] 占位(memory_tool.py:266-300);写记忆是变更动作,参照 02.08 助教章「写默认人确认」
          写了记忆但行为没改善 冻结快照:会话内 prompt 不刷新是特性 别当 bug 改;把「生效时点」设计进产品(下会话/压缩恢复 system_prompt.py:1084),并向用户说清

          7. 总结

          概念 一句话
          闭合学习环 用中学(工具迭代计数)→ 沉淀(回合尾 nudge)→ 画像变深(共用评审链写 USER.md)→ 行为改善(下会话快照注入),四环节循环
          确定性触发 计数/阈值/状态机/预算全是宿主代码;LLM 只做「写什么」最后一跳——时机永远不交给模型
          双轨 curator 确定性 stale/archive 默认跑(零成本);LLM umbrella 合并由 consolidate 显式开启(curator.py:204)
          评审 fork 最小化 nudge 置 0 防递归、写 origin 标记、memory/skills 两工具集、无终端、快照结构克隆
          成本闸门 响应送达后才跑(不抢注意力);cron 无人在环整体跳过(省 ~30K tok/事件)
          收官判断 Hermes 的自我进化 = 把 LLM 反思装进确定性笼子;可抄的是笼子(机制),要避的是让反思裸奔

          思考题:为什么 memory nudge 按「用户轮」计数、skill nudge 按「工具迭代」计数,互换会出什么问题?如果让评审 fork 也拥有全部工具,Hermes 的闭环会从哪一环开始崩坏?

          参考答案

          memory 沉淀的是「用户是谁、偏好什么」,只在用户说话时才有新信息,按用户轮计数使闲聊与工具密集回合公平;skill 沉淀的是「任务怎么做」,只在干活(工具迭代)时才有素材,若按用户轮计数,一轮 30 次工具调用的深度任务与一句「你好」同等计权,长任务的技能评审会被严重推迟。互换后:memory 钟被工具密集回合空转拉快(每次都是同一用户的旧信息),skill 钟被纯对话拖慢(阈值永远到不了)。②fork 若有全部工具,「后台反思」就变成「后台自主行动」:能写记忆也就能跑终端、改文件、出网——一旦 fork 读到恶意内容并照做(它继承的正是要沉淀的那段对话),递归防御(curator.py:1977)只挡 nudge 不挡工具调用,越权即发生;Hermes 用「两工具集 + 无终端 + 写 origin 标记触发 read-before-write」把 fork 钉死在「只许沉淀」上——这正是 02.08 助教章「最小权限 + 变更人确认」防线在自我进化场景的转写。
