          记忆的分类与需求

          02.04 走完一圈:课程助教有了会规划的大脑(02.03),也有了能调用的手(02.04),末篇 06 章还给手划了权限边界。可它仍有一个致命缺陷——每答完一题就彻底失忆:学员上周说「我是零基础」,这周它照样术语轰炸;刚才承诺「明天给你出三道练习题」,下一轮就忘得干干净净。模型本身无状态,想让 Agent「记得」,只能靠应用把状态写到模型之外。本章是 02.05 Memory and Retrieval 的第一课,回答三个问题:Agent 的记忆分哪几类、为什么 LLM 天生没有持久记忆、动手前要过哪三问。读完你会为课程助教画出一张「记忆需求表」,并给本模块后续每一章(会话记忆、外部存储、向量检索)找到它的位置。

          学习目标:学完本章,你将能够——

          1. 说出 Agent 记忆的四种形态(工作/情景/语义/程序记忆)及各自的载体与课程助教示例;
          2. 解释「模型权重是慢知识、上下文是快记忆、都不持久」,以及外部记忆为什么必需;
          3. 用「记什么、存多久、怎么取」三问拆解任意一条记忆需求;
          4. 用「便签、笔记本、图书馆」隐喻说明记忆分层的依据——取回成本;
          5. 判断哪些任务根本不需要外部记忆,哪些必须分层设计。

          1. 概念:Agent 记忆的四种形态

          • 认知科学早就给记忆分了类(情景/语义之分出自 Tulving,程序记忆出自 Squire),工程社区把它借来设计 Agent 记忆——Anthropic 的上下文工程指南、CoALA 框架都用这套词表。先泼盆冷水:这是设计词表,不是模型的解剖结构——模型没有海马体,分类的价值是逼你回答「这条信息属于哪类、该怎么存、怎么取」。
          • 四种形态与课程助教的对应:
          形态 通俗理解 计算机里的载体 课程助教例子
          工作记忆(working memory) 正在手头处理的 上下文窗口(每轮重装) 本轮问题、刚返回的检索片段
          情景记忆(episodic) 本会话发生的事,带时间线 会话历史(消息列表) 「学员刚问过 CASCADE」「我承诺了出题」
          语义记忆(semantic) 跨会话的事实知识 外部存储:SQLite/JSON/向量库 「学员零基础、学到第 3 章、偏好文字讲解」
          程序记忆(procedural) 怎么做事的技能 system prompt + 工具定义 + 代码 出题三步流程、算分规则、查课程工具用法
          • 最容易被忽略的是程序记忆:它几乎不「像记忆」——人骑车不用回忆操作步骤,课程助教调用工具也不用每次把工具说明「回忆」一遍,技能常驻在 system prompt 与代码里(呼应 02.01 的 Agent 五要素:记忆远不止「聊天记录」一种形态)。

          2. 为什么需要:权重是慢知识,上下文是快记忆

          • LLM 只有两种「自带」的记忆,而它们都不适合当 Agent 的持久记忆:
            • 模型权重 = 慢知识:训练时固化在参数里,记录语言规律与训练语料里的事实;要更新得重新训练或微调(呼应 01.03),成本以万元和数周计——你不可能因为学员说了句「我是零基础」就去微调一次模型。
            • 上下文 = 快记忆:每轮调用前装进窗口,模型立即「看到」;但每次 API 调用彼此独立、无状态(呼应 02.01),调用结束窗口即清空。多轮对话里模型「记得」不是它记住了,而是应用把历史又原样发了一遍(呼应 02.02 的 02 章:窗口 ≠ 记忆)。
          • 三种载体摆在一起看:
          载体 读写速度 能存多久 更新成本 谁在管
          模型权重 慢 训练截止时点,几乎永久 重训/微调,极高 模型厂商
          上下文窗口 快 单次调用,结束即清 每轮重发即可 应用代码
          外部存储(要建的) 中 跨会话,想留多久留多久 一次写入、随时读取 你自己的记忆模块
          • 结论:Agent 的「记得」只能由应用实现——把值得留的状态写到模型之外(数据库/文件/向量库),需要时再读回上下文。这就是本模块要建的记忆系统;本章先定「存什么」,02~05 章解决「怎么存、怎么取」。

          3. 作用:记忆设计三问——记什么、存多久、怎么取

          • 任何一条记忆需求,动手之前先过三问:
          问 展开 决定什么
          ① 记什么 什么信息会影响后续行为?进度、背景、偏好、承诺、查过的资料 信息价值:值不值得占存储
          ② 存多久 本会话内有效,还是跨会话都要? 存储介质与清理策略(短期/长期)
          ③ 怎么取 全量回填、按 ID 精确查,还是按语义检索? 存成原文、结构化条目还是向量
          • 三问的答案把需求分流到本模块的后续章节:
          一条记忆需求
   ├─ ②答「会话内」   → 情景记忆:02 章 会话记忆与会话压缩
   ├─ ②答「跨会话」   → 语义记忆(事实):03 章 长期记忆外部存储
   ├─ ③答「语义检索」 → 语义记忆(资料):04/05 章 向量检索与 RAG
   └─ ①答「是技能」   → 程序记忆:写进 system prompt 与代码,不进数据库
          text
          • 作用小结:三问把「感觉该记住点什么」的模糊冲动,翻译成「存哪一层、用什么技术、归哪一章实现」的工程决策;01 章的产物是一张分类清楚的需求表,而不是一段代码。

          4. 详细介绍:便签、笔记本与图书馆

          • 另一个流传更广的隐喻按「容量与取回成本」把记忆分成三层:
          隐喻 对应形态 特性 课程助教落点
          便签 工作 + 情景记忆 随手写随手撕:快、容量小、易失 本轮问答与最近几轮对话
          笔记本 语义记忆(个人事实) 持久、结构化、按条目翻找 学员档案:水平、进度、偏好
          图书馆 语义记忆(资料) 海量、不查就没有、检索有成本 课程讲义与资料全文
          • 三层的关键差异是取回成本:便签内容每轮全量摊开(便宜但容量小);笔记本按学员 ID 精确取几条(便宜且够用);图书馆藏书再多也得先检索才能用,检索本身要花 token 与时间(04 章)。一句话:记忆分层 = 按取回成本分配信息。
          • 程序记忆不在三层里:技能写进代码与 system prompt,「永远带着,无需取回」。
          • 用三问给课程助教填一张需求表,它就是本模块的路线图:
          需求 记什么 存多久 怎么取 形态与实现
          跟上本会话话题 问答原文 会话内 全量回填 情景/02 章
          记住学员背景 「零基础」等事实 跨会话 按学员 ID 语义/03 章
          记住辅导进度 学到第几章 跨会话 按学员 ID 语义/03 章
          引用课程原文 讲义片段 长期海量 语义检索 top-k 语义/04~05 章
          出题与算分 流程与规则 常驻 不需要取 程序/system + 代码
          • 判断「要不要记忆」的三步测试:任务只答一次、不依赖前文 → 不需要;多轮依赖前文 → 至少便签级(02 章);跨会话跟踪学员 → 笔记本级(03 章);回答要引用海量资料 → 图书馆级(04/05 章)。注意需求会变化:学员从零基础学到进阶,「零基础」这条取值必须更新——怎么更新、怎么删除,也是记忆设计的一部分(06 章展开)。

          5. 动手活动:为课程助教写记忆需求清单

          动手活动:memory_planner.py——三问自查 + 自动分层

          目标:产出 memory-requirements.md(≥5 条真实记忆需求,每条过三问、标形态与实现章),并用脚本自查三问是否齐全、分层是否合理。

          步骤:

          1. 回放一次你与课程助教的真实(或模拟)对话,列出 5 条它「应该记住却没记住」的信息;
          2. 对每条回答三问并填入需求表(记什么/存多久/怎么取);
          3. 运行脚本核对:三问齐全、分层建议与你的判断一致;
          4. 把表整理进 memory-requirements.md,作为 02~05 章动手活动的需求来源。
          # memory_planner.py —— 记忆需求三问自查与自动分层(纯 Python 3,无第三方依赖)
def layer_of(duration):
    """按『存多久』给出分层:会话内 = 便签级,跨会话 = 笔记本级。"""
    if duration == "session":
        return "便签级(情景记忆,02 章会话记忆与会话压缩)"
    return "笔记本级(语义记忆,03 章长期记忆外部存储)"
def check_three_questions(item):
    """三问完整性检查:返回缺失字段的显示名列表,空列表即齐全。"""
    fields = {"what": "记什么", "duration": "存多久", "how": "怎么取"}
    return [fields[key] for key in fields if not item.get(key)]
def main():
    needs = [
        {"name": "学员零基础背景", "what": "学习起点", "duration": "cross_session", "how": "按学员 ID 查询"},
        {"name": "本会话问答原文", "what": "对话内容", "duration": "session", "how": "全量回填"},
        {"name": "上次辅导进度", "what": "章节位置", "duration": "cross_session", "how": "按学员 ID 查询"},
        {"name": "推荐过的资料", "what": "资料编号", "duration": "", "how": ""},
    ]
    for item in needs:
        missing = check_three_questions(item)
        if missing:
            print("「%s」三问不齐,缺:%s" % (item["name"], "、".join(missing)))
        else:
            print("「%s」三问齐全,建议 → %s" % (item["name"], layer_of(item["duration"])))
if __name__ == "__main__":
    main()
          python

          完成标准:5 条需求全部三问可答;脚本零缺项(先把「推荐过的资料」补上存多久/怎么取再跑);能指着表格说出每条需求对应 02/03/04 章中的哪一章,并指出至少一条「其实不需要记忆」的需求。

          6. 边界:什么时候不需要记忆

          • 不需要记忆的三种情况:① 一次性问答(查个函数签名,答完即止);② 外部状态即真相(课程表系统里现查,别缓存成记忆——呼应 02.04:能现取的数据不要重复存);③ 纯近因信息(「上一句说了什么」由窗口自己管,存下来反而制造过期副本)。
          • 记忆不是越多越好:每轮回填都花 token,塞满窗口还稀释注意力(呼应 02.02 的 02 章:利用率与中段稀释);图书馆内容尤其要按需检索,不许整本搬进窗口。
          • 分类不是摆设:只写「情景记忆」四个字解决不了任何问题;分类必须落到「三问有答案、载体已选定、读取时机已定」才算数(03 章讲读写时机)。
          • 程序记忆别硬塞数据库:技能与规则属于代码与 system prompt;存进语义库再检索回来,既慢又可能被检索噪声带偏。

          7. 总结

          概念 一句话
          四种形态 工作=窗口内、情景=本会话发生的事、语义=跨会话事实、程序=技能
          为什么需要外部记忆 权重是慢知识(改不动),上下文是快记忆(留不住)
          三问 记什么(价值)、存多久(介质)、怎么取(格式)
          三层隐喻 便签(会话)、笔记本(档案)、图书馆(资料)——按取回成本分层
          何时不需要 一次性任务、外部现取、近因信息——别为记忆而记忆

          思考题:学员第 1 轮说「我是零基础」,第 30 轮才问「那 ORM 呢」——这条信息该进便签、笔记本还是图书馆?如果按「记忆越多越好」把它每轮全量回填,会发生什么?

          参考答案

          该进笔记本(语义记忆/跨会话):「零基础」是稳定的个人事实,不是本会话的临时事件;取回方式是按学员 ID 精确读取,而不是靠语义检索。若每轮全量回填,30 轮后它会和新增的问答、工具结果抢窗口空间,推高 token 成本并稀释注意力(02.02 的 02 章);而它真正被用到只有提问那一刻——平时存着、需要时取,正是 03 章「读写时机」要解决的问题。
