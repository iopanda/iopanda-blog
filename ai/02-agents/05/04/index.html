          长期记忆外部存储

          02 章的会话记忆对象把「关键事实」抽进了内存 dict:本会话内随取随用,可进程一退出、dict 归零——学员周二学到第 3 章,周五回来问「上次讲到哪」,助教依然一脸茫然。问题不在压缩技术,在存储介质:值得跨会话的信息,必须写到模型与进程之外的持久介质上。本章是 02.05 的第三课,把 01 章需求表里的「笔记本级」语义记忆实现出来:先讲外部存储是什么、为什么跨会话记忆必须落盘,再定「何时写入、何时读取」的读写时机,最后动手给课程助教做一个基于 SQLite 的长期记忆模块——验收标准只有一条:进程重启后,它还认得老学员。

          学习目标:学完本章,你将能够——

          1. 说清「外部存储」的含义:记忆驻留在进程之外(磁盘/数据库),跨会话、跨重启存活;
          2. 解释为什么学员档案必须落盘,而会话摘要、滑动窗口内容不必;
          3. 按「会话开始读、关键事实出现即写、任务结束收尾写」规划读写时机;
          4. 用 Python 标准库 sqlite3 实现学员档案的创建、覆盖写入(upsert)、精确读取与删除;
          5. 对比 JSON 文件、SQLite 与向量库的适用边界,并为自己的记忆模块选型。

          1. 概念:外部存储 = 把记忆写到进程之外

          • 长期记忆(long-term memory,语义记忆):跨会话稳定的事实——学员水平、学到哪一章、欠了哪些承诺。02 章已论证它在「本会话内」靠消息重放与压缩,本章解决「会话结束之后」:让事实活在模型、会话对象、甚至进程之外。
          • 外部存储(external storage):写入磁盘的存储介质,课程助教用的是三类——JSON 文件、SQLite 数据库、向量库(04 章)。它们在 01 章的隐喻里对应「笔记本」与「图书馆」:便签随手撕,笔记本要归档。
          • 为什么「外部」这个词是关键:02 章的 ConversationMemory 也是存储,但它住在进程内存里,进程结束即清空;SQLite 把数据写进 .db 文件,文件在,记忆就在——跨会话的真相是「文件比进程活得久」。一份最朴素的档案表:
          CREATE TABLE learners (
    learner_id TEXT PRIMARY KEY,   -- 学员唯一 ID,档案的「钥匙」
    level      TEXT,               -- 水平:零基础 / 入门 / 进阶
    chapter    TEXT,               -- 学到哪一章
    notes      TEXT,               -- 备注与承诺
    updated_at TEXT                -- 最近一次更新时间
);
          sql

          2. 为什么需要:没有长期记忆的课程助教

          • 把「学员上次学到第几章」这种需求(01 章需求表第二行)放进会话记忆是存不住的:会话对象随会话结束销毁,摘要与事实通道一并清空。三种典型场景直接暴露差距:
          场景 无长期记忆的表现 有长期记忆的表现
          隔三天回来问「上次讲到哪了」 当新学员重新摸底,重复讲已会内容 开场读取档案,直接续讲第 3 章
          学员说「其实我学过 SQL」 下次会话又按零基础教 一次覆盖更新,此后按入门讲
          上周承诺「明天出三道题」 忘得干净,学员来催 开场带出待办,先补承诺再讲新课
          • 为什么不用 02 章的手段硬扛:会话记忆优化的是「窗口预算内给模型看什么」,前提是会话还在;它从不承诺「重启后还记得」。把跨会话事实塞回每轮上下文也做不到——你无法预知学员下次问什么,更不可能把一年档案天天全量重放(token 与注意力都烧不起,呼应 02.02 的 02 章)。
          • 一句话:会话记忆管「别忘事」,长期记忆管「还记得人」——后者只能靠写盘解决。

          3. 作用:读写时机与在 Agent 里的位置

          • 长期记忆模块挂在 Agent 主循环上,只做两件事,但时机很讲究:
          会话开始 → load_progress(learner_id)        ← 读取时机:开场把档案装进上下文
会话中   → 关键事实出现 → save_progress(...)   ← 写入时机:不等会话结束
任务结束 → 收尾 save(进度、承诺、结论)          ← 写入时机:结果落地
                        ↕
              SQLite 文件(进程之外,跨会话存活)
          text
          时机 触发条件 写/读什么 反面教材
          会话开始(读) 学员 ID 已知 水平、章节、待办,拼进 system 上下文 每次重新摸底,浪费一轮问答
          会话中(写) 关键事实出现:「我零基础」「学过 SQL」 同名覆盖对应字段 只在会话结束才写,中途崩了就丢
          任务结束(写) 辅导完成、承诺给出 新进度与待办收尾落盘 只写进度不写承诺,下次开场还是忘
          • 与相邻章节的分工:02 章的关键事实抽取是「挑出来」(进内存 dict),本章是「存下去」(进 SQLite)——把 02 章的 facts 通道落盘,就是长期记忆的雏形;04 章的向量库存的是「资料全文」,靠语义检索取回,而本章档案按学员 ID 精确读取,不需要检索。
          • 设计红线:单一真相源。同一份进度只允许存在一处(SQLite),别在 JSON 备份、缓存、上下文里各存一份——三份迟早不一致,排错时你分不清谁是真的(呼应 01 章「更新也是记忆设计的一部分」)。

          4. 详细介绍:选型、表结构与幂等写入

          4.1 三种存储介质怎么选

          介质 写入并发 查询 规模 课程助教用途
          JSON 文件 无(整文件覆写) 加载后内存遍历 单学员原型 演示与单机玩具
          SQLite 好(行级锁 + WAL) SQL:按 ID/条件精确查 单机百万行内 学员档案、进度(本章)
          向量库(04 章) 好 按语义相似度 top-k 海量文本 课程资料全文
          • SQLite 是本章主角:Python 标准库自带 sqlite3,零安装;整个库是一个文件,备份即复制;支持事务(ACID)与并发读;官方定位就是「嵌入式应用的文件格式」(见引用)。单进程课程助教用它绰绰有余;JSON 文件在「只有一位学员、只追加不查询」时更简单,但并发写会互相覆写,查询要靠手写遍历。
          • 表结构即档案模型:主键 learner_id 保证「一名学员一行」;updated_at 记录最近写入时刻,既是审计线索(06 章)也是「这条档案新不新」的依据。

          4.2 幂等写入与覆盖语义

          • 学员说「其实我学过 SQL」时,系统要做的不是追加一行新记录,而是把旧值覆盖掉——02 章 facts 通道的同名覆盖,在数据库里就是 INSERT ... ON CONFLICT DO UPDATE(upsert):同一 ID 重复写入永不产生重复行,最新值恒为真相。
          • 忘掉一条事实同样是一条语句:DELETE FROM learners WHERE learner_id = ?——「记忆的删除」在 06 章展开,但 schema 从一开始就要支持它,别把档案设计成只能追加的日志。
          • 用命令行可以直接验证持久化(写完动手脚本后跑):
          sqlite3 assistant_memory.db '.schema learners'
sqlite3 assistant_memory.db 'SELECT learner_id, level, chapter FROM learners;'
          bash

          5. 动手活动:课程助教长期记忆模块

          动手活动:long_term_memory.py——重启后仍记得学员进度

          目标:实现 LearnerStore(建表 / upsert 写入 / 按 ID 读取 / 删除),模拟「周二会话写入 → 进程重启 → 周五会话读取」,验证模块验收:重启后仍记得学员进度,且同名覆盖不产生重复行。

          步骤:

          1. 保存为 long_term_memory.py 并运行两次(纯 Python 3,只用标准库 sqlite3;第二次运行验证 upsert 幂等:行数仍为 1);
          2. 观察输出:第一次运行先写入再「重启」读取,档案完整回来;随后学员水平更新为「入门」,再查已是新值;
          3. 用上文的 sqlite3 命令直接查库文件,确认数据真实落在磁盘(删掉 .db 文件再跑一次,观察「失忆」);
          4. 回答:为什么第二次运行不会出现两行 xiaoming?如果把 save_progress 里的 upsert 改成裸 INSERT,第二次运行会怎样?
          5. 加一个 forget(learner_id) 删除方法,在脚本末尾调用并验证档案消失——为 06 章的「遗忘」留好接口。
          # long_term_memory.py —— 课程助教长期记忆模块:SQLite 落盘,重启后仍记得(纯 Python 3)
import sqlite3

DB_PATH = "assistant_memory.db"

class LearnerStore:
    """学员档案的跨会话存取:upsert 写入,按 learner_id 精确读取。"""

    def __init__(self, db_path=DB_PATH):
        self.conn = sqlite3.connect(db_path)
        self.conn.execute(
            "CREATE TABLE IF NOT EXISTS learners ("
            "learner_id TEXT PRIMARY KEY,"
            "level TEXT,"
            "chapter TEXT,"
            "notes TEXT,"
            "updated_at TEXT)"
        )
        self.conn.commit()

    def save_progress(self, learner_id, level, chapter, notes=""):
        """写入时机:任务结束或关键事实出现。同名学员一律覆盖,不产生重复行。"""
        self.conn.execute(
            "INSERT INTO learners(learner_id, level, chapter, notes, updated_at) "
            "VALUES(?, ?, ?, ?, datetime('now')) "
            "ON CONFLICT(learner_id) DO UPDATE SET "
            "level=excluded.level, chapter=excluded.chapter, "
            "notes=excluded.notes, updated_at=excluded.updated_at",
            (learner_id, level, chapter, notes),
        )
        self.conn.commit()

    def load_progress(self, learner_id):
        """读取时机:会话开始。查不到返回 None,助教按新学员接待。"""
        row = self.conn.execute(
            "SELECT level, chapter, notes, updated_at FROM learners "
            "WHERE learner_id = ?",
            (learner_id,),
        ).fetchone()
        if row is None:
            return None
        level, chapter, notes, updated_at = row
        return {"level": level, "chapter": chapter,
                "notes": notes, "updated_at": updated_at}

    def forget(self, learner_id):
        """删除一条档案:记忆的删除接口,06 章数据治理会用到。"""
        self.conn.execute("DELETE FROM learners WHERE learner_id = ?", (learner_id,))
        self.conn.commit()

    def count(self):
        return self.conn.execute("SELECT COUNT(*) FROM learners").fetchone()[0]

    def close(self):
        self.conn.close()

def session_tuesday():
    """周二会话:任务结束,把学员进度写入外部存储。"""
    store = LearnerStore()
    store.save_progress(
        "xiaoming", level="零基础", chapter="第 3 章 主键与外键",
        notes="已布置 3 道练习题,承诺明天检查",
    )
    print("周二会话:写入完成,当前记录数 = %d" % store.count())
    store.close()

def session_friday():
    """周五会话:新进程、新连接,开场读取档案——重启后仍记得。"""
    store = LearnerStore()
    profile = store.load_progress("xiaoming")
    if profile is None:
        print("周五会话:查无此人,按新学员接待")
    else:
        print("周五会话:欢迎回来!上次学到 %s(水平:%s),备注:%s,更新于 %s"
              % (profile["chapter"], profile["level"],
                 profile["notes"], profile["updated_at"]))
    store.save_progress(
        "xiaoming", level="入门", chapter="第 4 章 索引与事务",
        notes="练习题已批改,5 对 3",
    )
    print("水平更新为「入门」后,记录数仍为 %d(upsert 覆盖,无重复行)" % store.count())
    store.close()

if __name__ == "__main__":
    print("=== 模拟:周二会话(进程 1)===")
    session_tuesday()
    print("=== 模拟:进程重启,周五会话(进程 2)===")
    session_friday()
          python

          完成标准:两次运行输出一致——周五会话开场读回周二写入的章节与备注(重启后仍记得);水平更新后 count() 恒为 1(覆盖而非追加);用 sqlite3 命令行能查到 xiaoming 一行真实落盘;把 upsert 换成裸 INSERT 重跑两次,能看到重复行并解释为什么「只追加」的档案会自相矛盾(旧值新值并存,读到哪条取决于运气)。

          6. 边界与排错

          症状 原因 处理
          sqlite3.OperationalError: database is locked 多进程同时写同一个库文件 课程助教单写者即可;必要时 PRAGMA journal_mode=WAL; 与写入重试(见引用)
          重启后查无此人 .db 文件路径是相对的,换了工作目录;或文件被删 用绝对路径/配置项固定 DB 位置;备份即复制文件
          记录在,读出来却是旧值 代码里另有一份内存缓存,双份真相 只信 store:所有读写走 LearnerStore,删掉旁路缓存
          「学过 SQL」没生效 实现成了只追加的日志,新旧档案并存 upsert 覆盖 + 主键约束,让「最新值」成为数据库原语
          档案越存越多,含手机号等敏感信息 什么都往档案里塞 记忆最小化:只存影响后续行为的事实;PII 与删除流程见 06 章
          表结构要加一列 旧库没有新字段 迁移:ALTER TABLE learners ADD COLUMN xxx;(先备份再改)
          • 边界提醒:本章档案存的是「学员事实」,不是「课程资料」——资料要按语义取回,是 04 章向量库的活;SQLite 也能存向量(存 BLOB + 自己算相似度),但海量资料下检索性能与索引都不如专用向量库。长期记忆一旦上线,写入即承诺:任何覆盖都是「替学员做决定」,关键字段的变更记录留给审计(06 章)。

          7. 总结

          概念 一句话
          长期记忆 跨会话稳定的事实,写在模型与进程之外
          外部存储 文件比进程活得久:SQLite/JSON/向量库
          为什么需要 会话记忆随会话销毁;「还记得人」只能靠落盘
          读写时机 开场读、关键事实即写、任务结束收尾写
          幂等写入 upsert + 主键:一名学员一行,最新值恒为真相;忘掉 = 一行 DELETE
          选型 JSON 单机原型、SQLite 档案、向量库管资料(04 章)

          思考题:02 章的事实通道放在内存 dict 里,本章把它落进 SQLite——为什么「学员进度」必须落盘,而滚动摘要不必?如果只把档案存成 JSON 日志、每次追加一行,学员先说「我零基础」再说「其实我学过 SQL」,下次会话读档会发生什么?

          参考答案

          进度与承诺要跨会话、跨进程存活,还要支持「覆盖旧值」与「按 ID 精确取回」,内存 dict 随进程消亡,JSON 文件则每次整文件覆写、无法表达「同一学员的最新值」;滚动摘要只服务本会话的回顾,会话结束即作废,落盘纯属浪费。JSON 追加日志会留下互相矛盾的条目——零基础与学过 SQL 并存,读取时只能按时间取最后一条,还要自己处理「删除无法表达」的问题;SQLite 的主键 + upsert 让覆盖成为数据库原语,忘掉一条事实也只是一行 DELETE,这正是 06 章「记忆的遗忘」需要的接口。
