          边想边做还是想完再做

          同一个报错，交给两个 Agent。

          第一个先生成六步计划：读日志、定位异常栈、查依赖版本、比对配置、改配置、跑测试。写完就开始执行。第三步查依赖版本时发现，计划里假定的那个库根本没装——它读的是另一套环境。后面三步全部作废。

          第二个直接读日志，读完发现异常栈指向一个配置文件，再读那个文件，改掉，跑测试。四步结束。

          差别不在模型，在计划成型的时间点。计划在拿到观察之前写成，就要承担观察推翻它的全部风险。

          两种循环的结构

          ReAct（Yao et al., 2022, arXiv:2210.03629）把每一步拆成三件事：想一句（当前该做什么）、做一个动作（调用一个工具）、看结果（观察）。观察进入上下文，下一步的“想”基于它。循环到模型判断任务完成，或触发终止条件。

          第一章第 6 节拆过这个循环的实现，那里有一个结论值得重述：ReAct 的质量主要由观察质量决定。 工具返回一堆无关文本时，模型的“想”就是在噪音上做推理，循环越久偏得越远。

          Plan-and-Execute 把循环切成两段。规划器看一次任务，产出一份完整计划（通常是带依赖关系的步骤列表）；执行器逐步执行，每步只看到“计划项 + 必要上下文”。

          两段的成本结构差别很大。

          成本：一次与 n 次

          ReAct 每一步都要把完整轨迹重新发一遍。走到第 n 步时，输入里包含前面 n−1 步的所有想法、动作和观察。

          粗糙估一下：每步净增 2K token，第 n 步的输入约 2n K。走十步，总输入约 2×(1+2+…+10) = 110K。这就是第二章那个“四轮见底”在长任务上的放大版——成本随步数平方增长。

          Plan-and-Execute 的执行器每次只带计划项和它需要的那块材料。同样是十步、每步 2K 的产出，总输入约 10 × 4K = 40K，线性增长。规划器本身只调一次，成本固定。

          省下来的钱买的是一个风险：计划写成时没有观察。

          两种失败形状

          ReAct 的失败：漂移与重复。走到第八步时忘了原始目标，开始处理一个相邻问题；或者反复调用同一个工具，因为上一次的结果没被读懂。这两类失败在轨迹里非常显眼——步数暴涨，动作类型集中，观察内容重复。

          Plan-and-Execute 的失败：盲目执行。计划第 2 步失败了，执行器依然按计划做第 3 步，最后交出一份建立在错误前提上的完整报告。它的失败更隐蔽，因为每一步都“完成了”，最终产物看起来齐全。

          还有一个 Plan-and-Execute 特有的错：规划器不知道执行器的真实能力。计划里写“调用订座接口查询空位”，而系统里根本没有这个工具，执行器只能跳过或编造。

          选择判据

          四个问题，按顺序问。

          环境反馈密度。 每一步都要读外部状态（文件、数据库、网页、报错）才能决定下一步，选 ReAct。信息在任务开始时就已经齐了（写一份基于给定材料的报告），选 Plan-and-Execute。

          任务可预知性。 步骤能被提前列全（流程固定、依赖清晰），计划先行有价值，因为它可以被审阅、被批准。步骤依赖执行中发现的东西（调试、探索性调研），计划必然过期。

          成本敏感度。 步数超过十步、调用量大，ReAct 的平方成本会成为主要开支。

          是否需要人工审批。 计划是唯一能在执行前给人看的产物。要做审批，就得有显式计划；纯 ReAct 的轨迹没法预审。

          维度 ReAct Plan-and-Execute
          计划成型时间 每步 执行前一次
          观察的用途 直接改变下一步 只能触发重新规划
          token 成本 随步数平方增长 随步数线性增长
          失败形状 漂移、重复、忘记目标 盲目执行、计划过期
          可审计性 事后看轨迹 事前审计划
          适合 环境不确定、步数少 流程固定、步数多、需审批

          混合：骨架加局部迭代

          生产系统里纯用某一种的不多，常见的组合是三层。

          规划器出骨架：五到八个粗粒度阶段，不写具体调用。

          执行器在阶段内用 ReAct：每个阶段内部允许自由调用工具、观察、调整，因为这一段的不确定性最高。

          触发式重新规划：不是每一步都重规划，只在几个明确条件成立时重来——某个阶段连续两次失败、观察与计划假设冲突、剩余预算不足以完成剩余步骤。第 3.5 节会展开这些条件。

          这个结构的关键是计划里的每个阶段都要有验收点。没有验收点的阶段，执行器无法判断自己是否完成，重新规划也无从触发。

          名字不重要

          ReAct 与 Plan-and-Execute 是两种编排习惯，不是两个必须选边的阵营。很多框架同时提供两者，行为差别远小于名字给人的印象。

          真正决定行为的是三件事：计划写到什么粒度、观察能不能改变计划、失败之后谁负责重来。把这三件事定清楚，用什么名字都行；定不清楚，套哪个框架都会跑偏。

          下一步：出错之后

          两种结构都会失败，区别只在失败的样子。剩下真正的问题是：Agent 怎么知道自己错了，错了之后做什么。

          这是下一节的主题，也是这一章里结论最不乐观的一节。
