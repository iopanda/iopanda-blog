          计划要能被推翻

          回到开头那个助教。它查到往年考题之后，发现了教材换版这件事。

          一个只能执行计划的 Agent，此刻会做什么？继续走第五步，用旧权重排序，交出一份看起来完整的提纲。它没有任何机制能表达“计划的前提错了”。

          一个能重新规划的 Agent，需要三样东西：一条写下来的前提、一个能判断前提是否成立的检查、一条“发现不成立就停”的规则。三样都不在模型里，都在代码里。

          计划里必须写前提

          计划能被执行，也能被推翻，前提是它把自己的假设写出来了。

          “第三步：查往年考题，估计权重”——这条步骤隐含三个假设：往年考题存在、考题对应本版教材、权重能从题数推算。三个假设都没有写在计划里，所以没人会去检查它们，直到最后发现整份提纲建立在错版教材上。

          改成带前提的写法：

          {"step": 3, "action": "查往年考题并估计权重",
 "assumes": ["存在 2023 年以后的考题", "考题依据当前版教材"],
 "check": "考题中第 5 章题数 > 0 且与本章小节数匹配",
 "on_violation": "replan"}
          json

          assumes 是给人看的，也是给模型看的；check 是可执行的；on_violation 决定了发现违例之后是重试、跳过还是重规划。

          这张结构化的步骤描述，比一段自然语言计划多花不了多少 token，但它把“计划能否被推翻”从一个态度问题变成了一个可以跑的条件判断。

          三个重新规划的触发条件

          并非每次偏差都值得重规划。三个条件，任意一个成立才触发。

          假设被推翻。 观察结果与 assumes 冲突。上面那个例子属于这一类。这是最该重规划的情况，因为继续执行的每一步都在加深错误。

          同一阶段连续失败。 两次尝试都失败，且失败原因不同。原因相同说明该换参数（第 3.4 节的确定性失败），原因不同说明这条路走不通。

          预算不足以完成剩余步骤。 剩余步数乘以单步均价，超过剩余预算。这时正确做法通常是缩小范围——交一份覆盖前三个知识点的提纲，而不是交一份残缺的十节提纲——这本身是一次重规划。

          反过来，以下情况不该重规划：单次瞬时失败（重试）、某一步结果不理想但整体路径成立（继续，最后校验）、以及“觉得可能有更好的计划”（这不是理由，重规划本身有成本）。

          重规划要保住什么

          重规划时最常见的破坏，是把已经做对的部分丢掉。

          新计划必须继承三样东西：已完成的产出（已抽好的知识点清单不再重抽）、用户的原始目标（不是当前计划的剩余部分）、已经花掉的预算（新计划的预算上限要扣掉已用量，否则总成本翻倍）。

          实现上，这意味着重规划带着状态重启，而不从零开始。状态需要一个显式的结构——任务目标、已确认的事实、已完成的步骤、当前假设——而不是靠把整段历史塞进上下文。历史越长，模型越容易把已经推翻的假设继续当作事实。

          这条也解释了为什么长任务需要检查点：每次重规划都从检查点重启，检查点之外的内容一律丢掉。

          人应该站在哪

          重新规划给了 Agent 一条自我纠正的路，也给了它一条自己改需求的路。第二件事必须有闸门。

          三个位置适合放人工确认。

          不可逆动作之前。 发邮件、提交代码、删除数据、扣款。这类动作一旦执行，重规划也救不回来。

          预算耗尽时。 带着“已完成什么、卡在哪、需要多少额外预算”来问，不许静默失败。

          目标冲突时。 用户的原始要求与观察到的实际情况矛盾——比如用户要求“按 2024 年大纲出题”，而检索到的资料显示 2024 年没有这门课。这时唯一正确的动作是回到用户。

          除这三处之外，中间步骤的确认越少越好。每一步都要人批准，等于把 Agent 退化成命令行工具。

          重规划本身也会绕圈

          同一条防死循环规则适用于规划层：限制重规划次数（通常两到三次），记录每次重规划的原因。第三次重规划通常说明任务本身有问题，而不是计划有问题。

          另一个信号是计划版本之间的差异。如果 v2 与 v1 有 70% 的步骤相同，只是顺序变了，那多半是在原地打转；如果 v2 完全换了路径，那是真的重新规划。

          它挡不住的部分

          错误的目标。 重规划保证“路径可以改”，不保证“目标是对的”。用户要的东西本身不可行时，任何计划都推不出来，只能回到用户，而很多 Agent 没有这条出口。

          错误的检查。 check 写错了，前提被推翻也发现不了。上面那个例子里，如果检查写成“考题中第 5 章题数 > 0”，换版之后题数依然大于零，检查会通过。检查要比计划的前提更严格，否则它只是一个装饰。

          状态丢失。 检查点做得不好，重规划之后 Agent 会重复已经做过的工作，或者忘掉已经确认的事实。

          最后：怎么知道改好了

          到这里，规划的几种做法都过了一遍。剩下一个工程问题：这些改动是否真的让系统变好了。

          下一节讲怎么量。这里有一个需要提前说的判断：多数规划改进的收益，小到靠主观感受无法区分。
