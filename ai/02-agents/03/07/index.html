          计划的好坏怎么量

          一个团队给助教加了“自我修正”环节，演示时效果明显：出错的题被它自己改对了。上线三周后，成功率没有变化，单次对话的费用涨了四成。

          问题出在验收方式上。他们看的是演示里那几次成功修正，没有跑固定任务集，也没有统计“把对的改成错的”有多少次——而后者几乎与前者相当。

          这一章讲的所有做法都要付出成本：分解、推理链、重规划、修正。衡量它们是否值得，只能靠一套固定的口径。规划改进的收益通常小到无法靠主观感受区分，这件事必须用数字。

          六个指标

          任务成功率。 唯一的总指标。前提是“成功”有明确判据——出题任务的一条硬判据可以是“十道题全部落在章节范围内，题数与难度比例符合要求”，由代码判定，不靠人看。

          平均步数。 完成一个任务用了几轮模型调用。它同时是效率指标和健康指标：步数突然上涨通常意味着漂移或重复。

          无效步占比。 对最终结果没有贡献的步骤占比。实现上不好自动统计，常用近似：重复动作次数、失败的工具调用数、被丢弃的中间产物数。

          重规划次数。 平均值与分布。零次说明计划僵硬，频繁说明计划质量差。健康的分布集中在零到一次。

          费用与延迟。 按任务计，按 P50 与 P95 报。只看平均会掩盖长尾——一次跑了两百步的任务足以吃掉一天的预算。

          人工介入次数。 每百次任务里，人被迫接管几次。这是最能反映可用性的数字，也是最容易被漏掉的。

          指标 口径 主要用途
          成功率 代码判定，逐任务 决定是否上线
          步数 模型调用轮次 效率与漂移预警
          无效步占比 重复动作 + 失败调用 提示词与工具质量
          重规划次数 每任务计数 计划质量
          费用/延迟 P50、P95 预算与容量
          人工介入 每百任务次数 可用性

          实验怎么搭

          四条要求，缺一条结论就不可信。

          固定任务集。 三十到五十个任务，按难度分层：单步、三到五步、十步以上各占一部分。任务集要覆盖真实分布，也要专门放几个已知的困难样本——只测容易的任务，任何改动都显得有效。

          每个任务跑三次以上。 温度不为零时，同一任务的结果差异很大。跑一次就下结论，等于把一个采样当成了系统的性质。

          同模型、同参数、只改一个变量。 比较 ReAct 与 Plan-and-Execute，就不能同时换模型；比较加不加修正环节，就不能同时改提示词。控制变量听起来是常识，实际做的时候最常见的错误是“顺手优化了几处”。

          开放式任务用盲评。 成功判据无法代码化时（写提纲、改文案），让评审在不知道版本的情况下打分。否则评分者会偏好自己预期的那个版本。

          怎么读结果

          有一个固定的判读顺序，顺序错了会得出反向结论。

          先看成功率。 改动没有提高成功率，后面所有数字都不用看——更便宜的失败没有价值。

          成功率持平，再看费用。 同成功率下，费用低四成是显著收益；费用低一成，考虑到实现复杂度，通常不值得。

          再看延迟。 用户能接受的等待上限通常是十到三十秒，超过这个量级，节省的费用换不回流失。

          最后看失败形状。 成功率相同但失败更集中（都发生在同一类任务上）比均匀失败更好处理——可以针对性放弃这类任务。

          用一组示意数字说明这个顺序：

          方案 成功率 平均步数 每任务费用 (P95) 人工介入
          基线 ReAct 71% 8.4 0.42 元 9/100
          加分解 84% 9.1 0.55 元 4/100
          加分解 + 修正 83% 11.6 0.78 元 4/100

          第三行是常见结局：修正环节没有提高成功率，只是把失败的尝试也做了两遍。它的价值要到成功率不再受格式类错误拖累时才会显现，那种场景下表里不会这么写。

          预算怎么定

          三道限制都写在代码里，都从数据里取，而不是从感觉里取。

          步数上限：取成功轨迹步数的 P95，乘以 1.5。低于 P95 会砍掉正常任务，高于 1.5 倍会让失控跑很久。

          费用上限：同样按 P95 取，按任务类型分别设。出题和改文案的单任务预算不该是同一个数。

          时间上限：用户可接受的等待，通常十到三十秒；后台任务可以放到几分钟。超时不是失败，超时是“交给人工或转异步”的信号。

          预算的作用不止省钱。它是终止条件的来源：一个 Agent 必须有“什么时候停”的确定规则，否则它会一直在“再试一次”上消耗。

          它挡不住的部分

          评测集过拟合。 拿同一批任务反复调提示词，调到 90% 之后上线只有 60%，这是最常见的落差来源。留一批不参与调优的保留集，只在最终验收时跑。

          判据本身错了。 成功率 92% 但判据只看格式，等于测了一件事，上线后崩在另一件事上。判据要覆盖任务真正的价值点，这通常需要产品方参与定义。

          指标之间的交换。 提高成功率、降低成本、缩短延迟三者互相牵制。任何一次改动都要说明它牺牲了什么，只说收益的报告不可信。
