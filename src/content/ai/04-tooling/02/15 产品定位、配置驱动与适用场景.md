# 产品定位、配置驱动与适用场景

> Promptfoo README 的第一句话就很明确：它是一个 CLI and library for evaluating and red-teaming LLM apps。[1] 这句话决定了它的产品气质：Promptfoo 不是从 tracing 出发，也不是从大一统工作台出发，而是从“开发者怎样把 AI 应用测试、安全和发布门禁真正落地”出发。

**学习目标**：学完本章，你将能够——

1. 用产品经理视角定义 Promptfoo；
2. 理解为什么它更像测试/安全工具而不是 observability 平台；
3. 判断什么团队最适合先上 Promptfoo；
4. 区分它和 Langfuse、Phoenix 的第一性差异；
5. 知道什么时候 Promptfoo 是最低阻力选择。

## 1. Promptfoo 到底是什么

一句话定义：**Promptfoo 是一个面向 prompt、agent、RAG 与 LLM 应用的配置驱动测试与红队工具，用 YAML/CLI/CI 的方式把评测、安全扫描和发布门禁落地。**[1][2][3][4]

这个定义里有几个关键词：

1. **CLI and library**：它首先是开发者工具；
2. **evaluating + red-teaming**：质量和安全是双核心；
3. **configuration-driven**：很多工作通过 YAML 配置和命令行完成；
4. **CI/CD integration**：它天生适合进入仓库与流水线。[1][2][5][6]

所以从产品语言看，Promptfoo 卖的不是“一个 AI 仪表盘”，而是“把 AI 测试与安全门禁真正接进开发流程”。

## 2. 它不是什么

- 它不是 tracing 平台：它不以 traces/spans 作为第一主角；
- 它不是统一 LLMOps 工作台：不以 prompt、dataset、trace、playground 全部一体化为核心卖点；
- 它也不是只做单元测试的 Python 库：它更强调配置、矩阵对比、web viewer、red team report、CI/CD。[1][2]

## 3. 为什么这类产品会出现

Promptfoo 的根本问题意识很现实：

- 团队靠“手工问几次模型”来判断 prompt 是否可用；
- 安全检查经常是上线前临时做甚至不做；
- prompt、模型、providers 的变化没有稳定回归机制；
- PR 合并前很难知道新改动是否引入 prompt injection、PII 暴露或过度授权风险。[1][5][6]

Promptfoo 的回答是：**把这些事情写进配置、跑进命令行、挂进 CI。**

## 4. 最适合的场景

| 场景 | 为什么适合 |
|---|---|
| 团队需要把 eval 接进仓库和流水线 | CI/CD 是 Promptfoo 的主场 [1][5] |
| 团队很重视发布前安全检查 | red teaming 与 code scanning 很强 [1][6][5] |
| 团队需要快速对比 prompts / models / providers | matrix view 和 assertions 很适合 [1][2] |
| 团队不想先搭完整观测平台 | Promptfoo 更轻、更直接 |
| 团队希望本地运行测试，不把 prompts 外发 | README 明确强调 evals run locally [1] |

## 5. 不太适合的场景

| 场景 | 为什么不一定先选 |
|---|---|
| 团队首要痛点是复杂链路排障 | Phoenix / Langfuse 更适合 |
| 需要统一管理 traces、datasets、prompts、playground | Langfuse 更像现成工作台 |
| 只想要 Python 内嵌评测框架 | DeepEval 可能更直接 |
| 应用还停留在一次性 demo 阶段 | 引入完整测试/红队门禁可能偏重 |

## 6. 从 PM 视角看它的产品价值

Promptfoo 的价值可以压缩成四句话：

1. 它让 prompt/agent/RAG 质量不再靠感觉；
2. 它让安全扫描和红队测试前移到开发流程；
3. 它让模型比较变成可配置、可复现工作；
4. 它让“上线前再看一眼”变成机器化门禁。

换句话说，Promptfoo 不是为了“更优雅地试 prompt”，而是为了**让 AI 质量和安全真正具备工程纪律。**

## 7. 总结

| 关键问题 | 一句话 |
|---|---|
| Promptfoo 是什么 | 配置驱动的 LLM eval + red teaming + CI/CD 工具 [1][2] |
| 它最核心的价值 | 把测试与安全门禁接进开发流程 |
| 最适合谁 | 工程团队、平台团队、重发布门禁的团队 |
| 不太适合谁 | 首要问题是 tracing/排障或只要轻量 demo 的团队 |

**思考题**：为什么 Promptfoo 的第一价值常常不是“帮你找最好模型”，而是“帮你阻止糟糕改动进入生产”？

> [!note] 参考答案
> 因为很多团队在真实环境里首先输的不是“没选到最强模型”，而是没有稳定的回归和安全门禁。Promptfoo 最直接的价值，是把质量与风险控制从事后补锅前移到发布前。
