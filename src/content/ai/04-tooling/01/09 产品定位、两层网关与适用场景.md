# 产品定位、两层网关与适用场景

> Envoy AI Gateway 最值得先理解的，不是它支持多少 provider，而是它用什么世界观来理解 AI 接入。官方 README 一上来就写得很直白：这是一个“using Envoy Gateway to handle request traffic from application clients to Generative AI services”的开源项目，并明确提出 two-tier gateway pattern：Tier One Gateway 负责集中入口、认证、顶层路由和全局限流；Tier Two Gateway 负责进入自托管模型服务集群时的细粒度控制。[1]

**学习目标**：学完本章，你将能够——

1. 用产品经理语言定义 Envoy AI Gateway；
2. 理解什么叫两层网关模式，以及它为什么服务于大组织；
3. 区分它和 LiteLLM 这种 AI-native 接入层的根本差异；
4. 识别它最适合的组织条件和应用场景；
5. 判断什么时候上 Envoy AI Gateway 是“平台升级”，什么时候只是“过度设计”。

## 1. Envoy AI Gateway 到底是什么

一句话定义：**Envoy AI Gateway 是一个建立在 Envoy Gateway 之上的 GenAI 流量入口层，目标是把模型访问、策略、限流、安全和自托管推理入口，纳入统一的云原生网关治理体系。**[1][2]

这句话里有三层重点：

1. 它首先是 gateway，而不是 SDK；
2. 它建立在 Envoy / Kubernetes / Gateway API 这些平台能力之上；
3. 它关心的不只是访问 SaaS 模型，也关心如何进入 self-hosted model serving cluster。[1][2]

所以它的起点非常“平台工程”：不是让单个开发团队更方便，而是让组织里所有 AI 流量更统一、更安全、更可控。

## 2. 两层网关模式：为什么这是它最有辨识度的设计

README 明确把 Envoy AI Gateway 的 usage 描述为 two-tier gateway pattern。[1]

- **Tier One Gateway**：集中入口，负责 authentication、top-level routing、global rate limiting；
- **Tier Two Gateway**：负责进入自托管模型服务集群时的细粒度控制，并支持 endpoint picker 以配合推理优化。[1]

从产品经理角度看，这套设计回答的是一个大型组织真实存在的问题：

- 第一层管组织级入口、权限和全局策略；
- 第二层管模型服务集群内部的细节、模型池和性能优化；
- 这样既不会把所有复杂度都压在入口，也不会让模型集群直接暴露给业务侧。

这和“单层代理 + 多 provider key”的思路完全不同。它更像一套可治理的 AI 流量基础设施分层，而不是接模型的便捷层。

## 3. 它服务的是谁

官方 Overview 页把项目目标写得非常企业化：统一路由和管理 LLM/AI traffic、自动 failover、端到端安全、usage limiting、observability、以及建立在 battle-tested Envoy Proxy 之上的可靠基础。[2]

这意味着它最自然服务的是这类组织：

- 已经在 Kubernetes 上跑业务；
- 已有 Envoy Gateway / Gateway API / 平台工程能力；
- 不只接外部 provider，也可能有自托管模型服务；
- 对认证、策略、限流、安全、可观测有统一治理要求。

换句话说，它首先面向的是**平台团队、基础设施团队、企业 AI 平台团队**，而不只是某个单一 AI 应用小组。

## 4. 核心价值：不是“多模型支持”，而是“平台一致性”

很多人看 AI Gateway 会先问：“支持哪些 provider？” Envoy AI Gateway 当然支持很多 provider，但这并不是它最核心的差异化卖点。[1]

它更重要的产品价值在于：

- 把 AI 流量纳入已有云原生治理模型；
- 让认证、限流、安全、资源编排进入标准化路径；
- 用控制面 + 数据面的方式管理 AI 流量；
- 兼容外部 provider 与自托管模型两类入口。[1][2]

如果用一句更产品化的话说：**Envoy AI Gateway 卖的不是“接得上模型”，而是“AI 流量不必成为组织里的例外流量”。**

## 5. 最适合的场景

| 场景 | 为什么适合 |
|---|---|
| 企业统一 AI 入口 | Tier One 适合承接统一认证、全局路由与限流 [1] |
| 自托管模型集群 + 外部 provider 混用 | Tier Two + self-hosted model serving 是官方主线之一 [1][2] |
| 已采用 Envoy / Envoy Gateway / Gateway API | 接入组织现有平台能力更顺 [1][2] |
| 需要策略治理和平台标准化 | CRD、控制面、数据面模型更适合大团队协作 [2][3] |
| 需要把 AI 接入与一般 API 治理合流 | 它本质上仍是 gateway 路线，而不是纯 AI SDK 路线 |

## 6. 不太适合的场景

| 场景 | 为什么不一定先选 |
|---|---|
| 单应用、单 provider 的早期项目 | 平台门槛过高，收益未必覆盖运维成本 |
| 没有 Kubernetes / Envoy 能力的团队 | 学习和上线门槛明显高于 LiteLLM 这类产品 |
| 主要目标是快速比较不同 SaaS provider | LiteLLM 往往更直接 |
| 主要目标是本地推理运行 | 更像 LocalAI / vLLM / Ollama 的问题 |

## 7. 和 LiteLLM 的第一眼差异

如果把 LiteLLM 和 Envoy AI Gateway 放在一起看，最关键差别不是功能列表，而是“默认服务对象”不同：

- LiteLLM 默认服务 AI 应用团队，要尽快统一模型接入；
- Envoy AI Gateway 默认服务平台团队，要把 AI 流量放回组织基础设施语境里。

所以，选择 Envoy AI Gateway 的团队通常不是在问“怎样最快接十家模型”，而是在问：

- AI 流量怎么纳入现有平台入口；
- 自托管模型集群怎么治理；
- 认证、限流、观察、策略怎么统一。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| Envoy AI Gateway 是什么 | 建立在 Envoy Gateway 上的 GenAI 流量治理入口 [1][2] |
| 它最独特的设计是什么 | 两层网关模式：组织级入口 + 自托管模型细粒度入口 [1] |
| 最适合谁 | 已有 Kubernetes / Envoy / 平台工程能力的组织 |
| 不适合谁 | 只想快速做多模型接入的小团队 |

**思考题**：为什么“两层网关”对大组织是价值，对小团队却可能是负担？

> [!note] 参考答案
> 因为大组织本来就有分层治理、权限、平台边界和多团队协作需求；两层网关能把复杂度放到恰当位置。小团队则往往只有一个应用和很少的上游，分层反而会把本来不存在的问题提前工程化。
