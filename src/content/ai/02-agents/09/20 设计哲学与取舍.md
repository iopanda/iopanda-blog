# 设计哲学与取舍

> 03 章看到扩展系统是内核「不建功能」的出口;本章对账这份哲学本身:作者把 Claude Code 形容为「80% 功能用不上的飞船」,于是 Pi 维护一份「不需要就不建」清单——不内置 MCP、子代理、plan mode、权限弹窗、后台 bash。但「不建」不是摆烂:信任模型(无内置权限=进程全权)、供应链硬化(精确锁版+install-scripts 白名单)与 AGENTS.md 开发纪律一起,构成了这份哲学在安全侧的完整代价。本章全部论断都有源码或作者博客(2025-11-30)出处,方便你逐条核证。

**学习目标**:学完本章,你将能够——

1. 逐条复述「不需要就不建」清单(六项),并为每项说出官方替代路径与出处;
2. 解释「无内置权限系统 = 进程全权」的信任模型,说明 project_trust 事件与默认四工具在其中的作用;
3. 说出供应链硬化的五件套(精确锁版/overrides、shrinkwrap、install-scripts 白名单、--ignore-scripts、npm audit CI)各自的代码位置;
4. 复述 AGENTS.md 的两条开发哲学(不保向后兼容、erasable TypeScript)与「示例即契约」的含义;
5. 完成一张「Pi 的答案 vs 其他 Agent 的答案 vs 我的判断」取舍对照表,并就至少两项给出自己的立场。

## 1. 概念:一份带替代路径的「不内置清单」

- Pi 的自我定位极短:docs/index.md:3「Pi is a minimal terminal coding harness. It is designed to stay small at the core」——「小」不是目标本身,而是手段;手段的产物是一份明确的否定清单。作者在博客里逐条声明「pi does not and will not support…」,说明这些**不是还没做,而是决定不做**。
- 默认给模型的工具面小到只有四个——agent-session.ts:2800-2802:

```ts
const defaultActiveToolNames = this._baseToolsOverride
    ? Object.keys(this._baseToolsOverride)
    : ["read", "bash", "edit", "write"];
```

- 不内置的功能与官方替代路径构成一张对照表(博客出处见引用;仓库出处已核证):

| 不内置项 | 替代路径 | 出处 |
|---|---|---|
| MCP | 带 README 的 CLI 工具,按需渐进披露 | 博客 No MCP support |
| 子代理 | 让 Pi 用 bash 自举 `pi --print`,或 tmux 会话 | 博客 No sub-agents |
| plan mode | 写 PLAN.md 文件 + `pi --tools read,grep,find,ls` | 博客 No plan mode |
| 权限弹窗 | 容器化(三种官方模式)+ permission-gate 扩展示例 | README.md:42-46 |
| 后台 bash | tmux | 博客 No background bash |
| 内置 to-do | TODO.md 文件,或 examples 的 todo.ts 扩展 | 博客 No built-in to-dos、docs/extensions.md:2948 |

- 六项可按被否定的成本归类:to-do/plan/后台进程是**状态与进程管理**——作者观点是这些活该由文件系统、终端与 OS 干,LLM harness 只负责「调用」,不负责「保管状态」(02 章讲过的会话压缩已是内核唯一破例);MCP 是**工具集成税**(协议复杂度 + 每会话 token 开销);子代理与 plan mode 的隐藏成本则是**可观测性缺失**(作者反复用「zero visibility」批评黑盒)。

## 2. 为什么:一个「simple boy」的反飞船宣言

- 一手材料在作者博客(2025-11-30「What I learned building an opinionated and minimal coding agent」):他自述长期用 Claude Code,直到「Claude Code has turned into a spaceship with 80% of functionality I have no use for」——而且系统提示与工具定义随每次发布变动,直接破坏他的工作流。Pi 是他的反例:系统提示加全部工具定义合计「below 1000 tokens」。
- 两条理由主线贯穿全文。其一是**复杂度是负债**:每个内置功能都要维护、测试、写文档,80% 用户用不上等于纯负债;砍掉它,内核才能保持「一个人能通读」(01 章的 monorepo 十包格局正是这样活下来的)。其二是**可观测性优先**:作者反复用「zero visibility」批评黑盒子——plan mode 里编排实例派出的子代理不可见、后台 bash 的进程状态不可查;而 TODO.md、PLAN.md、tmux 会话全都在磁盘与终端里,「I get full observability of everything」。
- 与 02.01 骨架的呼应:能跑通 ReAct 的最小集合就是四工具(read/bash/edit/write 覆盖观察与行动),多出来的都是「增强」而非「必需」——所以 Pi 把增强全部赶到 03 章的扩展系统里,由用户按需拼装。

## 3. 作用:清单画在「默认四工具」这条线上

```text
                    用户 / 容器边界(README.md:42-46 三种官方模式)
   ┌────────────────────────────────────────────────────────────┐
   │  Pi 进程(以启动用户全权运行,README.md:40)                     │
   │   默认四工具 read/bash/edit/write(agent-session.ts:2800)     │
   │   └─ 扩展系统:一切不内置功能的挂载点(03 章)                  │
   │       权限弹窗→permission-gate 示例    plan→plan-mode 示例   │
   │       子代理→bash 自举                 后台任务→tmux 会话     │
   └────────────────────────────────────────────────────────────┘
   TODO.md / PLAN.md(磁盘上的外部状态,跨会话可见、可版本化)
```

- 读图方式:内核只做「能力面」(默认四工具 + 事件),**不做「判断面」**(要不要批准、要不要规划、要不要后台)——判断留给用户、文件协议与容器;扩展系统是两者之间的插座。这样「不内置」就有了统一的作用位置:一切被否定的功能都改道到 03 章那四层载体上重生。

## 4. 详细介绍

### 4.1 清单逐条评:省了什么,把成本转嫁给了谁

| 不内置项 | 作者的理由(博客原文要点) | 替代路径与出处 | 省下的复杂度 → 转嫁给 |
|---|---|---|---|
| MCP | 「MCP servers are overkill…significant context overhead」;Playwright MCP 21 个工具 13.7k tokens、Chrome DevTools MCP 26 个工具 18k tokens,会话没开始就烧掉 7~9% 上下文 | 带 README 的 CLI 工具 + bash 调用,用时才读 README(渐进披露);非要 MCP 可用 mcporter 包成 CLI | 省:协议客户端、server 生命周期管理 → 转嫁:用户自己写/找 CLI 工具 |
| 子代理 | 编排实例派出的子代理是「a black box within a black box」,上下文交接不可控、出错难调试 | bash 自举:让 Pi 用 `pi --print` 派自己,tmux 里跑则全程可见可交互 | 省:子代理调度、上下文转移协议 → 转嫁:用户自己规划「先建上下文工件,再开新会话」(02 章会话树正好支撑) |
| plan mode | 规划需要可观测性:「I need observability for planning and I don't get that with Claude Code's plan mode」 | PLAN.md 文件(跨会话、可版本化、可人机协作编辑);只读探索用 `pi --tools read,grep,find,ls`;想要开关式 plan 也有 plan-mode/index.ts:22-24 扩展示例 | 省:只读模式、工具集切换的 UI 状态机 → 转嫁:文件纪律(自己维护 PLAN.md 不过期) |
| 权限弹窗 | 「pi runs in full YOLO mode…No permission prompts」;「security theater」——能读写文件又能跑代码的 Agent 拦不住数据外泄 | 容器:Gondolin 扩展(微 VM 路由工具)/Plain Docker/OpenShell(README.md:42-46);要「人确认」体验装 permission-gate.ts:10-34 示例 | 省:审批 UI、命令预检(作者点名 Claude Code 的 Haiku 预检)、审计状态机 → 转嫁:边界责任全部移交给用户选的外部容器 |
| 后台 bash | 进程管理要「process tracking、output buffering、cleanup on exit」;Claude Code 后台 bash 可观测性差,压缩后 Agent 会忘掉后台进程 | tmux:dev server、REPL、调试会话都挂 tmux,`tmux ls` 可查,人还能跳进去共调 | 省:进程表、输出缓冲、退出清理 → 转嫁:用户/模型学会 tmux 这一外部技能 |
| 内置 to-do | 「to-do lists generally confuse models more than they help」——多一份要模型自己跟踪的状态,多一处出错机会 | TODO.md 复选框文件,或 todo.ts 状态化工具扩展(docs/extensions.md:2948「Stateful tool with persistence」) | 省:状态同步、完成度推理 → 转嫁:状态以文件形式显式存在,模型每次现读 |

### 4.2 信任与安全模型:进程全权 + 事件,而不是权限系统

- 起点是一句直白的免责:README.md:40「Pi does not include a built-in permission system for restricting filesystem, process, network, or credential access. By default, it runs with the permissions of the user and process that launched it.」——**无内置权限 = 进程全权**,这句话把 02.04/06 的最小权限四件套(白名单/参数范围/人确认/审计)整体请出了内核。
- 信任边界书面化在 SECURITY.md:11-17:本地用户账户与 Pi 同信任域,「If an attacker can modify files under the user's home directory…they can generally influence Pi」——这类前置写权限不算漏洞;SECURITY.md:56 把 prompt injection 明确列入 Out Of Scope,理由是 AGENTS.md、注释、网页内容都能注入,「this cannot be protected against」。
- 内核里仅存的护栏是**事件而非策略**:① 项目信任决策点 project_trust——project-trust.ts:57 发射 `{ type: "project_trust", cwd }` 事件,先于项目资源加载,只有 user/global/CLI 扩展参与裁决(docs/extensions.md:280、:355),项目本地 `.pi/extensions` 在被信任前不加载(:113);② docs/security.md:7 强调信任「is not a sandbox」,只控制**项目资源**加载,不限制模型后续调工具;③ 默认四工具面(agent-session.ts:2800-2802)是唯一的内置最小权限。
- 对照 01.07/03 的注入链:注入 × 工具权限 = 越权,传统答案是代码闸门(02.04/06);Pi 的答案是承认「read data + execute code + network access」三件套无法在 harness 内同时约束(博客原话),于是把边界**外移**到容器、把「人确认」**下沉**为扩展示例(permission-gate)。代价很真实:没有默认护栏,新手在一个不可信仓库里跑 Pi 可能直接踩雷——所以信任决策(docs/security.md:18 默认 `"ask"`)与容器文档成了安全教育的全部载体。

### 4.3 供应链硬化:功能上 YOLO,依赖上保守

- **直接依赖精确锁版 + overrides**:coding-agent/package.json:46-67 几乎全部钉死小版本(`"undici": "8.9.0"`、`"chalk": "5.6.2"`),:68-74 再用 overrides 强制 `protobufjs 7.6.5`、`rimraf 6.1.2`;AGENTS.md:44「Direct external deps stay pinned to exact versions. Treat npm dep and lockfile changes as reviewed code.」——锁文件变更被视为代码评审对象。
- **shrinkwrap + install-scripts 白名单**:发布物带 `packages/coding-agent/npm-shrinkwrap.json`(package.json:33 files 字段);专用生成脚本 scripts/generate-coding-agent-shrinkwrap.mjs:13-16 维护一份显式白名单,每个带安装脚本的包必须登记并写明理由:

```js
const allowedInstallScriptPackages = new Map([
    ["@google/genai@1.52.0", "preinstall is a no-op in the published package"],
    ["protobufjs@7.6.5", "postinstall only warns about protobufjs version scheme mismatches"],
]);
```

- 校验逻辑双向收紧:任何带 install scripts 的包不在白名单即报错(:241-254「Review it and add it to allowedInstallScriptPackages if intentional」);白名单里已不存在的包也会报错要求移除(:257-261)。安装脚本是供应链投毒的头号入口,这份白名单等于把「每个脚本都被人审过」写进了构建。
- **全局 --ignore-scripts**:README.md:55「npm install --ignore-scripts」;AGENTS.md:46「Don't run lifecycle scripts unless the user asks」;CI 全链路 npm-audit.yml:25 也是 `npm ci --ignore-scripts --no-audit --no-fund`——正常开发根本不执行任何包的安装脚本。
- **npm audit CI 每日定时**:.github/workflows/npm-audit.yml:5 cron `'37 7 * * *'` 每天跑;:28 `npm audit --omit=dev --audit-level=moderate` 查生产依赖漏洞;:31 `npm audit signatures --omit=dev` 校验注册表签名;连 actions 都钉 SHA(:16 注释 `# v7.0.1`)。
- **锁文件变更门禁**:AGENTS.md:49「Pre-commit blocks lockfile commits unless `PI_ALLOW_LOCKFILE_CHANGE=1`」;shrinkwrap 再生成只走专用脚本(:48)。组合拳的逻辑:运行时权限哲学上「全给」,但**依赖进入的每一道门都上锁**——因为对本地 Agent 而言,恶意依赖与恶意仓库是仅剩的两条未授权代码入口。

### 4.4 AGENTS.md 开发哲学与「示例即契约」

- 仓库给人与 Agent 共用的开发规则 AGENTS.md 是哲学的执行细则,两条最锋利:AGENTS.md:25「Do not preserve backward compatibility unless the user asks for it.」——版本语义配套 AGENTS.md:129「minor = breaking changes」,小版本号里可以放心破坏;AGENTS.md:23「Use only erasable TypeScript syntax (Node strip-only mode)…no parameter properties, `enum`, `namespace`/`module`, `import =`」——只写 Node 能直接剥离类型的语法,不引入任何需要编译期发射的构造,把「零构建」的可能性焊死在代码风格里。
- **示例即契约**:examples/extensions/ 下共 85 个 .ts(含 9 个自带目录的复杂示例),它们不只是文档——tsconfig.examples.json:14 把 `examples/**/*.ts` 纳入编译,AGENTS.md:23 明确 examples 属于 root config 检查范围,即 **85 个示例全部被 tsgo 类型检查**:API 一改,示例先红。功能不成熟就进不了核心,先在示例层活下来被真实使用验证(03 章的 plan-mode、sandbox、subagent 全是这条路)。
- 这条纪律的闭环:不保向后兼容给内核「减负自由」,示例即契约给 API「回归刹车」——一个敢天天破坏、一个保证破坏能被立即看见,两者缺一不可。

## 5. 动手活动:取舍对照表

> [!example] 动手活动:六项取舍对照表(Pi 的答案 vs 其他 Agent 的答案 vs 我的判断)
>
> **目标**:对「不需要就不建」清单逐项做三方对照,形成你自己的取舍判断,而不是照抄作者结论。
>
> **步骤**:
> 1. 复制 4.1 的表,加两列:「其他 Agent 的答案」「我的判断」。其他 Agent 一列只填本模块各 README 已核证的定位级事实——Claude Code(01 README)内置 plan mode、子代理与审批弹窗;Codex(02 README)走 Rust 极简 CLI + 审批/sandbox 模式;Hermes(03 README)把权限与记忆/技能做成运行时资产;OpenCode(04 README)以 TS 插件生态承接扩展。不追任何外部源码细节;
> 2. 对每项写一行「Pi 省了什么 / 把成本转嫁给了谁」(可抄 4.1 末列再自己补一句);
> 3. 任选两项,写下你的立场:完全同意、部分同意还是反对,理由必须落在「代价」上(例:无内置权限弹窗对个人开发者爽,但对团队默认共享工作站的场景意味着什么?);
> 4. 笔记输出:六行对照表 + 两段立场 + 一段总结「Pi 的哲学里,哪一条是你最想抄走的、哪一条你绝不敢抄」。
>
> **完成标准**:六项每一行的替代路径都能报出出处(仓库文件:行号或博客小节名);「我的判断」列至少两项非空且给出代价分析;能一句话回答「Pi 为什么把权限策略做成扩展示例而不是内置功能」。

## 6. 边界与坑

| 现象/坑 | 原因 | 处理 |
|---|---|---|
| 以为 system prompt 能当安全边界 | Pi 无内置权限,提示词对注入无免疫力(SECURITY.md:56 明确 Out Of Scope) | 边界只能来自容器(README.md:42-46);不可信仓库先用 Docker/Gondolin |
| project_trust 点了信任就万事大吉 | 信任只放行项目资源加载,「is not a sandbox」(docs/security.md:7) | 信任 ≠ 授权模型随便跑;危险操作仍要容器或 permission-gate 示例 |
| 供应链硬化被误读为「依赖随便加」 | 硬化管的是依赖**来源与脚本**,扩展代码本身仍全权(docs/extensions.md:111) | 只装可信扩展;带 install 脚本的新依赖必须走白名单评审流程 |
| 升级 Pi 后自己的扩展/技能坏了 | 作者明确不保向后兼容(AGENTS.md:25),minor 即可破坏 | 把扩展当独立代码维护,锁 Pi 版本或跟 changelog |
| 以为「不内置 to-do/plan」= 模型不需要规划 | 规划能力仍在,只是状态载体换成文件 | 自己维护 PLAN.md/TODO.md 的版本化与更新纪律 |
| 讲义行号与本地快照对不上 | 2026-09 检出快照,仓库每日在变 | 用 grep/search 按方法名重定位,方法比行号可靠 |

**思考题**:① Pi 说权限弹窗是「security theater」,02.04/06 却说「闸门必须在代码里、执行前」——两种立场各自在什么前提假设下成立,冲突点在哪?②「功能上 YOLO、依赖上保守」矛盾吗?③ 如果你有权给清单加第七个「不内置」项,你选什么,替代路径是什么?

> [!note] 参考答案
> ① 02.04/06 的闸门假设「代码边界能被可靠执行」(服务端多租户、可审计、有强身份);Pi 的论点针对**本地单用户 harness**:模型已能读写文件+执行命令+联网,「读隐私→外发」无法被弹窗阻断,弹窗只增加打断成本——所以把边界外移到容器。冲突点在于「人确认」对不可逆动作(rm -rf、git push)是否仍有价值:Pi 的回答是交给 permission-gate 这类可选扩展,而不是默认内置。② 不矛盾,是同一信任模型的两面:运行时对「用户指令」全权放行(YOLO),是因为攻击面主要不在用户自己的指令,而在**未经评审的第三方代码**——依赖、锁文件、扩展脚本;供应链是唯一能「静默注入可执行代码」的入口,所以那里每一道门都上锁。③ 开放题,示例答案:内置终端复用/分屏——替代路径是 tmux(把进程可见性交给 OS 层),理由同后台 bash:状态管理不属于 LLM harness;或内置网页搜索——替代路径是 `curl` + 带 README 的 CLI 工具,理由同 MCP 的 token 开销论。
