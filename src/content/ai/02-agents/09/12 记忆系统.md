# 记忆系统

> 模型是无状态的,跨会话的「记得」全靠外部载体——02 章看完技能(怎么做事),本章看记忆(记住你是谁、说过什么、偏好什么)。Hermes 的记忆不追求「像人一样记住一切」,而是把「取回成本」分三层:会话全量进 SQLite 可检索、长期笔记与画像压成两个有界小文件常驻 prompt、写入靠回合尾的 nudge 后台沉淀。最反直觉的一处设计是:记忆写入后**当前会话的 prompt 不会变**——那是前缀缓存换来的稳定性,也是本章要读懂的第一行代码。

**学习目标**:学完本章,你将能够——

1. 说出 Hermes 三层记忆各自的载体、容量与读写工具,并对照 02.05/01 的四种形态说明取舍;
2. 解释 MemoryStore 的「双状态」设计——为何冻结快照进 prompt、活状态只进工具结果,前缀缓存如何受益;
3. 画出会话检索的 FTS5 三索引路由(fts5 / fts_cjk / trigram / like_scan),并说明 CJK 二元组扩展解决了什么问题;
4. 在代码中指认 nudge 触发点(memory 按用户轮、skill 按工具迭代,默认 10)与后台评审派发路径;
5. 建立「记忆该存什么、不该存什么」的工程判断,为 05 章自我进化闭环铺路。

## 1. 概念:三层记忆 = 一个运行时库 + 两个有界文件

| 层 | 载体 | 内容 | 对应 02.05 形态 | 取回方式 |
|---|---|---|---|---|
| 会话记忆 | SQLite SessionDB(hermes_state.py,messages 表) | 全部消息与工具调用,含 FTS5 全文索引 | 工作记忆 + 情景记忆 | 当前回合直接进上下文;历史按需全文检索 |
| 长期记忆 | `~/.hermes/memories/MEMORY.md`(默认 2200 字符) | Agent 给自己的笔记:事实、偏好、跨会话承诺 | 语义记忆 | memory 工具读写;冻结快照常驻 prompt |
| 用户画像 | 同目录 `USER.md`(默认 1375 字符) | who the user is:身份、习惯、沟通风格 | 用户模型 | 同上(target="user") |

- 载体路径由 `get_memory_dir()` 返回 `get_hermes_home() / "memories"`(tools/memory_tool.py:64-66),profile 切换(HERMES_HOME)即换一套记忆;
- 条目以 `ENTRY_DELIMITER = "\n§\n"` 分隔(tools/memory_tool.py:78),动作 add / replace / remove,支持批量 operations;
- 技能(02 章)是「程序记忆」的另一载体——它不进记忆文件,走 skills/ 目录与 curator 状态机。三层都服务于 02.05/01 的判断:分层依据是**取回成本**——会话历史量大,只按需检索(图书馆);笔记与画像小而常驻,每回合都带着(便签/笔记本)。

## 2. 为什么这样设计

- **无状态模型的必然**:跨会话只能靠外部持久化。三层的差异不在「存不存」,而在「取回成本」:全量历史塞进 prompt 会撑爆上下文(01 章压缩机制兜底),所以历史留库、按查询取;常驻内容必须小,所以长期记忆做**字符预算**而非无限追加——2200 字符约等于一屏,超限时工具返回 usage 并要求模型合并重试。
- **prompt 必须稳定**:常驻注入的内容每回合都要重复出现,若随写随变,前缀缓存(01 章三层 system prompt 设计)每回合失效一次。于是 MemoryStore 载入时生成**冻结快照**,会话内写操作只改活状态与磁盘,不改快照——稳定性换缓存命中率。
- **检索用 FTS5 关键词而非向量**:会话检索的本质是「记得说过什么」的字面子串召回——要的是精确、可审计、零模型成本;语义相近的模糊召回留给 02.05/04 的向量记忆,由外部 provider(Honcho 等)承担,不进内置主路径。

## 4. 详细介绍

### 4.1 MemoryStore:双文件 + 双状态 + 威胁扫描

MemoryStore 每 AIAgent 一个(tools/memory_tool.py:159),维护两套并行状态(tools/memory_tool.py:160-168 类注释):`_system_prompt_snapshot` 载入时冻结、永不中途变更;`memory_entries / user_entries` 是活状态,随工具调用改并落盘。默认容量 `memory_char_limit: int = 2200, user_char_limit: int = 1375`(tools/memory_tool.py:178-179)。

`load_from_disk()`(tools/memory_tool.py:227)读两个文件后立即做三件事:去重、**strict 级威胁扫描**、生成快照。扫描命中(中毒记忆文件、供应链投毒、姊妹会话写入)不静默丢弃——快照里替换为 `[BLOCKED: …]` 占位,原文留在活列表供用户查看删除(tools/memory_tool.py:266-300,`_sanitize_entries_for_snapshot` 以 `scan_for_threats(entry, scope="strict")` 判定):记忆进的是 system prompt,注入防线在这里与 01 章安全基线汇合。超限合并失败有单回合 3 次熔断(`_MAX_CONSOLIDATION_FAILURES_PER_TURN = 3`,tools/memory_tool.py:174),防脆弱 replace/add 把回合拖到预算耗尽。

注入侧的函数把设计意图写在 docstring 里(tools/memory_tool.py:706-717):

```python
def format_for_system_prompt(self, target: str) -> Optional[str]:
    """
    Return the frozen snapshot for system prompt injection.

    This returns the state captured at load_from_disk() time, NOT the live
    state. Mid-session writes do not affect this. This keeps the system
    prompt stable across all turns, preserving the prefix cache.
    """
```

快照经 `_render_block()`(tools/memory_tool.py:755)渲染为 `MEMORY (your personal notes) [n%]` 与 `USER PROFILE (who the user is)` 两段(块头常量 tools/memory_tool.py:73-76),带用量百分比提示模型「快满了」。

### 4.2 注入位置与重载时机

两块都进 system prompt 的 volatile 段,且排在技能索引之后(agent/system_prompt.py:928-937:`mem_block`、`user_block` 依次 `volatile_parts.append(...)`,技能在前 :926)——记忆变更只破 volatile 段缓存,stable 段(角色/规则)与技能快照不受影响。压缩或会话恢复时重载快照——`if agent._memory_store: agent._memory_store.load_from_disk()`(agent/system_prompt.py:1084-1085),所以「写后立即生效」只发生在下一回合的恢复路径,常规回合内新记忆通过工具结果回流给模型,而不是改 prompt。

### 4.3 外部 provider:一次一个的插件口

内置双文件只是默认实现;`class MemoryProvider(ABC)`(agent/memory_provider.py:110)定义插件契约,实现放 `plugins/memory/<name>`,一次仅启用一个,由 MemoryManager 编排(agent/memory_manager.py:433)。生命周期覆盖:回合前 `prefetch`(有语义信号才拉取——`is_trivial_prompt`(agent/memory_provider.py:90)把「hi / thanks / ok」这类无信号回合挡在阻塞网络往返之外)、回合末 `sync_turn`、压缩前 `on_pre_compress`(可 opt-in fail-closed 的 checkpoint 契约 `PRE_COMPRESS_CHECKPOINT_API_VERSION = 2`,agent/memory_provider.py:48)。记忆写入口(hook)可镜像给 provider——内部三层与外部 provider 不是二选一,而是共存。

### 4.4 会话检索:FTS5 三索引路由与 CJK 二元组

SessionDB 为 messages 维护三套全文索引:`messages_fts`(unicode61)、`messages_fts_trigram`(SQLite ≥3.34)、`messages_fts_cjk`(外部 tokenizer `cjk_unicode61`,工具行排除)。入口 `search_messages()`(hermes_state_search.py:1431)是带计时的包装器:慢查询日志阈值 `HERMES_SEARCH_SLOW_MS` 默认 1000ms(hermes_state_search.py:1449/1468),每条日志带路由路径——docstring 自述这是 2026-07 会话检索事故的产物:「the next regression is a grep」。

路由判定 `_describe_search_path()`(hermes_state_search.py:1481-1503):非 CJK 查询 → `fts5`;含 CJK 且 cjk 索引可用、无孤立 CJK 短段 → `fts_cjk`;CJK ≥3 字符且 trigram 可用 → `trigram`;否则 `like_scan` 兜底。为什么要第三套索引?**trigram 每 token 至少 3 个字符**,1-2 字的 CJK 词(「记忆」「画像」)根本进不了 trigram MATCH,早年全落 LIKE 全表扫(笔记实测 6.8GB 表 3-6 秒/查询)。修复是 native/fts5_cjk/fts5_cjk.c——约 250 行零依赖的 unicode61 包装:CJK 连续串重发射为**重叠字符二元组**(Lucene CJKAnalyzer 语义,单字退化 unigram),查询词转连续 bigram 短语即可索引级命中 ≥2 字符精确子串。装到 `~/.hermes/lib/libfts5_cjk.so`(`HERMES_FTS5_CJK_SO` 可覆盖,`sessions.cjk_fts: false` 可关)。CJK 表 DDL(hermes_state.py:4186-4200):

```sql
CREATE VIEW IF NOT EXISTS messages_fts_cjk_src AS
    SELECT id, role, content, tool_name, tool_calls
    FROM messages
    WHERE role <> 'tool';

CREATE VIRTUAL TABLE IF NOT EXISTS messages_fts_cjk USING fts5(
    content,
    tool_name,
    tool_calls,
    content='messages_fts_cjk_src',
    content_rowid='id',
    tokenize='cjk_unicode61'
);
```

外部内容表的关键是**触发器门控**:插入/删除触发器只在 id 越过 `fts_cjk_rebuild_high_water` / `fts_cjk_rebuild_progress` 双 marker 时才生效(hermes_state.py:4202-4224)——注释写明:陈旧索引对从未持有的 rowid 执行外部内容 delete 是 FTS5 经典损坏源(:4180-4185)。自愈路径 `_ensure_fts_cjk_schema()`(hermes_state.py:6040):tokenizer 不可用就先写 breadcrumb 再删 cjk 触发器,写消息永不挂,降级 trigram/LIKE 路由继续工作;`hermes sessions optimize-storage` 可回填重建。

### 4.5 写入触发:nudge 与后台评审

记忆写入不靠模型自觉,靠**回合尾 nudge 计数**。默认间隔 10:内存 `agent._memory_nudge_interval = 10`(agent/agent_init.py:1903,可配 `memory.nudge_interval` :1929);技能侧同默认(agent/agent_init.py:2032/2035)。memory 按**用户轮**计数,判定点在回合开始(turn_context.py:869-877):

```python
# Track memory nudge trigger (turn-based, checked here).
should_review_memory = False
if (agent._memory_nudge_interval > 0
        and "memory" in agent.valid_tool_names
        and agent._memory_store):
    agent._turns_since_memory += 1
    if agent._turns_since_memory >= agent._memory_nudge_interval:
        should_review_memory = True
        agent._turns_since_memory = 0
```

任一 memory 工具调用成功即清零(agent/tool_executor.py:709-710);会话恢复时从历史补齐计数。skill 按**工具迭代**计数(agent/conversation_loop.py:2369-2373,仅 `skill_manage` 可用时自增),用 skill_manage 后清零(agent/tool_executor.py:711-712)。真正的执行在回合**响应送达之后**(agent/turn_finalizer.py:810-830):满足 `final_response and not interrupted and not skip_background_review and (_should_review_memory or _should_review_skills)` 就 `_spawn_background_review(messages_snapshot=list(messages), review_memory=…, review_skills=…)`——快照结构克隆,后台 fork 的就地清洗器碰不到现场转录;异常全吞(best-effort)。后台线程见 agent/background_review.py:1754;评审 agent 自身把两个 nudge 间隔置 0 防递归(curator.py:1977-1978),fork 的整份工作就是发 memory / skill_manage 两种工具调用(background_review.py:388-391);cron 会话无人在环,默认 `skip_background_review=True`(每个评审事件约 3 万 token,turn_finalizer.py:812-814 注释)。

## 6. 边界与坑

| 症状 | 原因 | 处理 |
|---|---|---|
| 记忆「写了没生效」 | 冻结快照设计:会话内 prompt 不变是特性 | 用 memory 工具结果验证写入;新值下会话或压缩恢复后进 prompt |
| MEMORY.md 超 2200 字符 | 条目太多太碎 | 按工具提示 replace 合并;单回合 3 次失败熔断,别硬撑 |
| 1-2 字中文搜不到或极慢 | trigram 需 ≥3 字符,落入 like_scan 兜底 | 确认 cjk 索引已建(`optimize-storage` 回填),查慢日志路由路径 |
| cjk tokenizer 加载失败 | .so 缺失或被 HERMES_FTS5_CJK_SO 指错 | 重跑 native/fts5_cjk/build.sh;进程已自愈删触发器,写消息不挂 |
| 记忆文件被投毒 | 供应链/姊妹会话写入恶意条目 | strict 扫描命中→快照 `[BLOCKED:]` 占位,原文保留可删——别静默丢弃 |
| 外部 provider 每轮都慢 | 问候轮也触发 prefetch | trivial prompt 门控(memory_provider.py:90)只放行有语义信号的回合 |
| 后台评审烧 token | 每事件约 3 万 token | cron 会话默认 skip_background_review;本地高频会话可调大 nudge_interval |

- **存什么的判断**:存跨会话才值钱的事实与偏好(项目约束、用户习惯、长期承诺);不存一次性能检索到的细节(会话库就是档案)、明文密钥、可变指令(该进技能/system prompt,02 章路径)。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 三层记忆 | SessionDB 全量可检索 / MEMORY.md 2200 字符 / USER.md 1375 字符,分层的依据是取回成本 |
| 双状态 | 冻结快照进 prompt 保前缀缓存;活状态进工具结果,下会话快照才更新 |
| 双文件读写 | memory 工具 add/replace/remove 批量操作,strict 威胁扫描,3 次熔断防死循环 |
| 三索引路由 | fts5 / fts_cjk / trigram / like_scan 按查询形状选路,慢日志带路径可 grep |
| CJK 扩展 | trigram 卡 ≥3 字符 → cjk_unicode61 重叠二元组,索引级命中 1-2 字词 |
| nudge 写入 | memory 按用户轮、skill 按工具迭代,默认 10;回合送达后后台评审派发 |

**思考题**:为什么 Hermes 选择「关键词检索 + 冻结快照」而不是向量记忆常驻 prompt?如果某轮用户说「忘掉我刚写的那条记忆」,最快什么时候能真正生效?

> [!note] 参考答案
> ①会话检索要的是「说过什么」的字面召回——精确、可审计、零模型成本,查询本身还能解释;向量适合语义模糊召回(02.05/04),那是外部 provider(Honcho 等)的活,且 prefetch 进的是易失上下文而非长期快照。②冻结快照是前缀缓存换稳定:立即执行 memory(action=remove)能删活状态与磁盘,但本回合 prompt 里仍是旧快照,真正消失要等下次 `load_from_disk()`(压缩恢复 system_prompt.py:1084 或新会话);「立刻让模型不知道」做不到——这与 02.05/06 的遗忘设计一致:遗忘是持久化层的承诺,不是上下文层的即时抹除。
