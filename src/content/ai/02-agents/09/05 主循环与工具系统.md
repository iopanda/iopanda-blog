# 主循环与工具系统

> 01 章认完了仓库布局,本章把镜头对准「会动的那部分」:一次用户提问,如何在 Codex 内部变成若干轮「模型推理 + 工具执行」,最终以一条回答收场。答案藏在 core crate 的 session 模块里——从会话级 submission_loop 到 turn 级 step 循环,再到工具注册表与 AGENTS.md 分层拼接,每一层都在回答同一个问题:模型怎么拿到工具、工具结果怎么回到模型。这正对应 02.01/03「Agent 运行循环」与 02.04「Function Calling」在真实工程里的落地形态。
**学习目标**:学完本章,你将能够——

1. 区分 turn / step / iteration 三个术语,说出它们与 02.01「Agent 运行循环」概念的对应关系;
2. 沿 submission_loop → Op::TurnInput → run_turn 追完一次用户 turn 的启动链,指出会话级与 turn 级两层循环各自的边界;
3. 解释 Responses 流里 `Completed { end_turn: false }` 如何驱动「再来一轮」,`drain_in_flight` 如何把工具结果回灌会话历史;
4. 复述 ToolRouter → ToolRegistry → Handler 的工具分发路径,说出 PreToolUse hooks 的拦截点与内置工具的四大来源;
5. 说明 AGENTS.md 的逐层拼接规则,以及上下文超限时自动压缩的触发与执行方式。

## 1. 概念:turn / step / iteration 与两层循环

- 02.01/03 的「Agent 运行循环」是概念骨架:感知 → 思考 → 行动 → 观察,循环到任务完成。Codex 把它切成两个粒度:**turn**(回合)与 **step**(步)。一次用户 turn = 从收到一条用户消息到模型给出「本轮到此为止」信号的完整服务,用户可感知、UI 可呈现;一个 step = 一次「采样请求 + 由此触发的工具执行」,是 token、预算与压缩记账的边界。**iteration 不是代码里的类型**,它描述 step 反复发生的次数——一次长 turn 往往包含几十个 step。
- 代码里对应两层循环:**会话级** `submission_loop`(只分发 Op,不碰模型)与 **turn 级** step 循环(真正采样与执行工具)。同一会话同一时刻只跑一个 turn,靠 `TurnState` / `active_turn` 互斥保证串行;一次对话 = 多个 turn,一个 turn = 多个 step——一个 step ≈ 02.03/03 里 ReAct 的一轮「推理 + 行动」。

## 2. 为什么这样设计:模型一次只能推理一段

- 模型输出是流式的、单段的;工具执行结果不会自动出现在模型视野里,必须把它编码成新的输入 item 再发一次请求。因此任何编码 Agent 都必须在「采样」与「执行」间反复横跳,直到模型端给出完成信号(Responses API 的 `Completed` 且 `end_turn` 为真)。
- 把这段横跳封装成 turn,是因为 turn 边界提供了三个天然挂点:turn 级 stop hooks、上下文记账(超限压缩)、以及用户可感知的进度/终止语义。若只留一个巨大的 step 循环,这些策略就无处安放;而若把每个工具调用都算成一次 turn,预算与 hooks 又会在每次工具后重复评估,徒增开销。

## 3. 作用位置:session 与 tools 两个目录

主循环全部位于 `codex-rs/core/src/session/`(`handlers.rs` 会话分发、`turn.rs` turn 执行、`turn_input.rs` 入口、`mod.rs` 会话装配),工具系统位于 `codex-rs/core/src/tools/`(`router.rs` 调用归一、`registry.rs` 注册表、`parallel.rs` 并发门、`spec_plan.rs` 工具清单构建)。01 章所说的「Rust 核心」,在这里具象成两个异步循环与一张工具注册表。

## 4. 详细介绍

### 4.1 会话级 submission_loop:Op 分发器

`Session::spawn_internal`(session/mod.rs:518)在尾部把分发循环丢进 tokio,注释直接说明其生命周期:

```rust
// session/mod.rs:826-832 — 该任务会一直运行到收到 Op::Shutdown 为止
let session_for_loop = Arc::clone(&session);
let session_loop_handle = tokio::spawn(async move {
    submission_loop(session_for_loop, configured_config, rx_sub)
        .instrument(info_span!("session_loop", thread_id = %thread_id)).await;
});
```

`submission_loop`(session/handlers.rs:529)是会话级 `while let Ok(sub) = rx_sub.recv().await` 分发器:每个 `Op` 一个 arm,执行后返回 `should_exit: bool`,收到 `Op::Shutdown` 或 channel 关闭才退出(handlers.rs:719-728 做 teardown)。开始一次 agent turn 的关键路径是 `Op::TurnInput`(打断、手动压缩等 Op 也走同一分发器):

```rust
// session/handlers.rs:585-593 — 用户提交消息 → 进入 turn 处理,结果经 reply 回给调用方
Op::TurnInput { request, mode, reply } => {
    let result = turn_input::handle(&sess, *request, mode, sub.id.clone()).await;
    let _ = reply.send(result); false
}
```

### 4.2 turn 级 run_turn:step 循环与 SSE 驱动

`turn_input::handle`(session/turn_input.rs:197)→ `start_if_idle`(:327)→ **`run_turn`**(session/turn.rs:162)。run_turn 先固化首步的 `StepContext`——工具表在第一次采样前就固定下来,避免循环中工具漂移:

```rust
// session/turn.rs:229-246(要点)— 首个 step 的上下文(含工具表)在采样前固化
// run_turn owns the step used to seed context and make the first sampling request.
let first_step_context = match sess
    .capture_step_context_with_required_mcp_servers(... required_servers, required_plugins).await
```

随后进入主 step 循环(turn.rs:334)。每轮先组装发送给模型的输入:上下文保存在 `ContextManager`,经 `clone_history()` 取全量、`for_prompt`(context_manager/history.rs:315)做归一化与模态过滤后整段作为请求输入——这是「上下文组装」的核心。组装好输入后调 `run_sampling_request`(turn.rs:1418),其内部为每次重试建 `ToolCallRuntime` 并 `build_prompt`(turn.rs:1389)把工具表塞进 API 请求:

```rust
// session/turn.rs:1395-1405 — 每轮请求都携带「模型可见」的工具定义,且允许并行调用
Prompt {
    input,
    tools: step_context.tool_router.model_visible_specs(),
    parallel_tool_calls: true,
    base_instructions,
    output_schema: turn_context.final_output_json_schema.clone(),
    output_schema_strict: !crate::guardian::is_basic_session_source(...),
    cyber_access_program: turn_context.cyber_access_program,
}
```

流式采样在 `try_run_sampling_request`(turn.rs:2264):打开 responses 流后用 `FuturesOrdered` 维护在飞工具 future(turn.rs:2295-2308)。事件循环里两个关键分支:模型输出工具调用 item(`OutputItemDone`)→ `handle_output_item_done`(stream_events_utils.rs:290)转成工具 future 压入队列;流收尾事件 `Completed` 判定是否还要再来一轮:

```rust
// session/turn.rs:2666-2672 — SSE Completed:end_turn=false 表示模型还要继续(典型:刚发完工具调用)
if let Some(false) = end_turn {
    needs_follow_up = true;
}
break Ok(SamplingRequestResult { needs_follow_up, last_agent_message });
```

流结束后排空在飞工具——**工具结果回灌历史**就发生在这里:

```rust
// session/turn.rs:2216-2238(要点)— 把每个工具 future 的结果写回会话历史
async fn drain_in_flight(...) -> CodexResult<()> {
    while let Some(res) = in_flight.next().await {
        match res {
            Ok(envelope) => {
                sess.record_annotated_conversation_items(&turn_context, vec![envelope]).await;
            }
            Err(err) => error_or_panic(format!("in-flight tool future failed during drain: {err}")),
        }
    }
}
```

工具输出以 `FunctionCallOutput` 形态的 item 进入历史,下一轮 `clone_history().for_prompt` 自然包含它们。回到主循环:若 `needs_follow_up`,`continue` 进入下一轮采样;否则跑 `run_turn_stop_hooks`,`should_block` 时把 hook 提示注入历史后继续、`should_stop` 时 break(turn.rs:547-608),最终 `Ok(last_agent_message)` 结束整个 turn(turn.rs:646)。

### 4.3 工具路由:ToolRouter → ToolRegistry → Handler

- **归一**:模型原始输出是 `ResponseItem`,经 `ToolRouter::build_tool_call`(tools/router.rs:246)统一成 `ToolCall`:函数调用 → `ToolPayload::Function`,客户端执行的 `ToolSearchCall` → `ToolSearch`,自定义调用 → `Custom`;非工具 item(文本/推理)走 finalize 路径。
- **并发门**:`ToolCallRuntime::handle_tool_call`(tools/parallel.rs:74)→ `tool_supports_parallel` 决定拿读锁(并行工具可并发)还是写锁(串行工具全局互斥)(parallel.rs:116-159),然后进 registry 分发。
- **注册表分发**:`ToolRegistry::dispatch_any_with_terminal_outcome`(tools/registry.rs:495)。名字查不到不崩溃,而是生成解释文本回给模型:

```rust
// tools/registry.rs:516-536(要点)— 工具不存在 → RespondToModel:让模型「看见」错误并自我修正
let tool = match self.tool(&tool_name) {
    Some(tool) => tool,
    None => {
        let message = unsupported_tool_call_message(&invocation.payload, &tool_name);
        ... return Err(FunctionCallError::RespondToModel(message));
    }
};
```

- **PreToolUse hooks 拦截点**:真正执行 handler 之前,注册表先跑 hooks(registry.rs:567-591);hook 返回 `Blocked` 即 `RespondToModel` 拒回模型,也可改写调用输入——这是 02.04/06「权限边界」在工具链上的第一个闸门。放行后由 `handle_any_tool` 落地:

```rust
// tools/registry.rs:772-797(要点)— 最终执行:每个工具 handler 实现 ToolExecutor::handle
async fn handle_any_tool(tool: &dyn CoreToolRuntime, invocation: ToolInvocation)
    -> Result<AnyToolResult, FunctionCallError> {
    let output = tool.handle(invocation.clone()).await?;
    ...
    Ok(AnyToolResult { call_id, payload, result: output, post_tool_use_payload })
}
```

成功后还有 PostToolUse hooks(registry.rs:684-731,可整段拒绝结果),最终 `into_response()` 变成 `FunctionCallOutput` 写回历史(parallel.rs:83-90)。

- **注册表结构**(registry.rs:286-338):`IndexMap<ToolName, RegisteredTool>` + `first_collision`;内置工具重复注册直接 `error_or_panic`,外部(插件等)冲突则跳过并记录、保留内置——冲突裁决按信任度分层。
- **内置工具清单**:`build_tool_router`(tools/spec_plan.rs:125)→ `add_core_tool_sources`(spec_plan.rs:974)汇聚四大来源(spec_plan.rs:1028-1031):

```rust
// tools/spec_plan.rs:1028-1031 — 内置工具四大来源:shell / MCP 资源 / 通用工具 / 多智能体协作
add_shell_tools(context, registry);
add_mcp_resource_tools(context, registry);
add_core_utility_tools(context, registry);
add_collaboration_tools(context, registry);
```

  - **shell**(spec_plan.rs:1075):`ExecCommandHandler`(exec_command)、`WriteStdinHandler`;
  - **mcp-resource**(:1123):list/read MCP 资源三件套;
  - **utility**(:1132 起,多受 feature 开关控制):`PlanHandler`(:1138)、`WaitForEnvironmentHandler`、`RequestUserInputHandler`、`RequestPermissionsHandler`、`NewContextWindowHandler`、`ApplyPatchHandler`(:1250)等;
  - **collaboration**(多智能体,:1280 起):v2 全套 `SpawnAgentHandlerV2 / SendMessageHandlerV2 / WaitAgentHandlerV2` 等。

外部来源另计:MCP 服务器工具 `append_mcp_tools`(spec_plan.rs:159,按 exposure 策略直出或 deferred)、dynamic tools、扩展工具。guardian 审查子会话只拿 exec_command / write_stdin / view_image(spec_plan.rs:975-1026)。`ToolExposure`(Direct/Deferred/… )决定模型可见性,deferred 工具会被压缩成少量模型入口(如 list_tool),最终 `finalize_tool_router`(spec_plan.rs:352)产出 `model_visible_specs` 才真正发给模型。

### 4.4 上下文组装:AGENTS.md 分层拼接与自动压缩

AGENTS.md 的规则写在模块头部的常量里(agents_md.rs:39-46):

```rust
// agents_md.rs:39-46 — 文件名与拼接分隔符(用户指令与项目文档之间的「分水岭」)
pub const DEFAULT_AGENTS_MD_FILENAME: &str = "AGENTS.md";
pub const LOCAL_AGENTS_MD_FILENAME: &str = "AGENTS.override.md";
const AGENTS_MD_SEPARATOR: &str = "\n\n--- project-doc ---\n\n";
```

`load_project_instructions`(agents_md.rs:55)从项目 root 到 cwd **逐层收集**:root 用 `.git` 等 `project_root_markers` 向上探测且不越过;每层目录按候选文件名取第一个命中的文档;拼接时(agents_md.rs:352-378)用户指令(user_instructions,宿主侧)在前,第一个项目文档出现才插入 `--- project-doc ---` 分隔符,后续文档仅以空行相连——分隔符的存在让模型能区分「操作者指令」与「仓库自带说明」两种信任来源。每个 StepContext 捕获时刷新一次(session/mod.rs:3540-3543),随 initial context 发送。

**自动压缩**:采样后 `context_window_token_status` 记账(turn.rs:461-471),当模型还需要继续(`needs_follow_up`)且 token 逼近上限(`token_limit_reached`)时命中 `should_roll_over`(turn.rs:505-506),调 `run_auto_compact(..., CompactionReason::ContextLimit, CompactionPhase::MidTurn)`(turn.rs:517-539)后 `continue` 重新采样。压缩本身也调模型:`run_inline_auto_compact_task`(compact.rs:116)把 `compact_prompt` 当作一次 UserInput 发出去,让模型自己总结历史、生成 Compaction item 替换旧历史——「压缩不是删,是让模型写纪要」;手动 `/compact` 则走 `run_compact_task`(compact.rs:148)。

**参考骨架**(与真实文件逐行对照后简化,箭头即一次 await 或事件):

```text

...重复采样直到 Completed end_turn 为 true → stop hooks → break(turn.rs:547)
```

## 6. 边界与坑

| 症状/现象 | 原因 | 处理 |
|---|---|---|
| 模型调用不存在的工具 | 名字查不到 registry | 不崩溃,`RespondToModel` 文本回灌,让模型自我修正(registry.rs:516) |
| hook 拦不住某类工具调用 | PreToolUse hooks 是 handler 执行前唯一闸门 | 文件级策略靠 hook,进程级隔离靠 03 章沙箱兜底 |
| 并行工具吞吐上不去 | 串行工具拿写锁全局互斥(parallel.rs:116) | 新工具声明 parallel 能力前先评估是否真可并发 |
| 长会话每轮都慢 | 自动压缩是一次完整采样(模型写纪要) | 调 `compact_prompt`,或主动 /compact 挑时机;压缩 item 是模型输出,可能失真 |
| AGENTS.md 突然失效 | 探测 root 的 markers 被改或 cwd 超出 root | 拼接只覆盖 turn 环境 cwd 之下(agents_md.rs:55),项目别依赖 root 外的文档 |

- 边界提醒:turn 是「预算与 hooks 边界」,不是「安全边界」;`end_turn=true` 只表示模型认为本轮完成,不代表任务达成——step 级超限由 token_budget 与压缩兜底,命令级危险动作留给审批与沙箱(03、04 章)。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| turn / step | turn 是用户可见的服务边界,step 是内部采样+执行的最小记账单位,iteration 即 step 的反复 |
| 两层循环 | submission_loop 分发 Op(handlers.rs:529),run_turn 跑 step(turn.rs:162),会话内 turn 串行 |
| SSE 驱动 | `Completed { end_turn: false }` → `needs_follow_up` → 再采样;为真 → stop hooks → break(turn.rs:2666 / 547) |
| 结果回灌 | drain_in_flight 把 FunctionCallOutput 写回历史,下一轮 for_prompt 自然带上(turn.rs:2216) |
| 工具链 | build_tool_call 归一 → 并发门 → registry 分发 → PreToolUse hooks → handler → PostToolUse |
| 内置工具 | 四大来源:shell / mcp-resource / utility / collaboration(spec_plan.rs:1028-1031) |
| 项目指令 | AGENTS.md 从 root 到 cwd 逐层拼接,`--- project-doc ---` 分隔用户指令与项目文档(agents_md.rs:46) |
| 压缩 | token 超限 + 需续跑 → run_auto_compact → 模型自写纪要 → continue(turn.rs:505) |

**思考题**:一次 turn 里模型可能连续调用十几个工具,为什么 Codex 不把「每个工具调用」都当成一次新 turn?PreToolUse hooks 判定 Blocked 之后,拒绝信息以什么形态回到模型,这对安全审计有什么好处?

> [!note] 参考答案
> turn 是用户可感知的服务边界,step 是内部记账边界:把工具调用算成 turn,会让 stop hooks、预算、压缩在每个工具后都重新评估一次,并且破坏「一条用户消息 = 一个 turn」的语义;turn 内 step 过多由 token_budget 记账与自动压缩兜底。Blocked 后注册表返回 `FunctionCallError::RespondToModel(message)`(registry.rs:567-591),Codex 把拒绝原因拼成输出 item 回写历史,模型下一轮能看到「为什么被拒」并改弦更张——拒绝因此进入上下文成为可审计、可回放的事件,而不是硬错误中断会话,这正是 02.04/06 权限边界「拒绝要可解释」的工程实现。
