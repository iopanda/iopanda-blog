# 与大型实现对比

> 收官章把 Pi 放回 02.09 的六对象棋盘:00 Learning Path 的八维框架是每个子单元共用的解剖模板,前四章逐维交了 Pi 的「源码答案」,本章用同一张表给 Pi 打分——最小内核+四工具对 Codex 的 Rust 极简 CLI、Hermes 的记忆/技能资产化、Claude Code 的闭源全功能、OpenCode 的 TS 插件生态与 Copilot 的云 agent。分数之外更值得追问:一个「10 万+ star 却保持小代码库」的项目,到底证明了什么?哪些设计值得抄,哪些坑必须先知道?

**学习目标**:学完本章,你将能够——

1. 用 00 Learning Path 的八维框架给 Pi 逐维打分,每一分都能报出「文件:行号」或「见 XX README」的证据;
2. 解释「10 万+ star 保持小代码库」意味着什么:star 是注意力指标而非复杂度指标,以及 Pi 用哪些纪律对抗膨胀;
3. 复述可抄清单四条(极简 system prompt、树状会话、TypeBox 校验、扩展事件面)并说出各自的源码出处;
4. 复述要避清单两条(无默认权限护栏、功能全靠拼装的发现成本)并给出落地替代方案;
5. 完成六对象收官对照表,能回答「如果我自己写 Agent,Pi 这一格抄什么、不抄什么」。

## 1. 概念:同一张八维表,给六个实现排座次

- 00 Learning Path 定义的八维是:①源码结构与入口、②Agent 循环实现、③上下文构建、④工具系统、⑤记忆系统、⑥协议与扩展、⑦评测与质量、⑧安全设计——每个子目录都按这八维解剖,Pi 的 01~04 章就是逐维答案。收官只做一件事:**把 Pi 的答案与另外五个实现并排,逐维打分**。
- 六个对象在设计光谱上各占一格(均为各子目录 README 2026-09 核证口径):

| 对象 | 一句话定位 | 设计签名 |
|---|---|---|
| Pi | 极简可扩展终端编码 Agent(本讲义) | 最小内核+四工具,能力外置到扩展 |
| 02 Codex | Rust+TS 双栈全开源 CLI | 80+ crates 的 Rust 核心,三态沙箱策略「简单够用」(见 02 README) |
| 03 Hermes | Python 全栈自我进化 Agent | 技能/记忆/用户画像作为运行时可变资产(见 03 README) |
| 01 Claude Code | 闭源核心+开源 SDK 外壳 | permissionMode+hooks+SKILL.md 全功能内置(见 01 README) |
| 04 OpenCode | TS monorepo 社区 Agent | 插件生态+开箱 LSP+build/plan 双模式(见 04 README) |
| 06 GitHub Copilot | 平台化编码 Agent 家族 | 云 agent 的 Issue→PR 异步工作流+平台护栏(见 06 README) |

- 打分纪律:Pi 侧一律给源码出处(文件:行号,前四章核证过);其他实现只引用其子目录 README 已核证信息,标注「见 XX README」,不断言源码细节——这是本单元横向对比的共识边界。

## 2. 为什么:小核外置与全功能内置,不该用一把尺子量

- 「最小内核 + 扩展前置」和「全功能内置」是两种相反的赌注:前者赌**默认面小则行为可预测、可审计、可整读**(01 章的双层直路循环),后者赌**开箱即用、功能完整则用户留存高**(Claude Code 的权限模式与 hooks、Copilot 的平台工作流)。
- 八维打分因此不是「谁更强」,而是「每一维上,该实现的取向完成得怎样」:Pi 在「安全设计」维天然低分——README.md:40 明说无内置权限系统,这是**主动取舍**(04 章「不需要就不建」)而非疏漏;它在「协议与扩展」维则应该满分,因为那是它押注的全部。打分表的意义是把这种取舍摊开,让你按自己的场景加权,而不是按总分排名。
- 六对象里只有 Pi 和 Codex 把「极简」当卖点,但落点相反:Codex 用 Rust 重写换单二进制与低延迟、把沙箱做进内核(见 02 README);Pi 把内核削到只剩循环与四工具、把沙箱/权限/子代理全部外置成示例(04 章)。对照读这两格,「极简」的两种工程含义就清楚了。

## 3. 作用:一张表回答「Pi 站在哪、凭什么」

- 表的价值是**定位 + 溯源**:每个分数都能顺着「文件:行号 / 见 XX README」回到一段可核证的事实;这样读者可以不同意分数、但必须面对证据。读表时记住两个校正:①Pi 的低分维(记忆、安全)多为「外置」而非「缺失」,要去看它给出的扩展路径是否成立;②其他实现的描述来自 README 规划口径,闭源对象(Claude Code/Copilot)的能力以文档与行为实验为准(见 01/06 README)。

## 4. 详细介绍

### 4.1 八维打分表:Pi 逐维评分与对照

| # | 维度 | Pi 的落点与出处 | 评分 | 横向对照(见 XX README) |
|---|---|---|---|---|
| ① | 源码结构与入口 | 十包 monorepo,cli.ts 仅 21 行,启动链一次读到底(main.ts:561→675→816) | ★★★★★ | Codex 80+ crates 双栈(02);Hermes Python 全栈(03);Claude Code/Copilot 核心闭源(01/06) |
| ② | Agent 循环实现 | 双层直路循环:低层工具批+follow-up(agent-loop.ts:156),高层重试/压缩/续跑(agent-session.ts:1105) | ★★★★☆ | Codex turn/iteration 由 done 事件终止(02);OpenCode build/plan 双 agent(04);Copilot 云 agent 多轮迭代(06) |
| ③ | 上下文构建 | 极简 system prompt(system-prompt.ts:123-124)+ 树状 JSONL(session-manager.ts:846)+ 压缩(agent-session.ts:2125) | ★★★★☆ | Codex AGENTS.md 自动发现拼接(02);Claude Code skills 按需注入(01) |
| ④ | 工具系统 | 默认四工具 read/bash/edit/write,TypeBox schema 即契约(tools/index.ts:164、validation.ts:317) | ★★★★☆ | Codex 三态沙箱执行 exec(02);OpenCode 开箱 LSP(04) |
| ⑤ | 记忆系统 | 树状会话是「档案级」记忆;长期记忆/RAG 留给 dynamic context 扩展(extensions/types.ts:687/1275) | ★★★☆☆ | Hermes FTS5 全文检索+摘要压缩+画像(03);Copilot 云 session logs(06) |
| ⑥ | 协议与扩展 | ~40 个 on() 事件 6 类 + 四层资源 + 85 个示例(extensions/types.ts:1252-1382、loader.ts:711-720) | ★★★★★ | OpenCode TS 插件生态(04);Hermes skills/plugins/MCP(03);Claude Code hooks(01) |

| ⑧ | 安全设计 | 无内置权限系统(README.md:40),默认进程全权;供应链硬化反衬出「边界靠容器」(AGENTS.md、README.md:42-46) | ★★☆☆☆ | Codex 三态沙箱(02);Claude Code permissionMode 六模式(01);Copilot Actions 隔离+审批闸门(06) |

- 合计 30/40,形状说明一切:**在 ①⑥(可读性、扩展面)拿满,在 ⑧(安全默认)垫底**——这是「最小内核+扩展前置」哲学的精确投影:把复杂度从内核挪到事件面,把安全责任从内核挪到用户与容器。

### 4.2「10 万+ star 保持小代码库」意味着什么

- 事实(见本子目录 README,2026-09 核证):Pi 已达 10 万+ star;同列 Codex 约 12.1 万、OpenCode 约 20.3 万(见 02/04 README)。差别不在 star 数,而在**代码量**:Codex 是 80+ crates 大仓(02 README),OpenCode 是 TS monorepo 大仓(04 README),而 Pi 的核心可以被本讲义五章整读——最大的单文件 agent-session.ts 也就 3515 行。
- 这意味着四点:
  1. **star 是注意力指标,不是复杂度指标**。10 万 star 没有逼作者加功能,因为功能诉求被扩展系统吸收——85 个示例就是「需求中转站」(04 章:示例即契约);
  2. **小代码库需要反向纪律维护**。CONTRIBUTING.md:23 写明新贡献者的 issue/PR 默认自动关闭、:27 维护者每日复审;AGENTS.md 要求不保向后兼容、erasable TS——「拒绝膨胀」被写进了开发流程,而不是靠意志;
  3. **完整通读本身就是卖点**。对用户与安全审计者,「可读」意味着可验证:没有黑盒、没有闭源陷阱,这正对着 Claude Code/Copilot 的「闭源核心」(01/06 README);
  4. **但 star 替代不了默认护栏**。高关注度 + 无内置权限(README.md:40)意味着新手最容易「裸奔」——这直接引出要避清单第一条。

### 4.3 可抄清单(带源码出处)

1. **极简 system prompt**:模板只有身份、工具列表、两条固定指南与 cwd,其余(项目上下文/技能)一律**追加区块**而不改写模板——常驻指令压到最短,把上下文位置留给真实对话(system-prompt.ts:123-124、:128-166)。抄法:先写 10 行内的核心模板,再设计追加机制。
2. **树状会话**:单 JSONL append-only 树,entry 带 {type,id,parentId,timestamp}(session-manager.ts:846、:30),分支=移动 leaf、回溯=改指针,压缩=独立 LLM 调用+compaction entry 折叠(compaction.ts:126-136)。抄法:任何「要回溯、要分支」的会话需求,都比「复制整份日志」干净一个量级。
3. **TypeBox 校验**:工具参数 schema 即契约(read.ts:21-25、write.ts:15-19),运行时 Value.Convert+Check(validation.ts:317),校验失败转 isError 工具结果回灌模型而非抛异常(agent-loop.ts:625、:668-673)。抄法:execute 永远拿到「校验后参数」,工具内部零类型 if。
4. **扩展事件面**:把「功能清单」设计成「事件清单」——约 40 个 on() 事件覆盖会话/agent/工具/模型/输入/资源六类(extensions/types.ts:1252-1382),再配 registerTool/registerCommand/registerFlag 五类注册表(types.ts:1765-1778)。抄法:内核只留主循环与最小工具,所有「策略」(权限、plan、子代理)都做成事件消费者——permission-gate.ts:10-34 演示了如何用 tool_call 事件自造安全闸门。

### 4.4 要避清单

1. **无默认权限护栏**:默认四工具含 bash,进程以启动用户全权运行(README.md:40),官方给出的边界方案是「自己容器化」(README.md:42-46:Gondolin/Docker/OpenShell);permission-gate 只是 85 个示例之一,不装就没有。避法:生产环境要么直接容器化,要么抄 Codex 的三态沙箱默认只读(02 README)、Claude Code 的 permissionMode(01 README)或 Copilot 的 Actions 隔离(06 README)——**护栏必须默认存在,不能靠用户记得去扩展市场里找**。
2. **功能全靠拼装的发现成本**:内核只有四工具,plan mode/子代理/沙箱/权限全在 examples 里且 loader 只扫一层目录、不建注册中心(loader.ts:711-720);用户不知道「有这些扩展」就用不上,「80% 用户只用四工具还以为是全部」是真实风险。避法:团队自维护一份「必备扩展清单+预设配置」随仓库分发,把发现成本从每个用户身上转移到一次性的团队资产上。

## 6. 边界与坑

| 现象/坑 | 原因 | 处理 |
|---|---|---|
| 以为 Pi「功能少=不好」 | 少是主动取舍(04 章),低分维都有扩展出口 | 评分看「取向完成度」,不是功能数 |
| 以为 star 多=代码可信 | star 是注意力;护栏仍默认缺失 | 信「可读+可验证」,不信 star 背书 |
| 其他实现描述与源码有出入 | 只引 README 规划口径,闭源对象靠文档 | 需要深究时回到各对象自己的 01~05 章 |
| 把 examples 当内置功能 | 85 个示例是「可选配件」,默认不加载 | 用前先看 docs/extensions.md 信任边界 |
| 想照抄 Pi 的信任模型 | 它要求宿主自带容器/沙箱纪律 | 无容器条件就抄 Codex 的默认只读沙箱 |

- 边界提醒:本章所有「见 XX README」都是 2026-09 核证口径;代码库行号是检出快照,仓库每日在变,方法(重定位)比行号可靠——这条对六个对象一视同仁。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 八维打分 | Pi 30/40:可读性(①⑥)满分、安全默认(⑧)垫底,形状=哲学投影 |
| 10 万+ star 小代码库 | star 是注意力;小靠 CONTRIBUTING 纪律+扩展吸收需求维持 |
| 可抄 | 极简 system prompt / 树状会话 / TypeBox 校验 / 扩展事件面(4.3,各带出处) |
| 要避 | 无默认权限护栏 / 拼装发现成本(4.4) |
| 收官结论 | 小核外置的代价是安全默认与发现成本,收益是整读可审计与无限扩展面 |

**思考题**:① 八维表里 Pi 的「记忆系统」只得三星,但它的会话树对分支场景比线性日志强得多——三星合理吗?你会在什么场景给它加星?② 若你维护一个 10 万 star 的开源 Agent,敢不敢学 CONTRIBUTING.md:23 的「默认自动关 PR」?代价是什么?③ 「把安全外置给容器」与「把安全内置成沙箱(Codex)」,对个人用户与企业的适用边界分别在哪?

> [!note] 参考答案
> ① 三星评的是「默认能力」:树状会话(⑤维的档案层)确实一流,但长期记忆/RAG 需要扩展拼装,而 Hermes 把 FTS5 检索+摘要+画像做成了默认闭环(见 03 README)——若你的场景是「多会话跨天学习用户偏好」,Pi 需要你写扩展,该场景下三星合理;若你的场景是「单会话内反复改方案、来回试分支」,树的价值远超三星,可单独给它加星。② 敢,但要有配套:自动关是为了挡低质流量(作者博客称小团队+高门槛),代价是可能误伤真诚的新贡献者与社区热度;折中是 Hermes/OpenCode 式「bots 自动分流+维护者每日复审」(CONTRIBUTING.md:27 正是这么写的)。③ 个人用户:容器成本低、可接受「全权+自觉」;企业:审计与合规要求默认护栏,应选 Codex 式默认只读沙箱或 Copilot 式平台隔离——这正是 01.07 治理框架里「风险越高,自主度越低」的又一次印证。
