# 会话与压缩

> 01 章通读完「内核最小集」,但四个工具的对话如何活过一轮、活过一百轮?Pi 的答案是把一次会话存成「单文件、只追加、可分支」的树:每次回车都在 JSONL 末尾追加一条带 parentId 的记录,回溯只是把「叶子指针」移回某个旧条目,离开的分支被折成一段摘要继续参与上下文。本章看这份文件如何从一行 header 长成一棵树,以及上下文逼近窗口时,压缩在哪三个时刻被触发、摘要由谁生成、旧主线如何折叠。

**学习目标**:学完本章,你将能够——

1. 画出一次会话的 JSONL 文件结构(header + 带 {type,id,parentId,timestamp} 的追加条目),并说明 v3 树与线性日志的差别;
2. 复述 /tree、fork 与书签(label)在树上的操作语义,说明「只移动 leaf 指针、不改写历史」如何实现回溯与分支;
3. 说出 _checkCompaction 的三个自动触发情形(溢出带重试/可恢复截断/阈值),以及阈值触发所用公式与默认参数;
4. 解释 findCutPoint 反向攒保留预算、只许在 turn 边界下刀的原理,并描述「摘要 = 独立 LLM 调用 + compaction entry 折叠旧主线」的完整流程;
5. 说出换分支/继承时的 branch_summary 折叠与「每轮可改写消息」的 context 事件钩子,并对照 02.05 判断 Pi 的会话记忆属于哪种形态。

## 1. 概念:append-only 的树 = 分支不复制、回溯不重写

- 会话存储的权威注释一句话讲完设计:**"Manages conversation sessions as append-only trees stored in JSONL files."**(session-manager.ts:846)。每条记录是一个 entry,四个基础字段人人必有,其余字段随 type 不同而增删:

```ts
// core/session-manager.ts:46-51
export interface SessionEntryBase {
	type: string;
	id: string;
	parentId: string | null;
	timestamp: string;
}
```

- 追加即成为「当前叶子」的孩子:appendMessage 把 parentId 取为 this.leafId,落盘后推进 leaf(session-manager.ts:1058-1068);**分支就是把 leaf 移回某个较早的 entry 再继续 append**——旧子树原样留在文件里,零复制。当前分支 = 从 leaf 沿 parentId 一路回溯到根的路径,这是所有「重建上下文」操作的输入。
- entry 类型全集:message / thinking_level_change / model_change / compaction / branch_summary / label / session_info / custom / custom_message。其中 compaction 与 branch_summary 是「树的伤疤」——把被丢弃的历史以摘要形式留在树上;custom 与 custom_message 是扩展的持久化与上下文注入通道(session-manager.ts:69-141)。
- 文件版本号 CURRENT_SESSION_VERSION = 3(session-manager.ts:30);header 首行记录 {type:"session", version, id, timestamp, cwd, parentSession}(session-manager.ts:32-39);旧版本文件由 parseSessionEntries(session-manager.ts:299)容错续读并重建 byId/leaf 索引。

## 2. 为什么:对话不是日志,是带岔路的地图

- 02.05 讨论会话记忆时把重点放在「窗口放不下怎么办」(截断/摘要/RAG);Pi 的切入点更根本:**一次会话里用户会 fork、会回到历史岔口重试、会想同时保留多条候选分支**——线性日志只能用「复制文件」表达这些操作,而复制意味着历史割裂、同一段上下文重复计费。
- append-only 树让每个操作退化成「指针移动 + 一次追加」:fork 同一份历史开新文件(header 记 parentSession,main.ts:342 forkSessionOrExit),树内换分支只改 leaf。append-only 还天然抗崩溃——写坏最多丢最后半行,不可能毁掉一棵树;若要「物理删除」旧消息反而危险,因为 parentId 链会被打断。
- 「摘要即 entry」的哲学让丢失最小化:被放弃分支与被压缩旧文都不消失,而以 compaction / branch_summary 两种 entry 留在树的正确位置,重建上下文时再决定去留(session-manager.ts:853-854 注释:「handles compaction summaries and follows the path from root to current leaf」)。代价是每轮都要做一次树遍历 + 折叠计算(4.1 节),换来「想回到哪就能回到哪」。

## 3. 作用:一个真实会话文件长什么样

```text
<fileTimestamp>_<sessionId>.jsonl    # 目录 ~/.pi/agent/sessions/<编码后 cwd>/(session-manager.ts:476、954)
┌─ header    {"type":"session","version":3,"id":"…","timestamp":"…","cwd":"/repo","parentSession":…}
├─ entry     {"type":"message","id":"m1","parentId":null,   "message":{role:"user",…}}          ← 根
├─ entry     {"type":"message","id":"m2","parentId":"m1",   "message":{role:"assistant",…}}
├─ entry     {"type":"message","id":"m3","parentId":"m2",   "message":{role:"toolResult",…}}
├─ entry     {"type":"compaction","id":"c1","parentId":"m3","summary":"此前历史摘要…",
│            "firstKeptEntryId":"m12","tokensBefore":45123}                                      ← 折叠点
├─ entry     {"type":"message","id":"m12","parentId":"c1",  "message":{role:"user",…}}           ← 保留起点
│            …(m12 之后的保留消息,含后续 compaction 则再折一层)
├─ entry     {"type":"message","id":"m30","parentId":"m29", "message":{role:"user",…}}
├─ entry     {"type":"label","id":"l1","parentId":"m30","targetId":"m30","label":"checkpoint-A"} ← 书签
├─ entry     {"type":"branch_summary","id":"b1","parentId":"m30","fromId":"m31",
│            "summary":"分支里试过方案 X,失败原因是…"}                                           ← 离开的分支
├─ entry     {"type":"message","id":"m31","parentId":"b1",  "message":{role:"user",…}}           ← 新分支继续
└─ …每次 append 追加一行;重载时 parseSessionEntries(session-manager.ts:299)重建树
```

- 图上三处「非消息 entry」正是本章主角:compaction 折叠旧主线、branch_summary 折叠被放弃的分支、label 是用户书签——session-manager.ts:110-115 注释直言 "Label entry for user-defined bookmarks/markers on entries"。上下文重建时只有「沿 leaf 回溯路径」上的 entry 可见,旁支全靠摘要代表。
- /tree 在交互模式把同一份文件渲染成可导航树(slash-commands.ts:22,描述 "Navigate session tree (switch branches)";交互层在 interactive-mode.ts:3056 拦截 /tree),选中目标后调用 AgentSession.navigateTree(agent-session.ts:3105)完成「折去旧支、移叶子」。

## 4. 详细介绍

### 4.1 上下文重建:沿 parentId 回溯 + compaction 折叠

buildSessionContext(session-manager.ts:461)先沿 parentId 从 leaf 回溯到根,再经 buildContextEntries(session-manager.ts:418)处理路径上的 compaction:

```ts
// core/session-manager.ts:436-453
const compactionIdx = path.findIndex((entry) => entry.id === compaction.id);
if (compactionIdx < 0) {
	return path;
}

const contextEntries: SessionEntry[] = [compaction];   // 压缩点本身(摘要)保留
let foundFirstKept = false;
for (let i = 0; i < compactionIdx; i++) {
	const entry = path[i];
	if (entry.id === compaction.firstKeptEntryId) {
		foundFirstKept = true;
	}
	if (foundFirstKept) {
		contextEntries.push(entry);      // firstKept 之后的老消息才保留
	}
}
contextEntries.push(...path.slice(compactionIdx + 1));   // 压缩点之后原样保留
return contextEntries;
```

- 语义一句话:**compaction entry 占住历史位置,它之前的旧消息被丢弃,只留 firstKeptEntryId 之后的干净尾巴**;尾巴里若再有更新的压缩点,则递归再折一层——多次压缩在文件里就是串接的 compaction entry 链,回溯路径始终完整。丢弃发生在「重建上下文」这一步,文件本身一字未删。
- 重建产物 sessionContext.messages 直接回灌 agent.state.messages:自动压缩后(agent-session.ts:2351-2352)与换分支后(agent-session.ts:3277-3278)都走同一条重建路径,低层循环完全不感知树的形状。

### 4.2 分支、回溯与书签:换路时折 branchSummary

- 树内换分支(rewind/checkout):navigateTree(agent-session.ts:3105)先沿「旧 leaf → 共同祖先 → 目标」收集被放弃片段 collectEntriesForBranchSummary(branch-summarization.ts:108,调用点 agent-session.ts:3131-3135);若该分支值得留档,默认用一次独立 LLM 调用 generateBranchSummary(branch-summarization.ts:293,输入预算 = contextWindow − reserveTokens,:313)写摘要,再经 branchWithSummary 落成 branch_summary entry(session-manager.ts:1382-1407:type:"branch_summary",fromId 记「从哪条支路来」);最后移动叶子——有摘要时叶子落在摘要 entry 上,无摘要时直接 branch(newLeafId) 或 resetLeaf(agent-session.ts:3246-3268)。
- fork 开新文件:SessionManager.forkFrom(经 main.ts:342 forkSessionOrExit),新 header 的 parentSession 指向旧文件——分支跨文件,各文件内部仍是独立树。fork 继承的旧主线同样折成 branchSummary 消息(messages.ts:100 createBranchSummaryMessage),进上下文时包 BRANCH_SUMMARY_PREFIX/SUFFIX 的 <summary> 标签(messages.ts:19-24)。
- 书签:label 是真实树 entry(见 3 节图),targetId 指向被打标记的条目;appendLabelChange 在压缩/换分支后把 label 挂到摘要或目标上(agent-session.ts:3261、3273)。它只影响导航与展示,不参与 LLM 上下文。
- 生成的 branchSummary 消息在模型眼里是一条 role:"branchSummary" 的特殊消息(messages.ts:55-60),等价于告诉模型:「你曾在另一条路线上做过这些,现在回来了」。

### 4.3 压缩触发:_checkCompaction 的三情形

- 自动检查挂在每回合后处理链上:agent-session.ts:1141 由 _handlePostAgentRun 调用 _checkCompaction(实现在 :2125)。跳过条件很有讲究:设置关闭直接返回(:2127);aborted 消息不触发(:2130);**消息早于最近一次压缩边界不触发**(:2144-2149,防止压缩后旧 usage 立刻误触发第二次);溢出判断要求同模型(:2138-2139,换了更大窗口模型后旧错误不应再触发)。
- Case 1/2 溢出与可恢复截断(:2154-2195):isContextOverflow 判上下文溢出,isRecoverableLength 判「输出截断且原意未完成」。willRetry 取决于消息是否正常结束:正常完成的溢出只压缩不重试(:2161-2162);未完成的(截断/错误)则先把最后一条失败的 assistant 消息从 agent 状态摘除(:2191-2193),压缩后由 _handlePostAgentRun 返回 true 触发 agent.continue() 重试一次,_overflowRecoveryAttempted 防死循环(:2189,二次失败即放弃并报 "Context overflow recovery failed after one compact-and-retry attempt",:2165-2185)。
- Case 3 阈值(:2197-2228):usage 有效就用 calculateContextTokens 直接算;出错或零 usage 的消息用 estimateContextTokens 从最后一条有效 usage 起估算(compaction.ts:202,其后消息按 chars/4 估,图片按常量估,estimateTokens @266)。判据与默认参数:

```ts
// core/compaction/compaction.ts:132-136、235-238
export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
	enabled: true,
	reserveTokens: 16384,      // 给模型输出的预留
	keepRecentTokens: 20000,   // 压缩后保留的最近 token 预算
};

export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings): boolean {
	if (!settings.enabled) return false;
	return contextTokens > contextWindow - settings.reserveTokens;
}
```

- 三情形之外还有两条压缩入口:下一轮开始前——prepareNextTurn 钩子接 _compactBeforeNextAssistantResponse(agent-session.ts:542-559,同一判据,防「上一轮没事、这一轮开头就爆」);手动——/compact 或扩展调用(AgentSession.compact,agent-session.ts:1939;slash-commands.ts:39)。压缩全程异步并持 AbortController,压缩进行中不接受新 prompt。

### 4.4 下刀与摘要:findCutPoint + 独立 LLM 调用 + compaction entry

- prepareCompaction(compaction.ts:750)先定范围:末尾已是 compaction 则直接跳过(:754-756,说明 Pi 不允许连续两次空转压缩),否则范围 = 上次压缩的 firstKeptEntryId → 文件尾,并先记 tokensBefore(:776)。真正的切点由 findCutPoint(:403)决定:**从最新往回走,逐条累加估算 token,攒够 keepRecentTokens(默认 20k)后在最近的合法切点下刀**:

```ts
// core/compaction/compaction.ts:415-439(摘,注释为原文件注释)
// Walk backwards from newest, accumulating estimated message sizes
let accumulatedTokens = 0;
let cutIndex = cutPoints[0]; // Default: keep from first message (not header)

for (let i = endIndex - 1; i >= startIndex; i--) {
	const entry = entries[i];
	const messageTokens = sessionEntryToContextMessages(entry).reduce(
		(sum, message) => sum + estimateTokens(message),
		0,
	);
	if (messageTokens === 0) continue;
	accumulatedTokens += messageTokens;

	// Check if we've exceeded the budget
	if (accumulatedTokens >= keepRecentTokens) {
		// Find the closest valid cut point at or after this entry
		for (let c = 0; c < cutPoints.length; c++) {
			if (cutPoints[c] >= i) {
				cutIndex = cutPoints[c];
				break;
			}
		}
		break;
	}
}
```

- 合法切点只可能是 turn 边界:isTurnStartEntry(compaction.ts:338)只认 user/bashExecution/custom/branchSummary/compactionSummary 这类回合起点,assistant 与 toolResult 都不算;toolResult 永远不是切点,因为它必须紧跟所属 toolCall(isCutPointMessage,compaction.ts:308-321)。若预算把某个 turn 拦腰劈开(isSplitTurn),劈开处前半段会走第二次独立摘要 TURN_PREFIX_SUMMARIZATION_PROMPT(compaction.ts:835-848),给保留的后半段补「本回合开头发生了什么」,两段摘要最后合并成一个 compaction summary(compact(),compaction.ts:887-947)。
- 摘要是一次独立 LLM 调用,与主对话同供应商、独立计费:system 用专用 SUMMARIZATION_SYSTEM_PROMPT(buildSummarizationContext,compaction.ts:642-653),历史经 serializeConversation 成纯文本包进 <conversation> 标签(:686-693),增量压缩时旧摘要以 <previous-summary> 一并喂入做增量更新(:690-692);输出上限按 reserveTokens 比例掐死(:672-675),并校验「摘要请求不得调用工具」(:719-721)。产物除摘要文本外还自动附 readFiles/modifiedFiles 文件操作清单(compact() 结尾 :949-951,供结构化消费)。
- 落盘与回灌:摘要经 appendCompaction 写成 compaction entry(session-manager.ts:1098-1120,type:"compaction"、firstKeptEntryId=保留起点,另记 tokensBefore/usage/fromHook),同时生成 role:"compactionSummary" 的消息占住被丢历史的位置:

```ts
// core/messages.ts:11-17
export const COMPACTION_SUMMARY_PREFIX = `The conversation history before this point was compacted into the following summary:

<summary>
`;
```

- 重建时模型看到的是「compactionSummary 消息 + 保留的最近 20k」;文件里旧消息一行不少,只是不再参与上下文——折叠发生在读路径,不是写路径。

### 4.5 dynamic context:每轮可注入、可过滤的消息钩子

- 树与会话文件解决「跨轮持久」,而「每轮喂什么」由扩展的 context 事件掌管:它在每次 LLM 调用前触发、允许直接修改消息列表(extensions/types.ts:687-691,注册入口 on("context") @1275)。对照 02.05,这就是 RAG 与长期记忆的挂点——扩展可在每轮把检索结果作为消息注入,也可按主题把旧历史过滤出上下文,让窗口里只放当下需要的。
- 注入的持久化形态是 custom_message entry(session-manager.ts:135-141):内容在 buildSessionContext 时转成 user 消息进上下文,details 只给扩展自己看,display 控制 TUI 是否渲染;相比之下 custom entry 是纯扩展私有存储,永不进 LLM 上下文(session-manager.ts:94-108 注释明言 "Does NOT participate in LLM context")。三者分工:树 = 结构记忆、摘要 = 压缩记忆、context 钩子 = 工作记忆的实时编辑权。
- 压缩与换分支也各有对等钩子:session_before_compact 可取消压缩或整体替换压缩产物(agent-session.ts:2266-2297),session_before_tree 可取消换路或自定义分支摘要(agent-session.ts:3160-3187)——扩展若想用「结构化索引」代替「文本摘要」,在这两处接管即可(fromHook 字段标记扩展产物)。

## 6. 边界与坑

| 现象/坑 | 原因 | 处理 |
|---|---|---|
| 压缩后立刻又触发一次压缩 | 旧 usage 带的是压缩前的大窗口计数 | _checkCompaction 用最近 compaction 时间戳挡掉旧消息(:2144-2149) |
| 溢出恢复失败两次 | 一次压缩重试治不好根因(任务本身超窗) | Pi 放弃并报错(:2165-2185),换更大窗口模型或给用户减上下文 |
| 以为摘要把旧文件删了 | 折叠发生在读路径(buildContextEntries),文件只追加 | 排查历史直接看原始 JSONL;HTML 导出也保留完整树 |
| 切点砍在 assistant/toolResult 中间 | 切点只许 turn 边界;劈开 turn 会补二次前缀摘要 | 若摘要里见 "Turn Context (split turn)",说明该轮被拦腰折叠 |
| 把 branch_summary 当普通消息 | role:"branchSummary" 是特殊角色,来自被放弃分支 | 它是树导航产物,与文件系统分支无关 |
| fork 与 /tree 分不清 | fork 开新文件(parentSession 链),/tree 在同文件内移 leaf | 跨会话延续用 --fork/新建,同会话回退换路用 /tree |

- 边界提醒:本章的树与压缩是「窗口管理」的地基,但摘要质量、RAG 注入、结构化压缩默认都可由扩展接管(session_before_compact / session_before_tree / context 钩子)——扩展系统本身与钩子全清单留给 03 章;session-backends/sqlite-node 只是独立旁路后端,不改 JSONL 主路径(01 章已述)。

## 7. 总结

| 概念 | Pi 的落点 | 出处 |
|---|---|---|
| 会话存储 | 单 JSONL append-only 树,v3,entry {type,id,parentId,timestamp} | session-manager.ts:30/46/846/954 |

**思考题**:① 为什么切点必须落在 turn 边界,toolResult 为什么永远不能成为切点?② 溢出重试只给一次、失败即放弃——若你是设计者,会允许「换更大窗口模型后自动重试」吗,代价是什么?③ Pi 把被丢弃的历史全部留在文件里、只在读路径过滤,与「物理删除省空间」相比各自的坑在哪?

> [!note] 参考答案
> ① 若在 assistant 消息中间下刀,保留区会以半截思考/半截工具调用开头,模型既缺上文又可能看到孤立 toolResult(其 toolCall 已被丢弃),极易幻觉或重复执行;只许 turn 边界保证保留区从「新回合起点」开始自洽。toolResult 必须紧跟所属 toolCall,切在它前面会造成调用与结果分离,所以 isCutPointMessage(compaction.ts:308-321)把它排除。② 允许自动换大窗口重试看似贴心,但会让压缩逻辑与模型目录耦合、掩盖真正的问题(任务规模超出任何窗口),而且一次失败后立刻二次压缩同样烧 token;Pi 把决定权留给用户(换模型/减上下文),这是「主见且最小」取舍的延续。③ 保留全部历史:文件无限增长、每次重载重建索引的成本上升、旧内容长留磁盘(隐私/合规视角也是负担);物理删除:分支回溯与「压缩错了想恢复」的能力永久丢失。Pi 赌「可回溯 > 省空间」,代价由磁盘与重载时间承担——这也解释了它为何另起 sqlite-node 后端做搜索统计,而不是把主存储直接换成数据库。
