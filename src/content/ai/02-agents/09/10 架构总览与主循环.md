# 架构总览与主循环

> 02.09 蓝图六个对象里,Codex 是「Rust 单二进制的极简之美」,Hermes Agent 站在坐标系另一端:约 3900 行的单轮驱动函数、超过 9000 行的主循环文件、技能/记忆/网关全塞进同一个 Python 进程——「自我进化」的全部机制都要在这样一副躯体里跑起来。本章先给仓库地图与启动链,再钻进主循环,回答三个问题:Thought/Action/Observation 用什么协议编码?上下文怎么装进一次请求并防止超窗?安全基线铺在哪几层?答案集中在 agent/conversation_loop.py 与其周围的几个模块,所有行号为 2026-09 检出时点。

**学习目标**:学完本章,你将能够——

1. 说出 Hermes Agent 仓库的顶层布局,并把 02.01 的「模型+循环+工具」骨架映射到 agent/、tools/、gateway/ 等真实目录;
2. 沿「pyproject 入口 → hermes_cli/main.py → cli.py HermesCLI → _init_agent → AIAgent → agent_init.init_agent」指认完整启动链(带文件:行号);
3. 指出主循环的 while 条件、内层重试与结束路径,并解释为什么它是 function calling 编码而非 ReAct 文本;
4. 说清 system prompt 三层(stable/context/volatile)与 ContextEngine 压缩参数 0.75/3/6 的含义;
5. 列出安全基线的四个落点:上下文文件注入扫描、工具结果侧语义定界、审批/护栏回调、轨迹审计。

## 1. 概念:Python 全栈 Agent 的工程组织

- 一句话:Hermes Agent 是 Nous Research 用 Python 写成的「个人 Agent 全家桶」——对话主循环、内置工具、技能库、长期记忆、多平台网关、定时任务、评测脚本都在同一仓库(源码仓库顶层布局,2026-09 核证)。
- 顶层目录即架构地图:agent/(主循环与核心类)、hermes_cli/(CLI 入口与配置)、tools/(内置工具实现)、skills/ 与 optional-skills/(技能库,02 章)、gateway/ 与 tui_gateway/(多平台网关与终端 UI,04 章)、plugins/ 与 optional-mcps/(插件与 MCP server)、cron/(定时任务)、native/fts5_cjk/(会话全文检索的 C 扩展,03 章)、providers/(模型供应商)、evals/ 与 tests/(评测与测试)。
- 与 02 OpenAI Codex 对照(只引其 README 已核证信息):Codex 用 Rust 把引擎打成单二进制、外围套 TS;Hermes 用解释型 Python 把「引擎+网关+技能+记忆」装进同一进程——工程形态的差异,本质是「分发与性能优先」与「功能密度与迭代速度优先」的取舍。
- 一个容易踩的坑:run_agent.py 里的大类 AIAgent 与模块级函数并存,真正的主循环逻辑被抽到 agent/conversation_loop.py 的模块级函数(以 agent 为第一参数),读代码时别只盯类方法。

## 2. 为什么这样设计:解释型全栈换「功能密度」

- Hermes 的卖点不在单次推理性能,而在「自我进化」闭环(05 章):技能按文件系统声明、记忆跨会话沉淀、评审后台异步跑——这些机制用同一种语言平铺在循环周围,改动成本最低;Python 生态(LLM SDK、MCP、SQLite/FTS5 绑定)让每个机制都有现成零件。
- 全栈同构的代价是「大」:AIAgent.__init__ 是代码库最长的方法之一(60+ 参数、约 1400 行属性初始化,agent/agent_init.py:1-7 头注自述),所以 Hermes 的工程美德是「命名与分层」:顶层目录即领域,超长方法整段抽成模块级函数(init_agent、run_conversation 同款手法),函数名即文档。

## 4. 详细介绍

### 4.1 启动链:入口注册到循环真身

入口注册在 pyproject.toml:391-393,`hermes` 与 `hermes-agent` 指向两个不同 main:

```python
# pyproject.toml:392-393([project.scripts]:控制台命令 → 模块:函数)
hermes = "hermes_cli.main:main"
hermes-agent = "run_agent:main"
```

后续每一环(行号均已核证):

- hermes_cli/main.py:13526 def main()——早启动守卫(UTF-8、清理)、快速路径与 argparse 子命令分发;chat 子命令经 set_defaults(func=cmd_chat) 后委托 cli.py:21761 def main(...);
- cli.py:5191 class HermesCLI(CLIAgentSetupMixin, CLICommandsMixin, CLIBillingMixin)——交互与单轮参数的实际驱动者;TUI 主渲染循环在 cli.py:18221 def run;

- run_agent.py:467 class AIAgent 是「大对象」:会话状态、消息历史、预算、护栏、压缩器全挂在它身上;__init__ 主体被抽到 agent/agent_init.py:536 init_agent(agent_init.py:1-7 头注自述,「AIAgent.__init__ is one of the longest methods in the codebase」);工具装载在 agent_init.py:1625-1634:agent.tools = _ra().get_tool_definitions(enabled_toolsets=...) 并生成 agent.valid_tool_names 集合——它就是主循环校验工具名的白名单;

### 4.2 主循环:function calling 编码的 Thought/Action/Observation

主循环条件(注意 `_budget_grace_call` 给预算耗尽后的「最后一次机会」):

```python
# agent/conversation_loop.py:2289(每轮 = 一次 LLM 调用 + 工具执行或收尾)
while (api_call_count < agent.max_iterations and agent.iteration_budget.remaining > 0) or agent._budget_grace_call:
```

轮前序在 conversation_loop.py:2110 调 build_turn_context(实现在 agent/turn_context.py:572):会话恢复、system prompt 恢复/构建、preflight 压缩、崩溃持久化;preflight 压缩超时抛 PreflightCompressionTimedOut,由 :2133 捕获按 fail-closed 处理。内层 API 重试:conversation_loop.py:3338 while retry_count < max_retries:。

**编码协议**:循环内没有 ReAct 的「Thought:」文本模板——推理不编码进对话文本,模型直接输出结构化工具调用,先做名字与参数校验:

```python
# agent/conversation_loop.py:7717-7726(工具名校验:白名单在 agent_init.py:1632-1634 生成)
for tc in assistant_message.tool_calls:
    if tc.function.name not in agent.valid_tool_names:
        repaired = agent._repair_tool_call(tc.function.name)
        if repaired:
            print(f"{agent.log_prefix}🔧 Auto-repaired tool name: '{tc.function.name}' -> '{repaired}'")
            tc.function.name = repaired
invalid_tool_calls = [
    tc.function.name for tc in assistant_message.tool_calls
    if tc.function.name not in agent.valid_tool_names
]
```

校验分三层:名字去幻(_repair_tool_call 定义在 run_agent.py:5561,把「幻觉名」修回真实名);整批仅含非法调用才计 strike、三次即停(同段注释 :7727-7737,混合批只对该条报错、合法调用照常执行);参数 JSON 的修复兜底走 _repair_tool_call_arguments(conversation_loop.py:1543)。校验通过后 :8114 agent._execute_tool_calls(...)(run_agent.py:9066)做分发:批被切成并行安全段与顺序屏障(危险命令、clarify、写冲突由 agent/tool_dispatch_helpers.py 规划),再进 middleware 链与授权分发。

**Observation 回流**:工具结果经 tool_dispatch_helpers.py:586 make_tool_result_message 构造为 role:"tool" 消息,按 tool_call_id 与 assistant 消息配对回灌历史,下一轮原样送模型——没有文本化转换:

```python
# agent/tool_dispatch_helpers.py:621-627(观察 = 标准 tool 角色消息 + 调用 id 配对)
message = stamp_message_timestamp({
    "role": "tool",
    "name": name,
    "tool_name": name,
    "content": wrapped,
    "tool_call_id": tool_call_id,
})
```

高风险的 web_extract/web_search/browser_*/mcp_* 结果还会被包上「不可信数据」语义定界符(同函数 docstring :597-602)——这已是 4.4 的防线。结束路径:assistant 消息不再带 tool_calls 时,conversation_loop.py:8345-8351 取 final_response = assistant_message.content or "" 收尾返回;护栏要求停下则 :8125-8127 以 guardrail_halt 退出回合。工具副作用落地前先 _flush_messages_to_session_db(:8066),崩溃后可恢复。

### 4.3 上下文三层与压缩

system prompt 每轮首调 conversation_loop.py:993 _restore_or_build_system_prompt:优先从 SessionDB 恢复上一轮缓存的提示词(维持 provider prefix-cache),否则重建并持久化。组装链:run_agent.py:5355 _build_system_prompt → agent/system_prompt.py:1036 build_system_prompt → :435 build_system_prompt_parts,三层有序缓存(源码 docstring 原样):

```python
# agent/system_prompt.py:436-451(docstring:三层缓存 + 「会话中段不重渲」铁律)
"""Assemble the system prompt as three ordered cache tiers.

Returns a dict with three keys:
  * ``stable``   — the cross-session-stable prefix, through the coding
    operating brief when a workspace snapshot follows.
  * ``context``  — the workspace snapshot followed by the remaining
    session-stable guidance, context files, and caller-supplied
    system_message.
  * ``volatile`` — skills index, memory snapshot, user profile,
    external memory provider block, timestamp line.

Joined into a single string by :func:`build_system_prompt` and
cached on ``agent._cached_system_prompt`` for the lifetime of the
AIAgent.  Hermes never re-renders parts of this string mid-
session — that's the only way to keep upstream prompt caches
warm across turns.
"""
```

压缩策略的抽象在 agent/context_engine.py:89 class ContextEngine(ABC),生命周期 update_from_response → should_compress → compress;默认参数即「0.75/3/6」:

```python
# agent/context_engine.py:121-123(触发阈值 = 上下文窗 75%;头 3 条 / 尾 6 条非 system 消息逐字保留)
threshold_percent: float = 0.75
protect_first_n: int = 3
protect_last_n: int = 6
```

两个触发点:①回合序 preflight(在 build_turn_context 内,:2110,超时由 :2133 兜底);②每轮 API 前 :3034-3054 条件块——compression_enabled 且非冷却且 _compressor.should_compress(request_pressure_tokens)(:3038);本地模型先试 _maybe_grow_local_window(:3047)扩窗躲压缩,仍超阈才在 :3116 执行 messages, active_system_prompt = agent._compress_context(...)(实现于 run_agent.py:8565)。执行前 :2960-3054 有逐 token 估算与防抖注释(失败冷却、attempt 上限、定时器)。

### 4.4 安全基线:四层落点

- **上下文文件注入扫描**:AGENTS.md/.cursorrules/SOUL.md 在进 system prompt 之前先扫威胁,命中即 block-with-placeholder——「the actual content never reaches the system prompt」(agent/prompt_builder.py:50-57 头注);扫描实现 :112 _scan_context_content,模式库是 tools/threat_patterns.py:212 scan_for_threats(content, scope="context"),同一份库被记忆工具扫描与工具结果侧共用;
- **工具结果侧语义定界**:间接注入的主要通道是网页与 MCP 返回内容,定界符包装(tool_dispatch_helpers.py:597-602)改变模型对内容的解读方式,而非只靠正则命中;
- **工具权限回调与护栏**:cli.py:16534 _approval_callback 把危险命令升级给人确认;agent/tool_guardrails.py:413 ToolCallGuardrailController 监控重复失败/不进展的调用,halt 决策在 conversation_loop.py:8125-8127 以 guardrail_halt 退出回合;工具可用性本身由 enabled_toolsets 决定(agent_init.py:1625);
- **轨迹与审计**:agent/trajectory.py:30 save_trajectory 写 ShareGPT JSONL;每轮消息在工具副作用前增量落 SessionDB(conversation_loop.py:8066),崩溃可恢复、事后可审计。

## 6. 边界与坑

| 症状 | 原因 | 处理 |
|---|---|---|
| 以为 Hermes 是 ReAct 文本循环 | 02.01 的骨架是概念模型,工程实现是 function calling | 认准 tool_calls / role:"tool";推理在 provider 侧完成 |
| 行号对不上笔记 | 仓库持续演进,行号随检出漂移 | 以当前检出为准,先搜函数名再对行号 |
| 找不到「主循环」 | run_conversation 有两层:类方法薄转发 + 模块级真身 | 薄转发在 run_agent.py:9235,真身在 conversation_loop.py:2026 |
| 压缩把开头结尾也砍了 | 误以为压缩是无差别裁剪 | protect_first_n=3 / protect_last_n=6 只保首尾,压缩动中段 |
| toolsets.py 与 toolset_distributions.py 混淆 | 后者名字像运行时组件 | 前者才是运行时工具集定义;后者是批量 eval 的抽样配置,与主循环无耦合 |

边界提醒:本章只覆盖 CLI 单会话路径;多平台复用同一核心、terminal backend 沙箱、MCP 注册在 04 章;技能与记忆的注入细节分别在 02/03 章。「系统提示词会话中段绝不重渲」保的是上游 prompt cache,代价是会话内改了 SOUL.md 不生效、需重启会话——这是设计取舍,不是 bug。

## 7. 总结

| 概念 | 一句话 | 出处 |
|---|---|---|
| 工程形态 | Python 全栈全家桶:循环/工具/技能/记忆/网关同仓库 | 仓库顶层布局 |
| 启动链 | pyproject → hermes_cli/main.py → HermesCLI → _init_agent → AIAgent → init_agent → run_conversation | pyproject.toml:392-393、cli_agent_setup_mixin.py:373-525、agent_init.py:536 |
| 主循环 | while 双条件(迭代次数 × 预算),每轮 = LLM 调用 + 工具执行 | conversation_loop.py:2289 |
| T/A/O 编码 | 纯 function calling:tool_calls 校验 → 执行 → role:"tool" 回流,非 ReAct 文本 | conversation_loop.py:7717、tool_dispatch_helpers.py:621 |
| 上下文 | system prompt 三层 stable/context/volatile,中段不重渲保 prompt cache | system_prompt.py:436-451 |
| 压缩 | ContextEngine ABC,阈值 0.75、保护首 3 尾 6 | context_engine.py:89、121-123 |
| 安全基线 | 注入扫描(提示词前)、工具结果定界、审批/护栏、轨迹审计 | prompt_builder.py:50-57、tool_guardrails.py:413、trajectory.py:30 |

**思考题**:① 为什么 Hermes 宁可「改了 SOUL.md 本会话不生效」也要坚持中段不重渲 system prompt?② protect_first_n=3 与 protect_last_n=6 分别保护哪两类消息,砍掉它们各自会坏掉什么?

> [!note] 参考答案
> ① prefix-cache 命中要求提示词前缀逐 token 稳定:中段任何重渲都会让上游缓存整体失效,长会话每轮重复多付 token 成本;而缓存收益是每轮累计的、重渲成本是每轮重复的,所以「不重渲 + 改了重启会话」在账上划算。② 首 3 条保护 system prompt 之后紧邻的早期指令与上下文锚点——开头位置是模型注意力最强处,砍掉等于重排「优先级」;尾 6 条保护最近几轮完整的调用-结果对——tool 消息靠 tool_call_id 与 assistant 调用配对(4.2),砍掉中段会制造孤儿 tool 消息,下一轮推理立刻失真,这正是出站前要 scrub 孤儿序列的原因。
