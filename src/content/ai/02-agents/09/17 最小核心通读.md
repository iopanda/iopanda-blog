# 最小核心通读

> 04 OpenCode 用 TypeScript 插件生态证明了「能力外置」的路线;Pi 把这条路走到尽头——官方自述 minimal terminal coding harness,默认只给模型四个工具,刻意不内置 MCP、子代理、plan mode、权限弹窗,「需要什么就写扩展,或让 Pi 自己写」。作者 Mario Zechner(libgdx 作者)把 02.01 的最小 ReAct 骨架落成「两个主循环 + 四件工具 + 一段极简 system prompt」,本章通读整个 monorepo,验证内核被压到最小之后,循环本身还剩哪些环节。

**学习目标**:学完本章,你将能够——

1. 说出 monorepo 十个 npm 包的分工边界,指出编码 Agent 内核由哪几个包串成、主循环宿主在哪个文件;
2. 沿 cli.ts → main.ts → AgentSession 的启动链报出每步关键行号,说出交互/print/RPC 三种模式在哪分叉;
3. 复述双层主循环——低层 agent-loop.ts 的外层 follow-up + 内层工具批、高层 agent-session.ts 的重试/压缩/续跑后处理——并对应到 02.01 的循环环节;
4. 说出默认四工具 read/bash/edit/write 各自的 TypeBox schema 位置,解释参数校验失败如何转成 isError 工具结果;
5. 解释 AgentToolResult 的 content/details 双通道与 system prompt 极简设计的意图,并给出自己的判断。

## 1. 概念:把 02.01 骨架装进十个包

- 02.01 的最小骨架是「模型 + 循环 + 工具 + 上下文」;Pi 的工程化回答是 npm workspaces monorepo(root package.json:5-13 声明 `packages/*` 与 `packages/session-backends/*`),十个包各管一段:

| 包(目录) | npm 包名 | 职责 | 02.01 对应 |
|---|---|---|---|
| ai | @earendil-works/pi-ai | 统一多供应商 LLM API、TypeBox 工具声明与校验、模型目录 | 模型通道 |
| agent | @earendil-works/pi-agent-core | 通用 agent 运行时:低层主循环、事件流、AgentTool 类型 | 循环(低层) |
| coding-agent | @earendil-works/pi-coding-agent | CLI + 高层 AgentSession、会话 JSONL、四工具、system prompt | 循环(高层)+ 工具 |
| tui | @earendil-works/pi-tui | 差分渲染终端 UI 库 | 人机界面 |
| protocol | @earendil-works/pi-protocol | 远程会话的 CBOR 协议 | 通道扩展 |
| client | @earendil-works/pi-client | 远程会话客户端(帧化 CBOR 字节) | 通道扩展 |
| server | @earendil-works/pi-server | experimental 服务端包 | 通道扩展 |
| session-backends/sqlite-node | @earendil-works/pi-session-backend-sqlite-node | SQLite 会话后端(独立旁路,非主路径) | 记忆存储 |
| telemetry | @earendil-works/pi-telemetry | 供应商无关遥测契约与 schema 工具 | 观测 |
| evals | @earendil-works/pi-evals | 评测 | 评测 |

- 内核只占三包一条链:**ai 声明与校验 → agent 跑通用循环 → coding-agent 装具体工具与高层决策**;tui/telemetry/session-backends/evals 都是绕内核的附件。root package.json:16 的 build 脚本按 tui→telemetry→ai→agent→sqlite-node→protocol→client→server→coding-agent 的顺序执行,这个顺序本身就是依赖关系的实证。
- 分层的关键收益:agent 包不 import 任何 coding-agent 代码——换一套工具、换一个宿主(比如远程 RPC 服务端)就复用同一条低层循环,这正是「内核小、可复用」的工程形态。

## 2. 为什么这样设计:minimal terminal coding harness

- Pi 的定位是「极简终端编码壳」:coding-agent 的 package.json description 自述 "Coding agent CLI with read, bash, edit, write tools and session management"——能力清单里只有四个工具与会话管理,没有权限弹窗、没有内置沙箱。
- 「不需要就不建」的直接后果是**主循环没有等待分支**:不需要处理审批等待(02.04 的人确认环节被整体外包给扩展/容器),不需要子代理调度状态机(02.06 的编排被降级为普通工具调用),plan mode 也只是一个 example 扩展。循环只需要「思考 → 工具 → 观察 → 再思考」一条直路,于是低层循环单文件 agent-loop.ts 只有 803 行,可以整段读完。
- 作者在博客(2025-11-30)里自述构建「有主见且最小」的编码 Agent 的取舍,核心判断是:功能面越大,默认行为越难预测、维护成本越高;与其内置一堆 80% 用户用不上的功能,不如把钩子(扩展系统,03 章)做好——这些一手材料留到 04 章细读。

## 3. 作用:一次 pi 命令的全局地图

```text
pi "给 main.ts 加错误处理"
packages/coding-agent/src/cli.ts:1-13        极薄入口(全文件 21 行):设 env、configureHttpDispatcher、调 main
└─ main.ts:561 main():parseArgs(602) → 子命令短路(570-631) → resolveAppMode(633) → runMigrations(648)
   ├─ main.ts:675   createSessionManager(工厂在 :352,决定会话目录 ~/.pi/agent/sessions/<编码后 cwd>/)
   ├─ main.ts:731   createAgentSessionServices(SettingsManager / ModelRuntime / 扩展 / 技能)
   ├─ main.ts:796   buildSessionOptions(模型 / thinking / 工具)→ main.ts:816 createAgentSessionFromServices → AgentSession
   ├─ main.ts:840   createAgentSessionRuntime(包成可 /reload 的 runtime)
   └─ 按 appMode 分派:main.ts:929 runRpcMode | :931 new InteractiveMode | :965 runPrintMode
```

- 三种模式持有**同一个 AgentSession**(会话、压缩、扩展逻辑只写一份),区别只在人机接口:RPC 面向编辑器/IDE 的远程 CBOR 会话,InteractiveMode 是全屏 TUI,print 模式是一次性问答、答完带退出码返回——「同一引擎、多个人机接口」与 02.08/02 的观察一致。
- 装配都在 main() 里按序完成,而真正的循环不在 main.ts——启动链末尾只交付一个 runtime 对象,主循环在更深处(4.2 节)。

## 4. 详细介绍

### 4.1 入口:21 行的 cli.ts + 978 行的 main.ts

```ts
// packages/coding-agent/src/cli.ts:8-13(cli.ts 全文件仅 21 行)
import { APP_NAME } from "./config.ts";
import { configureHttpDispatcher } from "./core/http-dispatcher.ts";
import { main } from "./main.ts";

process.title = APP_NAME;
```

- 真入口 `export async function main(args: string[], options?: MainOptions)` 在 main.ts:561。main() 先把参数翻译成 AppMode(main.ts:633 resolveAppMode 依据 stdin/stdout 是否 TTY 与参数),跑迁移(main.ts:648 runMigrations),再依次创建会话管理器(675)、服务(731)、AgentSession(816)——816 行的 createAgentSessionFromServices 定义在 core/agent-session-services.ts:202,是「核心对象出生点」。
- AgentSession(core/agent-session.ts,约 3500 行)是 coding-agent 的心脏:内部持 sessionManager(JSONL 会话)、settingsManager、modelRuntime、extensionRunner,并再持一个低层 `Agent`(agent 包 agent.ts)——高/低两层对象,对应下面两层循环。

### 4.2 双层主循环:通用 runLoop + AgentSession 后处理

低层循环在 **packages/agent/src/agent-loop.ts:156**(runLoop,全文件 803 行),只懂「消息与工具批」,不懂会话:

```ts
// agent-loop.ts:156-261 骨架(节选,行号对应实际文件)
while (true) {                                    // :171 外层:follow-up 消息续跑
  let hasMoreToolCalls = true;
  while (hasMoreToolCalls || pendingMessages.length > 0) {   // :175 内层:工具批循环
    if (lastCompletedTurn) {
      const nextTurnSnapshot = await config.prepareNextTurn?.(lastCompletedTurn); // :177 压缩钩子
      /* …currentContext/config 按快照更新… */
    }
    /* …pendingMessages 注入 context.messages… */
    const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFunction); // :212
    if (message.stopReason === "length") {        // 截断 → 整批工具调用判失败(:232 failToolCallsFromTruncatedMessage)
      /* …否则 executeToolCalls(:409)… */
    }
    /* …turn_end 事件;shouldStopAfterTurn(:252) 决定是否整轮终止… */
  }
  const followUpMessages = (await config.getFollowUpMessages?.()) || []; // :261
  if (followUpMessages.length) { pendingMessages = followUpMessages; continue; }
  break;
}
```

- 内层循环=02.01 的「Action → Observation」:模型一次响应可带多个 toolCall,工具们串行(:431)或并行(:487)执行,结果消息 push 回 context 后再请模型;`terminate` 置 true 才提前停批。外层循环=多轮 follow-up(steer/follow-up 消息排队后继续)。工具执行的细节链:prepareToolCall(:607,工具不存在→立即错误结果 :615-621)→ validateToolArguments(:625)→ beforeToolCall 守卫(:626)→ executePreparedToolCall(:677,onUpdate 推 tool_execution_update)→ finalizeExecutedToolCall(:720)→ afterToolCall(:731)→ createToolResultMessage。
- 高层循环在 **packages/coding-agent/src/core/agent-session.ts:1105**,每次用户 prompt 是一次 `agent.prompt`,随后进入后处理循环:

```ts
// core/agent-session.ts:1105-1148(节选)
private async _runAgentPrompt(messages: AgentMessage | AgentMessage[]): Promise<void> {
  this._isAgentRunActive = true;
  try {
    await this.agent.prompt(messages);
    while (await this._handlePostAgentRun()) { await this.agent.continue(); } // 后处理决定是否再跑
  } finally { /* …flush 队列、_emitAgentSettled… */ }
}
private async _handlePostAgentRun(): Promise<boolean> {
  const msg = this._lastAssistantMessage; // …
  if (this._isRetryableError(msg) && (await this._prepareRetry(msg))) return true; // :1127 自动重试
  if (await this._checkCompaction(msg)) return true;   // :1141 压缩自动触发(02 章主角)
  return this.agent.hasQueuedMessages();               // :1147 还有排队消息就续跑
}
```

- 分界一句话:低层循环不知道「会话、压缩、UI」,高层 AgentSession 在每回合结束后拍板——要不要重试(上下文溢出/可恢复截断)、要不要压缩(_checkCompaction 实现在 :2125)、还有没有排队消息;返回 true 就 `agent.continue()` 再跑一轮,把「决策」留在 coding-agent、「执行」留在 agent 包。压缩钩子 prepareNextTurn 也反向接进低层 :177,供下轮开始前改写上下文(agent-session.ts:542 `_compactBeforeNextAssistantResponse`)。

### 4.3 默认四工具:read / bash / edit / write,TypeBox 声明参数

```ts
// core/tools/index.ts:164-171 —— 默认恰四件套
export function createCodingToolDefinitions(cwd: string, options?: ToolsOptions): ToolDef[] {
  return [ createReadToolDefinition(cwd, options?.read), createBashToolDefinition(cwd, options?.bash),
           createEditToolDefinition(cwd, options?.edit), createWriteToolDefinition(cwd, options?.write) ];
}
```

每个工具的参数是一个 TypeBox schema,既是给 LLM 的 function calling 声明,也是运行时校验依据(02.04/02 的「schema 即契约」):

```ts
// tools/read.ts:21-25(其余:write.ts:15-18、bash.ts:42、edit.ts:45)
const readSchema = Type.Object({
  path: Type.String({ description: "Path to the file to read (relative or absolute)" }),
  offset: Type.Optional(Type.Number({ description: "Line number to start reading from (1-indexed)" })),
  limit: Type.Optional(Type.Number({ description: "Maximum number of lines to read" })),
});
```

- 定义与执行分离:createXToolDefinition(parameters + execute + renderCall/renderResult)经 wrapToolDefinition(core/tools/tool-definition-wrapper.ts:5)包成运行时 AgentTool(agent 包 types.ts:387:parameters 泛型 TSchema,execute 抛错即失败)。
- **校验失败不是进程异常,而是工具结果**:prepareToolCall 里 validateToolArguments(agent 包 agent-loop.ts:625,实现在 packages/ai/src/utils/validation.ts:317:clone → 规范化 null → Value.Convert 强转 → validator.Check)抛错后,被 catch(agent-loop.ts:668-673)转成带 isError:true 的立即结果回灌模型——模型读到「参数不合法」的报错后可以自我修正重试。execute 永远只收到校验后(可能已被 coerce)的参数,工具内部不需要再写类型 if。

### 4.4 结果双通道:content 给模型,details 给 UI

```ts
// packages/agent/src/types.ts:362-371
export interface AgentToolResult<T> {
  content: (TextContent | ImageContent)[];   // 回给模型:文本/图片
  details: T;                                // 给 UI/日志的结构化细节
  usage?: Usage;
  addedToolNames?: string[];
  terminate?: boolean;                       // 置 true 提前停整批
}
```

- 两通道的归宿不同:content 经 createToolResultMessage(agent-loop.ts:399)存成 `{role:"toolResult", toolCallId, toolName, content, details, isError, timestamp}` 消息进会话,再随 convertToLlm 回模型;details 同存消息并经 tool_execution_end 事件带出,供 TUI/日志消费——bash 的完整输出落盘路径 fullOutputPath、read 的 truncation 截断信息都只在 details 侧(另有 renderCall/renderResult 供 TUI 直接渲染)。
- 为什么分离:模型上下文每一 token 都是窗口与成本(02.05);「界面装饰信息」与「模型推理必需信息」分开后,details 再大也不挤上下文——read 返回 2000 行文件时,content 只放截断后的文本与续读提示(read.ts:295-327),完整内容留给 UI 侧分页查看。

### 4.5 system prompt:刻意极简,追加而非改写

```ts
// core/system-prompt.ts:128-133 与 166(节选)
let prompt = `You are an expert coding assistant operating inside pi, a coding agent harness. You help users by reading files, executing commands, editing code, and writing new files.

Available tools:
${toolsList}
…`;
prompt += `\nCurrent working directory: ${promptCwd}`;
```

- 模板只有「身份 + 工具列表(每工具一行,来自工具自报的 promptSnippet,如 read.ts:27)+ 按工具集生成的指南 + cwd」;固定指南仅两条——"Be concise in your responses"、"Show file paths clearly when working with files"(system-prompt.ts:123-124)。
- 项目上下文(AGENTS.md/CLAUDE.md 等包成 `<project_context><project_instructions>` 区块)、skills、`--append-system-prompt` 全部是**追加区块**,不修改模板本身——模板保持可整段背诵的长度。对照 02.02:Pi 赌「常驻指令越少越好,把上下文位置留给真实对话与工具结果」。

## 6. 边界与坑

| 现象/坑 | 原因 | 处理 |
|---|---|---|
| 本地行号与讲义不一致 | 讲义是 2026-09 检出快照,仓库每天在变 | 用 grep/search 重定位;方法比行号可靠 |
| 以为主循环只有一个文件 | 实际是 agent 包 + coding-agent 包两层 | 记分界:agent-loop.ts 管消息与工具批,agent-session.ts 管回合后决策 |
| 校验失败看起来像「工具出错」 | 设计如此:isError 结果回灌模型供自我修正 | 排查看 isError 与 tool_execution_update/end 事件,别当进程崩溃 |
| 以为 execute 收到的就是模型原参 | Value.Convert 在 Check 前强转 | execute 拿到的是规范化/coerce 后参数(数字字符串可能已变 number) |
| 把 sqlite-node 当会话主存储 | 主路径是 JSONL 追加树,sqlite 是旁路后端 | 会话 JSONL 是 02 章主角;sqlite 仅服务独立搜索/统计 |
| 「四包」与「十包」两种说法 | 规划口径 vs 实际 workspaces | 以实际检出的 root package.json:5-13 与各包 package.json 为准 |

- 边界提醒:本章只通读「内核最小集」,会话树、压缩、扩展系统都只给了钩子位置;02 章沿 JSONL 会话与 _checkCompaction(agent-session.ts:2125)展开,03 章再讲钩子上挂什么。

## 7. 总结

| 概念 | Pi 的落点 | 出处 |
|---|---|---|
| monorepo | 十包分工,内核链 ai→agent→coding-agent | root package.json:5-13、:16 |
| 启动链 | cli.ts(21 行)→ main.ts:561 → 675 → 816 → runtime → 三模式 | main.ts:675/731/816/840/929-965 |
| 双层主循环 | 低层 runLoop(工具批+follow-up)∥ 高层后处理(重试/压缩/排队) | agent-loop.ts:156、agent-session.ts:1105/1120 |
| 默认四工具 | read/bash/edit/write,TypeBox 声明参数 | tools/index.ts:164、read.ts:21 |
| 校验转结果 | Value.Convert+Check 失败 → catch → isError 工具结果 | validation.ts:317、agent-loop.ts:625/668 |
| 结果双通道 | content→模型,details→UI/日志 | types.ts:362 |
| system prompt | 身份+工具列表+两条指南+cwd,其余一律追加 | system-prompt.ts:128/123/166 |

**思考题**:① 低层 runLoop 为什么把「截断(length)」单独拎出来整批判失败,而不是让工具逐个试跑?② content/details 若不分离,read 一个 2000 行文件会发生什么?③ 「内核最小化」把权限弹窗、子代理都挪出主循环——主循环因此少了什么分支,又把这部分成本转嫁给了谁?

> [!note] 参考答案
> ① 截断意味着模型的 toolCall 序列根本没生成完(输出窗口耗尽),这批调用是残缺的、执行了也是浪费,还可能执行到一半的语义错误动作;整批判失败并回灌错误,让模型在完整窗口里重发,比「部分执行 + 猜测」更安全。② 2000 行全文都会进模型上下文:read 一次消耗约等于几千 token,再叠加后续回复的预算,几分钟就能撑爆窗口触发压缩;分离后 content 只放截断文本与续读提示,details 承载全量供 UI 分页。③ 少了审批等待、子代理调度、plan 状态机等分支,主循环变成可整段读完的直路;成本转嫁给三处——扩展作者(自己实现权限门/子代理,03 章)、宿主进程(信任模型外置到容器,04 章)、以及用户(功能要靠拼装与发现,05 章对比)。
