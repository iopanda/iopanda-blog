# 沙箱与执行模型

> 02 章讲过,模型手里最重的工具是 exec_command——一条由模型现写的 shell 命令;本章回答「凭什么让它在你的机器上跑」。Codex 的答案是把「想要什么」与「怎么限制」拆成两层:上层 SandboxPolicy 只表达意图,下层 Seatbelt、bwrap+seccomp、Windows 受限令牌各自在三平台落地。这就是 02.04/06「权限边界」最硬核的一半:策略看得见,平台兜底看不见。

**学习目标**:学完本章,你将能够——

1. 说出 SandboxPolicy 的四个变体及语义,解释为什么常说「三态」而源码里是四态;
2. 讲清「策略-平台分离」:同一策略如何映射到 macOS Seatbelt、Linux bwrap+seccomp 与 Windows 受限令牌;
3. 复述 macOS 策略里 `(deny default)` 与 `(require-not ...)` 如何联手保护 .git/.codex;
4. 说明 Linux 双层结构(bwrap 外层建文件系统视图、seccomp 内层管网络)与 Windows 受限令牌的能力边界;
5. 描述「执行 → 拒绝检测 → escalation 升级 → 放宽重试」管线,并解释「deny-read 禁止裸奔」不变量。

## 1. 概念:沙箱三态与「策略-平台分离」

- 概念出处:02.04/06 权限边界讲过「最小权限 + 白名单」;沙箱是它的执行层落地——在操作系统层面把进程的读、写、网络能力削到策略允许的最小集,即使模型被提示注入带偏(02.02/06),命令也没有越界能力(呼应 02.04/04 代码执行型工具的风险)。
- 设计骨架一句话:协议层只声明意图,平台层各自翻译。`SandboxPolicy` 是序列化形态(legacy 兼容),运行时先把它转成平台无关的 `FileSystemSandboxPolicy`(protocol/src/permissions.rs:218-230:kind 为 Restricted/Unrestricted/ExternalSandbox,条目为 {path, access: Read/Write/Deny}),再由每个平台后端翻译成自己的机制;`SandboxPolicy::WorkspaceWrite` 展开为条目在 permissions.rs:2282 `legacy_runtime_file_system_policy_for_cwd`。

## 2. 为什么:模型生成的 shell 命令不可信

- 攻击面来自提示注入:仓库里一段 README 就可能诱导模型去读 ~/.ssh 或删文件。审批只能拦「看起来危险」的命令,模型无法预见所有间接危害,所以要第二道防线——即使命令真被执行,权限也已被削过。
- 只靠策略文本不够:macOS 的 Seatbelt 语言、Linux 的 namespace/seccomp、Windows 的 ACL 机制完全不同,必须逐平台写翻译器;策略与平台分离后,平台翻译出错只让单一机制失效,不会让策略语义漂移,新增平台也只需补一个后端。

## 3. 作用位置:一次 exec_command 的沙箱化路径

```text
exec_command / apply_patch 等工具(Sandboxable)
  → 询问策略:escalate_on_failure / sandbox_permissions(core/src/tools/sandboxing.rs:344)
  → SandboxManager::transform 把命令包上平台沙箱前缀(sandboxing/src/manager.rs:338-489)
  → ExecRequest 统一规格(core/src/sandboxing/mod.rs:49-74)
  → 平台执行:macOS sandbox-exec -p <策略> / Linux codex-linux-sandbox / Windows helper exe
  → 退出后拒绝检测(denial.rs)→ 疑似被沙箱拒绝?→ 请求审批升级 → 放宽后重试
```

- 与审批的分工(04 章细讲):审批决定「要不要跑」,沙箱决定「跑起来能碰到什么」;两者在 exec_policy.rs 与 tools/sandboxing.rs 的交界汇合(`prompt_is_rejected_by_policy`,exec_policy.rs:48-238)。

## 4. 详细介绍

### 4.1 策略层:SandboxPolicy——「三态」实为四变体

- 定义于 protocol/src/protocol.rs:1066-1118,文档注释自称 "Determines execution restrictions for model shell commands"(protocol.rs:1066):

```rust
#[serde(tag = "type", rename_all = "kebab-case")]
pub enum SandboxPolicy {
    #[serde(rename = "danger-full-access")]
    DangerFullAccess,             // 零限制,注释:Use with caution
    #[serde(rename = "read-only")]
    ReadOnly { network_access: bool },          // 只读;network_access 默认 false
    #[serde(rename = "external-sandbox")]
    ExternalSandbox { network_access: NetworkAccess }, // 已在外部沙箱内,磁盘全放行
    #[serde(rename = "workspace-write")]
    WorkspaceWrite {
        writable_roots: Vec<AbsolutePathBuf>,  // cwd/TMPDIR 之外额外可写目录
        network_access: bool,
        exclude_tmpdir_env_var: bool,          // 默认不排除 TMPDIR
        exclude_slash_tmp: bool,               // 默认不排除 /tmp
    },
}
```

- 「三态」指日常三个档位 ReadOnly / WorkspaceWrite / DangerFullAccess;`ExternalSandbox` 是容易被忽略的第四态:声明「本进程已经在外部沙箱里」,因此磁盘访问全部放行、只按 network_access 约束网络(protocol.rs:1084-1091 注释)。字符串标签仅用于诊断输出,代码注释明确「不得用于授权」(sandbox_tags.rs:90-105)。

### 4.2 macOS:Seatbelt——deny default + require-not

- 固定调用 `/usr/bin/sandbox-exec`(seatbelt.rs:63,注释说明:固定绝对路径防 PATH 注入、防被篡改);策略文本由 4 个内嵌 .sbpl 模板加动态段拼成(seatbelt.rs:21-34,`include_str!`)。基座模板写着 "; start with closed-by-default",随即就是 `(deny default)`(seatbelt_base_policy.sbpl:7-8):默认拒绝一切,再逐条放行——标准的 fail-closed。
- 组装入口:`create_seatbelt_command_args`(seatbelt.rs:844)委托 `create_seatbelt_command_args_with_profile`(seatbelt.rs:851):先由 FileSystemSandboxPolicy 反推 readable/writable/unreadable roots;可写 root 除了 allow 之外还要 deny 自身被 unlink(seatbelt.rs:511-517,防止授权边界目录被整体替换成符号链接);受保护元数据名由正则拒绝(seatbelt.rs:585-597),名称清单在 permissions.rs:32-36 `PROTECTED_METADATA_PATH_NAMES`。
- 最值得细读的核心片段:对每个「可写根下的被排除子路径」同时生成 literal 与 subpath 两条 `require-not`(seatbelt.rs:555-563):

```rust
// Exclude both the exact protected path and anything beneath it.
// `subpath` alone leaves a gap for first-time creation of the
// protected directory itself, such as `mkdir .codex`.
require_parts.push(format!(
    "(require-not (literal (param \"{excluded_param}\")))"
));
require_parts.push(format!(
    "(require-not (subpath (param \"{excluded_param}\")))"
));
```

- 讲解:literal 精确挡路径本身,subpath 挡其下全部内容;若只有 subpath,目录尚不存在时(如首次 `mkdir .codex`)匹配不到,模型可先建目录占位、之后再往里写——两条叠加才覆盖「创建 + 遍历 + 读写」全生命周期。防「rename 逃逸」的 deny 放在策略最末(seatbelt.rs:1008-1017):rename 一个被允许的祖先目录,会把受保护后代整体搬出 carveout,所以对受保护祖先目录补 `file-write-unlink` deny,且置于末尾避免被更宽的 allow 覆盖。

### 4.3 Linux:bwrap 外层 + seccomp 内层

- 进程以 argv[0] = `codex-linux-sandbox` 自调用(landlock.rs:6 `CODEX_LINUX_SANDBOX_ARG0`),把整个 PermissionProfile 序列化成参数传给自身。主流程 linux_run_main.rs:159 `run_main` 走三条路径:
  1. 默认路径:外层用 bubblewrap 建文件系统视图(网络全隔离时 `--unshare-net`,bwrap.rs:102 `should_unshare_network`),再以隐藏参数 `--apply-seccomp-then-exec` 重新 exec 自身进入内层(linux_run_main.rs:194-221):先 capget 校验进程没有任何 effective/permitted capability,再 fork + exec 目标命令——bwrap 管「文件系统长什么样」,seccomp 管「系统调用能不能发」;
  2. full-disk-write 且无代理网络:只施加进程级限制后直接 exec(linux_run_main.rs:277-288);
  3. legacy 路径 `--use-legacy-landlock`:线程内 Landlock 整盘只读 + dev/null 与 writable_roots 可写,代码注释自述已被 bwrap 取代、保留作兜底。
- 网络 seccomp 由 seccompiler 生成 BPF(linux-sandbox/src/landlock.rs:165-268):无论 Restricted 还是 ProxyRouted 都常拒 ptrace、process_vm_readv/writev、io_uring_*;Restricted 额外拒 connect/accept/bind/listen,socket() 只许 AF_UNIX;ProxyRouted 只许 AF_INET/AF_INET6(注释:AF_UNIX socket() 全拒,因为无法桥接);受管网络要求下,即使策略是 Enabled/DangerFullAccess 也强制装 seccomp(landlock.rs:96-103),宁可 fail-closed。

### 4.4 Windows:受限令牌

- 两个后端由 WindowsSandboxLevel 决定(sandboxing/src/windows.rs:32-34 `windows_sandbox_uses_elevated_backend`):Elevated 走提升后端,否则走 WindowsRestrictedToken 后端。受限令牌核心一次调用(windows-sandbox-rs/src/token.rs:480-481):

```rust
let flags = DISABLE_MAX_PRIVILEGE | LUA_TOKEN | WRITE_RESTRICTED;
let ok = CreateRestrictedToken(
    // ...以 capability SID 作为 restricting SID,次序见注释 "Exact order"
);
// 收尾:仅保留 SeChangeNotifyPrivilege(token.rs:504)
```

- 语义:禁止全部特权、转 LUA(limited user account)、写受限;restricting SID 按注释要求的精确次序排列(token.rs:461-477),文件系统「哪里可写」由目标 ACL 上是否含对应 capability SID 决定;额外 restricting SID 刻意不进默认 DACL,防止「持有路由身份即获得对象访问权」;最终只保留 SeChangeNotifyPrivilege(token.rs:504)。
- 能力边界:受限令牌后端表达不了「split 策略 / deny-read」,遇到就直接 Refuse-to-run(windows.rs:113-118,错误消息明说 "cannot enforce deny-read restrictions directly; refusing to run unsandboxed",windows.rs:126);嵌套可写子路径等无法忠实表达的情形同样拒绝(windows.rs:147-169)——绝不降级裸奔。

### 4.5 拒绝检测与升级(escalation)

- 沙箱内命令失败不一定是被沙箱拒绝,denial.rs:5-12 注释坦承没有确定性判定,只能用启发式(`is_likely_sandbox_denied`,denial.rs:13-42):exit_code == 0 直接放过;快速失败码 2/126/127 判非沙箱拒绝(denial.rs:25-28);LinuxSeccomp 下退出码 == 128+SIGSYS 判拒绝(denial.rs:31-38);再按关键词大小写不敏感地匹配 stderr/stdout/合并输出(denial.rs:50-58:`operation not permitted`、`permission denied`、`read-only file system`、`seccomp`、`sandbox`、`landlock`、`failed to write file`);executor 侧有上报标志则直接采信(denial.rs:45-72)。进程退出后留 20ms 宽限收齐输出,统一调用 `check_for_sandbox_denial`(core/src/unified_exec/process.rs:288)并转为 `UnifiedExecError::sandbox_denied`。
- 升级链:判定为沙箱拒绝后,工具运行时把 SandboxPermissions 升为 RequireEscalated(`escalate_on_failure`,core/src/tools/sandboxing.rs:344)→ 请求用户 approval → `BypassSandboxFirstAttempt`(core/src/tools/sandboxing.rs:235-266)放宽后重试;AskForApproval 为 Never 或 Granular 关闭 sandbox_approval 时,该请求会被策略直接拒绝(exec_policy.rs:48-238);同一会话已批准一次则不再打断(`should_bypass_approval`,sandboxing.rs:315-321)。

### 4.6 安全不变量:deny-read 禁裸奔、.git/.codex 只读 carveout、环境变量剥离

- 最重要的一条不变量(core/src/tools/sandboxing.rs:269-279):策略含任何 Deny read 时,禁止无沙箱升级:

```rust
pub(crate) fn unsandboxed_execution_allowed(
    file_system_sandbox_policy: &FileSystemSandboxPolicy,
) -> bool {
    !file_system_sandbox_policy.has_denied_read_restrictions()
}
```

- 注释点破动机:denied-read 只存在于沙箱内部;若含 deny-read 还允许绕过沙箱,等于把策略明令拒绝的路径静默放行(sandboxing.rs:272-274)。因此这类命令由 `sandbox_permissions_preserving_denied_reads` 回退为「默认沙箱重试」而非裸跑(sandboxing.rs:281-295)。
- .git/.codex carveout:`PROTECTED_METADATA_PATH_NAMES`(protocol/src/permissions.rs:32-36)列出 .git、.agents、.codex 等名字;每个可写 root 无显式规则时自动追加这些子路径的只读条目(append_default_read_only_*,permissions.rs:2353 附近);workspace root 的 .codex 在目录尚不存在时也受保护(`protect_missing_dot_codex`,permissions.rs:2263-2270),保证首次 mkdir .codex 也要走审批;git 子模块/worktree 的 gitdir 指针文件一并处理(permissions.rs:2236-2256)。冲突顺序 Deny > Write > Read(FileSystemAccessMode 的 PartialOrd,permissions.rs:88-111)。
- 环境变量剥离:`NON_INHERITABLE_ENV_VARS`(protocol/src/shell_environment.rs:14-20)列出 exec-server 认证 token、`NODE_REPL_AUTH_TOKEN` 等,spawn 时强制过滤,子进程拿不到宿主凭证;网络禁用信号 `CODEX_SANDBOX_NETWORK_DISABLED=1` 由系统注入(spawn.rs:21、87),用户无法自行注入因为这些变量在 ExecRequest 内被系统覆写(exec_env.rs:41-66)。

## 6. 边界与坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 命令被误判为沙箱拒绝 | 拒绝检测是启发式(denial.rs:5-9 自述无确定性方法),zshrc 报错可能恰好含关键词 | escalation 前把 stderr 片段展示给用户,而不是静默重试 |
| 跨平台行为不完全一致 | macOS 网络策略较宽(代理/直连),Linux 受管网络强制 seccomp 更紧;策略语义一致、平台强度有差 | 关键命令先在 Linux 侧验证 fail-closed;关注 macOS 网络放行的已知 issue #10390 |
| ExternalSandbox 配错环境 | 它是「信任声明」:说自己已在沙箱内就获得全盘访问 | 无外层沙箱时切勿使用,等于自废武功 |
| 请求绕过沙箱却被拒 | 策略含 deny-read 时 `unsandboxed_execution_allowed` 恒为 false(4.6) | 这是设计而非 bug:回退默认沙箱重试 |
| legacy Landlock 失效 | 容器内缺 Landlock ABI | 走 bwrap 外层路径,而非静默降级成全放行 |

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 三态实为四态 | ReadOnly / WorkspaceWrite / DangerFullAccess + ExternalSandbox(声明已在外部沙箱) |
| 策略-平台分离 | SandboxPolicy 序列化意图 → FileSystemSandboxPolicy → Seatbelt / bwrap+seccomp / 受限令牌 |
| macOS | `(deny default)` + 逐条 allow;require-not literal+subpath 挡 .git/.codex 首次创建与全部子路径;rename 防护置策略末尾 |
| Linux | bwrap 外层建文件系统视图,内层 capget 校验 + seccomp;网络分 Restricted / ProxyRouted 两档 |
| Windows | CreateRestrictedToken(禁特权 + LUA + 写受限);表达不了 deny-read 就 Refuse-to-run |
| 拒绝 → 升级 | denial.rs 启发式判拒绝 → RequireEscalated → 用户 approval → 放宽重试;已批准一次不再打断 |
| 不变量 | deny-read 禁裸奔;.git/.codex 只读 carveout 自动追加;凭证环境变量强制剥离 |

**思考题**:为什么「策略含 deny-read 时」绝不允许无沙箱升级,而 deny-write 情形相对可容忍?macOS 的 require-not 为什么需要 literal 与 subpath 两条而不是一条?

> [!note] 参考答案
> deny-read 只存在于沙箱机制内部:一旦绕过沙箱,内核里没有任何东西再阻止读,等于用「一次审批」换掉「一整条防线」,把 ~/.ssh 等被拒读路径静默放行;deny-write 绕过后的危害面是「写坏文件」,仍有只读兜底且用户已明确知情,风险量级不同。literal 管路径本身,subpath 管路径之下;只有 subpath 时,目录尚不存在(如首次 `mkdir .codex`)匹配不到,模型可先建目录占位再逐层写入,carveout 从根上被架空;两条叠加才覆盖「创建 + 遍历 + 读写」全生命周期——这也是 seatbelt.rs:555-556 注释里 "leaves a gap for first-time creation" 的含义。
