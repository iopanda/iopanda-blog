# 规划评测与预算

> 05 章让课程助教失败得「明明白白」:能重试的重试、该换法的换法、要放弃的优雅放弃。可当 03 章的 ReAct 与 04 章的 P&E 都完成了同一任务,谁能说自己更会规划?「感觉上 P&E 更稳」不算数——本章把两种模式放上同一张试验台:同一任务各跑 3 次,用任务完成率、步数、无效步占比、token 成本四个指标量化,再给出预算设定方法。结论先行:规划没有免费午餐,每一分「想清楚」都要花钱,评测与预算就是这笔账的记账员;02.07 将把这里的指标升级为完整的评测与可观测体系。

**学习目标**:学完本章,你将能够——

1. 说出规划评测四个核心指标(完成率 / 步数 / 无效步占比 / 成本)各自度量什么、怎么算;
2. 区分任务级与轨迹级指标,举出「结果相同、轨迹不同」的例子;
3. 设计一次控制变量的对照实验(任务 / 模型 / 温度 / 工具集固定,各跑 ≥3 次);
4. 运行 plan_eval.py,把两组运行日志变成对比表与预算建议;
5. 用数据回答「ReAct 还是 P&E」,并复述「规划没有免费午餐」的含义。

## 1. 概念:规划评测与预算
- **规划评测**:用一组可量化指标衡量 Agent 完成任务的**轨迹质量**——不只问「做没做成」(任务级),还问「怎么做的、花了多少」(轨迹级)。规划是 01~04 章的「想」,评测就是给这个「想」定价。
- **预算(budget)**:评测结论在运行期的化身——知道一次任务平均花多少 token、多少步之后,才能给 Agent 设步数 / 成本上限;05 章成本护栏的基线,正是来自本章的评测数据。

| 指标 | 度量什么 | 怎么算 | 典型问题 |
|---|---|---|---|
| 任务完成率 | 做成没有(任务级) | 成功次数 ÷ 总运行次数 | 这个方案可靠吗 |
| 平均步数 | 效率(轨迹级) | 各次运行步数的均值 | 是不是绕路了 |
| 无效步占比 | 动作质量(轨迹级) | 无效动作数 ÷ 总动作数 | 是不是在乱试 |
| 成本 | 经济性(轨迹级) | 累计 token 数或折算金额 | 长期用得起吗 |

- 呼应 01.06:那里评测的是「单轮回答质量」(准确率、裁判均分);本章评测的是「多步轨迹」——评测对象从一句回答变成了整段行动史,这正是 Agent 评测与模型评测的分水岭,02.07 展开。

## 2. 为什么需要:没有评测,就没有改进
- 三个具体动机:
  - **单次成功是假象**:一次跑通可能是运气;同一任务跑 3 次,ReAct 可能 1 成 2 败,单次 demo 完全看不出来——完成率必须来自多次运行;
  - **「感觉变好了」不可靠**:改 prompt、换规划模式后凭印象判断,等于没有版本管理(呼应 02.02 01 章的回归思想);只有固定任务集 + 固定指标,才能区分「真进步」与「随机噪声」;
  - **成本是硬约束**:ReAct 每次动作都要一次全量推理,P&E 每步一次执行调用——两种模式的钱包完全不同;不量化,预算失控会以账单的形式出现在线上(05 章的成本护栏需要基线)。
- 反例现场:课程助教团队把模式从 ReAct 换成 P&E,「感觉快了」;上线后超时率反而上升——因为没有记录步数与 token,说不清快在哪、慢在哪。评测的终极价值:**让每一次改动都可辩护**。

## 3. 作用:评测与预算在 Agent 工程中的位置
```
开发期(离线)                           运行期(在线)
固定任务集 × N 次 → 指标表 → 达标?上线  每任务携带预算上限 → 超限即熔断
轨迹日志 → 沉淀为下一轮评测集(02.07)  (护栏参数来自本章评测基线)
```

- **任务级 vs 轨迹级**(02.07 预告):

| 层级 | 问什么 | 本章指标 | 02.07 展开 |
|---|---|---|---|
| 任务级 | 做成了吗 | 任务完成率 | 端到端成功率、裁判评分、黄金数据集 |
| 轨迹级 | 怎么做成的 | 步数、无效步占比、成本 | 轨迹回放、逐步校验、可观测性埋点 |

- 关键提醒(引用 1):**同一结果可能掩盖完全不同的行为**——一个 Agent 直线完成,另一个靠 20 次重试蒙对,任务级指标一样,轨迹级指标天差地别;评测必须两层都看。

## 4. 详细介绍:指标口径、实验设计与参考代码
### 4.1 指标口径(先定义清楚,再谈数字)

- 「一步」= 一次 Thought→Action→Observation 的完整决策(ReAct),或执行器对计划项的一次认领(P&E);口径不同不能直接比,所以对照实验里两种模式必须用同一任务、同一记录器。
- 「无效步」= 解析失败、工具报错(参数错 / 文件不存在)、与目标无关的绕路动作;注意:瞬时错误触发的一次重试算「有效步」——它是处置策略的一部分(05 章 4.1),同一种错误反复犯才算无效。
- 「成本」建议用 token 数而非金额:同一模型下 token 与金额线性相关,却不受计价表变动干扰;跨模型对比时再折算金额。

### 4.2 实验设计:控制变量

- 固定:同一任务文本、同一模型、temperature=0、同一工具集、同一数据快照;只允许「规划模式」这一个变量变化。
- 重复:每种模式 ≥3 次(本章规定各 3 次);样本越大完成率越可信,方差分析与显著性检验留给 02.07。
- 记录:每次运行一条 JSON,`{"mode": "react", "steps": 8, "invalid": 1, "tokens": 9800, "success": true}`——steps / invalid / tokens 从运行日志里数出,success 由最终答案与数据核对判定(任务级);轨迹截图留档备查(轨迹级)。

### 4.3 参考代码(plan_eval.py)

```python
"""plan_eval.py —— 规划评测小工具:汇总运行日志,输出指标对比表与结论。
记录格式 {"steps","invalid","tokens","success"};用法:python3 plan_eval.py [react.json plan_execute.json],无参数用内置样例。"""
import json
import statistics
import sys
def load_runs(path):
    """读取 JSON 数组格式的运行日志。"""
    with open(path, encoding="utf-8") as fh:
        return json.load(fh)
def metrics(runs):
    """四个核心指标:完成率 / 平均步数 / 无效步占比 / 平均 token 成本。"""
    n = len(runs)
    total_steps = sum(r["steps"] for r in runs)
    return {
        "n": n,
        "done": sum(1 for r in runs if r["success"]),
        "completion": sum(r["success"] for r in runs) / n,
        "avg_steps": statistics.mean(r["steps"] for r in runs),
        "invalid_rate": sum(r["invalid"] for r in runs) / total_steps if total_steps else 0.0,
        "avg_tokens": statistics.mean(r["tokens"] for r in runs),
    }
def show_row(name, m):
    print("| %s | %d/%d = %.0f%% | %.1f | %.0f%% | %.0f |" % (
        name, m["done"], m["n"], m["completion"] * 100,
        m["avg_steps"], m["invalid_rate"] * 100, m["avg_tokens"]))
def conclude(react, pe):
    print("\n== 结论要点 ==")
    if pe["completion"] > react["completion"]:
        print("- 完成率 P&E 更高:任务可预分解,计划先行更稳(04 章判据)")
    elif react["completion"] > pe["completion"]:
        print("- 完成率 ReAct 更高:任务含探索成分,临时决策更灵活")
    else:
        print("- 完成率持平:继续比成本与效率,别只看成功")
    cheaper = "P&E" if pe["avg_tokens"] < react["avg_tokens"] else "ReAct"
    print("- 平均成本:%s 更省(%.0f vs %.0f token);预算上限建议取均值 × 1.5~2" % (
        cheaper, react["avg_tokens"], pe["avg_tokens"]))
    if react["avg_steps"] > pe["avg_steps"]:
        print("- 平均步数 P&E 更短;无效步占比反映「计划对动作的约束力」")
    else:
        print("- 平均步数 ReAct 更短或相当:计划开销没换来效率,考虑换回 ReAct")
SAMPLE = {   # 内置样例:同一 5 步任务各跑 3 次的模拟日志;真机实验请替换为自己的 JSON
    "react": [
        {"steps": 7, "invalid": 2, "tokens": 9100, "success": True},
        {"steps": 9, "invalid": 1, "tokens": 12300, "success": True},
        {"steps": 12, "invalid": 4, "tokens": 15800, "success": False},
    ],
    "plan_execute": [
        {"steps": 6, "invalid": 0, "tokens": 7400, "success": True},
        {"steps": 6, "invalid": 1, "tokens": 7900, "success": True},
        {"steps": 7, "invalid": 1, "tokens": 8600, "success": True},
    ],
}
def main():
    if len(sys.argv) >= 3:
        data = {"react": load_runs(sys.argv[1]), "plan_execute": load_runs(sys.argv[2])}
    else:
        data = SAMPLE   # 无参数时用样例演示,先把流程跑通再换真数据
    react_m = metrics(data["react"])
    pe_m = metrics(data["plan_execute"])
    print("| 模式 | 完成率 | 平均步数 | 无效步占比 | 平均 token |")
    print("|---|---|---|---|---|")
    show_row("ReAct", react_m)
    show_row("Plan-and-Execute", pe_m)
    conclude(react_m, pe_m)
if __name__ == "__main__":
    main()
```
- 代码怎么读:① `metrics` 把 6 条运行记录压成四个指标,完成率同时给出「成功次数 / 总次数」方便核对;② `conclude` 按「完成率 → 成本 → 步数」的顺序自动生成结论要点,与 4.4 的判读顺序一致;③ 无参数运行时用内置样例数据演示输出格式,拿到真实日志后把路径传进去即可。

### 4.4 怎么读结果:判读顺序与预算设定

- **判读决策树**:先比完成率(可靠性优先)→ 完成率相同时比平均成本 → 成本相近时比步数与无效步占比(效率与动作质量)→ 各项都差不多就选实现更简单的(工程偏好,呼应 04 章选型判据)。
- **预算设定**:取「成功轨迹」的成本均值 × 1.5~2 作为运行期上限,失败轨迹的成本可作为熔断阈值参考;步数上限同理——05 章护栏的 max_calls / max_tokens 参数就从这里来。

## 5. 动手活动:同一任务,ReAct vs P&E 各跑 3 次
> [!example] 动手活动:规划对照实验与评测报告
> **目标**:产出 `runs/react.json`、`runs/plan_execute.json` 与 `reports/planning-eval-06.md`,用数据回答「这个任务该用哪种规划」。
> **步骤**:
> 1. 确认 03 章 `react_multi.py` 与 04 章 `plan_execute_demo.py` 就位,选定同一 4~5 步任务(建议沿用 04 章活动任务:「统计全班两次小测平均分,列出两次都低于 60 分的学员并给补强建议」);
> 2. 两种模式各跑 3 次(temperature=0、同一数据快照),每次把 steps / invalid / tokens / success 记成一条 JSON,分别存入 `runs/react.json` 与 `runs/plan_execute.json`;
> 3. 运行 `python3 plan_eval.py runs/react.json runs/plan_execute.json`,得到指标对比表与结论要点(先无参数跑通样例,再换真数据);
> 4. 把输出整理进 `reports/planning-eval-06.md`,补一段轨迹观察:哪种模式绕路多、无效步集中在哪类动作(轨迹级证据);
> 5. 按 4.4 给所选模式设定预算上限(写出均值 × 系数 的计算过程),写进报告;
>
> **完成标准**:① 6 次运行记录字段齐全、可复现;② 报告含指标对比表 + 数据支撑的一句话结论(能指出 P&E 省在哪、贵在哪,或相反);③ 预算上限有计算过程,与 05 章护栏参数呼应。

## 6. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 3 次结果方差极大,不敢下结论 | 样本太小或任务太难 | 增加运行次数;先保证任务能跑通再统计;结论限定「在 3 次样本内」 |
| 两种模式完成率都是 100% | 任务过简单,天花板效应 | 加难:换更长任务或引入失败注入(05 章),让步数与成本拉开差距 |
| token 数与账单对不上 | 记录口径不一(重试 / Observation 是否计入) | 统一记录器;把重试调用与工具返回的 token 都计入 |
| 「无效步」各人数法不一 | 定义模糊 | 先在报告里写下判定规则(4.1),再统计,保证可复现 |
| 评测任务与真实任务脱节 | 样例偏差 | 任务集覆盖典型场景(查询 / 计算 / 资料检索);02.07 讲黄金数据集 |

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 规划评测 | 用完成率 / 步数 / 无效步占比 / 成本给「轨迹质量」定价 |
| 任务级 vs 轨迹级 | 做没做成 vs 怎么做成的;两层都要看——同一结果可掩盖不同轨迹 |
| 为什么需要 | 单次成功是假象;没有指标,改动不可辩护、预算不可控 |
| 实验设计 | 只换「规划模式」一个变量,各跑 ≥3 次,记录结构化日志 |
| 结论 | 没有免费午餐:规划的钱要花在明处,选型用数据说话,预算按基线设上限 |

**思考题**:为什么「完成率相同」时还要比无效步占比?预算上限设成「成功轨迹成本均值 ×1.5」比设成「成功轨迹最大值」更松还是更紧,各有什么风险?

> [!note] 参考答案
> 完成率只回答「做成没有」,无效步占比回答「怎么做成的」——高无效步意味着 Agent 靠乱试蒙对,换一个数据分布就可能翻车(轨迹不稳定;Anthropic 的评测实践同样强调:结果相同、过程不同,可靠性不同),轨迹级指标是任务级指标的「过程审计」。均值 ×1.5 是更松:它把失败与绕路波动也纳入了容忍区间,减少误熔断,但代价是单次最坏情况可能吃掉更多预算;取成功轨迹最大值则更紧、更省,却可能在波动稍大时频繁触发 05 章护栏、打断正常任务。实务上先用均值 × 系数跑一段,观察熔断率再回调。
