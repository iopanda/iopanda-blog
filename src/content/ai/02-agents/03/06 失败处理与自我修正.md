# 失败处理与自我修正

> 04 章给 Agent 装上了「先计划后执行」的能力,可计划终究要落地执行,执行就会失败:文件路径写错、限流超时、检索结果为空、甚至计划本身过时——上一章的修订机制只在「某一步失败」时触发,却没回答三个更基本的问题:这个失败值不值得重试?该换一种方法还是干脆放弃?如何保证 Agent 不会在一个错误上重试到天荒地老?本章先给失败分类,再介绍把失败反馈「写回再试」的 Reflexion 思想,最后装上防死循环的三道护栏,让课程助教失败得明明白白。

**学习目标**:学完本章,你将能够——

1. 按「可重试 / 需换法 / 应放弃」三类给失败分类,并各举课程助教的实例;
2. 说出瞬时错误与参数错误的本质区别,解释为什么 429 该重试而 400 不该;
3. 复述 Reflexion 的「actor + evaluator + 反思缓冲」结构与它在 HumanEval 上的成绩(91% pass@1);
4. 说出防死循环三件套(最大步数 / 重复动作检测 / 成本上限)各自的适用场景与代价;
5. 运行一个带失败注入的 Agent 循环,观察三类处置与护栏触发,产出测试记录。

## 1. 概念:失败分类与自我修正
- **自我修正(self-correction)**:Agent 利用执行反馈(错误信息、失败 Observation)调整后续行为的能力;它与重试的区别是,重试「同一动作再来一次」,自我修正「换个动作再来」或「决定不再来」。执行中失败首先表现为 Observation 里的错误,例如:`Action: read_scores['data/scores.jso']` → `Observation: 失败:文件不存在`;失败处理就是在这条 Observation 之后、下一次决策之前插入的一段「分诊」逻辑。
- **三分法**(本章主线):任何失败先回答三个问题——换了时间做会成功吗?动作本身错了吗?目标现在可达吗?

| 类别 | 判定问题 | 课程助教实例 | 处置 |
|---|---|---|---|
| 可重试 | 换了时间做会成功吗(瞬时) | 429 限流、读取超时、网络抖动、5xx | 指数退避重试,设上限 |
| 需换法 | 动作本身错了吗(方法/参数) | 选错工具、中文参数、路径拼错、计划过期 | 换工具 / 改参数 / 修订计划,不重试原动作 |
| 应放弃 | 目标现在可达吗 | 资料不存在、权限不足、需求自相矛盾、成本已超 | 停止并上报:给中间成果 + 原因 + 替代建议 |

- 处置顺序是**瀑布**:先判断能否重试(成本最低),再判断要不要换法,最后才考虑放弃;三类处置在 4.4 的代码里各有一个落点。

## 2. 为什么需要:失败是常态,不是异常
- 多步 Agent 的成功率是各步成功率的乘积:5 步任务每步 90% 的把握,整体只有约 59%(0.9⁵≈0.59);10 步则只剩 35%。步骤越多,「至少失败一次」越是大概率事件——规划(01~04 章)本身就是把任务变长,所以失败处理是规划的**配套基建**。
- 不做失败处理的三种现场:①卡死:同一请求无限重发,烧钱又加剧限流(官方建议重试要限次限时,见引用 2);②硬撑:动作失败仍继续下一步,把错误结果当输入,一路错到最终答案(呼应 01.06 的错误分析);③裸奔:直接崩溃退出,把半成品丢给用户。课程助教版本更糟:学员问「为什么我导出的成绩表少了两行」,Agent 先读错文件、再算错公式、最后自信地给出错误结论——比不给答案更糟,因为**错误答案不可疑**。失败处理的目标不是「不失败」,而是「每次失败都有名字、有去向」。

## 3. 作用:失败处理在 Agent 循环里的位置
```
外层:计划循环(04 章 P&E):任一步失败 → 失败原因回传规划器 → 修订计划 / 放弃
内层:动作循环(02.01 / 03 章 ReAct):Thought → Action → Observation
        └─ 失败分诊(本章,横切层):
            ├ 可重试 → 退避后重试同一 Action
            ├ 需换法 → 生成新 Thought / 上报外层修订计划
            └ 应放弃 → 熔断:停止循环,上报中间结果
```

- 失败分诊是**横切层**:它不改变 Thought 的生成方式,只接管 Observation 的「失败分支」;内层兜不住(如资源缺失)就逐级上报,由外层计划循环决定换法或放弃——与 04 章 4.1 的「任一步失败 → 失败原因回传规划器,修订计划重跑」正好接上。呼应 01.07 与 02.04 预告:工具返回不可信,失败信息同样来自工具侧,分诊时把失败 Observation 当「数据」处理,别把它当指令执行。

## 4. 详细介绍:重试策略、Reflexion 与防死循环
### 4.1 处置①:重试策略——只重试瞬时错误

| 错误特征 | 例子 | 是否重试 | 策略 |
|---|---|---|---|
| 瞬时:换时间会成功 | 429 限流、5xx、连接超时 | 是 | 指数退避 + 抖动,2~5 次封顶,读 Retry-After |
| 永久:换时间一样失败 | 400 参数错、401 鉴权失败、文件不存在 | 否 | 走「换法 / 放弃」分支 |

- 要点:①**退避**让重试间隔指数增长(如 0.2s、0.4s、0.8s),**抖动**加随机量防止多请求同时重试;②**限次限时**——无限重试等于把瞬时错误拖成慢速灾难(引用 2 明确建议限制重试次数与总耗时);③**幂等性**:重试写操作(如「提交批改」)前先确认上次是否其实已成功,否则可能重复执行——对应课程助教里的「重复提交批改单」事故。

### 4.2 处置②:Reflexion——把失败反馈写回上下文再试

- **Reflexion**(Shinn et al., NeurIPS 2023,引用 1):不更新模型权重,而是让 Agent 把失败经历**转写成语言反思**,存入 episodic memory buffer(情景记忆缓冲),下一次尝试开始时注入上下文——论文称这种「用语言当强化信号」的方式为 verbal reinforcement learning(言语强化学习)。
- 结构三件套:**actor**(生成轨迹并行动)→ **evaluator**(打分或判定成功与否)→ **self-reflection**(把失败转成「下次该怎么做」的文本)。失败不是被吞掉,而是被加工成可复用的教训。
- 数据与接法:HumanEval 编程任务 pass@1 达 91%(GPT-4 为 80%),ALFWorld 等序列决策任务同样显著超基线——对 Agent 来说,**一段高质量失败描述 ≈ 一次免费「梯度更新」**。落到本模块:04 章失败时把「第几步失败 + 原因」追加给规划器重排计划,本章更进一步,把教训沉淀成反思缓冲跨轮次复用(「calc 不接受中文参数」这类教训不必每次重新踩坑);4.4 代码里的 memory 列表就是该缓冲的最小雏形,真机上把它拼进下一轮 system 消息即可。

### 4.3 处置③与护栏:防死循环三件套

| 护栏 | 防什么 | 实现 | 代价 |
|---|---|---|---|
| 最大步数 | 无限绕圈 | 循环计数,超过即熔断 | 可能误杀长任务 → 上限按任务类型设定 |
| 重复动作检测 | 原地打转(同一动作反复失败) | 连续失败计数 / 动作哈希(呼应 AgentBench:连续 3 次相同输出判失败,引用 4) | 误判「正常相似动作」→ 只对连续失败计数,成功即清零 |
| 成本上限 | 预算失控 | 累计 token / 金额 / 时长,超限熔断 | 需先有成本基线(06 章评测给出) |

- 护栏的共性:触发后不是静默退出,而是**优雅放弃**——输出已完成的中间结果、失败原因与替代建议,并写入日志;这些日志正是 02.07 评测与可观测性的素材(呼应预告)。

### 4.4 参考代码(self_correct_demo.py)

```python
"""self_correct_demo.py —— 失败处理三步曲 + 防死循环护栏(纯 Python 3,无第三方依赖)。"""
import time
class ToolError(Exception):
    """带类别的工具失败:kind 取 transient(瞬时)/ invalid(参数错)/ missing(资源缺失)。"""
    def __init__(self, kind, message):
        super().__init__(message)
        self.kind = kind
env = {"flaky_left": 2}   # read_scores 前 2 次调用模拟瞬时错误(429 限流 / 网络抖动)

def read_scores(path):
    if path != "data/scores.json":
        raise ToolError("missing", "文件不存在:%s,请检查路径或换用 search_course" % path)
    if env["flaky_left"] > 0:
        env["flaky_left"] -= 1
        raise ToolError("transient", "429 限流:读取超时,请稍后重试")
    return "张伟:58,62;李娜:91,88"
def calc(expr):
    if not set(expr) <= set("0123456789.+-*/() "):   # 中文词 / 中文括号一律判为非法参数
        raise ToolError("invalid", "参数不合法:算式含中文或非法字符:%s" % expr)
    return str(eval(expr))   # 仅演示用;生产环境请换白名单解析器
TOOLS = {"read_scores": read_scores, "calc": calc}
def call_with_retry(action, max_retries=2):
    """处置① 可重试:只对瞬时错误做指数退避重试;其余错误直接抛给上层分类。"""
    name, arg = action.split("(", 1)
    arg = arg.rstrip(")").strip("'\"")
    for attempt in range(max_retries + 1):
        try:
            return TOOLS[name](arg)
        except ToolError as err:
            if err.kind != "transient" or attempt == max_retries:
                raise
            delay = 0.2 * (2 ** attempt)   # 退避:0.2s → 0.4s → 0.8s
            print("    [重试] 瞬时错误,退避 %.1fs 后重试(%d/%d)……" % (delay, attempt + 1, max_retries))
            time.sleep(delay)
def run(trajectory, max_steps=8, max_calls=10, max_tokens=2000):
    """按序尝试动作;循环顶部的三个 if 即防死循环三件套。"""
    steps = calls = tokens = 0
    failed_streak = {}   # 重复动作检测:动作 → 连续失败次数
    memory = []          # 反思缓冲:失败教训写回,供下一轮参考
    print("== 任务:读取成绩并计算平均分 ==")
    for action in trajectory:
        steps += 1
        calls += 1
        tokens += 120    # 每次模型决策的 token 开销(模拟)
        if steps > max_steps:                        # 护栏①:最大步数
            print("[放弃] 超过最大步数 %d,停止并上报" % max_steps)
            return "give_up"
        if calls > max_calls or tokens > max_tokens: # 护栏③:成本上限
            print("[放弃] 超过调用次数 / token 预算上限,停止并上报")
            return "give_up"
        if failed_streak.get(action, 0) >= 2:        # 护栏②:同一动作将第 3 次连败 → 叫停
            print("[放弃] 动作 %s 连续失败,判定方法无效,停止" % action)
            return "give_up"
        print("步骤 %d:%s" % (steps, action))
        try:
            obs = call_with_retry(action)
        except ToolError as err:
            failed_streak[action] = failed_streak.get(action, 0) + 1
            if err.kind == "invalid":   # 处置② 需换法:参数错不重试,记教训换写法
                note = "教训:calc 只接受 ASCII 算式,中文参数必败;下一步改写参数而非重试"
                memory.append(note)
                print("    [换法] %s" % note)
                continue
            print("    [放弃] %s" % err)  # 处置③ 应放弃:资源缺失,不空转
            return "give_up"
        failed_streak.clear()            # 成功后清零:重复检测只看「连续」失败
        tokens += len(obs)
        print("    Observation:%s" % obs)
    print("== 完成 == 反思缓冲:%s" % (memory or ["无"]))
    return "done"

if __name__ == "__main__":
    run(["read_scores('data/scores.json')", "calc('平均分')", "calc('(58+62)/2')"])  # 场景 1:重试→换法→成功
    print("\n—— 场景 2:资源缺失 → 应放弃,不空转 ——")
    run(["read_scores('data/others.json')"])
    print("\n—— 场景 3:同一无效动作连犯 → 重复护栏叫停 ——")
    run(["calc('平均分')", "calc('平均分')", "calc('平均分')"])
```

- 代码怎么读:① `call_with_retry` 只对 `transient` 重试并退避,`invalid / missing` 一律上抛——这就是 4.1 的「分类重试」;② `run` 的异常分支里,`invalid` 把教训写进反思缓冲并 continue(换法),`missing` 直接 give_up(放弃);③ 循环顶部的三个 if 是防死循环三件套,场景 3 演示重复护栏如何叫停同一无效动作。

## 6. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 重试把瞬时错误拖成慢速灾难 | 无退避、无上限,重试加剧限流 | 退避 + 抖动 + 限次限时;优先读 Retry-After(引用 2) |
| 反思让 Agent「越修越错」 | 反思本身可能幻觉:把成功轨迹误判为失败 | 反思注入前经 evaluator 复核;限制每任务反思轮数 |
| 重复护栏误杀正常流程 | 把「不同但相似」的动作当重复 | 只对**连续失败**的同一动作计数;成功即清零 |

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 失败分类 | 可重试(瞬时,退避重试)/ 需换法(动作错,不重试)/ 应放弃(不可达,优雅上报) |
| 为什么需要 | 步骤越多失败越常态;不处理 = 卡死烧钱,或自信地错 |
| Reflexion | 把失败转写成语言反思存入 episodic buffer,下一轮注入上下文;HumanEval 91% pass@1 |
| 防死循环 | 最大步数 + 重复动作检测 + 成本上限,触发即优雅放弃 |
| 位置 | 失败分诊是横切层:接管 Observation 的失败分支;内层兜不住逐级上报外层计划 |

**思考题**:为什么 429 值得重试而 400 不值得?Reflexion 的反思应该拼进「这一轮」还是「下一轮」的上下文,为什么?防死循环三件套里,为什么「成本上限」不能由「最大步数」完全替代?

> [!note] 参考答案
> 429 是瞬时状态(限流窗口过去就会成功),重试有正收益;400 是请求本身错了(参数非法、鉴权失败),重试一万次也不会成功,只会放大成本,应换法或放弃。反思要拼进**下一轮**的上下文:当前轮次已经失败,把反思写回本轮改变不了已成事实的轨迹,它的价值在于指导后续尝试——Reflexion 的 episodic buffer 正是跨轮次复用的设计;担心反思幻觉时,可先经 evaluator 复核再注入。成本上限无法被最大步数替代:步数只约束「轮数」,而每轮消耗的 token 差异巨大(长文档检索、超长 Observation 都可能让单轮极贵);真正管钱的是累计 token / 金额上限,两者管的是不同资源,缺一不可。
