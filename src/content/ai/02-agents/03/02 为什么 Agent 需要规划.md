# 为什么 Agent 需要规划

> 02.02 让课程助教 Agent 说得稳、扛得住提示注入,但它仍然是「一问一答」的形状:问题进、答案出,中间没有岔路。真实助教工作不是这样的——「统计 20 份作业的错误知识点,给全班生成个性化补强练习」这类任务没法一次生成:得先取到成绩数据,看到统计结果,才知道该补强谁。本章承接 02.02 末篇(06 章)的预告,作为 02.03 Planning and Reasoning 的开篇,回答一个承上启下的问题:**为什么 Agent 需要规划?**读完你会分清「一步能答完」与「必须拆开做」两类任务,并为课程助教写出第一份目标→子目标→步骤的计划。

**学习目标**:学完本章,你将能够——

1. 说出规划的定义(目标 → 子目标 → 步骤序列)与它和「一次回答」的本质区别;
2. 解释为什么复杂任务无法一步生成、为什么中间结果必须依赖外部观察;
3. 用判断清单识别「无规划就够用」的单步问答与简单工具任务;
4. 列出规划的四类代价(时间与 token、失败点、评测难度、维护成本),判断何时不必规划;
5. 把 CoT / ReAct / Plan-and-Execute 摆进 Agent 循环的正确位置,预告本模块后续章节。

## 1. 概念:规划是什么

- **规划(Planning)**:在执行之前(或执行之中),把**目标(goal)**分解为若干**子目标(subgoal)**,再把每个子目标落实为有序的**步骤(step)**序列,并标明步骤间依赖关系的过程。对 Agent 来说,规划就是它的「行动路线图」:先想清楚到哪、分几段、每段做什么、先后顺序如何。
- 拆解后的每一步,必须小到「一次模型生成或一次工具调用能完成」——这正是 02.02 反复强调的窗口意识:上下文能装下的是步骤,不是整座山。
- 注意:规划 ≠ 推理。**推理**是在「一步」内部做判断(这道题怎么解);**规划**是在「多步」之间做组织(先做哪步、结果给谁用)。本章谈规划的组织,02 章谈单步内的推理。
- 课程助教示例,目标:「批改期中作业并给每位学员写反馈」:

```
目标:批改期中作业,给每位学员写个性化反馈
 ├─ 子目标① 取到作业与参考答案        ← 外部观察:必须先读文件
 ├─ 子目标② 逐份评分                  ← 依赖 ①
 ├─ 子目标③ 汇总全班弱项              ← 依赖 ②
 └─ 子目标④ 生成个性化反馈            ← 依赖 ②③
步骤序列:read_file(作业) → score_each → summarize_gaps → compose_feedback
```

### 1.1 与 02.01 循环的关系

- 02.01 的 03 章把 Agent 循环画成「感知 → 规划 → 行动 → 观察」,但当时的「规划」只是模型每轮临场想一句 Thought。从本章起,规划从「一句话」变成「一张路线图」:它仍然发生在循环的规划位,只是不再随用随丢,而是可以预先产出、执行中修订(04/05 章)。
- 呼应 02.01 的五要素:规划把「目标」翻译成一系列「工具调用 + 中间判断」,让大脑(模型)、手(工具)、便签(记忆)协作完成单次生成做不到的事。

## 2. 为什么需要:复杂任务无法一步生成

### 2.1 一步生成的错误率随任务深度上升

- 模型单次生成 = 依据当前上下文一口气推出最终答案。任务内部每多一层「先…再…」,一步到位的出错率就明显上升(呼应 01.04:上下文越长、跳数越多,模型精度越低)。
- 课程助教反例:「按错误率从高到低列出 Top3 知识点,并为每个知识点配一道补强题。」若一步生成,模型必须同时完成统计、排序、选题、出题;任何一位学员的分数记错,排序与选题全错,而且你**看不到错在哪一步**。

### 2.2 中间结果依赖外部观察

- 更硬的原因:许多步骤的输入不在模型权重里、也不在用户问题里,而在**外部世界**——成绩文件、课程资料库、作业提交系统。模型没读过成绩表,就「算」不出平均分,只能编(呼应 02.01:工具是手,工具返回才是观察)。
- 规划的核心作用之一,就是把「取外部数据」安排在「用它计算」之前,并让后一步的输入来自前一步的观察:**观察在代码层流转,不靠模型记忆**。
- 为什么单次生成做不到?一次生成里,模型不能「先读文件、等结果、再继续」——调用之间必须由代码循环拼接(这正是 03 章 ReAct 做的事)。本章先把结论立住:**多步任务 = 多次生成/调用 + 步骤间显式传值**。

## 3. 作用:规划在 Agent 里的位置

| 形态 | 需要几次调用 | 中间决策 | 失败影响 | 典型课程助教任务 |
|---|---|---|---|---|
| 单步问答 | 1 次生成 | 无 | 答错重问 | 「什么是外键?」 |
| 简单工具调用 | 1 次生成 + 1 次工具 | 无 | 工具错则答错 | 「查 03 章作业截止时间」 |
| 多步规划执行 | N 次生成/调用 | 每步都可能 | 一步错可连累后续 | 「统计错误率并生成补强计划」 |

- 规划把 Agent 从「应答器」升级为「执行者」:单步形态只回答「用户问的问题」;规划形态承接「用户给的**任务**」——任务需要自己决定做哪些事、按什么顺序。
- 本模块的能力谱系(预告,后几章逐一展开):

| 章节 | 推理/规划形态 | 是否调用工具 | 一句话 |
|---|---|---|---|
| 02 | Chain-of-Thought(脑内推理) | 否 | 先把推理写出来,再给答案 |
| 03 | ReAct(想一步做一步) | 是 | 边想边做,观察修正下一步 |
| 04 | Plan-and-Execute(先计划后执行) | 是 | 计划先行,逐项执行 |

## 4. 详细介绍:什么时候规划,什么时候不必

### 4.1 无规划形态:什么时候够用

- **单步问答**够用:概念解释、事实问答、代码片段生成——上下文里已有全部所需信息,一次生成即可,规划是纯浪费。
- **简单工具调用**够用:只需一次外部查询就能答(查截止时间、查某学员单科成绩),且不需要根据查询结果再决定下一步动作。
- 判断清单(三条全「是」就别规划):① 任务能在一次模型调用内完成?② 最多用一个工具,且不必看结果再决策?③ 所需信息当前上下文里都有?任一条为「否」,才考虑规划。

### 4.2 规划的代价

| 代价维度 | 说明 | 课程助教例子 |
|---|---|---|
| 时间与 token | 每步一次往返,延迟与费用随步数上涨 | 3 步任务 ≈ 3 次调用,而非 1 次 |
| 失败点增多 | N 步有 N 个出错机会,一步错可能全盘错 | 读错文件 → 统计、反馈全错 |
| 评测变难 | 不只评最终答案,还要评中间步骤对错(呼应 02.07) | 「排序对了但统计口径错」算不算对? |
| 维护成本 | 循环、解析、终止条件、传值都要自己写(02.01 05 章) | 步骤多了要处理工具异常与重试 |

### 4.3 何时不必规划(代价超过收益)

- 用户只要快答、对正确性要求不高;
- 任务无法预分解,只能边走边看——这时硬套固定计划反而僵化(04 章讲 ReAct 与 Plan-and-Execute 的取舍);
- 规划本身比任务贵:为一个「一句话能答」的问题写 5 步计划,是最常见的过度工程。
- 工程原则(引用 1、2 的共识):**从最简单形态开始,用评测数据证明不够了,再往上加复杂度**——先单步问答,评测;不够,加一个工具;还不够,才上规划。

## 5. 动手活动:给课程助教写第一份计划

> [!example] 动手活动:期中作业分析——无规划 vs 有规划
>
> **目标**:产出 `plans/plan_demo.py` 与 `reports/plan-vs-oneshot.md`,用同一任务对比两条执行路径。
>
> **步骤**:
> 1. 写下任务:「统计期中作业,给出全班平均分、最低分学员,并生成补强提示」的目标/子目标/步骤分解(≥3 个子目标,标出依赖);
> 2. 实现工具函数:取数据、算统计、生成报告(先用模拟数据跑通,再换成你 01 部署的模型 + OpenAI 兼容调用,参考 02.01 05 章);
> 3. 实现两条路径:`one_shot(task)`(一次生成、不给工具)与 `planned_run(task)`(按步骤序列执行,观察在步骤间显式传递);
> 4. 各跑一次并记录:是否成功、步数、大致 token 数(响应字符数 ÷ 4 估算即可);
> 5. 把结论写入 `reports/plan-vs-oneshot.md`:该任务该不该规划?依据是什么?
>
> **完成标准**:① 分解含 ≥3 个子目标且依赖标注正确;② 无规划路径因缺外部观察而失败或编造数据(如实记录);③ 规划路径按序完成,输出含平均分与最低分学员的报告;④ 报告里写得出「这次任务需要规划」的两条理由。

### 5.1 可运行骨架(plan_demo.py,零 API 依赖)

```python
"""plan_demo.py —— 课程助教「期中作业分析」:无规划 vs 有规划。"""
import json

def fetch_answers():
    """工具①:取成绩数据。外部观察只能靠工具,模型不会自带(02.01 呼应)。"""
    raw = '[{"name": "张三", "score": 88}, {"name": "李四", "score": 91}, {"name": "王五", "score": 73}]'
    return json.loads(raw)      # 生产环境改为读文件/查数据库

def compute_stats(answers):
    """工具②:算平均分与最低分学员,依赖前一步的观察结果。"""
    avg = sum(item["score"] for item in answers) / len(answers)
    lowest = min(answers, key=lambda item: item["score"])
    return {"avg": round(avg, 1), "lowest": lowest["name"]}

def build_report(stats):
    """工具③:生成补强提示,输入全部来自观察,不靠记忆。"""
    return "全班平均 %s 分;最低分学员 %s,建议补强对应章节练习。" % (stats["avg"], stats["lowest"])

TOOLS = {"fetch_answers": fetch_answers,
         "compute_stats": compute_stats,
         "build_report": build_report}

def one_shot(task):
    """路径 A:无规划。一次生成最终答案,不调用任何工具。"""
    print("[路径 A] 工具调用次数 = 0(真实实现:chat.completions.create 只调一次)")
    return "报告:全班平均 ? 分,最低分 ?……(从未读取成绩数据,只能编造)"

def planned_run(task):
    """路径 B:有规划。按 (输出名, 工具, 依赖) 顺序执行,后一步消费前一步的观察。"""
    plan = [
        ("answers", "fetch_answers", []),        # 子目标①:取数据,无前置依赖
        ("stats", "compute_stats", ["answers"]), # 子目标②:依赖 answers
        ("report", "build_report", ["stats"]),   # 子目标③:依赖 stats
    ]
    obs = {}
    for idx, (name, tool, deps) in enumerate(plan, 1):
        args = [obs[key] for key in deps]        # 参数显式取自观察,不靠模型记忆
        obs[name] = TOOLS[tool](*args)
        print("[路径 B] 第 %d 步 %s -> %s" % (idx, tool, str(obs[name])[:40]))
    return {"steps": len(plan), "report": obs["report"]}

if __name__ == "__main__":
    task = "统计期中作业:给出全班平均分与最低分学员,并生成补强提示。"
    print(one_shot(task))
    result = planned_run(task)
    print("规划路径:步数 = %d,报告 = %s" % (result["steps"], result["report"]))
```

- 观察路径 A 的缺口:没有任何中间观察,报告里的数字只能来自「记忆」——这正是无规划在多步任务上的典型失败。跑通骨架后,把各步骤替换成真实模型调用,就是本模块后几章要讲的「会推理的规划」。

## 6. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 计划很完整,执行时第一步就缺数据 | 分解时漏了「取外部数据」的子目标 | 回到分解图,逐个检查子目标的输入来自哪 |
| 步骤间传值错乱(用到上上步的旧数据) | 观察未显式命名与传递 | 给每步输出起名,参数只从观察字典取(见 5.1 骨架) |
| 任务简单却总在规划上烧 token | 过度工程 | 用 4.1 清单自查;该单步就单步 |
| 计划写死,中途发现任务变了 | 任务不可预分解 | 改用 03 章 ReAct 边想边做,或 04 章的计划修订 |
| 拿不准该不该规划 | 凭感觉、无依据 | 用 4.3 的代价清单逐项打勾,写进实验报告 |

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 规划 | 把目标拆成子目标与步骤序列、标注依赖的路线图 |
| 为什么需要 | 复杂任务一步生成错误率高;中间结果必须来自外部观察 |
| 无规划何时够用 | 一次生成能答、最多一个工具、无需中间决策 |
| 规划的代价 | 时间与 token、失败点、评测难度、维护成本 |
| 工程原则 | 从最简单形态开始,评测证明不够再加(呼应 02.07) |

**思考题**:为什么「统计作业错误率并生成补强计划」必须规划,而「查作业截止时间」不必?如果学员的问题是「把下面 3 道题按难度排序并逐题解释」,它需要工具型规划吗?判断依据是什么?

> [!note] 参考答案
> 前者需要多次外部观察(成绩数据、统计结果)且步骤间有依赖,一步生成必然缺数据或编造;后者一次查询即可返回,无中间决策。「3 道题排序并解释」不需要工具,但排序加逐题解释已超过一步推理,单次生成的正确率会下降——正确做法是先不规划,用 02 章的 CoT 让模型分步作答,评测不过再考虑工具与多步。规划与否取决于任务深度,不只看要不要调工具。
