# Chain-of-Thought 与单步推理

> 01 章立了「要拆」的原则:复杂任务要变成子目标与步骤。可拆完之后,每一步内部怎么保证正确?答案是先别急着给结论,让模型把推理过程写出来——这就是 Chain-of-Thought(思维链,CoT)。它是本模块能力谱系的最左端:全程不调用工具,推理发生在一次生成之内,是「纯脑内」的规划;也是 02.01 最小 ReAct 里 Thought 的原型。读完你会用一句话触发它(zero-shot CoT)、用示例驯服它(few-shot CoT),并看清它够不着外部世界的边界——那正是 03 章 ReAct 要补的洞。

**学习目标**:学完本章,你将能够——

1. 说出 CoT 的定义与「先想后答、推理可见」的特征;
2. 解释推理链为什么有效:把一步大跳跃切成多步小步,每步只消费上一步的结论(呼应 02.02 的上下文工程);
3. 用 zero-shot CoT(「请逐步思考」)让模型分步作答,并说出它的不稳定之处;
4. 构造 few-shot CoT 提示(问题 + 完整推理链 + 答案的示例),说明它比 zero-shot 稳在哪、贵在哪;
5. 复述 CoT 的三条边界(一次生成、接不到外部信息、链上幻觉),并指出升级方向 ReAct。

## 1. 概念:Chain-of-Thought 是什么

- **Chain-of-Thought(CoT,思维链)**:一种提示技术——要求模型在给出最终答案之前,先输出一串**中间推理步骤**,把「怎么想到这个答案的」写在回答里(Wei et al., 2022,引用 1)。
- 与直接回答的本质区别:**推理可见**。直接回答给你一个黑盒结论;CoT 给你一条可检查的推导路径。
- 课程助教示例,学员问:「期中作业张三 88、李四 91、王五 73,平均分是多少,谁最需要补强?」

| 形态 | 模型输出 | 问题 |
|---|---|---|
| 直接回答 | 「平均 84 分,王五最需要补强。」 | 怎么算的?不可见,错了无从查 |
| CoT 回答 | 第 1 步求和:88 + 91 + 73 = 252;第 2 步平均:252 ÷ 3 = 84;第 3 步比较:73 最低,是王五。最终答案:平均 84 分,王五最需要补强。 | 每一步可检查,错了能指出第几步 |

- 与 01 章的关系:CoT 是「脑内规划」——01 章的目标 → 子目标,在 CoT 里变成一段段中间推理;区别在于它不调工具、不产生观察,属于谱系最左端(见第 3 节表格)。

## 2. 为什么有效:推理链让模型逐步利用上下文

- **把大跳跃切成小步**:模型在「从问题直接跳到结论」的长距离推理上容易丢精度(呼应 01.04);CoT 让每一步只做「上一步结论 + 当前局部信息」的短距离推理——短距离正是模型最擅长的。
- **自生成上下文(呼应 02.02)**:模型逐 token 自回归,每生成一个 token,它就进入上下文、参与下一个 token 的预测。CoT 等于让模型「自己喂自己」:第 k 步的中间结论被写下来,成为第 k + 1 步的上下文;不写下来,后续步骤就没有可引用的对象,只能「凭感觉」——这正是「算着算着丢了进位」这类错误的来源。
- **可校验、可定位**:中间步骤可见 → 人能指出「是第 2 步加法错了」,而不是面对一个黑盒答案(呼应 01.06 的错误分析;也为 02.07 评测中间步骤打基础)。
- 数据证据(引用 1):在 GSM8K 数学题等基准上,触发 CoT 后准确率显著高于直接回答——不是模型变聪明了,而是提示让它把「隐性多步推理」显性成「显性多步推理」。

## 3. 作用:CoT 在 Agent 里的位置

| 形态 | 推理位置 | 是否多次生成 | 是否调工具 | 能否观察外部 |
|---|---|---|---|---|
| 直接回答 | 不可见 | 否 | 否 | 否 |
| CoT(本章) | 一次生成内、可见 | 否 | 否 | 否 |
| ReAct(03 章) | 分散在每轮 Thought | 是 | 是 | 是 |
| Plan-and-Execute(04 章) | 计划与执行分家 | 是 | 是 | 执行阶段是 |

- Agent 视角:课程助教的「单步推理」环节(判断一段 SQL 错在哪、比较两份答案谁更符合评分标准)都可以用 CoT 提高单次正确率,而**循环结构完全不用改**——CoT 是最低成本的改造,只动提示词。
- 工程化:不少模型的 API 提供 thinking / reasoning 开关,内部机制与 CoT 同源;对使用者来说,关键是决定推理过程**要不要对外可见**:可见 = 可审计但回答更长;隐藏 = 省 token 但出错难定位。

## 4. 详细介绍:zero-shot CoT 与 few-shot CoT

### 4.1 zero-shot CoT:一句话触发

- 做法:在问题后追加「请逐步思考再作答」或英文的 "Let's think step by step",模型就会先写推理链再给答案(Kojima et al., 2022,引用 2)。
- 优点:零示例、零准备成本,开箱即用;对多数模型、多数推理题都有效。
- 不稳定之处:① 模型可能「口说思考」却并不真写步骤;② 步骤格式不统一,难程序化解析;③ 对过难的题,链写了但照样错。

### 4.2 few-shot CoT:用示例驯服

- 做法:在提示里放 1~3 条「问题 + 完整推理链 + 最终答案」示例,让模型模仿示例的推理深度与输出格式(呼应 02.02 的 03 章:示例是给模型看的「图」,比抽象指令更准)。课程助教判分版示例:

```
问:一次小测 5 人成绩为 60、70、80、90、100,平均分多少?
答:第 1 步,求和:60 + 70 + 80 + 90 + 100 = 400;
第 2 步,平均:400 ÷ 5 = 80。
最终答案:平均分 80 分。
```

- 优点:更稳(格式与步长被示例锚定)、可控(可在示例里规定单位、取舍、术语);代价:示例占 token、要人工挑选——示例本身带错,模型会连错一起模仿。

### 4.3 三种形态对比

| 提示形态 | 准备成本 | 稳定性 | 输出格式 | 适用场景 |
|---|---|---|---|---|
| 直接回答 | 零 | 多步任务差 | 自由 | 单步问答 |
| zero-shot CoT | 零 | 中(偶发不写步骤) | 半自由 | 快速试水、临时任务 |
| few-shot CoT | 中 | 好 | 可被示例约束 | 生产环境固定任务 |

### 4.4 局限:为什么 CoT 还不够

- **一次生成,接不到外部信息**:CoT 的推理全部发生在单次调用内。问它「查数据库里本学期缺勤最多的学员并分析」,它没有数据库,推理链再漂亮也是无源之水——缺外部观察(01 章结论)。
- **链上幻觉**:中间步骤可能整整齐齐地错——模型一本正经地「算出」一个编造的平均分,而且因为每一步自洽,看起来比直接答更可信。「看起来很对的链」比明显瞎猜更难防。
- **无反馈环**:一次生成,错了不会回头;链越长,误差累积与 token 成本越高。
- 升级方向:让「想」与「做」交错——**Thought → Action → Observation**(03 章 ReAct;02.01 05 章的最小实现已见雏形):推理到某一步发现缺数据,就去调用工具拿 Observation,再继续想。**CoT 就是 ReAct 的纯脑内版本**。

## 5. 动手活动:让课程助教「先想后答」

> [!example] 动手活动:三种提示 × 5 道题
>
> **目标**:产出 `cot_demo.py` 与 `reports/cot-compare.md`,用同一组题对比直接回答 / zero-shot CoT / few-shot CoT。
>
> **步骤**:
> 1. 准备 5 道多步题(如:3 人成绩求平均与最低分、嵌套括号的四则运算、按两条条件筛选学员并排序),可混入 1 道「一步能答」的控制题;
> 2. 写 `ask(prompt)`:OpenAI 兼容调用,用你 01 部署的端点(参考 02.01 05 章,设好 `base_url` 与模型名);
> 3. 实现 `build_prompt(style, question)`:direct 直接问;zero_shot 追加「请逐步思考」;few_shot 前放一条完整推理链示例;
> 4. 每种提示跑全部 5 题(共 15 次调用),记录每题的「最终答案对错」与「是否真的写出中间步骤」;
> 5. 观察并记录:至少 1 题 CoT 纠正了 direct 的错误(指出是第几步被纠正);至少 1 题 CoT 仍错(分析原因);写入 `reports/cot-compare.md`。
>
> **完成标准**:① 15 次调用结果入表(提示 × 题号 × 对错 × 有无中间步骤);② 能指认「某题在第几步出错/被纠正」——推理可见性落地;③ 报告里有一条 CoT 局限的实测证据(算错但链自洽,或说了思考却没写步骤)。

### 5.1 参考代码(cot_demo.py)

```python
"""cot_demo.py —— 课程助教 CoT 对比:direct / zero-shot CoT / few-shot CoT。"""
from openai import OpenAI

client = OpenAI()            # 默认读 OPENAI_API_KEY;自建端点加 base_url(01.04)
MODEL = "gpt-4o-mini"        # 换成你 01 部署的模型名

QUESTIONS = [
    "期中作业:张三 88、李四 91、王五 73,全班平均分是多少?谁最需要补强?",
    "计算 (3 + 5) * (10 - 4) / 2 的结果,并说明运算顺序。",
    "按成绩从高到低排序:李四 91、王五 73、张三 88、赵六 95。",
]

def build_prompt(style, question):
    """按三种提示形态拼装用户消息。"""
    if style == "direct":
        return "你是课程助教,直接回答:\n" + question
    if style == "zero_shot":
        return ("你是课程助教。请逐步思考再作答,先写出推理步骤,"
                "再给出最终答案。\n" + question)
    example = ("问:一次小测 5 人成绩为 60、70、80、90、100,平均分多少?\n"
               "答:第 1 步,求和:60 + 70 + 80 + 90 + 100 = 400;"
               "第 2 步,平均:400 / 5 = 80。\n最终答案:平均分 80 分。\n")
    return ("你是课程助教,请模仿下面示例的推理格式作答:\n" + example
            + "问:" + question + "\n答:")

def ask(prompt):
    """一次 OpenAI 兼容调用,返回模型回答文本。"""
    reply = client.chat.completions.create(
        model=MODEL, messages=[{"role": "user", "content": prompt}],
        temperature=0)          # 低温便于复现;端点不支持可删
    return (reply.choices[0].message.content or "").strip()

def main():
    styles = ["direct", "zero_shot", "few_shot"]
    for style in styles:
        for idx, question in enumerate(QUESTIONS, 1):
            answer = ask(build_prompt(style, question))
            print("== [%s] 第 %d 题 ==\n%s\n" % (style, idx, answer))

if __name__ == "__main__":
    main()
```

- 跑完把结果抄进 `reports/cot-compare.md` 的表格;重点不是「哪种全对」,而是观察**中间步骤与最终正确性的关系**:direct 答错的题,CoT 是否在第 1 步(取数)或第 2 步(运算)就纠偏了。把 QUESTIONS 换成你自己课程的真实题目,就是课程助教「单步推理质检」的雏形。

## 6. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 说了「逐步思考」却只给一句答案 | 模型对口头指令不敏感 | 换 few-shot CoT,用示例强制格式;或换更强模型 |
| 推理链自洽但最终答案错 | 链上幻觉:某一步算错却被包装成「显然」 | 逐步检查(尤其第一步取数);需要真实数据时上工具(03 章) |
| few-shot 把示例原样抄回 | 示例与题目太像 | 换领域、换数字的示例;减少示例条数 |
| 长链 token 暴涨 | 每步都写长句 | 提示约束「每步一行,只写算式与结论」;或截断中间输出 |
| 简单题用 CoT 反而更差 | 引入不必要的中间判断 | 先分类:单步题直接答,多步题才 CoT(路由思想,呼应 02.02) |

## 7. 总结

| 概念 | 一句话 |
|---|---|
| Chain-of-Thought | 让模型先输出可见的中间推理,再给最终答案 |
| 为什么有效 | 把一步大跳跃切成短距离小步;中间结论自生成,成为后续步骤的上下文 |
| zero-shot CoT | 「请逐步思考」一句话触发,零成本但不稳定 |
| few-shot CoT | 用带推理链的示例锚定格式与深度,更稳也更贵 |
| 局限 | 一次生成、无外部观察、链上幻觉 → 需要 ReAct(03 章) |

**思考题**:CoT 让模型把中间步骤写出来,为什么反而比「闷头直接答」更准?如果学员问的是「明天天气如何」,用 CoT 能让答案更准吗——这暴露了 CoT 的什么边界?

> [!note] 参考答案
> 更准是因为模型逐 token 自回归:写下来的中间结论会进入上下文、成为后续步骤的参考,相当于自己给自己铺路,把「多步隐性推理」变成「多步显性推理」,每步只需做短距离判断;同时步骤可见,错误可定位。天气问题暴露边界:CoT 不产生任何外部观察,模型不知道明天的天气,再长的推理链也只能编——要答准必须调用天气 API(外部工具),这正是 03 章 ReAct「想一步做一步、Observation 喂给下一步」要解决的问题。
