# RAG 在 Agent 中的角色

> 04 章建好的课程资料向量库像一位「只懂递书的图书管理员」:你问一句,它按语义相似度递来最像的几页,一次搞定。可课程助教不是单次问答机,而是一个循环——它先要判断「这题需不需要翻讲义」,翻完还要判断「这几页够不够、是不是答非所问」,不够就换一种问法再翻。**把检索从一条固定流水线,升级成 Agent 循环里由 Agent 自己决定何时发起、可以重入的动作**,这就是 RAG 在 Agent 中的角色。本章是 02.05 的第五课:先厘清「RAG 是工具,不是 Agent 本身」,再回答「什么任务应该先检索」,最后动手把 04 章检索器包成一个工具,实现「先检索、评估不足则改写查询再检索」的检索-规划联动循环。

**学习目标**:学完本章,你将能够——

1. 区分流水线 RAG、工具化 RAG 与 Agentic RAG,说清「RAG 是 Agent 的工具而非 Agent 本身」;
2. 按「私有/新语料、需引用、错误代价高」判断何时该先检索,何时不必;
3. 描述检索-规划联动的两个方向:先检索再规划、边规划边检索(Agentic RAG);
4. 把 04 章的检索器封装为 Agent 工具,实现带「改写重查」上限的检索循环;
5. 用命中率与引用正确性两个口径评估检索质量,并指出 02.07 将如何展开。

## 1. 概念:RAG 是工具,不是 Agent 本身

- **RAG(Retrieval-Augmented Generation,检索增强生成)**:生成前先从外部语料检索相关片段、拼进上下文再回答。它解决「模型权重里没有」的内容(呼应 01 章:权重是慢知识,课程讲义是私有语料)。
- RAG 在工程里有三种存在形态,务必分清:

| 形态 | 结构 | 检索发起者 | 典型例子 |
|---|---|---|---|
| 流水线 RAG | 检索→拼上下文→生成,一次走完 | 脚本,固定执行 | 「查资料问答机器人」 |
| 工具化 RAG | 检索封装成工具,Agent 循环里按需调用 | Agent(02.01 的循环) | `search_course_notes(query)` |
| Agentic RAG | 检索在循环里可重入:先检→评估→改写/再检 | Agent + 评估逻辑 | 本章的「改写重查」演示 |

- 为什么说 RAG 不是 Agent:Agent 是「感知-决策-行动」的循环(02.01),有目标、会规划、能选动作;流水线 RAG 只是一条没有决策的直线——查什么、查几次都由外部代码定死。**把 RAG 塞进循环、让模型决定何时检索,检索才成为 Agent 的能力**;此时它是 Agent 工具格与记忆格的接口(检索把外部记忆取回上下文),而不是 Agent 本身。类比:翻书之于学生,是手段不是主体;决定「何时翻、翻到什么程度为止」的才是会用资料的学生。

## 2. 为什么需要:什么时候先检索

- 三个「先检索」信号,命中越多越该先检:
  - **私有/新语料**:课程讲义、版本更新、内部 FAQ 不在训练数据里,模型没见过(04 章向量库存在的理由);
  - **需要引用出处**:回答要能回指「课程资料第几节」(02.02 的 01 章),不检索就没有可回指的对象;
  - **错误代价高**:考试题、规范解释答错会误导学员,宁可先查证再作答。
- 反例——何时不必先检索:闲聊寒暄、通用常识(「什么是数据库」)、按 ID 精确取档案(03 章走 SQL,不走向量库)、纯计算(02.04 的计算器)。**检索有成本**:每次检索耗一次嵌入请求、片段占上下文窗口(02.02 的 02 章预算)、还可能带回噪声;「每问必检」与「永不检索」一样是设计失误。一句话:**先问「答案在不在我脑子里」,不在或不敢确定,才去翻书**。

## 3. 作用:检索在 Agent 循环里的位置

- 在 Agent 循环(02.01)中,检索是一个**只读工具调用**,位置如下:

```text
Agent 循环(每轮)
  ├─ 规划:这题需要讲义依据吗?
  │    ├─ 不需要 → 直接作答(闲聊/常识/档案)
  │    └─ 需要 → Action: search_course_notes(query)   ← RAG 在这一格
  ├─ 观察:返回带来源元数据的片段(top-k)
  ├─ 评估:片段够不够回答?(不够 → 改写 query,再走一轮)
  └─ 生成:依据片段作答,并回指来源
```

- **检索结果在循环里的地位**:与 02.04 的任何工具返回同级——带来源元数据(块 ID/章节/标题)的**不可信内容**;模型据它作答,但要标注来源、可质疑、可拒答(呼应 04 章「相关性≠正确性」)。这与 01.05 的图文检索同构:讲义配图、白板截图嵌入同一语义空间,检索动作不变,只是语料从纯文本扩到多模态。
- **检索-规划联动**是本章的钥匙,分两个方向:先检索再规划(Retrieve-then-Plan,开场先把相关讲义拉进上下文再组织回答,适合「先摸清资料再动手」的开放任务);边规划边检索(Agentic RAG,边答边发现缺口再检索补上,适合「先讲外键、再讲删父记录会怎样」这类需要两块资料的多跳问题)。
- 与 01.02 数据质量纪律呼应:**检索质量的上限由语料质量决定**——来源不明、重复、脏乱、版权不清的资料进了库,向量检索只会把垃圾捞得更快更准;先治理语料(来源可溯、清洗去重),再谈检索效果。

## 4. 详细介绍:Agentic RAG 的检索决策

### 4.1 流水线 RAG vs Agentic RAG

| 维度 | 流水线 RAG | Agentic RAG(工具化检索) |
|---|---|---|
| 结构 | 固定一次「检索→生成」 | 检索是循环里的一步,可重入 |
| 检索次数 | 恒为 1 | 0~N 次,由评估结果决定 |
| 查询处理 | 用户原话直接用 | 可改写、可拆分(呼应 02.03 规划) |
| 失败处理 | 捞到什么答什么,或空答 | 评估不足→改写重查;仍无→明说「资料未覆盖」 |
| 适用场景 | 单跳、语料表达与问法接近 | 多跳、口语问法、需要引用核验 |

### 4.2 检索循环的四个决策点

1. **要不要检**:query 分类(知识密集?需引用?)——决定 0 次还是 ≥1 次检索;
2. **检到什么程度**:相似度阈值(04 章的 `MIN_SCORE`),低于阈值视为「没检索到依据」;
3. **够不够答**:命中片段是否真正覆盖问题(按命中分数与数量做启发式,或让模型判断);
4. **不够怎么办**:改写查询重试(rewrite)、换检索源,或坦承无法回答——并设重试上限,防止无限循环(呼应 02.03 的 05 章「防死循环」)。

```text
检索(query) → 命中低于阈值?→ 是:改写重试(≤ MAX_RETRY),仍低则拒答「资料未覆盖」
             └ 命中够 → 片段覆盖问题?→ 否:改写再检 / 是:依据片段作答并回指来源
```

### 4.3 评测:命中率与引用正确性

- **命中率(hit rate)**:评测集中「应该命中的那块」是否出现在 top-k 里——衡量检索器本身(呼应 01.06 的评测纪律);
- **引用正确性(citation correctness)**:答案声称引用某片段,该片段是否真的支撑这句话——衡量「检索→生成」整链,防止「答对了但引用是编的」;
- 评测集形态:黄金问答对(问题, 应命中块 ID, 参考答案);先离线测命中率,再端到端抽检引用;完整框架在 02.07 Evaluation and Observability 展开(见其 README)。

## 5. 动手活动:把检索器包成 Agent 工具

> [!example] 动手活动:retrieval_agent_demo.py——工具化检索与「改写重查」循环
>
> **目标**:把 04 章的教学检索器封装成工具 `search()`,实现 `answer_agentic()`(评估→改写→重查,带重试上限),并对比不做评估的 `answer_naive()`;脚本纯 Python 3 可运行,`embed_text` 沿用 04 章的字符二元组教学近似。
>
> **步骤**:
> 1. 保存为 `retrieval_agent_demo.py` 并运行,观察三问在 naive 与 agentic 两条路径下的差异;
> 2. 指认:第 1 问为何命中 k01 而非 k04?第 2 问 naive 为何拒答,agentic 改写后命中哪一块?改写做了什么(口语「证件号」→ 术语问法,含「学号/业务编号/主键/重复」);
> 3. 把 `MIN_SCORE` 调到 0.60 重跑:第 1 问相似度约 0.46,虽指向 k01 却被阈值否决,触发改写仍无果、最终拒答——解释「阈值太高=否决够用的依据,白花一轮检索」;把 `MAX_RETRY` 改为 0 重跑第 2 问,改写被禁止、检索失败即拒答——解释重试上限如何防检索死循环;
> 4. (思考,不必写码)若把改写换成由模型完成,你会给它什么 system prompt 约束(提示:只能改写表述、不许编造答案,呼应 02.02 的 01 章)。
>
> ```python
> # retrieval_agent_demo.py —— 工具化检索 + 评估-改写-重查循环(纯 Python 3,无第三方依赖)
> import math
>
> DIM = 8192         # 高维桶降低哈希碰撞(教学版低维会造成假命中;真实 embedding 数百~数千维)
> MIN_SCORE = 0.10    # 低于此分视为「没有依据」
> MAX_RETRY = 1       # 改写重查上限,防死循环
>
> CORPUS = [
>     {"id": "k01", "title": "主键与唯一性",
>      "text": "主键唯一标识一行记录,不能重复也不能为空,一张表只能有一个主键。"},
>     {"id": "k02", "title": "外键与引用完整性",
>      "text": "外键引用他表的主键,外键列允许为空,为空代表尚未关联任何父记录。"},
>     {"id": "k03", "title": "索引与写入性能",
>      "text": "索引能加速查询,但每次写入都要同步维护索引,写入因此变慢。"},
>     {"id": "k04", "title": "业务主键的选型",
>      "text": "学号、订单号这类业务编号常被选作主键,同样不能重复,选定后不宜修改。"},
> ]
>
> def to_chars(text):
>     """只保留中文字符,便于做字符二元组(同 04 章)。"""
>     return "".join(ch for ch in text if "\u4e00" <= ch <= "\u9fff")
>
> def stable_hash(pair):
>     """确定性哈希:进程无关,保证每次运行结果一致。"""
>     value = 0
>     for ch in pair:
>         value = (value * 131 + ord(ch)) & 0xFFFFFFFF
>     return value
>
> def embed_text(text):
>     """教学近似 embedding:中文字符二元组哈希累加后归一化。"""
>     vector = [0.0] * DIM
>     chars = to_chars(text)
>     for i in range(len(chars) - 1):
>         vector[stable_hash(chars[i:i + 2]) % DIM] += 1.0
>     norm = math.sqrt(sum(v * v for v in vector))
>     return [v / norm for v in vector] if norm > 0 else vector
>
> for chunk in CORPUS:  # 入库:给每块预计算向量
>     chunk["vector"] = embed_text(chunk["text"])
>
> def cosine_similarity(a, b):
>     return sum(x * y for x, y in zip(a, b))
>
> def search(query):
>     """检索工具:返回超过阈值、按分数降序的命中块。"""
>     q_vec = embed_text(query)
>     hits = []
>     for chunk in CORPUS:
>         score = cosine_similarity(q_vec, chunk["vector"])
>         if score >= MIN_SCORE:
>             hits.append((score, chunk))
>     hits.sort(key=lambda pair: pair[0], reverse=True)
>     return hits
>
> def rewrite_query(query):
>     """改写查询:把口语说法扩展为含资料术语的问法(教学规则版;真实系统由 LLM 完成)。
>     只改表述、不编内容,是改写必须守住的边界。"""
>     expansions = [
>         ("证件号", "学号这类业务编号能否重复,学号适合作为主键吗"),
>         ("学生证号", "学号这类业务编号能否重复,学号适合作为主键吗"),
>     ]
>     for slang, canonical in expansions:
>         if slang in query:
>             return canonical
>     return query
>
> def answer_naive(query):
>     """对照:只检索一次,不做评估与改写。"""
>     hits = search(query)
>     if not hits:
>         return "拒答:一次检索无依据,资料未覆盖或问法不匹配。"
>     score, chunk = hits[0]
>     return "直接作答:依据 %s「%s」(相似度 %.2f)" % (chunk["id"], chunk["title"], score)
>
> def answer_agentic(query):
>     """Agentic:检索→评估不足→改写重查,受 MAX_RETRY 限制。"""
>     for attempt in range(MAX_RETRY + 1):
>         hits = search(query)
>         if hits and hits[0][0] >= MIN_SCORE:
>             score, chunk = hits[0]
>             return "作答:第 %d 轮检索命中 %s「%s」(相似度 %.2f)" \
>                    % (attempt + 1, chunk["id"], chunk["title"], score)
>         if attempt < MAX_RETRY:
>             old = query
>             query = rewrite_query(query)
>             print("  → 评估:依据不足,改写查询「%s」→「%s」后重查" % (old, query))
>     return "拒答:重试 %d 次仍无依据,明说资料未覆盖。" % MAX_RETRY
>
> def main():
>     questions = [
>         "主键能不能为空?能不能重复?",
>         "班里两名学员会拿到相同的证件号吗?",
>         "外键列允许为空吗?",
>     ]
>     for question in questions:
>         print("提问: %s" % question)
>         print("[naive]   %s" % answer_naive(question))
>         print("[agentic] %s" % answer_agentic(question))
>         print("-" * 52)
>
> if __name__ == "__main__":
>     main()
> ```
>
> **完成标准**:输出符合预期——第 1 问两条路径都命中 k01;第 2 问 naive 拒答,agentic 先打印「评估:依据不足」再命中 k04;第 3 问命中 k02。调阈值与 `MAX_RETRY` 后能解释「阈值越高检索成本越高」「上限防止检索死循环」;并能用一句话说出:工具化检索让「查不查、查到何时为止」从代码决定变成 Agent 决定。

## 6. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 每问都触发改写重查 | `MIN_SCORE` 过高,或语料缺口语同义表达 | 调低阈值;补语料(收集高频未命中问法) |
| 改写后仍查不到 | 语料确实未覆盖该内容 | 明说「资料未覆盖」,不硬编(呼应 02.02 的 01 章) |
| 命中片段但答非所问 | 语义相似 ≠ 覆盖问题(04 章) | 加决策 3:评估片段够不够,不够就再检 |
| 引用是编的 | 生成时没限制只能引用返回片段 | 引用正确性评测(4.3);system prompt 约束引用范围 |
| 检索循环停不下来 | 无重试上限 | 设 `MAX_RETRY` 与成本预算(呼应 02.03 的 05 章) |
| 讲义含图/表查不到 | 语料只有纯文本,未做多模态索引 | 01.05 的图文检索:图与文嵌入同一语义空间 |

- 边界提醒:**工具化检索不是越复杂越好**。单跳、问法与讲义接近时,流水线 RAG 更省更快;Agentic RAG 的改写与重查是「以更多 token 和延迟换召回率」,适合多跳与口语问法密集的场景;检索再聪明,也补不了脏语料的坑(01.02)。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| RAG | 生成前先从外部语料检索片段拼进上下文(04 章向量库的用途) |
| 何时先检索 | 私有新语料、需引用、错误代价高;闲聊与常识不必 |
| 检索-规划联动 | 先检索再规划(开场拉料)vs 边规划边检索(缺口驱动) |
| 四个决策点 | 要不要检 → 阈值够不够 → 片段答不答得了 → 改写还是放弃 |
| 评测口径 | 命中率(检索器)+ 引用正确性(整链),02.07 展开 |

**思考题**:同样回答「证件号能撞吗」,为什么流水线 RAG 会直接拒答或乱答,而 Agentic RAG 有机会答对?改写查询多花了一次检索,这笔成本在什么场景下值得、什么场景下纯属浪费?

> [!note] 参考答案
> 流水线 RAG 用用户原话检索一次,「证件号」与语料里的「学号/主键」字面零重叠(教学近似版尤其明显),捞不到就空答或硬编;Agentic RAG 多一次「评估→改写」的机会,把口语归约为资料术语后命中业务主键选型块,再依据片段作答。值得的场景:问法自由、多跳、答错代价高(考试答疑、规范解释);浪费的场景:单跳且问法与资料接近,或语料覆盖面小——改写只是把「没有」再确认一遍,此时应把成本花在补语料而非加循环。
