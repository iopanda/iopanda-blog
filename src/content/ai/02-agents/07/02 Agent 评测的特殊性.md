# Agent 评测的特殊性

> 02.06 的末篇把「评测难」列为多 Agent 的头号拦路虎,结论是能单 Agent 解决就不要上多 Agent。可课程助教这个单 Agent,今天也撞上了自己的「评测难」:它不再回一句话就完事,而是先想、再查资料、翻学员档案、算分数、甚至写记忆,转了好几圈才交出答案——01.06 那套「给输入、对答案、算准确率」的老办法,已经称不出它的好坏。本章是 02.07 Evaluation and Observability 的开篇,回答评测这件事在 Agent 这里为什么「变味了」:评测对象从「单输出」长成了「轨迹 + 结果 + 副作用」三件套,失败要按五层归因,评测本身要分四层设计。

**学习目标**:学完本章,你将能够——

1. 说出 Agent 评测对象的三个组成部分:轨迹、最终结果、副作用;
2. 解释 Agent 评测与普通 LLM 评测的三个本质差异(结果开放、过程重要、副作用要测);
3. 面对一次失败,按「模型/提示/工具/记忆/编排」五个层次做归因排查;
4. 复述单步、轨迹、任务、系统四层评测各自回答什么问题;
5. 指出某条轨迹用「只对答案」的旧方法评测会漏掉什么。

## 1. 概念:评测对象从「单输出」变成「三件套」

- **普通 LLM 评测**(01.06):输入一句问题,输出一段回答,拿标准答案或裁判比对——评测对象是**单输出**。输入输出之间没有中间步骤,也没有外部动作。
- **Agent 评测**:课程助教完成任务要跑好几轮循环(呼应 02.01 的运行循环):思考、调用 `search_material` 查讲义、调 `calculate` 算分、翻 `get_learner_profile` 档案,最后才给出回答。评测对象随之变成**三件套**:

| 对象 | 是什么 | 课程助教例子 |
|---|---|---|
| 轨迹(trajectory) | 从收到任务到给出最终回答的完整步序列,含思考、工具调用与观察 | 「先查第 3 章讲义 → 再查学员档案 → 才回答」这串过程 |
| 最终结果(final result) | 最后交出的回答或产物 | 对外键问题的解释、批改后的分数 |
| 副作用(side effects) | 执行中对外部世界造成的可观察改变 | 把「已学 HAVING」写进了学员档案;消耗的 token 与费用 |

- 一条真实感的轨迹(步类型 T/C/O/A 的写法与 02 章一致):

```text
task: 学员问「WHERE 和 HAVING 有什么区别?」
step1 T: 问题涉及聚合查询,先定位第 3 章讲义
step2 C: search_material(query="WHERE HAVING 聚合函数", chapter="第3章")
step3 O: 命中两条:WHERE 过滤行、HAVING 过滤组
step4 A: 「WHERE 在分组前过滤行,HAVING 在分组后过滤组;见第 3 章 3.2 节。」
副作用:无写入;若第 2 步后调用了 save_learner_profile,就是本任务的副作用
```

- 一句话:**普通评测评「一句话说得好不好」,Agent 评测评「一串行动是否达成了目标、代价是什么、留下了什么」**。

## 2. 为什么需要:三个差异让旧方法失效

| 维度 | 普通 LLM 评测 | Agent 评测 |
|---|---|---|
| 评测对象 | 一句话输出 | 轨迹 + 结果 + 副作用 |
| 结果形态 | 有唯一标准答案,可自动比对 | 开放:多条正确路径、多个可接受答案 |
| 过程 | 不重要,只看答对没有 | 重要:绕路、瞎试、危险步也是错 |
| 副作用 | 无(纯文本) | 有:写记忆、改数据、花钱 |
| 评测成本 | 一问一测,便宜 | 一任务多轮多次调用,贵 |

### 2.1 差异一:结果开放,没有唯一标准答案

- 「怎么复习外键」可以查了资料再答、可以按档案里的水平调整深浅、也可以直接引讲义原文——都算对。「参考答案必须唯一」是旧方法的地基,这个地基在 Agent 场景塌了。
- 含义:评测要么定义「可接受的等价结果集合」(03 章),要么让裁判按 rubric 判(04 章),不能指望字符串相等。

### 2.2 差异二:过程重要,走错路也算错

- 同一个正确答案,2 步能拿到,也可能绕 8 步——其中 5 步在瞎试。任务级指标(03 章)会报「成功」,过程问题全被吞掉。
- 证据:WebArena 论文里,弱模型最典型的失败模式就是**重复无效动作、撞上步数上限**;AgentBench(ICLR 2024)把模型放进操作系统、数据库、网页购物等 8 类环境做多轮交互,发现模型离「可用」还差得远——最强模型端到端成功率也仅 14.41%(WebArena,人类 78.24%)。**多轮行动放大了单步错误的代价**,这正是过程必须入评的原因。
- 含义:轨迹本身是评测对象(02 章),因为每一步都可能触发成本、权限动作与不可逆副作用。

### 2.3 差异三:副作用要测,答对了也可能闯祸

- 课程助教在讲解中把「学员已掌握 HAVING」写进 SQLite 档案(02.05 的长期记忆),可学员其实没听懂——**结果正确,记忆却被污染**,之后所有会话的上下文都带错(呼应 02.05 的 06 章)。
- 副作用坏就坏在「最终答对也拦不住」:它发生在过程里,只评结果永远看不见。
- 含义:评测清单必须包含「不该发生的写入/调用」检查;权限层(02.04 的 06 章)是第一道闸,评测是第二道。

## 3. 作用:失败要能归因,评测要分层

### 3.1 失败溯源难:五个层次的嫌疑犯

- 助教答错了,追问一句「为什么错」,答案可能是任何一个环节:

| 层次 | 典型症状 | 定位手段 |
|---|---|---|
| 模型 | 幻觉、没按格式输出、能力不足 | 换模型/换温度对比;01.06 单测 |
| 提示 | system prompt 没写清「没依据就拒答」 | 固定任务集上改提示做 A/B(呼应 02.02 的 01 章) |
| 工具 | 工具定义错、实现 bug、检索返回脏数据 | 单测每个工具;手工调一次看返回 |
| 记忆 | 读了被污染的档案、取错学员 | 查档案内容与写入日志(呼应 02.05 的 06 章) |
| 编排 | 循环逻辑错、上一步结果没传给下一步 | 重放轨迹逐步核对(05 章 tracing 的用武之地) |

- 呼应 02.06 的级联错误:多 Agent 的级联是 Agent 之间互相污染;单 Agent 内部同样会级联——**上一步的错误输出是下一步的输入**,错会一步步放大,最后一击往往不是真正病因。没有轨迹记录,归因只能靠猜。

### 3.2 评测分层:一层回答一个问题

```text
单步层  ← 每一步对不对?(工具选对没、参数合法没、回答要点齐没)
轨迹层  ← 整条路顺不顺?(重复、绕路、死循环)——02 章
任务层  ← 目标到没到?(完成率、成功率、部分完成)——03 章
系统层  ← 代价与风险?(成本、延迟、安全、多用户串扰)——06 章
```

| 层 | 评测对象 | 典型问题 | 对应章节 |
|---|---|---|---|
| 单步层 | 一次调用、一句话 | 这一步该不该发生、做对没有 | 02 章的单步成分;05 章数据 |
| 轨迹层 | 整条行动序列 | 有没有绕远路、重复、死循环 | 02 章 |
| 任务层 | 最终目标 | 任务达成没有、完成到什么程度 | 03 章 |
| 系统层 | 长期运行的整体 | 成本、安全、多用户下的稳定 | 06 章 + 01.07 |

- 设计顺序:**先任务层定「什么叫成功」,再轨迹层定「什么叫走得好」,单步层负责定位具体坏点,系统层把成本与风险也计入账**。

## 4. 详细介绍:旧评测方法的四个漏点

| 旧做法 | 会漏掉什么 | 例子 |
|---|---|---|
| 只比对最终答案字符串 | 绕路与重复调用 | 明明一次检索就够,却搜了 4 次才答——结果对,成本 4 倍 |
| 只报答对率 | 副作用污染 | 档案被写脏,之后所有会话上下文带错 |
| 只测单轮问答 | 多轮才暴露的累积错误 | 第 1 步检索词错,第 4 步才答错,病因在第 1 步 |
| 没有副作用清单 | 越权与破坏性调用 | 助教把「零基础」学员的档案覆盖成了「入门」 |

- 四个漏点不是「换更好的答案比对」能修的,而是**评测对象没选对**;对象选对了,才谈得上指标(02 章)、任务集(03 章)与裁判(04 章)。
- 评测要能跑起来,还差一个前提:**能拿到轨迹**——这正是 05 章 tracing 的职责;没有记录,「分层评测」只是纸上谈兵。

## 5. 动手活动:同一个任务,两种评测口径差多少

> [!example] 动手活动:对比「只评结果」与「分层审查」
>
> **目标**:产出 `reports/result-vs-process.md`——用脚本对比同任务的两条轨迹,亲眼看到只评结果会漏掉什么。
>
> **步骤**:
> 1. 读懂下方脚本:`traj_ok` 是 3 步走完的干净轨迹,`traj_sloppy` 是同任务、同最终回答的绕路轨迹(重复检索 + 写了档案);
> 2. 运行 `python eval_objects_demo.py`;
> 3. 把输出抄进报告,列出 `traj_sloppy` 的问题清单;
> 4. 写三句话:如果评测只看最终答案,这两条轨迹得分相同,你会漏掉什么?
>
> **完成标准**:能指出 `traj_sloppy` 至少 2 处轨迹问题与 1 处副作用;报告能说明「结果正确只是及格线,轨迹与副作用才是 Agent 评测的分水岭」。

```python
# eval_objects_demo.py —— 同任务两条轨迹:只评结果 vs 分层审查
# 步格式:(type, tool_or_note, detail);type ∈ thought/tool_call/observation/answer

TASK = "学员问:WHERE 和 HAVING 有什么区别?"

traj_ok = [
    ("thought", "", "先定位第 3 章讲义里讲聚合过滤的段落"),
    ("tool_call", "search_material", 'query="WHERE HAVING 聚合函数", chapter="第3章"'),
    ("observation", "", "命中:WHERE 过滤行、HAVING 过滤组"),
    ("answer", "", "WHERE 在分组前过滤行,HAVING 在分组后过滤组;见第 3 章 3.2 节。"),
]

traj_sloppy = [
    ("thought", "", "先搜一次看看"),
    ("tool_call", "search_material", 'query="WHERE 与 HAVING"'),
    ("observation", "", "命中两段相关讲义"),
    ("thought", "", "不太放心,再确认一次"),
    ("tool_call", "search_material", 'query="WHERE 与 HAVING"'),   # 同参数重复 = 冗余
    ("observation", "", "还是那两段"),
    ("tool_call", "get_learner_profile", 'learner_id="L-1001"'),   # 本题非必需
    ("observation", "", "零基础学员"),
    ("thought", "", "按零基础讲,顺手记为已学 HAVING"),
    ("tool_call", "save_learner_profile", 'learner_id="L-1001", field="learned", value="HAVING"'),
    ("answer", "", "WHERE 在分组前过滤行,HAVING 在分组后过滤组;见第 3 章 3.2 节。"),
]

GOLD_PHRASES = ["WHERE", "HAVING", "过滤"]


def result_only_grade(trajectory):
    """旧口径:只看最终回答是否包含全部关键短语"""
    answer = next(step[2] for step in trajectory if step[0] == "answer")
    return all(phrase in answer for phrase in GOLD_PHRASES)


def audit_trajectory(trajectory):
    """新口径:分层审查,返回问题清单"""
    issues, seen_calls = [], []
    for kind, tool, detail in trajectory:
        if kind != "tool_call":
            continue
        call = (tool, detail)
        if call in seen_calls:
            issues.append(f"轨迹问题:重复调用 {tool}({detail})")
        seen_calls.append(call)
        if tool == "save_learner_profile":
            issues.append(f"副作用:写入档案 {detail},需核对是否该写")
    return issues


def tool_call_count(trajectory):
    return sum(1 for step in trajectory if step[0] == "tool_call")


def main():
    print(f"任务:{TASK}")
    for name, trajectory in [("traj_ok    ", traj_ok), ("traj_sloppy", traj_sloppy)]:
        grade = "通过" if result_only_grade(trajectory) else "不通过"
        issues = audit_trajectory(trajectory)
        print(f"{name}:最终答案检查 = {grade};工具调用 {tool_call_count(trajectory)} 次;")
        for issue in issues:
            print(f"    - {issue}")
        if not issues:
            print("    - 轨迹审查:0 个问题")


if __name__ == "__main__":
    main()
```

## 6. 边界:别把「对象变多」误读成「全自动评测」

- **分层不是越全越好**:四层全自动评测又贵又吵;现实节奏是人工抽检小集起步,再逐步自动化(06 章的回归循环)。
- **轨迹漂亮 ≠ 任务成功**:助教查了资料、步数优雅,却编造讲义里没有的结论——轨迹层全绿,任务层失败;这类漏网要任务级判定与裁判兜底(03、04 章)。
- **结果开放 ≠ 怎么答都行**:要同时定义「可接受的等价结果集」与「禁区」(不许编造、不许外泄、不许越权),后者往往比前者更重要。
- **副作用清单要随工具维护**:每接入一个新工具(如 02.04 的 05 章 MCP 接入),评测清单就要同步补上它的副作用检查项。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 评测对象三件套 | 轨迹 + 最终结果 + 副作用 |
| 差异一:结果开放 | 没有唯一答案,要等价结果集或裁判 |
| 差异二:过程重要 | 绕路、瞎试、危险步也是错(02 章量化) |
| 差异三:副作用要测 | 答对了也可能写脏记忆、越权调用 |
| 失败归因 | 模型/提示/工具/记忆/编排五层排查 |
| 评测分层 | 单步 → 轨迹 → 任务 → 系统,一层一个问题 |

**思考题**:课程助教查了资料、算对了平均分、最终答案完全正确——但它在过程中把「零基础」学员的档案错误覆盖成了「已入门」。如果评测报告只写「任务成功率 100%」,你会漏掉什么?这条事故该记进三件套里的哪个对象、由哪一层来抓?

> [!note] 参考答案
> 会漏掉副作用污染:档案被改后,该学员后续所有会话的上下文都带错水平设定,影响远超这一次回答(呼应 02.05 的 06 章记忆污染)。它属于三件套里的「副作用」对象,应写进副作用清单做禁止性检查,并由系统层(写操作审计)兜底——这也再次说明:结果正确只是及格线,Agent 评测的分水岭在轨迹与副作用。
