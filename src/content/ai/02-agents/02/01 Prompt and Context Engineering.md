# Prompt and Context Engineering

> 模块定位：Agent 与普通聊天的区别之一在于它会连续多轮使用上下文：system prompt、用户输入、工具结果、历史、检索片段都挤在同一个上下文窗口。本模块解决「怎么构建这个上下文，让模型稳定做对事、且不被不可信内容带偏」。

**学习目标**：完成本模块后，你将能够——

1. 设计 system prompt 定义角色、边界与输出格式；
2. 管理长上下文：截断、压缩、关键信息前置；
3. 用结构化输出（JSON schema / function calling 格式）约束模型；
4. 识别并缓解提示注入（呼应 01.07 的 OWASP LLM01）；
5. 为 Agent 写出「上下文构建清单」。

## 子主题清单（每章讲义要点）

### 01 System Prompt 设计
- 概念：system prompt 是 Agent 的行为宪法（角色/边界/规则/输出风格）
- 为什么需要：模型没有内置「助手应该如何做事」，全靠上下文塑造
- 写法：具体而非抽象、正反例、分层（角色 → 任务 → 约束 → 输出格式）
- 关键警告：system prompt 不是安全边界——不可信用户仍可诱导（引 01.07）

### 02 上下文窗口管理
- 概念：上下文窗口 = 模型一次能看到的 token 数上限；Agent 的「工作台」
- 为什么难：Agent 多轮累积（历史+工具结果）会迅速占满窗口
- 策略：窗口预算分配表、滑动窗口、关键信息前置、滚动摘要
- 指标：实际利用率 vs 窗口上限、截断丢了什么

### 03 少样本示例与指令遵循
- 概念：in-context learning——在上下文里放少量「输入→期望输出」示例
- 为什么有效：示例比抽象指令更易被模仿（呼应 01.02 数据混合直觉）
- 选例：覆盖边界与失败案例、与任务同分布
- 局限：示例过多吃上下文、示例本身可被注入利用

### 04 结构化输出约束
- 概念：让模型输出 JSON / 特定 schema，而非自由文本
- 为什么需要：Agent 的下游是代码——工具调用参数、状态转移都需要机器可读
- 手段：提示要求 JSON、response_format/json_schema、function calling 参数约束
- 校验闭环：schema 校验 + 解析失败重试；不能只信「模型说它是 JSON」

### 05 Agent 上下文构建模式
- 概念：一次 Agent 步的上下文 = system + 历史 + 当前输入 + 工具结果 + 检索片段
- 常用模式：角色块、工具说明块、检索引用块、历史压缩块
- 动手：为课程助教 Agent 设计上下文模板，比较「乱拼」与「结构化拼」的效果
- 关键：工具结果属于「不可信内容」——与用户输入同等对待（防间接注入）

### 06 提示注入与上下文隔离
- 概念：直接注入（用户消息里写指令）vs 间接注入（网页/检索内容带指令）
- 为什么难防：指令与数据共用同一窗口，无参数化查询（呼应 02.07/01.07）
- 缓解思路：内容与指令标记隔离、输入输出过滤、权限最小化
- 动手：构造 3 条注入样例，测试自己的上下文模板是否扛得住

## 交付物与验收标准

| 章 | 交付物 | 验收 |
|---|---|---|
| 01+05 | system prompt + 上下文模板 | 固定 10 问上行为稳定、格式符合 |
| 04 | 结构化输出解析器 | 非法 JSON 能检出并重试，不崩溃 |
| 06 | 注入测试记录 | 能复现并说明哪种缓解有效/无效 |
