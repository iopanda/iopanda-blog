# 上下文窗口管理

> 01 章定住了「模型该怎么表现」——system prompt 是行为宪法。可另一道算术题随之而来:system prompt、学员 20 轮提问、你的回答、检索工具每次吐回的整页资料,模型一次推理真的全看得过来吗?答案是看不过来:**上下文窗口是有限的**。本章是 02.02 的第二课,讲清窗口的物理上限、Agent 为什么特别容易把它塞满,以及预算分配、滑动窗口、关键信息前置、滚动纪要四类策略——最后用模拟脚本亲眼观察「窗口占满与压缩」的现场。

**学习目标**:学完本章,你将能够——

1. 说出上下文窗口的概念(token 上限 / 工作台)与它的两个物理限制;
2. 用算术解释为什么 Agent 的多轮历史与工具结果会迅速占满窗口;
3. 按「预算分配表」为一次调用规划 system / 历史 / 工具 / 输入的配额;
4. 解释滑动窗口、关键信息前置、滚动纪要各解决什么问题、代价是什么;
5. 用「窗口利用率」与「截断丢了什么」两个指标审计自己的 Agent。

## 1. 概念:上下文窗口 = Token 上限 + 工作台

- **上下文窗口(context window)**:模型一次推理能「看到」的全部 token 数量上限;模型只基于窗口内内容作答,窗口之外的内容对它等于不存在,不会自动翻页去找。**Token** 是模型处理文本的最小单位——英文约 4 字符 ≈ 1 token(≈ 0.75 词),中文大致 1 字 ≈ 1~2 token(因分词器而异);「窗口 128K」= 一次最多容纳约 12.8 万 token 的输入。
- **工作台类比**:窗口像一张桌面——资料全摊开才好引用,但桌面就那么大;放不下的资料,要么收进抽屉(外部存储,02.05 展开),要么忍痛精简。注意:**窗口 ≠ 记忆**,窗口内容每次调用都重新组装,关闭即清空,多轮「记忆」只是你把历史又塞了回来。
- 两个物理限制:①**硬上限**——输入(含输出)超限,API 直接报错或静默截断;②**软稀释**——内容越长,模型对中段的注意力越弱(呼应 01 章 4.3「中间规则被稀释」)。

## 2. 为什么需要:Agent 是怎么把窗口塞满的

- 聊天机器人每轮只新增一问一答,增长慢;Agent 的上下文却要叠加 system + 全部历史 + 工具结果 + 检索片段,「重物」多、增长快:

| 来源 | 单次体量(典型) | 为什么大 |
|---|---|---|
| System Prompt | 0.5K~2K token | 常驻,每轮都在 |
| 问答历史 | 每轮 1K~3K token | 随轮数线性累积,默认永不清空 |
| 工具结果与检索片段 | 每次 2K~30K token | 检索吐整页、日志不截断、一次带回 3~10 段 |

- 算一笔账:128K 窗口,预留 8K 给输出;system 1K + 每轮(问答 2K + 工具结果 8K)≈ 11K,约 11 轮后输入逼近上限,若单次工具结果 30K 则两三轮即满。塞满后的两种死法:①直接报错 `context_length_exceeded`,学员看到助教「卡死」;②框架「贴心」静默截断——通常丢最早的内容,模型毫无察觉,于是忘了早期约定、引用已被删除的检索、前后矛盾(呼应 01 章:角色设定也可能随截断丢失)。

## 3. 作用:窗口管理在 Agent 里的位置

- 回看 02.01 的运行循环:每轮「感知」都要重装上下文——窗口管理正是感知环节的**装载策略**:装什么、装多少、装不下怎么办。一句话:system prompt 决定「往哪个方向表现」,窗口管理决定「装不装得下」;输入 token 按量计费,塞得越满每轮越贵(呼应 01.04)。
- 与前后章节的分工:01 章定 system prompt(常驻块);03 章少样本示例继续占用窗口;02.05 记忆与检索负责把「窗口装不下的」搬到窗外。

## 4. 详细介绍:四类管理策略

### 4.1 预算分配表:先分钱,再花钱

- 思想:每次调用前把窗口当预算逐块分配,总和留 10%~20% 给输出与余量——**输出 token 与输入共用同一窗口**,预算算错照样超限;预算表应写进代码或工程备注,让「每轮装什么」从拍脑袋变成可审计的约定。以 128K 窗口、目标输入 ≤ 100K 为例:

| 块 | 配额 | 装什么 | 超配怎么办 |
|---|---|---|---|
| System Prompt | ≤ 5K | 角色 / 任务 / 约束 / 格式(01 章产物) | 精简措辞,不许超 |
| 当前输入 | ≤ 10K | 学员本次问题与附件 | 提示拆问或精简 |
| 工具结果 | ≤ 40K | 本轮检索 / 工具返回 | 只留命中段落 |
| 历史 | ≤ 35K | 滚动纪要 + 最近原文轮次 | 压缩旧轮(4.4) |
| 输出余量 | ≥ 28K | 模型的回答 | 压缩阈值前移 |

### 4.2 滑动窗口:只留最近 N 轮

- 规则:历史只保留最近 N 轮(如 6 轮),更早的直接丢弃;system 永远保留。实现只有几行(见第 6 节),把输入从「线性增长」变成「封顶」;代价是**硬遗忘**——被滑掉的早期信息模型彻底看不到,学员第 2 轮说的「我是零基础」,第 9 轮起不再影响回答。

### 4.3 关键信息前置:开头结尾最容易被记住

- 位置效应:模型对上下文开头(primacy)与结尾(recency)的遵循最好,中段最易被稀释——与 01 章「system prompt 中间规则失效」同源。落地:①最重要的约束与目标放 system 开头;②每轮把「本轮任务」放最新一条消息重申(占住结尾);③必须在场的事实(学员水平、课程范围)放开头或在用到它的那一轮附近重提——别把重要内容埋在历史中部,截断时它最先被牺牲。

### 4.4 滚动纪要:旧轮次浓缩成一段话

- 思想:与其丢,不如压——把早期轮次提炼成纪要(模型生成或规则抽取均可),置于 system 之后享受开头效应;每轮携带「纪要 + 最近几轮原文」。升级路径:单层纪要 → 分层纪要(天级 / 会话级,02.05 展开),纪要自身膨胀到配额上限时,就轮到「纪要的纪要」。

| 策略 | 解决什么 | 代价 / 风险 |
|---|---|---|
| 预算分配表 | 结构失控、静默超限 | 配额需人工维护 |
| 滑动窗口 | 历史线性膨胀 | 早期信息硬丢失 |
| 关键信息前置 | 重要内容被稀释 / 截断 | 重提占用 token |
| 滚动纪要 | 早期语义流失 | 纪要失真、有压缩开销 |

- 工程惯例:四者组合——预算表定框架;利用率超 70% 触发压缩;压缩先滑掉最旧原文,把被滑轮次喂给纪要;纪要置于开头。

## 5. 指标:利用率与「截断丢了什么」

- **窗口利用率**:本轮输入 token ÷ 窗口上限。OpenAI 兼容 API 每次返回 `usage.prompt_tokens`,直接可测;维护利用率曲线并设双阈值——70% 预警(启动纪要 / 滑窗),90% 强制压缩。
- **截断审计**:每次压缩记录「丢了哪几轮、哪段工具结果」并回答三问:影响规则吗(如 system 中段条款丢失 → 三点式失守)?影响事实吗(如学员「零基础」背景丢失 → 用词过专业)?影响证据吗(回答依据的检索被删 → 引用凭空出现)?三问都否才安全。
- 隐藏成本:模型通常**不知道自己被截断**——被删的内容不会打招呼;压缩动作要写入可见处(如纪要注明「早期对话已压缩」),并保留审计日志。

## 6. 动手活动:模拟窗口占满与压缩

> [!example] 动手活动:window_sim.py——亲眼看窗口被塞满与压缩
>
> **目标**:观察课程助教五轮问答中窗口利用率「爬升 → 超限 → 压缩回落 → 再爬升」的锯齿曲线,并说清两次压缩各丢了什么、留下了什么。运行方式:保存为 `window_sim.py` 后执行 `python3 window_sim.py`(纯 Python 3、无第三方依赖;`count_tokens` 是粗略估算,真实限额以 API 返回的 `usage.prompt_tokens` 为准)。
>
> **步骤**:
> 1. 运行脚本,记录每次输出的占用与利用率,标出「超限!」所在行;
> 2. 对照审计输出,说明两次压缩各丢弃几条原文、纪要新增几句结论;
> 3. 数一数两次压缩后利用率各回落到多少,解释为什么还会再涨上来;
> 4. 删掉 `compress` 里 `self.notes.extend(added)` 一行重跑,对比第二次压缩后助教还记得多少早期结论。
>
> ```python
> # window_sim.py —— 模拟课程助教窗口占满与压缩(纯 Python 3,无第三方依赖)
> def count_tokens(text):
>     cn = sum(1 for ch in text if "\u4e00" <= ch <= "\u9fff")   # 中文字符 1 个 ≈ 1 token
>     return cn + (len(text) - cn + 3) // 4                       # 其余按 4 字符 ≈ 1 token
> def join(messages, summary):
>     parts = ["[纪要] " + summary] if summary else []
>     parts += ["[%s] %s" % (m["role"], m["content"]) for m in messages]
>     return "\n".join(parts)
> class Window:
>     """上下文窗口:system 常驻;超限即压缩(滑窗 + 滚动纪要)。"""
>     def __init__(self, system_prompt, limit):
>         self.system_prompt = system_prompt   # 常驻块,永不压缩(01 章产物)
>         self.limit = limit                   # 窗口上限(token)
>         self.history = []                    # 原文消息 [role, content]
>         self.notes = []                      # 纪要:被压缩轮次提炼出的结论
>         self.audit = []                      # 截断审计:每次压缩丢了什么
>     def used(self):
>         head = [{"role": "system", "content": self.system_prompt}]
>         return count_tokens(join(head + self.history, self.summary()))
>     def summary(self):
>         return "纪要:" + "；".join(self.notes)
>     def add(self, role, content):
>         """追加一条消息;超限先压缩。返回(是否压缩, 压缩前占用, 压缩后占用)。"""
>         self.history.append({"role": role, "content": content})
>         before = self.used()
>         if before <= self.limit:
>             return False, before, before
>         self.compress()                     # 超限 → 压缩
>         return True, before, self.used()
>     def compress(self):
>         """滑窗:原文只留最近 2 条;滚动纪要:丢弃轮次的助手结论提炼保留。"""
>         old, self.history = self.history[:-2], self.history[-2:]
>         added = [m["content"] for m in old if m["role"] == "assistant"]
>         self.notes.extend(added)
>         self.audit.append("丢弃 %d 条原文,纪要新增 %d 句结论" % (len(old), len(added)))
> def main():
>     win = Window("你是课程助教。仅依据课程资料回答,没有依据时说不知道。", limit=290)
>     events = [
>         ("user", "主键和外键有什么区别?"),
>         ("tool", "检索结果:主键唯一标识一行记录,不能为空、全表唯一;外键引用另一张表的主键,子表该列的值必须在父表主键中存在或为 NULL,以此保证引用完整性。"),
>         ("assistant", "结论:主键管本表唯一,外键管跨表引用,杜绝悬空引用。"),
>         ("user", "那 CASCADE 会删掉父表行吗?"),
>         ("tool", "检索结果:CASCADE 级联删除:父表行被删除时,数据库自动删除子表中所有引用它的行;适合父子数据同生共死的场景,但子行巨大时锁表时间长。"),
>         ("assistant", "结论:会,删父表行时子表引用行被自动连带删除。"),
>         ("user", "SET NULL 和 CASCADE 有什么不同?"),
>         ("tool", "检索结果:SET NULL 不删除子表行,而是把子表外键列置为 NULL,前提是该列允许空值;适合父记录删除后子记录仍要保留的场景。"),
>         ("assistant", "结论:SET NULL 只置空外键不删行,CASCADE 连坐删除。"),
>         ("user", "那 RESTRICT 又是什么意思?"),
>         ("tool", "检索结果:RESTRICT 与 NO ACTION 都拒绝删除被引用的父表行:只要有子行引用,删除直接报错;区别仅在检查时机(立即 vs 语句结束)。"),
>         ("assistant", "结论:RESTRICT 直接拒绝删除,子行存在就报错。"),
>         ("user", "给学员出两道练习题吧?"),
>         ("tool", "检索结果:练习题模板:①选择题覆盖定义辨析;②简答题要求举例说明两种 ON DELETE 行为的差异,参考答案见课程资料。"),
>         ("assistant", "结论:已按模板出题,题目与答案都回指资料章节。"),
>     ]
>     print("课程助教多轮对话 · 窗口上限 = %d token" % win.limit)
>     for role, content in events:
>         cut, before, after = win.add(role, content)
>         if cut:
>             print("%-10s 超限!%d > %d → 压缩后 %d(利用率 %d%%)" % (role, before, win.limit, after, after * 100 // win.limit))
>             print("   审计:" + win.audit[-1])
>             print("   窗口内:原文 %d 条 + %s" % (len(win.history), win.summary()[:26] + "…"))
>         else:
>             print("%-10s 占用 %d/%d(利用率 %d%%)" % (role, before, win.limit, before * 100 // win.limit))
> if __name__ == "__main__":
>     main()
> ```
>
> **完成标准**:能指着输出说清「哪一行超限、压缩后利用率回落到多少、纪要保留了哪几句结论」;能回答:若只滑窗不纪要(删掉 `self.notes.extend(added)`),第二段对话里助教还记得第一轮讲的「主键管本表唯一」吗?

## 7. 边界与排错

| 症状 | 原因 | 处理 |
|---|---|---|
| 调用报错 context_length_exceeded | 输入 + 输出超窗口上限 | 预算表留足输出余量;压缩阈值降到 70% |
| 越聊越「笨」,忘了早前约定 | 早期轮次被静默丢弃 | 关键约定进纪要或 system;做截断审计 |
| 压缩后仍引用已删的检索 | 纪要失真或丢得太狠 | 纪要保留「结论 + 依据出处」,不只留结论句 |
| 超大单条工具结果,压完仍超限 | 压缩救不了「一条巨物」 | 源头截断:只取命中段落 / 前 N 字符 |

- 边界提醒:窗口管理解决「装不下」,解决不了「窗口内内容互相矛盾或被注入」——那是 06 章提示注入与上下文隔离的战场;超长任务的最终出路是外部记忆(02.05),窗口永远只放「本轮要用的」。

## 8. 总结

| 概念 | 一句话 |
|---|---|
| 上下文窗口 | 一次推理的 token 上限;Agent 的「工作台」,窗外 = 不存在 |
| 为什么难 | 多轮历史 + 工具结果线性累积,十几轮即可占满 128K |
| 预算分配表 | 先定配额、留输出余量,超配逐块压缩 |
| 三件套策略 | 滑窗封顶、关键前置、滚动纪要保语义 |
| 两个指标 | 利用率(触发压缩)与截断审计(丢了什么) |

**思考题**:为什么「把所有历史原封不动塞回窗口」的聊天机器人做法,在 Agent 身上会先撑爆窗口?如果你的课程助教必须记住学员「零基础」这个第 2 轮就提到的背景,而窗口只留最近 6 轮——你会把它放在哪,才能保证第 20 轮还在用?

> [!note] 参考答案
> 聊天机器人每轮只新增一次问答,增量小;Agent 每轮还叠加工具结果与检索片段,单轮增量常是前者的数倍,线性累积下窗口快速见底。「零基础」背景有三条出路:①写进滚动纪要(置于 system 之后,享受开头效应);②写进 system prompt 的「学员档案」区(产品已知信息,常驻最稳,呼应 01 章);③由代码在最新消息里周期性重提。工程上 ① + ② 最常用:纪要管动态,档案管静态。
