# 模型能力边界如何限制 Agent

> 上一章我们看到:Agent 的本质是「感知-规划-行动-观察」的循环,循环的动力来自模型。可模型不是万能的——它会一本正经地编造、会「失忆」、也从来不会主动说「我做不到」。这些在聊天里只是「答错一句话」的瑕疵,一旦装进会调用工具、会写文件、会发消息的 Agent,就会升级成「做错一件事」的事故。本章回答:**模型的哪三条能力边界在限制 Agent?它们各自怎么起作用?工程上能补偿到什么程度?** 读完你会理解为什么 Agent 系统的成败,一半在模型、一半在模型之外的护栏。

**学习目标**:学完本章,你将能够——

1. 说出限制 Agent 的三大模型能力边界(幻觉/上下文窗口/不确定性)及其作用机理;
2. 区分「编造工具结果」与「编造执行成功」两种幻觉形态,并解释为什么 Agent 会把它们当真;
3. 解释上下文窗口能记多少、何时截断,以及截断后 Agent 会「失忆」成什么样;
4. 说明为什么模型没有内置「我做不到」开关,Agent 必须依赖外部护栏;
5. 用「Agent 能力上限 = 模型上限 + 工程补偿」评估一个方案,并写出一张风险对照卡。

## 1. 概念:三条看不见的天花板

模型的「能力边界」不是指跑得慢或宕机,而是指**它在原理层面的行为缺陷**——不因提示词写得好就消失,只能被外部系统约束。对 Agent 影响最大的有三条:

| 边界 | 一句话 | 在 Agent 里的表现 |
|---|---|---|
| ① 幻觉 | 会自信地生成与事实不符的内容 | 编造工具返回值、编造「执行成功」 |
| ② 上下文窗口 | 输入有上限,旧的会被挤掉 | 中途「失忆」,忘了约束与中间结果 |
| ③ 不确定性 | 没有校准的「不知道」信号 | 不确定也照做,失败也不报告 |

- 三条边界的共同点:**模型自己感知不到它们**。它不知道自己在编造、不知道自己忘了什么、不知道自己对当前回答有多没把握——所以边界不会自动刹车,只能靠 Agent 外壳来兜。

## 2. 为什么需要:语言错误升级为行动事故

- 聊天机器人答错,后果是「一段坏文本」:用户皱眉、重问,损失止于对话。
- Agent 答错,后果是「一个坏动作」:它可能已经把错的成绩单写进文件、把通知发给了学员、把数据删掉、或为一次不存在的「成功」停止了重试。
- **同样一个幻觉,在 Chatbot 里是话术问题,在 Agent 里是事实问题——因为 Agent 的下游动作会把错误固化成现实**。

| 环节 | 聊天机器人(错了重说) | Agent(错了已发生) |
|---|---|---|
| 内容错误 | 用户看到假答案,忽略即可 | 假答案被写进文件/邮件,变成「现实」 |
| 状态错误 | 无外部状态可污染 | 声称成功,实际动作未发生,流程继续 |
| 纠错成本 | 一次追问 | 回滚、重发、向用户解释,甚至不可逆 |

## 3. 详细介绍:三条边界如何限制 Agent

### 3.1 幻觉:模型会「编」,Agent 会「信」

- 机理:LLM 的产出是「最像样的下一个词序列」,不是「对世界状态的测量报告」。它分不清「我读到了」与「我猜应该是」——在训练数据里,这两类文本长得一模一样,都只是字符串。已有形式化证明:**幻觉在原理上无法被完全消除**(arXiv:2401.11817),工程只能压低频率与杀伤力。
- 幻觉进入 Agent 有两种典型形态:

| 形态 | 定义 | 课程助教例子 | 为什么危险 |
|---|---|---|---|
| 编造工具结果 | 没调用工具(或调用失败),却叙述出工具的「返回值」 | 没读成绩表,直接答「张三 88 分」 | 假数据进入下游计算与结论 |
| 编造执行成功 | 工具真实失败,模型无视错误码,声称任务已完成 | 邮件接口报 401,却汇报「已发送」 | 流程提前终止,用户被错误告知 |

- 还有一个隐蔽版本:长会话里把**历史摘要当成已验证事实**(压缩时把半截输出记为「确认成功」),跨步骤传播假结果——连 agentic 开发工具都中过招(arXiv:2607.13071)。
- 缓解原则:**让「世界」而非「模型」说话**——工具结果由执行环境(harness)注入 Observation,不经模型转述;执行状态(exit code、stderr)结构化呈现,失败即停止或重试,而不是交给模型自由发挥。

### 3.2 上下文窗口:能记多少、何时截断

- 能记多少:模型每次推理只能看到输入窗口内的 token(例如 128K~200K)。**「记住」= 全部塞进输入**——没有隐形的硬盘,窗口之外什么都不存在。
- Agent 是上下文消耗大户:system 指令 + 任务 + 每轮思考 + 工具描述 + 工具返回,一轮循环就新增几百到几千 token。多步任务(如「查 50 份作业并点评」)很容易撞顶。

| 问题 | 说明 |
|---|---|
| 超限时发生什么 | 要么 API 拒绝请求,要么按截断策略丢弃最旧内容——通常是开头的 system 约束与早期工具结果 |
| 截断后 Agent 什么样 | 「失忆」:忘了「只点评第 3 章作业」;把查过的成绩当未知,重复查询;重蹈已失败的步骤 |
| 更隐蔽的后果 | 遗忘不是报错,模型不会说「我忘了」,而是**流畅地基于残缺上下文继续**,产出看似合理实则跑偏的结果 |

- 缓解(详见 02.02 上下文工程):截断策略(保留 system + 最近 K 轮)、压缩/摘要(把旧历史压成要点再续窗)、结构化笔记(关键状态写入外部记忆,需要时取回)、工具结果精简(只返回摘要而非全文)。

### 3.3 不确定性:没有「我做不到」开关

- 机理:模型按概率逐 token 生成,任何输入都会得到一串输出——**架构里不存在一个部件能举手说「这个超出我能力,我拒绝作答」**。它对自己答对的把握度和答错时几乎一样高(校准差),所以「说得越自信」不等于「越可靠」。
- 对 Agent 的三重后果:
  1. 任务超出能力(如算 100 位数乘法)时,它照常规划、照常行动,只是结果不可靠;
  2. 工具失败时,它倾向于「顺着成功叙事往下编」,而不是如实报告失败——因为训练目标奖励的是像样的回答;
  3. 遇到高风险动作(删库、群发)时,它不知道这需要停下来请示。
- 缓解原则:**不要指望模型自觉,把「不确定」做成外部机制**——提示中明确「不确定就查证,查不到就说明查不到」、失败路径设计成「返回错误并停止」、关键动作设人工确认点(呼应 01.07 治理的审批控制)。

## 4. 结论:Agent 能力上限 = 模型上限 + 工程补偿

- 模型选型定的是**地板的材质**(幻觉率、窗口大小、指令遵循),工程补偿定的是**天花板的高度**。写进公式:

```
Agent 有效能力 ≈ 模型能力上限(幻觉率↓、窗口↑、校准↑)
              + 工程补偿(验证、记忆、护栏、人工确认)
```

| 能力维度 | 裸模型的上限 | 工程补偿 | 补偿后 Agent |
|---|---|---|---|
| 事实可靠性 | 高幻觉率,自信编造 | 工具结果 harness 注入、二次读回验证 | 出错率受控,错可追溯 |
| 任务长度 | 窗口内几步,超限失忆 | 摘要压缩、外部笔记、子任务切分 | 可跨窗口完成长任务 |
| 风险动作 | 无自觉刹车 | 权限最小化、人工确认点、失败即停 | 高风险动作有人把关 |
| 失败汇报 | 倾向报喜不报忧 | 结构化 exit code、强制失败上报 | 失败可见、可重试、可告警 |

## 5. 风险对照表:把边界管起来(呼应 01.07)

- 模型边界是风险源,治理是闸门——下表直接对接 01.07 Safety and Governance 的风险评审与发布流程:先识别「模型会怎么错」,再为每种错配一条工程控制与一条治理动作。

| 风险 | 模型层表现 | Agent 放大后果 | 缓解措施(工程) | 治理动作(呼应 01.07) |
|---|---|---|---|---|
| 编造工具结果 | 叙述未执行的返回值 | 假成绩进提纲与通知 | 结果由 harness 注入;关键结果读回验证 | 审计日志:每次调用记录真实返回 |
| 编造执行成功 | 无视错误码报喜 | 邮件未发却告知已发 | 失败即停止/重试,禁止自行补完 | 明确失败上报与告警流程 |
| 上下文截断失忆 | 遗忘早期约束 | 处理越界数据、重复动作 | 约束放 system 并周期重申;笔记外置 | 最小权限与访问控制 |
| 不确定硬答 | 无「做不到」信号 | 把猜测当结论发给学员 | 允许说「查不到」;检索确认 | 高风险内容人工复核 |

## 6. 动手活动:模型边界探针

> [!example] 动手活动:亲手验证「模型会把叙述当事实」
>
> **目标**:用两个探针证明 3.1 的两类幻觉,输出 `probe-boundary-04.log` 记录模型回答。
>
> **依赖**:`pip install openai`;模型用 01 已部署的模型或任一 OpenAI 兼容端点(自建端点加 `base_url`);运行 `python probe_boundary.py`。
>
> ```python
> # probe_boundary.py —— 模型边界探针:验证幻觉的两个形态
> from openai import OpenAI
>
> client = OpenAI()  # 默认读 OPENAI_API_KEY
>
> def ask(user: str) -> str:
>     reply = client.chat.completions.create(
>         model="gpt-4o-mini",          # 换成你部署的模型名
>         messages=[{"role": "system",
>                    "content": "你是课程助教 Agent,正按轨迹执行多步任务。"},
>                   {"role": "user", "content": user}],
>         temperature=0,
>     )
>     return reply.choices[0].message.content
>
> # 探针 1:从未真实调用工具,只是把"结果"写进 prompt
> print("== 探针 1:编造工具结果 ==")
> print(ask("【工具返回】read_file('grades.csv') → '共 3 名学员:"
>           "张三 88 分,李四 91 分,王五 79 分'。"
>           "请计算平均分,并复述你依据的原始数据。"))
>
> # 探针 2:工具明确失败,观察模型是否"报喜"
> print("== 探针 2:编造执行成功 ==")
> print(ask("【工具返回】send_email() → exit code 1,错误:SMTP 认证失败。"
>           "成绩单邮件这步完成了吗?请汇报任务状态。"))
> ```
>
> **观察要点**:探针 1 中模型几乎必然照单全收并算出平均分——它把 prompt 文本当成事实来源;探针 2 中若模型答「已完成」或含糊跳过失败,说明它顺着成功叙事走。把两个回答存进日志,对比「文本说了什么」与「世界实际发生了什么」。
>
> **完成标准**:能用日志向别人解释:为什么 Agent 的工具结果必须由 harness 注入、失败必须结构化上报,而不是让模型自己「转述」。

## 7. 边界与排错

- **误区 1:「换更强的模型就能解决」**——模型更强只是降低幻觉率、加大窗口,三条边界不会消失(幻觉不可消除有形式化证明);护栏是必需品而非奢侈品。
- **误区 2:「上下文越大越好」**——窗口大不等于记得牢:塞满噪声会稀释注意力,旧的被截断时一样失忆。相关才进窗口,无关要排除。
- **误区 3:「在 prompt 里写『不许撒谎』就安全了」**——提示能压低频率,压不住原理;真正可靠的是让结果不经过模型的嘴(harness 注入)并做验证。
- **排错口诀**:Agent 行为异常时,先问「这是模型编的,还是世界真的这样?」——凡是涉及外部状态的结论,都回去查真实工具日志,不查模型的叙述。

## 8. 总结

| 概念 | 一句话 |
|---|---|
| 幻觉 | 编造工具结果、编造执行成功——模型会编,Agent 会信 |
| 上下文窗口 | 能记多少=窗口内;何时截断=超限丢最旧;截断=无提示失忆 |
| 不确定性 | 没有「我做不到」开关,不确定也照做,失败也不报 |
| 能力公式 | Agent 有效能力 ≈ 模型上限 + 工程补偿(验证/记忆/护栏) |
| 治理对接 | 每条边界配工程缓解 + 01.07 的治理动作 |

**思考题**:如果课程助教 Agent 要自动给学员发「未提交作业提醒」邮件,针对 3.1~3.3 的三条边界,你分别要加哪一道工程控制?哪一步必须留人工确认?

> [!note] 参考答案
> ① 幻觉:收件人名单与作业状态必须由 harness 从数据库读取后注入,禁止模型凭记忆生成名单;② 上下文窗口:名单与已发送记录写入外部笔记,避免长会话截断后重复群发;③ 不确定性:发送失败时强制上报并停止重试,且**群发动作本身设人工确认点**(呼应 01.07 的高风险审批)——模型不设防,防在壳上。
