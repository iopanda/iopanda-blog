# Agent 类型与生态全景

> 上一章你徒手写出了第一个 ReAct Agent:会查文件、会算数、会打印轨迹——你已经「会造循环」了。但真实世界里 Agent 不是一个东西,而是一整个谱系:有的只调一次工具,有的像团队一样分工协作;它们各有各的用途,也各有各的框架。本章是 02.01 的收尾课,回答:**Agent 分哪些类型?生态里有哪些框架与协议?拿到一个任务,该选哪种自主度?** 读完你能给任何任务做一次「选型」,并为后面的框架章节画好地图。

**学习目标**:学完本章,你将能够——

1. 说出按自主度划分的四档(单步工具调用/工作流/自主 Agent/多 Agent),并讲清每档的决策权在谁手里;
2. 列举代码、数据分析、浏览器、客服四类用途 Agent,解释用途与自主度为什么是两个独立维度;
3. 说明 LangGraph、AutoGen、MCP 在生态里各解决什么问题(低层编排/多 Agent 框架/工具连接标准);
4. 用「任务风险 × 错误代价」判定一个任务适合哪一档,并在高代价环节插入人工确认点;
5. 为课程助教的三个真实任务各填一张选型卡,产出 `agent-type-matrix.md`。

## 1. 概念:两个坐标轴,一张全景图

- Agent 类型不是一张清单,而是一张**以任务为中心的地图**,有三个层次:

```
┌─────────────────────────────────────────────────────────┐
│ 用途轴(干什么):代码 / 数据分析 / 浏览器 / 客服 / ……       │
│ 自主度轴(怎么干):单步工具调用 → 工作流 → 自主 Agent →     │
│                  多 Agent                                │
│ 生态层(拿什么干):LangGraph / AutoGen / MCP / 自研         │
└─────────────────────────────────────────────────────────┘
```

- **自主度轴回答「谁在做决定」**:每一步是代码写死的,还是模型临场判断的?决定一个系统的形态。
- **用途轴回答「要接什么工具、什么权限」**:决定系统的工具箱与数据域。
- 两轴正交:同是「代码用途」,既有补全式 Copilot(低自主度),也有自动修 bug 的自主 Agent(高自主度)。本章先沿自主度轴纵向走一遍(§3),再沿用途轴横向扫一遍(§4),最后落到生态与选型。

## 2. 为什么需要:会造循环,更要会选形态

- 05 的 ReAct 循环是「最小引擎」,但真实任务不会问「给我一个循环」,只会问「帮我整理复习提纲」。**同一个引擎,套在不同形态上,成本和风险完全不同**。
- 形态决定三件事:**成本**(每一步都要调用模型吗)、**可控性**(过程能被预判和打断吗)、**风险**(错了能补救吗)。选错形态的典型后果:把一句话能答的题硬做成多 Agent,贵且慢;把必须人审的操作交给全自主 Agent,错得悄无声息。
- 生态里框架众多(LangGraph/AutoGen/……),但**框架是脚手架,不是答案**:不理解形态差异,换个框架只会换一种方式踩同样的坑——这也是本模块坚持先手写、后看生态的原因。

## 3. 详细介绍:按自主度分档

| 档位 | 谁做决定 | 循环 | 代表形态 | 课程助教例子 |
|---|---|---|---|---|
| ① 单步工具调用 | 模型决定「调不调」,只调一次 | 无 | function calling 问答 | 「查一下张三的成绩」 |
| ② 工作流 | 代码/人预编排步骤 | 步骤写死,LLM 只做片段 | RAG 管道、评测流水线 | 「检索资料→生成提纲」固定两步 |
| ③ 自主 Agent | 模型规划、循环直到完成 | 完整 ReAct | 05 手写的循环、调研 Agent | 「调研这章→写讲义→自查」 |
| ④ 多 Agent | 多个角色分工、互相通信 | 多循环并行 | 编排者+专家团队 | 「出题 Agent」+「审题 Agent」 |

- **① 单步工具调用**:一问一答间带一次工具调用,是 01/02 里 function calling 的直接应用。无状态、可预测,错误只影响当前回答。它是 Agent 的最小胚子。
- **② 工作流(Workflow)**:步骤、分支、顺序由**代码预先写死**,LLM 只在被指定的环节出力(写摘要、生成问题)。可调试、便宜、稳定——能确定性写死的步骤,不要交给模型自由发挥。
- **③ 自主 Agent(Agentic)**:步骤事先不可枚举时(「查资料,但查什么资料要边查边定」),模型自己规划-行动-观察,循环直到完成。05 的 ReAct 就是它的最小形态。灵活,但会漂移、会烧 token、会不收敛——04 的三条边界在这里全部放大。
- **④ 多 Agent**:多个 Agent(或 Agent+人类)各持角色与工具,通过消息协作。适合单 Agent 干不完的大任务;代价是通信开销、错误跨角色传播、责任模糊(02.06 展开)。
- 工程建议(Anthropic 也这么主张):**能用低档解决的,不要上高档**。档位是「按需加装」,不是「越高越高级」。

## 4. 详细介绍:按用途分

| 用途 | 核心工具 | 代表产品/形态 | 典型护栏 |
|---|---|---|---|
| 代码 Agent | 读写文件、跑测试、git、终端 | Copilot 补全 → Claude Code/Cursor 类自主编码 | 只读权限、PR 人工合入 |
| 数据分析 Agent | Python 执行、SQL、画图库 | 代码解释器形态 | 沙箱执行、禁止外联 |
| 浏览器 Agent | 浏览器自动化(点击/填表/抓取) | OpenAI Operator、Anthropic Computer Use | 敏感操作二次确认 |
| 客服/知识 Agent | 知识库检索、工单/消息 API | 各厂客服机器人、我们的课程助教 | 回复模板、转人工开关 |

- 洞察一:**底层循环同源**。四类用途跑的都是 05 那个循环,差别只在「工具集」与「上下文素材」——数据 Agent 多一个执行沙箱,浏览器 Agent 多一个点击工具。
- 洞察二:**用途决定权限,自主度决定控制权**。用途告诉你该接哪些工具、给多大权限;自主度告诉你该在哪个环节让人确认。两份决策都要做,缺一不可。
- 课程助教属于「客服/知识类」:工具是资料检索、学员进度查询、讲义生成;而「把成绩写进教务系统」则要单独评估权限与自主度(§6 会用到)。

## 5. 生态与框架预告

| 项目 | 是什么 | 定位 | 何时想起它 |
|---|---|---|---|
| LangGraph | LangChain 团队的低层编排框架 | 用「节点+条件边」的有向图描述循环,自带状态持久化、流式、人工确认(interrupt) | 要把循环做成可控、可断点续跑的生产系统 |
| AutoGen | 微软研究院开源的多 Agent 框架(2023) | AgentChat 等 API 快速搭建「多角色对话团队」;AutoGen Studio 可无代码原型 | 想快速实验多 Agent 协作;新项目官方建议转向 Microsoft Agent Framework(与 Semantic Kernel 融合的长期支持版) |
| function calling | 模型接口协议 | 模型输出里声明「要调用哪个函数」,宿主代为执行并回填结果 | 单步工具调用的底座,02 讲过的催化剂 |
| MCP | 工具连接开放标准 | 「AI 的 USB-C」:宿主↔工具服务器统一协议(发现/调用/鉴权),一次接入处处可用 | 工具要跨多个 Agent/客户端复用时(02.04 展开) |

- 关键时间线(MCP):Anthropic 2024 年 11 月开源 → 2025 年 3 月 OpenAI 采纳、4 月 Google 跟进 → 2025 年 12 月捐给 Linux 基金会下属 Agentic AI Foundation,由多家厂商共同治理。协议之争基本落幕,「工具怎么接」从此有标准答案。
- 定位差别:**LangGraph 管「一个 Agent 内部怎么循环」,AutoGen 管「多个 Agent 之间怎么协作」,MCP 管「Agent 与工具之间怎么连接」**——三者叠加,构成工具协议(function calling/MCP)与编排框架(LangGraph/AutoGen)两层的完整生态。
- 课程地图:02.04 展开工具与 MCP;02.06 展开多 Agent;03 用框架做完整应用。**理解主线仍是 05 那个手写循环**——框架只是把它的状态、重试、断点、人工确认工程化了。

## 6. 选型:任务风险 × 错误代价 → 自主度

- 两问定档:

```
问题 1:任务路线事先固定吗?
  固定(查成绩/固定两步)      → 单步工具调用或工作流
  开放(边查边定下一步)        → 候选自主 Agent
问题 2:一步做错的代价有多大?
  低(答错一句话,重问即可)     → 按问题 1 结果执行
  中/高(写库、发通知、删文件)  → 降一档 + 在危险动作前加人工确认点
```

- 判定表(可复制到选型卡):

| 任务特征 | 推荐档位 | 理由 |
|---|---|---|
| 单次查询,工具明确 | ① 单步工具调用 | 无状态,错只影响一问 |
| 多步但路线固定 | ② 工作流 | 可预测、可调试、便宜 |
| 步骤开放且错误代价低 | ③ 自主 Agent | 灵活换路,错了可重来 |
| 步骤开放且错误代价高 | ③ 自主 Agent + 人工确认点 | 保持灵活,高代价动作前设闸 |
| 任务庞大、需多域专长 | ④ 多 Agent | 分工并行(慎用,先问是否单 Agent 够用) |

- 一句话口诀:**路线固定走工作流,路线开放上自主;错误代价高,就降档、加闸、留审计**——自主度每升一档,护栏(呼应 01.07 与 04 章)就要加一层。

## 7. 动手活动:课程助教任务选型卡

> [!example] 动手活动:为三个真实任务做 Agent 选型
>
> **目标**:输出 `agent-type-matrix.md`——三张选型卡 + 一段可运行的判定脚本。
>
> **步骤**:
> 1. 对下面三个任务各填一张卡(路线固定?错误代价?推荐档位?在哪个环节加人工确认?):
>    a. 学员问「我上次作业多少分」——按学号查成绩表回答;
>    b. 期末前自动生成「每人一份的个性化复习提纲」并发到学员邮箱;
>    c. 让 Agent 直接批改学员主观题作业并把分数写进教务系统。
> 2. 用判定脚本验证你的结论(纯标准库,无需安装,保存为 `agent_selector.py` 后 `python3 agent_selector.py` 运行):
>
> ```python
> def recommend(route_fixed: bool, error_cost: str) -> str:
>     if not route_fixed and error_cost in ("中", "高"):
>         return "自主 Agent + 人工确认点(高代价动作前设闸)"
>     if not route_fixed:
>         return "自主 Agent"
>     return "工作流(或单步工具调用)"
>
> for name, fixed, cost in [("查作业分", True, "低"),
>                           ("发个性化提纲", False, "低"),
>                           ("批改并写入成绩", False, "高")]:
>     print(f"{name}: {recommend(fixed, cost)}")
> ```
>
> **完成标准**:能对每个任务讲出「为什么是这一档、错误代价在哪一步、闸门设在哪」——这正是 06 章交付物「Agent 类型对比表」的验收方式。

## 8. 边界与常见误区

- **误区一:「用了 LangGraph/AutoGen 就是 Agent」**——框架是脚手架,不是 Agent 本身;不会 05 的循环思想,框架只会让你更快地把错误循环上线。
- **误区二:「自主度越高越好」**——成本、延迟、不可预测性随档位上升。Anthropic 明确建议:先上最简单的形态,复杂度按需加装。
- **误区三:混淆用途与自主度**——「代码 Agent」是用途标签,不是自主度;问「它是 Copilot 还是自主 Agent」才对。
- **误区四:多 Agent 是银弹**——两个能干的 Agent 别急着上五个;通信开销与跨角色错误传播往往吃掉分工收益。
- **排错提示**:若你的 Agent 系统「贵且乱」,先别换框架——回到 §6 重新定档,八成是自主度给高了。

## 9. 总结

| 概念 | 一句话 |
|---|---|
| 全景两轴 | 自主度(怎么干)+ 用途(干什么),形态由自主度决定 |
| 自主度四档 | 单步工具调用 → 工作流 → 自主 Agent → 多 Agent |
| 用途四类 | 代码/数据分析/浏览器/客服,底层是同一个循环 |
| 生态三件套 | LangGraph(低层编排)/ AutoGen(多 Agent)/ MCP(工具连接标准) |
| 选型口诀 | 路线固定用工作流,路线开放上自主;错误代价高就降档、加闸、留审计 |

**思考题**:任务 b「自动生成个性化复习提纲并发邮件」,若把错误代价从「低」改为「高」(比如发错学员、泄露他人进度),你的选型卡要怎么改?闸门设在哪一步?

> [!note] 参考答案
> 档位从「自主 Agent」改为「自主 Agent + 人工确认点」:生成提纲后、点发送前插入人工确认(或改为草稿+学员自查),同时给发送工具加收件人白名单护栏。错误代价升高时,闸门应设在「不可逆动作(发消息/写库)之前」,而不是任务开头——开头的人工确认拦不住中途生成的错误内容。
