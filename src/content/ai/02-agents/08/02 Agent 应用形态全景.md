# Agent 应用形态全景

> 02.07 给课程助教装上了评测显微镜与回归循环:每次改动先在 golden 任务上过一遍,「敢迭代」有了制度保障。可评测回答的是「改得好不好」,还没回答「做成什么样才敢放权」——这正是收官模块 02.08 的问题:把前七个模块的能力组装成真实 Agent 应用。本章先画全景图:真实世界的 Agent 按风险与自主度分三档,按工具与产物分四种形态;看懂这张图,02~04 章的案例深挖与 05 章的结业组装才有坐标系。

**学习目标**:学完本章,你将能够——

1. 用「辅助型/任务型/自主型」三档给任意 Agent 应用定级,并说出各档的人机分工与介入点;
2. 对比代码、数据分析、知识客服、浏览器四种形态的核心工具与典型产物;
3. 为一种形态画出「人(确认闸门)+ Agent 循环 + 工具层 + 护栏带」的架构草图;
4. 用「任务风险×错误代价→自主度」框架为课程助教的子任务选档配护栏;
5. 说清档位是任务属性而非模型能力标签,并解释「自主≠无人负责」。

## 1. 概念:按风险与自主度分三档

- **辅助型(assistive,copilot 式)**:Agent 产出建议与草稿,关键动作经人确认后才执行——人做决定、Agent 提效,对应 02.02 学过的补全、建议、待批准命令等形态。
- **任务型(task-level,有限自主)**:人给定任务与边界,Agent 在边界内自主完成常规步骤,只在三类时机请人介入——例外情况、高风险动作、任务收尾合入。
- **自主型(autonomous,少人干预)**:人只定目标与停止条件,Agent 自定步骤并执行,干预点收敛到任务开始、任务结束与异常停摆。
- 学界把档位差刻画成一条谱系:Microsoft 2025 年的研究按用户角色从 operator(操作者)递进到 observer(观察者)排成五级自主度;产品落地时常收敛成三档口径,本讲义取后者,方便对照真实产品(见引用)。

| 档位 | 人机分工 | 人在圈内的介入点 | 典型产物 | 出错时谁兜底 |
|---|---|---|---|---|
| 辅助型 | 人做决定,Agent 提建议/待批动作 | 每个关键动作之前 | 建议、草稿、待批准的命令 | 人(每步都看过) |
| 任务型 | Agent 执行常规步骤,人设边界 | 例外、高风险动作、收尾合入 | 完成的子任务、批注、PR | 人审边界内产物 |
| 自主型 | Agent 自定步骤执行,人定目标 | 任务开始/结束、异常停摆 | 端到端结果(如批量迁移) | 人与 Agent 按审计分担 |

- 与 02.01 的定义对齐:三档共享同一副「循环+工具」骨架,差别只在**决策权归谁**、**人在哪几道闸门**。

## 2. 为什么需要:不分级会怎样

| 做法 | 表现 | 后果 |
|---|---|---|
| 一律全自动 | 删库、群发这类动作也无人把守 | 一次高代价事故就能让整个项目下马 |
| 一律人确认 | 改格式也要人点头 | 人变橡皮图章,确认流于形式,还拖慢所有任务 |
| 名义辅助、实际自动 | 界面写「建议」,代码却直接执行 | 最危险:人以为自己在圈内,其实早已出圈 |

- 一刀切行不通,是因为两个变量在打架:**错误代价**(金钱、隐私、口碑、是否不可逆)与**人工成本**(每轮确认的时间与注意力)。代价高,人必须在圈内;代价低,人守在圈外只查结果。
- 分档就是把这两个变量对准的工程动作;而「名义辅助、实际自动」之所以最危险,是因为它骗过了人这一层唯一的防线——这是 04 章公开事故里反复出现的死法。

## 3. 作用:四种形态与一张共享骨架

| 形态 | 擅长什么 | 核心工具(呼应 02.04) | 典型产物 | 课程助教的对应场景 |
|---|---|---|---|---|
| 代码 Agent | 读写代码、跑测试、按报错迭代 | 编辑器 + 代码检索 + 沙箱执行器 | 代码改动、PR、批注 | 批改学员编程作业(02 章深挖) |
| 数据分析 Agent | 自然语言→查询/代码→图表 | 数据库 + 代码执行 + 出图工具 | 报表、图表、结论 | 统计课程学习数据(03 章) |
| 知识/客服 Agent | 依据资料问答、跟进工单 | 向量检索 + 记忆 + 工单系统 | 带引用的回答、工单摘要 | 课程助教主形态,本模块主线底子 |
| 浏览器 Agent | 观察网页并执行操作 | 截图/DOM 观察 + 动作空间 | 表单提交、页面状态变更 | 课程站点上的演示形态(03 章) |

- 四种形态共享同一副骨架,差异集中在两处:**工具层挂什么**、**护栏带怎么收紧**:

```text
┌────────────── 人:目标 / 验收 / 确认闸门 ──────────────┐
│  ┌──────────────────────────────────────────────┐  │
│  │  Agent 循环:模型 + 规划 + 记忆 + 工具调用     │  │
│  │       ↓ 一次工具调用                         │  │
│  │  工具层(按形态不同):                         │  │
│  │  检索器 / 代码沙箱 / 数据库 / 浏览器动作 / 工单 │  │
│  └──────────────────────────────────────────────┘  │
│  护栏带:权限最小化 | 预算上限 | 沙箱隔离 | 审计日志  │
└────────────────────────────────────────────────────┘
```

- 为什么这副骨架成立:模型循环(02.01)、工具接入(02.04)、记忆(02.05)、评测(02.07)在之前模块各自建好,形态差异只是「在工具层与护栏带上换配置」——这正是 05 章组装课程助教时你会亲手验证的事。

## 4. 详细介绍:每形态的护栏配置与选型框架

### 4.1 四形态的默认档位与关键护栏

| 形态 | 默认档位 | 关键护栏 | 挡住什么 |
|---|---|---|---|
| 代码 Agent | 任务型(危险命令回辅助) | 沙箱执行、diff 审阅、只读默认 | 改坏文件、执行恶意命令(02 章) |
| 数据分析 Agent | 任务型 | 只读数据库账号、查询超时、图表校验 | SQL 写错、全表扫描烧钱(03 章) |
| 知识/客服 Agent | 辅助~任务型 | 检索白名单、拒答规则、记忆最小化 | 编造依据、越权透露他人信息 |
| 浏览器 Agent | 辅助型(每步确认) | 登录态隔离、动作白名单、截图审计 | 误提交表单、跨站点操作 |

- 护栏清单不是四份,而是同一份「权限/预算/沙箱/审计」按形态收紧:能改文件的比能读数据的严,能点击下单的比能回复消息的严。

### 4.2 选型框架:任务风险×错误代价→自主度

- 定档只问两个问题:① 做错代价多大(金钱、隐私、口碑、是否不可逆)?② 结果能不能自动验收(有测试、断言、schema 校验吗)?
- 决策表如下——它就是 5. 动手活动里 `recommended_tier()` 的判定逻辑:

| 错误代价 | 能自动验收? | 建议档位 | 课程助教例子 |
|---|---|---|---|
| 低 | 能 | 自主型 | 批量统一代码格式 |
| 低 | 不能 | 任务型 | 生成讲义初稿(人校后发布) |
| 中 | 能 | 任务型 + 自动闸门 | 批改作业:测试把关,合入前人工确认 |
| 高或不可逆 | 不论 | 辅助型 | 删除学员档案、群发成绩邮件 |

- 为什么「能自动验收」是放手的底气:自动验收把错误挡在门外,人才能退到「只看结果」;没有它,放手等于盲飞。呼应 02.07:回归评测就是 Agent 世界的自动验收——评测跑不过,什么都不用谈。

## 5. 动手活动:给课程助教的子任务定级配护栏

> [!example] 动手活动:autonomy_selector.py——子任务自主度选型器
>
> **目标**:实现任务的档位判定与护栏配置,让 5 个课程助教子任务自动输出「档位 + 护栏清单」,并与 4.2 决策表逐行对照。
>
> **步骤**:
> 1. 保存为 `autonomy_selector.py` 并运行(纯 Python 3,零依赖);
> 2. 核对 5 行输出:三档各至少出现一次,「批量统一代码格式」应是唯一自主型;
> 3. 把「删除学员档案」的 `error_cost` 改成 1 再跑,档位不变——解释为什么(不可逆优先于代价);
> 4. 回答:为什么「回复课程答疑」是任务型而不是自主型?
>
> ```python
> # autonomy_selector.py —— 课程助教子任务自主度选型器(纯 Python 3,零依赖)
>
> class TaskProfile:
>     """任务画像:错误代价、能否自动验收、是否不可逆。"""
>
>     def __init__(self, name, error_cost, auto_verifiable, irreversible):
>         self.name = name
>         self.error_cost = error_cost          # 1=低 2=中 3=高
>         self.auto_verifiable = auto_verifiable  # 有测试/断言能自动验收吗
>         self.irreversible = irreversible        # 错了能回滚吗
>
>     def recommended_tier(self):
>         """定档规则:不可逆或高代价→辅助型;无法自动验收→任务型;低代价且可验收→自主型。"""
>         if self.irreversible or self.error_cost >= 3:
>             return "assistive"
>         if not self.auto_verifiable:
>             return "task_limited"
>         if self.error_cost >= 2:
>             return "task_limited"
>         return "autonomous"
>
>     def guardrails(self):
>         """按档位配护栏;任务型里可验收的加自动闸门,不可验收的靠例外转人。"""
>         tier = self.recommended_tier()
>         if tier == "assistive":
>             return ["human_confirm_every_action", "dry_run_first"]
>         if tier == "autonomous":
>             return ["auto_check_before_finish"]
>         if self.auto_verifiable:
>             return ["auto_check_before_finish", "human_confirm_before_merge"]
>         return ["human_confirm_on_exception"]
>
> def main():
>     tier_names = {"assistive": "辅助型", "task_limited": "任务型", "autonomous": "自主型"}
>     tasks = [
>         TaskProfile("回复课程答疑", error_cost=1, auto_verifiable=False, irreversible=False),
>         TaskProfile("生成讲义初稿", error_cost=1, auto_verifiable=False, irreversible=False),
>         TaskProfile("批改作业代码", error_cost=2, auto_verifiable=True, irreversible=False),
>         TaskProfile("删除学员档案", error_cost=3, auto_verifiable=False, irreversible=True),
>         TaskProfile("批量统一代码格式", error_cost=1, auto_verifiable=True, irreversible=False),
>     ]
>     for task in tasks:
>         print("%-8s → %s,护栏: %s" % (task.name, tier_names[task.recommended_tier()],
>                                       ", ".join(task.guardrails())))
>
> if __name__ == "__main__":
>     main()
> ```
>
> **完成标准**:5 行输出与 4.2 决策表一致——回复答疑/讲义初稿/批改作业为任务型,删除档案为辅助型,批量格式为自主型;批改作业比另两个任务型多出「自动闸门 + 合入确认」;把 `error_cost` 改 1 动摇不了不可逆任务的辅助型结论;能口头讲清「答疑为什么不是自主型」。

## 6. 边界:选型陷阱与护栏误区

| 陷阱 | 表现 | 处理 |
|---|---|---|
| 橡皮图章审批 | 每步都确认,人不再细看 | 只在高风险动作设确认点,常规动作走事后审计 |
| 名义辅助、实际自动 | 标称「建议」却自动执行 | 权限系统里根本没有「自动」通道——只有代码能保证口径一致 |
| 把档位当能力标签 | 换更强模型就顺手提档 | 档位由任务风险与验收能力决定,与模型强弱无关 |
| 一次定死 | 任务内容或工具变了,档位过时 | 每次加工具、改流程都重跑一遍选型器 |

- 边界提醒:**自主型不是「无人负责」**。任何档位都要能回答「出了事谁负责、靠什么审计」——评测与 trace(02.07)提供证据,护栏与人工确认负责拦截,发布评审(06 章)做最后裁决。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 三档 | 辅助型人确认 / 任务型有限自主 / 自主型少人干预 |
| 四形态 | 代码、数据分析、知识客服、浏览器——共享骨架,差在工具与护栏 |
| 架构骨架 | 人(确认闸门)+ Agent 循环 + 工具层 + 护栏带(权限/预算/沙箱/审计) |
| 选型框架 | 任务风险×错误代价→自主度;「能自动验收」是放手的底气 |
| 两个认知 | 档位是任务属性不是产品标签;自主≠无人负责 |

**思考题**:为什么「低代价 + 能自动验收」可以放手到自主型,而「高代价 + 能自动验收」仍要人在圈内?「回复课程答疑」这类无法自动验收的低代价任务,若强行升到自主型,最可能在哪里翻车?

> [!note] 参考答案
> 自动验收只能证明「结果符合预设断言」,挡得住过程失控,挡不住「目标本身错了」的代价——高代价错误的成本(隐私、合规、不可逆副作用)大多落在断言之外,所以可验收是放手的必要条件而非充分条件,高代价必须人在圈内。答疑无法自动验收,若升到自主型,一次「拿不准却自信作答」的幻觉会直达学员:没有测试兜底、没有例外转人,坏答案既发得出也收不回——任务型的「例外转人」闸门正是为这类任务保留的。
