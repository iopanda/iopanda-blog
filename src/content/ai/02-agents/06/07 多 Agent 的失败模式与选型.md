# 多 Agent 的失败模式与选型

> 01~05 章把多 Agent 越讲越顺手:角色化、三种协作模式、通信协议、框架执行——课程助教已经能「组队干活」了。可 01 章末尾那盆冷水——通信成本、级联错误、责任归属、成本爆炸——一直没泼透:它们以什么方式坏、坏了为什么特别难查、以及最该记住的一句「能单 Agent 解决就不要上多 Agent」。本章是 02.06 Multi-Agent Systems 的收官课,回答:多 Agent 的典型失败模式、为什么单 Agent 的评测方法在此失效(02.07 展开),并给出一张三问决策清单与 5 任务选型判断表——看完你会理解,多 Agent 的默认答案为什么是「不用」。

**学习目标**:学完本章,你将能够——

1. 列举四大失败模式(级联错误放大、上下文互相污染、成本失控、调试困难)并各举一个课程助教实例;
2. 用「组件可靠性相乘」解释级联错误为什么随 Agent 数放大;
3. 解释为什么多 Agent 让单 Agent 评测方法失效、失败难以归因(预告 02.07);
4. 对 5 个给定任务运用三问决策清单,给出用/不用多 Agent 的结论与理由;
5. 说出至少三条多 Agent 护栏(预算上限、超时与人工闸门、轨迹日志),并复述本章结论。

## 1. 概念:多 Agent 的四大失败模式

| 失败模式 | 机理 | 课程助教实例 | 早期信号 | 防线 |
|---|---|---|---|---|
| 级联错误放大 | 错误沿 agent 链传递并叠加:单步 95% 可靠的三级流水线,整链成功率仅约 86%(0.95³);MAST 实证研究里主流框架任务失败率高达 41%~86.7%,且多数失败源于「组织设计」而非单个模型不行 | 检索员查错档案 → 计算员算出漂亮数字 → 回答员一本正经解读错的数字(04 章「假成功」的放大版) | 输出「自信但错」,单步抽查却都对 | 每步 schema 校验;关键步人工抽检;评测集兜底 |
| 上下文互相污染 | 多角色共享/复读同一段上下文,一方的幻觉污染公共黑板;MAST 把「带着错误假设继续推进」(FM-2.2,占 11.65%)与「历史上下文丢失」(FM-1.4)单列为高频模式 | 辩论里正方编了个数据,反方懒得核实直接引用;批改员顺手把共享学员档案写脏 | 角色输出出现别的角色的措辞/数据 | 角色上下文隔离;共享状态只读+版本号(04 章) |
| 成本失控 | 调用次数 = 角色数 × 轮数,token 又因每角色重述上下文而膨胀;辩论与重试是放大器 | 一次答疑从单 Agent 的 1 次调用变成编排者+3 worker 的 4+ 次,还带重试 | 账单翻倍但质量没涨 | 预算上限;轮数上限;小模型干杂活 |
| 调试困难 | 状态分散在多个角色与轮次,「改一行 prompt 全线漂移」;MAST 三分类中执行期的 agent 间错位(FC2,约 37%)最难一眼定位 | 学员投诉批改不公:分不清是评分细则、检索到的历史、还是回答员的表达哪一环坏了 | 修一个 bug 引出三个新 bug | 轨迹日志;单步重放(02.07) |

- 证据来源:UC Berkeley 的 MAST 研究对 7 个主流多 Agent 框架的 200+ 条真实轨迹做标注,归纳出 14 种细粒度失败模式、三大类(规格问题 FC1 ≈ 41.8%、Agent 间错位 FC2 ≈ 36.9%、任务验证不足 FC3 ≈ 21.3%),并发现**带显式验证角色的系统(如 MetaGPT)整体失败更少**——但验证者不是银弹,有的系统成功率仍低到 33%。这条证据链说明:**失败主要是设计问题,不是模型问题**。

## 2. 为什么需要:隐性税与评测失效

### 2.1 可靠性相乘、成本相乘

- 假设单次模型调用 95% 可靠(已经很乐观):单 Agent 一次任务 ≈ 95%;02 章编排 Demo 至少 4 次调用(编排者 + 3 worker),全对概率 ≈ 81%;加一次失败重试、一次辩论回合,轻松掉到 70% 以下。**多 Agent 用调用次数换质量上限,也同时把可靠性做成乘法**——每一步都必须有校验,否则整链精度被最弱一环拖死。
- 成本:调用次数倍增之外,每个角色都要背一份上下文(02.02 的窗口管理在多 Agent 里按角色重复计费)。单 Agent 一次 1 万 token 的任务,编排版轻松到 5 万以上;辩论按轮数再翻倍。**预算上限不是优化项,是启动条件**。

### 2.2 评测难:单 Agent 方法为什么失效

- 单 Agent 评测(01.06)是「同一问题 → 一次回答 → 与参考答案比对」;多 Agent 下,一次交付是 N 次调用 + 通信的产物,同一条「错的答案」可能源自检索错、计算错、编排拆错、上下文污染或回答员跑题——**只比对最终答案无法归因**。
- MAST 显示近半数失败发生在执行过程中(步骤重复、带错假设推进、提前终止),最终答案反而「看起来正常」;只评结果会漏掉大部分病灶。
- 再加上 01 章的责任归属问题:多角色时「谁为坏结果负责」没有天然答案。**结论:多 Agent 需要 02.07 的轨迹级评测与可观测性;没有它们,多 Agent 就是不可调试的黑盒加速器**——这是本章把评测难列为头号风险的原因。

## 3. 作用:三问决策清单

- 上多 Agent 前,逐条回答三个问题,**全为「是」才继续**:

| 问 | 判断标准 | 反例 |
|---|---|---|
| Q1 任务能拆吗 | 存在边界清晰、天然独立的子任务 | 「总结这段讲义」——拆成 5 段各写各的,合并质量反而差 |
| Q2 角色真不同吗 | 各角色需要不同工具/上下文/约束,不是同一模型换段 prompt | 「查成绩+算平均」——两步都是工具调用,一个 Agent 就能做 |
| Q3 单 Agent+工具搞不定吗 | 有评测证据(02.07 黄金任务集),不是感觉 | 「再跑个辩论试试」——没有评测对照,加了也不知道好不好 |

```
任务进来
  └─ 先用单 Agent + 工具跑,过评测集(02.07)
        ├─ 达标 → 结束(默认答案:不用多 Agent)
        └─ 不达标 → 过三问
              ├─ 任一为「否」→ 回到单 Agent:补工具/补 prompt/补记忆
              └─ 三问全真 → 上多 Agent,同时装齐护栏:
                  预算上限 | 每步超时与重试 | 人工闸门 | 轨迹日志
```

- 护栏不是可选项,是 02~04 章工程手段的汇总:预算与超时(04 章)、失败传播带原因(04 章)、人工确认闸门(02 章)、每步打点(02.07)——**没有护栏的多 Agent 上线 = 开着没刹车的车**。

## 4. 详细介绍:5 个任务选型判断

| 任务 | Q1 可拆? | Q2 角色真不同? | Q3 单 Agent 不够? | 结论 | 理由与替代方案 |
|---|---|---|---|---|---|
| A 学员问「我第三章练习平均分在班里什么水平?」 | 弱(查+算两步) | 否(查与算都是工具调用,不需要两个 Agent 人格) | 否 | **不用多 Agent** | 单 Agent + 成绩查询与计算工具一次调用;02 章拆三 worker 是为教学演示,不是该问题的最优解 |
| B 「500 篇作业逐篇批改并写评语」 | 强(每篇独立) | 否(500 篇是同一批改角色 × 500,不是 5 种角色) | 否(串行慢,但能做) | **不用多 Agent;可并行 worker 提速** | 真正缺的是并行不是新角色:同一 worker 起 10 个副本各批 50 篇;要盯的是批改质量评测 |
| C 「每周自动生成课程更新简报:抓各章 diff、核对引用出处、写摘要」 | 强 | 是(diff 检索要搜索工具,核对要引用库,摘要要写作上下文) | 是(三者工具与上下文互斥,塞一个窗口会角色冲突,呼应 01 章) | **用多 Agent** | 编排者-工作者(02 章):diff-worker、verify-worker、writer-worker;每步产物可审计、可单独重跑 |
| D 「学员情绪激动投诉『助教根本没批我作业』」 | 否(事实核查+安抚,一气呵成) | 否 | 否 | **不用多 Agent** | 单 Agent 查批改记录 + 道歉模板最快最稳;多 Agent 的延迟与出错面只会火上浇油 |
| E 「出一份『多 Agent 是否值得』的正反方辩论展示」 | 强(正/反/裁决三角色) | 是(正反方 prompt 必须隔离才不会一边倒,裁决者须独立) | 是(一人分饰两角容易自说自话) | **用多 Agent(辩论模式),须加护栏** | 03 章辩论:正反方各执一词 + 裁决者;护栏:轮数上限、预算上限、裁决者用更强模型、要求先找茬再赞同(防互相附和) |

- 看表要抓住两个陷阱:**「任务大」≠「需要多 Agent」**(B 是同一角色 × 500,要的是并行,不是角色分化);**「角色多」≠「值得拆」**(D 拆了只会更慢更易错)。多 Agent 只对 C/E 这类「角色、工具、上下文确实分化且有评测可证收益」的任务成立。

- **一页纸备忘(不用的红旗)**:任务单轮能答;角色全靠换 prompt 凑;没有评测集兜底;失败代价高却无人确认;预算敏感;团队没人能维护 N 个角色的 prompt——出现任一条,回到单 Agent + 好工具。

## 5. 动手活动:5 任务选型决策 + 失败模式实验

> [!example] 动手活动:multi_agent_decision.py 与两个失败实验
>
> **目标**:运行决策脚本核对 4 节选型表;亲手制造并观察「假成功级联」与「脏数据污染」两条失败路径;把判断过程写成 checklist。
> **步骤**:
> 1. 保存并运行 multi_agent_decision.py(纯标准库,离线可跑),对照 4 节表格核对 A~E 的结论与理由;
> 2. 打开 02 章 orchestrator_workers.py,把 Calculator.run 的平均分改成永远返回 None 但保留 ok=True——模拟「假成功」,观察 None 如何穿过 require() 直达交付(答案里出现 None);这演示了 schema 校验只查形状、不查内容时的级联漏洞;
> 3. 给 Retriever 的档案里塞一条脏数据(如把某学员第三次成绩改成 150),再跑一次,观察上下文污染如何让计算员、回答员在「正确代码」下输出错误答案;
> 4. 写 reports/selection-checklist.md:对 A~E 各填一行「三问答案 → 结论 → 若上多 Agent 会装哪两条护栏」;
> 5. 从课程助教真实问题里挑一个单 Agent 能答的问题,写一份「硬拆成多 Agent」的演示稿,再用三问否决它,记录否决理由。
> **完成标准**:脚本输出与 4 节表结论一致;能画出「假成功级联」与「脏数据污染」的传播路径并解释防线(内容校验、只读共享状态);checklist 五行三问与结论齐全。

```python
# multi_agent_decision.py —— 06 章动手:三问决策清单代码化(纯标准库,离线可跑)
# 三问(本章 3 节):
#   Q1 splittable    任务能拆成边界清晰的独立子任务吗?
#   Q2 distinct_role 角色/工具/上下文真的不同吗?(只是换 system prompt 不算)
#   Q3 single_fails  单 Agent + 工具确实搞不定、或评测不达标吗?(用 02.07 的评测说话)


def decide(splittable, distinct_role, single_fails):
    """三问全真才上多 Agent;否则返回 avoid 并给出否决理由"""
    reasons = []
    if not splittable:
        reasons.append("任务不可拆:拆分只是增加通信与出错面")
    if not distinct_role:
        reasons.append("角色同质:只是换 prompt,不是真分工")
    if not single_fails:
        reasons.append("单 Agent + 工具能完成:多 Agent 是纯开销")
    if splittable and distinct_role and single_fails:
        return "USE", reasons + ["三问全过:分工带来可测收益,上多 Agent 并装护栏"]
    return "AVOID", reasons


CASES = [  # (任务, 可拆?, 角色真不同?, 单Agent+工具失败?)
    ("A:问平均分与班级水平",     False, False, False),
    ("B:500 篇作业逐篇批改",      True,  False, False),
    ("C:每周课程更新简报",        True,  True,  True),
    ("D:情绪化投诉处理",          False, False, False),
    ("E:正反方辩论展示",          True,  True,  True),
]

if __name__ == "__main__":
    for name, q1, q2, q3 in CASES:
        verdict, why = decide(q1, q2, q3)
        print("[%s] %s" % (verdict, name))
        for line in why:
            print("    - %s" % line)
```

- 说明:A 的「可拆」判为否,是因为查+算两步合起来一次调用就能完成——可拆性要按「拆了是否有收益」来判,不是按「能不能拆成两句话」来判;这与 4 节表格的「弱可拆」同义,代码里为保持三问的布尔语义取「否」。

## 6. 边界与排错:多 Agent 系统「坏掉」的早期信号

| 症状 | 可能原因 | 处理 |
|---|---|---|
| 上多 Agent 后质量反而低于单 Agent | 级联错误 / 角色同质 / 拆错任务 | 回到单 Agent 做对照评测(02.07);三问重过 |
| token 账单翻倍却无质量收益 | 每角色重述上下文;轮数失控 | 预算与轮数上限;减角色;压缩共享上下文 |
| 一次失败整个流程重跑 | 无检查点,失败即从头(05 章) | 上 checkpointer;失败进状态分流(05 章 Demo) |
| 改一个 worker prompt,全线漂移 | 上下文污染:旧轨迹/共享黑板串扰 | 角色上下文隔离;共享状态只读;重跑回归评测 |
| 辩论双方互相夸,结论空泛 | 附和(03 章):无对抗指令或裁决者弱 | 裁决者独立且更强;要求先找茬再赞同;轮数封顶 |
| 出了事故找不到责任环节 | 无轨迹日志 | 02.07 tracing:每步打点,失败可重放 |

- 边界提醒:本章的「不用多 Agent」不是否定 01~05 章——01~05 章教会你「拆」,本章给你「什么时候才值得拆」的标尺。生产环境里课程助教 90% 的问题应走单 Agent + 工具;多 Agent 留给 C/E 这类「拆了有可测收益」的任务,且每次上马都带护栏与评测。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 四大失败模式 | 级联错误(可靠性相乘)、上下文污染(共享变脏)、成本失控(角色×轮数×token)、调试困难(归因无门) |
| 评测失效 | 最终答案 ≠ 病灶;轨迹级评测与可观测性是解药(02.07) |
| 三问决策清单 | 可拆?角色真不同?单 Agent + 工具搞不定?——三问全真才上 |
| 护栏 | 预算上限、超时重试、人工闸门、轨迹日志,缺一不可 |
| 结论 | 能用单 Agent + 好工具解决的,不要上多 Agent |

**思考题**:「500 篇作业批改」被判不用多 Agent;若任务改成「先按 A/B/C 分级,再按级用不同细则批改」,三问的答案会怎么变?多 Agent 出错后,为什么「重跑一遍」常常没用?

> [!note] 参考答案
> 批 500 篇是同一角色 × 500,角色数没变,要的是并行;加分级后,角色出现真分化:分级员(读作业判级,判错代价高)与 A/B/C 各级批改员(细则、查重与引用工具各不相同),Q2 变真;若单 Agent 一锅炖的准确率经评测(02.07)确实不达标,Q3 也真——此时编排者-工作者才有依据,且分级结果值得人工抽检。重跑没用,因为级联错误既有随机性也有系统性:随机部分重跑可能换个样子再现,系统性部分(拆解设计缺陷、验证不足)重跑必然重现同类错误——MAST 案例里 ChatDev 被反复提示仍产出同一类 bug。正确动作是轨迹归因:定位是哪一步、哪个角色、哪类失败,改设计后重跑回归评测,而不是原地重试。
