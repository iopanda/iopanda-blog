# 工具定义与校验

> 01 章让课程助教学会了「递调用单」:它不再空口说「我查过了」,而是输出结构化的 `tool_calls` 等应用去执行。可调用单上的「工具」从哪来?模型凭什么知道该选 `search_course` 而不是 `calculate_score`?答案是工具定义。本章回答两个问题:**描述怎么写,模型才选得准;参数怎么校验,应用才接得稳**。读完你会为课程助教配齐「查课程、算分、查资料」三件工具,并装上参数校验这道应用侧防线。

**学习目标**:学完本章,你将能够——

1. 说出工具的三要素(名字、描述、参数 JSON schema)与各自的作用;
2. 解释为什么描述是模型选工具的核心依据,烂描述必然导致选错工具;
3. 用 JSON schema 写出参数定义(类型、必填、枚举、范围);
4. 在应用侧实现参数校验,拦截类型错、越界、缺字段的调用并把错误回填给模型;
5. 打印课程助教「问题→选中工具→参数→校验→执行」的全过程,验证三件工具各司其职。

## 1. 概念:工具 = 名字 + 描述 + JSON Schema

- 在 function calling 里,一个工具就是三样东西的打包:调用时用的**名字**、给模型看的**描述**、约束参数的 **JSON schema**。它本质是模型与应用之间的一份「契约」:模型按 schema 生成参数,应用按 schema 校验参数。

```json
{
  "type": "function",
  "function": {
    "name": "search_course",
    "description": "按模块编号检索课程目录,返回模块主题与章节清单",
    "parameters": {
      "type": "object",
      "properties": {
        "module_id": {
          "type": "string",
          "description": "课程模块编号,例如 02.04"
        }
      },
      "required": ["module_id"]
    }
  }
}
```

| 要素 | 给谁看 | 作用 | 类比 |
|---|---|---|---|
| 名字 | 应用与模型 | 调用与分发的唯一标识,和真实函数一一对应 | 工牌号 |
| 描述 | 模型 | 模型选工具时读的「说明书」,决定选得准不准 | 菜品说明 |
| 参数 schema | 模型 + 应用 | 模型按它生成参数,应用按它校验 | 点单规格 |

- 名字只负责「区分」,不负责「解释」——模型看到一串工具名并不会自动知道每个工具干嘛,它唯一的信息来源是描述与参数说明。所以描述写得好不好,直接决定选择环节的质量。

## 2. 为什么需要:描述烂,必然选错工具

- 模型选工具的本质,是把「当前用户问题」与「工具清单」做一次匹配:读每个工具的描述,挑最像能解决当前问题的那个。schema 只约束参数形状,名字只用于区分,唯一承载「这个工具是干嘛的、什么时候该用」的就是描述。
- 描述写不好,后果立现:课程助教问「帮我算一下 85 分按 60% 加权是多少」,如果 `calculate_score` 的描述只写「处理分数」,模型可能不调用它、或把算分问题交给 `search_course`,然后对着课程目录胡说。

| 差描述 | 好描述 | 模型的实际表现 |
|---|---|---|
| 「处理分数」 | 「计算成绩:按权重折算分数并给出等级;当学员问『考了多少分/加权/等级』时使用」 | 差:算分问题不调用或调用错工具;好:触发条件明确,稳定选中 |
| 「查课程」 | 「按模块编号检索课程目录,返回该模块主题与章节清单;当学员问某模块讲什么时使用」 | 差:查资料问题也会选它;好:与查资料工具边界清晰 |
| 「搜索资料」 | 「在课程资料库做关键词检索,返回匹配片段与出处;当学员问概念定义、原理细节时使用」 | 差:与查课程混用;好:只接知识性问题 |

- 写描述的三条经验:① 写清楚**何时用**(触发条件)与**返回什么**;② 别用「处理/管理/获取」这类万能动词开头,它会吞掉相邻工具的问题;③ 相邻工具的描述要刻意写出**边界**(「课程目录」vs「资料片段」),否则模型只能掷骰子。
- 呼应 01 章:工具清单是递给模型的「菜单」,描述是菜单上的说明文字——说明写得含糊,顾客(模型)点错菜不能怪顾客。

## 3. 作用:定义与校验在调用链中的位置

```
① tools 参数随请求发出(工具定义此刻生效)
        │
        ▼
② 模型按描述决策 → 返回 name + arguments      ← 描述质量决定这一环
        │
        ▼
③ 应用按 name 查分发表,找到真实函数           ← 名字必须与函数一一对应
        │
        ▼
④ 执行前参数校验(类型/必填/范围/枚举)          ← 本章重点:应用侧防线
        │ 通过                    │ 不通过 → 返回可读错误,让模型修正后重试
        ▼
⑤ 调用真实函数,结果以 role:"tool" 回填
```

- 定义质量影响步骤②,校验质量兜底步骤④。schema 是双端契约:模型生成时参考它,应用执行前检查它——任何一端放松,另一端就要承担后果。校验不通过时,把错误信息回填给模型让它修正参数,而不是直接崩溃,这正是 01 章闭环的常规用法。

## 4. 详细介绍:JSON Schema 与参数校验

### 4.1 Schema 常用的约束字段

| 约束 | 写法 | 课程助教示例 |
|---|---|---|
| 类型 | `"type": "string"/"number"/"integer"/"boolean"/"array"` | 分数必须是数字 |
| 必填 | `"required": ["score"]` | 缺分数直接拒绝 |
| 枚举 | `"enum": ["video", "exercise", "quiz"]` | 资源类型只能取三种 |
| 范围 | `"minimum": 0, "maximum": 100` | 分数不可能超过 100 |
| 数组元素 | `"items": {"type": "string"}` | 关键词列表里的每个元素都是字符串 |
| 禁多余字段 | `"additionalProperties": false` | strict 模式必需,防模型塞进未知参数 |

### 4.2 为什么不能盲信模型给的参数

- **schema 在普通模式下只是「软约束」**:模型被训练成尽量生成合法 JSON,但没有任何机制保证参数落在你定义的范围内。OpenAI 2024 年 8 月之后的 strict 模式才在采样层强制 JSON 合法,但它只保证「形状对」,不保证「语义对」——模型照样可能给出 `score: 150` 这种类型正确、范围荒谬的值。
- 模型没有你的业务常识:它不知道满分是 100、不知道学期只有三个模块;参数越界轻则算出无意义结果,重则触发真实副作用(删除、下单,06 章展开)。结论是**双端校验**:schema 负责把生成引向正确的形状,应用负责在执行前做语义检查;发现非法参数,把「错在哪、合法范围是什么」回填给模型,让它修正后重试。

### 4.3 应用侧校验器

```python
# validators.py —— 参数校验:类型、必填、范围;不通过时返回可读错误
import json

TOOL_RULES = {
    "calculate_score": {
        "required": ["score"],
        "types": {"score": (int, float)},
        "range": {"score": (0, 100)},
    },
    "search_material": {
        "required": ["keyword"],
        "types": {"keyword": str, "top_k": int},
        "range": {"top_k": (1, 5)},
    },
}


def check_args(name: str, raw_args: str) -> tuple:
    """返回 (ok, message);message 面向模型,给出可修正的错误说明。"""
    try:
        args = json.loads(raw_args)
    except json.JSONDecodeError as err:
        return False, f"arguments 不是合法 JSON:{err}"
    rules = TOOL_RULES.get(name)
    if rules is None:
        return False, f"未知工具:{name}"
    for field in rules["required"]:
        if field not in args:
            return False, f"缺少必填参数:{field}"
    for field, field_type in rules["types"].items():
        if field in args and not isinstance(args[field], field_type):
            return False, f"参数 {field} 类型应为 {field_type.__name__}"
    for field, (low, high) in rules["range"].items():
        if field in args and not low <= args[field] <= high:
            return False, f"参数 {field} 超出范围 [{low}, {high}]"
    return True, "ok"


if __name__ == "__main__":
    samples = ['{"score": 85}', '{"score": 150}', '{"keyword": "外键"}', "{}"]
    for sample in samples:
        ok, msg = check_args("calculate_score", sample)
        print(sample, "->", "通过" if ok else f"拦截:{msg}")
```

- 校验通过只是「形状与范围合法」,业务语义(比如分数与学员对不上号)还要靠真实函数或查询结果把关——校验器是防线,不是保险箱。

## 5. 动手活动:三件课程助教工具与选择日志

> [!example] 动手活动:定义 search_course / calculate_score / search_material
>
> **目标**:产出 `tools/assistant_tools.py`:三个工具的定义 + 分发函数 + 校验器,并打印「问题 → 选中工具 → 参数 → 校验 → 执行结果」全过程;产出 `reports/tool-choice-log.md` 记录观察。
>
> **步骤**:
> 1. 定义三个工具并填进 `tools` 参数:`search_course`(参数 `module_id`,string 必填)、`calculate_score`(参数 `score`,number,范围 0~100)、`search_material`(参数 `keyword` string 必填、`top_k` integer 1~5);
> 2. 在本地用字典/常量实现三个真实函数(目录、加权公式、资料片段),分发表按工具名一一对应;
> 3. 复用 4.3 的校验器,在每次分发前执行校验;把 01 章的循环脚本扩展为:每轮打印 `[问题]`、`[选中工具]`、`[arguments]`、`[校验]`、`[执行结果]`;
> 4. 依次跑这五问:「02.03 讲了什么」「我考了 85,按 60% 加权后多少分」「考了 150 分怎么算」「外键是什么,查下资料」「今天天气不错」,记录每问选中了哪个工具;
> 5. 破坏性实验:把 `calculate_score` 的描述改成「处理学员成绩相关请求」,重跑第二问,把选型变化写进 `reports/tool-choice-log.md`。
>
> **完成标准**:五问中工具选对至少 4 问;`score: 150` 被校验器拦截,且模型能依据回填的错误修正参数重试;日志里能看出「好描述 vs 烂描述」下模型选型的前后差异,并总结出一句描述写作经验。

## 6. 边界与排错

- **schema 表达不了跨字段依赖**:「附加分不能超过卷面分的一半」这类关系必须写进校验函数,别指望 schema 解决;描述与 schema 要同步维护,描述说接受 `top_k` 而 schema 忘写,模型生成后必被校验拦截,白白浪费一轮。
- **描述会稀释**:工具清单过长或描述啰嗦时,模型对每条描述的注意力下降(呼应 02.02 的 02 章);同一领域工具过多时,考虑合并或分组(03 章展开)。
- **校验层替代不了权限层**:校验管「参数对不对」,权限管「能不能调」(06 章);工具返回内容仍要按不可信输入处理(呼应 01.04)。
- 常见排错:① 模型总是选同一个工具——描述太宽泛,把它写窄并给出触发条件;② 校验报错但模型不修正——错误信息只写「非法」不行,要给出合法范围(「分数应在 0~100 之间」);③ strict 模式开启后报 schema 错误——需要 `additionalProperties: false` 且所有属性进 `required`;④ 怀疑是选型问题而非生成问题时,先用 `tool_choice` 指定工具名做对照实验。

## 7. 总结

| 概念 | 一句话 |
|---|---|
| 工具三要素 | 名字(区分)+ 描述(选型依据)+ JSON schema(参数契约) |
| 描述 | 写清触发条件与返回内容;烂描述 = 选错工具 |
| Schema | 模型按它生成,应用按它校验;软约束,非保险 |
| 应用校验 | 类型/必填/范围/枚举逐项检查,失败回填可读错误让模型重试 |
| 校验器定位 | 防线不是保险箱,业务语义仍靠真实函数把关 |

**思考题**:为什么说 strict 模式开启后应用侧校验依然必要?如果两个工具的描述都写成「查东西」,模型面对相关提问会怎样表现?

> [!note] 参考答案
> strict 模式只保证输出「形状合法的 JSON」,不保证语义正确——`score: 150` 完全合法却毫无意义,业务范围、跨字段依赖只有应用侧代码知道,所以执行前校验不能省。两个描述都写「查东西」等于把选型信息抹掉了:模型没有依据区分它们,只能靠名字猜,表现为随机选、反复换或把问题硬塞给第一个工具;这也再次说明描述是选型的唯一线索,必须写出边界。
