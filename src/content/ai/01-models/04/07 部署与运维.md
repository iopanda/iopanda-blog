> 上一章测清了服务「能扛多少」,本章解决「如何交付、如何运维」:把本地 FastAPI 服务做成可重复启动的容器,并建立版本、健康、日志、指标、告警与回滚的最小闭环。你会先理解为什么容器是可复现交付的答案、镜像与容器与 Dockerfile 各是什么,再亲手构建镜像、做一次发布演练,最后认清演示与生产的差距——认证、TLS、密钥与权限不会因为用了 Docker 而自动存在。

**学习目标**:学完本章,你将能够——

1. 解释「在我的电脑能运行」为什么不可交付,容器如何实现可复现;
2. 区分 Dockerfile、镜像与容器,描述从配方到运行实例的构建链路;
3. 说明健康检查回答什么、不回答什么;
4. 写出并构建 API 容器镜像,理解容器内 `127.0.0.1` 与端口映射的含义;
5. 建立版本、日志脱敏、指标、告警与回滚的最小运维清单,并演练一次发布与回滚;
6. 列出演示部署与生产部署的差距:认证、TLS、密钥与权限。

## 1. 为什么需要容器:从「能跑」到「可复现交付」

- 上一章结束时,服务在本机 `127.0.0.1:8080` 上表现良好。但它依赖的远不止 `api.py` 一个文件:Python 版本、每个 pip 依赖及其版本、环境变量、启动顺序、GPU 驱动……换一台机器,这些条件几乎不可能原样存在。
- 「在我的电脑能运行」是交付的起点而不是终点:把代码交给另一台机器,常常死于「缺依赖」「版本不对」「启动方式不同」这类环境差异,而不是代码本身的逻辑。这类问题尤其难排查,因为报错往往只出现在你没装的那个依赖里。
- **容器把「代码 + 运行环境」一起打包**:基础系统、语言运行时、依赖库、配置文件与启动命令被做成一个不可变的镜像;任何装了容器引擎的机器,用同一条命令启动的都是同一份环境。「交付」于是从「拷贝代码 + 口述安装步骤」变成「交付一个镜像」。
- 这与 01 章的「性能基线」、03 章的「可复现量化实验」是同一纪律的延续:凡是影响结果的东西都应当被固定、被记录。可复现不只是工程便利,也是故障排查的前提——出问题时你能确切知道线上跑的是什么,而不是「大概是我当时装的某个版本」。

## 2. 概念:配方、镜像与运行实例

| 概念 | 是什么 | 类比 | 关键性质 |
|---|---|---|---|
| **Dockerfile** | 制作镜像的配方:逐行声明基础镜像、拷贝文件、安装依赖与启动命令 | 菜谱 | 可读、可审核、可版本化 |
| **镜像(image)** | 按配方构建出的打包结果,含完整文件系统快照与元数据 | 做好的菜 | 不可变,有唯一 ID 与 tag |
| **容器(container)** | 镜像启动后的运行实例,有独立进程与网络视图 | 端上桌的那份菜 | 可启停、可删除、彼此隔离 |

- 三者构成单向链路:改 Dockerfile → `docker build` 得到新镜像 → `docker run` 启动容器。同一个镜像可启动多个互不影响的容器;容器内的写入不会「写回」镜像。
- **镜像不可变正是它的价值**:构建完成后内容不再改变,交付的是「确定的那个镜像」,而不是「大概能装的依赖清单」;回滚回到的也是「上一个确定的镜像」,而不是「重装一遍碰运气」。
- 容器不是虚拟机:它共享宿主内核、只做进程与文件系统层面的隔离,因此更轻、启动更快;但隔离不等于安全边界,共享内核仍有被突破的风险(呼应第 7 节「容器不替你保护密钥」)。

```mermaid
flowchart LR
 A[Dockerfile] --> B[docker build: image]
 B --> C[docker run: container]
 C --> D[/health]
 D --> E[日志、指标、告警]
 E --> F[失败时回滚旧 image]
```

## 3. 动手:制作 API 容器

前置:按 04、05 章启动的 vLLM 与 FastAPI 服务仍在 `minigpt-course` 项目根目录(激活 `.venv`);本机需安装 Docker(如 Docker Desktop)并确认 `docker version` 可用。在项目根目录创建 `finetune/Dockerfile`:

```dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY finetune/src/api.py /app/finetune/src/api.py
RUN pip install --no-cache-dir fastapi "uvicorn[standard]" httpx
EXPOSE 8080
CMD ["uvicorn", "finetune.src.api:app", "--host", "0.0.0.0", "--port", "8080"]
```

逐行读这份配方:`FROM` 固定了基础镜像(Python 3.11 slim,版本锁定才有可复现);`COPY` 只打包业务 `api.py`——模型权重留在受控 GPU 环境,不进镜像;`RUN` 装运行时依赖;`EXPOSE 8080` 只是文档声明,并不自动开放端口;`CMD` 是容器启动时执行的命令,监听 `0.0.0.0:8080` 是因为容器内没有「宿主的 127.0.0.1」,进程必须监听容器自己的全部接口,由端口映射决定谁能访问。

构建并试运行:

```bash
docker build -f finetune/Dockerfile -t course-api:0.1 .
docker run --rm -p 127.0.0.1:8080:8080 course-api:0.1
```

`-p 127.0.0.1:8080:8080` 把「宿主的 127.0.0.1:8080」映射到「容器的 8080」——只有本机能访问,这正是演示想要的边界。由于 `api.py` 里的 `127.0.0.1` 在容器内指向容器自身,先不要假设它能连到宿主上的 vLLM;把模型服务接入前,必须显式设计内部网络地址、认证与网络策略。预期此时 `/health` 返回 **503**(模型未作为同一网络依赖接入),这不是健康检查通过,详见下一节。

## 4. 健康检查:回答什么,不回答什么

- **健康检查回答什么**:容器内的进程与它声明的依赖是否「活着、能响应」。`/health` 返回 200,意味着进程在监听、它所依赖的部分按声明在工作——这是编排器决定「重启容器、摘除流量」的依据。
- **健康检查不回答什么**:回答是否正确、模型权重是否就绪、是否过载、是否安全。200 只证明「管道通」,不证明「水干净」——健康检查通过而回答质量劣化(见 06 章的尾部延迟)完全可能,所以它不能替代指标与告警。
- 演示里 `/health` 只探 API 自身,而上一章的容量结论来自 `/ask` 压测;若健康检查永远只探 `/health`,它会比真实体验乐观。生产健康检查因此常探真实推理路径(合成提示 + 校验返回),并区分两种语义:**liveness**(进程死了就重启)与 **readiness**(依赖未就绪就别把流量分给它)。
- 本章的 503 恰恰是健康检查在如实工作:它把「模型依赖未就绪」翻译成了可观测的状态码——健康检查在说真话,而不是在说谎。

## 5. 版本与回滚:让「回到上个好版本」成为一条命令

- 镜像 tag(`course-api:0.1`)是给人看的名字,可以移动;镜像 ID 与 digest 才是内容的指纹。记录必须同时保存 tag 与 digest,否则「0.1 指向什么」可能事后被改变,回滚就失去了目标。
- 一次发布 = 镜像 tag + 模型 ID + adapter hash(如有)。只记镜像不记模型,回滚后 API 与模型版本错配,故障依旧;这正是第 3 节「模型不进镜像」的另一面——它必须被单独记录。
- **回滚是镜像不可变性的红利**:新版本出问题,不必逆向修复,只需停掉新容器、用上个已验证的 tag 重新启动——旧代码与数据原样可用。演示规模下回滚是两条命令;生产规模下它演化为蓝绿发布、金丝雀发布与自动回滚。
- 何时回滚由证据决定:健康检查持续失败、错误率或 P95 突破告警阈值。这要求第 6 节的记录先于故障存在,否则你无法判断「哪个版本是好的」。

## 6. 最小运维清单:日志、指标、告警

| 事项 | 要记录/执行 | 为什么 |
|---|---|---|
| 版本 | image tag、模型 ID、adapter hash | 找回运行的确切版本 |
| 健康 | `/health` 状态、模型依赖状态 | 区分 API 与模型故障 |
| 指标 | 请求数、P95、503、GPU 显存 | 发现容量退化 |
| 日志 | 请求 ID、耗时、错误码 | 排查问题,不记录原始敏感文本 |
| 回滚 | 停止新容器、启动上个已验证 tag | 有问题时快速恢复 |

- **日志脱敏**:日志的价值在可排查,但请求里可能含用户提问等敏感内容。记录「请求 ID、耗时、错误码、输出 token 数」这类元数据足以定位绝大多数问题;把请求原文写进日志,等于把用户数据复制到每一台机器。演示项目默认只记元数据、不记原文;确需记录时先脱敏再落盘。
- **指标与告警分工**:指标回答「现在怎么样」(请求数、P95、503 数、显存),告警回答「什么时候该叫人」。把 06 章的容量上限转成阈值,例如「P95 超过 2 s 持续 1 分钟」或「503 率超过 1%」触发告警;没有阈值的指标只是事后考古,而均值不适合做告警信号(见 06 章),要盯分位数。
- 清单是「最小」的:每条都对应一种具体故障——版本对不上、依赖没就绪、容量退化、无法排查、无法恢复。新增记录项前问一句「它对应哪次故障」,避免日志变成无人阅读的存储开销。

## 7. 生产与演示的差距:认证、TLS、密钥与权限

- 本章的容器是本地演示:监听 `127.0.0.1`、无认证、无限流。它**不授权直接部署公网**——原样暴露公网,等于把 06 章压测过的无防护 API 直接交给任何人(呼应 05 章「无认证无限流的服务不暴露公网」的边界)。
- 逐项列出差距:

| 能力 | 演示(本章) | 生产必须 |
|---|---|---|
| 认证 | 无,任何本机进程可调用 | 身份认证与授权(API key / OIDC) |
| 传输 | 明文 HTTP | TLS/HTTPS 与证书轮换 |
| 密钥 | 硬编码或空 | 由密钥管理在运行时注入,不进镜像 |
| 权限 | 容器内默认用户运行 | 最小权限:非 root、只读文件系统、网络策略 |
| 数据 | 无状态演示 | 备份、加密与数据留存策略 |
| 审查 | 个人提交 | 镜像签名、供应链扫描、组织安全审查 |

- **密钥不进镜像**:镜像是要分发、留存、回滚的——任何写进镜像的秘密都会随之扩散到所有副本与历史版本;密钥应由运行环境在启动时注入,镜像保持「无秘密」。
- **容器不替你负责**:它不保护密钥、不限制权限、不处理模型许可证(见 01.02 的数据许可纪律);这些是部署者的责任,容器化不会改变许可条款。
- 从演示到生产是一条有检查点的路:先加认证与 TLS,再迁密钥管理,再最小化权限——每步可单独验证。跳过这些直接暴露公网,是本章反复警告的边界。

## 9. 总结

| 关键问题 | 一句话 |
|---|---|
| 为什么需要容器 | 代码 + 环境一起打包,同一条命令启动同一份环境,交付从「口述步骤」变成「交付镜像」 |
| Dockerfile / 镜像 / 容器 | 配方、不可变打包结果、运行实例;改配方 → 构建 → 启动的单向链路 |
| 健康检查 | 只回答「依赖能否响应」,不回答正确性、过载与安全;503 可能是它正在说真话 |
| 版本与回滚 | 镜像不可变,停新容器、启旧 tag 即恢复;版本 = 镜像 tag + 模型 ID + adapter hash |
| 运维清单 | 日志脱敏记元数据、指标看现状、告警叫醒人;每条对应一种故障 |
| 演示 vs 生产 | 认证、TLS、密钥、权限、审查缺一不可,Dockerfile 省略不了 |

**思考题**:为什么 `/health` 返回 200 不能证明「回答正确」?为什么密钥不能写进 Dockerfile?为什么「用 Docker 部署」不等于「可以暴露公网」?

> [!note] 参考答案
> 健康检查只验证进程与依赖能否响应,不验证输出质量与安全——回答劣化、过载、越权都可能在 200 之下发生,所以生产健康检查要探真实推理路径,并配合指标与告警。镜像是要构建、分发、留存、回滚的,写进镜像的密钥会随之扩散到所有副本与历史版本,密钥必须在运行时由环境注入。演示容器无认证、无限流、明文 HTTP,还缺 TLS、密钥管理与最小权限;这些是部署者的责任,容器不会自动提供,原样暴露公网等于把无防护 API 交给任何人。
