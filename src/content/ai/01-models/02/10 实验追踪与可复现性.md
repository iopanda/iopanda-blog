> 上一章 [采样与定性评测](/ai/01-models/02/09/) 用固定提示词与解码参数给模型做定性体检;本章为整个 01.02 单元收尾:把一次 Mini GPT 训练整理成别人能够检查、你未来能够重跑的实验,而不是散落在磁盘上的权重文件和记忆。动手前先弄清两个概念:什么叫可复现,以及为什么固定随机种子远不是全部。

**学习目标**:学完本章,你将能够——

1. 用自己的话说清可复现的定义,以及它为什么是预训练实验的底线;
2. 用配置文件定义一次训练,而非把超参数散落在代码中;
3. 为数据、tokenizer、代码、环境和 checkpoint 建立可追溯关系,并解释为什么 seed 只是其中一项;
4. 记录并比较多个实验的指标与生成结果,遵守「一次只改一个变量」;
5. 区分「尽量复现」与跨设备绝对逐位一致的边界,并撰写一页可审查的实验报告。

## 1. 可复现性:概念与为什么需要它

- **可复现(Reproducibility)** 指:给定同一份输入——数据、代码、配置、环境——他人能够按你的记录重跑,得到足够接近的结果;若结果不同,也能定位到已记录的原因。「我昨天跑过」不是可复现,因为它没有留下证据。
- 为什么预训练里需要它?预训练动辄上千步、耗时以小时计,每一步改动都可能改变最终 checkpoint(第 8 章)与生成表现(第 9 章)。没有实验记录,你就无法回答两个最基本的问题:**这次结果比上次好吗?它为什么变好了?** 结论只能停留在「损失好像降了」的模糊记忆里。
- 它解决什么问题?可复现把实验变成**审计对象**:任何数值差异都能沿着记录逐项排查;评审者或未来的你不需要现场追问,就能独立判断实验是否可信。
- 不做的代价:超参数遗忘在聊天记录里、数据被悄悄替换而无人察觉、重跑结果对不上却无法解释——此时「训练成功」不再是工程结论,而是无法核验的说法。

### 1.1 为什么 seed 不是全部

固定随机种子(如 `seed: 42`)只固定了**随机数发生器**的起点:参数初始化、数据打乱顺序、dropout 掩码等。但一次实验的结果由远多于随机性的因素决定:

| seed 没管住的东西 | 例子 | 后果 |
|---|---|---|
| 数据版本 | 清洗脚本改动、文件被替换 | 输入变了,loss 曲线照旧画得出来 |
| 代码 | 忘了保存 commit、改了采样逻辑 | 生成结果不同却无法归因 |
| 依赖环境 | PyTorch 升级、CUDA 版本变化 | 同一代码数值就出现细微差异 |
| 硬件 | CPU 与 GPU、不同 GPU 型号 | 浮点累加顺序不同,结果不完全一致 |

PyTorch 官方说明:不同版本、不同平台或 CPU/GPU 之间**不承诺完全一致**;即便 seed 相同,GPU 上的卷积与原子操作也会引入非确定性。因此你的目标不是追求逐位一致,而是**让设置与产物可追溯,并在固定环境中获得足够接近的结果**。seed 是六要素之一(见下),不是唯一的保险。

### 1.2 一次可复现实验的检查单

至少应能回答下表中的问题:

| 要素 | 必须记录 | 例子 |
|---|---|---|
| 数据 | 来源版本、清洗版本、split、hash | `data/tokenized/train.pt` 的 SHA-256 |
| tokenizer | 文件与词表大小 | `artifacts/tokenizer.json` 的 hash |
| 代码 | 提交版本或源码快照 | Git commit / archive |
| 配置 | 模型、训练、采样参数 | `configs/minigpt-v1.yaml` |
| 环境 | Python、PyTorch、CUDA、设备 | `requirements.lock`、`environment.txt` |
| 结果 | loss、best step、生成报告 | `metrics.csv`、`generation.md` |

## 2. 让配置成为训练入口

- **概念**:配置文件是一次训练的**唯一入口与单一事实来源**。超参数散落在代码各处时,每次实验都「差不多」,却永远说不清差在哪;把全部会改变结论的参数收进一个 YAML,两次实验的差异就变成了两个文件之间的差异。
- **为什么需要它**:比较实验、回溯结果、重建环境都以配置为锚点。只记录学习率是不够的——数据路径、评测频率、解码参数同样会改变结论。

创建 `configs/minigpt-v1.yaml`。所有会改变实验结论的参数都应在这里,包括数据路径和评测频率;不要只记录学习率。

```yaml
run_name: minigpt-v1
seed: 42
data:
  train_path: data/tokenized/train.pt
  valid_path: data/tokenized/valid.pt
  tokenizer_path: artifacts/tokenizer.json
model:
  vocab_size: 2000
  context_length: 128
  d_model: 128
  n_heads: 4
  n_layers: 4
training:
  batch_size: 16
  learning_rate: 0.0003
  max_steps: 1000
  eval_every: 100
  checkpoint_every: 500
```

运行命令也要写进报告,例如:

```bash
python -m src.train --config configs/minigpt-v1.yaml --run-dir runs/minigpt-v1
```

每次运行创建独立目录,避免不同实验覆盖:

```text
runs/minigpt-v1/
  config.yaml
  environment.txt
  data-manifest.json
  metrics.csv
  checkpoints/best-valid.pt
  generation.md
```

数据 manifest 至少存路径、字节数和 SHA-256。hash 只能证明文件未变,不能证明数据有权使用,因此它是对第 2 章 [数据来源与许可](/ai/01-models/02/02/) 数据来源记录的**补充**,不是替代。

### 2.1 用一条命令生成输入清单

在项目根目录运行下面命令,将真实输入的大小和 hash 写入 run 目录。macOS/Linux 可用 `shasum`;Windows PowerShell 使用第二行:

```bash
shasum -a 256 data/processed/train.txt data/processed/valid.txt artifacts/tokenizer.json > runs/alice-bpe-v1/input-sha256.txt
```

```powershell
Get-FileHash data/processed/train.txt, data/processed/valid.txt, artifacts/tokenizer.json -Algorithm SHA256 | Out-File runs/alice-bpe-v1/input-sha256.txt
```

接着保存环境信息:

```bash
python --version > runs/alice-bpe-v1/environment.txt
pip freeze >> runs/alice-bpe-v1/environment.txt
python -c "import torch; print(torch.__version__, torch.cuda.is_available(), torch.version.cuda)" >> runs/alice-bpe-v1/environment.txt
```

打开两个文本文件确认它们实际有内容。这样拿到 run 文件夹的人,能先判断自己的输入、依赖是否一致,再讨论 loss 差异。

## 3. 记录指标以便作比较

- **概念**:指标记录是实验的「仪表盘」——它把 loss、学习率、梯度范数随时间的变化变成可比较的原始数据,而不是凭印象判断训练好坏。
- **为什么需要它**:没有逐 step 的记录,就无法画出曲线、无法定位 loss 在第几步开始异常、也无法在多个实验之间做受控比较。

先用 CSV/JSONL 就足够,不必一开始接入平台。每次记录一行,且带 `run_name` 与 `step`:

```text
run_name,step,split,loss,learning_rate,grad_norm
minigpt-v1,100,train,5.72,0.0003,0.84
minigpt-v1,100,valid,5.81,0.0003,
```

比较实验时一次只改变一个变量,例如从 `context_length=64` 改到 128,其他配置、数据切分、训练步数和评测提示尽可能不变。若同时改变模型大小、数据和学习率,即使结果变化也无法知道原因。

Weights & Biases、MLflow 等工具可帮助可视化和集中保存指标,但它们不是可复现性的前提。使用第三方服务前,检查项目可见性、团队权限及是否会上传受限制数据、提示词或模型输出。

> [!example] 动手活动 1:打包并重跑一个实验
>
> **目标**:交付 `runs/minigpt-v1/` 和 `reports/reproducibility.md`。
>
> **步骤**:1)复制实际使用的 config 到 run 目录;2)生成数据与 tokenizer 的 manifest/hash;3)导出 `python --version`、`pip freeze`、PyTorch/CUDA/设备信息;4)从该 config 在新目录重跑至少 100 step;5)比较 step 100 的 train/valid loss 与两条固定提示的输出。
>
> **完成标准**:报告能定位全部输入、代码和产物;说明首次与重跑的数值差异;若不一致,记录设备、版本、非确定性设置或数据变化等已核查原因,不能只写「结果不同」。

## 4. 在项目结束时写一页实验报告

- **概念**:训练结束不等于实验结束。报告把散落的记录汇总成一页可审查的结论,回答「我训练了一个模型」的证据到底是什么。
- **为什么是「一页」**:强制你只保留能支撑结论的证据,而不是把平台截图堆成资料夹;同时便于评审者一次读完。

`reports/pretraining-report.md` 可按下面模板填写:

1. **问题与边界**:训练教学规模 Mini GPT,不将其表述为通用大模型;
2. **数据声明**:来源、许可证、清洗和 split;
3. **配置**:模型参数量、tokenizer、训练预算、硬件;
4. **选择规则**:以最低 valid loss 选 checkpoint,测试集不参与选择;
5. **证据**:训练/验证曲线、固定提示词的全部输出、已知失败案例;
6. **限制与风险**:小数据记忆、偏见、无安全对齐、不可用于高风险用途;
7. **复现方法**:准确命令、run 目录和版本信息。

这份报告使「我训练了一个模型」成为可审查的工程结论。生产级预训练还会增加数据治理、分布式容错、隐私和安全评估等大量工作;本项目建立的是能够迁移到那些工作中的最小纪律。

## 5. 总结

| 你要保留的东西 | 它避免的问题 |
|---|---|
| config + 命令 | 忘记实际超参数 |
| 数据/tokenizer manifest | 输入悄悄变化 |
| 环境信息 | 无法解释重跑差异 |
| metrics + 全部生成输出 | 只挑成功案例 |
| checkpoint 选择规则 | 用测试集调参或事后挑选 |

常见误区:固定 seed 不会自动固定数据版本和代码;只保存最好模型而不保存 config 不能重建实验;把实验平台截图当作原始记录会丢失精确数值和上下文。

思考题:为什么 hash 不能证明训练数据合法?为什么比较两个实验时要固定提示词和解码参数?

> [!note] 参考答案
> hash 仅标识一个字节序列,没有来源、授权范围或个人信息处理结论。固定提示词和解码参数能排除随机生成差异,使观察到的变化更可能来自训练本身。
