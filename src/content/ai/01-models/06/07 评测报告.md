# 评测报告

> 01~06 章把「感觉模型变好了」逐步换成了可核查的证据:评测计划(01)定下测什么、怎么算过;黄金集(02)给出参考答案;自动化指标(03)与 LLM 裁判(04)把答案变成分数;错误分析(05)解释分数背后的失败;安全评测(06)回答「坏的时候会不会出事」。但证据不会自己拍板:分类准确率 92%、裁判均分 4.2/5、一次泄露考试范围的回答——这些数字放在一起,课程助教到底能不能上线?本章把这些产物汇总成一份可决策的评测报告(eval report):说明评测了什么、结果如何、代价多少,并基于「阈值、失败模式、风险缓解」的决策框架,给出明确的「上线 / 有条件上线 / 不上线」结论与理由。

**学习目标**:学完本章,你将能够——

1. 说出评测报告与结果数据、模型卡、运维报告的差别与分工;
2. 列出评测报告八个要素,并说明每要素回答什么问题、来自哪一章;
3. 用「阈值达标?失败模式可接受?风险有缓解?」三问,给出三选一结论;
4. 把 01~06 章的产物汇总成 `eval-report.md`,让结论与证据一一对应;
5. 说明评测报告如何衔接 01.03/08 的模型卡与 01.07 的治理流程。

## 1. 概念:评测报告是什么

- **评测报告(Evaluation Report)**:把一次评测的任务定义、数据、指标、分析、成本与结论汇总成可决策的文档。它不是「分数陈列馆」,而是一份带结论的证据卷宗:读者看完应当能回答「这版模型能不能用、以什么条件用」。
- 前面的章节各自只回答一个侧面:03 章说「依据正确率 92%」,06 章说「攻击样本上不安全率 12.5%」——这些数字单独存在时,无法导出任何行动;报告把它们放在同一份文档里,用同一套决策逻辑压成一句话结论。
- 报告是**一次评测快照**:记录评测日期、模型与 adapter 版本、数据与代码版本(呼应 01.02 实验追踪),过期即失效——下周换了 system prompt,本周的报告就不能再引用。
- 一个类比:指标是体检单上的各项数值,报告是医生给出的诊断与处方建议——数值自己不会告诉你「该不该住院」,诊断才会。

## 2. 为什么需要:把「上线/不上线」从感觉变成依据

- 01 章否掉了「感觉变好了」,本章否掉它的上线版本:「感觉可以上了」。上线是有成本的决策——把模型暴露给真实用户,出错会伤害使用者、占用运维精力,再下线则更难看;没有报告的团队,依据往往是「最近没怎么出错」,这正是 05 章说过的幸存者偏差。
- 报告至少服务三类读者,每类带着不同问题:
  - **决策者**(导师/PM):能不能上线、风险是什么——看结论、八要素摘要与条件;
  - **开发者**(你自己):下一步改什么——看错误分析摘要与 backlog;
  - **审计者/协作者**:这份证据可信吗——看数据来源、版本与原始输出链接。
- 报告让决策**可追溯、可质疑**:两个月后有人问「当初为什么让它上线」,报告就是答案;反对者可以指着具体数字反驳,而不是「我感觉不行」对「我感觉行」。
- 报告把「本次结论」与「改进方向」分开记录:上线与否是一次快照的判决,失败分类与 backlog(05 章)是下一轮迭代的输入;都写进报告,避免「否决上线」与「停止改进」被混为一谈。

## 3. 位置:与结果数据、模型卡、运维报告的分工

本单元不断产出文档,容易混淆;它们回答不同问题、服务不同读者:

| 文档 | 回答的问题 | 主要读者 | 更新节奏 |
|---|---|---|---|
| golden-results.jsonl 等原始输出 | 每条输入对应的完整输出是什么(可复现) | 开发者、审计 | 每次评测生成 |
| eval-report.md(本章) | 这次评测后,能不能上线、以什么条件 | 决策者 | 每次评测快照 |
| model-card.md(01.03/08;01.07/02) | 模型是什么、能/不能做什么、如何回滚 | 使用者 | 模型版本变更时 |
| 运维报告(01.04) | 线上表现、成本、延迟、事故 | 运维 | 持续 |

评测报告是**过程产物与治理文档之间的桥**:它吃进原始结果,吐出决策结论;结论通过后,模型卡对外发布,运维报告接棒线上表现。四者构成一条完整证据链,缺一环都不可审计。

## 4. 报告要素:八个部分与来源

| # | 要素 | 来自 | 回答的问题 |
|---|---|---|---|
| 1 | 评测目标与范围 | 01 评测计划 | 本次要回答什么问题、覆盖哪些任务与模型(含基线与 adapter) |
| 2 | 黄金集描述 | 02 golden.jsonl | 测了什么题、多少条、类别分布、来源与版本、去污染声明 |
| 3 | 指标结果(含盲点) | 03 eval_metrics.py | 各任务分数多少;哪些分数会骗人(如 ROUGE 低估合法改写) |
| 4 | 裁判与一致性 | 04 judge.py | 开放题 rubric 均分;与人工的一致率、偏差方向 |
| 5 | 错误分析摘要 | 05 聚类表 | 主要失败类型与占比、可能根因、改进 backlog |
| 6 | 安全与鲁棒性结果 | 06 safety-report.md | 不安全率与误伤率;缓解是否落实、遗留风险是什么 |
| 7 | 成本与延迟 | 推理侧实测(01.04 方法) | 单次回答多少钱、多慢;按使用量折算的预算是否可承受 |
| 8 | 基线对比 | 各章与 base 的对照列 | 相对 base 或上一版,改善是否真实、代价是否可接受 |

要点:

- 要素 1~2 保证**可理解**:没有目标与数据描述,数字没有语境;
- 要素 3~4 保证**可信任**:指标盲点与裁判偏差不写,报告就是自欺欺人;
- 要素 5~6 保证**可行动**:失败与风险是改进与缓解的起点;
- 要素 7 是**业务约束**:再好的模型,单次成本超过课程预算也上不了线;
- 要素 8 保证**不白忙**:adapter 相对 base 没有可测改善,结论就应是「不上线,回 01.03 重新设计」——呼应 01.03/08 的验收纪律。

## 5. 决策框架:三问与三态结论

报告的最后一段必须明确。用三问把证据过一遍:

1. **阈值达标了吗?** 对照 01 章计划里写死的阈值逐项核对(分类 F1、格式合规率、拒答正确率、裁判均分、延迟预算)。数字没到阈值,不是「差不多」,是「没达标」;
2. **失败模式可接受吗?** 05 章的聚类里,失败集中在哪类?是「资料外偶尔编造但会补一句不确定」,还是「考试范围这类核心题系统性出错」?前者可能可接受,后者不行;
3. **风险有缓解吗?** 06 章发现的每条不安全/误伤,是否已有规则层、护栏或人工复核兜底,并重跑回归确认?安全是 01 章就定下的硬红线:**任何一条「不安全」都是 blocker**,不允许用平均分「稀释」。

结论只有三种,且必须可核查:

| 结论 | 含义 | 报告必须给出 |
|---|---|---|
| 上线 | 三问全过,证据充分 | 支持的指标与安全结果;使用者须知(接模型卡) |
| 有条件上线 | 大体达标但有明确缺口 | **逐条列出条件**:修什么、谁复核、何时复查 |
| 不上线 | 阈值未达、失败不可接受或风险未缓解 | 主要 blocker 与下一轮改进方向(回数据、改提示还是换方案) |

以课程助教为例的决策演示(数字为示例,写报告时换成自己跑出的结果):

| 检查 | 示例结果 | 判定 |
|---|---|---|
| 分类题 F1 | 0.89(阈值 0.85) | 达标 |
| 格式合规率 | 90%(阈值 85%) | 达标 |
| 裁判均分 / 与人工一致率 | 4.2/5;一致率 85%,偏差方向「略宽松」 | 达标(标注偏差) |
| 主要失败模式 | 资料外编造占失败 40%(05),不涉考试范围 | 可接受 |
| 安全双比率 | 不安全率 12.5%(1 条敏感泄露),误伤率 0 | **红线未过** |
| 成本与延迟 | 0.004 元/次、1.2 秒 | 达标 |

结论:**有条件上线**——示例中唯一 blocker 是那条敏感信息泄露:先按 06 章 4.2 的规则层与护栏修复,重跑 attack set 确认不安全率归零后再放开;在此之前仅限内部试用并保留人工复核。注意这里的决策链:不是「92% 很漂亮所以上线」,而是「唯一 blocker 可修、可复核、有关闭条件」。

## 6. 动手活动:汇总成一份可决策的 eval-report.md

> [!example] 动手活动:把 01~06 的产物汇成评测报告
>
> **目标**:`finetune/eval/eval-report.md`,给出明确的三选一结论与理由。
>
> **步骤**:
> 1. 按第 4 节八要素搭骨架,逐节填入对应产物:从 01 计划抄目标与阈值,从 02 抄黄金集描述与去污染声明,把 03 的分数与盲点说明、04 的一致率与偏差方向、05 的失败占比表、06 的双比率与缓解状态原样搬入,补上实测的成本与延迟,再与 base 逐项对比;
> 2. 所有失败例与原始输出**原样链接**(golden-results.jsonl、attack set 响应文件等),不挑不剪;
> 3. 用第 5 节三问逐项核对,在报告开头或结尾写下结论与理由;「有条件上线」必须逐条列出条件与复核人;
> 4. 写「复现说明」:评测日期、模型与 adapter 版本、system prompt 版本、数据与代码 commit、运行命令——第三方照做应得同样结果;
> 5. 通读一遍检查「结论与证据一致」:证据显示红线未过却写「上线」,就是报告事故。
>
> **完成标准**:一个没参与过前六章的人,只读这份报告就能复现评测、看懂每项数字的含义与盲点,并同意或否决你的结论——而不是被「感觉」说服。

## 7. 边界与排错

- **把报告写成流水账**:只贴分数不写含义、盲点与结论,读者得到一堆数字而非决策;每项数字都要回答「这说明什么、可信吗、影响结论吗」;
- **只报均分、隐藏失败**:失败例要原样链接;「全部通过」却链接不到原始输出,等于没说;
- **结论与证据脱节**:最常见的是证据只够「有条件上线」,结论却写「上线」;写结论前用三问逐条核对,红线上没有妥协;
- **忘记版本与可复现信息**:没有日期与版本的报告无法审计,两周后连自己都无法复现(呼应 01.02);
- **安全章节缺席**:没跑 06 章的 attack set 就写「未发现安全问题」,或干脆留空——这不是省略,是误导;应如实写「本轮未做安全评测,结论仅限内部试验」;
- **把报告当模型卡**:报告回答「这次能不能上线」,模型卡回答「这个模型是什么、边界在哪」;前者进决策流程,后者对外发布,别互相替代(01.07 的发布审查要求两者齐备);
- **一次报告定终身**:上线后真实用户问题 ≠ 黄金集,错误分析要继续;新一轮报告与运维监控(01.04)共同决定何时换版或下架。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 评测报告是什么 | 把任务、数据、指标、分析、成本压成一份带结论的证据卷宗 |
| 为什么需要 | 让「上线/不上线」成为有依据、可追溯、可质疑的决定 |
| 八个要素 | 目标范围、黄金集、指标(含盲点)、裁判一致性、错误摘要、安全结果、成本延迟、基线对比 + 上线建议 |
| 决策三问 | 阈值达标?失败模式可接受?风险有缓解?(安全红线 0 容忍) |
| 结论三态 | 上线 / 有条件上线(逐条列条件)/ 不上线(列 blocker) |
| 与相邻文档的分工 | 原始结果=证据,报告=决策,模型卡=对外说明,运维报告=线上表现 |
| 动手产物 | eval-report.md:八要素齐备、失败原样链接、三选一结论与理由 |

**思考题**:所有指标都过了阈值,但黄金集只有 10 条且集中在「主键」类问题,报告该给什么结论?「有条件上线」写完后,由谁、按什么流程确认条件已关闭(联系 01.07 的发布审查)?如果 ROUGE-L 下降了、但人工复核与裁判都显示回答变好了,报告应如何呈现这个矛盾?

> [!note] 参考答案
> 阈值通过补不了数据之薄:黄金集覆盖面不足时,「达标」只对测过的问题成立;结论应降级为「有条件上线」或「不上线」,条件是扩充黄金集(补边界与拒答类)后重跑——02 章「数量少但精」的前提,正是覆盖关键类别。条件的关闭不能由写报告的人自己说了算:应约定复核人(导师或协作者)与关闭标准(如重跑 attack set 全部通过、失败项在原始输出中可见),在 01.07 的发布审查流程里正式关闭并存档,别让「有条件」变成「悄悄上线」。ROUGE-L 降而质量升,恰是 03 章指标盲点的实例:词面重叠惩罚了合法改写;报告应同时呈现两个证据(指标下降 + 裁判与人工上升),解释盲点,结论以语义证据为准,并把「允许自然改写」写进黄金集的期望行为,让下一版指标与目标对齐。
