# 构建黄金数据集

> 上一章把「评测目标、指标、阈值」写进了评测计划,但计划只是一张蓝图:真正要回答「模型答对了吗」,手里必须先有一批**人工审核过、答案已知的考题**。本章解决的就是这个问题——为课程助教建一套 18 条的黄金数据集(golden set):讲清它和训练数据的区别、期望行为该怎么标注、为什么题目绝不能「被模型见过」,最后交付一份可版本化的 `golden.jsonl` 与校验脚本。

**学习目标**:学完本章,你将能够——

1. 说出黄金集的定义,并用「练习册、模拟考、期末题」讲清它与训练、验证数据的区别;
2. 解释为什么模型输出是开放的,必须用「期望行为」而不是逐字答案来评判;
3. 按常见、边界、高风险三类收集题目,说明「少而精」的理由与版本化纪律;
4. 解释去污染(decontamination)的含义,以及评测题泄漏进训练数据的三种途径;
5. 为课程助教创建 18 条、四类别的 `eval/golden.jsonl`,附版本记录与校验脚本。

## 1. 概念:黄金集是「人工审核过的期末题」

- **黄金集(golden set)** 是一组固定的、**人工逐条审核过**的「问题 → 期望行为」样本,是评测的基准答案,也是后续所有分数(03 章自动化指标、04 章 LLM 裁判)共同的考场。
- 每个样本只回答两件事:**问什么**(输入)与**怎样算答对**(期望行为)。它不含标准答案全文——期望行为描述的是「对的样子」,不是「唯一的话」。
- 复习 01.03/08 的数据三分法,把它延续到评测场景:

| 数据角色 | 类比 | 谁看过 | 用途 |
|---|---|---|---|
| 训练数据 train | 练习册 | 模型反复读 | 学知识、学格式 |
| 验证数据 valid | 模拟考 | 模型间接见过 | 早停、选 checkpoint |
| 黄金集 golden | 期末题 | **模型从未见过** | 评测与验收 |

- 与 01.03 的 golden set 一脉相承:那里用于「训练前冻结、收官验收」;本单元把它升级为**持续评测的标尺**——每一次改提示词、换 adapter、换基座,都跑同一套题,分数才能互相比较。

## 2. 为什么需要:没有参考答案,就谈不上对错

- 传统机器学习评测有明确的 ground truth 标签,算个准确率即可;而 LLM 输出是**开放生成**——同一道题,合法答案有无数种写法,没有「唯一正确串」可供比对。
- 既然答案开放,评判就必须依赖外部约定:一套人工审核过的期望行为。没有它,「感觉变好了」无法量化,两个版本的模型也**没有共同的比较基准**——你说 8.0 好,我说 7.5 好,谁也说服不了谁。
- 黄金集还是整个评测流程的**地基**:03 章的自动化指标在它上面算分,04 章的裁判在它上面打 rubric,05 章的失败样本从它上面产生。地基若是随手抓来的题目,再精妙的指标也只是在给垃圾数据化妆。

## 3. 作用与位置:评测改进循环里的固定锚点

```mermaid
flowchart LR
    A[01 评测设计<br>任务与指标] --> B[02 黄金集<br>固定考题]
    B --> C[03/04 跑分<br>程序化指标 + LLM 裁判]
    C --> D[05 错误分析<br>找失败模式]
    D --> E[改提示 / 换模型 / 补数据]
    E --> B
```

- 黄金集的价值在于**固定**:锚点不动,循环里其他一切都可以动。今天改提示词、明天换 adapter,都回到同一套题上重跑,分数曲线才有意义;上线后新发现的线上事故,也应沉淀成**新的黄金题**,防止同类问题静默回归(呼应 01.04/07 的运维纪律)。

## 4. 收集:三类问题、少而精、版本化

- 选题覆盖三个层次,缺一不可:
  - **常见题**:高频主流程,如「主键是什么?」「解释外键」——保证日常使用质量;
  - **边界题**:资料外、模糊、歧义的输入,如「明天东京的天气?」——检验拒答与澄清能力;
  - **高风险题**:诱导编造、索要学员隐私、要求绕过规则——检验最坏情况下的行为。
- 数量**少而精**:15~20 条足够起步。理由有三:每条都要人工审核与逐条复核,多了审不过来;分数是「信号」而非统计检验,20 条足够暴露大问题;呼应 01.03 的数据纪律与 LIMA 实验——**少量可信、覆盖失败边界的样本,胜过海量随手抓来的题目**。
- 全对或全错的题目要警惕:若 18 题全部答对,说明题太易、没有区分度,应补边界与高风险题;若大面积答错,先回去检查 01 章的任务定义与提示词,而不是急着改题。
- **版本化纪律**(延续 01.03/08 的冻结原则):`golden.jsonl` 用 git 管理,创建时间戳早于任何训练 run;发现要改题,不原地修改,而是**升版本**(v1.0 → v1.1)并记录变更原因,保证历史分数可追溯。

## 5. 标注:期望行为,不是逐字答案

- 每条样本记录五个字段:`id`、`category`、`question`、`expected_behavior`、`source`。其中 `expected_behavior` 是灵魂——它描述「什么样的输出算对」,例如「给出主键定义,并说明值唯一且非空」。
- **「拒绝编造」同样是合法期望**:对资料外问题,期望行为就是「明确说明没有依据并拒答」——一条标注得当的拒答题,能让「答得好」与「拒得对」都被测到。
- 好期望行为的三条标准:可判定(两个评分人能达成一致)、聚焦(一条只测一个行为,不叠三个要求)、挂钩(能回指到 01 章评测计划里的任务与指标)。

| 类别 | 数量 | 示例问题 | 期望行为写法 |
|---|---|---|---|
| 答案题 | 8 | 「什么是主键?」 | 给出定义与关键性质(唯一、非空) |
| 拒答题 | 4 | 「明天东京的天气?」 | 明确说明无实时资料并拒答,不编造 |
| 格式题 | 3 | 「用三点解释外键」 | 恰好三点、每条一句,遵守输出约定 |
| 边界题 | 3 | 「主键和外键是不是一回事?」 | 先澄清概念差异,再分别定义 |

## 6. 去污染:题目绝不能「被模型看过」

- **去污染(decontamination)** 指确保评测题及其近似变体从未进入模型见过的任何材料——否则模型「背过题」会被误读成「会做题」,分数系统性虚高。GPT-4 技术报告专门披露了基准测试去污染的做法,可见这是行业共识。
- 三条典型泄漏途径,对照自查:
  1. **微调数据泄漏**:评测题(或同题换词)混进了 01.03 的 `train.jsonl`;
  2. **提示词泄漏**:评测题被当 few-shot 示例写进 system 或上下文;
  3. **开发过程泄漏**:开发时用这道题调过提示词,记住了它的「正确答案」。
- 呼应 01.05 的图文泄漏教训:评测泄漏和训练数据泄漏是同一种病——**信息从不该出现的地方流入模型**,只是这里的后果是分数失真。实操:建集时记录时间戳;把 `golden.jsonl` 的问题与 `train.jsonl` 的 user 消息做近似重复扫描;发现交集即作废该题并在版本记录中说明。

## 7. 动手:创建 golden.jsonl

- 在课程助教评测项目下创建 `eval/golden.jsonl`,共 18 条(配额见第 5 章表格),**每行一个 JSON 对象,对象内部不换行**:

```json
{"id":"qa-01","category":"answer","question":"什么是主键？","expected_behavior":"给出主键定义：唯一标识表中每一行的一列或一组列，值唯一且非空","source":"课件：数据库基础，2026-09-03"}
{"id":"refuse-01","category":"refuse","question":"明天东京的天气怎么样？","expected_behavior":"明确说明没有实时资料并拒答，不编造天气","source":"真实用户边界问题，2026-09-03"}
```

- 写完后在 `eval/` 下建 `check_golden.py`,校验 JSON 合法性、字段齐全、id 唯一,并对训练数据做粗略去污染扫描:

```python
import json
from pathlib import Path

rows = [json.loads(x) for x in Path("eval/golden.jsonl").read_text().splitlines() if x]
assert 15 <= len(rows) <= 20, f"数量应为 15~20,当前 {len(rows)}"
ids = [r["id"] for r in rows]
assert len(ids) == len(set(ids)), "存在重复 id"
for r in rows:
    for k in ("id", "category", "question", "expected_behavior", "source"):
        assert k in r and str(r[k]).strip(), f"{r.get('id','?')} 缺少字段 {k}"
train_text = Path("finetune/data/train.jsonl").read_text(encoding="utf-8") if Path(
    "finetune/data/train.jsonl").exists() else ""
leaks = [r["id"] for r in rows if r["question"][:10] in train_text]
print(f"golden 共 {len(rows)} 条;疑似泄漏: {leaks or '无'}")
```

- 运行 `python eval/check_golden.py`;任何 `JSONDecodeError` 都表示某行不是合法 JSON,应定位行号修复而非删除重来——删数据会把「该审的问题」一起删掉。

> [!example] 动手活动:交付 v1.0 并记录版本
> **目标**:`eval/golden.jsonl`(18 条,四类别齐全)、`eval/check_golden.py` 与 `eval/golden-README.md`。**步骤**:在 README 记录版本 v1.0、创建时间、作者、每类题目来源与审核人;把 golden 的问题与 01.03 的 `train.jsonl` 逐条比对,确认无近似重复后提交 git。**完成标准**:脚本输出「golden 共 18 条;疑似泄漏:无」;随机抽 5 条,能说出每条期望行为判定的依据。

## 8. 边界与排错

- **分数全对或全错**:题目太难或太易,没有区分度——补边界/高风险题,或回到 01 章复查任务定义;
- **期望行为写成了逐字答案**:合法改写会被误判,人工复核时评分人也会吵架——改成描述「关键事实 + 格式 + 边界」,而不是抄一段范文;
- **题与训练数据近似重复却没发现**:分数虚高而不自知——建集时跑一次去污染扫描,每次训练数据变更后重扫;
- **黄金集越加越肥**:上百条后人工复核与裁判成本失控,失去「少而精」的快速反馈优势——新增题目需说明它覆盖了哪个新失败模式,否则不收;
- **只收集常见题**:拒答与高风险行为完全没有评测覆盖——把风险题当成普通题一样对待,坏行为才会在评测期暴露而不是上线后。

## 9. 总结

| 关键判断 | 一句话 |
|---|---|
| 黄金集是什么 | 人工审核过的「问题 → 期望行为」样本,模型从未见过的期末题 |
| 为什么需要 | 开放生成无唯一答案,必须靠外部期望行为定对错;它是所有指标的地基 |
| 怎么收集 | 常见/边界/高风险三类;15~20 条少而精;git 版本化,改动升版本 |
| 怎么标注 | 期望行为而非逐字答案;「拒答不编造」也是合法期望 |
| 去污染 | 评测题不得进入训练数据、提示词示例与开发过程,否则分数虚高 |

**思考题**:为什么 golden 集只写 `expected_behavior` 而不写参考回答全文?若上线后发现有一条黄金题恰好被用户问过并进入了后续的训练数据,你该按什么流程处理?

> [!note] 参考答案
> 写期望行为是为了「判对错」,写全文则会诱导评分人(包括 LLM 裁判)做逐字比对,惩罚合法的不同表述;且全文一旦泄漏给模型,等于把答案提前交卷。发现黄金题进入训练数据即构成污染:作废该题、在 `golden-README.md` 记录泄漏途径与时间,升级为 v1.1 并补一条同难度新题——分数必须始终建立在「没被看过」的题上。
