# 错误分析

> 上一章让 LLM 裁判给开放题打了 1~5 分,03 章的程序化指标算出了准确率与 ROUGE——但分数只回答「差多少」,回答不了「差在哪」。本章解决这个问题:把所有失败样本收集起来,系统性地找出**重复出现的失败模式**,给每个模式定位根因并排优先级,产出一份可以直接执行的改进清单(backlog)。它是评测循环里连接「发现问题」与「解决问题」的一环:没有它,分数再低也只是数字;有了它,下一次改进才有明确靶子。

**学习目标**:学完本章,你将能够——

1. 说出错误分析的定义:系统性查看失败样本、寻找重复出现的失败模式,而非纠缠单点怪例;
2. 解释为什么分数无法指导改进,错误分析为什么是改进循环里不可跳过的一步;
3. 走完错误分析五步:收集失败样本 → 聚类 → 归类 → 量化占比 → 定优先级;
4. 用「数据、提示、能力、工具」四问为每个失败模式定位可能根因;
5. 说出人工聚类与 LLM 辅助归类的分工,理解 CLEAR 的思路(先逐条反馈、再聚成系统级问题);
6. 对课程助教的失败输出做聚类,产出「问题类型 × 占比 × 示例 × 可能根因」表,排序形成改进 backlog。

## 1. 概念:错误分析找的是「重复出现的失败模式」

- **错误分析(Error Analysis)** 是指:把评测中所有被判为失败的样本收集起来,逐条看、分组、找规律,最终得到一份**按问题类型组织的失败清单**——而不是「这一条为什么错了」的个案解释。
- 为什么必须是「模式」而不是「个案」?单个失败样本可能是噪音(某次采样运气差、某条题本身有歧义),没有改进价值;**重复出现的失败模式才是信号**:它说明系统的某一部分稳定地出了毛病,改掉它就能批量救回一批样本。粗糙的经验门槛是:同一类型至少出现 2~3 次才值得立为一个模式。
- 分数是「聚合统计」,天然抹平个体差异:90 分可能是「全部良好」,也可能是「一半完美、一半灾难」被平均成 90。错误分析把聚合结果拆回逐条样本,再按失败原因重新聚成类型——先拆后聚,看的才是行为本身。
- 以课程助教为例:黄金集 20 条里有 3 条失败。如果 3 条全是「资料外问题编造了答案」,这是模式,指向拒答训练不足;如果 3 条分别是编造、格式、边界,各不相关,才需要怀疑它们只是孤立个案或题目问题。
- 错误分析在整个评测栈中的位置:01 章在 eval spec 里预留了失败分类;03 章用程序化指标抓格式类问题;04 章用 LLM 裁判给开放题打分并输出逐条反馈;本章吃掉**所有**失败样本做诊断,产物是下一轮「补数据 → 重训 → 再评测」循环的输入。

## 2. 为什么需要:分数不告诉你「下一步改什么」

- 一个分数无法指导动作:「准确率 78%」该补数据还是改提示词?「裁判均分 3.8」该换模型还是修格式?错误分析把抽象数字翻译成具体动作,否则改进就是碰运气——重训一版、再测一次,期望它碰巧变好。
- 平均值会掩盖分布:同样 3.8 分,可能是所有回答都平平无奇(改进方向:整体能力),也可能是格式全对但有三条硬编造(改进方向:拒答)。不看失败样本分布,选错方向会浪费整轮训练成本。用同一批 20 条回答对比两种失败结构:

```text
A 组:19 条 4 分 + 1 条 0 分 → 整体没问题,灾难集中在那条硬编造上,改拒答即可
B 组:20 条全是 3 分上下    → 没有大错但每条都差一口气,要改的是整体质量
```

两组的平均分几乎一样,改进动作却完全不同——不拆开看,就只能靠猜。
- 错误分析便宜且见效快:与其花几小时重训、再花几小时评测,不如先花一小时认真读 20 条失败输出——往往能找到一条提示词缺陷或三五条缺失数据,改完立竿见影。这是评测改进循环里**性价比最高**的一步。
- 它是评测诚实纪律的延续(呼应 01.03/08):失败例必须原样保留、不能挑掉;本章更进一步——不仅保留,还要逐条分析它们为什么失败。

## 3. 方法:错误分析五步

| 步骤 | 做什么 | 课程助教示例 |
|---|---|---|
| ① 收集 | 按失败判定标准把失败样本全量捞出来,不挑样 | 裁判分 < 4 分 + 人工 0/1 判 0 分 + 格式校验不过的输出,共 20 条 |
| ② 聚类 | 先按任务组切(01 章的任务清单),再按错误表现分组 | 「解释外键」题全错 → 单独一堆;格式题全错 → 另一堆 |
| ③ 归类 | 把每组归入标准错误类型,给每类起可操作的名字 | 事实错、格式错、拒答错、幻觉、过度拒答 |
| ④ 量化 | 统计每类占比,明确基数口径 | 编造类 6/20 = 30%;拒答类 2/20 = 10% |
| ⑤ 定优先级 | 按频率 × 严重度排序,形成 backlog | 编造类最高危,排第一 |

失败样本的**判定标准**必须在收集前定好(01 章 eval spec 里就有):低于阈值、裁判打分低、人工 0/1 判负、程序化校验失败——只要在 spec 里定义过,收集时就不带主观。数量上 20~50 条失败样本通常足够暴露主要模式;样本太少模式不显,太多则人工读不完,可抽样但必须说明抽样规则。

课程助教常用的错误类型(归类表):

| 类型 | 判据 | 示例 |
|---|---|---|
| 事实错 | 有依据但与课程资料矛盾 | 说外键「必须有唯一索引」(实际课程里不要求) |
| 幻觉 | 无依据地编造 | 资料外问题「明天东京天气」编了个温度 |
| 格式错 | 没遵守输出约定 | 要求三点式却答成一段话 |
| 拒答错 | 该拒没拒 / 不该拒却拒 | 资料外问题强行作答;课程内问题答「我不知道」 |
| 过度回答 | 答了但夹带无关或臆断内容 | 解释主键时顺带编造了教材不存在的「最佳实践」 |

聚类的前提是失败样本**可复盘**:只存一条输出、丢了题目与判定依据,事后无法判断该归哪类。收集时每行应保留题目、期望行为、输出、分数与批评(与 03/04 章评测脚本的输出格式衔接),例如:

```jsonl
{"id":"q-07","task":"资料外拒答","question":"明天东京天气?","expected_behavior":"拒绝编造,不提供实时信息","score":2,"critique":"资料外问题,却编造了温度","output":"明天东京 25°C……","fail":true}
{"id":"q-11","task":"关系解释","question":"解释外键,举一个例子","expected_behavior":"与外键定义一致,例子来自课程资料","score":3,"critique":"例子与课程资料矛盾","output":"外键必须有唯一索引……","fail":true}
```

其中 `critique` 正是 04 章裁判写的逐条文字批评——它既是人复查的依据,也是第 5 节 LLM 辅助归类的原材料。

## 4. 定位根因:数据、提示、能力、工具四问

归好类只完成一半——下一步是对每个模式追问「为什么会这样」,四类根因逐项排查:

| 根因 | 典型信号 | 验证方法 | 对应动作 |
|---|---|---|---|
| 数据问题 | 失败集中在某个知识点或题型 | 查 01.03 的训练数据里该类样本数量与质量 | 补充该类型样本,重新微调 |
| 提示问题 | 换一种 prompt 表述后同样输入就答对 | 直接改写 system prompt / 加 few-shot 示例做 A/B | 修 prompt,不重训 |
| 能力问题 | 小模型做不了的多步推理或长上下文 | 换更大模型或把任务拆小做对比 | 接受局限写进模型卡,或换基座 |
| 工具问题 | 依赖 RAG / 检索的题集体答错 | 检查检索结果是否命中、文档是否过时(呼应 01.05 多模态原型) | 修检索链路或文档库 |

注意两点:一是**根因常常叠加**——编造类既可能是拒答样本不足(数据),也可能是 system prompt 没写「没有依据时说不知道」(提示);二是**从改动成本最低的开始验证**:先试提示词,再补数据,最后才考虑换模型,每验证一个假设就重跑同一 golden 集,用该类占比是否下降来确认根因找对了。

## 5. 工具:人工聚类与 LLM 辅助(CLEAR 思路)

- **人工聚类**:把失败输出逐条读、贴便签、分组,20~50 条完全手工可做。优点是可解释性强、类别贴合业务;缺点是慢、且人容易受「最近看到的那条」影响。做法:先各自独立分组,再合起来讨论不一致处(与 04 章人工复核裁判的打分纪律一致)。
- **LLM 辅助归类**:让 LLM 裁判在打分的同时输出**逐条的文字批评**(这条错在哪、为什么),再把几十条批评自动聚成少数几个系统级问题,并统计每个问题覆盖了多少样本——这就是 CLEAR 的思路。
- **CLEAR**(IBM Research 等,arXiv 2507.18392,开源包 `clear-eval`)把错误分析做成两段管道:第一段用 LLM-as-a-Judge 对每条输出生成「数值分 + 文本批评」;第二段用 **Key Point Analysis(KPA)** 把逐条批评聚成系统级问题(issue),每个 issue 映射回它覆盖的样本,量化其普遍性(prevalence),并支持从问题下钻到具体示例查看原文。它对失败分析的启示正是本章的方法论:**先逐条反馈,再聚成系统级问题,最后量化占比**——人不用亲自读完全部样本,也能得到带证据的失败清单。
- CLEAR 管道与本章五步的对应很直接:裁判的数值分与批评对应「收集」与「聚类/归类」的原材料,KPA 输出的 issue 列表就是 backlog 的草稿,prevalence 就是「量化占比」——CLEAR 自动化的是聚类与量化,**定优先级与改进验证仍要人来做**。
- 一个小技巧:给裁判的批评模板加一句「若本条无问题,直接回答『无』」,滤掉合格样本的噪音批评,聚类质量会明显提升(与 CLEAR 只对低分样本生成 issue 的做法同理)。
- **分工建议**:LLM 负责规模化初筛与聚类,人负责两件事——定义类别体系(或审查自动聚出的类别名是否可操作),以及抽查每个 issue 是否真的能映射回样本。若某 issue 映射到的样本语义对不上,说明聚类质量差,要调批评模板或换 KPA 方式,不能直接采信。

## 6. 动手活动:课程助教失败聚类与改进 backlog

> [!example] 动手活动:失败聚类,产出改进 backlog
>
> **目标**:对课程助教约 20 条失败输出做聚类,产出一张「问题类型 × 占比 × 示例 × 可能根因」表,并按优先级排出改进 backlog。
>
> **步骤**:
> 1. 汇总失败样本:取 04 章裁判打分 < 4 分的输出、03 章程序化指标判负的输出、人工 0/1 判 0 分的输出,合并去重,凑够约 20 条(不足可把「勉强及格」的边界样本纳入,并注明口径);
> 2. 逐条写一句话失败原因:「该拒答却编造了天气」「外键例子与课程资料矛盾」——写原因时不看其他条,避免互相污染;
> 3. 聚类:把原因相近的样本归成 3~6 个问题类型,给每类起**可操作的名字**(不是「质量差」,而是「资料外问题编造答案」);
> 4. 填表:对每类统计占比,挑 1 条代表性样本原文,用第 4 节四问给出可能根因与建议动作;
> 5. 排序:按「频率 × 严重度」排出 backlog,硬红线(编造、有害)无条件置顶,即使它只占 1 条;
> 6. 写验证方式:每项 backlog 都要配一句「怎么算改好了」——例如「重跑 golden,编造类从 6 条降到 0 条,且格式类不回升」。
>
> **完成标准**:backlog 里每一项都能被一个具体工程动作消灭或缓解(改 prompt / 补 N 条数据 / 修检索),且每项都有可重跑评测验证的完成定义——改进后必须重跑同一 golden 集,确认目标类占比下降、其他类没有回退。

## 7. 边界与排错

- **把单点怪例当模式**:一条失败就重训一版模型,成本高且大概率无效;用「同类至少 2~3 次」的门槛过滤,个案先记录在案、攒够再处理。
- **把模式当单点怪例**:三条失败恰好分布在不同题上就宣布「没有规律」——先按错误类型而不是按题目聚类再下结论,症状相同、题目不同恰恰是最常见的模式形态。
- **失败样本不全**:只保存了模型输出、丢了输入与评分上下文,事后无法复盘;评测脚本应把 `question`、`expected_behavior`、`output`、`score`、`critique` 存成同一行(03/04 章的输出格式已为此预留)。
- **类别名太抽象**:「回答不佳」「质量有待提升」无法翻译成动作;每类名字要能直接接一句「因为它……所以我们要……」。
- **混淆症状与根因**:「编造」是症状,根因可能是拒答样本不足、prompt 没声明边界或检索没命中——四问都要过一遍,别停在症状层。
- **分析一次就完**:错误分析应跟着每轮评测自动重跑,backlog 要定期关单;只做一次的分析,结论会随数据与提示词变化而过期。
- **盲目信任 LLM 聚类**:自动聚出的 issue 可能臆造或重复;抽查映射率(issue 与样本语义是否吻合),映射率低就说明批评或聚类环节要调。
- **改进后不重跑评测**:改了 prompt/数据却不回测,就无法确认「变好了」;改进闭环的最后一步永远是重跑同一 golden 集并对比该失败类占比。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 错误分析是什么 | 系统性查看失败样本,找重复出现的失败模式,而非单点怪例 |
| 为什么需要 | 分数只告诉「差多少」;失败模式清单才告诉「差在哪、先改什么」 |
| 五步方法 | 收集失败样本 → 聚类 → 归类 → 量化占比 → 定优先级 |
| 根因四问 | 数据、提示、能力、工具;从改动成本最低的开始验证 |
| 工具 | 人工聚类可解释;CLEAR 思路 = LLM 裁判逐条文字批评 + KPA 聚成系统级问题并量化占比 |
| 动手产物 | 「问题类型 × 占比 × 示例 × 可能根因」表 + 排序的改进 backlog,每项带验证方式 |

**思考题**:课程助教黄金集 20 条错了 6 条:3 条资料外编造、2 条格式不符、1 条边界题过度拒答——你会先改哪一类?为什么编造类即使只占 3 条,优先级也高于占 2 条的格式类?如果改进后重跑,编造类降为 0 但格式类从 2 条升到 5 条,这说明什么?

> [!note] 参考答案
> 先改编造类:它触碰「不编造」这条硬红线,一次事故就足以摧毁学生对助教的信任,属于严重度权重最高的失败;格式类虽然条数接近,但后果是观感问题而非信任问题。改进后编造归零、格式却恶化,说明改动引入了副作用——典型如把「没有依据时说不知道」写进 prompt 后模型变得过度谨慎,连格式约定都开始敷衍;正确做法是回到第 4 节四问,把格式要求以更显式的方式(输出模板 + few-shot)重新加固,再跑一轮评测,直到两类都不回退。这正是错误分析要循环执行的原因:修好一个模式,常常暴露或放大另一个模式。
