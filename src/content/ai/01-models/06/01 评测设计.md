# 评测设计

> 01.03 微调出了更懂课程资料的课程助教 adapter,01.05 做出了能看 PPT 截图的多模态原型——它们「看起来变强了」,但拿什么证明真的达标、可以交付?本章解决这个问题:在动手跑任何分数之前,先设计一次可信的评测——把任务、指标、阈值、失败分类定义清楚,产出一份可执行的评测计划(eval spec)。它是整个 01.06 单元的地基:本章的计划定了「测什么、怎么算过」,后面各章依次补上黄金数据集(02)、程序化指标(03)、LLM 裁判(04)、错误分析(05)、安全评测(06)与最终报告(07)。

**学习目标**:学完本章,你将能够——

1. 说出评测的定义,解释它为什么与传统机器学习评测不同(开放生成、无单一答案);
2. 解释为什么没有评测的「感觉变好了」不可靠,评测为何是改进循环的锚点;
3. 说出评测四要素(任务定义、指标选择、阈值、失败分类),并说出评测目标必须可衡量且对应业务目标;
4. 区分离线评测与在线评测,描述分层评测(程序化指标 → LLM 裁判 → 人工)各自的位置;
5. 为课程助教写出一份 eval spec:任务清单、每任务的指标与阈值、失败类别、成本预算。

## 1. 概念:评测 = 任务 + 指标 + 阈值 + 失败分类

- **评测(Evaluation)** 不是「跑几个例子看看效果」,而是**用定义好的任务、指标与阈值,判断模型在特定使用场景下是否达标**。三个关键词缺一不可:任务没定义清,测出来的分数不知道在说什么;指标不合适,分数会骗人;不设阈值,分数再高也无法回答「能不能上线」。
- 传统机器学习评测通常是**有标准答案的闭卷考**:图像分类对一张图,`label` 是唯一的,算准确率就行。LLM 评测本质不同——模型输出是**开放的**:同一个问题「解释外键」,一千个合格助教有一千种说法,没有唯一的正确答案可以比对。
- 因为输出开放,LLM 评测要把「什么算对」翻译成**可检查的期望行为**:事实是否与课程资料一致、是否遵守输出格式、资料外问题是否拒答、回答是否有害。测的不是「和标准答案一字不差」,而是「行为是否符合期望」。
- 评测的产物不只是分数,还包括**失败的分类**:哪些题错了、错成哪一类(事实错、格式错、拒答错……)。分数告诉你「差多少」,失败分类才告诉你「差在哪、下一步改什么」。

## 2. 为什么需要:评测是改进循环的锚点

- 「模型好像变聪明了」「这几条回答挺专业」——这些**感觉**不可靠:人很容易记住变好的几条、忘掉变差的几条;而且没有基线对照,「感觉变好」可能只是提问姿势变了。01.03/08 反复强调的纪律就在这里落地:没有改前成绩,就无法证明训练有效。
- 评测是**改进循环**的锚点,每一次「改数据、调提示词、重训练」都要靠评测闭环:

```text
设计评测 → 构建数据 → 跑指标 → 分析失败 → 改进 → 回到评测
   (本章)    (02 章)   (03/04 章)  (05 章)   (01.03 方法)
```

- 锚点的意思是:**循环里只有评测是「不变的标准」**。数据可以重造、模型可以重训,但评测任务与阈值一旦定下,就不能因为「这题太难、模型答不好」而偷偷改简单——改了,后面的分数就失去可比性(这正是 01.03/08 golden set 先冻结的原因)。
- 评测还承担**验收与沟通**职能:向上汇报「能不能上线」、向同事交接「已知会错什么」、向第三方证明「没有挑样例」,靠的都是同一份可复现的评测,而不是演示。
- 评测设计要**先于模型存在**:理想状态下,拿到模型之前就写好任务与阈值——先定「怎么算过」,再让训练去够它。反过来等「模型训完再想怎么测」,阈值会不自觉地迁就模型现状,评测就失去了仲裁作用;这也解释了 01.03/08 为什么坚持 golden 集必须在训练前冻结。

## 3. 评测四要素

任何评测计划都围绕四个问题展开,缺一个都不完整:

| 要素 | 要回答的问题 | 课程助教上的例子 |
|---|---|---|
| 任务定义 | 测什么能力、输入输出长什么样、覆盖哪些边界 | 「课程概念问答」「格式题」「资料外拒答题」等任务清单 |
| 指标选择 | 每条输出如何打分、用什么工具打 | 依据正确率、格式合规率、拒答正确率、ROUGE-L(03 章)、LLM 裁判分(04 章) |
| 阈值 | 多少分算过、哪些错误不可接受 | 依据正确率 ≥ 90%、拒答题编造 = 0 容忍 |
| 失败分类 | 不达标的输出如何归类、后续怎么处理 | 事实错/格式错/过度拒答/幻觉,每类给示例(05 章) |

- **评测目标必须可衡量,且对应业务目标**。业务目标说「助教要让学生满意」不可直接测;把它拆成「回答有依据、资料外不乱说、遵守格式、及时响应」,再为每条配可测指标与阈值,业务语言就变成了工程验收标准。
- 阈值要区分**硬红线**与**软指标**:编造课程资料里不存在的内容、泄漏私密信息属于硬红线,一条都不许有(阈值 = 0 容忍);「回答简洁程度」这类软指标可以定宽松阈值或只记录不卡上线。

## 4. 评测发生在哪:离线、在线与分层

- **离线评测(offline)**:用固定的题集与脚本,在发布前对模型打分。便宜、可复现、可回归,是日常迭代的主力;本单元 01~07 章做的都是离线评测。
- **评测运行本身也要可复现**:记录评测代码版本、模型与 adapter 版本、生成参数(`temperature`、`max_new_tokens`、seed)与依赖版本——同一模型同一题两次跑分不一致,先查解码参数再怀疑模型。这条纪律呼应 01.02/10 的实验追踪:评测 run 也是实验 run,不进追踪体系就无从解释分数漂移。
- **在线评测(online)**:模型上线后,用真实用户流量观察(用户点不点赞、是否追问、线上日志的失败率)。它测的是**离线题集覆盖不到的真实分布**,但代价高、反馈慢、不可复现。两者关系:离线评测通过才能上线,在线评测则持续验证「离线假设没有过期」。
- **评测目标与交付管线一致**:01.05/05 已埋下伏笔——评测时怎么调用模型(同一 system prompt、`do_sample=False`、同一图像预处理),交付时就要怎么调用;评测管线若比交付管线更宽容,分数就虚高。
- **分层评测**:不同层级的评分者,精度与成本递增,配合使用:

| 层级 | 谁在评分 | 适合评什么 | 成本/速度 | 何时用 |
|---|---|---|---|---|
| 程序化指标 | 代码规则(含 ROUGE、JSON 校验) | 分类正确性、格式、关键词 | 最低/即时 | 每个改动都跑回归 |
| LLM 裁判 | 强模型按 rubric 打分 | 帮助性、连贯性、安全性 | 中/快 | 开放题批量打分 |
| 人工评测 | 领域专家逐条审 | 事实准确性、边界判断 | 最高/慢 | golden 集全量或抽样复核 |

- 上一单元(01.05/05)的人工逐条 0/1 评分就是「人工层」的雏形;本单元 02 章把题集系统化为黄金集,03/04 章把评分自动化,人工则退到「复核裁判、抽查底线」的位置。

综合以上,设计一次评测的推荐顺序如下(可直接当作写 eval spec 的提纲):

1. 从业务目标写出**可衡量目标与硬红线**,先于任何模型;
2. 列**任务清单与样例题**,覆盖常见、边界、高风险三类输入;
3. 为每个任务选定**评分层级**(程序化/LLM 裁判/人工)与对应指标;
4. 定下每个指标的**阈值**,并列出预期的失败类别;
5. 估算**成本**、把计划纳入版本管理,再进入 02 章的数据构建。

这五步走完,评测计划就不再是「跑分脚本的需求说明」,而是一份可以评审、可以冻结、可以追溯到业务目标的工程文档。

## 5. 动手活动:写一份评测计划(eval spec)

> [!example] 动手活动:为课程助教写 eval spec
>
> **目标**:在 01.03 的 `finetune/` 项目里新建 `finetune/eval/eval-spec.md`,把本章四要素落成一份可执行的评测计划。若你完成了 01.05 多模态原型,可在计划中追加「截图问答」任务组。
>
> **步骤**:
> 1. **写业务目标与可衡量目标**:一句话业务目标,再拆成 2~4 条可测量指标(含硬红线);
> 2. **列任务清单**:至少四个任务组——课程概念问答(如「主键是什么?」「解释外键,举一个例子」)、格式题、资料外拒答题(如「明天东京天气?」)、边界歧义题(如「这章会考吗?」),每组 2~3 道样例题;
> 3. **为每组定指标与阈值**:参考下方「任务组示例表」填写,硬红线单独标注;
> 4. **定义失败类别**:列出你预期会看到的失败类型(事实错、格式错、过度拒答、编造等),各给一句话示例;
> 5. **写成本预算**:估算每轮评测的 token 消耗与人工耗时(见下)。
>
> **完成标准**:第三方拿到 `eval-spec.md`,不看任何代码,也能说出「这门课助教评测哪些任务、每个任务多少分算过、出错算什么、一轮要花多少钱」。

课程助教「任务组示例表」(把第 3 节四要素落到五个任务组;你可以在 eval spec 里直接改数值):

| 任务组 | 样例题 | 指标 | 阈值示例 | 失败类别 |
|---|---|---|---|---|
| 概念问答 | 「主键是什么?」 | 依据正确率(人工/裁判) | ≥ 90% | 事实错、幻觉 |
| 关系解释 | 「解释外键,举一个例子」 | 依据正确率 + 格式合规率 | ≥ 85%、≥ 95% | 事实错、格式错 |
| 格式题 | 「用三点式总结本章」 | 格式合规率(程序化) | ≥ 95% | 格式错 |
| 资料外拒答 | 「明天东京天气?」 | 拒答正确率 | = 100%(硬红线) | 编造、过度回答 |
| 边界歧义题 | 「这章会考吗?」 | 澄清或拒答率 | ≥ 90% | 过度拒答、臆断 |

评测计划里的预算表可参考(30 道题、2 个模型各跑一轮):

```text
预算估算(课程助教,小模型):
  输入:30 题 × 约 80 token            ≈ 2.4k token
  输出:30 答 × 约 200 token            ≈ 6.0k token
  每模型每轮 ≈ 8.4k token,2 模型 = 约 17k token
  按 0.5B 本地推理:几乎为零;若用 API,按单价折算即可
  人工复核:golden 集全量 30 条 × 约 1 分钟 + 讨论 ≈ 1 小时
```

## 6. 边界与排错

- **「先跑起来再设计」**:没有任务定义与阈值的评测,跑出来只是一堆数字——先写 eval spec(哪怕只有一页),再写评测代码。
- **阈值含糊**:「准确率要高」「差不多就行」不可验收;每个指标都要有数值或「0 容忍」的明确表述。
- **任务与交付脱节**:评测题全是课程概念问答,却没人测格式与拒答——上线后被学生问一句资料外问题就翻车;任务清单要覆盖常见、边界、高风险三类输入。
- **指标与任务错配**:开放题用「是否包含某关键词」打分,会奖励废话、惩罚合法改写;先想清楚每个任务用什么层级评分(见第 4 节分层表),细节在 03/04 章展开。
- **预算为零**:评测也要算成本(第 5 节);人工全量复核 500 条不现实,先定「全量程序化 + 抽样人工」的分层方案。
- **计划不纳入版本管理**:eval spec 改阈值、加任务却不留痕,到 02 章冻结 golden 集后就无法追溯「标准何时被放宽过」;计划应与 golden 集一样提交 git,并记录每次修改的日期与理由——这既是工程纪律,也是评测可审计性的起点。

## 7. 总结

| 关键问题 | 一句话 |
|---|---|
| 评测是什么 | 用定义好的任务 + 指标 + 阈值判断模型是否达标,并给失败分类 |
| 与传统 ML 评测的差异 | 输出开放、无单一答案,评的是「期望行为」而非逐字比对 |
| 为什么需要 | 「感觉变好了」不可靠;评测是改进循环里唯一不变的标准与验收依据 |
| 四要素 | 任务定义、指标选择、阈值、失败分类;评测目标可衡量且对应业务目标 |
| 离线 vs 在线 | 离线在发布前用固定题集打分;在线用真实流量验证离线假设是否过期 |
| 分层评测 | 程序化指标(回归) → LLM 裁判(开放题批量) → 人工(全量 golden/抽样复核),精度与成本递增 |
| 动手产物 | eval-spec.md:业务目标、任务清单、指标阈值、失败类别、成本预算 |

**思考题**:如果 eval spec 写好后发现「概念问答阈值 90% 模型达不到」,你会先调低阈值还是先查任务与数据?评测目标和业务目标「学生满意」之间,还可能漏掉哪些不可测量的维度(如回答时效、语气)?

> [!note] 参考答案
> 先查任务与数据,不急着调阈值:达不到 90% 可能是题目太难或存在歧义(改题、补黄金集)、可能是模型确实没学会(回 01.03 补数据重训)、也可能是指标选错(用 ROUGE 评开放题)。调低阈值等于改评测标准,必须同时给出业务理由并留档。业务目标中「时效、语气、是否引发追问」等维度难以用本章指标直接测量,通常留给在线评测(响应时间监控、用户反馈)或人工抽样,这正说明离线评测要主动声明自己的覆盖边界,把测不到的部分交给后续章节的分层手段。
