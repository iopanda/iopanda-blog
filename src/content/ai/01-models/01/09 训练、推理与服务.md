> 前八章回答「模型是什么、为什么能学、长什么样」;本章回答「一个模型从出生到上线服务的完整旅程」。预训练烧掉天文数字的算力、后训练把它调教成听话的助手、推理让它在毫秒间响应、服务化让成千上万用户安全稳定地用上它——这四个环节的资源特征、衡量指标和工程手段完全不同。读完后你会理解:为什么训练看重吞吐、服务看重延迟;KV cache、量化、连续批处理这些词到底在解决什么问题;以及「把模型上线」为什么远不止「把模型跑起来」。

**学习目标**:学完本章,你将能够——

1. 用一张图讲清训练、推理、服务三阶段的分工与资源特征;
2. 区分预训练与后训练,并说清 SFT、偏好优化(RLHF/DPO)、对齐各自解决什么问题;
3. 解释延迟、吞吐、批处理、KV cache、量化五个推理性能核心概念;
4. 列举服务化工程的关键环节:认证限流、日志脱敏、版本回滚、回归评测;
5. 为一个具体场景判断:该直接调用 API、该微调开源模型,还是自己训练。

## 1. 概念:训练、推理与服务是什么

- 回到第一章的公式 `y = f(x; θ)`:**训练**是调整参数 `θ`;**推理**是固定 `θ`,对一条新输入 `x` 计算输出 `y`;**服务**是把「推理」包装成 7×24 小时稳定、安全、可计费、可回滚的在线能力。
- 三者的关系可以类比开车:**训练**=驾校练车(成本高、要专门场地、练完技能内化在身体里);**推理**=每次上路驾驶(一次只服务一段行程,延迟决定体验);**服务**=出租车公司运营(把驾驶组织成千上万人随时叫得到、出了事故能追责的车队)。

| 阶段 | 在做什么 | 时间尺度 | 资源与成本特征 | 主要失败代价 |
|---|---|---|---|---|
| 训练 | 从海量数据中学参数 | 数周~数月(离线) | 数千张 GPU 集群,一次性大额投入 | 训坏了重来,烧钱烧时间 |
| 推理 | 固定参数,对请求前向计算 | 毫秒~秒(在线) | 单卡到数十卡,按用量持续产生 | 出错只丢这一次请求 |
| 服务 | 把推理组织成可运营的系统 | 7×24 持续运行 | GPU + CPU 网关/存储,运营成本 | 出错影响全体用户与口碑 |

## 2. 为什么需要区分三个阶段

### 2.1 训练与推理是两种「相反」的优化目标

- **训练追求吞吐,不在乎延迟**:数据是预先准备好的大批量,跑得慢一点没关系,甚至可以失败后断点重来;它关心的是「单位算力算出多少梯度、模型收敛多快」,所以总是一次喂几千条样本(大 batch)把 GPU 喂饱。
- **推理追求延迟,用户在线等**:每次请求只有一条输入,用户多等 100 毫秒都能感知到;它关心「单条请求多快返回、单位时间能服务多少请求」,因此 GPU 常常喂不饱也要先响应。
- 同一份权重,训练时的前向传播还要跟反向传播、梯度更新绑定,显存占用与计算量通常是纯推理的数倍——这就是为什么训练需要集群,而一个 7B 模型推理有时单张消费级显卡就够用的原因。

### 2.2 服务是「推理 + 工程化」,不是「推理」

- 推理只是一次计算;服务要回答一连串工程问题:谁来用(认证)?一次能用多少(限流与计量)?出问题怎么第一时间发现(日志与监控)?新版本改坏了怎么退回(回滚)?能力有没有悄悄变差(回归评测)?
- 类比:**实验室里做出新药(训练)和建厂量产、通过药监、供给全国药店(服务)是两套完全不同的能力**——很多团队模型训得出来,却死在上线后的可靠性上。

## 3. 它有什么作用

- **看清成本结构**:训练是一次性大额投入;推理成本随调用量持续累积,高频 C 端应用运营两三年,推理总成本常常超过训练。预算与定价都要按这个结构来设计。
- **提供选型决策框架**:绝大多数团队不该从零预训练。正确顺序通常是:先直接调用现成 API 验证效果 → 效果不够再用 RAG 与提示词工程补 → 还不够才考虑微调开源模型 → 只有算力、数据、人才都齐备的极少数情况才自训基座模型。
- **让「快、便宜、稳、安全」变成可度量的工程指标**:延迟、吞吐、每千 token 成本、可用性 SLA、安全审计,这些是模型能否真正成为产品的分水岭。

## 4. 详细介绍

### 4.1 训练:预训练 → 后训练

```
预训练(自监督) → 基座模型(会续写,不会对话) → SFT(学会遵循指令)
→ 偏好优化 RLHF/DPO(学会「好回答」= 对齐)→ 部署服务 → 上线后评测反馈
```

#### 4.1.1 预训练(Pre-training)

- **概念**:用海量无标注文本做自监督学习——上一章讲过,目标就是「预测下一个 token」。模型从网页、书籍、论文、代码里吸收语言规律与世界知识。
- **为什么需要**:语言能力无法靠人工标注获得(谁标得起几万亿 token?);「预测下一个词」天然免费提供标签,规模可以无限放大。
- **作用**:产出**基座模型(base model)**——它只会续写,不会问答,但承载了后续一切能力的底座。公开例证:Meta 训练 Llama 3 70B 用了约 16000 张 H100 跑数十天。
- **详细介绍**:数据规模以万亿 token 计、动辄数千 GPU 数月;损失只对预测的 token 计算交叉熵;工程上依赖数据并行、张量并行等分布式手段(见 01.03)。注意区分:预训练是「学知识」,不等于「学会做人」——它甚至分不清自己在被提问。

#### 4.1.2 后训练(Post-training):SFT、偏好优化与对齐

- **SFT(监督微调)**:**概念**——用人工整理的「指令—理想回答」对继续训练,让模型从「续写模式」切到「指令遵循模式」。**为什么需要**:基座模型知识渊博却「听不懂人话」,你问它北京有什么好吃的,它会继续写「北京有什么好玩的」;SFT 就是教它:看到问题要回答问题。**作用**:把通用能力收束成可用的助手。**详细介绍**:数据量远小于预训练(万~百万条),但质量优先——1000 条高质量数据胜过百万条噪音;实践中常混入少量预训练数据防止「灾难性遗忘」。
- **偏好优化(RLHF/DPO)**:**概念**——SFT 只教「像答案」,不教「什么是更好的答案」;RLHF 收集人类对多个回答的排序,先训练奖励模型,再用 PPO 强化学习优化策略;DPO 则省掉奖励模型,直接从偏好数据优化。**为什么需要**:只做 SFT 的模型仍会一本正经胡说八道、回答有害问题、废话连篇——它不知道人类更喜欢「准确、简洁、安全」的回答。**作用**:实现**对齐(Alignment)**——让模型有用、诚实、无害。InstructGPT 论文的著名结论:1.3B 参数、经 RLHF 的模型在人类评估中胜过 175B 的原始 GPT-3。
- **对比小结**:

| 维度 | 预训练 | SFT | 偏好优化(RLHF/DPO) |
|---|---|---|---|
| 数据 | 万亿 token 无标注文本 | 万~百万条指令对 | 人类偏好排序/对比数据 |
| 教什么 | 语言规律与世界知识 | 遵循指令、会问答 | 回答「更好」而非只是「对」 |
| 成本量级 | 千万~亿美元 | 百万级 | 百万级,RLHF 比 DPO 更高 |
| 产物 | 基座模型 | 指令模型(可对话) | 对齐模型(可安全上线) |

### 4.2 推理:模型如何「用」起来

#### 4.2.1 自回归生成与延迟的两段论

- Decoder-only 模型逐 token 生成:先对整段输入做一次预填充(prefill),得到第一个输出 token;之后每生成一个 token 都依赖全部历史。因此一次请求的总延迟被切成两段,工程上分别度量:

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| TTFT(首 token 延迟) | 从请求发出到吐出第一个字 | 决定用户「第一印象」,对话流式体验的关键 |
| TPOT(每 token 延迟) | 每生成一个字的耗时 | 决定长回答的总等待:总时长 ≈ TTFT + TPOT × 输出字数 |
| 吞吐(Throughput) | 单位时间处理的请求数或 token 数 | 决定单卡能服务多少用户、每 token 成本 |
| 延迟(Latency) | 用户感受到的单次请求总时长 | 直接决定产品体验与 SLA |

#### 4.2.2 Batching:为什么「合起来算」反而更快

- **概念**:GPU 擅长并行矩阵运算,把多条请求拼成一批同时前向计算,单位时间产出的 token 数远高于逐条处理。**为什么需要**:单条请求喂不饱 GPU(类似出租车空驶率高),批处理是推理吞吐的杠杆。**详细介绍**:早期**静态批处理**要等一批请求凑满才开工,早到的请求干等;现代推理引擎用**连续批处理(continuous batching)**——任何一条请求生成完毕就腾出位置插入新请求,不再等整批结束。vLLM 论文报告,这类优化带来 2~4 倍吞吐提升。

#### 4.2.3 KV cache:自回归的「记忆」与显存大头

- **概念**:生成第 N 个 token 时,前 N-1 个 token 的注意力 Key/Value 向量其实早就算过;KV cache 就是把这些向量缓存下来,避免每一步都重算全部历史。**为什么需要**:没有缓存,计算量随序列长度平方级增长,长文本几乎不可用。**代价**:缓存随序列长度线性增长,长上下文场景下它占掉 GPU 显存的大头——显存不够,批处理就装不下,吞吐就上不去。**详细介绍**:vLLM 用 **PagedAttention** 把 KV cache 切成固定大小的块、按需分配——灵感来自操作系统的虚拟内存分页,把内部碎片和浪费降到接近零,还支持多请求共享相同前缀(如同一条 system prompt)的缓存。这是 2023 年后所有主流推理引擎的标配。

#### 4.2.4 量化与其他加速手段

- **概念**:把权重从 FP16(16 位浮点)压缩到 INT8/INT4 等低精度表示。**为什么需要**:显存占用近似减半或减到四分之一,单卡能装下更大模型,同时访存变少、吞吐上升。**代价**:精度损失,需要校准数据并评测验证;GPTQ、AWQ、GGUF 等是常见落地格式。**详细介绍**:工程上通常「先量化再压榨」——先保证延迟达标,再看吞吐与成本。此外还有**投机解码**(小模型起草、大模型一次验证多个 token)、前缀缓存、分布式张量并行等手段,目标都是让推理更快、更省。

### 4.3 服务化工程:把推理变成产品

```
客户端 → API 网关(认证 / 限流 / 计量)→ 推理引擎(GPU,批处理 + KV cache)
              ↓                              ↓
        审计与脱敏日志                评测流水线(回归检测)
              ↓
        模型版本库(权重 + 配置,支持回滚)
```

#### 4.3.1 认证、限流与计量

- **认证**:API Key、OAuth 或网关签名,确认「谁在用」;按团队/项目做密钥隔离与权限分级,防止越权调用。
- **限流**:按 QPS、并发数或 token 配额限速,防止个别用户打爆 GPU、也防恶意刷量;超限返回 429 并排队或降级。类比:食堂窗口再多也要排队,否则所有人都吃不上。
- **计量**:按输入/输出 token 数记录用量,支撑计费、成本分摊与容量规划——token 是推理时代的「流量计」。

#### 4.3.2 日志与数据脱敏

- 服务日志要记录请求与响应用于排障,但输入输出里常含手机号、身份证、密钥等**个人敏感信息(PII)**;落库前必须做脱敏(掩码、哈希、丢弃),满足《个人信息保护法》、GDPR 等合规要求。
- 两个提醒:提示词日志既是宝贵的排障资产,也是泄密风险源(员工可能把内部信息贴进 prompt);日志系统本身要防注入、限访问。

#### 4.3.3 版本管理与回滚

- 模型上线要像软件发布一样管理:每个版本记录「权重文件 + 推理配置 + 评测结果 + 发布时间」,可复现、可追溯。
- 发布策略:先**影子模式**(新老并行、新模型输出只记录不服务)观察差异 → **金丝雀**(小流量试点)→ 全量;一旦指标异常,**蓝绿部署**可在一分钟内切回旧版本。注意 prompt 与模型版本是耦合的,回滚时两者要一起回。

#### 4.3.4 回归评测

- **概念**:维护一套覆盖核心场景的评测集(golden set:标准问答、安全用例、格式遵循、领域考题),每次换模型、改 prompt、调参数后自动全量跑一遍。**为什么需要**:新模型往往「这里变好、那里变差」,没有评测,上线就是开盲盒;评测是防止能力悄悄退化的安全网(与下一章的「能力与局限」直接相关)。**详细介绍**:对比基线模型逐项打分,任何关键指标下滑即拦截发布;评测集本身也要随线上 badcase 持续扩充,避免「评测过拟合」。

## 5. 总结

### 5.1 本章一览

| 主题 | 一句话 |
|---|---|
| 三阶段分工 | 训练调参数、推理用参数、服务把推理组织成可靠产品 |
| 预训练 vs 后训练 | 前者学知识与语言,后者教「听话」与「好回答」(SFT → RLHF/DPO) |
| 推理两大指标 | TTFT 决定第一印象,TPOT × 字数决定总等待;批处理提升吞吐 |
| KV cache | 缓存历史 K/V 避免重复计算,是显存与吞吐的胜负手(PagedAttention) |
| 服务化四件事 | 认证限流、日志脱敏、版本回滚、回归评测 |

### 5.2 思考题

1. 为什么训练可以离线慢慢跑,推理却对延迟如此敏感?两者的 GPU 利用策略有何不同?
2. 只做 SFT、不做偏好优化的模型会有什么典型毛病?偏好优化(RLHF/DPO)补上了什么?
3. 某服务首 token 要 8 秒,后续每个字 20 毫秒,用户抱怨「太慢」。你会先优化哪个指标,为什么?
4. 上线新模型前,为什么要先跑回归评测而不是只看新模型的演示效果?
5. 哪些请求数据不能直接写进日志?脱敏通常怎么做?

> [!note] 参考答案
> 1. 训练是离线批量任务,可重试可断点,追求用大 batch 喂饱 GPU 提高算力利用率;推理是用户在线等待,必须先响应,常牺牲吞吐保延迟(或用连续批处理在两者间平衡)。
> 2. 只做 SFT 的模型会一本正经胡说、回答有害问题、输出冗长废话——它不知道什么是「更好」;偏好优化用人类排序教它朝有用、诚实、无害的方向对齐。
> 3. 先优化 TTFT(首 token 延迟):8 秒的 TTFT 会让用户觉得「卡死」,把它降到 1 秒内,配合流式输出,体验立即改善;TPOT 影响的是长回答的总时长。
> 4. 新模型往往有得有失,演示样本是挑选过的;回归评测用统一基准对比新旧模型,任何关键项下滑都会暴露,防止「换了个更强的模型,线上反而变差」。
> 5. 含手机号、身份证、密钥等 PII 的输入输出不能原文落库;先掩码/哈希/丢弃敏感字段再写日志,并做访问控制与审计。
