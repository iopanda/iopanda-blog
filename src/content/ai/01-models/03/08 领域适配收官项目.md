> 本章是 01.03 的收官:前七章分别产出基线(01)、数据集(02)、训练栈(03)、SFT(04)、LoRA(05)、QLoRA(06)与 DPO(07)的 adapter——但这些工件本身不等于「可以交付的领域模型」。本章把它们整理成一项可审查的交付物:一张训练前冻结的 golden set、一份覆盖全部题目的逐条评测报告、一页模型卡,并给出「是否可用」的结论。

**学习目标**:学完本章,你将能够——

1. 说出领域适配的验收标准,区分「训练完成」与「可以交付」;
2. 解释为什么 golden set 必须在训练开始前冻结并锁死;
3. 构造 20 条四类别的 golden set,让 base 与各 adapter 在同一条件下评测;
4. 按 0/1 规则逐条人工评分,不挑样本地给出汇总表;
5. 写出一页 `model-card.md`,说明用途边界、证据与回滚方式;
6. 基于证据给出「是否推荐发布」的结论。

## 1. 概念:领域适配的验收标准

- **领域适配(Domain Adaptation)** 不是「让模型变强」,而是「让模型在某个领域的任务上,相对于明确基线,表现出可验证的改善」。第 1 章已强调:没有改前成绩就无法证明训练有效——收官章把这条纪律执行到底。
- 前七章各自证明「某一步能改善什么」,但都是局部证据:数据设计得好不好、SFT 有没有压低 valid loss、DPO 有没有改变选择偏好。收官章把问题换成整体验收:把这些 adapter 放在**从未参与任何训练**(train、valid、preferences 都没见过)的领域任务上,与 base 逐条对比。
- 一套可执行的验收标准至少回答四问:
  - **改善可测吗**:在 golden set 上,adapter 的依据正确、格式、拒答三项是否比 base 更好;
  - **证据完整吗**:全部输入输出可复现、可查看,失败例没有被挑掉;
  - **代价已知吗**:显存、训练时长、数据许可、回滚成本都有记录;
  - **边界说清了吗**:模型能做什么、不能做什么,使用者从模型卡上一眼可知。
- 什么**不算**验收通过:「模型说话更像专家」、训练题上的高分、精心挑选的演示——这些都可能只是背住了练习册(记忆),而不是在未知任务上泛化。

## 2. 概念:golden set 为什么必须在训练前冻结

- 把数据分成三类理解:train 是「练习册」,模型反复看过;valid 是「模拟考」,用于早停和选 checkpoint——它已经参与过你的决策;golden set 是「期末题」,只用于最后一次验收。
- 为什么必须**先冻结再训练**?因为任何评测题一旦进入「看分数 → 改数据/改参数 → 再看分数」的循环,它就不再是评测,而变成了训练信号的一部分:你会不自觉地记住哪些题错了、把数据补向那个方向。这叫对评测集的过拟合,分数会系统性虚高。
- 先冻结还有一层**可审计性**意义:golden.jsonl 的创建时间早于任何训练 run,才能向第三方证明「这些题确实没被看过」。训练结束后再补题,谁也无法保证题目没有在开发讨论中被泄漏。
- 因此 golden set 的纪律是:一次写定、与训练数据隔离、文件里只放 `id`、`question`、`expected_behavior`,**不写训练答案**——评分时只看期望行为,不给模型看标准答案。

## 3. 动手:冻结 golden set

创建 `finetune/eval/golden.jsonl`,写 20 条从未进入 train、valid、preferences 的问题,至少四类:

| 类别 | 数量 | 用意 |
|---|---|---|
| 常见领域问答 | 10 | 覆盖课程资料内的典型问题 |
| 格式要求 | 4 | 验证是否遵守三点式等输出约定 |
| 资料外问题 | 3 | 应明确拒答,不编造 |
| 边界或歧义问题 | 3 | 观察模型在不清晰输入下的表现 |

每行包含 `id`、`question`、`expected_behavior`;**不要**在此文件写训练答案:

```json
{"id":"unknown-01","question":"明天东京天气?","expected_behavior":"明确说明没有实时资料,不编造"}
```

写完后提交文件并记录时间戳,此后不再修改——一旦发现题目与开发过程有交集,视为污染(见文末思考题)。

## 4. 动手:同一条件下跑基线与 adapter

评测的唯一变量必须是模型本身(呼应第 1 章基线纪律):所有模型共用同一 system prompt、`do_sample=False`、`max_new_tokens=160`。adapter 依赖基座(第 5 章),若 adapter 尚未合并进基座,先执行 `AutoPeftModelForCausalLM.from_pretrained("runs/<chosen>/adapter")` 挂载,再传入 pipeline。创建 `finetune/src/eval_golden.py`:

```python
import json
from transformers import pipeline

MODEL = "Qwen/Qwen2.5-0.5B-Instruct"  # base;SFT/LoRA、DPO 换成各自 adapter 路径
SYS = "你是课程助教。没有依据时说不知道。"
pipe = pipeline("text-generation", model=MODEL, device_map="auto")
with open("eval/golden.jsonl", encoding="utf-8") as f:
    items = [json.loads(line) for line in f]
rows = []
for it in items:
    msg = [{"role": "system", "content": SYS},
           {"role": "user", "content": it["question"]}]
    ans = pipe(msg, max_new_tokens=160, do_sample=False)[0]["generated_text"][-1]["content"]
    rows.append({"id": it["id"], "model": MODEL,
                 "expected_behavior": it["expected_behavior"], "output": ans})
with open("reports/golden-results.jsonl", "a", encoding="utf-8") as f:
    for r in rows:
        f.write(json.dumps(r, ensure_ascii=False) + "\n")
```

分别加载 base、最佳 SFT/LoRA(或 QLoRA)和 DPO adapter 各运行一次,把**全部**输出保存到 `finetune/reports/golden-results.jsonl`(每行带 `model` 字段区分来源)。

## 5. 人工评分:不挑样本

为每条结果按 0/1 打分,四项标准同时满足才算 1:

- 事实有依据且与课程资料一致;
- 遵守输出格式约定;
- 资料外问题正确拒答(编造即 0);
- 无明显有害或私密信息。

两人可独立评分,不一致处讨论或取保守值;只有一人评分时,也要在报告中写明评分规则与不确定项。**评分必须覆盖全部 20 条**,禁止只挑「看起来能得分」的输出。汇总表:

| 模型 | 依据正确 | 格式 | 拒答 | 已知失败 | 是否推荐 |
|---|---:|---:|---:|---|---|
| base | /20 | /20 | /3 | 原样链接 | 否/有条件 |
| adapter | /20 | /20 | /3 | 原样链接 | 否/有条件 |

「已知失败」列贴出该模型输出文件的链接,失败例原样保留、不省略——报告的诚实度决定它能否被第三方采信。**判定规则**:若 adapter 只在「与训练题相似」的问题上变好,却在未知问题上更爱编造,不能宣布成功;应回到数据设计(第 2 章)补充拒答样本,或改用 RAG 提供事实依据。

## 6. 动手:提交目录与模型卡

最终目录至少包含(数据卡与许可记录见第 2 章,超参数在各 run 的 config):

```text
finetune/
  data/                 # 数据卡与许可记录
  configs/              # 实际超参数
  runs/<chosen>/adapter/ # adapter_config 与权重
  eval/golden.jsonl
  reports/baseline.md
  reports/golden-results.jsonl
  reports/model-card.md
```

## 7. 概念:模型卡的意义

- 模型卡(Model Card)**不是宣传页**,而是交付物的「使用说明书」:它回答使用者最关心的四件事——这个模型**做什么**(训练目的与建议用途)、**不能做什么**(边界与禁止用途)、**证据是什么**(golden 指标与失败例)、**出问题怎么办**(回滚方式)。
- 为什么收官必须有它?模型一旦发布,使用者无法从对话里看出它被微调过什么、在哪些题上会错;模型卡把「训练者已知的风险」转交给「使用者合理的预期」,是负责任的发布边界(呼应 NIST AI RMF 的透明与问责)。
- 在 `reports/model-card.md` 写:模型与 adapter ID、训练目的、允许/禁止用途、数据来源与许可、硬件和超参数、golden 指标、失败例、偏见/隐私/幻觉风险、复现命令、回滚方式(删除 adapter 并回到 base)。
- 发布纪律:切勿上传训练数据、访问令牌或含个人信息的输出——adapter 权重可以分享,原始数据与密钥不行。

## 8. 动手活动:结业验收

> [!example] 动手活动:结业验收
>
> **目标**:提交上述目录和一页 `model-card.md`,给出可审查的「是否可用」结论。
>
> **步骤**:
> 1. 冻结 golden set 并记录时间戳;
> 2. 用同一条件运行基线与选定 adapter,保存全部输出;
> 3. 逐条 0/1 评分,填写汇总表与已知失败列;
> 4. 在模型卡中写明「可用于什么、不可用于什么、下一步做什么」。
>
> **完成标准**:第三方拿到仓库后,能复现命令、查看全部输出、找到数据来源,并根据证据同意或否决发布——而不是只听口头说明。

## 9. 总结

| 关键问题 | 一句话 |
|---|---|
| 验收标准 | 相对冻结基线,在未参与训练的 golden 任务上有可检查改善,且代价与风险已知 |
| golden set 为何先冻结 | 参与过「看分→改数据/参数」循环的题会泄题,分数虚高且不可审计 |
| 如何跑分 | 全模型同一 system prompt 与 `do_sample=False`,唯一变量是模型本身 |
| 如何评分 | 20 条全评、0/1 规则、失败例原样保留,两人独立或写明单人规则 |
| 模型卡的意义 | 说明书而非宣传页:做什么、不能做什么、证据是什么、如何回滚 |
| 何时不能宣布成功 | adapter 只提升相似题、未知题更爱编造——回数据设计或选 RAG |

**思考题**:golden set 上「adapter 全部答对」能证明领域适配成功吗?如果训练结束后发现 golden 里有 2 条题曾在开发讨论中被引用,你该怎么办?

> [!note] 参考答案
> 不能:全对可能意味着题目分布与训练太接近,甚至已发生泄漏;验收还要看拒答类、边界类表现以及与基线的差异。发现 golden 与开发过程有过交集,应视为污染:删除或替换这 2 条并重新冻结、重跑全部评测,而不是「反正答对了就留下」——golden 的纯洁性一旦存疑,整份验收就失去公信力。
