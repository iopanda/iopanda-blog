> SFT(第 4 章)已经教会模型「答案应该长什么样」,但现实里常有两个回答都能答、一个却更可靠或更守边界的情形。本章引入偏好优化:制作可审计的偏好对,并在小样本上运行最小 DPO,让模型在「同样能答」时学会倾向更好的那一个。全程要守住一条边界——偏好优化不会让模型自动「安全」或「真实」,也不能替代安全机制。

**学习目标**:学完本章,你将能够——

1. 说出 SFT 与偏好优化的差别,解释为什么「只有一个标准答案」表达不了相对偏好;
2. 写同一 prompt 下的 `chosen`/`rejected` 偏好对,并为每对附上人工审核理由;
3. 解释为什么 prompt 必须相同、`beta` 在控制什么;
4. 在 LoRA 上运行最小 DPO,并从日志读出偏好指标;
5. 说明 DPO 的约束原理,以及它为什么不能替代安全机制。

## 1. 概念:偏好优化与 SFT 差在哪

SFT 的标准答案只表达「一个答案应该长什么样」,却难以表达「两个都能回答、但一个更可靠或更守边界」的相对取舍。偏好优化把同一问题的优选答案(`chosen`)和拒选答案(`rejected`)放在一起训练,使模型倾向前者。本章解决「让模型学会选择更合适的回答」这一问题;它不等于价值观真理,也不能替代安全机制。

### 1.1 SFT vs 偏好优化

| 对比项 | SFT(第 4 章) | 偏好优化(本章 DPO) |
|---|---|---|
| 数据形态 | 一个问题 → 一个标准答案 | 同一 prompt → `chosen`/`rejected` 一对 |
| 学习信号 | 增加标准答案的续写概率(模仿示例) | 拉大 `chosen` 相对 `rejected` 的偏好差距(对比) |
| 能表达 | 「答案应该长什么样」 | 「两个都能答,但 A 更可靠、更守边界」 |
| 局限 | 无法表达相对取舍;标准答案未必最优 | 只反映偏好数据的取舍,不新增知识,仍会幻觉 |

一句话概括:SFT 教模型「这样答」,偏好优化教模型「同样能答时,优先这样答」——前者是模仿,后者是对比。

### 1.2 chosen / rejected / beta 是什么

- **`chosen`(优选)**:同一问题下人工认为更符合要求的回答;
- **`rejected`(拒选)**:同一问题下被放弃的回答——它不必是错误答案,常常只是「次优」;
- **人工理由**:每对都要写出「为什么 chosen 更好」,这是结果可解释的前提,也是事后审核的依据;
- **`beta`**:DPO 的超参数,控制偏好变化的强弱。它同时约束「模型偏离未更新参考行为的程度」——`beta` 越大,模型越坚决贴合偏好,也越容易走偏;`beta` 越小,更新越温和。

### 1.3 为什么 prompt 必须相同

偏好学习本质是一场对照实验:唯一允许变化的变量应当是「回答本身」,所以 `chosen` 与 `rejected` 必须共享同一个 `prompt`。若 prompt 不同,模型无法分辨输出差异来自回答质量,还是来自题目难度、话题或措辞——它可能只是学到「某种问法配某种答法」,而不是「这个回答更好」。同理,两个回答只应在质量上拉开差距:不能把「更长」误当「更好」,更长的回答如果夹带编造,反而更差。

### 1.4 DPO 的约束原理:为什么它不需要奖励模型

经典的 RLHF 需要先训练一个奖励模型,再用 PPO 让策略去最大化奖励——两阶段、重且难调。DPO(Direct Preference Optimization,引用见文末)发现:偏好数据本身足以定义隐式奖励,于是把对齐直接写成二分类式 loss,省掉奖励模型与 PPO 两套组件。

但 DPO 并非无约束地「往偏好方向猛推」,它有两个内建约束:

- **参考锚点**:loss 中以训练前的模型为参考策略(reference policy),用 `log πθ/πref` 的比值衡量每一步偏离——模型可以改变,但不能为了迎合训练偏好而把预训练学到的能力冲掉太多;
- **KL 强度 `beta`**:`beta` 就是这条约束的松紧旋钮,控制「偏好收益」与「偏离参考代价」之间的权衡。

本章沿用 LoRA 只更新 adapter、基座冻结(呼应 05/06 章),这从工程上又加了一层限制,让偏离天然更小——小样本偏好训练尤其需要这种保守。

### 1.5 它不能替代安全机制

偏好优化只会反映「偏好数据与训练设置」里的取舍,有三件它做不到的事:

- 数据里有偏见或仇恨,模型会学着放大,而不是学会拒绝——`rejected` 的选择本身就是一种价值观输入;
- 它不改变模型的底层知识,也不保证事实正确,幻觉不会因此消失;
- 政策、权限控制、人类审核与安全评测是另一套机制,一个都不能省。

数据量很小时尤其容易过拟合「写法」:模型学会了更礼貌、更长的措辞,可观察行为却没有真正变可靠——这正是本章动手活动要用留出问题验证的原因。

## 2. 动手:制作偏好对

SFT 告诉模型「应该输出什么」;DPO 告诉模型「对于相同 prompt,A 比 B 更好」。创建 `finetune/data/preferences.jsonl`,每一行必须有同一问题、一个优选和一个拒选,不能把「更长」误当「更好」:

```json
{"prompt":[{"role":"system","content":"你是课程助教。没有依据时说不知道。"},{"role":"user","content":"主键允许重复吗？"}],"chosen":[{"role":"assistant","content":"不允许。主键用于唯一标识每一行，因此值必须唯一且不能为 NULL。"}],"rejected":[{"role":"assistant","content":"主键一般允许重复，只要查询速度快即可。"}]}
```

写至少 15 对,覆盖三类:有依据的正确回答、拒绝编造、遵守简洁格式。每对由人工写出「为什么 chosen 更好」,并确认 rejected 不含仇恨、隐私、恶意指令等不应反复训练的内容。逐行自检:

| 检查项 | 要求 |
|---|---|
| prompt 完全一致 | `chosen`/`rejected` 必须共享同一问题,不允许「换题」 |
| rejected 可接受 | 只是次优,不含仇恨、隐私、恶意指令等不该训练的内容 |
| 理由可解释 | 能写出「为什么 chosen 更好」,而不是「因为更长/更礼貌」 |
| 覆盖三类 | 有依据正确 / 拒绝编造 / 简洁格式 都要有样本 |

## 3. 动手:运行最小 DPO

先在 `check_data.py` 增加 JSON 加载检查:每行 `prompt`/`chosen`/`rejected` 三字段齐全,且 `chosen` 与 `rejected` 的 prompt 部分逐字一致。再创建 `finetune/src/train_dpo.py`:

```python
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer, TrainingArguments
from trl import DPOTrainer

model_id = "Qwen/Qwen2.5-0.5B-Instruct"
data = load_dataset("json", data_files="finetune/data/preferences.jsonl", split="train")
tokenizer = AutoTokenizer.from_pretrained(model_id); tokenizer.pad_token = tokenizer.eos_token
model = AutoModelForCausalLM.from_pretrained(model_id)
args = TrainingArguments(output_dir="finetune/runs/dpo-v1", per_device_train_batch_size=1,
    gradient_accumulation_steps=8, learning_rate=5e-6, num_train_epochs=1,
    logging_steps=1, report_to="none", seed=42)
peft = LoraConfig(r=8, lora_alpha=16, target_modules=["q_proj", "v_proj"], task_type="CAUSAL_LM")
trainer = DPOTrainer(model=model, args=args, train_dataset=data, processing_class=tokenizer,
    peft_config=peft, beta=0.1)
trainer.train(); trainer.save_model("finetune/runs/dpo-v1/adapter")
```

先运行 3 step,查看日志是否有 `rewards/chosen`、`rewards/rejected` 或当前版本等价指标;版本 API 不匹配时,按 TRL 官方版本文档调整,不能混抄旧教程参数。

### 3.1 排错速查

| 现象 | 处理 | 原因 |
|---|---|---|
| 日志没有 `rewards/chosen` 类指标 | 对照 TRL 当前版本文档找等价字段 | 不同 TRL 版本指标命名不同 |
| 报错提示字段/API 不存在 | 按官方版本文档调整,勿抄旧教程 | 版本不匹配 |
| 训练很快结束且指标无变化 | 检查 `preferences.jsonl` 是否被正确加载、行数是否足够 | 数据没进训练或样本过少 |
| 回答变得更「油滑」而非更可靠 | 用留出问题复查,考虑降低 `beta` | 小数据过拟合偏好写法 |

## 5. 总结

| 关键问题 | 一句话 |
|---|---|
| SFT 与偏好优化的差别 | SFT 教「这样答」(模仿),DPO 教「同样能答时优先这样答」(对比) |
| chosen / rejected | 同一 prompt 下的优选与拒选,每对必须附人工理由 |
| 为什么 prompt 必须相同 | 偏好是对照实验,唯一变量应是回答质量而非题目 |
| beta 在控制什么 | 偏好变化的强弱,同时约束对参考模型的偏离程度 |
| DPO 的约束原理 | 以训练前模型为锚点、`beta` 作 KL 约束强度,省掉奖励模型与 PPO |
| 它不能替代什么 | 政策、权限、人类审核、安全评测;也不消除幻觉 |

**思考题**:为什么说「rejected 里没有仇恨内容」只是底线,而不是「数据已经安全」?小样本 DPO 训练后回答变得更礼貌,能说明对齐成功吗?

> [!note] 参考答案
> rejected 无仇恨/隐私/恶意指令只是避免把不该学的内容放大;偏好数据仍可能含偏见、片面取舍,所以还需要政策与人工审核,不能只靠数据干净。回答变礼貌可能只是过拟合了偏好数据的「写法」(更长、更客气),并不代表行为更可靠或更守边界;必须用未参与训练的留出问题逐条对比 SFT 与 DPO,确认某个可观察行为真的改善。
