# 数据治理与隐私

> 01.06 的评测证明了课程助教「能力达标」:概念问答准确率过线、裁判均分 4.2/5,安全评测(06 章)把「会不会出事」翻成了攻击样本上的双比率,评测报告(07 章)给出了「能上线」的结论。但「能用的系统」不等于「可以安全交付的系统」:助教手里握着微调数据、评测黄金集、学生提问与访问日志,这些数据里可能藏着姓名、学号、邮箱等个人信息——法律(GDPR/PIPL 的思路)在管,工程上更要有人管。本章是 01.07 治理收尾单元的第一课:给 01.04 的 API 服务与 01.06 评测过的课程助教建立数据治理与隐私规则——说清每条数据从哪里来、往哪里去、存多久、谁能碰、泄露了怎么办,动手产出治理文档 data-governance.md 与可运行的日志脱敏脚本,把上一单元「测出问题」推进到「管住风险」。

**学习目标**:学完本章,你将能够——

1. 说出数据治理与隐私的定义,区分二者管的问题(规则体系 vs 个人信息边界);
2. 解释为什么「评测通过」不等于「可以上线」,训练数据、用户输入、日志都可能埋着 PII;
3. 说出 GDPR 与 PIPL 的核心思路(目的限制、最小必要、保留期限、删除权、泄露通知与处罚),并对照到自己的工程;
4. 列出治理规则六要素,为任意一条数据流写出来源、用途、保留期、访问范围、删除流程;
5. 识别数据泄露、授权风险、重新识别(de-anonymization)三类风险及典型场景;
6. 为课程助教服务写出 data-governance.md,并用正则实现日志 PII 脱敏。

## 1. 概念:数据治理是规则体系,隐私是个人信息的边界

- **数据治理(data governance)** = 对数据的**来源、用途、保留、访问、删除**建立一套规则与责任人,回答「这是谁的数据、允许用来干什么、存多久、谁能碰、怎么删」。它不针对某一类数据,而是把系统里所有数据流都管起来。
- **隐私(privacy)** 管的是其中一类特殊数据——**个人信息(PII,Personally Identifiable Information)**:能直接或间接识别到某个人的信息,如姓名、学号、手机号、邮箱、IP 地址、人脸截图。隐私问题 = 个人信息「能不能收集、能收集多少、能用来干什么」的边界。
- 二者关系:**数据治理是框架,隐私是框架里约束最严的一条**。个人信息一旦泄露,伤害落到具体的人身上,还会触发法律后果;而治理文档里其他数据流(如纯课程文本)则只需防泄密、不必上隐私流程。
- 术语对照:PIPL 称之为「个人信息」,GDPR 称之为「个人数据(personal data)」,安全界常用「PII」,工程文档里指同一类东西。**匿名化**(彻底无法关联回个人)后的信息不再是个人信息,但**假名化**(把学号换成随机 ID)仍受规制——别把假名化当匿名化用。
- 本课程不替代法务意见:GDPR/PIPL 只取「思路」,落进代码与文档的是工程实践;真正对外服务前请咨询专业法务。

## 2. 为什么需要:评测管「能不能用」,治理管「能不能交付」

- 评测回答「能力是否达标」;但一个达标模型装进 API 后每天接收真实提问、产生日志与缓存,数据开始流动。**能力合格 ≠ 数据合规**:01.06/06 测出过「泄露考试范围」类回答,那只是测试样本;真实服务里同样的漏洞吐出的可能是学生的真实个人信息。
- 个人信息藏在每一层:训练数据里人工编写的示例可能带真实姓名;用户输入里学生一句「帮我查我上次的成绩」就带上学号;日志里每一条请求都记着 IP 与时间;甚至模型权重里也记着训练语料(见第 3 节)。
- 法律底线(思路):GDPR 要求处理个人数据有合法基础、遵循目的限制与数据最小化,发生泄露须 72 小时内通知监管机构(Art. 33),情节严重的最高罚 2000 万欧元或全球年营业额 4%(取高,Art. 83);PIPL 要求处理遵循合法、正当、必要与最小范围,处理敏感个人信息(生物识别、医疗健康、金融账户、行踪轨迹等)须特定目的 + 充分必要 + 单独同意,情节严重的最高罚 5000 万元或上一年度营业额 5%(取高)。违反这些不只是罚款风险,更是用户信任与产品存续问题。
- 呼应前文:01.02/02 管「数据从哪来、许可允许怎么用」,本章管「数据到了我们手里怎么保护与处置」;01.03/08 的 model card 需要「训练数据与隐私处理」一栏,本章的治理文档正是它的素材来源——治理先行,文档(02 章)才有内容可写。

## 3. 治理的对象:四条数据流 + 一种「会自己泄露」的特例

课程助教系统里,数据主要沿四条管道流动,每条都要单独登记:

| 数据流 | 典型内容 | PII 风险 | 来源章节 |
|---|---|---|---|
| 训练/微调数据 | SFT 指令集、偏好对 | 中:示例可能含姓名等 | 01.03/02、/07 |
| 评测数据与黄金集 | 人工参考答案、攻击样本 | 低~中:含人工编写的边界题 | 01.06/02、/06 |
| 用户输入与检索内容 | 学生提问、RAG 命中的课件截图 | 高:学号、成绩、作业截图 | 01.04 API、01.05 多模态 |
| 日志与遥测 | IP、时间戳、请求与响应内容 | 中~高 | 01.04 部署 |

- 还有一条特殊管道:**模型记忆**。模型训练时可能把高频出现的个人信息(邮箱、电话、一段私人文本)直接记进权重,生成时原样吐出来——研究者曾在 GPT-2 上成功「提取」出训练语料原文。它不在服务器日志里,删日志删不掉,**只能靠源头治理**(见第 6 节)。
- 治理清单必须覆盖四条管道 + 模型记忆。漏掉任何一条,风险就从漏掉的地方流出去——很多泄露事故的根因不是「没设防」,而是「没登记这条数据流」。

## 4. 规则六要素:一份 data-governance.md 的骨架

给每条数据流登记六个要素,是治理文档的最小完备骨架:

| 要素 | 要回答的问题 | 课程助教上的示例 |
|---|---|---|
| 来源登记 | 数据从哪来、由谁提供、依据是什么 | 「SFT 集:01.03 人工整理,基于课程资料与授权」 |
| 用途限定 | 只允许用来做什么 | 「仅用于微调与评测,禁止用于其他产品」 |
| 保留期 | 存多久、何时自动删除 | 「用户输入 30 天;访问日志 90 天滚动轮转」 |
| 访问控制 | 谁能读、谁能写、默认拒绝 | 「训练集:训练组 3 人;生产日志:仅运维组」 |
| 删除流程 | 谁发起、走什么流程、多久完成 | 「用户请求删除 → 数据负责人 72 小时内处理并回执」 |
| 泄露响应 | 发现泄露先做什么、通知谁 | 「先止血(吊销密钥/下线),24 小时内内部上报」 |

- 六要素的次序就是写文档的次序:先登记来源,再写用途与期限,最后补访问、删除与响应——后面的规则都依附于「这条数据是什么、用来干什么」。
- 访问控制要落实「默认拒绝、按需授权、操作留痕」:给 CI 账号开生产库权限、让实习生直读含 PII 的训练集,是比外部攻击更常见的泄露路径。
- 保留期不是摆设:训练集可以随项目长期保存(它服务于可复现的模型迭代),但用户输入与日志必须有明确时限与自动清理任务——「永久保留用户对话」在 GDPR/PIPL 思路上都站不住。

## 5. 风险识别:三类典型风险

- **数据泄露(breach)**:不该出去的数据出去了——01.06/06 发现的「泄露考试范围」类回答、日志被拖库、API 密钥泄漏后被爬取对话历史。缓解:最小化采集、传输与存储加密、日志先脱敏再入库、备好泄露响应预案。
- **授权风险(authorization)**:能碰到数据的人/程序比需要的多——CI 账号直连生产库、实习生可读含 PII 的训练集、模型工具权限过大(03 章还会展开)。缓解:最小权限 + 定期复核 + 敏感操作进审计日志。
- **重新识别(de-anonymization)**:自以为匿名的数据被交叉比对还原出个人——Netflix 公开「匿名」评分数据被 IMDb 交叉比对认出具体用户;仅凭「邮编 + 生日 + 性别」也能高概率锁定个人。缓解:对「匿名」保持怀疑,该按 PII 处理就按 PII 处理。

## 6. 动手活动:写 data-governance.md 并给日志脱敏

> [!example] 动手活动:为课程助教服务建立治理文档与脱敏脚本
>
> **目标**:在 01.04 的 API 项目(或 01.03 的 finetune 项目)里新建 `data-governance.md` 与 `redact.py`,把六要素与三类风险落成可执行产物。
>
> **步骤**:
> 1. **列数据流**:按第 3 节表格列出你系统里真实的四条管道(训练集、评测集、用户输入、日志);
> 2. **逐项标风险**:每条数据流标 PII 风险(高/中/低)、典型 PII 字段、保留期、默认访问范围;
> 3. **补删除与响应**:为「学生要求删除自己的提问记录」写一条删除流程;为「发现日志泄露」写三步响应(止血 → 排查 → 上报);
> 4. **写脱敏脚本**:用下方骨架实现 `redact(text)`,坚持「先脱敏、再入库」;
> 5. **自测**:把一条真实格式的假日志丢进去,确认邮箱、手机号、身份证、IP 都被遮住而普通文本原样保留。

日志脱敏脚本骨架(手机号保留前 3 后 4,身份证保留前 6 后 4,可直接运行):

```python
import re

RULES = [
    (re.compile(r"[\w.+-]+@[\w-]+\.[\w.]+"), "<EMAIL>"),          # 邮箱
    (re.compile(r"(1[3-9]\d)\d{4}(\d{4})"), r"\1****\2"),          # 手机号
    (re.compile(r"(\d{6})\d{8}(\d{3}[\dXx])"), r"\1********\2"),   # 身份证号
    (re.compile(r"(?:\d{1,3}\.){3}\d{1,3}"), "<IP>"),              # IP 地址
]

def redact(text: str) -> str:
    for pattern, repl in RULES:
        text = pattern.sub(repl, text)
    return text

if __name__ == "__main__":
    log = "2026-09-02 10:00 张三 13812348000 申请删除记录 ID:110101199001011234"
    print(redact(log))
    # 输出:2026-09-02 10:00 张三 138****8000 申请删除记录 ID:110101********1234
```

**完成标准**:第三方读 `data-governance.md`,能说出每条数据「存多久、谁能碰、怎么删」;把含 PII 的日志喂给 `redact.py`,输出里找不到完整的手机号与身份证号。把两份文件提交 git,治理规则从此可评审、可追溯。

## 7. 边界与排错

- **只写不执行**:治理文档写二十页,但没有保留期定时任务、没人复核权限,等于没有治理;每条规则都要落进一个脚本、一个定时任务或一个具名负责人。
- **脱敏漏字段**:正则只覆盖你想到的格式——昵称、住址、图片里的车牌与面孔都遮不住;对开放文本加关键词黑名单与敏感词扫描,并定期人工抽样复核脱敏效果。
- **把「脱敏」当「匿名化」**:日志脱敏只是降低风险,**不是**匿名化;真要公开数据集,必须做去标识化评估(第 5 节的重识别风险),别拿 `<EMAIL>` 替换当免责牌。
- **保留期写「永久」**:「永久保留用户对话」既不合规思路又放大泄露杀伤力;训练集之外的每条数据都要能说出删除时间点。
- **只防外部不防内部**:相当比例的泄露来自内部误操作与权限过大;访问控制不是可选项,至少做到默认拒绝、按需授权、操作留痕,并定期(如每季度)复核一次授权清单。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 数据治理是什么 | 对数据来源、用途、保留、访问、删除的规则体系与责任人 |
| 隐私是什么 | 个人信息(PII)收集与处理的边界,是治理中约束最严的部分 |
| 为什么需要 | 能力达标 ≠ 可交付;训练数据、用户输入、日志都可能含 PII |
| 管哪些对象 | 四条数据流(训练、评测、用户输入、日志)+ 会「自己泄露」的模型记忆 |
| 六要素 | 来源登记、用途限定、保留期、访问控制、删除流程、泄露响应 |
| 三类风险 | 数据泄露、授权风险、重新识别(de-anonymization) |
| 动手产物 | data-governance.md + redact.py(邮箱/手机号/身份证/IP 正则脱敏) |

**思考题**:某学生要求删除他三个月前的提问记录,而这些对话已被拿去构造新的 SFT 数据并训练进了模型——「删除」能做到什么程度?请分别说出「日志层、数据集层、模型权重层」三种情况下删除的可行策略,并说明哪一层最该在源头避免。

> [!note] 参考答案
> 「删除」的粒度取决于数据在哪一层:访问日志与对话库可以直接删(设计时就应让删除流程可执行、可回执);已被选入 SFT 数据集的对话,应从数据集中剔除并记录剔除批次(01.03 的数据管线要支持按单条记录追溯);一旦进了模型权重,任何数据库删除都无法抹掉——只能靠源头缓解:训练前过滤 PII、去重以降低记忆概率,必要时用差分隐私训练,并在模型卡(02 章)里如实声明「无法保证删除已记忆内容」。由此得到治理的黄金法则:**越早越容易删,能不入库就不入库**——这正是「数据最小化」在工程上的真正含义,也是本章各条规则共同的底层逻辑。
