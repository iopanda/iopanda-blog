# 运营、扩展性与工程边界

> Kestra README 说它「designed to handle millions of workflows, with high availability and fault tolerance」。[15] 这不是一句空洞的营销话——它背后是一套明确的控制面/数据面分层架构，角色之间只通过队列通信，任何角色都可以独立扩展。[36] 这一篇讲清楚这套架构，以及 Kestra 相对 Temporal/Airflow/Prefect/Dagster 的工程边界在哪。

**学习目标**：学完本章，你将能够——
1. 理解控制面（control plane）与数据面（data plane）的分工；
2. 说出 Executor、Scheduler、Worker Controller、Worker、Webserver、Indexer 六个角色各自的职责；
3. 理解“角色之间只通过队列通信”为什么是可扩展性和容错性的关键；
4. 理解它的工程边界：什么场景下 Kestra 不是最佳答案；
5. 为系统写一张 kestra-ops-boundary card。

## 1. 控制面与数据面：谁能碰用户的基础设施

架构文档把六个角色分成两层：[36]
- **控制面**（Executor、Worker Controller、Scheduler、Webserver、Indexer）：「never execute user code and have no access to user infrastructure」；
- **数据面**（Worker）：唯一有权限接触用户基础设施和内部存储的角色。

这个分层意味着：控制面出问题不会直接威胁到用户的外部系统，而真正“碰用户数据/系统”的路径被收窄到 Worker 这一个角色上，便于隔离和审计。

## 2. 六个角色各自在做什么

| 角色 | 职责 |
|---|---|
| Executor | 驱动执行状态机、决定下一步、派发任务，但「runs no user code」 |
| Scheduler | 评估大多数 trigger 条件并把执行推入队列（flow trigger 由 Executor 处理） |
| Worker Controller | 「the sole communication point for workers」，通过 gRPC 推送任务、接收结果 |
| Worker | 真正执行任务和 polling trigger，通过 gRPC 而不是直连队列 |
| Webserver | 承载 REST API 和 UI |
| Indexer | 把队列数据（flow、执行记录、日志、指标、审计日志）落地到存储，「Required in all deployments」 |

standalone 模式下六个角色作为一个进程内的多个线程运行；分布式模式下每个角色可以独立扩展。[36]

## 3. 队列通信：解耦带来的可扩展性和容错性

所有角色之间只通过队列通信——「no role calls another directly」。[36] 具体机制：
- Worker 不直接读队列，而是通过一条持久的双向 gRPC 流和 Worker Controller 通信，后者负责转发任务、结果、日志、指标以及 kill 信号；[36]
- 队列后端可以是 JDBC（默认，开源版可用）或企业版的 Kafka/Redis/AMQP/GCP Pub/Sub；[36]
- 任务的输出单独存到 internal storage，按需读取，让执行记录本身保持轻量；[36]
- 监控上暴露 Prometheus/OpenTelemetry 指标，比如 `kestra.queue.message.lag.count`——「a steadily rising lag means consumers cannot keep up with producers」，能提前发现瓶颈。[36]

这套“角色无状态 + 只通过队列通信”的设计，直接决定了 Kestra 能不能真正做到“百万级 workflow、独立扩容 Worker、混合云部署”——Worker 可以跑在云上、本地或混合环境，只要能连上 Worker Controller 的 gRPC 端点即可，不需要直接访问控制面内部网络。[36]

## 4. Enterprise 版是叠加，不是分叉

企业版被描述为「an additive overlay on the open-source core」——通过替换同一套契约的不同实现来加多租户、RBAC 等能力，「all open-source behavior is preserved」。[36] 这意味着从开源版升级到企业版，架构模型是连续的，不是另起一套系统。

## 5. 工程边界在哪里

Kestra 官方自己给出的市场定位里，也间接划了边界：[38]
- **专精的深度事务型微服务编排**（比如 Temporal、Camunda 这类）：Kestra 认为它们在自己的领域很强，但「too heavy or too dev-centric for broad company-wide adoption」——反过来说，如果你真正需要的是这种深度、专精的 durable execution 语义，Temporal 更对症，而不是 Kestra；
- **纯代码优先框架**（如 Airflow）：学习曲线陡、运维负担重，如果团队已经完全是工程师主导且不需要业务方参与，重的代码优先框架的生态成熟度可能仍有优势；
- **资产血缘与治理**：Kestra 的声明式 YAML 长于统一调度和事件驱动，但不是围绕数据资产血缘设计的，这类需求更适合 Dagster；
- **纯 Python 脚本原地升级**：如果团队的诉求就是“已有 Python 脚本变得更可靠”，且不需要跨语言、跨角色协作，Prefect 的门槛可能更低。

## 6. 正确位置

Kestra 最自然的位置通常是：
- 需要同时支撑定时调度和事件驱动自动化的跨团队平台；
- 需要工程师和业务方共同参与流程定义和调整；
- 需要广泛的第三方系统集成，且不想为每个集成手写对接代码；
- 流程需要正式的人工审批节点，且审批状态要能长期持久化、可审计。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 控制面/数据面分层的价值 | 把“碰用户基础设施”的权限收窄到 Worker 一个角色 |
| 队列通信的价值 | 解耦角色，故障不直接级联，支撑独立扩容 |
| Enterprise 版的定位 | 开源核心之上的叠加层，不是另起一套系统 |
| 最大边界 | 不是深度事务型微服务编排、资产治理或纯脚本升级的最佳答案 |
