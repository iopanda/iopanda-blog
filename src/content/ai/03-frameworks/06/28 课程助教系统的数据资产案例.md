# 课程助教系统的数据资产案例

> 把 Dagster 放回课程助教主线时，它最自然的角色不是“管理长时审批流程”，也不是“运营大量定时批处理 DAG”，而是：**课程助教背后其实有一整套需要被治理的数据资产——知识库表、切片与向量索引、评估数据集、模型/prompt 版本、问答日志聚合表。** 这时候最关键的问题不是任务怎么排、流程怎么恢复，而是这些资产是否新鲜、依赖关系是否清楚、责任人是谁。

**学习目标**：学完本章，你将能够——
1. 判断课程助教系统何时适合 Dagster；
2. 设计知识库、向量索引、评估数据集这类资产的依赖与分区结构；
3. 说明为什么这里最重要的是资产血缘与新鲜度，而不是任务调度或状态恢复；
4. 识别这个案例里的关键风险：资产建模成本、check 门禁的粒度、partition 数量膨胀；
5. 写一张课程助教系统的 Dagster 适配卡。

## 1. 什么时候课程助教适合 Dagster

- 知识库内容会持续更新，需要清楚“这份切片/索引是从哪个课程文档、哪个版本产生的”；
- 评估数据集、模型/prompt 版本需要被追踪新鲜度，而不是散落在某次脚本运行的日志里；
- 多个团队（内容组、算法组、运营组）都要对同一批数据资产负责，需要明确 owner 和数据结构；
- 需要在“内容变更”和“评估结果变化”之间建立可追溯的血缘，而不是靠人工记忆。

## 2. 推荐架构

- asset 层：`course_content_raw`（原始课程文档）→ `course_chunks`（切片）→ `course_embeddings`（向量索引）→ `qa_eval_dataset`（评估集）→ `qa_eval_report`（评估报表）
- op 层：抓取、清洗、切片、embedding 调用、检索评估、报表生成——这些是资产背后的计算细节
- resource 层：向量数据库、LLM API、对象存储——按本地/测试/生产环境切换实现
- sensor 层：新课程内容上线时触发 `course_content_raw` 重新物化，进而联动下游资产
- partition 层：按课程/按更新周期给 `course_chunks`、`course_embeddings` 分区，只重算变化的那部分课程内容
- asset check 层：切片完整性检查、embedding 维度校验、评估集覆盖率检查，必要时用 `blocking=True` 挡住带质量问题的资产继续下传
- 治理层：给关键资产标 owner（内容组/算法组）、tag（课程名、敏感度），在资产目录里统一检索

## 3. 为什么这里不优先选 Temporal、Airflow 或 Prefect

不是因为这三者不强，而是这里的问题主语更偏：
- 关心的是“这份知识库/评估集资产现在新不新鲜、依赖了哪些上游”，不是长时审批或跨天等待（这是 Temporal 的主场）；
- 关心的是资产之间的依赖与血缘，而不只是“任务图按什么顺序跑”（这是 Airflow 更偏 task-first 的主场）；
- 关心的是跨工具、跨团队的资产治理和数据目录，而不是“把已有脚本原地升级”（这是 Prefect 更偏开发者体验优先的主场）。

如果课程助教之后长出跨天人工审批环节，那部分更适合评估 Temporal；如果主要诉求变成大量稳定定时批处理而资产血缘不是当务之急，Airflow 可能性价比更高。

## 4. 动手活动

> [!example] 输出 `course-ta-dagster-card.md`
>
> 为课程助教列：哪些是需要被追踪血缘和新鲜度的数据资产、哪些资产该分区、哪些环节需要 blocking 的数据质量门禁、谁是每份资产的 owner。写一句结论：你的课程助教后台主复杂度是资产治理，还是任务调度或流程状态恢复。

## 5. 总结

| 关键问题 | 一句话 |
|---|---|
| 课程助教为什么适合 Dagster | 因为知识库、评估集、模型版本本质上是需要被治理的数据资产 |
| 最大价值 | 让内容更新、评估结果变化之间的血缘可追溯 |
| 不适合什么 | 主要问题是长时审批/补偿流程，或还没到需要资产治理的阶段 |
