# 运营可视化、部署与工程边界

> Airflow 的一个重要价值，从来不只是“DAG 能跑”，而是它很强调运营可视化：Dags、Grid、Graph、Assets、Backfill、Home 都是正式 UI 面。[11] 安装文档也明确说明 standalone 模式会启动 scheduler、web server、triggerer、API server 等多个组件。[12] 这说明 Airflow 的主问题不仅是 authoring，还包括长期运营。

**学习目标**：学完本章，你将能够——
1. 理解为什么 Airflow 的 UI/ops 面如此重要；
2. 说出 scheduler、triggerer、web/API 等组件为什么一起构成平台；
3. 理解它的工程边界：它不是所有长时状态机的最佳答案；
4. 判断什么时候 Airflow 足够，什么时候该转向其他编排框架；
5. 为系统写一张 ops-boundary card。

## 1. Airflow 是调度平台，不只是库

安装文档里连 standalone 都会拉起多个组件：[12]
- scheduler
- web server
- triggerer
- API server

这说明 Airflow 天然就不是“一个 Python 包而已”，而是一个运行平台。

## 2. UI 为什么重要

README 里专门列出多个 UI 视图：[11]
- Dags
- Assets
- Grid
- Graph
- Home
- Backfill
- Code

这说明对 Airflow 而言，workflow 的价值不仅是被定义，更是被运营、被观察、被排障。

## 3. 工程边界在哪里

Airflow 很强，但它也有明显边界：
- 如果流程本质上是 long-lived stateful workflow，Temporal 更自然；
- 如果你更关心 Python-native flow DX，Prefect 更轻；
- 如果你更关心资产治理和 lineage，Dagster 更合适。

## 4. 正确位置

Airflow 最自然的位置通常是：
- 数据/AI batch orchestration 平台；
- 定时调度中心；
- 统一运营和排障入口；
- 不是复杂业务状态机的唯一底座。

## 5. 动手活动

> [!example] 输出 `airflow-ops-boundary-card.md`
>
> 列你的系统是否需要 DAG UI、backfill、任务历史、统一调度平台、triggerer/API 组件。写一句结论：你的主问题是运营 batch pipelines，还是恢复 long-lived stateful workflows。

## 6. 总结

| 关键问题 | 一句话 |
|---|---|
| Airflow 的平台主语是什么 | 调度 + 运营 + 可视化 |
| UI 为什么重要 | 它让工作流成为可运营系统，而不是隐藏脚本 |
| 最大边界 | 不以 long-lived durable execution 为第一主语 |
| 正确使用方式 | 用于稳定 batch/data/AI pipelines 的长期运营 |
