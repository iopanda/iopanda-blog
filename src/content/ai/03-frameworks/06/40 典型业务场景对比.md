# 典型业务场景对比

> 上一篇的矩阵是“框架视角”，这一篇换成“场景视角”：把五个框架各自最擅长的场景抽出来，变成四类典型业务场景——长流程业务系统、数据管线、AI automation、资产平台。每类场景直接对应前五个子目录里已经写过的案例篇（各系列的 05），这里做的是横向收拢，而不是重新论证。

**学习目标**：学完本章，你将能够——
1. 把“我的系统属于哪类典型场景”作为选型的第一道筛选；
2. 理解四类场景各自的核心特征和最合适的框架；
3. 识别一个场景同时具备多类特征时该怎么拆解；
4. 用场景视角反过来验证矩阵视角的判断是否一致；
5. 为下一篇的课程助教综合选型卡打好基础。

## 1. 长流程业务系统：状态恢复、人工审批、跨天补偿是主矛盾

**典型特征**：流程会运行很久（几小时到几天）；中间要等外部系统回调或人工审批；某一步失败不能简单“从头重跑”，需要按语义恢复或补偿。

**最合适**：[Temporal](/ai/03-frameworks/06/02/)。对应案例：[课程助教 Agent 的 Temporal 架构案例](/ai/03-frameworks/06/07/)——课程助教一旦长出跨审批、跨异步反馈、多阶段处理的环节，问题主语就变成了“流程在等待、失败、补偿之后还能不能继续得对”，这正是 durable execution 的主场。

**次选/补充**：如果人工审批只是偶尔出现、不要求彻底的状态机语义，[Kestra](/ai/03-frameworks/06/30/) 的 Pause/HumanTask 也能覆盖较轻量的审批场景。

## 2. 数据管线：定时批处理、backfill、运维可视化是主矛盾

**典型特征**：任务图相对稳定；按 schedule interval 重复运行；需要 backfill 补历史数据；需要统一 UI 做运营和排障。

**最合适**：[Apache Airflow](/ai/03-frameworks/06/09/)。对应案例：[课程助教系统的数据/评估管线案例](/ai/03-frameworks/06/14/)——知识库更新、离线评估、日志聚合、定时报表，这类问题的主语是“稳定的批处理任务图怎么被调度和运营”，而不是流程状态恢复或资产血缘。

**次选/补充**：如果团队规模较小、还没到需要成熟 ops UI 的阶段，且数据管线本质上是一堆 Python 脚本，[Prefect](/ai/03-frameworks/06/16/) 是更轻的起点。

## 3. AI automation：脚本升级、事件响应、跨角色协作是主矛盾

**典型特征**：团队本来就在写 Python 脚本（生成、批改、检索）；需要重试/缓存/事件告警但不想先接受重平台；或者需要跨语言、跨团队、非工程角色也能调整流程的自动化（通知、审批、集成第三方系统）。

**最合适**：视具体子问题分两种：
- 如果核心诉求是“把已有 Python 脚本原地升级成生产工作流”，选 [Prefect](/ai/03-frameworks/06/16/)。对应案例：[课程助教 Agent 的 Prefect 架构案例](/ai/03-frameworks/06/21/)。
- 如果核心诉求是“统一调度+事件驱动+多角色协作”，选 [Kestra](/ai/03-frameworks/06/30/)。对应案例：[课程助教与运营自动化的 Kestra 架构案例](/ai/03-frameworks/06/35/)。

这两者经常会同时出现在同一个 AI automation 系统里——这不矛盾，恰恰说明“AI automation”本身不是单一框架能通吃的一类场景，而是要看子问题落在“脚本可靠性”还是“跨角色事件协作”上。

## 4. 资产平台：血缘、新鲜度、数据治理是主矛盾

**典型特征**：核心对象是数据资产（表、向量索引、评估集、模型版本），需要跨工具统一追踪依赖关系、责任人、字段结构；需要把数据质量检查变成正式的、可阻断的门禁。

**最合适**：[Dagster](/ai/03-frameworks/06/23/)。对应案例：[课程助教系统的数据资产案例](/ai/03-frameworks/06/28/)——知识库切片、向量索引、评估数据集本质上是需要被治理的数据资产，问题主语是“这份资产新不新鲜、依赖谁、谁负责”，不是任务调度或流程恢复。

## 5. 一张场景速查表

| 场景 | 主矛盾 | 首选框架 | 对应案例篇 |
|---|---|---|---|
| 长流程业务系统 | 状态恢复、人工审批、跨天补偿 | Temporal | [05 课程助教 Agent 的 Temporal 架构案例](/ai/03-frameworks/06/07/) |
| 数据管线 | 定时批处理、backfill、运维可视化 | Airflow | [05 课程助教系统的数据/评估管线案例](/ai/03-frameworks/06/14/) |
| AI automation（脚本可靠性） | 脚本升级、重试/缓存/事件告警 | Prefect | [05 课程助教 Agent 的 Prefect 架构案例](/ai/03-frameworks/06/21/) |
| AI automation（跨角色协作） | 统一调度+事件驱动+多角色维护 | Kestra | [05 课程助教与运营自动化的 Kestra 架构案例](/ai/03-frameworks/06/35/) |

## 6. 一个系统可能同时覆盖多类场景

课程助教就是最直接的例子：它同时有长流程审批（Temporal）、定时评估管线（Airflow 或更轻的方案）、脚本可靠性诉求（Prefect）、跨角色自动化（Kestra）、数据资产治理（Dagster）。下一篇会把这五类子问题在同一个系统里拼成一张完整的选型卡。

## 7. 动手活动

> [!example] 动手活动：更新 `workflow-framework-selection-card.md`
>
> 把你的系统拆成子系统，逐个对照第 5 节的速查表，标出每个子系统属于哪类场景、对应哪个框架。写一句结论：你的系统是单一场景，还是需要按子系统边界组合多个框架。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 场景视角的价值 | 把“选框架”变成“先认场景”，降低误判概率 |
| 四类场景 | 长流程业务系统 / 数据管线 / AI automation / 资产平台 |
| AI automation 为什么拆成两类 | 脚本可靠性和跨角色事件协作是两个不同的子问题 |
| 系统覆盖多场景怎么办 | 按子系统边界组合框架，而不是强求一个框架通吃 |
