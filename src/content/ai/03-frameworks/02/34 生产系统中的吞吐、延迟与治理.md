# 生产系统中的吞吐、延迟与治理

> Pathway README 一直在强调：同一套代码可用于 local、CI、batch、stream replay、stream processing；底层 Rust engine 支持 multithreading、multiprocessing、distributed computations，并提供 persistence。[68] 这说明它看问题的方式不是“怎么做一个 demo RAG”，而是“怎么把 live retrieval system 放进生产运行语境”。

**学习目标**：
1. 理解为什么 Pathway 从 Day 1 就更像生产系统框架；
2. 说出吞吐、延迟、一致性、持久化在 live RAG 中的关系；
3. 解释 persistence 和 replay 为什么对实时知识系统重要；
4. 判断什么时候你真的需要这类重运行时框架；
5. 为一个流式知识系统写出生产约束卡。

## 1. 吞吐和延迟不是后话

在静态 RAG 里，大家常先看回答效果；
在 Pathway 场景里，吞吐和延迟本身就是一等设计变量：
- 数据更新太快；
- 查询不能总等全量重建；
- 系统重启后要尽快恢复；
- 回放期间不能语义失控。

## 2. persistence / replay 是 live retrieval 的主线

Pathway README 明说：支持 persistence 保存计算状态，支持 stream replay。[68]

这意味着它关心的是：
- 崩溃后恢复；
- 历史流重放；
- 数据乱序和延迟后的结果一致性。

这和普通 RAG “重启后重新加载索引”完全不是同一种世界。

## 3. 什么时候它会偏重

若系统只是：
- 一批静态文档；
- 每周更新一次；
- 主要诉求是文档问答；
Pathway 往往会显得偏重。

但若系统是：
- 实时日志
- 持续同步知识源
- 高频数据库变更
- 在线分析 + 问答混合
它就会变得非常自然。

## 4. 动手活动

> [!example] 输出 `pathway-production-constraints.md`
>
> 写一页卡片：你的系统更新频率、可接受延迟、重启恢复要求、一致性要求是什么。判断它是否真的需要 live data framework。

## 5. 总结

| 关键问题 | 一句话 |
|---|---|
| Pathway 为什么像生产框架 | 因为它从一开始就处理吞吐、持久化、重放和一致性 |
| 什么时候值得用 | 当更新语义本身就是主问题 |
| 什么时候显得偏重 | 当数据其实很静态、流程也不流式 |
