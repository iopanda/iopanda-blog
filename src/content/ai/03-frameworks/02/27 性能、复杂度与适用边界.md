# 性能、复杂度与适用边界

> LightRAG README 一边强调效率和低成本，一边也坦白它需要 entity-relation extraction、图存储、可选 reranker、可选多种 parser、可选多种 storage backend。[72][73][74][75][76] 这说明它虽然比重型 GraphRAG 轻，但绝不是零成本。

**学习目标**：
1. 理解 LightRAG 为什么“轻”但并不“免费”；
2. 说出它的主要复杂度来自哪里；
3. 判断什么系统值得引入图增强；
4. 解释什么时候它会比普通 vector RAG 更划算；
5. 为一个知识系统写适用边界卡。

## 1. 它轻在哪里

- 不走特别重的报告式 GraphRAG 路线
- 强调效率和低 LLM 调用成本
- 用 dual-layer retrieval 平衡图与向量[72]

## 2. 它重在哪里

- entity/relation 抽取本身要成本
- 图更新和删除有额外语义
- embedding / reranker / role-specific LLM 配置更多
- chunking 还有多策略和 parser 复杂度[72][73][74][76]

## 3. 什么时候值得用

适合：
- 关系密集知识
- 复杂比较和跨文档关系问题
- 需要比纯 vector RAG 更强结构语义

不适合：
- 超轻 FAQ
- 纯静态小型知识库
- 完全没有关系型问题

## 4. 总结

| 关键问题 | 一句话 |
|---|---|
| LightRAG 轻在哪里 | 比重型 GraphRAG 更克制、更高效 |
| 重在哪里 | 抽图、配置、更新、存储都会带来额外复杂度 |
| 适合什么 | 关系语义真的重要的知识系统 |
