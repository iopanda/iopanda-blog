# 多用户、权限、平台化运营与评测

> RAGFlow 和很多 retrieval framework 的最大差别之一，是它很早就把团队协作、权限、资源共享、dataset retrieval testing 放进同一个产品面板语境里。[65][66][67] 这说明它不是只在乎“开发者怎样编程”，而是也在乎“组织怎样运营知识层”。

**学习目标**：
1. 解释为什么 RAGFlow 对团队、权限、共享范围讲得这么重；
2. 理解 dataset testing、metadata、permission system 为什么都是 retrieval platform 的一部分；
3. 说出平台型 RAG 与框架型 RAG 在运营层的差异；
4. 判断什么时候团队真正需要平台化，而不是只需要 SDK；
5. 为一个多用户知识系统设计运营视角下的 retrieval 规则。

## 1. permissions 说明它不是单用户 demo

权限系统总览明确写出三层：team membership、resource sharing scope、resource operation permissions。[67]

这说明 RAGFlow 默认的世界里：
- 知识库是共享资源；
- agent 也是共享资源；
- memories、search apps、chat 等都有资源边界。

这和只在代码里 new 一个 retriever 的框架完全不同。

## 2. metadata 说明治理不是事后补丁

metadata 文档强调：metadata 可来自 built-in fields、auto generation、table column roles、manual maintenance，并用于 filtering、retrieval range restriction、result analysis。[66]

这意味着：
- metadata 不只是检索技巧；
- 还是运营、治理、权限、分析的一部分。

## 3. retrieval testing 说明评测是平台一等能力

RAGFlow 的 retrieval testing 文档本质上在要求团队：
- 先测召回；
- 再测聊天；
- 再测 agent；
- 问题排查按 parsing → chunk → metadata → retrieval params 的顺序做。[65]

这和只在 notebook 里跑几次 query 的工作方式差别很大。它把评测做成了平台工作流的一部分。

## 4. 什么时候平台化是刚需

当系统开始出现：
- 多团队共享知识库；
- 多角色管理 Agent / dataset；
- 权限和共享范围要治理；
- retrieval testing 要成为日常流程；
- parsing / chunking 要可视化和可运营；
平台化就不再是“好看 UI”，而是系统需求。

## 5. 动手活动

> [!example] 输出 `ragflow-platform-governance.md`
>
> 为课程助教系统写一页平台运营规则：哪些 dataset 共享，哪些 metadata 必填，哪些 retrieval params 需要被测试后才能进生产，哪些权限只给教师或管理员。

## 6. 总结

| 关键问题 | 一句话 |
|---|---|
| RAGFlow 为什么像平台 | 因为它把权限、共享、测试、知识运营一起纳入产品主线 |
| permission system 的意义 | 知识层天然是多用户资源 |
| metadata 的意义 | 不只是召回技巧，也是治理字段 |
| retrieval testing 的意义 | 把检索验收纳入平台流程 |
