# 课程助教系统的 retrieval framework 选型卡

> 前三篇分别给了方法论、矩阵、场景速查表。这一篇把它们收口成一份完整的选型卡，对象就是这一整章反复用来做案例的课程助教系统。目标不是“选出唯一的框架”，而是示范一种更现实的结论：**一个真实的知识问答系统往往需要按知识来源和查询形态的边界组合多个 retrieval framework，选型卡的价值在于把每个子系统的判断依据写清楚，而不是强求统一。**

**学习目标**：学完本章，你将能够——
1. 把课程助教的知识系统拆成若干子问题，分别对应不同框架的主场；
2. 说出每个子问题选择对应框架的判断依据，以及“为什么不选别的”；
3. 理解子系统之间怎么交接（谁的输出是谁的输入）；
4. 判断这份选型卡在什么情况下需要重新评估；
5. 把这份卡当作模板，套用到自己的知识系统上。

## 1. 课程助教知识系统的四类子问题

课程助教的知识来源并不是单一形态，按第 03 篇的场景分类，可以拆成四类子问题（“生产化检索链路”这一维度不是单独的知识来源，而是贯穿其他四类的评测/编排能力，会在第 3 节单独说明）：

| 子问题 | 核心特征 | 框架 |
|---|---|---|
| 课程正文资料问答 | 讲义、PDF、课件为主，结构相对静态，元数据丰富（章节、课程、知识点） | [LlamaIndex](/iopanda-blog/ai/03-frameworks/02/02/) |
| 想要完整的知识运营平台 | 需要多教师协作、citation 可追溯、testing、权限隔离，且希望少自己拼零件 | [RAGFlow](/iopanda-blog/ai/03-frameworks/02/16/) |
| 跨章节概念关系问答 | “这个知识点和哪些前置概念相关”“这条规则依赖哪些前提”这类关系型问题 | [LightRAG](/iopanda-blog/ai/03-frameworks/02/23/) |
| 课程公告/FAQ/规则问答 | 公告、答疑规则、外部资料高频更新，静态索引很快过期 | [Pathway](/iopanda-blog/ai/03-frameworks/02/30/) |

## 2. 每个子问题的判断依据（为什么选它，为什么不选别的）

**课程正文资料问答 → LlamaIndex**：主矛盾是“文档、节点、索引这些知识对象怎么被组织，才能支撑单域和跨知识点问答”。不选 RAGFlow，因为课程正文相对静态，暂时不需要平台化的多用户协作和权限治理；不选 LightRAG，因为课程正文的知识点关系密度还没到必须靠图检索才能回答的程度；不选 Pathway，因为课程正文更新频率低，不是“新鲜度”驱动的问题。

**想要完整的知识运营平台 → RAGFlow**：主矛盾是“多个教研/运营角色要共同维护知识库，citation 可追溯，且想要一套现成的解析/testing/共享能力”。不选 LlamaIndex，因为团队已经不想自己拼平台层的权限和协作能力；不选 Haystack，因为这里的诉求已经超出“显式调链路”，变成“要一整套治理能力”。

**跨章节概念关系问答 → LightRAG**：主矛盾是“知识点之间的前置依赖、概念关联，普通向量召回很难覆盖”。不选 LlamaIndex/Haystack，因为它们默认路径更偏向量召回，处理关系型查询需要额外拼装；不选 Pathway，因为这里的问题不是新鲜度，是关系结构。

**课程公告/FAQ/规则问答 → Pathway**：主矛盾是“数据持续变化，答案必须跟着更新，而不是定期重建索引”。不选其他三个框架，因为它们都默认知识相对稳定，用它们处理高频变化的数据会持续面临“索引没刷新、答案是旧的”的问题。

## 3. 生产化检索链路能力：贯穿性的评测/编排层

如果课程助教团队需要对以上任意子系统做**显式的检索质量评测**（比如 A/B 测试不同 rerank 策略、比较 hybrid retrieval 和纯向量检索的效果），[Haystack](/iopanda-blog/ai/03-frameworks/02/09/) 的角色不是替代上面四个框架，而是作为**编排/评测层**叠加在某个子系统之上——比如在“课程正文资料问答”这条链路里，用 Haystack 的 pipeline 把 LlamaIndex 产出的检索结果接入一套可评测、可切换组件的生产链路。这说明五个框架不总是互斥选择，Haystack 尤其经常以“链路治理层”的角色和其他框架组合。

## 4. 子系统之间怎么交接

四类子系统不是孤立的，一个学生的问题进来后，大致交接顺序是：

1. 问题先经过一层**路由判断**：这是课程正文问题、平台协作问题、概念关系问题，还是公告/FAQ 问题？
2. 课程正文问题交给 **LlamaIndex** 的 query engine 处理；如果这条链路需要生产化评测，中间可以接入 **Haystack** 的 pipeline；
3. 概念关系问题交给 **LightRAG** 的图检索处理；
4. 公告/FAQ/规则问题交给 **Pathway** 驱动的实时索引处理，保证答案不会因为索引没刷新而过期；
5. 如果整个知识库需要多教师协作、citation 追溯、权限隔离，**RAGFlow** 可以作为知识运营层包裹在最外层，管理数据源和团队协作，底层仍可以复用前面几类检索能力。

## 5. 什么情况下需要重新评估这份选型卡

- 如果“课程正文资料问答”的知识点关系密度显著上升（比如课程体系变得高度依赖前置知识链），需要重新评估是否要把部分正文检索也迁到 LightRAG；
- 如果“课程公告/FAQ”的更新频率其实并不高（比如一学期才变几次），Pathway 带来的实时语义价值会下降，这时可以评估是否收敛回更轻量的方案；
- 如果团队规模缩小、不再需要多角色协作和权限治理，RAGFlow 的平台化价值会下降，可以评估是否收敛掉一个框架，降低维护复杂度；
- 任何时候，重新评估都应该回到第 01 篇的方法论：先问主矛盾有没有变，而不是先看有没有新框架出现。

## 7. 总结

| 关键问题 | 一句话 |
|---|---|
| 课程助教需要几个框架 | 四类子问题对应四个框架，Haystack 常作为贯穿性的评测/编排层叠加使用 |
| 选型卡的核心价值 | 不是选出“唯一答案”，而是让每个判断依据可追溯、可复查 |
| 子系统怎么交接 | 先路由判断问题类型，再分流到对应框架，RAGFlow 可作为最外层知识运营层 |
| 什么时候要重新评估 | 主矛盾变了才重新评估，不是有新框架就重新评估 |

## 8. 思考题

**为什么一个 retrieval framework 的最佳选择，常常不是由模型本身决定，而是由“知识如何进入系统、如何更新、如何被查询、如何被治理”决定？把这个判断做对了，会比盲目追热门框架多省下哪类代价？**

> [!note] 参考答案
> 因为 retrieval framework 解决的不是模型能力上限，而是知识系统的组织方式。模型相同，检索层设计不同，系统体验可以完全不同。把这个判断做对，会明显减少后续在重构索引、重写检索链、补 metadata、补评测、补权限治理、补更新语义上的返工代价。换句话说，好的选型不是让第一版更酷，而是让第十版还改得动。
