# 五个框架横向矩阵

> 这一篇把上一篇的五类复杂度，逐一对齐到 [LlamaIndex](/ai/03-frameworks/02/02/)、[Haystack](/ai/03-frameworks/02/09/)、[RAGFlow](/ai/03-frameworks/02/16/)、[LightRAG](/ai/03-frameworks/02/23/)、[Pathway](/ai/03-frameworks/02/30/) 五个框架，形成一张可以直接拿来对照的横向矩阵。所有判断都来自前五个子目录已经建立的事实，这里只做收敛。

**学习目标**：学完本章，你将能够——
1. 一眼看出五个框架在“第一语言”上的根本差异；
2. 按数据形态、查询形态、治理运营三个角度分别定位框架；
3. 用横向矩阵快速比较最强点、最大代价、最适合、最不适合；
4. 识别数据形态或查询形态判断错误会带来什么后果；
5. 把矩阵直接套进 retrieval-framework-selection-card。

## 1. 五条路线的第一性差异

| 框架 | 第一语言 | 首先解决什么 | 更像什么 |
|---|---|---|---|
| [LlamaIndex](/ai/03-frameworks/02/02/) | Document / Node / Index / QueryEngine | 知识怎样成为可查询对象 | 文档与查询对象框架 |
| [Haystack](/ai/03-frameworks/02/09/) | Component / Pipeline / Route | 检索链怎样显式编排和评测 | 检索工作流框架 |
| [RAGFlow](/ai/03-frameworks/02/16/) | Context Engine / Dataset / Testing / Sharing | 如何先拿到完整知识平台 | RAG 平台 / engine |
| [LightRAG](/ai/03-frameworks/02/23/) | Entity / Relation / Chunk / Query Mode | 如何用轻量图结构增强召回 | 轻量 graph RAG 路线 |
| [Pathway](/ai/03-frameworks/02/30/) | Stream / Incremental Update / Freshness | 数据持续变化时如何保持答案新鲜 | 实时数据流框架 |

一句话：LlamaIndex 先讲对象，Haystack 先讲链路，RAGFlow 先讲平台，LightRAG 先讲图增强，Pathway 先讲数据流。

## 2. 数据形态：先问你喂进去的到底是什么

| 数据形态 | 更自然的路线 | 原因 |
|---|---|---|
| 文档为主、知识库为主、元数据丰富 | LlamaIndex | 先把文档对象与索引对象组织清楚 |
| 多种处理组件要显式拼接 | Haystack | 组件边界和流水线边界最清楚 |
| 异构文档很多、解析质量和平台治理很重要 | RAGFlow | 先拿完整 context engine / parsing / testing / sharing |
| 实体关系密、跨文档结构关系强 | LightRAG | 图增强检索更自然 |
| 数据本身在持续流入流出 | Pathway | 更新语义比一次性构建更重要 |

最常见的误判之一，是明明系统面对的是持续变化的数据流，却还按“静态文档问答”设计；或明明系统只是静态课程资料，却过早引入流式框架。这两种都会导致复杂度错位。

## 3. 查询形态：系统到底是在回答哪类问题

| 查询形态 | 更自然的框架倾向 |
|---|---|
| 单域文档问答 | LlamaIndex / Haystack |
| 多知识域路由问答 | LlamaIndex / Haystack |
| 复杂比较、子问题分解、跨索引综合 | LlamaIndex |
| 高治理、可视化 chunking、citation-first 知识平台 | RAGFlow |
| 关系驱动查询、跨实体链路查询 | LightRAG |
| 近实时问答、更新优先级高于静态索引精雕细琢 | Pathway |

查询形态错判，会导致整个检索层表达语言错位。比如把复杂关系查询强行塞进普通 top-k RAG；或者把需要稳定 pipeline 评测的系统交给“整个平台默认配置”，都会很快出现盲区。

## 4. 治理与运营：你的系统只是能答，还是要长期被运营

| 治理 / 运营需求 | 更自然的路线 |
|---|---|
| 主要是开发者自己维护，重代码可编程性 | LlamaIndex |
| 主要是团队内显式评测、调链、换组件 | Haystack |
| 需要 dataset 管理、权限、共享、testing、citation 一体化 | RAGFlow |
| 需要评估图抽取、图更新、图查询效果 | LightRAG |
| 需要 persistence、replay、freshness、一致性治理 | Pathway |

选型不仅是检索问题，还是运营问题。RAGFlow 和 Pathway 在这里的差异尤其大：前者更像知识平台运营，后者更像数据流运营。

## 5. 横向矩阵：最强点、最大代价、最适合、最不适合

| 框架 | 最强点 | 最大代价 | 最适合 | 最不适合 |
|---|---|---|---|---|
| LlamaIndex | 知识对象和查询对象组织极强 | 需要自己做较多架构判断 | 文档/知识库主导系统 | 你只想要一台现成平台 |
| Haystack | 检索链路透明、评测和组件化清晰 | pipeline 心智偏重，初学者可能觉得繁 | 生产化 retrieval workflow | 极简问答 demo |
| RAGFlow | 完整平台体验、citation/testing/sharing 一体化 | 平台层更重，灵活度与平台边界要权衡 | 想快速拿完整知识平台 | 只想轻量本地代码实验 |
| LightRAG | 轻量图增强检索，适合关系密集知识 | 图抽取与图存储仍会带来额外复杂度 | 关系驱动 / 图增强问答 | 完全不需要图关系的简单系统 |
| Pathway | 数据持续变化时的 live retrieval 语义最强 | 对静态知识库会显得偏重 | 实时知识流 / 增量更新系统 | 低频更新的静态文档库 |

## 6. 反向信号：快速排除不对症的框架

| 如果你的系统… | 优先排除 |
|---|---|
| 数据基本静态、更新很少 | Pathway（先看 LlamaIndex/Haystack） |
| 只是单一知识域的简单问答 | RAGFlow、LightRAG（先看 LlamaIndex/Haystack） |
| 实体关系并不密集、不需要跨文档关系查询 | LightRAG |
| 团队想要高度可编程、不想被平台边界卡住 | RAGFlow |
| 需要显式控制和评测检索链路的每一步 | 先看 Haystack，而不是一步到位上平台 |

## 7. 动手活动

> [!example] 动手活动：更新 `retrieval-framework-selection-card.md`
>
> 把上一篇给自己系统的诊断结果，对照第 1-5 节的表格找出最接近的 1-2 个框架。用第 6 节的反向信号表再交叉验证一次：有没有哪个候选框架其实该被排除。

## 8. 总结

| 关键问题 | 一句话 |
|---|---|
| 五条路线的根本差异 | 对象 / 链路 / 平台 / 图增强 / 数据流，五种第一语言 |
| 数据形态判断错了会怎样 | 静态系统被当成流系统会心智负担过重，反之则会追新鲜度追不上 |
| 查询形态判断错了会怎样 | 检索层表达语言错位，复杂查询被硬塞进简单 top-k |
| 治理运营维度为什么重要 | RAG 选型不只是检索问题，还是长期运营问题 |
