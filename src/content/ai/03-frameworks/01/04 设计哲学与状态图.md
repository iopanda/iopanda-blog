# 设计哲学与状态图

> [Agent 运行循环](/iopanda-blog/ai/02-agents/01/04/) 已经说明了 Agent 的最小骨架是 Thought → Action → Observation；[Planning and Reasoning](/iopanda-blog/ai/02-agents/03/) 又让这个骨架开始分叉、回退、重试。问题是：**当一个 Agent 不再只有 2~3 步，而是开始拥有状态、分支、人审、中断与恢复时，为什么它很自然会长成图？** LangGraph 的答案非常激进也非常工程化：不要把复杂 Agent 继续写成一条越来越长的 prompt 链，而要把它重写成**显式状态机**。从官方定位看，它是 long-running、stateful agents 的 low-level orchestration framework；从源码入口看，`libs/langgraph/langgraph/graph/state.py` 直接把 `StateGraph` 定义成“nodes communicate by reading and writing to a shared state”的图构建器。[1][2]

**学习目标**：学完本章，你将能够——

1. 解释为什么 LangGraph 的主角不是 Agent，而是 `StateGraph`；
2. 说出共享状态、节点、边、reducer 在图模型中的职责；
3. 理解 LangGraph 为什么把 `.compile()` 前后的世界分成“构建期”和“执行期”；
4. 用开发者视角看懂 `state.py`、`graph/_node.py`、`pregel/` 这些源码入口大致在干什么；
5. 判断一个 Agent 什么时候值得从循环升级成图。

## 1. 概念：LangGraph 的第一抽象是图，不是 Agent

- 很多框架的入口是 `Agent(...)`；LangGraph 的入口却常常是 `StateGraph(...)`。[1][2]
- 这说明它的根本设计判断是：复杂 Agent 的核心问题不是“再包一层模型对象”，而是**把运行过程显式建模**。
- 在 `state.py` 里，`StateGraph` 的核心注释非常清楚：
  - nodes 通过读写 shared state 通信；
  - 节点签名可以理解为 `State -> Partial<State>`；
  - 每个 state key 还能带 reducer，用于聚合来自多个节点的更新。[2]
- 这套设计和普通链式调用非常不一样：
  - 链式调用默认“上一步输出是下一步输入”；
  - 状态图默认“整个系统共享一个事实账本，不同节点只增量修改其中一部分”。

这背后的架构含义很深：**LangGraph 默认你做的不是“文本流水线”，而是“决策系统”。**

## 2. 为什么要这样设计：链适合线性，图适合现实

线性 chain 在三个场景下会迅速失效：

1. **状态跨步累积**：你不只是把一段文本传下去，而是要同时保存用户问题、检索结果、审批状态、工具调用结果、风险级别；
2. **流程会分支**：资料不足要回去继续检索，风险过高要转人工，工具失败要重试或降级；
3. **多个节点会共同更新同一事实**：比如多个检索节点都往 `retrieved_chunks` 追加内容，这时不是简单覆盖，而是聚合。

LangGraph 的 shared state + reducer 组合，就是专门为这三件事生的：

- shared state 让所有阶段围绕同一份运行事实工作；
- reducer 让并发或多来源更新有定义好的合并规则；
- graph edges 让分支路线显式，而不是埋在 prompt 里的“如果……则……”。

为什么这对开发者和架构师重要？因为一旦系统复杂到这里，**隐式逻辑会比模型幻觉更早杀死可维护性**。

## 3. StateGraph：源码层面它到底在做什么

从 `libs/langgraph/langgraph/graph/state.py` 可以抓到几个最重要的设计点：[2]

| 设计点 | 源码信号 | 工程含义 |
|---|---|---|
| `StateGraph` 是 builder class | 文档明确说必须先 `.compile()` | 构建期与执行期分离 |
| node 签名是 `State -> Partial<State>` | 顶层 docstring 明写 | 节点做增量更新，不必关心全状态重建 |
| state key 可带 reducer | 文档说明可用 `Annotated[type, reducer]` | 并发/多节点更新可控聚合 |
| 有 `context_schema` | 文档建议把 `user_id`、`db_conn` 放这里 | 把运行时上下文与业务状态分离 |
| 底层接 `Pregel` | 文件中直接 import `langgraph.pregel.Pregel` | 执行模型不是随手递归，而是运行时引擎 |

其中最关键的一点是 `context_schema` 与 `state_schema` 的分离：

- `state_schema` 是**会在流程里演化**的东西；
- `context_schema` 是**本次运行可读取、但不应随节点任意篡改**的东西。

这个区分非常像后端系统里的：
- mutable state
- immutable run context

很多 Agent 原型把这两者混在一起，后面一定出事故。

## 4. 节点不是函数分解，而是“决策边界分解”

很多初学者会误以为：节点 = 把大函数拆小。实际上在 LangGraph 里，更合理的理解是：

**节点 = 一次值得被单独观察、单独恢复、单独测量的决策边界。**

例如课程助教 Agent 的节点不应该只是：
- query()
- search()
- answer()

而应该更像：
- 输入清洗
- 检索资料
- 判断证据是否足够
- 生成草稿
- 风险检查
- 人工复核
- 输出校验

因为后者每一步都对应：
- 是否继续？
- 是否重试？
- 是否升级？
- 是否留审计？

也就是说，LangGraph 要你拆的不是代码结构，而是**运行语义**。

## 5. reducer 为什么重要：它决定并发状态是不是可解释

`StateGraph` 允许每个 state key 带 reducer，这在普通教程里常常一笔带过，但对复杂系统其实很关键。[2]

原因很简单：
- 一旦多个节点都能更新同一字段，就必须定义合并语义；
- 如果不定义，系统最后状态要么覆盖、要么顺序偶然，都会难以解释；
- reducer 本质上是给共享状态写并发协议。

举例：
- `retrieved_chunks` 需要 append 合并；
- `risk_flags` 可能需要 set union；
- `final_answer` 通常应该只有一个节点能写；
- `tool_errors` 可能要聚合成列表。

这件事和 prompt 无关，和架构有关。也是为什么 LangGraph 更像 workflow/runtime，而不像普通 prompt framework。

## 6. `.compile()`：为什么它要把图构建和图执行分开

源码和文档都反复强调：`StateGraph` 只是 builder，必须 `.compile()` 之后才能 `invoke()`、`stream()`、`ainvoke()`。[2]

这不是形式主义，而是工程边界：

- 构建期做静态检查：
  - 节点有没有定义；
  - 边是否连通；
  - schema 是否合理；
  - reducer/branch/managed values 是否能成立；
- 执行期才关注：
  - 运行状态如何流动；
  - 工具是否成功；
  - 流式输出如何产生；
  - checkpoint 如何保存。

开发者的一个常见误区，是把这些都堆进 runtime 动态猜。LangGraph 则尽量把一部分错误前移到 compile 阶段。这种“尽早失败”的品味，非常适合复杂 Agent 系统。

## 7. Pregel：为什么 LangGraph 底层执行引擎值得知道

在 `state.py` 里可以直接看到它依赖 `langgraph.pregel.Pregel`。[2] 顶层 README 还明确承认灵感来自 Pregel、Apache Beam、NetworkX。[1]

这至少说明三件事：

1. 它不是把图当可视化装饰，而是真把图当执行模型；
2. 它借的是“图式计算/流式数据处理”的系统思路，而不只是 LLM 包装技巧；
3. 它的野心不只是跑一次 Agent，而是承载更长、更可观测、更可恢复的工作流。

对架构师来说，这很重要：你不是在选一个“模型小工具”，而是在选一种**运行时世界观**。

## 8. 和同类框架相比，LangGraph 的第一性原理是什么

| 框架 | 第一性问题 | LangGraph 相比的特点 |
|---|---|---|
| [CrewAI](/iopanda-blog/ai/03-frameworks/01/18/) | 怎么组织角色团队和流程 | LangGraph 更少“角色语义”，更多“状态机语义” |
| [OpenAI Agents SDK](/iopanda-blog/ai/03-frameworks/01/25/) | 怎么快速获得现代 Agent 原语 | LangGraph 更像底层编排内核 |
| [PydanticAI](/iopanda-blog/ai/03-frameworks/01/32/) | 怎么把 Agent 做成 typed Python 组件 | LangGraph 更先问控制流和恢复 |
| [AutoGen](/iopanda-blog/ai/03-frameworks/01/11/) | 多 Agent 之间怎样通信协作 | LangGraph 更先问系统当前处于哪个状态 |

一句话：**LangGraph 不先把 Agent 当“会说话的人”，而先把它当“会迁移状态的系统”。**

## 9. 动手活动：把课程助教最小循环翻译成 StateGraph

> [!example] 动手活动：输出 `langgraph-state-design.md`
>
> **目标**：把手写 ReAct 循环翻译成 LangGraph 式状态图，而不是直接写代码。
>
> **步骤**：
> 1. 定义 `state_schema`：`user_query`、`retrieved_chunks`、`draft_answer`、`risk_flags`、`final_answer`；
> 2. 定义 `context_schema`：`user_id`、`role`、`db_conn`、`request_id`；
> 3. 画节点：检索、判断证据、生成草稿、风险检查、人工复核、结束；
> 4. 给 `retrieved_chunks` 设计 reducer；
> 5. 标出哪些边是确定性的，哪些边依赖模型判断。
>
> **完成标准**：你能回答“哪个字段是状态、哪个字段是上下文、哪个节点在修改什么、为什么某个字段需要 reducer”。

## 10. 边界与排错

- **误区一：一切流程都值得建图。** 两步问答也上图，建模成本会超过收益；
- **误区二：state 什么都塞。** 共享状态是运行事实账本，不是原始日志垃圾桶；
- **误区三：节点按代码函数切，而不是按决策边界切。** 这样图会看起来工整，运行语义却很糊；
- **误区四：忽视 reducer。** 多节点共写一个字段却不定义聚合语义，迟早出现“为什么这个状态被覆盖了”的排错噩梦；
- **误区五：把 compile 当样板动作。** 构建期与执行期分离，本来就是为了把错误提前暴露。

## 11. 总结

| 关键问题 | 一句话 |
|---|---|
| LangGraph 的核心抽象是什么 | `StateGraph`，不是一个普通 `Agent` 容器 |
| 为什么会需要它 | 复杂 Agent 迟早会遇到共享状态、分支、恢复和聚合问题 |
| 节点本质是什么 | 可观测、可恢复、可测量的决策边界 |
| reducer 为什么关键 | 它定义了共享状态的并发合并语义 |
| `.compile()` 为什么重要 | 它把图的构建期检查与运行期执行分开 |
| 底层执行模型是什么 | 图运行时 + Pregel 风格引擎，而不是顺手递归调用 |

**思考题**：如果你当前的 Agent 系统只有“问题进入 → 检索资料 → 生成答案 → 返回结果”四步，且没有共享状态聚合、没有分支恢复、没有人工审批，为什么 LangGraph 可能还不是最佳起点？哪些新需求一旦出现，才会让它的建模成本开始值回票价？

> [!note] 参考答案
> 这类系统的复杂度还主要停留在线性流程上，LangGraph 的图建模、schema、compile、state 管理会显得偏重。只有当你开始面对资料不足要回查、多节点共写状态、风险请求要转人工、流程中断后要从 checkpoint 继续、输出前要过多道关卡时，图的收益才会迅速超过心智和样板成本。LangGraph 不是让简单问题更简单，而是让复杂问题不至于失控。
