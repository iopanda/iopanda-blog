# 核心原语与运行时设计

> [总览篇](/iopanda-blog/ai/03-frameworks/01/25/)已经说明 OpenAI Agents SDK 的吸引力不在“再造一个 Agent 类”，而在于它试图把 2026 年现代 Agent 系统高频重复出现的原语一次收口：tools、handoffs、guardrails、sessions、tracing、sandbox、realtime、voice。[1][2] 这一章要深入的问题是：**为什么这些东西会被收进同一个 SDK，它们之间的关系到底是什么？** 从源码 `src/agents/agent.py` 可以直接看到 `AgentBase` 顶层就挂着 tools、MCP servers、handoffs、guardrails、model settings、stream handling 等一整套运行时概念；这不是“接口越来越多”，而是它在把 Agent 定义为一个真正的运行时单元。[3]

**学习目标**：学完本章，你将能够——

1. 说出 OpenAI Agents SDK 为什么把 tools、handoffs、guardrails、sessions、tracing 视为同一层问题；
2. 理解 `AgentBase`、nested agent、tool state、strict schema 这些源码关键词在表达什么；
3. 解释 handoff 和 agent-as-tool 为什么比“多个 Agent 并排摆着”更成熟；
4. 比较它与 [AutoGen](/iopanda-blog/ai/03-frameworks/01/11/)、[CrewAI](/iopanda-blog/ai/03-frameworks/01/18/) 的协作观差异；
5. 为一个多 specialist 的 Agent 系统设计 runtime 结构。

## 1. 概念：OpenAI Agents SDK 在收口“现代 Agent 最常见的胶水层”

一个 2026 年像样的 Agent 应用，往往都会反复遇到这些问题：
- 工具怎么接；
- 工具结果怎么再反馈给模型；
- 多 Agent 怎么委托；
- 哪一层做 guardrail；
- 多轮上下文怎么管理；
- 运行轨迹怎么 trace；
- 某些工作是不是应该进 sandbox；
- 某些交互是不是应该实时/语音化。

OpenAI Agents SDK 的设计判断是：这些不再是“各项目自由拼装”的偶然需求，而是**现代 Agent 系统的共性基础设施**。[2]

所以它做的事不是“让你更快发 prompt”，而是“让你少写一整层运行时胶水”。

## 2. `AgentBase`：源码说明它不是薄包装

在 `src/agents/agent.py` 里，`AgentBase` 顶层就包含：
- `name`
- `handoff_description`
- `tools`
- `mcp_servers`
- `mcp_config`
以及后续与 handoff、tool name reservation、model settings、streaming 等相关的运行时逻辑。[3]

这几个字段非常说明问题：

1. **Agent 有身份**：不是匿名函数；
2. **Agent 有可委托语义**：handoff description 说明它可能成为别人的 specialist；
3. **Agent 有能力面**：tool 与 MCP server 共同定义它能触达的外部世界；
4. **Agent 有运行配置**：并非“同一个模型到处跑”。

换句话说，OpenAI Agents SDK 里的 Agent 从第一天起就被设计成：**可独立运行、可被委托、可接工具、可被观测的执行单元。**

## 3. tools：为什么它把工具当系统边界，而不是功能点

tool 在 Agent 体系里最大的问题从来不是“能不能调用”，而是：
- 输入结构是否严格；
- 调用错误是否可归因；
- 返回结果是否还能继续驱动下一轮推理；
- 有没有副作用；
- 是否该被 guardrail 审查。

OpenAI Agents SDK 之所以成熟，在于它没把 tool 当成一个“随手的 Python 函数”，而是当成运行时的重要边界：
- 有 tool input schema；
- 有 tool state；
- 有 tool guardrail；
- 有 tool as agent 的委托能力。

这说明它真正关心的是：**模型通过工具走出对话框以后，系统边界是否还能站住。**

## 4. handoffs / agents-as-tools：为什么这是更成熟的多 Agent 路线

和 AutoGen 的“角色互相说话”不同，OpenAI Agents SDK 对多 Agent 更强调**受控委托关系**。[2]

这体现在两个概念：
- Agent as tool：把 specialist agent 作为一种能力提供给上层 agent；
- handoff：把控制权交给另一个 agent。

这两种方式的好处是：
1. 协作关系更显式；
2. 专长边界更清楚；
3. 更容易 trace 谁在什么时候接管了任务；
4. 比群聊式协作更适合产品化与治理。

你可以把这看成多 Agent 协作从“会话范式”走向“运行时范式”的一步。

## 5. strict schema：为什么现代 Agent SDK 会越来越强调结构约束

在 `agent.py` 顶部可直接看到 `ensure_strict_json_schema` 之类依赖。[3] 这件事说明一个现实趋势：

- 现代 Agent 应用越来越少只是输出自由文本；
- 越来越多要输出结构化数据、被下游系统消费；
- 所以 schema 不再是 nice-to-have，而是运行时基础设施的一部分。

这和 [结构化输出约束](/iopanda-blog/ai/02-agents/02/05/) 的结论一模一样：输出约束不是礼仪，是系统契约。

## 6. tracing：为什么运行轨迹在这里被当成核心原语

源码目录里 `src/agents/tracing/` 单独是一大片子系统：spans、traces、processors、setup、provider、logger 等。[1] 这足以说明 tracing 在这里不是调试附件，而是正式运行时能力。

其架构含义非常清楚：
- Agent 不是一个黑箱调用；
- Agent run 是可分段、可关联、可处理的事件链；
- 只有把 tracing 做成一等公民，多 agent/handoff/tool/guardrail 才真的可排障。

## 7. 与同类框架相比，它的运行时哲学是什么

| 框架 | 协作/编排的第一语言 | OpenAI Agents SDK 的不同 |
|---|---|---|
| AutoGen | 角色会话 | 它更强调受控委托，而非自由对话 |
| CrewAI | 角色团队 + 业务流程 | 它更强调通用运行时原语，而非业务语义 |
| LangGraph | 状态图 | 它更强调原语组合，而非显式图建模 |
| PydanticAI | 类型契约 + capability | 它更强调统一运行时体验，而非 Python 类型系统先行 |

一句话：OpenAI Agents SDK 的第一性问题不是“状态图怎么画”，也不是“团队角色怎么讲”，而是“现代 Agent 应用最常见的运行时原语如何一次给齐”。

## 8. 动手活动：为课程助教设计 router + specialists 架构

> [!example] 动手活动：输出 `openai-agents-runtime-plan.md`
>
> **目标**：不是画角色团队，而是画运行时委托结构。
>
> **步骤**：
> 1. 设计一个 Router Agent；
> 2. 设计三个 specialists：课程问答、成绩查询、治理规则；
> 3. 决定哪些是 handoff，哪些是 agent-as-tool；
> 4. 给成绩查询 specialist 明确 tool 与 schema；
> 5. 写明 tracing 里最想观察哪几类事件。
>
> **完成标准**：你能清楚说明“谁在什么时候接管任务，为什么不是所有 Agent 平铺同时运行”。

## 9. 边界与排错

- **误区一：有多个 Agent 就等于会多 Agent 设计。** 委托关系不清，系统照样混乱；
- **误区二：tool 只是能力点。** 它其实是系统边界与风险边界；
- **误区三：handoff 和 tool 混为一谈。** 一个是控制权转移，一个是能力调用；
- **误区四：有 tracing 就自动可调。** 你还要先把关键原语和责任边界设计清楚；
- **误区五：统一运行时 = 适合所有复杂状态系统。** 当主矛盾变成显式状态图与恢复时，图式框架仍可能更合适。

## 10. 总结

| 关键问题 | 一句话 |
|---|---|
| 它在解决什么 | 现代 Agent 应用的共性运行时胶水层 |
| `AgentBase` 暴露了什么 | Agent 是身份、能力、委托、观测合一的执行单元 |
| tool 在这里是什么 | 外部世界边界，而不只是功能接口 |
| handoff 的价值 | 让多 Agent 协作从群聊变成受控委托 |
| tracing 的位置 | 正式原语，不是调试附件 |
| 最适合什么 | 想快速获得完整现代 Agent runtime 的团队 |

**思考题**：为什么一个拥有 tools、handoffs、sessions、tracing 的 SDK，仍然不一定自动适合所有复杂 Agent 系统？什么时候“原语齐全”仍然不如“控制流显式”？

> [!note] 参考答案
> 因为原语齐全解决的是“能力拼装问题”，并不天然解决“复杂状态如何建模与恢复”的问题。若系统复杂度主要来自 specialist 分流、工具接入、多轮会话、输入输出校验与 trace，一体化 runtime 会非常高效；但若复杂度主要来自长流程分支、节点级暂停恢复、共享状态聚合与审批链，显式控制流往往比原语齐全更重要。不是原语越多越高级，而是要看你的系统先被哪类复杂度压垮。
