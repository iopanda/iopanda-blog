# 类型系统、依赖注入与输出契约

> 如果说 [OpenAI Agents SDK](/ai/03-frameworks/01/26/) 的第一感觉是“现代 Agent 原语很全”，那么 PydanticAI 给开发者和架构师的第一感觉往往是：**终于有个框架在认真对待 Python 工程契约了。** 官方文档对 Agent 的定义里，和 instructions、tools 并列的不是“魔法能力”，而是 `structured output type`、`dependency type constraint`、`capabilities`；文档甚至明确说 agent 设计成像 FastAPI app 一样可复用。[1][2] 从源码 `pydantic_ai/agent/abstract.py` 看，整套运行接口围绕 `run()`、`run_sync()`、`run_stream()`、`run_stream_events()`、`iter()` 展开，而类型、输出和事件流是这套接口的第一等公民。[3]

**学习目标**：学完本章，你将能够——

1. 解释 PydanticAI 为什么把 output_type、deps_type、capabilities 放在 Agent 定义中心；
2. 说出它为什么特别适合 Python 后端团队，而不只是“另一个 Agent SDK”；
3. 理解 `abstract.py` 中多种 run 接口和 event stream 暗示的工程设计；
4. 比较它与 [OpenAI Agents SDK](/ai/03-frameworks/01/25/) 在统一原语上的差异；
5. 为一个结构化输出为主的 Agent 设计 typed contract。

## 1. 概念：PydanticAI 的第一性问题是“Agent 怎么像系统组件一样被维护”

PydanticAI 官方对 Agent 的说明非常关键：Agent 本质上是一个容器，里面装着 instructions、tools、structured output type、dependency type constraint、model、model settings、capabilities。[2]

这说明它的世界观是：
- Agent 不是单纯文本生成器；
- Agent 也不是只靠 prompt 驱动的脚本；
- Agent 是有输入依赖、输出契约、能力组合边界的组件。

这正是 Python 后端团队熟悉的设计语言：
- 输入类型
- 输出类型
- 依赖注入
- 中间件/能力组合
- 可测试接口

所以 PydanticAI 给人的感觉常常不像“AI 框架”，而像“把 AI 拉回正经后端工程”的框架。

## 2. output_type：为什么结构化输出在这里不是附件，而是主轴

很多 Agent 原型最痛的问题不是“模型不够聪明”，而是：
- 下游以为会得到 JSON，结果拿到半段自然语言；
- 结构对了，但字段类型错了；
- 模型同时返回文本和工具调用，系统不知道该信谁；
- 输出不稳定导致业务代码写满防御逻辑。

PydanticAI 把 output_type 做成正式抽象，本质上是在说：
**Agent 最终要对下游系统负责，而不仅仅是对人类读者负责。**

这种设计非常适合：
- 信息抽取
- 分类打标
- 多步骤中间产物结构化
- 需要下游程序直接消费的结果

这和 [结构化输出约束](/ai/02-agents/02/05/) 的结论完全一致，只不过 PydanticAI 把它前移成框架语言的一部分。

## 3. deps_type：为什么依赖必须显式，而不是靠闭包和全局变量飘

PydanticAI 文档把 dependency type constraint 与 tools、output 并列，非常不寻常。[2]

原因在于真实 Agent 一进工程就会带来这些依赖：
- 数据库客户端
- HTTP 客户端
- 当前用户身份
- 审计 logger
- cache / retriever
- feature flags / settings

如果这些依赖不显式化，Agent 系统就会很快退化成：
- 闭包里偷偷拿对象；
- 全局单例到处飞；
- 测试时很难 mock；
- specialist agent 之间依赖不透明。

`deps_type` 的价值是把这些运行依赖收进类型和运行上下文里，让 Agent 更接近“有明确依赖的应用组件”。

## 4. capabilities：为什么它在这里更像组合式中间件，而不是插件列表

PydanticAI 文档对 capabilities 的描述是可重用 bundles：把 tools、hooks、instructions、model settings 等组合成能力单元。[1][2]

这和普通插件清单的差别很大：
- 插件常常是平铺功能点；
- capability 更像一组相关行为、约束和上下文处理的整体封装。

比如一个 coding agent capability，不只是“多几个工具”，而是可能同时带入：
- 文件访问
- shell 执行
- repo context
- planning
- sub-agents
- context management

这很适合复杂 Agent 的真实复杂度：你加的往往不是一个功能，而是一整簇行为语义。

## 5. `abstract.py`：为什么 run 接口这么多，而且这不是重复设计

在 `agent/abstract.py` 里，PydanticAI 提供了：
- `run()`
- `run_sync()`
- `run_stream()`
- `run_stream_events()`
- `iter()`
等多种运行接口。[3]

它们看似繁琐，实际上反映了一个很成熟的判断：**Agent 不是只有“得到最终答案”这一种消费方式。**

不同接口对应不同工程需求：

| 接口 | 更适合什么 |
|---|---|
| `run()` | 普通异步完成式调用 |
| `run_sync()` | 同步脚本或简单后端场景 |
| `run_stream()` | 用户要边生成边看到结果 |
| `run_stream_events()` | 需要看到工具、流事件、过程轨迹 |
| `iter()` | 需要按节点/步骤级别驱动或检查运行 |

这意味着 PydanticAI 从一开始就承认：
- 有人只要结果；
- 有人要流式体验；
- 有人要事件流；
- 有人要更底层的步骤控制。

这不是 API 冗余，而是**把不同消费层次显式化**。

## 6. 为什么它对开发者特别友好

PydanticAI 最让 Python 工程师安心的地方，往往不是它“功能最多”，而是它和日常工程直觉一致：

1. 类型提示是认真的；
2. 输出校验是正式能力；
3. 依赖显式注入；
4. 工具定义与函数签名紧密绑定；
5. 测试和 mock 路径天然存在；
6. 运行过程并非完全黑箱。

这种风格特别适合那些已经经历过：
- LLM 原型很好看；
- 但上线后全是胶水代码和 if/else 的团队。

## 7. 与同类框架相比，它“稳”的地方在哪里

| 框架 | 首先想稳住什么 | PydanticAI 的不同 |
|---|---|---|
| OpenAI Agents SDK | 现代运行时原语 | PydanticAI 更先稳住类型与依赖契约 |
| LangGraph | 状态图与恢复 | PydanticAI 更先稳住组件接口 |
| CrewAI | 角色与流程业务语义 | PydanticAI 更先稳住后端工程边界 |
| AutoGen | 多 Agent 协作范式 | PydanticAI 更先稳住单体系统质量 |

一句话：PydanticAI 很少先问“系统看起来多聪明”，而更先问“这套代码能不能长期维护”。

## 8. 动手活动：为课程助教定义 typed output 与 deps

> [!example] 动手活动：输出 `pydanticai-contract-plan.md`
>
> **目标**：先把课程助教 Agent 的契约设计清楚，而不是先写 prompt。
>
> **步骤**：
> 1. 定义三类输出：普通问答、成绩查询、升级人工；
> 2. 为每类输出写 schema；
> 3. 定义依赖：当前用户、数据库 client、检索器、审计 logger；
> 4. 说明哪些 capability 是一组整体能力，而不是单个工具；
> 5. 写一句结论：如果输出契约改不了，系统下游会怎么痛。
>
> **完成标准**：你能让另一个后端工程师只看类型和依赖设计，就大致明白这个 Agent 怎样进入系统边界。

## 9. 边界与排错

- **误区一：typed output 就等于语义正确。** 结构正确不代表业务判断正确；
- **误区二：依赖随便放全局，反正能跑。** 短期省事，长期测试与治理都会痛；
- **误区三：capability 什么都包。** 过度抽象会让追踪和定位变难；
- **误区四：把多种 run 接口看成 API 重复。** 它们对应的是不同消费层次；
- **误区五：以为这只是“给 Python 爱好者的框架”。** 实际上它在解决的是长期维护问题。

## 10. 总结

| 关键问题 | 一句话 |
|---|---|
| PydanticAI 首先关心什么 | Agent 能否像一个工程组件那样被维护 |
| output_type 的价值 | 让下游系统能依赖结构化、可验证的结果 |
| deps_type 的价值 | 让运行依赖显式化、可测试、可注入 |
| capability 的价值 | 把一簇相关行为作为能力整体组合 |
| 多 run 接口的价值 | 显式承认结果消费、流式消费、事件消费、步骤消费是不同层次 |

**思考题**：如果你的团队最痛的是“输出老不稳、依赖乱飞、测试难写、业务代码里全是解析兜底”，为什么 PydanticAI 常常比先上多 Agent 协作更合理？什么时候这种“先稳住契约”的路线会开始不够？

> [!note] 参考答案
> 因为这些痛点都发生在系统边界层，而不是协作层：先把输出、依赖、工具和能力组合收紧，才能让系统从演示脚本变成可维护服务。若一开始就放大成多 Agent 协作，只会把本来就不稳定的边界复制到更多角色身上。只有当系统主矛盾从契约与维护性转向复杂控制流、长生命周期恢复或大规模角色协作时，这条路线才可能显得不够，需要进一步引入 graph、durable execution 或更强编排能力。
