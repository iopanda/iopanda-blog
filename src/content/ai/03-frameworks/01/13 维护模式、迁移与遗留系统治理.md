# 维护模式、迁移与遗留系统治理

> [上一章](/ai/03-frameworks/01/12/)讲的是 AutoGen 为什么在多 Agent 协作史上重要；这一章讲更现实也更工程的问题：**重要，不等于今天还应该默认新项目就选它。** 2026 年的官方 README 已经明确写出 caution：AutoGen 进入 maintenance mode，新用户应从 Microsoft Agent Framework 开始；旧用户则应参考迁移指南。[1][4] 对开发者和架构师来说，这不是一句新闻，而是选型与治理上的硬信号：框架的历史价值、生态影响力和“今天适不适合作为新项目主干”必须分开判断。

**学习目标**：学完本章，你将能够——

1. 解释 maintenance mode 对技术选型意味着什么；
2. 区分“教学/研究价值高”与“绿地项目优先级高”这两件事；
3. 为一个存量 AutoGen 系统做保留、局部替换或迁移判断；
4. 说明从 AutoGen 迁出时，真正要迁移的不是 API，而是协作语义与控制流；
5. 用一张体检卡评估遗留多 Agent 系统的治理风险。

## 1. maintenance mode 到底意味着什么

官方 README 的措辞很明确：
- AutoGen 不再接收新特性与增强；
- 社区继续维护；
- 新用户应转向 Microsoft Agent Framework；
- 现有用户可参考迁移指南。[1][4]

这对架构师的含义不是“它明天就不能用”，而是：

1. **长期演进能力变弱**：未来新模式、新协议、新接口的原生支持大概率会放慢；
2. **生态中心迁移**：教程、插件、公司投入、讨论焦点会逐渐流向继任者；
3. **维护责任回到自己**：如果你的系统高度绑定框架内部行为，长期成本将越来越多由你自己承担。

所以 maintenance mode 不是情绪标签，而是**未来维护成本与生态风险的信号**。

## 2. 为什么它仍然值得学，但不该被神化

AutoGen 仍然值得认真学，原因至少有三条：

1. 它定义了多 Agent 协作的一代范式；
2. 市面上已经存在大量存量项目、样例与思维模式；
3. 你很可能不是只做绿地项目，还会接手旧系统、评估旧设计。

但不该被神化，也有三条原因：

1. 官方维护状态已经改变；
2. 很多团队现在更需要的是显式状态恢复、统一原语、类型契约，而不只是“多角色会话”；
3. 后继框架往往在吸收它的经验后，对治理和工程边界给出更明确答案。

一句话：**学 AutoGen，是为了理解一个时代的问题意识；选 AutoGen，则要服从 2026 年的现实约束。**

## 3. 旧系统真正依赖的，往往不是 API，而是“隐式协作协议”

迁移 AutoGen 时，最容易犯的错误是把问题理解成“把类名替换一下”。实际上真正难迁的是这些东西：

- 角色之间的职责约定；
- 谁先说、谁后说；
- 谁可以结束任务；
- 某类消息意味着继续，还是意味着转人工；
- 哪些协作规则只存在于 prompt 或会话习惯里。

这些内容常常没有写成显式流程图，却真实决定了系统行为。

所以一个 AutoGen 系统的迁移，本质上是在做**隐式协作协议显式化**。如果你做不到这一点，换任何新框架都只是在搬运旧混乱。

## 4. 保留 / 局部替换 / 全量迁移：怎么判断

| 场景 | 更合理的选择 | 理由 |
|---|---|---|
| 系统稳定、需求冻结、团队熟悉现状 | 保留 | 迁移风险可能大于收益 |
| 系统仍在发展、需要新能力和长期支持 | 局部替换或迁移 | maintenance mode 会持续累积机会成本 |
| 控制流、恢复、人审越来越复杂 | 倾向迁往显式编排框架 | 主矛盾已从协作转向治理 |
| 团队想保留多角色业务语义 | 可迁往 [CrewAI](/ai/03-frameworks/01/18/) 一类 | 保留协作直觉，但提升流程语义 |
| 团队想统一现代运行时原语 | 可迁往 [OpenAI Agents SDK](/ai/03-frameworks/01/25/) | 以 tools / handoffs / guardrails / sessions 重建边界 |
| 团队想把系统拉回显式状态与恢复 | 可迁往 [LangGraph](/ai/03-frameworks/01/03/) | 从会话式协作转向状态图治理 |

这张表背后的核心不是“迁到谁”，而是“系统今天主要卡在哪里”。

## 5. AutoGen 遗留系统的五个高风险区

### 5.1 角色过多，职责不清

如果你发现：
- 研究员也在调用高风险工具；
- 审稿代理也能直接产出最终动作；
- 用户代理和系统代理边界不清；

那么问题不在 AutoGen 本身，而在协作建模失控。

### 5.2 会话即控制流

如果真正决定流程的是“看起来谁先回复了什么”，而不是显式规则，那么你已经把控制流埋进对话了。这类系统最难测，也最难回放。

### 5.3 成本不透明

多 Agent 协作最容易造成 token 成本膨胀：
- 多个角色各带自己的系统提示；
- 相同上下文被多次复制；
- 反复互评拖长回合数。

### 5.4 恢复困难

一旦任务中断，很难回答：
- 哪个角色已经完成；
- 哪些结论可信；
- 哪些副作用已经发生；
- 是否可以从半程继续。

### 5.5 治理边界缺失

高风险动作、人审、权限、审计如果只是“约定如此”，而不是代码与流程语义的一部分，系统就会随着复杂度上升而失控。

## 6. 一个更现实的迁移观：迁的是“系统复杂度管理方式”

迁移方向不应按流行度选，而应按复杂度类型选：

- 若你痛的是**状态与恢复**，迁向图/编排框架更自然；
- 若你痛的是**角色和业务流程表达**，迁向 CrewAI 一类更自然；
- 若你痛的是**运行时原语拼装成本**，迁向 OpenAI Agents SDK 更自然；
- 若你痛的是**类型契约、依赖与测试**，迁向 PydanticAI 更自然。

这和 [06 Agent Framework 选型矩阵](/ai/03-frameworks/01/02/) 的方法是一致的：别问“从 AutoGen 迁到谁最流行”，而要问“我的系统最先死在哪”。

## 7. 动手活动：给一个 AutoGen 系统写迁移体检卡

> [!example] 动手活动：输出 `autogen-migration-assessment.md`
>
> **目标**：不是立刻重构，而是先让团队对现状达成同一认知。
>
> **步骤**：
> 1. 列出系统中所有角色及其工具权限；
> 2. 画出真实消息流，而不是理想中的消息流；
> 3. 找出三个“只存在于 prompt/习惯里”的隐式规则；
> 4. 记录一次中断后恢复流程，写出它为什么难；
> 5. 给出结论：
>    - 保留
>    - 局部替换
>    - 分阶段迁移
>    - 全量迁移
>
> **完成标准**：团队能清楚回答“我们现在在维护什么复杂度，它是否仍适合留在 AutoGen 上”。

## 8. 边界与排错

- **误区一：maintenance mode = 立刻重写。** 不对，稳定存量系统仍可能继续运行；
- **误区二：历史贡献大 = 今天还应默认新项目首选。** 这两件事必须分开；
- **误区三：迁移就是替换 API。** 真正难的是把隐式协作契约显式化；
- **误区四：不迁就等于稳。** 若需求和复杂度持续增长，拖延迁移只是把债滚大；
- **误区五：迁移方向只看热度。** 应看你系统的首要矛盾是什么。

## 9. 总结

| 关键问题 | 一句话 |
|---|---|
| maintenance mode 意味着什么 | 长期演进能力与生态中心转移，不是立刻失效 |
| 为什么还要学 AutoGen | 它定义了多 Agent 协作范式，且有大量存量系统 |
| 迁移真正难在哪 | 难在隐式协作协议，而不是类名替换 |
| 何时保留 | 系统稳定、需求冻结、团队已掌握 |
| 何时迁移 | 主矛盾开始变成治理、恢复、长期支持或新能力接入 |
| 迁向谁 | 取决于系统最先死在状态、协作、运行时原语，还是工程契约 |

**思考题**：如果一个 AutoGen 系统现在“还能跑”，但团队已经越来越说不清谁有权限、为什么某个任务会在第 5 轮结束、失败后怎么恢复，这种情况下“不动它”真的是保守策略吗？为什么“暂时还能跑”不等于“技术风险可接受”？

> [!note] 参考答案
> 这类系统的风险并不主要体现在“今天有没有报错”，而体现在复杂度已经超出团队的解释能力：权限边界不清、停止条件隐式、恢复路径模糊，意味着一旦需求变化、团队成员流动或事故发生，排查和修改成本会急剧上升。因此“不动它”未必是保守，可能只是把系统性风险延后。真正保守的策略是先把隐式规则显式化，再决定保留还是迁移。
