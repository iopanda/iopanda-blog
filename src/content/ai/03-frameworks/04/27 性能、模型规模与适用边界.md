# 性能、模型规模与适用边界

> llama.cpp 经常被误解成“只适合小模型本地玩玩”，但 README、build 文档、quantize 文档都说明它其实覆盖了非常广的设备与模型空间。[9][11][13] 不过它的边界也同样清楚：它的强项是 portability、本地部署、轻量服务面，而不是默认去做超大规模数据中心平台。

**学习目标**：学完本章，你将能够——
1. 识别 llama.cpp 的真实性能来源与限制；
2. 理解为什么量化、本地后端、设备差异会强烈影响体验；
3. 判断它适合什么模型规模、不适合什么系统形态；
4. 理解为什么 portability 是优势，也是一种取舍；
5. 为系统写一张 local-inference-boundary card。

## 1. 性能不是绝对快，而是“在更多地方可接受地快”

llama.cpp 的价值不在于每项 benchmark 都赢，而在于：
- 在 CPU 上也能跑；
- 在 Mac Metal 上能很好地跑；
- 在多种 GPU 后端上都能跑；
- 在资源有限设备上仍有量化主路径。[9][13]

这是“可达性能”，不是“单一硬件极限性能”。

## 2. 模型规模边界来自设备现实

quantize README 直接列出不同量化下的体积变化。[11]
这说明模型能否落地，不是抽象问题，而是：
- RAM 够不够；
- VRAM 够不够；
- 是否能接受更激进量化；
- 是否要 hybrid inference。

## 3. 为什么 portability 是优势也是取舍

支持很多后端，意味着：
- 更多设备能跑；
- 更多产品能交付；
但也意味着：
- 不一定在某一高端硬件上做到最深专用优化；
- 大规模平台治理能力不一定是第一优先级。

## 4. 工程边界

如果你的系统开始出现：
- 高并发公网服务；
- 多租户治理；
- 多模型大型平台运营；
- 极端吞吐/时延 SLA；
那就可能该转向 vLLM / Triton / TensorRT-LLM 等路线。

## 5. 动手活动

> [!example] 输出 `llamacpp-boundary-card.md`
>
> 列你的目标模型大小、设备内存、是否离线、是否公网暴露、是否高并发。写一句结论：你的系统最需要的是 portability，还是吞吐平台化。

## 6. 总结

| 关键问题 | 一句话 |
|---|---|
| llama.cpp 的性能主语是什么 | 在广泛设备上可接受地快 |
| 最大限制是什么 | 设备资源和系统形态决定上限 |
| portability 的代价是什么 | 不以单一高端数据中心优化为唯一目标 |
| 正确使用方式 | 在本地/边缘/轻量服务面场景用它的长板 |
